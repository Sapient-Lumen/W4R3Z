# Stable release evidence

Status: stable/no-concern gate format implemented; sync receipt classes are
hash-bound and shape-checked, and the repository now carries one accepted
local stable dossier for the current evidence scope. Stable still fails closed
by default unless the operator supplies that manifest explicitly. Updated
2026-09-27.

`iotox ship-check all stable` still fails closed without evidence. Stable
graduation now has an explicit dossier format:

```sh
tools/iotox-repo.sh stable-evidence-plan
iotox evidence dossier-plan \
  --dataset /dataset \
  --out /proof/stable \
  --terminal-root ~/.local/state/iotox \
  --peer alias:desktop
iotox evidence collect sync /dataset read-write 30 --out stable-sync-evidence ...
iotox evidence manifest stable-sync-evidence --out stable-evidence.manifest
iotox evidence dossier-status /proof/stable \
  --scope all \
  --manifest /proof/stable/stable-evidence.manifest
iotox ship-check all stable --evidence-manifest stable-evidence.manifest
tools/iotox-repo.sh release-check stable \
  --iotox /path/to/iotox \
  --evidence-manifest stable-evidence.manifest
```

`evidence dossier-plan` is the binary-native porch for building the dossier:
it prints the sync trust/backup/runbook/retention commands, precious-data
status and signoff commands, Ratox daily/service/soak commands, sync and
terminal evidence collectors, manifest generation, dossier status, and final
ship-check. It is plan-only. `evidence dossier-status` is the status side: it
checks each expected receipt file with the same shape rules as the manifest
builder, verifies the manifest SHA bindings separately, and stays blocked if
anything is missing, placeholder, stale, or hash-mismatched.

This dossier is a local accepted evidence bundle, not a reusable universal
claim. Do not reuse it across a different binary, host class, route class,
dataset class, security review, or operator decision without rechecking scope.

The manifest is a bounded `key=value` file. The first required line is:

```text
schema=iotox.stable-evidence.v1
```

Every stable gate then needs three lines:

```text
GATE=accepted
GATE.receipt-path=relative/or/absolute/path
GATE.receipt-sha256=<64 lowercase hex>
```

The path points at the content-free receipt or review record that supports the
claim. Relative paths resolve from the manifest directory. The binary opens each
receipt as one bounded no-follow regular file and verifies that its SHA-256
matches `GATE.receipt-sha256`.

ADR 0398 adds native sync receipt shape checks on top of the hash check. These
checks are deliberately small release-brake sanity checks: they reject obvious
placeholder prose, but they do not replace the dedicated Python verifiers or
operator review. The repository tools and human release process must still
verify that the referenced records are real, reviewed, retained, and in scope.

## Required sync gates

```text
sync.local-preflight
sync.storage-readiness
sync.long-soak
sync.recovery-custody
sync.restore-drill
sync.recovery-runbook
```

These correspond to the local sync doctor, repository storage-readiness report,
accepted long-soak receipt, accepted versioned recovery-custody receipt,
restore drill, and operator recovery runbook. The sync
long-soak receipt should cite the accepted same-host 24-hour three-writer
Sandwurm proof or a stronger replacement.

The current accepted repository sync long-soak proof is
`.sandwurm/exports/three-writer/run.2nPKtCoX`. Generate the native stable-gate
receipt from that proof with:

```sh
tools/iotox-repo.sh current-sync-long-soak-receipt --out /PROOF/long-soak.json
```

That deterministic verifier receipt has SHA-256
`6e88a2efcf33b268ff82cf0fdaaa99e8c45be612f50c9e77dc0714ab2d6759a0` and is
the file to pass as `--long-soak`. The raw guest receipt remains inside the
compact proof at
`live/workspace-export/guest-receipts/iotox/sync-three-writer.json`, with
SHA-256 `687b4ace878465ba733399a722d009a8d99afc616fe244ad7f2721443263356b`,
for lab audit and export verification.

The native stable gate now expects these sync receipt shapes:

| Gate | Required receipt shape |
| --- | --- |
| `sync.local-preflight` | `iotox-sync-doctor-v3` or `iotox-sync-doctor-v4` with `decision=ready`. |
| `sync.storage-readiness` | JSON `schema=iotox.storage-readiness.v1`, `status=ready`, `ready_for_precious_data=true`, `contains_secrets=false`, and accepted local storage science. |
| `sync.long-soak` | JSON `schema=iotox.sync-three-writer-sandwurm-verification.v1`, `status=passed`, `contains_secrets=false`, `soak_campaign=true`, nonzero `soak_cycles`, and at least 86,400,000 `soak_elapsed_ms`. |
| `sync.recovery-custody` | JSON `schema=iotox.sync-backup-custody.v1`, `status=passed`, `contains_secrets=false`, supported `custody_class`, immutable/versioned generation, verified repeatable restore, matching recovery comparison, distinct-device metadata, and nonclaims for disk loss, host compromise, filesystem-wide corruption, media certification, and content custody. Legacy manifests named `sync.independent-backup` are accepted only as a compatibility alias. |
| `sync.restore-drill` | JSON `schema=iotox.sync-retained-recovery-drill.v1`, `status=passed`, `contains_secrets=false`, `decision=match`, and satisfied local provenance/device requirements. |
| `sync.recovery-runbook` | Line record with `schema=iotox.sync-recovery-runbook-review.v1`, `status=reviewed`, `content-free=1`, `operator-runbook=present`, a valid `reviewer-label`, `dataset-selector-sha256`, `runbook-sha256`, nonzero `runbook-bytes`, `accepted-reviewed-runbook=1`, `not-content-custody=1`, valid access/interval fields, and the five required stop/restore/verify/retire/rehearse coverage flags. |

If one of those files is merely a note such as “accepted,” stable ship-check
fails with a gate-specific blocker such as `sync-storage-readiness-invalid` or
`sync-recovery-runbook-invalid`. The native way to create the runbook receipt
is:

```sh
iotox sync runbook receipt /dataset read-write 30 \
  --runbook /proof/recovery-runbook.md \
  --reviewer owner --accept-reviewed-runbook \
  --out /proof/recovery-runbook.receipt
```

`iotox evidence collect sync` is the native sync-side manifest porch. It runs a
fresh local preflight receipt, copies only receipt files that pass the same
native shape checks listed above, and writes `stable-evidence.manifest` when
all six sync gates are present. It can also carry the reviewed retention policy
used by `iotox sync precious-status`; retention is required for local
operator-signable precious status even though the stable manifest format keeps
the historical six sync release gates.

After `precious-status` is green, `iotox sync precious-signoff PATH ...` can
write a separate local operator receipt. That receipt is intentionally outside
the stable manifest: it binds the manifest and receipt hashes plus a hashed
dataset selector, records explicit operator responsibility, and repeats
`repo-certified=0`. It is the owner’s “I accept this evidence for this
dataset” artifact, not a release-wide certification.

## Required Ratox gates

```text
terminal.daily-control
terminal.profile-freshness
terminal.service-supervision
terminal.reconnect-continuity
terminal.cgroup-delegation
terminal.route-loss
terminal.long-soak
terminal.tor-route-loss
terminal.i2p-route-loss
terminal.sudo-policy
terminal.security-review
terminal.activation-decision
```

These correspond to a host/route/operator daily-driver decision: profiles are
fresh, service supervision is known, reconnect and route-loss behavior are
qualified, delegated cgroup behavior is accepted for the host, long soak has
run, Tor/I2P route-loss claims are scoped, sudo/PAM policy has been reviewed,
security review has been completed, and the owner explicitly accepted the
activation. `terminal.long-soak` is not an opaque label: stable ship-check
verifies that the receipt uses `iotox.terminal-long-soak-receipt.v1`, is
accepted, covers at least 86,400 observed seconds, has at least two samples,
keeps maximum sample gaps at or below 900 seconds, and records zero failures.
The other terminal gates are no longer free-form placeholder prose when they
are collected natively. Most of them use
`iotox.terminal-stable-evidence.v1` receipts with a gate name, safe
operator-label, hashed root/peer labels, `content-free=1`, and
`repo-certified=0`. `terminal.service-supervision` has a stronger preferred
path: `iotox service status-receipt` writes
`iotox.service-reality.v1`, which is accepted only when the operator records
active service-manager state, enabled/static/managed activation, reviewed
logs, passing health, and passing upgrade checks. Legacy
`iotox.terminal-stable-evidence.v1` service labels are still accepted for old
dossiers, but new dossiers should use `--service-reality`.

The recommended long-soak entry is native and elapsed:

```sh
iotox terminal soak-run \
  --root ~/.local/state/iotox \
  --peer alias:desktop \
  --route native \
  --seconds 86400 \
  --sample-every 300 \
  --out /proof/terminal-24h.receipt

iotox terminal soak-verify /proof/terminal-24h.receipt
```

`terminal soak-run` writes the same
`iotox.terminal-long-soak-receipt.v1` schema as `terminal soak-receipt`. If it
is interrupted, it writes a rejected receipt so the partial attempt is retained
without pretending it passed.

The native terminal collection porch is:

```sh
iotox evidence collect terminal \
  --root ~/.local/state/iotox \
  --peer alias:desktop \
  --out /proof/stable \
  --service-reality /proof/terminal-service-supervision.receipt \
  --long-soak /proof/terminal-24h.receipt \
  --evidence daily-control=local.gate \
  --evidence profile-freshness=profile.check \
  --evidence reconnect-continuity=cli.reconnect \
  --evidence cgroup-delegation=nixos.cgroup \
  --evidence route-loss=tox.loss \
  --evidence tor-route-loss=tor.operator \
  --evidence i2p-route-loss=i2p.fronts \
  --evidence sudo-policy=host.sudo \
  --evidence security-review=owner.review \
  --evidence activation-decision=owner.decree
```

Create the service reality receipt after the service has actually been
enabled, started, logged, health-checked, and upgrade-checked:

```sh
iotox service status-plan \
  --target all \
  --root ~/.local/state/iotox \
  --manager systemd-user \
  --unit-prefix iotox-self \
  --binary /usr/bin/iotox

iotox service status-receipt \
  --target all \
  --root ~/.local/state/iotox \
  --manager systemd-user \
  --unit-prefix iotox-self \
  --binary /usr/bin/iotox \
  --service-manager-state active \
  --enabled-state enabled \
  --log-state reviewed \
  --health-state passed \
  --upgrade-state passed \
  --accept-operator-responsibility \
  --out /proof/terminal-service-supervision.receipt
```

If `/proof/stable` already contains complete sync receipts, the terminal
collector writes a combined `stable-evidence.manifest` suitable for
`iotox ship-check all stable --evidence-manifest /proof/stable/stable-evidence.manifest`.
If it contains only terminal receipts, use `iotox ship-check terminal stable`
with the same manifest.

## Boundaries

A complete manifest can make `ship-check stable` pass for the selected scope.
It does not make missing evidence real. The release owner must keep the receipt
set with the release notes or support bundle and must not reuse a manifest
across a different binary, host class, route class, dataset class, or security
review scope without rechecking it.

The current repository can pass stable release checks when the accepted local
manifest above is supplied. Without an explicit evidence manifest, stable still
fails closed by design.
