# Standards-control mapping and release checklist

The archive now has enough schemas that a release can look official while hiding an empty control map. rev0171 therefore adds a control-mapping and release-readiness layer.

## Control-map rule

A standards map is not a bibliography. Each external requirement or standard claim must be paired with:

- personhood-specific control;
- evidence object;
- owner;
- review cadence;
- exception process;
- subject/representative access rule;
- public summary rule;
- fixture or drill;
- reliance effect if failed.

A row that merely says "aligned with NIST" or "consistent with ISO" must be rejected.

## External frameworks worth mapping

- **EU AI Act.** Risk management, recordkeeping, transparency, human oversight, post-market monitoring, incident reporting, GPAI transparency/safety/copyright obligations, and market-surveillance interfaces.
- **ISO/IEC 42001.** Organizational AI management system, roles, lifecycle governance, performance evaluation, monitoring, audit, and continual improvement.
- **NIST AI RMF / CSF / Privacy Framework.** Govern, map, measure, manage, cybersecurity governance, privacy-risk management, and incident-response integration.
- **DORA / Data Act.** Operational resilience, third-party ICT risk, incident handling, switching, portability, and exit.
- **OWASP Agentic Top 10 / agent identity standards.** Tool misuse, goal hijack, identity/privilege abuse, rogue agents, authorization, delegation, and non-human identity governance.
- **OpenTelemetry / provenance / credential standards.** Common telemetry names, evidence traceability, signed statements, and verifiable claims.

These frameworks are not substitutes for personhood rights. They are carriers. A mapped AI Act technical file or ISO management-system control can host a personhood annex, but it does not itself decide recognition, continuity, welfare, or remedy. ## Release-readiness checklist

A persistent or frontier agent deployment should not pass release readiness unless the checklist answers yes, no, or exception-with-effect for at least:

1. personhood-impact assessment filed;
2. moral-status uncertainty bridge considered;
3. continuity topology assigned;
4. packet chain complete;
5. subject/representative access path named;
6. safety case carries outward-risk and subject-risk ledgers;
7. incident response includes subject-harm disclosure;
8. legal hold and data room named;
9. compute host undertaking attached;
10. continuity escrow tested;
11. host switching test class assigned;
12. dispute-finance and public-backstop path named;
13. monitor cadence and roster-capture metrics set;
14. open-weight aftercare plan, if relevant;
15. sealed-annex and special-advocate path tested;
16. dashboard small-cell suppression configured;
17. negative fixture suite passed or reliance effect entered;
18. live-safe weekend drill completed;
19. standards-control map attached;
20. appeal, invalidation, and reopening route public.

## Failure effects

| Checklist defect | Minimum reliance effect |
|---|---|
| no PIA-P or packet chain | block release |
| no continuity or escrow answer | stay deprecation / transfer |
| no subject-risk ledger | downgrade safety reliance |
| no host switching test | block host-exit reliance |
| no finance/backstop route | block final-end and deprecation reliance |
| no monitor cadence | conditional release only |
| no fixture run | no verifier-grade reliance |
| no dashboard privacy review | suppress public metrics until cured |
| no appeal route | reject live-effect decision |

## Why this matters

The archive's long-term problem is not that future actors will ignore governance vocabulary. It is that they will say the vocabulary while omitting the personhood-specific control. The standards-control map forces every borrowed framework to name what it actually carries and what happens if it fails.
