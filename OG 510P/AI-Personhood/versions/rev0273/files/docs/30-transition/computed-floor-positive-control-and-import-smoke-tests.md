# Computed floor positive control and import smoke tests

## Purpose

rev0203 made the live receipt floor generated instead of hand-edited. That solved one overclaim path, but it introduced a quieter failure mode: the computation engine could become a permanent zero machine. A permanent zero machine is safe against overclaim but useless when the first genuine non-host response arrives.

rev0204 adds quarantined positive controls. They prove that the engine can recognize a strict live-counterparty import inside a test harness, can keep a single valid class class-local, can satisfy cross-critical quorum only when every required class is present, and can still exclude an otherwise eligible gate when a challenge or rollback applies.

## Current rule

**Positive control is not archive receipt.**

A control case may exercise the import algorithm, but it has `archive_effect=none-control-only`. Control gates are embedded inside the control-case object. They must not be copied into `examples/actual-receipt-import-gate*.json`, must not change `examples/live-receipt-floor-computed-snapshot-rev0204.json`, and must not increase `independent_receipts_present` in the live drill packet.

## Required control branches

The control harness must exercise three branches before the release can claim the computed floor is operational:

1. **Class-local positive branch.** One strict result-return import should compute one eligible class-local import in control mode. It must leave cross-critical quorum false and the archive floor unchanged.
2. **Full-vector positive branch.** A synthetic vector with all required receipt classes should satisfy quorum inside the control harness. This proves the engine is not hardcoded to reject every import.
3. **Challenge exclusion branch.** An otherwise eligible import gate with an upheld challenge or rollback must be excluded, and the computed floor must return to zero.

## Archive/live separation

The archive source of truth remains `examples/live-receipt-floor-computed-snapshot-rev0204.json`, generated by `tools/compute_live_receipt_floor.py` from archive examples and challenge records. The control case is a test input only. It may demonstrate expected behavior, but it cannot satisfy live quorum, WRSR closure, result-return completion, representative contact, or any missing receipt class.

The next actual artifact must still pass:

`custody -> envelope -> response -> intake -> import gate -> challenge/rollback if contested -> class-local replay -> computed-floor snapshot -> quorum recomputation`.

## Failure modes blocked in rev0204

- A positive-control gate leaks into the archive floor.
- The engine ignores a strict eligible control import and remains an accidental always-zero calculator.
- A single class-local control import is counted as cross-critical quorum.
- A synthetic full-vector control is treated as ordinary archive reliance.
- A challenged control import survives rollback because the computation path forgot challenge exclusions.

## Operational consequence

The archive still has zero live external receipts. rev0204 does not collect a counterparty response. It makes the next counterparty response safer to process because the computation engine is now tested on both zero and positive branches.
