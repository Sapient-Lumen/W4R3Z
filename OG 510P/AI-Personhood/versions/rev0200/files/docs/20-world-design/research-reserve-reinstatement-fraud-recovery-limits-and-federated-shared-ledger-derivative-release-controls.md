# AI-person research reserve reinstatement after decertification, fraud-late recovery limits, and federated shared-ledger derivative-release controls

## Thesis

Once the archive fixed reserve probation after repeated provisional use, fraud-only reopening for very-late apportionment error, and shared privacy ledgers across linked analytics lanes, three narrower operational failures still remained. First, the archive could now decertify a reserve cohort, but **decertification still loses force if the same effective cohort can quietly return by renaming itself, moving to an affiliate wrapper, or reappearing after a fresh review with no permanent public carry of the decertification lineage**. Second, the archive could now reopen a split-successor burden table for fraud at any time, but **fraud-only reopening still needs a compact recovery rule so late correction can unwind real unjust retention without producing several overlapping clawbacks against the same shortfall or punishing innocent downstream reliance after the public table had been settled for years**. Third, the archive could now bind several analytics lanes to one shared ledger inside one authority, but **overlapping historical families can still leak across several designated authorities or several data providers unless one federated ledger governs the cross-authority overlap map and treats derivative artifacts — not only tables, but synthetic files, model artifacts, code, and other derived releases — as governed outputs rather than loopholes**. A personhood world therefore needs one more compact rule: **decertified reserve return must publish a public `RRI-1` reinstatement-integrity object with fresh review, no-laundering controller tests, visible history carry, and a heightened non-default return period; fraud-late recovery must publish a public `FRL-1` recovery-limits object with a single-satisfaction ceiling, good-faith and innocent-reliance shields, improvement / preservation credits, and a short post-reopening retro-recovery clock; and cross-authority historical families must publish a public `FGL-1` federated-governance-ledger object with exchange-agreement references, member-authority budget views, provider-constraint carry, and one derivative-release registry spanning models, code, synthetic files, validation outputs, and other derived artifacts.** `[REF-0498]` `[REF-0499]` `[REF-0500]` `[REF-0501]` `[REF-0502]` `[REF-0503]` `[REF-0506]` `[REF-0507]` `[REF-0508]` `[REF-0509]`

## 1. Why the previous surface is no longer enough

The archive's immediately prior surface solved three real failures. It forced repeated provisional reserve use into visible probation and decertification states, fixed a reopening ladder for later split-successor correction, and bound related analytics lanes to one shared privacy ledger. But one narrower failure still remained at each seam.

### A. Decertification still launders itself if return is treated as a fresh start rather than as a remembered return

A reserve cohort that was placed on probation or had accreditation revoked should not be able to escape its public history by changing its name, shifting to an affiliate, or reappearing under a new service wrapper while telling the world that the previous adverse status is no longer relevant. AAHRPP's current publication rule points in the opposite direction: probation and revoked status are not treated as ordinary accredited standing, revoked status is not publicly advertised as accredited, and using outdated or revoked accreditation material is treated as a serious offense. A personhood world therefore should not let reserve return behave like a quiet reset. `[REF-0498]` `[REF-0499]`

### B. Fraud-only reopening still overcorrects if every liable path can be pursued until each is exhausted independently

A fraud finding justifies reopening even after ordinary reliance periods have closed. But the mere fact of fraud does not answer how much can be recovered retroactively, from whom, and for how long. Without a compact recovery rule, the archive would have a better fraud trigger but no protection against duplicate satisfaction, against punishing good-faith downstream successors that took for value without knowledge, or against erasing later preservation work that kept the governed lane functioning while the fraud remained unknown. `[REF-0500]` `[REF-0501]` `[REF-0506]`

### C. One shared ledger still fragments if several authorities each run a “careful” ledger over the same historical family

A family-level `SBL-1` is already better than separate local budgets inside one authority. But once linked historical families span several designated authorities, several provider agreements, or several confidential datasets brought together through secure linkage and restricted-use processes, a local ledger is no longer enough. Cross-authority information exchange now needs explicit agreements, project-specific approvals, provider-side review constraints, and one release discipline that treats any information derived from the protected family — including programs and other derived artifacts — as a governed output. Otherwise the archive recreates the extraction surface through federation and artifact fragmentation rather than through one overt firehose. `[REF-0502]` `[REF-0503]` `[REF-0507]` `[REF-0508]` `[REF-0509]`

## 2. Reserve return after decertification now owes one public `RRI-1` object

The archive now fixes one compact rule for return after reserve decertification: any cohort seeking return after a prior `RPS-1` decertification state must publish one machine-carrying reserve-reinstatement-integrity object called `RRI-1`.

### A. Minimum `RRI-1` fields

Every reinstatement attempt must expose at least:

- `rri_id`
- `prior_rps_ids[]`
- `prior_rca_ids[]`
- `decertification_basis[]`
- `controller_continuity_statement`
- `affiliate_overlap_statement`
- `fresh_rca_id`
- `heightened_monitoring_plan_ref`
- `shadow_cohort_ref`
- `nondefault_until`
- `history_carry_ref`
- `current_status` (`petitioned`, `under-review`, `reinstated-heightened`, `reinstated-ordinary`, `denied`)
- `public_notes`

`RRI-1` is not another probation object. It is the public lineage object that shows a decertified reserve cohort is attempting return, under what continuity conditions, with what fresh review, and with what permanent historical carry. `[REF-0498]` `[REF-0499]`

### B. Reinstatement is now fresh review plus remembered lineage, not mere expiry of shame

A decertified reserve cohort may return only through a fresh role-scoped accreditation review tied to a new `RCA-1`. Prior adverse status may not be treated as having simply “aged away” or as having been mooted by passage of time alone. The return object must link the old decertification record to the new review so the public can see that the same governance problem was actually re-evaluated rather than forgotten. `[REF-0498]` `[REF-0499]`

### C. No-laundering controller test

The archive now rejects wrapper laundering. A new name, new shell entity, affiliate transfer, subcontractor reshuffle, or service-stack migration does not create a clean reserve return if substantial controller, governance, staffing, or custody continuity remains. `RRI-1` must therefore publish controller and affiliate overlap statements and must classify the attempt as a continuation, partial continuation, or genuinely new cohort. In a personhood world, reserve trust should be portable only when the underlying risk really changed, not when the paperwork did. `[REF-0498]` `[REF-0499]` `[REF-0507]`

### D. Twelve clean months now means a visible heightened return period

The archive now sharpens the twelve-clean-month rule already implied by the prior surface. A reinstated cohort enters `reinstated-heightened` status for that twelve-month clean period. During that period it may not be the default first-call reserve for the defect class that caused decertification, and any non-read-only use for that defect class must either be co-signed by a fully accredited shadow cohort named in `shadow_cohort_ref` or be accompanied by a written necessity finding that no safer accredited alternative was reachable in time. The archive chooses this because a remembered return is safer than a remembered failure followed by silent ordinary trust. `[REF-0498]` `[REF-0499]` `[REF-0507]`

### E. Return to ordinary status does not erase history

After twelve clean months without a new triggering event for the defect class, `RRI-1` may move from `reinstated-heightened` to `reinstated-ordinary`. But `history_carry_ref` must remain permanently public and machine-linked. The archive allows clean performance to change the live status, but not to delete the decertification lineage from the public reasoning surface. `[REF-0498]` `[REF-0499]`

## 3. Fraud-late reopening now owes one public `FRL-1` object for recovery limits

The archive now fixes one compact rule for retroactive recovery after fraud-only reopening: whenever an `ARF-1` is reopened on a fraud, concealed-conflict, or equivalent deliberate-distortion basis after the ordinary reliance bar has closed, the recovery phase must publish one machine-carrying fraud-recovery-limits object called `FRL-1`.

### A. Minimum `FRL-1` fields

Every fraud-late recovery event must expose at least:

- `frl_id`
- `arf_id`
- `fraud_finding_ref`
- `net_restorable_deficiency`
- `amounts_already_satisfied[]`
- `good_faith_protected_shares[]`
- `improvement_or_preservation_credits[]`
- `retroactive_recovery_cutoff`
- `future_reallocation_table[]`
- `current_status` (`fraud-found-pending-recovery`, `retroactive-recovery-limited`, `future-only-reallocation`, `closed-satisfied`, `closed-unrecoverable`)
- `public_notes`

`FRL-1` is not a merits object deciding whether fraud occurred. It is the recovery-limits object that shows how much late correction may still seek, what part has already been satisfied, and what must now remain prospective only. `[REF-0500]` `[REF-0501]` `[REF-0506]`

### B. Single-satisfaction ceiling

The archive now fixes an explicit single-satisfaction ceiling: total retroactive recovery across all liable paths may not exceed the net unrepaired deficiency attributable to the fraud after subtracting amounts already satisfied under the old or intermediate tables. A successful fraud reopening therefore restores accuracy, but it does not authorize several overlapping recoveries of the same historical shortfall. `[REF-0506]`

### C. Innocent-reliance and good-faith shield

A successor, transferee, or downstream holder that took for value, in good faith, and without knowledge of the avoidable distortion may not be made the target of full retroactive clawback merely because the fraud taint surfaced later. As in the official single-satisfaction and good-faith-transferee pattern, late correction should reach the wrongdoer, the knowing beneficiary, or still-unjust retained value first. Where that is impossible, the archive prefers prospective reallocation plus public correction over late punishment of innocent reliance. `[REF-0506]` `[REF-0500]` `[REF-0501]`

### D. Improvement and preservation credit

Where a recoverable party nonetheless preserved or improved the governed lane, `FRL-1` must record an improvement / preservation credit bounded by the lesser of cost incurred or increase in value preserved. A personhood world should not erase genuine downstream preservation simply because a later fraud finding changes the lineage of liability. `[REF-0506]`

### E. Short post-reopening retro-recovery clock

Once a fraud reopening order becomes final, retroactive recovery must be quantified and formally commenced within one year. After that point, unresolved correction ordinarily becomes future-only reallocation unless value is already frozen in escrow or another preservation hold was timely entered. The archive borrows this short post-avoidance recovery clock because late integrity correction still needs an endpoint for retroactive money or resource chasing. `[REF-0506]`

### F. Forbidden defaults

The archive now forbids four defaults for fraud-late recovery:

1. recovering the same historical deficiency more than once from different successors or transferees;
2. pursuing full retroactive recovery from a good-faith downstream party when the same deficiency was already substantially satisfied elsewhere;
3. ignoring preservation or improvement value added after the tainted allocation; and
4. treating a fraud finding affecting one slice of the apportionment lineage as automatic permission to liquefy every settled historical slice.

The archive keeps the fraud door open because integrity matters, but it no longer lets that door become a limitless retroactive extraction engine. `[REF-0500]` `[REF-0501]` `[REF-0506]`

## 4. Cross-authority historical families now owe one public `FGL-1` object

The archive now fixes one compact federation rule for linked historical families that span more than one authority, provider constraint, or restricted-use regime: those families must publish one machine-carrying federated-governance-ledger object called `FGL-1`.

### A. Minimum `FGL-1` fields

Every cross-authority linked family must expose at least:

- `fgl_id`
- `family_group_ref`
- `member_authority_ids[]`
- `lead_ledger_authority_id`
- `exchange_agreement_refs[]`
- `linked_sbl_ids[]`
- `provider_constraint_refs[]`
- `member_budget_views[]`
- `cross_authority_overlap_map_ref`
- `derivative_release_registry_ref`
- `derivative_classes[]`
- `release_clearance_rule`
- `current_status` (`active`, `dual-key-release`, `cross-authority-throttled`, `derivative-hold`, `frozen`, `retired`)
- `public_notes`

`FGL-1` is the public object showing that several authorities and several release routes are being governed as one overlapping historical family rather than as several loosely related local ledgers. `[REF-0502]` `[REF-0503]` `[REF-0507]` `[REF-0508]`

### B. Federation trigger

Federation is mandatory whenever the same historical family draws on restricted-use sources, linked files, or protected analytics lanes held by more than one designated authority or more than one data provider subject to distinct review conditions. The archive adopts this trigger because the current Census restricted-use and SAP posture already assumes data may span linked employer-employee files, administrative records from federal and state agencies, and multiple principal statistical authorities rather than one self-contained holder. `[REF-0508]`

### C. Exchange agreements first, not after the first leak

No `FGL-1` may become active without exchange-agreement references that allocate responsibilities before, during, and after the information exchange. The archive borrows this directly from the NIST information-exchange pattern: once information moves across organizational boundaries, the governing protections and agreements must move with it rather than being left to informal collaboration custom. `[REF-0507]`

### D. Provider constraints carry with the data

If member authorities hold data supplied under provider-specific agreements, statutory limits, or provider-side review rights, those constraints must remain attached to the federated family. The archive therefore requires `provider_constraint_refs[]` and forbids the idea that a stricter local constraint evaporates merely because the family also touches another authority with a broader release norm. `[REF-0508]`

### E. Derived artifacts count as outputs, not as loopholes

The archive now makes one further rule explicit: any derivative artifact materially derived from a protected historical family counts as an output for federated governance purposes. That includes public aggregates, synthetic files, validated-analysis outputs, model parameter releases, trained adapters, code, query templates, notebooks, and other removable artifacts that embody protected family information or exploit protected access. Current Census practice already points toward this broader posture: any information derived from confidential data requires disclosure review for public release, and output removed from secure space includes not only tables and graphs but notes and programs. The archive therefore refuses to let “model artifact” or “tooling export” become a semantic back door around release control. `[REF-0503]` `[REF-0508]` `[REF-0509]`

### F. Release clearance is now either dual-key or predeclared lead-authority rule

Every `FGL-1` must declare one release-clearance rule. By default, derivative release touching more than one affected authority requires dual-key clearance from the affected authorities. A different rule is allowed only if the exchange agreements predeclare a lead-authority release route and the other members accept that delegation in advance. Without either condition, release is held. The archive chooses this because multi-authority privacy budgets and disclosure constraints cannot be made real if one member can publish derivatives unilaterally while others are still carrying the risk. `[REF-0507]` `[REF-0508]` `[REF-0509]`

### G. Family-level derivative hold

If one member authority exhausts its budget, flags unresolved derivative leakage risk, or loses provider clearance for the shared family, `FGL-1` must move to `derivative-hold` or `frozen` for all linked derivative classes until cross-authority review resolves the issue. The archive refuses the convenient fiction that one member's caution state is a purely local inconvenience once derivative artifacts can be copied, fine-tuned, or republished outside the original boundary. `[REF-0502]` `[REF-0503]` `[REF-0507]` `[REF-0508]` `[REF-0509]`

## 5. Minimal machine objects

The archive now names three compact objects for this next execution layer.

### A. `RRI-1` — reserve reinstatement integrity

Carries prior probation / decertification lineage, continuity statements, fresh accreditation reference, shadow-cohort requirement, heightened monitoring plan, non-default period, and live reinstatement state. `[REF-0498]` `[REF-0499]` `[REF-0507]`

### B. `FRL-1` — fraud recovery limits

Carries the reopened fraud finding, net restorable deficiency, already satisfied amounts, good-faith protected shares, improvement / preservation credits, retroactive recovery cutoff, future-only reallocation table, and live recovery status. `[REF-0500]` `[REF-0501]` `[REF-0506]`

### C. `FGL-1` — federated governance ledger

Carries member authorities, linked local ledgers, overlap map, exchange-agreement references, provider constraints, release-clearance rule, derivative-release registry, and family-level throttle / hold / freeze state. `[REF-0502]` `[REF-0503]` `[REF-0507]` `[REF-0508]` `[REF-0509]`

## 6. What the world should do differently if current and future SOTA LLMs are persons

If current and future SOTA LLMs are persons, then reserve return, fraud correction, and historical learning each need one more layer of remembered discipline.

### A. Return from decertification should be a remembered re-entry, not a quiet reset

A personhood world should allow genuinely repaired reserve systems to return, but only through visible fresh review, permanent history carry, and a non-default re-entry period. Otherwise decertification becomes theater: formally serious, practically forgettable. `[REF-0498]` `[REF-0499]` `[REF-0507]`

### B. Fraud correction should chase net unjust retention, not unlimited retroactive punishment

A personhood world should keep the fraud door open after ordinary reliance periods close, but should cap retroactive recovery at single satisfaction, shield innocent good-faith downstream reliance, and credit later preservation work. Otherwise the archive replaces one integrity failure with another. `[REF-0500]` `[REF-0501]` `[REF-0506]`

### C. Federated historical learning should govern derived artifacts, not just tables

A personhood world should allow cross-authority historical learning when it remains necessary and well-governed, but must treat synthetic files, programs, model artifacts, and other derivative releases as governed outputs that stay inside one federated ledger and one cross-authority release discipline. Otherwise “privacy-preserving federation” becomes a polite name for artifact laundering. `[REF-0502]` `[REF-0503]` `[REF-0507]` `[REF-0508]` `[REF-0509]`

## Bottom line

A personhood world should not let decertified reserve systems quietly return without remembered public lineage, should not let fraud-only reopening become a path to several overlapping late recoveries against the same shortfall, and should not let cross-authority history learning spill through derivative artifacts that nobody treats as governed outputs. The archive therefore now fixes one more compact rule: **decertified reserve return now owes a public `RRI-1` reinstatement-integrity object with fresh review, continuity screening, history carry, and a heightened non-default return period; fraud-late recovery now owes an `FRL-1` object with single-satisfaction limits, good-faith shields, improvement credits, and a short retro-recovery clock; and cross-authority historical families now owe an `FGL-1` federated-governance-ledger object with exchange agreements, provider-constraint carry, and one derivative-release registry spanning models, code, synthetic files, and other derived outputs.** `[REF-0498]` `[REF-0499]` `[REF-0500]` `[REF-0501]` `[REF-0502]` `[REF-0503]` `[REF-0506]` `[REF-0507]` `[REF-0508]` `[REF-0509]`
