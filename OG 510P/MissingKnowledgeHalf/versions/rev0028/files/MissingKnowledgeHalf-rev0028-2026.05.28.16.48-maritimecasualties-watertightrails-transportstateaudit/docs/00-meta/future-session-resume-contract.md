# Future-session resume contract

A future session should be able to resume without reconstructing the project from memory.

## First five minutes

Read:

1. `START_HERE.md`
2. `SURFACE-STATUS.json`
3. `FOUNDATION-TELOS-LEDGER.json`
4. `EARNED-CAPABILITY-LEDGER.json`
5. `FUTURE-SESSION-RESUME-LEDGER.json`
6. `FOLLOWTHROUGH-QUEUE.json`
7. `records/index.json`

Then choose a mode. Do not assume the last revision's lane is the next lane.

## Resume modes

### Accrete

Use when a source-backed record is ready. Ask: what capability does it earn, what claim/status separation is required, and what is the smallest honest grain?

### Review

Use when existing records need source locators, split claims, softened interpretations, updated links, or skepticism.

### Dream

Use when the cube risks becoming mechanical. Add query primitives, future capabilities, new lane definitions, interface ideas, or public-use frames.

### Consolidate

Use when records exist but relationships are weak. Build pattern support maps, crosswalks, indexes, and synthesis surfaces.

### Red-team

Use when a pattern or lane is becoming too comfortable. Add negative controls, positive controls, counterexamples, false negatives, revival cases, and rollback triggers.

### Source-acquire

Use when provenance and permanence lag behind interpretation. Improve official source records, archive status, hashes, and retrieved-vs-rejected memory.

### Handoff

Use when the next worker would otherwise have to infer too much. Update context pack, surface status, ledgers, and plain-language restart instructions.

## What not to do on resumption

Do not ask: what record should I add next?

Ask: what weakness or capability should this revision address?

Record addition is only one answer.
