# Software opacity and attribution traps — rev0011 method note

Rev0011 opens the software accountability lane. The record unit is not merely “software failed.” The method asks five questions for every case:

1. What internal software or system state mattered?
2. What external surface did patients, operators, users, courts, regulators, or the public see?
3. How did attribution initially travel: to a person, a compliant-looking test result, a branch shortfall, an operator action, or a system claim?
4. What rail later made the hidden state visible: engineering analysis, adverse-event reporting, litigation, statutory inquiry, in-use testing, regulator enforcement, or disclosure?
5. What remains invisible even after the correction rail?

This method is designed for cases where software acts as **machine testimony**: a system output becomes evidence about the world, but the people affected cannot inspect the state that generated it.

## Promoted rev0011 records

- `MKH-ENG-0001` — Therac-25, medical-device software safety and misleading state.
- `MKH-ENG-0006` — UK Post Office Horizon, branch accounting software as legal/evidentiary surface.
- `MKH-ENG-0019` — Volkswagen Dieselgate, software-mediated regulatory evasion.
- `MKH-INF-0017` — FDA MDR / MAUDE, medical-device adverse-event visibility rail.
- `MKH-INF-0018` — Horizon IT Inquiry, late statutory correction-memory rail.
- `MKH-INF-0019` — EPA/CARB in-use testing and defeat-device detection rail.
- `MKH-PAT-0011` — attribution-trap pattern candidate.

## Guardrails

Therac-25 is not reduced to operator error. Horizon is not reduced to “a bug.” Dieselgate is not treated as accidental outage. MAUDE/MDR, the Horizon Inquiry, and EPA/CARB testing are partial visibility rails, not complete denominators or universal software accident boards.
