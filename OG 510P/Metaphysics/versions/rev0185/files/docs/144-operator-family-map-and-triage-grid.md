# Operator-Family Map and Triage Grid

## Why this file exists

The archive has grown past the point where a new case can safely be handled by asking, one file at a time, whether it resembles the newest operator. After the rapid run from **turnover** through **valving**, the main risk is no longer that the archive lacks distinctions. The main risk is that it now has enough neighboring distinctions for a future revision to choose the wrong one too quickly.

That risk shows up in several ways:

- treating every **component change** as substitution even when the better diagnosis is turnover, repair, succession, migration, or duplication,
- treating every **inside relation** as hosting, embedding, enclosure, or constitution without asking which relation actually bears the explanatory load,
- treating every **surface or boundary case** as coating, wrapping, sealing, shielding, or gating without locating the relevant interface,
- treating every **hold relation** as attachment, clamping, latching, threading, joining, gripping, support, or fusion by vocabulary alone,
- treating every **path relation** as routing, guidance, circulation, bottlenecking, or valving without distinguishing path, rate, aperture, pressure, target, and control law,
- treating every **changed response** as habituation, saturation, depletion, fatigue, masking, inhibition, or malfunction without checking whether the response basis or the available stock actually changed,
- and treating every **successful description** as a candidate for a new file rather than first using the existing family of comparison classes.

This file therefore adds a control layer: a **family map** for the whole archive and a **triage grid** for deciding where a future case should go before adding another operator.

## Compressed default

The archive should now say explicitly:

> **Do not classify a case by the first operator-word that fits; classify it by the smallest family of operators that explains the target, basis, grain, continuity consequence, rival diagnoses, and artifact risks.**

In compressed form:

> **Operator choice is a triage problem before it is a theory-building problem.**

And more carefully:

> **The archive should treat its files as a nested diagnostic apparatus: first identify the kind of metaphysical pressure, then the relevant operator family, then the nearest rival files, and only then decide whether a case needs a new distinction, a refinement of an existing distinction, or no ontological promotion at all.**

## The main triage question

Every difficult case should be routed by asking:

> **What sort of confusion would occur if this case were classified too coarsely?**

The most common answers are:

1. **Status confusion** — something is called real, objective, fictional, constructed, derivative, fundamental, indispensable, or merely representational without specifying the status profile.
2. **Category confusion** — object, event, process, fact, relation, property, kind, structure, power, and role are treated as interchangeable.
3. **Unity confusion** — one, many, same, coincident, overlapping, continuous, fused, branching, or successive cases are collapsed.
4. **Dependence confusion** — composition, constitution, realization, grounding, causation, support, hosting, and scaffolding are flattened.
5. **Modal confusion** — essence, possibility, law, power, chance, potentiality, and counterfactual support are treated as one can-talk.
6. **Access confusion** — measurement, evidence, representation, reference, appearance, directness, robustness, and artifact-risk are not separated.
7. **Process confusion** — onset, persistence, cessation, return, delay, inertia, attrition, irreversibility, and transition are collapsed.
8. **Stock/flow confusion** — accumulation, depletion, replenishment, turnover, circulation, bottlenecking, leakage, release, retention, and routing are not separated.
9. **Interface confusion** — hosting, attachment, embedding, enclosure, coating, wrapping, lamination, sealing, joining, articulation, retention, traction, support, guidance, and valving are read as one generic relation.
10. **Control confusion** — gating, feedback, saturation, filtering, metering, throttling, buffering, and selective responsiveness are collapsed.

If a case falls cleanly into one answer, begin there. If it falls into several, identify the **primary** confusion and list the **secondary** ones explicitly.

## Triage grid

### A. If the question is “Is this real?”

Start with status and access, not with an interface operator.

1. Use `21`, `58`, `59`, `60`, and `74` to determine the status issue.
2. Use `61` through `67` if the claim depends on measurement, evidence, representation, or artifact-risk.
3. Use the local operator only after the target is no longer a mere readout, label, proxy, or modeling convenience.

Failure mode: promoting a convenient diagnostic category into a new real operator without asking whether it is only a proxy or regime-bound idealization.

### B. If the question is “Is it the same thing?”

Start with unity, identity, materiality, and temporal profile.

1. Use `12`, `17`, `28`, `29`, `35`, `36`, and `41` to classify the bearer.
2. Use `79` through `88`, `100` through `104`, and `107` through `108` if the continuity issue is temporal or processual.
3. Use `120`, `124`, `125`, `126`, or `141` only after it is clear whether the relevant continuity is constituent exchange, substitution, movement, hosting, or support.

Failure mode: reading same function, same role, same route, same host, same valve, or same label as numerical identity.

### C. If the question is “What depends on what?”

Start with dependence and category.

1. Use `08`, `16`, `32`, `33`, `48`, and `53` to distinguish dependence type.
2. Use `17`, `35`, `76`, `77`, `126`, `127`, `128`, `129`, and `141` when support, location, hosting, embedding, enclosure, and constitution are close rivals.
3. Do not infer constitution from indispensability, support from mere helpfulness, or grounding from causal production.

Failure mode: turning every enabling condition into a part, every internal location into incorporation, or every support relation into identity.

### D. If the question is “What changed?”

Start with the process and transition family.

1. Use `50`, `79` through `88`, `100` through `108`, and `120` through `125` to determine whether the case is onset, cessation, return, succession, duplication, fusion, turnover, migration, or substitution.
2. Use `103` through `111` if the change is gradual weakening, one-wayness, fragility, delay, inertia, resistance, deformation, or slack.
3. Use `117` through `123` if the change concerns stock, flow, throughput, or route.

Failure mode: treating every difference across time as replacement, every return as persistence, every reroute as repair, or every threshold event as new entity formation.

### E. If the question is “Why did output change?”

Start with capacity, response, and control.

1. Use `82`, `91` through `99`, `109` through `113`, and `143` to distinguish masking, inhibition, counteraction, redundancy, amplification, feedback, synchronization, gating, saturation, habituation, friction, elasticity, slack, filtering, and valving.
2. Use `114` through `119` if output changed because availability changed.
3. Use `121` through `123` if output changed because throughput, congestion, backpressure, or route changed.

Failure mode: treating all reduced output as absence, all flat output as saturation, all delayed output as blockage, or all selective output as intentional control.

### F. If the question is “How is one thing related to another at an interface?”

Start with the interface family, but do not stop at the first plausible word.

1. Use `126` through `129` for residence, insertion, enclosure, or housing.
2. Use `130` through `133` for surface, cover, layer, or seal.
3. Use `134` through `140` for joining, motion-coupling, retention, positive lock, threaded fastening, toothed engagement, or grip.
4. Use `141` through `143` for load path, guided passage, or regulated passage.
5. Use `124` and `125` when changed occupant, component, bearer, route, host, site, or role makes the interface question also a continuity question.

Failure mode: treating all “in”, “on”, “through”, “attached”, “held”, “sealed”, “joined”, “guided”, or “controlled” language as one relation.

## Adjacency rules for the late operator family

### Substitution versus turnover

Use **substitution** when a role, component, realizer, or stand-in is explicitly replaced under a functional-equivalence condition. Use **turnover** when constituent cycling is ongoing, distributed, and maintenance-like rather than an explicit swap.

### Substitution versus succession

Use **substitution** when the focus is role or function continuity under a replacement item. Use **succession** when lineage, office inheritance, charter continuity, descent, or transmitted practice is the main bearer of continuity.

### Migration versus substitution

Use **migration** when the same bearer, process, function, or lineage is moved, ported, transplanted, or redeployed across site, host, or platform. Use **substitution** when a different bearer fills the role.

### Hosting versus embedding

Use **hosting** when the target occupies, lodges, rides, or is carried by a host while remaining comparatively guest-like. Use **embedding** when the target is inserted into a surrounding matrix, substrate, body, system, or site such that placement within that substrate does explanatory work.

### Embedding versus enclosure

Use **embedding** when insertion or insetting into a substrate matters. Use **enclosure** when surrounding, casing, housing, encapsulation, or protective containment matters.

### Enclosure versus wrapping

Use **enclosure** when a housing or surrounding container relation is central. Use **wrapping** when a flexible or conformal cover is draped, sheathed, bandaged, or wound around the target.

### Coating versus wrapping

Use **coating** when a surface layer is deposited, applied, lined, clad, or veneered. Use **wrapping** when the cover's sheet, sheath, fold, band, or encircling form matters.

### Wrapping versus lamination

Use **wrapping** when one layer covers a target from outside. Use **lamination** when multiple layers, sheets, or strata are stacked, interleaved, bonded, or arranged as a sandwich architecture.

### Sealing versus enclosure

Use **sealing** when closure integrity, gap-blocking, perimeter compression, gasketing, caulking, plugging, or leak-prevention at an opening or interface is central. Use **enclosure** when the case is about surrounding housing or containment even without a seal-quality question.

### Sealing versus valving

Use **sealing** when the point is maintaining closure or blocking unintended passage. Use **valving** when the point is controlled, metered, throttled, or pressure-triggered passage through an aperture.

### Joining versus attachment

Use **joining** when the interface makes a bonded, welded, soldered, brazed, adhesive, stitched, stapled, or otherwise jointed assembly. Use **attachment** when the case is anchored, tethered, docked, mounted, moored, or connected without the stronger joint profile doing the main work.

### Joining versus fusion

Use **joining** when an interface or seam remains diagnostically relevant. Use **fusion** when the many-to-one transition forms a stronger new unity whose explanatory profile is not just interface retention.

### Articulation versus joining

Use **articulation** when a joint or coupling is defined by permitted motion, range, pivot, hinge, socket, or gliding. Use **joining** when the main work is stable connection rather than motion-governing coupling.

### Clamping versus latching

Use **clamping** when retention is generated by compression, preload, cinching, crimping, or press-fit holding. Use **latching** when retention is generated by capture, keying, detent, positive engagement, or lock-state completion.

### Latching versus threading

Use **latching** when discrete engagement, capture, keying, detent, or lock completion matters. Use **threading** when helical engagement, torque, pitch, preload, tapped retention, or bolt-and-nut structure matters.

### Threading versus joining

Use **threading** when a serviceable helical fastener relation is central. Use **joining** when the interface is welded, soldered, brazed, adhesive, stitched, or otherwise made joint-like in a way not explained by thread geometry.

### Meshing versus gripping

Use **meshing** when toothed, geared, splined, interdigitated, indexed, or backlash-managed engagement matters. Use **gripping** when traction, friction, contact patch, normal force, slip threshold, or surface-mediated hold matters.

### Gripping versus clamping

Use **gripping** when surface traction and slip-limited engagement carry the explanation. Use **clamping** when compression preload or constriction is the holding basis.

### Support versus attachment

Use **support** when load path, bearing, suspension, bracing, hanging, propping, or carriage is central. Use **attachment** when the connection relation matters without load-bearing support doing the main explanatory work.

### Support versus hosting

Use **support** when load-bearing or bracing is central. Use **hosting** when occupancy, platform residence, lodging, tenancy, or carriage is central.

### Guiding versus support

Use **guiding** when path constraint, route, conduit, duct, rail, sleeve, or corridor is central. Use **support** when load path or bearing relation is central.

### Guiding versus rerouting

Use **guiding** when the issue is constrained passage along or within a guide. Use **rerouting** when the issue is alternative path selection, bypass, diversion, or shunting relative to a usual path.

### Guiding versus valving

Use **guiding** when the case controls direction or path. Use **valving** when it controls admission, rate, aperture, dose, shutoff, pressure relief, or throttled passage.

### Valving versus bottlenecking

Use **valving** when restriction is governed by an aperture, setting, control relation, or metering architecture. Use **bottlenecking** when congestion, capacity limit, queueing, chokepoint dependence, or backpressure arises from throughput imbalance rather than regulated aperture.

### Valving versus gating

Use **valving** when actual passage, flow, dose, rate, pressure, or aperture control is central. Use **gating** when the issue is selective responsiveness, coupling window, switch-like admissibility, or tuned sensitivity even if no flow aperture is at stake.

## Bloat-control rules

### 1. Require a nearest-three comparison

No proposed new operator should be accepted until it names the **three nearest existing files** and says why each is insufficient.

A good proposal says:

- why the case is not merely a special case of one existing file,
- why it is not handled by a pair of neighboring files,
- what diagnostic question would remain unanswered without the new operator,
- what false inference the new operator prevents,
- and what compression rule would keep the new operator from expanding uncontrollably.

### 2. Require a basis test

A vocabulary word is not enough. A new or selected operator must identify the basis doing the work: material, formal, functional, causal, modal, organizational, institutional, representational, evidential, boundary, interface, control, temporal, or mixed.

### 3. Require a grain test

Many apparent disagreements vanish when the grain changes. A case may be one thing at the token level, another at the type level, another at the role level, another at the system level, and another at the regime level.

### 4. Require a failure-mode test

The archive should ask what failure would reveal the relation. The failure mode for sealing is not the same as the failure mode for guidance, latching, support, valving, or representation.

### 5. Require a continuity-consequence test

Every operator should say whether it tends to preserve, alter, suspend, replace, split, merge, route, host, support, regulate, or merely redescribe the relevant target.

### 6. Require an artifact-risk test

Every operator should identify the easiest way proxy evidence can mislead: same label, same location, same readout, same hardware, same route, same function, same status, or same appearance.

### 7. Prefer refinement over addition

If an existing file can be repaired by adding a contrast class, failure mode, or diagnostic question, do that before adding a new file.

### 8. Prefer family consolidation after rapid expansion

After several adjacent operator files have been added, the next revision should often consolidate the family rather than add another neighbor.

## Diagnostic worksheet

For future cases, fill this out before choosing an operator:

1. **Target:** What exactly is under discussion?
2. **Target kind:** Object, process, relation, role, status, fact, power, structure, representation, or mixed?
3. **Primary pressure:** Status, category, unity, dependence, modality, access, process, stock/flow, interface, control, or mixed?
4. **Operator family:** Which family from this file is primary?
5. **Nearest three files:** Which existing files could plausibly handle it?
6. **Basis:** What makes the description non-accidental?
7. **Grain:** At what level does the relation hold?
8. **Continuity consequence:** What remains the same, what changes, and what is unsettled?
9. **Failure mode:** What would show breakdown, absence, or misclassification?
10. **Artifact risk:** What proxy, label, readout, or ordinary-language shortcut might mislead?
11. **Compression verdict:** Existing file, paired-file treatment, amended control rule, or genuinely new operator?
12. **Revision consequence:** Should the next revision add content, consolidate a family, repair a map, or leave the archive unchanged?
13. **Case-ledger consequence:** Should this case become an illustration, accepted calibration case, negative control, hard positive, hard negative, boundary case, regression case, demotion case, promotion case, or quarantine case?
14. **Propagation consequence:** Which front-door, synthesis, method, frontier, source, family-map, adversarial, ledger, index, version, manifest, or package files must reflect the accepted verdict?
15. **Terminology consequence:** Which words are canonical terms, aliases, family umbrellas, neighboring rivals, domain-specific terms, diagnostic prompts, source-specific anchors, deprecated terms, quarantined metaphors, or unsafe shortcuts?


## Relation to adversarial stress testing

This file routes a case. It does not by itself prove that the routing is stable. After applying this triage grid, use `145-adversarial-stress-tests-and-revision-protocol.md` to test the verdict under hostile variation:

- same vocabulary with changed basis,
- same basis with changed vocabulary,
- shifted grain,
- proxy-only evidence,
- fission or duplication,
- altered failure mode,
- and explicit defeater conditions.

The intended sequence is: **route first, then try to break the route**. If the route survives, the archive may use it with greater confidence. If it breaks, the next revision should repair the relevant family map, method rule, frontier test, or operator file before adding another first-order distinction.


## Relation to diagnostic case ledgering

This file routes a case to a family. `145-adversarial-stress-tests-and-revision-protocol.md` then attacks the routed verdict. `146-diagnostic-case-ledger-calibration-set-and-benchmark-protocol.md` records the result when the case becomes reusable or precedential.

The intended extended sequence is: **route first, try to break the route, then ledger the discriminating result**. If the case is merely illustrative, no ledger entry is needed. If the case will guide later additions, demotions, family consolidations, or synthesis-level claims, it should be treated as a calibration instrument rather than an anecdote.

## Relation to revision-dependency propagation

This file identifies where a case belongs. `147-revision-dependency-graph-update-propagation-and-drift-control.md` identifies where the consequences of an accepted routing must be propagated. A family-map change is incomplete if it does not update the method rules, frontier tests, ledger cases, source notes, and package files that now depend on the changed routing.

The intended full sequence is: **route, stress-test, ledger when precedential, then propagate before packaging**.

## Relation to terminology registration

This file routes cases by family. `148-terminology-register-synonym-control-and-crosswalk-protocol.md` routes words by status. A case can be correctly routed while its vocabulary remains unsafe, especially when an umbrella term such as support, control, interface, status, continuity, access, or process tempts a local verdict.

The intended vocabulary-safe sequence is: **route the case, stress-test the route, ledger the precedent, propagate the accepted change, and register or audit the terms that now carry doctrine**.

## Default verdict

The default verdict of this file is conservative:

> **Most future cases should be routed, contrasted, or compressed before they are promoted.**

That does not mean the archive should stop growing. It means growth should now be **family-aware, stress-tested, calibration-aware, propagation-complete, terminology-safe, status-assigned, dossiered, reuse-governed, transmission-safe, and reception-audited**. The archive has earned enough operator vocabulary that responsible expansion requires a routing discipline, adversarial discipline, case-ledger discipline, and update-propagation discipline as strict as the operator files themselves.
