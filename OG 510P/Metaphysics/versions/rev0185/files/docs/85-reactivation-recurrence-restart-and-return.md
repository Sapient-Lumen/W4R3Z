# Reactivation, Recurrence, Restart, and Return

## Why this file exists

The archive now has explicit files on **dormancy**, **repair-resilience**, **delegation**, **masking**, **onset**, and **cessation**, but it still lacks one direct file saying what to do when something **comes back**, **restarts**, **is reactivated**, **returns to force**, **recurs**, **relapses**, **is reinstated**, or **resumes after a gap**.

That omission matters because the archive still risks eight opposite mistakes:

- treating every **return** as if it were automatically **strict persistence of one uninterrupted bearer**,
- treating every **restart** as if it were automatically **fresh creation**,
- treating **reactivation**, **recurrence**, **reinstatement**, **repair**, **reassembly**, **reboot**, and **replacement** as if they were one flat phenomenon,
- treating cyclical or seasonal return as if the bearer literally vanished and reappeared each time,
- treating archival record, legal continuity, or retained configuration as if they automatically guaranteed the very same target,
- treating a repeated output as if it automatically proved the same ongoing process rather than a new run of the same type,
- treating later recovery, relapse, or resumed exercise as if the path taken to get there did not matter,
- or treating history-sensitive return as if it settled nothing beyond surface similarity.

This file gives the archive a compact **return-reactivation profile** so future revisions can say whether a case is chiefly about resumption, recurrence, restart, reinstatement, relapse, cyclical return, replay, reconstruction, or successor formation.

## Working default

The archive should now say explicitly:

> **A real target can come back by resumption, reactivation, recurrence, reinstatement, relapse, reboot, or restart without all such returns being one thing.**

In compressed form:

> **Coming back is not one thing.**

And more carefully:

> **A later return may preserve one bearer, resume one interrupted process, reinstate one status by record or authority, repeat one phase-type, reconstruct a successor, or only reproduce a similar output; the verdict must be typed.**

This fits the archive's wider commitments:

- **identity and sortals** still matter because the same return-profile does not hold across organisms, devices, offices, institutions, and processes,
- **process** still matters because interruption, recurrence, restart, and cycling are temporally organized,
- **power** still matters because reactivation often involves retained capacities now re-exercised,
- **dormancy** still matters because waking differs from rebuilding,
- **repair** still matters because restored operation differs from replacement under a familiar label,
- **delegation and social ontology** still matter because offices, permissions, and corporate procedures can be reinstated without the same individual performer,
- **onset** still matters because reactivation differs from first coming-into-being,
- **cessation** still matters because how something ended constrains what a later return could be,
- **measurement and evidence** still matter because apparent return can reflect renewed detection or reporting rather than changed ontology,
- and **history-sensitive organization** still matters because hysteresis, path dependence, and record-governed continuity can make the route back ontologically significant.

## Core distinctions

### 1. Resumption is not mere repetition

A process can resume after interruption. But many things that look like return are only another token of the same kind.

So the archive should distinguish:

- **same interrupted process resumed**,
- **new run of the same process-type**,
- **same bearer performing again**,
- **same role enacted by a different performer**,
- and **mere superficial resemblance of output**.

Otherwise it will keep mistaking repeatability for persistence.

### 2. Reactivation is not reinstatement

A device can reactivate because a retained organization becomes live again. A contract, office, or status can return because a rule, vote, record, or authority reinstates it. Those are not the same metaphysical story.

So the archive should distinguish:

- **reactivation of retained capacity**,
- **release from inhibition or suspension**,
- **reinstatement by record or authority**,
- **recommissioning of retained infrastructure**,
- and **fresh institution or status created under an old name**.

Otherwise it will keep flattening operational return and normative return into one case.

### 3. Restart is not repair

A system may be restarted after a pause, repaired after a breakdown, rebuilt after destruction, or replaced by a successor that inherits files, parts, or users.

So the archive should distinguish:

- **same system restarted**,
- **same system repaired then restarted**,
- **same design newly rebuilt**,
- **successor replacement with continuity of function**,
- and **archival emulation or replay**.

Otherwise it will keep confusing restored continuity with reconstruction.

### 4. Recurrence of phase is not persistence of one uninterrupted token

Many real things are cyclical: sleep/wake, seasonal activity, market opening/closing, recurring ritual, recurrent inflammation, repeated committee sessions, oscillatory processes. These cases often involve one bearer revisiting a phase, not one uninterrupted active episode.

So the archive should distinguish:

- **same bearer revisiting a phase**,
- **same stage-kind cycling through phases**,
- **series of distinct token episodes in one broader pattern**,
- **recurrent institutional enactment**,
- and **discrete replacements under a cycle-like description**.

Otherwise it will keep forcing cyclical cases into either uninterrupted persistence or repeated creation.

### 5. Return after cessation depends on what ended

If only activity ceased, later return may be resumption. If the bearer dissolved, later return may instead require reconstruction, reappointment, or successor formation.

So the archive should distinguish:

- **return after temporary offlining**,
- **return after dormancy**,
- **return after revoked but restorable status**,
- **return after dissolution with reconstruction**,
- and **return after terminal ending where only successor talk remains**.

Otherwise it will keep ignoring the metaphysical significance of the earlier ending-mode.

### 6. Relapse and re-emergence are not pure repeats

A disease may remit and relapse. A social conflict may cool and reactivate. A capability may be lost, retrained, and recovered. Later return can be history-laden rather than a neutral replay.

So the archive should distinguish:

- **same underlying condition resurfacing**,
- **new episode enabled by retained vulnerability**,
- **reactivation through unchanged standing basis**,
- **reacquisition after loss**,
- and **new but similar episode under a reused label**.

Otherwise it will keep treating the later episode either as numerically the same thing without argument or as wholly unrelated.

### 7. Return can be history-sensitive

Some systems exhibit hysteresis, lock-in, path dependence, ratcheting, or route-sensitive recovery. What counts as a return may depend on how the target got there, what was retained, and what cannot be simply undone by reversing the last visible input.

So the archive should distinguish:

- **simple reversal**,
- **history-sensitive return**,
- **route-dependent reinstatement**,
- **state restoration with altered thresholds**,
- and **only apparent return under changed underlying organization**.

Otherwise it will keep assuming that back-to-the-same-output means back-to-the-same-ontological-situation.

### 8. Archival continuity is not live continuity

Records, code repositories, constitutions, biological traces, user accounts, blueprints, and memories can support later return. But what they preserve may be a permission, a design, a script, a template, or a succession route rather than the very same active bearer.

So the archive should distinguish:

- **live retained organization**,
- **dormant but continuous bearer**,
- **record-backed reinstatement**,
- **template-based reconstruction**,
- and **mere historical remembrance**.

Otherwise it will keep reading every durable trace as automatic sameness.

## Typology of return-cases

### A. Resumption

A target remains in existence through the gap and later resumes operation.

**Examples:** a paused process resumes; a sleeping organism wakes; a powered-down device boots with retained state; an office-holder resumes a temporarily suspended authority.

### B. Reactivation

A retained capacity or organization becomes active again.

**Examples:** a quiet circuit re-energizes; a dormant pathway is triggered; a previously suppressed competence is exercised again.

### C. Reinstatement

A status, office, permission, or institutional standing returns through rule, recognition, vote, ratification, or procedural restoration.

**Examples:** a license is reinstated; an office is restored by legal act; a suspended account is reauthorized.

### D. Restart

A system begins running again after interruption, with varying degrees of retained organization and state.

**Examples:** a computer reboots; a factory line restarts; a research program resumes after funding returns.

### E. Recurrence

A phase, episode-type, or patterned event appears again.

**Examples:** seasonal migration; recurrent symptoms; regular sessions of one legislature; oscillatory activity.

### F. Reconstruction-like return

Something returns only because a successor is rebuilt, reconstituted, reassembled, or reappointed under inherited design, records, or role-structure.

**Examples:** an institution is re-founded using prior charter; a destroyed system is rebuilt from stored plans; a social office resumes with a new office-holder.

## Cross-domain pressure

### Organisms and life

Sleep, hibernation, suspended animation, remission, relapse, regeneration, and revival pressures make clear that return is not one phenomenon. Waking from sleep, recovering from illness, recurring symptoms, and reconstruction after death are not metaphysically interchangeable.

### Artifacts and technical systems

Boot, reboot, wake, restart, recover, reinstall, restore-from-backup, and rebuild all differ. Some preserve the same running system; some restore one retained system-state; some rebuild a successor using saved structure.

### Institutions and social reality

A parliament can reconvene, a legal status can be reinstated, a contract can be renewed, an office can be reoccupied, and an organization can be re-founded. These cases mix records, authorization, performers, and procedures in ways that ordinary “it came back” talk hides.

### Persons and agency

A person can resume agency after sleep, restraint, sedation, or repression. But role-return, authority-return, memory-return, and responsibility-return need not all line up. The archive should not let one vocabulary of “back again” settle first-personal, normative, legal, and biological continuity at once.

### Processes and regimes

A process may resume, recur, or restart. A regime may return after parameter reversal, or only approximately return under hysteresis. An equilibrium-like appearance may therefore hide deep route-sensitivity.

## False moves to avoid

- Do **not** infer strict numerical sameness from every successful return.
- Do **not** infer fresh creation from every restart.
- Do **not** equate recurrent phase return with uninterrupted persistence of one active episode.
- Do **not** let archival record, memory, or blueprint do more identity work than the target kind allows.
- Do **not** treat path dependence as merely epistemic when it may affect what sort of return is possible.
- Do **not** assume that the same name, office, interface, or user-facing output fixes the same bearer.
- Do **not** assume that return after terminal ending is always impossible across all domains; but also do **not** assume that any later reconstruction is literally the same thing.

## Default test for future revisions

When a future revision says that something **came back**, **resumed**, **was reactivated**, **returned**, **recurred**, **relapsed**, **restarted**, **was rebooted**, **was reinstated**, **reopened**, **reoccupied**, **was restored**, or **returned to force**, it should ask:

1. **What is the target?**
   - bearer, process, role, office, institution, signal, capacity, regime, or phase?
2. **What ended or went quiet earlier?**
   - activity, manifestation, authority, one role, one phase, one organization, or bearerhood itself?
3. **What remained across the gap?**
   - same organization, standing power, records, permissions, materials, traces, memory, code, or only a name?
4. **What is the return mode?**
   - resumption, reactivation, release, repair-and-restart, reinstatement, cyclical recurrence, reconstruction, successor appointment, or mixed?
5. **What is the continuity basis?**
   - retained organization, causal continuity, memory continuity, legal record, role continuity, control continuity, environmental restoration, or mixed?
6. **What is the timescale and cycle profile?**
   - episodic, periodic, seasonal, emergency restart, indefinite dormancy, one-off reinstatement, or mixed?
7. **What is the history-sensitivity / hysteresis / path-dependence profile?**
   - route-insensitive return, history-sensitive threshold, lock-in, ratchet, relapse-prone, or mixed?
8. **What is the bearer verdict?**
   - same bearer resumed, same bearer reactivated, same stage-kind revisited, same status reinstated, new run of same type, successor reconstructed, or still unsettled?

## Compression rule

> **When the archive says that something came back, it must state whether the case is one of resumption, reactivation, recurrence, reinstatement, restart, or successor reconstruction, what remained across the gap, and whether history-sensitive return matters.**

## Why this improves the archive

Without this file, the archive would keep oscillating between two bad habits:

1. **cheap continuity** — every return counts as the very same thing back again, and
2. **cheap restart ontology** — every gap forces a new thing.

The better default is stricter and more useful:

> **A later return is ontologically informative only when typed by what ended, what remained, how the return occurred, and what kind of target is at issue.**

That rule is what the archive was missing.
