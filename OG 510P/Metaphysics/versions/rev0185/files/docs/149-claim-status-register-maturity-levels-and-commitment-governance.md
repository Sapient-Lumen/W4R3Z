# Claim Status Register, Maturity Levels, and Commitment Governance

## Why this file exists

The archive now has a strong governance sequence:

1. `144-operator-family-map-and-triage-grid.md` routes candidate cases.
2. `145-adversarial-stress-tests-and-revision-protocol.md` attacks the routed verdict.
3. `146-diagnostic-case-ledger-calibration-set-and-benchmark-protocol.md` records reusable hard cases.
4. `147-revision-dependency-graph-update-propagation-and-drift-control.md` propagates accepted changes through the archive.
5. `148-terminology-register-synonym-control-and-crosswalk-protocol.md` registers the terms by which the accepted changes are expressed.

That sequence still leaves a serious risk: **commitment inflation**. A large archive can make every written distinction sound equally accepted, equally central, and equally stable. A reader may see a file heading, a synthesis sentence, a method rule, a frontier question, a calibration case, or a term crosswalk and assume that it has the same status as the archive's kernel commitments. That is false.

The archive contains many different kinds of claims:

- core commitments that define the current project,
- working defaults that organize the present synthesis,
- diagnostic distinctions that help prevent bad inferences,
- local operator profiles that may be strong in one family and weak in another,
- live rivals intentionally preserved for pressure,
- provisional probes that are not yet doctrine,
- source-dependent distinctions that should not be exported without care,
- quarantined metaphors that are useful only under control,
- deprecated or compressed items that should no longer guide new work,
- and open debts that the archive knows it has not yet paid.

This file adds a **claim-status register** and **maturity-level protocol**. Its purpose is not to make the archive timid. Its purpose is to prevent every useful distinction from hardening into doctrine merely because it has a file, a name, or a vivid example.

## Compressed default

The archive should now say:

> **No claim should be treated as a commitment until its status, scope, maturity level, owner file, rivals, defeaters, and update obligations are explicit.**

In shorter form:

> **A file is not a commitment level. A name is not a verdict. A useful distinction is not automatically doctrine.**

And more carefully:

> **Every stable thesis, operator, term, case verdict, source-dependent claim, compression rule, and synthesis sentence should be assigned a status strong enough to guide use but weak enough to avoid pretending that provisional, local, diagnostic, rival, or deprecated material is part of the archive's core doctrine.**

## Place in the control sequence

The intended hard-case sequence is now:

1. **Route** the case or proposed addition with `144`.
2. **Stress-test** the routed verdict with `145`.
3. **Ledger** reusable or precedent-setting cases with `146`.
4. **Propagate** accepted changes with `147`.
5. **Register terminology** with `148`.
6. **Assign commitment status** with this file.
7. **Write an application dossier** with `150-application-dossier-decision-record-and-verdict-report-protocol.md` when the verdict will be reused, taught, cited, source-bound, calibrated, or used to guide future revisions.
8. **Govern precedent reuse and appeal** with `151-precedent-reuse-appeal-transfer-and-review-governance.md` when the dossiered verdict will be reused, transferred, taught, appealed, narrowed, superseded, deprecated, or marked do-not-reuse.
9. **Govern transmission and compression** with `152-transmission-excerpt-compression-and-pedagogical-governance.md` when a status-assigned claim will be summarized, excerpted, taught, diagrammed, tabled, cited in a prompt answer, or exported into a derivative artifact.

The addition of this file changes the meaning of closure. A revision is not complete merely because its content has been written, tested, propagated, and terminologically audited. It must also state what level of commitment the archive is taking on.

The archive should now reject two opposite failures:

- **under-commitment** — everything stays a suggestive note, so the archive never learns;
- **over-commitment** — every suggestive note becomes doctrine, so the archive cannot revise itself.

Commitment governance is the discipline between those failures.

## Basic unit: the status-bearing item

A **status-bearing item** is any archive element whose strength may be misunderstood. At minimum, status can attach to:

| Item type | Status question |
|---|---|
| Kernel operator | Is this part of the project-defining grammar, or only a local helper? |
| Synthesis thesis | Is this a current default, a live option, a speculative extension, or a rejected alternative? |
| First-order operator file | Is the operator a mature diagnostic distinction, a local family term, or a provisional expansion? |
| Control file | Is the procedure required for closure, recommended for hard cases, or only a worksheet? |
| Method rule | Is this a hard gate, a default compression rule, a warning, or a local heuristic? |
| Frontier question | Is this unresolved debt, optional research pressure, or a stress test that blocks promotion? |
| Case verdict | Is this a positive control, negative control, hard positive, hard negative, boundary case, regression case, or anecdote? |
| Term | Is this canonical, alias, umbrella, rival, source-specific, deprecated, quarantined, or unsafe? |
| Source anchor | Is the source constitutive for the claim, illustrative, domain-specific, historical, or obsolete? |
| Revision note | Is the change doctrine, method, metadata, cleanup, quarantine, consolidation, or packaging repair? |

The guiding rule is simple:

> **Different archive objects can occupy different status levels even when they appear in the same file.**

A file can contain a mature distinction, a provisional example, a live rival, a deprecated metaphor, and an open debt. The file title does not make all of those equally authoritative.

## Commitment statuses

Use these statuses unless a future revision justifies a replacement vocabulary.

### 1. Kernel commitment

A **kernel commitment** defines the current project. Removing it would change the architecture, not merely a local verdict.

Examples include the archive's standing commitment to non-skeptical, non-reductive metaphysics; the five-operator kernel of form, process, power, structure, and grounding; dependence pluralism; category discipline; and the refusal to treat higher-level reality as either magical independence or mere eliminable shorthand.

Rules:

- Do not add a kernel commitment during an ordinary operator expansion.
- Do not demote a kernel commitment without a major synthesis-level revision.
- Record rivals explicitly if a kernel commitment remains live under pressure.
- Do not let a source-specific doctrine become kernel merely because it is well anchored.

### 2. Working default

A **working default** is the archive's present best answer. It guides interpretation until defeated, but it is not unrevisable.

The current synthesis, Layered Process Realism, is a working default. Many of its component theses are also working defaults: powers are real; form and organization matter; some higher-level realities are robust; temporal becoming cannot be treated as mere decoration; evidence is world-constrained but access-mediated.

Rules:

- A working default must name its live rivals.
- It must be revisable by frontier questions, calibration failures, or source-dependent pressure.
- It may appear in `00` and `01`, but should not be worded as if it were a final theorem.
- It should survive at least basic adversarial variants before guiding new files.

### 3. Mature diagnostic distinction

A **mature diagnostic distinction** is strong enough to prevent bad inference across cases, even if it is not a fundamental metaphysical posit.

Most first-order operator files from the archive should be read this way. Their function is often diagnostic: distinguish hosting from embedding, sealing from valving, substitution from succession, leakage from release, support from attachment, evidence from proxy artifact.

Rules:

- A mature distinction must have a basis, grain, nearest rivals, failure modes, and artifact-risk profile.
- It does not automatically imply fundamentality.
- It can be mature in one family while weak or merely analogical in another.
- It should have at least negative-control discipline: cases that sound similar but should route elsewhere.

### 4. Calibrated precedent

A **calibrated precedent** is a verdict that has become reusable because it survived routing, stress-testing, and ledgering.

Rules:

- Calibrated precedents should be recorded or summarized through `146`.
- They should include positive controls, negative controls, hard positives, hard negatives, boundary conditions, regression instructions, and defeaters.
- They can constrain future revisions without becoming kernel commitments.
- If a future revision reverses them, it must state the regression cost.

### 5. Domain-local rule

A **domain-local rule** is authoritative only inside a specified domain, regime, or source-family.

Examples include legal-personhood usage, engineering fastening vocabulary, biological individuality criteria, clinical pathology classifications, mathematical representation conventions, measurement protocols, institutional status systems, or particular scientific models.

Rules:

- Do not export a domain-local rule into general metaphysics without a cross-domain translation.
- State the domain and the source anchors when external authority matters.
- Treat domain-local vocabulary as source-specific unless `148` registers a safe alias or canonical destination.
- Do not let a domain-local failure mode become a universal metaphysical failure mode without triage.

### 6. Live rival

A **live rival** is a view, carving, or operator that the archive does not currently prefer but preserves because it exposes pressure on the default.

Rules:

- A live rival is not an error merely because it is not the default.
- It should have the strongest case stated charitably enough to test the default.
- It should not be silently demoted into a straw target.
- It can become a working default if it wins enough frontier, stress, and calibration tests.

### 7. Provisional probe

A **provisional probe** is a candidate distinction, example, term, or synthesis adjustment that may be useful but has not yet passed enough gates.

Rules:

- Mark it as provisional in the owner file or ledger.
- Do not place it in the front-door default sequence except as an open pressure.
- Do not use it as a premise for further expansion.
- Specify which tests would promote, narrow, quarantine, or abandon it.

### 8. Quarantined analogy or metaphor

A **quarantined analogy** can guide discovery but cannot carry doctrine.

Rules:

- Use `148` to identify the metaphor or analogy.
- State what transfers and what does not transfer.
- Do not infer identity, parthood, causation, grounding, evidence, agency, function, normativity, or consciousness from the source domain unless the target basis independently earns it.
- Promote only after the analogy is translated into target-side basis and grain.

### 9. Source-dependent commitment

A **source-dependent commitment** depends on a source, practice, dataset, text, legal rule, engineering standard, scientific model, historical record, or domain convention.

Rules:

- Add or update anchors in `05` when the claim depends on current or external authority.
- Record whether the source is constitutive, evidential, illustrative, classificatory, or historical.
- Do not treat source-dependent usage as archive-wide terminology unless `148` licenses the crosswalk.
- Recheck time-sensitive source-dependent claims in future revisions.

### 10. Deprecated, compressed, or absorbed item

A **deprecated item** should no longer guide new work. A **compressed item** has been folded into a broader rule. An **absorbed item** remains valid only as a subcase of another file or family.

Rules:

- Say what replaced it.
- Preserve the reason for deprecation if the old term or case is likely to recur.
- Update `144`, `148`, and the relevant method/frontier files when a deprecated item affects routing or terms.
- Do not delete too aggressively; visible deprecation is often safer than disappearance.

### 11. Open debt

An **open debt** is a known unresolved obligation: missing source anchor, unstable term, untested rival, unledgered precedent, update-footprint gap, method-rule gap, or synthesis ambiguity.

Rules:

- Name the debt rather than bury it.
- State whether it blocks publication, blocks promotion, or merely guides future work.
- Do not turn an open debt into a conclusion by repeating it.
- Close the debt only by source update, test result, ledger record, propagation action, or explicit demotion.

## Maturity levels

Statuses say **what kind of commitment** an item has. Maturity levels say **how far it has traveled through the archive's governance sequence**.

Use the following ladder.

| Level | Name | Minimum condition | Typical use |
|---|---|---|---|
| M0 | Prompt | Interesting pressure only | Note, question, possible example |
| M1 | Named distinction | Has a term or contrast | Provisional vocabulary, local observation |
| M2 | Routed distinction | Has family and nearest rivals | Candidate operator or method-rule pressure |
| M3 | Stress-tested distinction | Survives basic hostile variants | Stronger candidate, still not precedent |
| M4 | Ledgered distinction | Has calibration cases or regression instruction | Reusable verdict or hard-case standard |
| M5 | Propagated distinction | Update footprint has been completed or declined | Archive-visible change |
| M6 | Terminology-safe distinction | Terms, aliases, rivals, metaphors, and forbidden inferences are controlled | Stable wording and crosswalk |
| M7 | Status-assigned distinction | Commitment level, scope, owner, and defeaters are explicit | Usable doctrine, default, live rival, or quarantine |
| M8 | Regression-protected distinction | Future revisions know what not to reverse accidentally | Stable calibration/control anchor |

Do not confuse maturity with strength. A live rival can be M7 if its role is explicit. A kernel commitment can become unstable if new revisions reveal unclosed M3 or M4 failures. A source-dependent term can be M6 without becoming a working default. A provisional probe can be useful at M2 without being promoted.

## Status register schema

When a status-bearing item becomes important enough to guide future work, record it using this compact schema. The record may live in the relevant file, in `146` for cases, in `148` for terms, or in a future dedicated register if the archive becomes too large.

| Field | Required question |
|---|---|
| Item | What claim, operator, term, case, source anchor, or method rule is being classified? |
| Owner file | Which file is responsible for maintaining it? |
| Status | Kernel, working default, mature diagnostic distinction, calibrated precedent, domain-local rule, live rival, provisional probe, quarantined analogy, source-dependent commitment, deprecated/compressed/absorbed item, or open debt? |
| Maturity level | M0 through M8? |
| Scope | Archive-wide, family-local, file-local, domain-local, case-local, source-local, or metaphor-only? |
| Basis | What makes the item non-accidental? |
| Grain | At what level does it hold? |
| Rivals | Which neighboring claims, terms, files, or views could be confused with it? |
| Defeaters | What would demote, narrow, quarantine, or reverse it? |
| Dependencies | Which files, source anchors, terms, and calibration cases must remain aligned? |
| Forbidden upgrade | What stronger claim must not be inferred? |
| Update obligation | What must be changed if the item changes status? |
| Review trigger | What event, source change, failure case, or revision type should force review? |

Minimal form:

> **Item / owner / status / maturity / scope / basis / rivals / defeaters / forbidden upgrade / update obligation.**

## Promotion rules

A candidate may be promoted only by satisfying the gates appropriate to its requested status.

### Prompt to named distinction

A prompt may become a named distinction when:

- the relevant target is stable enough to discuss,
- the term does not merely repeat an existing file under a new label,
- the candidate has at least one nearest rival,
- and the source of pressure is stated.

### Named distinction to routed distinction

A named distinction may become routed when:

- `144` can place it in a family,
- the nearest three rival files have been checked,
- the basis and grain are not merely verbal,
- and the proposed distinction does some compression work.

### Routed distinction to stress-tested distinction

A routed distinction may be treated as stress-tested when:

- same-word / changed-basis and same-basis / changed-word variants have been tried,
- the wrong-grain variant has not captured the verdict,
- proxy artifact has been considered,
- at least one failure mode has been specified,
- and defeaters have been named.

### Stress-tested distinction to ledgered precedent

A stress-tested distinction becomes a ledgered precedent only when:

- the case is reusable rather than merely illustrative,
- positive and negative controls can be stated,
- hard positives or hard negatives expose a genuine boundary,
- and future revisions would be harmed if the case were forgotten.

### Ledgered precedent to propagated doctrine

A ledgered precedent can guide doctrine only after:

- the update footprint has been run through `147`,
- non-updates have been explicitly accepted,
- source obligations have been checked,
- and the package metadata will not mislead future readers.

### Propagated doctrine to terminology-safe doctrine

A propagated doctrine becomes terminology-safe when:

- `148` has identified canonical terms, aliases, umbrellas, rivals, metaphors, and unsafe shortcuts,
- forbidden inferences have been named,
- cross-domain translation has been handled,
- and source-specific terms have not been exported without license.

### Terminology-safe doctrine to status-assigned doctrine

A terminology-safe doctrine becomes status-assigned when:

- this file records whether it is kernel, default, diagnostic, calibrated, local, rival, provisional, quarantined, source-dependent, deprecated, or open debt,
- the maturity level is explicit,
- the owner file is clear,
- and the update obligation is known.

## Demotion rules

Demotion is not failure. It is one of the archive's main ways of learning.

Demote an item when:

- it fails hostile variants from `145`,
- its positive controls collapse into a neighboring file,
- its vocabulary turns out to be an unsafe shortcut,
- its source authority is narrower or obsolete,
- its basis is present only at a different grain,
- its continuity consequence was overstated,
- its term was an alias rather than a canonical destination,
- its apparent ontology is an artifact of model, measurement, legal label, administrative category, or interface display,
- or its update footprint would force changes the archive is not prepared to accept.

Possible demotion verdicts:

- working default → live rival,
- working default → domain-local rule,
- mature diagnostic distinction → provisional probe,
- mature diagnostic distinction → absorbed subcase,
- calibrated precedent → boundary case,
- domain-local rule → source-specific anchor only,
- canonical term → alias or neighboring rival,
- metaphor → quarantined analogy,
- operator candidate → method-rule warning,
- source-dependent claim → open debt.

When demoting, update the file map only if the role of the file changes. Often it is better to keep the file but change its status, because future readers need to know why a tempting option was narrowed.

## Status conflict rules

Conflicts are expected. Resolve them explicitly.

### File-status conflict

A file may contain items at multiple statuses. The title can be a mature diagnostic distinction while some examples remain provisional and some terms remain aliases.

Rule: **Do not infer the status of an item from the status of its file.**

### Synthesis-status conflict

A synthesis sentence may lean on a distinction that is only family-local or provisional.

Rule: **The synthesis cannot be stronger than the weakest necessary support unless it states the gap as open debt.**

### Source-status conflict

A source may strongly support a domain-local distinction while the archive uses the same words more broadly.

Rule: **Source strength does not automatically become metaphysical generality.**

### Term-status conflict

A term may be canonical in one family and a misleading umbrella in another.

Rule: **Term status is scope-sensitive.**

### Case-status conflict

A case may be a positive control for one operator and a hard negative for a neighboring operator.

Rule: **Record the contrast rather than forcing one global label.**

### Rival-status conflict

A live rival may be more mature than the working default in a narrow region.

Rule: **Let local maturity pressure the default without pretending that local victory settles the whole synthesis.**

## Family-specific status guidance

### Dependence, grounding, realization, constitution, and composition

Do not let a dependence claim become a kernel commitment unless it changes the architecture of dependence pluralism itself. Most local dependence verdicts should be working defaults, mature diagnostic distinctions, calibrated precedents, or domain-local rules.

Forbidden upgrade: from **this depends on that in one respect** to **all dependence of this kind is grounding**.

### Identity, unity, persistence, substitution, migration, and succession

Continuity verdicts should usually be status-assigned at a narrow grain. A case can be a calibrated precedent for role continuity while remaining open debt for numerical identity.

Forbidden upgrade: from **same role, function, host, route, or lineage** to **same individual**.

### Truthmakers, absences, privations, and negative truths

Absence-related claims should be status-governed carefully. A successful negative-truth treatment may be a mature diagnostic rule without committing the archive to negative entities.

Forbidden upgrade: from **truth requires reality-answerability** to **every negative truth requires a negative object**.

### Access, evidence, measurement, representation, and artifact risk

Evidence claims often deserve domain-local or source-dependent status. Measurement success does not automatically promote a measured proxy into the target's ontology.

Forbidden upgrade: from **reliable indicator** to **constitutive basis**.

### Social, institutional, normative, agential, personal, living, and conscious reality

Higher-level reality claims are often working defaults or mature diagnostic distinctions, not kernel commitments about the whole world. Domain-local recognition, records, roles, and practices may be robust without becoming fundamental.

Forbidden upgrade: from **derivative but robust reality** to **independence from lower-level and institutional conditions**.

### Process, transition, irreversibility, resilience, and history-sensitivity

Process-family distinctions should be mature when they track real temporal profiles, but their status should not imply that every recurrence, trace, or threshold is fundamental.

Forbidden upgrade: from **stable dynamical profile** to **hidden substance**.

### Stock, flow, retention, release, leakage, accumulation, and throughput

Traffic and stock-flow distinctions often function as mature diagnostic distinctions or domain-local rules. Their claims should not automatically settle identity or parthood.

Forbidden upgrade: from **same flow path or stock role** to **same bearer**.

### Interface, placement, attachment, embedding, enclosure, surface, joining, and retention

Many late operator files are best read as mature diagnostic distinctions. They prevent false collapses among being in, on, with, through, around, attached to, supported by, joined to, and regulated by.

Forbidden upgrade: from **stable interface relation** to **fusion, parthood, or identity**.

### Control, guidance, gating, valving, and regulation

Control-family distinctions need status discipline because control words easily overstate agency, autonomy, design, or intentional governance.

Forbidden upgrade: from **regulated passage or selective responsiveness** to **agent-level control**.

### Control-layer files themselves

Files `144` through `149` are required governance layers for hard revisions. But their worksheets are not all equally mandatory for trivial edits.

Default status:

- `144` — required for candidate first-order additions and major rerouting.
- `145` — required for promoted, demoted, or precedent-setting verdicts.
- `146` — required when a case becomes reusable calibration.
- `147` — required for all packaged revisions, at least in minimal checklist form.
- `148` — required when terms, aliases, metaphors, or source-specific vocabulary carry doctrine.
- `149` — required when a claim, operator, term, source-dependent item, rival, or open debt might be mistaken for a stronger commitment than intended.

## Status worksheet

Use this worksheet before promoting a claim into the synthesis, method rules, README, archive index, or a future operator file.

1. **Item:** What exactly is being assigned status?
2. **Owner:** Which file is responsible for maintaining it?
3. **Requested status:** Kernel, default, diagnostic, calibrated, local, rival, provisional, quarantined, source-dependent, deprecated, or open debt?
4. **Current maturity:** M0 through M8.
5. **Scope:** Archive-wide, family-local, file-local, domain-local, source-local, case-local, metaphor-only, or mixed?
6. **Basis:** What makes the item non-accidental?
7. **Grain:** At what grain does it apply?
8. **Rivals:** Which files, terms, views, or cases could be confused with it?
9. **Defeaters:** What would demote or narrow it?
10. **Forbidden upgrade:** What stronger claim must not be inferred?
11. **Dependencies:** Which source anchors, terms, ledgers, method rules, or family maps must remain aligned?
12. **Update obligation:** What changes if the status changes?
13. **Review trigger:** What future event should force re-evaluation?
14. **Final verdict:** Promote, narrow, demote, quarantine, keep as rival, mark open debt, or leave unsettled?

## Minimal status labels for quick use

When a full worksheet is too heavy, use one of these compact labels:

- **KERNEL / M7+ / archive-wide**
- **DEFAULT / M5-M7 / archive-wide or family-wide**
- **DIAGNOSTIC / M3-M7 / family-local**
- **CALIBRATED / M4+ / case-family-local**
- **LOCAL / M2-M7 / domain- or source-bound**
- **RIVAL / M2-M7 / pressure-preserving**
- **PROVISIONAL / M0-M3 / not doctrine**
- **QUARANTINED / M1-M6 / metaphor-only unless translated**
- **SOURCE-DEPENDENT / M2-M7 / anchor required**
- **DEPRECATED / M1-M7 / do not use as default**
- **OPEN-DEBT / any maturity / must not be hidden**

These labels are not decorative. They should affect how the item may be used.

## How this changes future revision notes

Every future revision note should now say not only what changed, but what status the change has. Recommended minimal form:

> **Revision type:** operator addition / control-layer addition / family consolidation / demotion / source update / package repair.  
> **Status result:** kernel change / working-default adjustment / mature diagnostic clarification / calibrated precedent / domain-local rule / live rival / provisional probe / quarantine / deprecation / open debt.  
> **Maturity result:** M0-M8.  
> **Update obligation:** completed / declined / ledgered as debt.  
> **Forbidden upgrade:** the strongest misleading conclusion the revision blocks.

A revision can add a file without adding doctrine. A revision can remove a default without deleting a file. A revision can strengthen a live rival without changing the synthesis. A revision can mark open debt without failing.

## How this changes front-door writing

Front-door documents should avoid status ambiguity. In particular:

- `README.md` should distinguish what the revision changes from what it merely records as pressure.
- `00-start-here.md` should state the current default without pretending all local distinctions are equally central.
- `01-working-synthesis-layered-process-realism.md` should keep synthesis claims at the right status.
- `03-method-selection-and-compression-rules.md` should mark which rules are hard gates and which are heuristics.
- `04-open-questions-and-discriminating-tests.md` should mark whether a question blocks promotion, guides future work, or preserves a rival.
- `05-source-citations.md` should mark whether source anchors are constitutive, evidential, illustrative, domain-specific, historical, or absent because the revision is source-neutral.
- `144` through `149` should state their control role without pretending that every worksheet is required for every minor edit.
- `150` should state when a verdict needs a compact decision record, standard application dossier, full archive-grade dossier, local answer only, source-dependent hold, or do-not-reuse result.

## Common mistakes this file is designed to block

1. **File-title inflation** — treating the existence of a file as proof that the archive is fully committed to a new metaphysical kind.
2. **Synthesis smuggling** — using a provisional distinction inside a front-door thesis without marking its status.
3. **Example inflation** — treating an illustrative case as a calibrated precedent.
4. **Source inflation** — treating a domain source as archive-wide metaphysics.
5. **Term inflation** — treating a registered alias as a canonical destination.
6. **Rival erasure** — treating a live rival as a defeated error merely because the current default is preferred.
7. **Kernel creep** — letting repeated successful diagnostics become project-defining commitments without explicit promotion.
8. **Open-debt concealment** — hiding unresolved obligations inside confident prose.
9. **Deprecated ghosting** — deleting an old distinction so completely that future revisions accidentally reinvent it.
10. **Maturity confusion** — treating a high-maturity live rival as a default, or a low-maturity default-supporting prompt as doctrine.

## Relation to earlier control files

### Relation to `144`

`144` decides where a case belongs. This file decides how strongly the archive is committed to the result. Routing is not commitment.

### Relation to `145`

`145` attacks verdicts. This file records what status remains after the attack. Survival is not always promotion; sometimes it just narrows the scope.

### Relation to `146`

`146` preserves cases. This file classifies the commitment created by those cases. Ledgering is not always doctrine; some ledgered cases are hard negatives, boundary cases, or regression warnings.

### Relation to `147`

`147` propagates accepted changes. This file makes sure the propagated change is not stronger than intended. Propagation without status can spread overcommitment.

### Relation to `148`

`148` governs terms. This file governs commitments. A term may be canonical while the claim using it remains provisional; a claim may be a working default while one of its terms remains domain-local.

### Relation to `150`

`150` governs how status-assigned verdicts travel. This file can assign kernel, default, diagnostic, local, rival, provisional, source-dependent, deprecated, or open-debt status; `150` records that status in the final application verdict so a summary does not erase the limits. Status assignment is not yet report discipline.

## Future expansion rule

Before adding another control-layer file after this one, ask whether the pressure is really new. A new control layer is warranted only if the archive lacks a reusable answer to one of these questions:

- Where does the case route?
- Does the verdict survive attack?
- Should the case become calibration?
- Where must the change propagate?
- What terms are safe?
- What status does the claim have?
- How should the completed verdict be reported?
- How may the reported result be reused, transferred, appealed, superseded, or refused?
- How may the allowed result be summarized, excerpted, taught, diagrammed, or exported without status inflation?
- How is the transmitted material received, corrected, and package-gated before release?

If the pressure is a variant of one of those questions, amend `144` through `161` rather than adding another governance file. `150` is not a replacement for this restriction; it answers a downstream question: how should a completed verdict be reported without losing the status limits assigned here? `151` answers the next downstream question: how may that reported verdict be reused, transferred, appealed, superseded, or refused without becoming stronger than its status permits? `152`, `153`, `154`, and `155` answer later downstream questions: how should the result be transmitted, how was it received, when is the package ready for release, and how should the release relate to other versions, forks, derivatives, migrations, and citations?

## Closing formulation

The archive's current governance sequence can now be compressed as:

> **Route the case. Attack the route. Ledger the hard result. Propagate the accepted change. Register the words. Assign the commitment level.**

In `rev0144`, the applied version of that sequence adds: **write the auditable verdict**. In `rev0145`, the post-dossier version adds: **govern the verdict's reuse and appeal**. In `rev0146`, the output-facing version adds: **control the verdict's transmission and compression**. In `rev0147`, the correction-loop version adds: **audit the verdict's reception and feedback**. In `rev0148`, the package-readiness version adds: **gate the release and ledger maintenance state**.

This is not bureaucratic decoration. It is the archive's protection against its own success. The richer the map becomes, the more important it is to know which parts are kernel, which are default, which are diagnostic, which are local, which are rivals, which are probes, which are quarantined, which are deprecated, and which remain debts.
