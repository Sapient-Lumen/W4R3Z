# Cross-case application protocol

## What this note is for

The archive already has a compact **single-case memo standard** in [`case-application-protocol.md`](case-application-protocol.md) and a compact **multi-case order of operations** in [`cross-case-decision-path.md`](cross-case-decision-path.md).
What it still lacked was the thing between them:
**a thin retained memo shape for actual cross-case work.**

That gap matters because multi-case work can fail in two opposite ways:
- it can sprawl into a shadow dashboard that restages every memo in full,
- or it can stay so implicit that later readers cannot tell what the comparison actually decided, what failed, what travels, and what should change in the archive.

This note gives the archive one compact **retained comparison-memo protocol**.
It is not a new doctrine note.
It is a **memo-shape bridge** for comparison work that has already been worth retaining.

## Minimum operating rule

Every retained cross-case memo in this archive should answer **nine questions in order**:

1. **What is the comparison question and why do these cases belong in one set?**
2. **What shared pattern, if any, survives on the archive's operator spine?**
3. **How confident should the archive be in the pattern, the mechanism story, portability, and any wider consequence?**
4. **What is the strongest live rival or measurement rival?**
5. **What is the hardest deviant case, and what kind of anomaly is it?**
6. **What part of the lesson actually travels beyond this set?**
7. **Would another case still be the most verdict-moving next move?**
8. **If no stable positive pattern survives, what is the smallest honest archive action?**
9. **If something does survive, where should its consequence actually land?**

That sequence exists so future comparison work can stay cumulative without turning every retained cross-case memo into its own miniature archive.

## The required memo shape

### 1. Comparison-question block

Open with four short lines:
- **comparison question**
- **cases included**
- **cases excluded or postponed and why**
- **comparison level**

This block should make the set intelligible before any pattern language appears.
If the comparison question or level cannot be written plainly, the archive usually does not need a retained comparison memo yet.
It usually needs a narrower set, fresher case work, or honest non-comparability.

### 2. Shared-pattern block

State the smallest real recurring pattern that survives the cases on the archive's ordinary operator spine.
Usually three short lines are enough:
- **shared pattern candidate**
- **shared mechanism candidate**
- **comparison consequence candidate**

Do not make this a new metric universe.
A retained comparison memo should normally compare cases on verdict, dominant breach, fastest washout, mode, opening package, watch posture, and closely related burdens rather than inventing a fresh dashboard just because more than one case is present.

### 3. Confidence-burden block

Add four separate labels:
- **pattern-existence confidence**
- **mechanism confidence**
- **portability confidence**
- **doctrine-consequence confidence**

This block matters because recurrence, explanation, transfer, and doctrine motion are different burdens.
A good cross-case memo should never rely on smooth prose to collapse them into one implied confidence posture.

### 4. Rival-and-disconfirmation block

Add four short lines:
- **main live rival**
- **main measurement rival**
- **cleanest disconfirmation trigger**
- **next discriminating proof burden**

This keeps the comparison from surviving only because the strongest alternative explanation was never named.
It also keeps the archive from mistaking a weakly discriminated pattern for a portable lesson.

### 5. Deviant-case block

Add four short lines:
- **hardest deviant case**
- **why it strains the pattern**
- **anomaly type**
- **archive consequence of the anomaly**

The deviant case should be the most pattern-straining comparable case, not the easiest anomaly to dismiss.
A retained comparison memo should say whether the anomaly is repairable, rail-dependent, local, family-bounding, contradictory, or transfer-blocking.

### 6. Portability block

Add four short lines:
- **portable core**
- **required rails for transfer**
- **local dependence**
- **transfer posture**

This is where a comparison earns or loses wider travel.
A recurring pattern can be real and still be only case-family usable.
If the lesson travels only with named rails, the memo should say so plainly instead of letting later readers infer portability from repetition alone.

### 7. Saturation-or-null block

Every retained comparison memo should close the accumulation question explicitly.
Use one of two narrow outputs.

If a positive pattern survives, add:
- **saturation posture**
- **why enough / not enough yet**
- **next most verdict-moving case, if any**
- **archive consequence of that saturation posture**

If no stable positive pattern survives, add:
- **null-result posture**
- **what failed to survive**
- **smallest next discriminating move**
- **retention decision**

This block is the archive's anti-warehouse rule for cross-case work.
It stops a comparison from continuing merely because more plausible cases exist.

### 8. Consequence-routing block

Only after the earlier burdens are met should the memo say where any surviving lesson belongs.
Add four short lines:
- **primary revision target**
- **why that target and not a larger one**
- **explicit non-consequence**
- **next governed route**

A successful comparison does not automatically belong in doctrine.
Sometimes the honest target is a case-family bridge, a package-routing note, a source-priority note, or no archive promotion yet.

### 9. Minimal retained memo close

End with one short paragraph that says, in ordinary language, what the archive actually learned.
That paragraph should usually do only one of four things:
- keep the cases separate,
- record one narrow cross-case pattern,
- narrow where the pattern travels,
- or route one small consequence to its proper target.

If the memo tries to do more than that, it is usually becoming a shadow dashboard or a stealth doctrine rewrite.

## Minimal reusable template

A future retained cross-case memo can often stay narrow with only these headings:

- **Comparison question / level**
- **Cases included**
- **Cases excluded or postponed**
- **Shared pattern candidate**
- **Confidence burdens**
- **Main rival and measurement rival**
- **Hardest deviant case / anomaly type**
- **Portability posture**
- **Saturation posture or null-result posture**
- **Primary revision target / explicit non-consequence**
- **Smallest next proof burden**
- **Short ordinary-language close**

If those twelve lines cannot be filled cleanly, the archive usually does **not** need more rhetoric yet.
It needs a narrower set, fresher case work, a clearer rival test, or an honest decision to park the comparison.

## The main false moves this note is meant to stop

### 1. Rebuilding the archive inside every comparison memo

A retained cross-case memo fails compression when it restages whole case histories, whole package rationales, and whole theory sections instead of recording only the shared lesson that survived the comparison burdens.

### 2. Letting a multi-case note become a shadow dashboard

A comparison note should almost never invent a fresh metric universe.
If the archive really needs new standing surfaces, that is a scoreboard or doctrine question, not just a comparison memo.

### 3. Treating a retained comparison as automatic doctrine motion

A surviving pattern may still belong only in case-family guidance, package-routing adjustment, or measurement priority.
The consequence-routing block exists so cross-case work does not drift upward by momentum.

### 4. Keeping dead or mixed comparisons alive by inertia

When no stable pattern survives, the archive should be able to say so cleanly and either park the comparison or retain only a thin null note.
A retained comparison memo does not earn life merely because the work already happened.

### 5. Hiding the hardest anomaly in the middle of prose

A comparison that never names its hardest deviant case is usually protecting the pattern rather than testing it.
This protocol forces anomaly handling into the retained output itself.

## Fast use rule

When drafting a cross-case memo:

1. **State the comparison question and set first.**
2. **Extract only the smallest real shared pattern.**
3. **Keep the four confidence burdens separate.**
4. **Name the strongest rival and the hardest deviant case.**
5. **Say what, if anything, actually travels.**
6. **Close the accumulation question with saturation or null posture.**
7. **Route any surviving consequence to the smallest honest target.**
8. **End with one short plain-language paragraph, not a second archive.**

## Bottom line

The archive should now be able to retain **cross-case** work as thinly as it already retains **single-case** work.
A good comparison memo is not a second research program.
It is a short governed answer to a narrow multi-case question, written on the archive's standing spine, with explicit burdens for rivals, anomalies, portability, stopping, nulls, and consequence routing.
That is how the archive learns from several cases without turning every comparison into a warehouse or an unwritten doctrine rewrite.
