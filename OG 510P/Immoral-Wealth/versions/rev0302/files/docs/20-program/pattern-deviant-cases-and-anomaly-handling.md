# Pattern deviant cases and anomaly handling

## What this note is for

The archive can now choose a comparison set, extract a recurring pattern, state separate export burdens, name live rivals, and screen portability.
What it still lacked was the compact bridge for a different pressure point:
**what to do with the hardest deviant case once a pattern seems to be emerging.**

That gap matters because cross-case work can fail in two opposite ways at once:
- a claimed pattern survives by quietly burying the case that strains it most,
- or one noisy anomaly is allowed to collapse a still-real pattern without first asking whether the anomaly is local, stale, badly measured, or rail-specific.[S04][S05][S06][S15][S18][S19][S20][S21][S22][S23][S31][S32][S33]

This note gives the archive a compact rule for handling the **hardest deviant case** in a retained comparison.
It is not a new doctrine note and not a comparison dashboard.
It is an **anomaly-handling bridge**.

## Minimum rule

A cross-case pattern claim should usually name **one hardest deviant case** before it speaks confidently about recurrence, portability, or doctrine consequence.
That deviant case is the compared case that most clearly strains the proposed pattern after freshness, claim-level, and evidence-comparability filters have already been applied.

If no such case exists because the set is tiny or too homogeneous, say so plainly.
If more than one candidate looks equally straining, name the one that would do the most damage to the pattern **if it proved genuinely comparable and genuinely contrary**.

The archive should not let a pattern survive without confronting its hardest live strain.
It also should not let one apparent anomaly destroy a pattern before asking whether the anomaly is actually:
- a **freshness mismatch**,
- a **measurement artifact**,
- a **rail difference**,
- a **case-family boundary marker**,
- or a **real contradiction**.

## What should usually count as a deviant case

A case counts as deviant for archive purposes when it appears to share the comparison set's question and operator spine but does **not** fit the emerging pattern cleanly.
Typical examples include:
- a case with the same nominal opening package but no observed washout,
- a case with the same apparent dominant breach but a different governing mode,
- a case where the same proposed mechanism seems absent,
- or a case that survives ordinary pressure better or worse than the rest of the set would have predicted.[S07][S13][S15][S18][S19][S20][S21][S22][S23][S31][S32][S33][S36]

A case should usually **not** count as a true deviant case yet when the mismatch is mostly driven by:
- stale memo status,
- clearly weaker evidence architecture,
- a different claim level,
- or comparison-set admission that should probably have been denied in the first place.

## The archive's anomaly outcomes

A serious cross-case pass should usually classify the hardest deviant case into one of five outcomes.
Use one outcome only.

### 1. Not actually deviant after refresh or repair

Use this when the apparent anomaly mainly came from stale memo status, bad comparison-set admission, or a measurement mismatch that disappears once the comparison is repaired.
The pattern itself may survive unchanged.
The archive consequence is usually **comparison repair, not doctrine motion**.

### 2. Rail-dependent deviant case

Use this when the anomaly mostly reveals that the proposed pattern only travels under stronger named rails.
The pattern may still survive, but its portability tier should usually narrow and its required rails become less optional.

### 3. Case-family boundary marker

Use this when the deviant case shows that the pattern is real only inside a narrower family of cases.
The archive consequence is usually **case-family only**, not archive-wide portability.

### 4. Live contradiction under shared burden

Use this when the deviant case remains fresh, comparable, and genuinely contrary after repair.
Now the pattern-existence or mechanism-confidence label should usually weaken, and the doctrine-consequence burden should rarely rise.
If enough comparable contradictions accumulate, route the result through promotion quarantine or doctrine-repair governance rather than smoothing it away.[S15][S18][S19][S20][S21][S22][S23][S31][S32][S33]

### 5. Transfer blocker

Use this when the hardest deviant case does not merely narrow the pattern but blocks honest export beyond the compared set.
A retained pattern may still be useful locally.
It just should not travel further yet.

## What a cross-case note should output about deviant cases

Keep this block to four short lines:

1. **hardest deviant case** — name it, or say none yet
2. **why it strains the pattern** — one sentence only
3. **anomaly outcome** — one of the five outcomes above
4. **archive consequence** — repair comparison / narrow rails / narrow to case family / weaken confidence / block transfer

That is enough.
Do not turn deviant-case handling into a second comparison memo.

## How this block should change nearby archive calls

### If the anomaly is not actually deviant

Repair freshness, evidence, or set-selection problems first.
Do not let a false anomaly weaken a pattern the archive has not yet compared cleanly.

### If the anomaly is rail-dependent

The portability call should usually become narrower and the required rails should be named more sharply.
Often the most important lesson is not that the pattern failed, but that it never travelled without a rail the archive had treated too casually.

### If the anomaly marks a case-family boundary

The archive should usually stop export at **case-family only** and resist saying more until a wider comparison set exists.

### If the anomaly is a live contradiction

The pattern-confidence block should usually soften before doctrine consequence hardens.
A pattern with a serious live contradiction can still be useful, but it should travel less confidently and should very rarely rewrite doctrine yet.

### If the anomaly blocks transfer

The archive may retain the comparison as local or family-bound knowledge, but it should say **transfer blocked** plainly rather than letting a catchy pattern sentence keep travelling.

## What this note is meant to stop

### 1. Burying the hardest contrary case in footnotes

If a pattern survives only because the most difficult case never gets named, the archive is not doing comparison discipline.
It is doing curation by omission.

### 2. Treating every anomaly as fatal on first sight

Some anomalies are real contradictions.
Others are mostly freshness, measurement, or rail differences.
The archive should diagnose that before overthrowing a still-useful pattern.

### 3. Letting vivid anomalies dominate more than comparable ones

The hardest deviant case is not just the most interesting story.
It is the case that would most strain the pattern **under the same comparison burden**.

### 4. Letting portability outrun anomaly handling

A pattern should rarely be exported beyond the comparison set before the archive has said what its hardest deviant case is doing to the claim.

## Fast use rule

When a cross-case pattern seems to survive:

1. **Name the hardest deviant case.**
2. **Say in one sentence why it strains the pattern.**
3. **Classify the anomaly outcome.**
4. **Let that outcome narrow confidence, portability, or doctrine consequence before anything wider is exported.**
5. **Prefer honest narrowing to elegant overclaim.**

## Bottom line

The archive now has a thinner answer to a question that appears after rival explanations but before wider export:
**what should be done with the hardest case that does not fit the pattern cleanly?**
Name it, diagnose whether the anomaly is repairable, rail-bound, family-bound, contradictory, or transfer-blocking, and let that answer narrow what the archive says next.
