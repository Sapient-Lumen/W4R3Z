# Cross-case comparison and pattern extraction

## What this note is for

The archive now has strong rules for choosing, writing, monitoring, recertifying, capping, retiring, promoting, and repairing real-case memos.
What it still lacked was the thin bridge for a different job:
**how to compare several cases without turning the comparison itself into a shadow dashboard, a ranking game, or accidental doctrine.**

That gap matters because future archive work will eventually have more than one live case or exemplar.
Without a comparison rule, later revisions can drift in two bad directions at once:
- one vivid case quietly becomes the standard for all others,
- or a comparison memo starts rehosting a whole new scoreboard, package league table, or theory branch.[S15][S18][S19][S20][S21][S22][S23][S31][S32][S33]

This note gives the archive a compact way to compare multiple case memos and extract only the pattern that genuinely survives the comparison.
It is not a casebook and not a new doctrine note.
It is a **comparison discipline**.

## Minimum rule

Before comparing, use [`comparison-set-selection-and-non-comparability.md`](comparison-set-selection-and-non-comparability.md) so the archive states which candidate cases actually belong in the same retained set and which do not yet bear the same comparison burden.

A cross-case note should usually compare cases on the archive's **same small operator spine**, not invent a fresh metric universe for each round.
In ordinary use that means comparing only these things first:

1. **verdict**,
2. **dominant breach**,
3. **fastest washout**,
4. **mode**,
5. **opening package**,
6. **confidence posture**,
7. **watch posture**,
8. **next scoreboard / main evidence debt**.

If a comparison cannot stay mostly inside those lines, the archive usually does not need a bigger comparison memo yet.
It usually needs either:
- better single-case work,
- a clearer portfolio choice,
- or an honest doctrine question routed elsewhere.

## What cross-case comparison is allowed to do

A cross-case pass should normally do only one of three jobs.

### 1. Choose among candidate case work

When the archive is deciding which cases deserve memo space first, the comparison should help with **portfolio triage**, not with global ranking rhetoric.
Route that decision through [`case-portfolio-triage-and-memo-selection.md`](case-portfolio-triage-and-memo-selection.md) and [`case-portfolio-caps-and-retirement.md`](case-portfolio-caps-and-retirement.md).

### 2. Extract a recurring pattern

When two or more cases show the same dominant breach, washout channel, rail failure, or watch failure, the comparison may extract that recurring pattern in one paragraph.
The pattern should stay narrow enough that later work can still say what is local and what is not.

### 3. Put pressure on doctrine

When repeated case comparison keeps straining the same live rule, the comparison should not quietly become unwritten doctrine.
Route that pressure through [`../00-meta/case-to-doctrine-promotion-and-quarantine.md`](../00-meta/case-to-doctrine-promotion-and-quarantine.md) or [`../00-meta/doctrine-revision-and-demotion-under-case-pressure.md`](../00-meta/doctrine-revision-and-demotion-under-case-pressure.md), depending on whether the archive is learning something new or repairing something old.

## The archive's fixed comparison spine

A serious cross-case pass should usually hold each case to the same compact grid.
For each case, state only:

- **memo status** — live / live but refresh due / partly stale / recertify before soft reuse
- **verdict**
- **dominant breach**
- **fastest washout**
- **mode**
- **opening package**
- **confidence posture**
- **watch posture**
- **next scoreboard / main evidence debt**

That is enough to make most useful comparisons.
It is usually **not** necessary to restage full narrative history, every metric series, or the whole package rationale for each case.

## The first comparison cuts

Before comparing cases on policy appeal or numerical surfaces, cut on four upstream questions.

### 1. Are the memos comparably current?

Do not compare a freshly recertified case to an older memo that only survives as salvageable verdict memory.
Use [`case-staleness-and-recertification.md`](case-staleness-and-recertification.md) first.
If memo freshness is badly mismatched, the comparison should say so plainly rather than pretending the cases are equally live.[S04][S05][S06][S15][S20][S23][S31][S32][S33]

### 2. Are the evidence burdens comparable?

A case with strong verdict confidence but thin package confidence should not be compared as if its package call were as settled as a case with stronger package evidence.
Keep the archive's confidence labels separate rather than flattening them into one comfort score.

### 3. Are we comparing the same level of claim?

Do not compare:
- one case's **verdict** to another case's **package**,
- one case's **watch posture** to another case's **soft pass**,
- or one case's **rail feasibility** to another case's **moral target**.

Name the comparison level first.
Otherwise later readers infer more agreement than the archive actually earned.

### 4. Is the comparison for selection, pattern extraction, or doctrine pressure?

A cross-case note should say which of those jobs it is doing.
If it is doing more than one, split the output.
That keeps one comparison from quietly becoming queue discipline, doctrine repair, and scoreboard redesign at the same time.

## What should usually count as a real pattern

Treat a recurring pattern as stronger when it survives across cases that differ in visible surface features but keep converging on the same deeper failure.
Examples include:
- different cases with different headline shares but the same **rent-washout** problem,
- different policy packages that keep failing on the same **claimability** or **rail** problem,
- or different settings where softer readings keep collapsing because the same durability window is not survived.[S07][S13][S17][S18][S19][S20][S21][S22][S23][S31][S32][S33][S36]

Treat a pattern as weaker when it depends mostly on:
- one vivid jurisdiction,
- one unusually good or bad data series,
- one special legal structure,
- or one comparison built from mismatched memo freshness.

## The eight things a cross-case note should usually output

Keep the output narrow.
A good cross-case pass usually ends with only these eight blocks.

### 1. Comparison finding

One short paragraph saying what actually survived the comparison.
Examples:
- the same washout keeps undoing nominal gains,
- the same package family keeps failing under weak rails,
- or the cases really do split into different governing modes.

### 2. Pattern-confidence block

Add four short labels using [`pattern-confidence-and-export-burdens.md`](pattern-confidence-and-export-burdens.md):
- **pattern-existence confidence**
- **mechanism confidence**
- **portability confidence**
- **doctrine-consequence confidence**

That keeps recurrence, transfer, and doctrine pressure from being inferred by tone alone.

### 3. Rival-and-disconfirmation block

Add four short lines using [`pattern-rival-explanations-and-disconfirmation.md`](pattern-rival-explanations-and-disconfirmation.md):
- **main live rival explanation**
- **main measurement rival**
- **cleanest disconfirmation trigger**
- **next discriminating proof burden**

That keeps recurrence, portability, and doctrine pressure from hardening just because the comparison never named what would count against them.

### 4. Deviant-case block

Add four short lines using [`pattern-deviant-cases-and-anomaly-handling.md`](pattern-deviant-cases-and-anomaly-handling.md):
- **hardest deviant case**
- **why it strains the pattern**
- **anomaly outcome**
- **archive consequence**

That keeps a pattern from surviving only because its hardest contrary case never got named, and it keeps one apparent anomaly from doing more work than a clean comparison warrants.

### 5. Portability call

One short line saying what, if anything, actually travels:
- **portable core**,
- **portable only with named rails**,
- **case-family only**,
- **local only**,
- or **transfer blocked**.

If the lesson seems to travel, route that call through [`pattern-portability-and-transfer-limits.md`](pattern-portability-and-transfer-limits.md) rather than letting the comparison memo smuggle portability by tone alone. A portability claim should usually count for less if the main live rival or main measurement rival is still poorly discriminated, and it should usually count for less still if the hardest deviant case remains live, comparable, and poorly absorbed.

### 6. Saturation posture

One short line saying whether the comparison is:
- **too thin to talk about saturation**,
- **still needs one more decisive case**,
- **saturated enough for local or case-family claim**,
- **saturated enough for portable-core claim**,
- or **pattern may be saturated while doctrine still is not**.

Use [`pattern-saturation-and-stopping-rules.md`](pattern-saturation-and-stopping-rules.md) so the archive names the next most verdict-moving case if one still matters, or says plainly that continued case accumulation would mostly be drift. If no stable positive pattern survives after that, route the close through [`pattern-null-results-and-parking-rules.md`](pattern-null-results-and-parking-rules.md) before any wider consequence is even considered.

### 7. Archive consequence

One short line saying what follows:
- **portfolio choice**,
- **keep cases separate**,
- **extract one narrow bridge**,
- **pressure an existing doctrine note**,
- or **no archive promotion yet**.

### 8. Smallest next proof burden

One short line naming the smallest evidence that would most change the comparison.
Do not paste a full new dashboard here.
Use [`next-scoreboard-and-evidence-debt-selection.md`](next-scoreboard-and-evidence-debt-selection.md) to keep this burden thin.

## The main false moves this note is meant to stop

### 1. Building a shadow scoreboard

A comparison note fails when it starts inventing a new omnibus ranking table with many fresh indicators the archive does not use elsewhere.
If a new metric family is really needed, that is a scoreboard or doctrine question, not just a comparison note.

### 2. Letting vivid cases become law

One memorable case should not quietly become the archive's general rule just because later comparisons keep mentioning it first.
That is what the promotion and doctrine-pressure notes are for.

### 3. Flattening confidence into one number

A case can be highly comparable on verdict and weakly comparable on package choice.
Do not compress that into one neat score.
That only hides where the archive is actually uncertain.

### 4. Comparing packages without comparing rails

A package that looks elegant in one case may only work because the rails there are stronger.
Cross-case package comparison without rail comparison is usually theatre.[S04][S15][S23][S31][S32][S33]

### 5. Treating local anomaly as global lesson too early

Sometimes the correct output is simply:
**interesting case, no archive-wide pattern yet.**
The archive should prefer that sentence to a premature bridge or doctrine patch.

## Fast use rule

When comparing several cases:

1. **Recertify or narrow stale memos first.**
2. **Compare the cases on the fixed operator spine, not on a fresh metric universe.**
3. **Say whether the comparison is for selection, pattern extraction, or doctrine pressure.**
4. **Extract only the pattern that really survives the comparison.**
5. **Route any broader lesson through promotion or doctrine-repair rather than letting the comparison memo become doctrine by drift.**

## Bottom line

The archive now has a compact answer to a question that sat between single-case work and doctrine change:
**how should several cases be compared without turning the comparison itself into a warehouse, a scorecard arms race, or accidental law?**
Compare cases on the same small operator spine, extract only the pattern that genuinely survives, and route any larger lesson into the archive's explicit promotion or repair rules instead of letting it spread by comparison drift.
