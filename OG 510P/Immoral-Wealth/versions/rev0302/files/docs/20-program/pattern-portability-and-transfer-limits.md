# Pattern portability and transfer limits

## What this note is for

The archive now has a way to choose a comparison set and a way to extract a surviving cross-case pattern.
What it still lacked was the bridge that comes **after** that: 
**what part of the pattern is actually portable, what part is local, and what should block transfer entirely?**

That gap matters because a tight archive can fail in two opposite directions once several cases are on the table:
- it can over-export one pattern into doctrine or package advice that only worked under special rails, timing, or ownership structure,
- or it can quarantine every lesson so aggressively that repeated case work never yields a usable general lesson at all.[S04][S05][S06][S15][S18][S19][S20][S21][S22][S23][S31][S32][S33]

This note gives the archive a compact transfer rule.
It is not a new doctrine note and not a new package catalog.
It is a **portability screen** for cross-case lessons.
Use [`pattern-confidence-and-export-burdens.md`](pattern-confidence-and-export-burdens.md) alongside this note when the archive also needs to say how much confidence belongs to the portability claim itself and to any wider doctrine consequence.

## Minimum rule

A cross-case pattern is **not** portable just because it recurs.
It is portable only when the archive can separate four things cleanly:

1. **portable core** — the mechanism or operator lesson that appears to survive across cases,
2. **required rails** — the conditions that must exist for the lesson to travel honestly,
3. **local dependence** — what still seems to depend on local legal structure, asset mix, timing, or state capacity,
4. **transfer blockers** — what would make export actively misleading.

If those four lines cannot be written, the archive should usually stop at: 
**interesting recurring pattern, portability not yet certified.**
That is a disciplined output, not a weakness.

## What should usually count as the portable core

The archive should prefer portability claims about **mechanism, sequencing, rail need, and watch failure** before it makes portability claims about whole packages or whole doctrines.
Ordinarily the most portable thing is one of these:
- the same **dominant breach** keeps appearing,
- the same **fastest washout** keeps reabsorbing gains,
- the same **rail weakness** keeps breaking otherwise attractive packages,
- the same **watch failure** keeps making softer readings collapse,
- or the same **timing burden** keeps separating apparent gains from durable ones.[S07][S13][S15][S18][S19][S20][S21][S22][S23][S31][S32][S33][S36]

The archive should be more cautious about calling these portable:
- a whole lane mix,
- a whole jurisdictional implementation pattern,
- or a full doctrine repair.

Those larger claims usually require an extra step through promotion, quarantine, or doctrine-repair governance.

## The archive's portability tiers

Use one tier only.
The point is to make transfer discipline explicit rather than letting portability drift in by tone.

### Tier 1. Portable core

Use this only when the same lesson survives across cases that differ on visible surface features and still converge on the same mechanism.
The output here should stay narrow: usually one sentence on the portable mechanism and one sentence on the required rails.

Examples:
- rent-washout closes apparent lower-half gains unless housing and land closure are hit directly,
- claimant-burden and take-up friction can nullify formally broad programs even when the nominal entitlement looks generous,
- weak controller visibility blocks softer certification more often than it justifies it.[S10][S17][S20][S21][S22][S23][S31][S32][S33][S36]

### Tier 2. Portable only with named rails

Use this when the lesson seems real but only under explicit conditions.
Name the conditions.
Typical rails include:
- credible registries or visibility,
- low claimant burden,
- anti-seizure or non-forfeiture protection,
- public delivery capacity,
- anti-capture enforcement,
- or a timing window long enough to survive ordinary pressure.

If the rails are not named, this is not a portable lesson yet.
It is a flattering abstraction.

### Tier 3. Case-family only

Use this when the lesson travels only inside a narrower family of cases.
For example:
- owner-heavy housing systems,
- highly financialized asset structures,
- already-capture-heavy top tails,
- or weakly federalized welfare delivery systems.

This is still useful.
It simply should not be exported as archive-wide guidance for every case.

### Tier 4. Local only

Use this when the pattern seems mostly driven by local statute, one-off administrative design, one unusual subsidy path, or one specific asset composition.
The archive may still keep the insight inside the case memo or exemplar comparison.
It just should not travel further.

### Tier 5. Transfer blocked

Use this when the comparison itself is too freshness-mismatched, too proof-mismatched, or too rail-dependent to support honest export.
This tier should be easy to say.
It is what stops vivid cases from becoming archive law by momentum.[S04][S05][S06][S15][S20][S23][S31][S32][S33]

## The four questions to ask before exporting a pattern

### 1. Is the pattern a mechanism or just a package outcome?

Prefer export of mechanism first.
If what recurs is only that one package looked better in one place and worse in another, the archive usually still needs the explanation before it has a transferable lesson.

### 2. Are the enabling rails explicit?

A pattern is not portable if the rails do the real work but remain unstated.
For example, a package may travel only where registries are legible, tenant protections bite, or public delivery is not fragmented into claimant attrition.
Name that dependence or refuse the transfer.

### 3. What remains local?

Say which part still depends on local law, local asset mix, local housing structure, local public-finance design, or local political capture.
This is the archive's simplest guard against exporting a real but narrow lesson as if it were universal.

### 4. What would falsify the transfer?

Name the smallest future case or evidence pattern that would most strain the portability claim.
A portability call without a clear falsifier is usually just doctrine drift in a nicer tone.

## What a retained portability call should output

Keep it to four short blocks:

1. **portable core**
2. **required rails**
3. **local dependence / limits**
4. **transfer tier** — portable core / portable with named rails / case-family only / local only / transfer blocked

A fifth short line may name the **smallest next proof burden** if that is what would upgrade or downgrade the tier.
Do not turn this note into a second comparison dashboard.

## What should usually block transfer

Block or narrow transfer when one of these dominates:

### 1. Memo freshness mismatch

Do not export a common lesson from one fresh case and one mostly stale salvage memo as though both carried the same present-tense burden.

### 2. Proof mismatch that tracks data architecture more than reality

If one case is only more legible, not obviously more equal or more durable, the archive should not treat cleaner measurement as proof that a portable rule has been found.

### 3. Unnamed rail dependence

A pattern that only works under strong registries, low-friction delivery, protected minima, or unusual public capacity must say so.
Unstated rail dependence is one of the archive's main anti-transfer alarms.

### 4. Local legal exceptionalism

A lesson built on one unusual legal form, one pension architecture, one land regime, or one transfer rule may still matter.
It just may not travel.

### 5. Vividness doing more work than repetition

The archive should ask whether the pattern is surviving across cases or merely borrowing authority from one memorable case.
If vividness is doing the heavy lifting, stop the export.[S18][S19][S20][S21][S22][S23][S31][S32][S33]

## What this note is meant to stop

### 1. Smuggling full packages across cases

A lane mix that is sensible in one case can become theatre in another if the rails, asset mix, or capture structure differ.
Portable mechanism is not the same thing as portable package.

### 2. Letting pattern extraction become doctrine by atmosphere

Cross-case work should not quietly become archive-wide doctrine because a repeated sentence starts sounding familiar.
If the lesson has become strong enough for doctrine, route it through the archive's promotion or doctrine-repair rules.

### 3. Treating rail dependence as an embarrassing footnote

Often the most important portable lesson is exactly that a certain rail is decisive.
Do not hide that by exporting only the pleasant package headline.

### 4. Treating local dependence as failure

A lesson can be useful and still local, or useful and still case-family only.
The archive should prefer an honestly narrow transfer tier to a falsely general one.

## Fast use rule

When a cross-case pattern seems to travel:

1. **State the portable core in one sentence.**
2. **Name the rails without which that lesson does not travel honestly.**
3. **Name what remains local or case-family bound.**
4. **Assign one transfer tier only.**
5. **Route broader promotion or doctrine repair separately rather than letting portability prose do the doctrinal work.**

## Bottom line

The archive now has a thinner answer to a question that appears **after** comparison and **before** doctrine: 
**what part of a recurring cross-case lesson is actually portable, and what part must stay local, conditional, or blocked?**
Export the smallest real core, declare the rails, declare the limits, and prefer honest narrow transfer to elegant overreach.
