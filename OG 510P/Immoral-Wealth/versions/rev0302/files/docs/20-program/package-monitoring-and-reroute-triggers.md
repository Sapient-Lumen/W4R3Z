# Package monitoring and reroute triggers

## What this note is for

This note gives the archive a **thin live-package rule** for the period after an opening package has begun but before the full verdict should be rewritten.
The archive already has a rule for picking an opening package and a rule for reopening correction when softer verdicts decay.
What was still missing was the compact bridge in between:
**when a launched package is landing badly, washing out, or getting captured, what should trigger fast reroute rather than years of ceremonial patience?**

The archive's answer is that package monitoring should not be a vanity dashboard and it should not wait for full-cycle failure.
A serious monitoring rule should ask whether the package is:
1. reaching the intended entrants,
2. sticking long enough to become a foothold,
3. being washed back upward through rent, debt, fees, or markups,
4. being narrowed to insiders, households, or favored places,
5. being gamed or politically hollowed out,
6. or simply overreaching the current rails.[S07][S10][S15][S17][S18][S19][S20][S21][S22][S23][S31][S32][S33][S36][S39][S40]

## Minimum operating rule

A serious package-monitoring discipline should usually do **six things at once**:

1. **Watch only the decisive surfaces.** Monitor entrant passage, retention, washout, skew, capture, and rail strain rather than a long comfort dashboard.[S13][S18][S19][S20][S21][S22][S23][S31]
2. **Compare observed incidence with intended incidence early.** Do not assume the package is landing where the statute or model said it would.[S27][S28][S29][S30][S31][S36][S37]
3. **Classify the failure mode before changing the package.** Delivery failure, washout failure, capture failure, and rail overreach call for different repairs.[S07][S10][S15][S17][S20][S23][S31][S32][S33][S36]
4. **Reroute as soon as the dominant failure is clear.** Do not wait for the whole package to fail theatrically before adding the missing closure lane, simplification move, enforcement rail, or anti-capture hardening.[S15][S20][S21][S22][S23][S31][S32][S33]
5. **Harden the posture when sabotage or opacity is doing the damage.** Some failures are not implementation noise; they are evidence of wealth-to-rule pressure or blocked governability.[S15][S23][S31][S32][S33]
6. **Keep repair smaller than replacement when possible.** The default reroute should be the smallest effective correction that restores passage, durability, and closure rather than a full platform reset.[S20][S23][S31]

So the standing rule is:
**monitor the small set of surfaces that reveal whether the package is landing, name the dominant failure mode quickly, and reroute before washout or capture is allowed to write the story for you.**
When the package is landing rather than missing, hand off to [`hardening-gains-into-ratchets.md`](hardening-gains-into-ratchets.md) so early success is converted into harder institutional form rather than narrated as closure.

## The six main false passes

### 1. The package is judged by outputs announced, not footholds retained

A package fails when leaders report units spent, statutes passed, accounts opened, homes approved, or beneficiaries enrolled while the intended entrants still do not retain usable footholds through ordinary shocks.[S17][S18][S19][S21][S22][S31][S39][S40]

### 2. One flattering average hides skewed take-up or insider capture

A package counts less when its gains look broad only because the monitoring view is too aggregated to see household masking, person-level skew, excluded-group blockage, or place-based closure.[S13][S18][S19][S27][S28][S29][S30][S31]

### 3. Rising prices or tolls are treated as background noise rather than package failure

When housing costs, fees, debt service, or monopoly markups rise in the same lane the package was meant to broaden, the archive should treat that as a live washout problem rather than as irrelevant macro weather.[S07][S10][S17][S20][S21][S31][S34][S35][S36]

### 4. Delivery friction is misread as lack of need or lack of demand

A package fails when non-take-up, abandonment, churn, appeals bottlenecks, or renewal burden are interpreted as weak need rather than as evidence that the claiming machine or support machinery is too thin.[S21][S22][S27][S28][S29][S30][S31][S39][S40]

### 5. Avoidance, opacity, or sabotage is treated as a later enforcement issue

The archive should count less seriousness when top-tail avoidance, controller invisibility, procurement capture, litigation delay, or political dilution is allowed to continue while the package is still being graded as if clean implementation were underway.[S15][S23][S31][S32][S33]

### 6. Every disappointment is answered with a whole new platform

A package fails governance discipline when monitoring instantly turns into a maximal rewrite.
Most live-package failures should first be read as a question of missing closure, mis-specified incidence, missing rail, or underbuilt enforcement before the whole program is discarded.[S20][S23][S31]

## The standing monitoring and reroute stack

### 1. Monitor six surfaces, not a decorative dashboard

Every serious launched package should be watched on six surfaces:

- **entrant passage:** who actually gets through,
- **retention / durability:** who keeps the gain long enough for it to count,
- **washout:** where gains are being reabsorbed,
- **skew:** which persons, groups, households, or places are being left behind,
- **capture / gaming:** where the package is being arbitraged, diluted, or politically hollowed out,
- **rail strain:** where the package is outrunning visibility, staffing, appeals, valuation, or enforcement capacity.[S13][S15][S18][S19][S20][S21][S22][S23][S27][S28][S29][S30][S31][S32][S33]

The archive does not need dozens of indicators to know whether a package is landing.
It needs the small set that reveals whether the intended foothold is real, durable, and not quietly reabsorbed.

### 2. Sort failure into five recurring families

#### A. Delivery failure

The design is pointed at the right breach, but entrants are not getting through because claims, staffing, verification, appeals, timing, or renewal are failing.[S21][S22][S31][S39][S40]

Default repair:
- simplify claims,
- add automatic or pre-filled routes where appropriate,
- fund staffing and live support,
- widen access channels,
- shorten waits,
- and repair renewal or portability friction before changing the target lane.

#### B. Washout failure

The package lands, but housing, land, debt, fees, markups, or new scarcity absorb the gain fast enough that household security barely moves.[S07][S10][S17][S20][S21][S31][S34][S35][S36]

Default repair:
- add or harden lane **5**,
- pair gains with anti-capitalization rules,
- protect modest buffers from routine erosion,
- and treat the live washout channel as mandatory closure rather than as a secondary concern.

#### C. Skewed-incidence failure

The package lands mainly on insiders, incumbents, older cohorts, advantaged households, or favored places while the intended entrants still wait.[S13][S18][S19][S27][S28][S29][S30][S31]

Default repair:
- move design closer to person-level title or person-level receipt,
- narrow insider capture pathways,
- change outreach and adjudication toward blocked groups,
- reopen high-opportunity places,
- and tighten the monitoring cut so skew cannot hide inside the household or national average.

#### D. Capture or opacity failure

The package is being gamed, politically thinned, legally delayed, or shielded behind weak controller visibility and beneficial-ownership gaps.[S15][S23][S31][S32][S33]

Default repair:
- strengthen visibility and registry work,
- harden anti-capture firewalls,
- simplify where complexity is enabling arbitrage,
- and consider a harder governing posture when the failure is really blocked governability rather than ordinary noise.

#### E. Rail-overreach failure

The package asks more of valuation, staffing, procurement integrity, appeals, data linkage, or enforcement than the current state can honestly carry.[S04][S15][S23][S31]

Default repair:
- shrink the package to the smallest governable form,
- move easier floor, tenant, labor, or registry moves earlier,
- build the missing rails while moving,
- and stop selling gated tools as already ready.

### 3. Reroute by adding the smallest missing thing

The archive's bias is to **repair by the missing function** rather than by ideology.
That usually means:

- add **simplification and staffing** when the problem is delivery,
- add **closure against the live washout channel** when the problem is reabsorption,
- add **person-level passage and blocked-group repair** when the problem is skew,
- add **visibility, enforcement, and anti-capture hardening** when the problem is sabotage or opacity,
- add **honest gating and smaller sequencing** when the problem is rail overreach.[S15][S18][S19][S20][S21][S22][S23][S27][S28][S29][S30][S31][S32][S33]

This is why monitoring should not collapse into generic “implementation issues.”
The function that failed tells you what the reroute should be.

### 4. Use three trigger classes for live revision

Treat the need for reroute as present when any of the following appears:

- **one severe trigger:** a decisive washout channel opens, entrant passage collapses, controller visibility fails, or sabotage plainly blocks the package,
- **repeated moderate misses:** take-up, retention, price response, exclusion, or enforcement repeatedly diverge from the package story across the first monitoring windows,
- **design-to-outcome mismatch:** ex ante distribution looked broad, but observed incidence is persistently narrow, late, household-masked, or incumbent-biased.[S15][S20][S21][S22][S23][S27][S28][S29][S30][S31][S32][S33][S36][S37]

The archive does **not** require full constitutional failure before rerouting a package.
It requires enough evidence that the present package story is no longer the governing truth.

### 5. Escalate when live failure reveals blocked governability

Some reroutes should stay inside the same mode.
Others should harden it.
Escalate when monitoring shows that failure is being driven mainly by:

- concentrated veto power,
- controller invisibility,
- repeated crisis laundering or downside socialization,
- procurement or legislative capture,
- or reform sabotage strong enough that softer correction is no longer materially available.[S15][S23][S31][S32][S33]

At that point the lesson is not only “improve delivery.”
It is that the case may have moved deeper into **anti-oligarchy response** territory than the opening memo admitted.

### 6. Keep the reroute note short and comparable

A live reroute note should usually fit in a few lines:

- **package being monitored**,
- **dominant failure mode**,
- **main evidence of divergence**,
- **smallest repair or reroute now required**,
- **whether mode changes**,
- **next watch window and remaining proof debt**.

That keeps monitoring cumulative instead of turning every disappointing rollout into another essay.

## Fast operating rule

Use this note in five steps:

1. **Watch the six decisive surfaces early.**  
   Do not wait for a final evaluation cycle to find out that passage, retention, or closure is failing.
2. **Name the dominant failure mode.**  
   Ask whether the package is missing delivery, closure, person-level passage, anti-capture hardening, or honest rails.
3. **Add the smallest missing function.**  
   Repair the actual missing lane before replacing the whole package.
4. **Escalate when the failure is really blocked governability.**  
   Capture, opacity, and sabotage are not neutral implementation noise.
5. **Write the reroute note and reset the watch window.**  
   Say what changed, why, and which evidence would show the repair is landing.

Default shortcut:
- **delivery miss** -> simplify, staff, auto-route, support claimability;
- **washout miss** -> add closure against housing, debt, fees, or markups;
- **skew miss** -> redesign toward person-level and blocked-group passage;
- **capture / opacity miss** -> harden visibility, enforcement, and anti-capture, and consider a harder mode;
- **rail-overreach miss** -> shrink, gate honestly, and build capacity while moving.

## Non-substitution rule

Do **not** let any of the following excuse delayed reroute:

- high spending totals,
- favorable press or coalition rhetoric,
- one attractive headline metric,
- formal eligibility without real passage,
- temporary market calm,
- or a promise that the package will look better after a few more cycles.

Likewise, do **not** let live-package disappointment become an excuse for fatalism.
The archive's question is narrower and stricter:
**what failed first, what is the smallest effective reroute, and does the live failure reveal an implementation miss, a washout channel, or a deeper governability breach?**

## Bottom line

The archive should now read launched packages in this order:

1. **Ask whether the intended entrants are actually getting through.**
2. **Ask whether the gain is durable enough to count as a foothold.**
3. **Ask where the gain is being washed back upward.**
4. **Ask who is being skipped, masked, or closed out.**
5. **Ask whether capture, opacity, or rail strain is the real failure.**
6. **Then reroute by the smallest missing function before the package's narrative outruns reality.**

That is the archive's live-package discipline.
It stops the program from making two equal and opposite mistakes:
**celebrating announced progress long after it has washed out, or throwing away a sound direction before the actual missing closure, support, or rail has been honestly identified.**
