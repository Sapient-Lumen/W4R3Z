# Source refresh and citation compression

## What this note is for

This archive already has a strong rule for **which questions deserve bytes** and a strong rule for **how large different note types should be**.
It still needed one compact rule for a narrower but repeated curation question:

- when does a source earn a **new retained byte**,
- when does it earn only a **citation refresh**,
- and when should temporary source scratch be **thrown away before the long-run bundle is written**.

That matters because source growth can quietly become archive growth even when no theory branch is being added.
Without a compression rule, annual reports, narrow restatements, convenience PDFs, and revision-time scratch can slowly turn a tight archive into a source warehouse.

Use this note with [`archive-policy.md`](archive-policy.md), [`research-triage-and-closure-rules.md`](research-triage-and-closure-rules.md), [`archive-growth-budgets-and-refactor-triggers.md`](archive-growth-budgets-and-refactor-triggers.md), [`source-function-map-and-coverage-gaps.md`](source-function-map-and-coverage-gaps.md), and [`../../SOURCES.md`](../../SOURCES.md).

## The default rule

The archive should retain the **smallest durable source footprint** that still supports its live claims responsibly.

That usually means:
- keep the citation,
- keep the short relevance note,
- refresh the anchor when needed,
- and throw away the bulky retrieval path, temporary download, or intermediate extraction once the live claim has been carried forward.

The archive should keep **reusable support**, not a museum of every step taken to reach it.

## The three ways a source earns new retained bytes

A source should usually earn a new retained byte only when it does at least one of these things.

### 1. It covers a genuinely new moral surface

Keep it when it supports a live claim that the current source ledger does not already cover in a usable way.

Examples:
- a new source on beneficial ownership when the ledger only has broad wealth shares,
- a new source on claimant friction when the ledger only has statutory entitlement language,
- a new source on land-value capture when the ledger only has generic housing affordability discussion.

### 2. It materially strengthens a weak or stale anchor

Keep it when an existing anchor is too old, too indirect, withdrawn, broken, or no longer the best compact support for a claim the archive still actively uses.

This is a **replacement or strengthening** move, not a license to keep every vintage of the same claim.

### 3. It could move a live archive decision

Keep it when the new source could realistically change:
- a verdict,
- a package choice,
- a rail / gating judgment,
- a confidence label,
- or a provisional-pass / reopen posture.

If it would not likely move one of those, it usually does **not** earn permanent new bytes.

## The four common cases that do *not* earn new retained bytes

### 1. Same claim, newer wrapper, no real gain

A 2026 page repeating the same institutional point as a 2025 page does not automatically earn a new source ID.
If the newer item only refreshes the citation without improving the archive's support, update the existing pointer or note the newer anchor in place.

### 2. Annual churn without decision movement

The archive should not collect each annual release just because the series continues.
If the new edition does not materially change a live claim, prefer a citation refresh, a note-level wording update, or no retained change at all.

### 3. Convenience downloads and heavy mirrors

If the same claim can be supported by a stable public landing page, official summary page, or lighter canonical source, do not keep the heavier file just because it was easier to download during drafting.

### 4. Temporary scratch that solved only a local drafting problem

A scratch PDF, local extraction, copied table, or temporary note used to settle one revision-time question should be removed before packaging unless it now serves a repeated-use archive function.

## Citation compression rule

When a note is already well supported, the archive should prefer **citation compression** over source multiplication.

That means:

1. **Lead with the source that bears the claim most directly.**
2. **Add a second source only when it adds a distinct surface, a stronger bound, or a real conflict check.**
3. **Do not collect near-duplicate citations only to signal thoroughness.**
4. **Prefer replacing a weak anchor over stacking a stronger anchor beside it forever.**
5. **Prefer one compact relevance note in `SOURCES.md` over repeated mini-literature tours across many files.**

The archive should look **supported**, not **crowded**.

## Refresh in place versus new source ID

Use this fast rule.

### Prefer refresh in place when:
- the institution and substantive claim are basically the same,
- the newer item mainly updates dates, examples, or formatting,
- the older anchor is not broken or misleading,
- and the archive's decision posture would not change.

### Prefer a new source ID when:
- the new source covers a distinct live surface,
- the new source would replace a materially weaker anchor,
- the older source has become unavailable or no longer reflects the current institutional position,
- or the newer evidence could change the archive's actual judgment or routing.

If the answer is mixed, the default is usually:
**refresh the existing anchor first, and only mint a new source ID if the archive still lacks a distinct support function afterward.**

## Scratch lifecycle rule

Temporary scratch is allowed while producing a revision.
That can include PDFs, local notes, small extracted tables, or short-lived comparison files.

But before the long-run bundle is written, scratch should usually be forced through three questions:

1. **Did it produce a reusable claim the archive will keep citing?**
2. **Can that claim now be supported by a compact public citation instead of the scratch object itself?**
3. **Would a future revision likely need this exact local artifact again, or only the conclusion already carried forward into a note or source annotation?**

If the answer to the third question is no, the scratch should usually be removed.

The archive may keep the **claim**, the **citation**, and the **resulting note edit**.
It should usually not keep the temporary evidentiary scaffolding.

## Source-refresh triggers

A source refresh should usually be considered when one of these things happens:

- a cited link is dead, redirected badly, or withdrawn,
- a time-sensitive institutional claim has clearly been superseded,
- a live case memo now depends on a surface the current anchor only covers indirectly,
- the archive is leaning on a summary where a more direct official anchor is now available,
- or a conflict between sources now matters enough to affect verdict, package, rails, confidence, or watch posture.

Without one of those triggers, the archive should usually resist source churn.

## What a source update should say

When a revision changes source support materially, it should say briefly:

- which claim or surface needed stronger support,
- whether the move was a **new source**, a **replacement**, or a **refresh in place**,
- what existing source or note it strengthens, replaces, or leaves unchanged,
- and what temporary scratch was removed before packaging, if any.

That keeps source growth visible and auditable without making the archive keep every intermediate object.

## Bottom line

The archive should keep **enough live support to justify its claims and update them when necessary**, but it should resist turning each refresh, annual release, or drafting convenience file into permanent archive mass.

The standing bias is:
**refresh in place before adding, replace before stacking, and drop temporary scratch unless it has become genuine repeated-use doctrine or evidence.**
