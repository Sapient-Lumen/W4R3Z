# Note status and supersession discipline

## What this note is for

This archive now has explicit rules for **which questions deserve bytes**, **how big notes should be**, **which note in a cluster is the anchor**, and **when sources deserve retained weight**.
What it still needs is one compact rule for **what status a note currently has**, **when an older note should stop counting as live doctrine**, and **how to retire or shrink notes without leaving either dead links or undead guidance behind**.

Use this note with [`archive-policy.md`](archive-policy.md), [`archive-growth-budgets-and-refactor-triggers.md`](archive-growth-budgets-and-refactor-triggers.md), [`research-triage-and-closure-rules.md`](research-triage-and-closure-rules.md), and [`canonical-anchors-and-bridge-note-discipline.md`](canonical-anchors-and-bridge-note-discipline.md).

## Default rule

Every note should be treated as one of only a few statuses.
The archive should not leave status implicit.
When a note is no longer the place where a judgment mainly lives, the archive should **say so clearly** and either:

1. keep it as live support with a narrow role,
2. shrink it into a redirect / stub,
3. merge its living rule elsewhere,
4. or demote it out of the main route.

The archive should preserve usable memory, not let old routing fixes or partially replaced statements linger as if they still govern.

## The five standing note statuses

### 1. Live doctrine

A note is **live doctrine** when it still carries a rule the archive actively relies on for verdict, target, package choice, rails, confidence, or archive governance.

Live doctrine should usually be one of:
- a canonical anchor,
- a stable bridge that still finishes a repeated decision,
- or a compact governance note that still changes revision behavior.

Live doctrine belongs in ordinary routes and may be cited as current archive position.

### 2. Active bridge

A note is an **active bridge** when it is still live, but only as a subordinate operator or routing step under a parent anchor.
Its job is not to restate the doctrine but to help a reader finish the next decision cleanly.

An active bridge should state or imply:
- what upstream question should already be settled,
- what downstream decision it helps finish,
- and which anchor still outranks it.

### 3. Stable support note

A note is **stable support** when it still helps interpret the archive, but is not where a recurring decision mainly lives.
These are often companion notes, narrower diagnostics, or durable background clarifications.

Stable support may stay in the archive for reuse, but it should not quietly outrank the anchor or front-door route.

### 4. Ledger or question note

A note is a **ledger / question note** when it mainly records sources, open questions, revision memory, or other archive-maintenance state.
These notes may accumulate, but they should not be mistaken for live doctrine merely because they are current or detailed.

### 5. Superseded stub

A note is a **superseded stub** when its main living rule has moved elsewhere, but keeping a short redirect is still useful for continuity, old citations, or route memory.

A superseded stub should usually be very short.
It should say:
- what note now governs,
- what narrow residue, if any, still remains here,
- and whether the old note survives only for redirect / citation continuity.

A superseded stub should not keep enough prose to masquerade as current doctrine.

## What makes a note count as still live

A note should usually remain live only when at least one of these is true:

1. future revisions would still tighten **this note first** before adding new bytes elsewhere,
2. removing it would make a recurring decision materially harder to finish,
3. it still cuts repeated rereading across multiple cases or revisions,
4. or it carries a distinct rule that has not been cleanly absorbed by another live note.

If none of those is true, the note is often ready for demotion, merge, or shrinkage.

## Supersession triggers

Treat these as standing triggers to change status.

### 1. Anchor absorption trigger

If a parent anchor now states the rule cleanly enough on its own, a former bridge should often be demoted or folded back.

### 2. Route-bypass trigger

If front-door routes and real case work stop needing the note, but it still exists mostly because it once solved a problem, it is often a support note or a superseded stub now.

### 3. Redundant-rule trigger

If another live note now carries the same judgment more clearly, the older one should not remain equally live just because it arrived earlier.

### 4. Historical-memory trigger

If the main reason to keep a note is archive memory rather than present guidance, prefer a changelog entry plus a short redirect over a full undead note.

### 5. Byte-waist trigger

If keeping a formerly important note fully alive would widen the archive more than it now helps decision quality, demote or compress it.

## Redirect-stub rule

When a note is superseded but still worth keeping as a pointer, the archive should usually prefer:

- a short heading,
- a one-paragraph status explanation,
- a link to the current anchor,
- and, if genuinely needed, one sentence on what residue still belongs here.

Do not leave a near-full former note in place while also telling readers elsewhere that another file is now canonical.
That is how archives grow a second, accidental doctrine layer.

## Route discipline under supersession

`START_HERE.md`, `README.md`, and other front-door routes should normally point only to **live doctrine** and, where necessary, **active bridges**.
Stable support notes belong deeper in the module routes or index.
Superseded stubs should almost never appear in front-door reading paths unless the point of the route is to explain archive history.

## Closure discipline for old notes

Closing a question does not require deleting all the notes that helped resolve it.
But it usually does require changing their status.
Once a rule lives cleanly in an anchor or stable bridge, the archive should prefer:

- keeping one current live note,
- demoting older companions to support or redirect,
- and letting the changelog remember the transition.

The archive should avoid both extremes:
- **amnesia**, where earlier paths disappear with no trace,
- and **undead doctrine**, where obsolete or half-replaced notes still look current.

## Fast use rule

When touching an existing cluster of notes:

1. name which notes are still **live doctrine**,
2. identify which ones are only **active bridges**,
3. demote anything that survives mainly as history or route memory,
4. shrink superseded notes into redirects when continuity still matters,
5. and keep front-door routes pointed only at notes that still deserve authority.

## Bottom line

The archive should make it obvious not only **what its current doctrine is**, but also **which older notes still matter, in what way, and with what remaining authority**.

The standing bias is:
**keep live doctrine explicit, keep support notes subordinate, and turn obsolete guidance into honest redirects instead of undead doctrine.**
