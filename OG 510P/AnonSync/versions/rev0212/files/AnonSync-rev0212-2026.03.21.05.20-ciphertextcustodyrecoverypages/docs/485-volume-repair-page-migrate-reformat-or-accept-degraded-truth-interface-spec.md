# Volume repair page: migrate, reformat, or accept degraded truth interface spec

## Purpose

This page answers:

> is the honest next step to keep this degraded target, migrate the subject to a better volume, reformat the target, or intentionally accept the weaker ceiling; and what proof do we owe afterward?

The page exists because `fix`, `reconnect`, and `try another folder` are not enough truth when the real issue is target capability.

## Core rule

Every capability-limited target that materially narrows product promises must compile to one first-class **Volume repair** page before the product suggests high-cost moves.
That page owns:

- keep / migrate / reformat / accept-degraded decision
- rebuild and reindex cost
- non-effects and preserved facts
- postcondition proof
- repair receipt

## Primary layout

The page always renders the same regions:

1. repair verdict
2. option ladder
3. cost and non-effects card
4. postcondition-proof card
5. receipt and follow-on links

### 1) Repair verdict

Show:

- verdict label: `keep-degraded`, `migrate-subject`, `reformat-target`, `re-pick-target`, `wait-for-proof`, `unknown`
- strongest honest one-line summary
- main reason this verdict is recommended
- one safest next action

### 2) Option ladder

Show the reviewed options in strength order, such as:

1. keep current degraded target knowingly
2. move subject to a stronger target volume
3. reformat or rebuild target for required primitives
4. abandon this target and choose another

For each rung show:

- what improves
- what stays degraded
- what new cost is introduced
- what evidence would justify choosing it

The operator must be able to answer: **what are my real repair lanes here?**

### 3) Cost and non-effects card

Show:

- whether data bytes move
- whether metadata proof changes
- whether subject identity or hidden state is preserved
- whether reindex or rebuild is required
- strongest non-effect

The operator must be able to answer: **what expensive thing happens, and what surprisingly does not happen?**

### 4) Postcondition-proof card

Show:

- exact proof expected after repair
- what capability should now be native
- what action or affordance should now appear
- strongest unresolved doubt if proof is incomplete

The operator must be able to answer: **how will I know the repair actually changed the truth?**

### 5) Receipt and follow-on links

Link to:

- Volume capability
- Metadata fidelity
- Affordance ceiling

After any accepted action, emit a receipt that preserves:

- repair lane chosen
- costs acknowledged
- preserved versus replaced state
- postcondition checks promised or completed

## Honest outputs

This page may conclude:

- `accept degraded target knowingly; do not promise native metadata fidelity`
- `migrate subject to stronger volume; preserve bytes but widen capability ceiling`
- `reformat target only if stream-native semantics are required`
- `wait for proof; target class still unknown`

It may not reduce all of these to one generic `Move folder` or `Try another drive`.

## Rules

### Rule 1 — degraded acceptance is a first-class choice

The product must allow the operator to keep a weaker target knowingly rather than forcing fake optimism or unnecessary migration.

### Rule 2 — migration and reformat are different interventions

One moves the subject; the other changes the target.
Their costs and receipts must stay separate.

### Rule 3 — postcondition proof belongs in the same page

If the operator has to guess whether native capability was restored, the repair review failed.

### Rule 4 — unknown target class blocks strong repair advice

Do not recommend reformat or migration from rumor.
First prove the class and capability gap.

## Event language

Use explicit phrases such as:

- `degraded target accepted with explicit ceiling`
- `subject migration recommended because native primitives are unavailable here`
- `reformat only if native stream support is required`
- `repair incomplete; postcondition proof still missing`

Avoid vague lines such as:

- `storage problem fixed`
- `better drive recommended`
- `should work now`

## Non-clone reason

Current official Resilio docs are candid that some targets fall back, some actions disappear, and some volumes simply do not carry the stronger contract.
But the repair answer still lives in scattered folklore and old fix notes.
AnonSync should instead expose one Volume repair page where costs, ceilings, stronger targets, and proof stay adjacent.
