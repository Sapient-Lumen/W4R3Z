# Successor activation proof page — new seat handle, carried-forward subjects, and invalidated predecessor world

## Purpose

Prove exactly what became live after a reviewed successor import or seat-replacement action.

This page exists to answer:

- `what is live now?`
- `what predecessor was replaced or narrowed?`
- `which truths continued and which were reborn?`
- `what stronger continuity sentence is still blocked?`

## Required sections

### 1. Activation verdict

Must show:

- activation id
- resulting runtime/world id
- result class (`cold-successor-live`, `reborn-seat-live`, `inspect-only`, `blocked`, `partial`)
- recorded time

### 2. New live seat block

Must show:

- live seat handle / certificate / proof-handle family
- whether it is identical to predecessor, reborn from predecessor, or unrelated
- confidence class

### 3. Carried-forward continuity block

Must list separately:

- subject roster continued
- policy continued
- receipts preserved
- approval memory narrowed or rereviewed
- helper/cache residue dropped or recomputed
- any stale or refused components

### 4. Predecessor invalidation block

Must show:

- predecessor seat or world reference
- whether it was stopped, hidden, revoked, inspect-only, unknown, or not proven retired
- whether concurrent reuse remains blocked

### 5. Strongest safe sentence

Examples:

- `A reviewed replacement seat is now live with carried-forward subject state; predecessor same-seat continuity was not claimed.`
- `Subject policy continued, but trust memory was narrowed pending rereview.`

### 6. Follow-up obligations

Must link to any still-required:

- predecessor retirement
- trust reapproval
- route/cache recomputation
- seat rename or device labeling
