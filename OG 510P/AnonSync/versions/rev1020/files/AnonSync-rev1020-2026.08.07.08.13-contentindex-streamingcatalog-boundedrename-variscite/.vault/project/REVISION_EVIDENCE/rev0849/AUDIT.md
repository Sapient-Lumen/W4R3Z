# AnonSync rev0849 audit

## Audit target

This revision audits retained SQLite callback lifetime as an authority problem,
not merely as callback registration syntax. The reviewed path is:

1. adopt one exact FULLMUTEX database generation in `SyncSqliteDbHandleSlot`;
2. mint one exact serialized generation borrow;
3. attach a named connection client-data lifetime claim;
4. register the retained callback address;
5. execute only within the callback owner's process/thread contract;
6. revoke the callback;
7. synchronously detach the named claim; and
8. release the generation borrow before closing the connection owner.

## Findings corrected

### Critical: double close in exceptional pending-report cleanup

The old nested catches both received the same raw `sqlite3*`. The inner catch
could close it and rethrow without nulling it; the outer catch could then call
`sqlite3_close_v2()` on freed storage. Rev0849 replaces this with a typed owner
whose reset consumes the handle once. The failure order is now progress-handler
detach, transaction rollback while the database is still live, then owner reset.

### High: progress callback had no exact-generation pin

`SqliteVerificationBudget` retained its own address inside SQLite but accepted a
raw database pointer. Thread affinity did not prove connection lifetime or
connection generation. It now consumes `SyncSqliteSerializedDbBorrow`, retains
that exact generation for its whole callback lifetime, and releases it only
after callback and client-data revocation.

### High: one-off busy-handler sentinel invited policy drift

The busy-handler owner had a sound but private client-data claim state machine.
Duplicating that mechanism for progress handlers would create two subtly
different close/replacement protocols. The state machine, process binding,
magic/self checks, lock-free state, and exact-thread destruction witness now
live in `SqliteRetainedCallbackClaim` and are shared by both owners.

### Medium: raw resident-snapshot opens amplified cleanup risk

`SealedSqliteSnapshot::open_database_or_throw()` returned raw ownership. New
production verification paths use `open_database_owner_or_throw()` and
`SyncSqliteDbHandleSlot`, preserving the exact connection generation through
verification and making close idempotent.

### Medium: release inventory did not require the extracted owner

A self-consistent archive could have omitted the new callback-claim files until
a later build exposed the omission. The verifier now makes them mandatory from
revision 849 onward while continuing to validate the sealed rev0848 parent.
Snapshot-seal tests and its audit are also explicit global package members.

### Waste corrected: generated audit bytecode entered the active tree

Final patch replay found `tools/__pycache__/...pyc` generated by audit execution.
It was removed before projection and packaging. Release hygiene rejects Python
bytecode, build output, VCS metadata, symlinks, and other generated residue.

## Remaining architectural risk

SQLite provides no progress-handler getter. A foreign raw
`sqlite3_progress_handler()` call can replace the callback without a direct
runtime query to detect it. The current defense is typed connection ownership,
source inventory, and structural audits. A longer-term connection callback
registry should own all singleton callback slots together and make replacement
an explicit typed transition.

The shared claim protects destruction and named-slot replacement, but it is not
a universal concurrency proof. Callers must still quiesce connection use before
teardown. A raw `sqlite3_close_v2()` with outstanding statements can create a
zombie connection; this is deliberately documented and tested rather than
misrepresented as synchronously detectable by client data.
