# Remedy-landing review page — did the right repair land in the right place for the right object?

## Decision question

This page answers one operational question:

**Did the cure that finished moving actually land as the intended repaired object, in the intended operative target, for the required cohort — or are we still relying on duplicate paths, placeholders, archive rebounds, unreadable backups, or operator memory about where the fix really went?**

## Review sections

### 1) Finished transfer versus target-bound landing

The review must begin by comparing the already-proven finish protection with the stronger landing claim actually available now.
It must show:

- what bytes or objects finished
- what target they were supposed to bind to
- whether binding is verified or still ambiguous
- what stronger landing sentence is still blocked

### 2) Path and object identity audit

The page must separate:

- intended target path
- actual landing path
- duplicate-directory creation risk
- side-path reconnect risk
- local-only rename caveat
- target mismatch across cohorts

### 3) Landing material class audit

The review must show what actually landed, including:

- full readable content
- placeholder-only shell
- archive-backed rebound copy
- encrypted unreadable survivorship
- merge into pre-existing directory
- `.sync` continuity and final-name adoption

### 4) Cohort-specific landing scope

The page must model which cohorts have true operative landing and which remain weaker.
It must separate:

- named pilot cohort
- currently connected cohort
- required cohort
- placeholder-only cohort
- duplicate-path cohort
- encrypted-only or substrate-only cohort

### 5) Highest honest sentence

The page must always conclude with one highest honest sentence from this family:

- `landing requested`
- `bytes finished pending target-bind verification`
- `landed in duplicate or side path`
- `landed through merge into pre-existing target`
- `landed as placeholder-only shell`
- `landed unreadable or encrypted only`
- `landed via archive rebind pending adoption`
- `landed for named cohort`
- `landed for required cohort`
- `landing misbound`
- `landing verification collapsed`

It must also name the blocked stronger sentence and why it remains blocked.

## Review invariants

- the review never lets finished transfer impersonate target-bound landing
- the review never lets folder visibility impersonate operative adoption
- the review never lets placeholder presence impersonate readable landed repair
- the review always names the exact blocker that prevents the stronger landing sentence
