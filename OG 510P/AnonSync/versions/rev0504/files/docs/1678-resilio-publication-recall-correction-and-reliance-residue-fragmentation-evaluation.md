# Resilio publication-recall, correction, and reliance-residue fragmentation evaluation

## Claim

Current official Resilio docs are still admirably candid that `disconnect`, `remove`, `future updates suspended`, `already synchronized files remain`, `archive retention`, `history`, and `encrypted unreadable custody` are not one flat recall truth.
That candor is useful.
It is also exactly why AnonSync should not clone the present contract.

The missing product object is now sharper than publication-and-reliance grade:

> after the product knows **who saw which version of an act and what they were allowed to rely on**, it still needs one first-class answer to **what can later be corrected, withdrawn, or narrowed, who was actually reached by that correction, and what prior reliance residue still survives even after publication is recalled**.

Current Resilio materials still do not provide one typed recall object for:

- stopping future publication without pretending already-disclosed bytes were extinguished
- distinguishing `new reliance revoked` from `historic reliance residue still survives`
- proving which audiences were actually reached by a correction or retraction
- distinguishing `withdrawn from Sync UI`, `future sync halted`, `deleted locally`, and `semantic claim clawed back`
- preserving audit-grade trace while narrowing ordinary reliance
- distinguishing recoverable historical trace from an actually erased sentence
- showing when the product should admit that some prior viewers may still retain bytes or knowledge beyond the current allowed publication set

Instead, the operator still has to translate disconnect dialogs, archive settings, history rows, and encrypted-host caveats into recall meaning.

## What current official docs still say

Current official docs still jointly show all of the following:

- `Disconnecting and Removing Folders` still says disconnect stops syncing but leaves the folder in the file system, and removing a folder from Sync also leaves it in the file system on desktop.
- `User Management` still says disconnect revokes access and suspends future updates for that peer, but all files already synchronized so far remain in the folder.
- `Folder Preferences` still says remotely changed or deleted files are copied into `.sync/Archive` by default for 30 days, and that disabling Archive stops that preservation behavior.
- `Using Archive for file versioning and restoring deleted files` still says Archive does not identify which peer made changes and that History must be used for that detail.
- `Sync Main View (Desktop)` still says History shows general syncing activity for the last 30 days.
- `Encrypted folders` still says an untrusted device can hold encrypted bytes without revealing readable contents.

This is strong operational candor.
It is not a first-class publication-recall contract.

## Why this still fragments the decisive answer

One ordinary fairness answer still requires stitching together several docs and surfaces:

- whether the old publication is merely blocked from future updates or actively corrected for already-reached viewers
- whether a correction reached every required audience or only some of them
- whether already synchronized files, screenshots, exports, or mirrored linked-device views still leave surviving reliance residue
- whether archive or history preserves enough trace for adjudication even after a retraction
- whether encrypted or unreadable custody still means old bytes survive somewhere without semantic access
- whether the product may honestly say `recalled`, `corrected`, `narrowed`, `withdrawn`, or only `future flow stopped`

That means current official materials can help answer `will this peer keep syncing`, `did files remain on disk`, `is archive enabled`, or `can history still show something?`
They still do not directly answer `what exactly was clawed back, who was reached, and what prior reliance residue still survives?`

That gap is exactly where AnonSync should refuse cloning.

## Hard replacement line for AnonSync

AnonSync should borrow the useful ingredients:

- explicit separation between future synchronization and already-delivered bytes
- explicit archive / version-retention controls
- visible history trace and its horizon limits
- explicit unreadable encrypted custody for infrastructure peers
- visible permission and disconnect routes

But AnonSync should replace the page contract with a first-class **publication recall and reliance residue** object where each typed act has its own:

- recall target set
- correction / retraction / narrowing class
- reached-vs-unreached audience ledger
- surviving reliance residue class
- audit-trace preservation class
- stronger blocked erasure sentence
- recall lineage receipt

## Product decision tightened here

The new design line is:

- **retracted publication is weaker than extinguished reliance**
- **future flow stopped, corrective publication reached, reliance narrowed, audit trace preserved, and prior semantic residue surviving are separate public truths**
- **already delivered bytes and already learned semantics cannot be silently flattened into `revoked access`**
- **correction reach must be proved audience by audience**
- **the product must preserve what stronger `fully clawed back` or `fully erased` sentence remained blocked**

## Consequence for the non-clone score

Resilio still belongs on the borrow side for disconnect candor, archive controls, history presence, and encrypted-custody honesty.
Resilio remains on the non-clone side for the fairness-critical recall contract.

The reason is now precise:

> current Resilio docs still expose disconnect, remove, archive, history, and encrypted-host behavior as separate operational facts rather than one typed recall object for `correction issued`, `retraction reached`, `future publication halted`, `reliance narrowed`, `audit residue preserved`, and `extinguished sentence still blocked`, so the operator still has to reconstruct whether anything was truly clawed back from scattered traces instead of one owned interface family.
