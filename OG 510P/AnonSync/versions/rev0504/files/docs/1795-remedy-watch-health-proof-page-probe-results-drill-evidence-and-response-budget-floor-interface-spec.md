# Remedy-watch-health proof page — probe results, drill evidence, and response-budget floor

## Purpose

This page is the proof bundle behind the claim that a discharged case's relapse guard is still credible right now.
It exists so later readers can inspect probe freshness, drill results, and response-budget evidence instead of inferring them from quiet surfaces or a support workflow.

## Proof bundle

The proof page must preserve evidence for:

- source remedy-surveillance result
- required guarded cohort
- actually probed cohort
- actually drilled cohort
- platform blind-spot evidence
- runtime blind-spot evidence
- signal-family freshness evidence
- notification-surface evidence
- history-window evidence
- logging posture evidence
- canary-probe execution evidence
- end-to-end drill execution evidence
- measured response-budget evidence
- strongest honest watch-health sentence
- strongest blocked stronger ordinary-life sentence

## Proof sentence families

The page must support concise summaries such as:

- `the case remained discharged, but watch-health was stale because the required-cohort canary probe aged past its ceiling`
- `the required cohort passed the canary probe, but the last end-to-end re-fence drill exceeded the allowed response budget`
- `the case stayed honestly in ordinary life because the required cohort passed a recent probe and recent drill inside budget, with declared Linux blind spots excluded from the stronger sentence`
- `watch health degraded when watcher fallback moved detection to periodic rescan and no fresh proof re-established the old response budget`
- `logging remained available for diagnosis, but that was weaker than recent case-scoped drill evidence`

## Stronger-sentence blockers

The page must explicitly name blockers such as:

- probe missing
- probe stale
- drill missing
- drill stale
- response budget exceeded
- required cohort not covered
- platform blind spots too broad
- runtime blind spots too broad
- evidence basis too weak
- watch-health collapse

## Evidence handling rules

The proof page must never let these substitute for stronger proof:

- a single quiet UI surface
- one synchronized notification
- one log toggle without fresh capture
- one historic success outside the freshness ceiling
- one named-cohort pass when required-cohort proof is demanded
