# Remedy-hardening-baseline proof page — default absorption, arrival inheritance, and scaffold-retirement floor

## Purpose

This page is the proof bundle behind the claim that a case which already achieved bounded rollout may let later arrivals inherit the hardened behavior as the continuing safe baseline.
It exists so later readers can inspect future-arrival surfaces, baseline sources, temporary scaffold retirement, and exception scars instead of inferring them from linked-device convenience and folder defaults.

## Proof bundle

The proof page must preserve evidence for:

- source remedy-hardening-rollout result
- triggering cause family
- current hardening or change class
- named current protected cohort
- named future-arrival surfaces
- required future-arrival cohort
- linked-device future-arrival inheritance evidence
- Standard-versus-Advanced future-admission evidence
- key-versus-link admission evidence
- default path and arrival-binding evidence
- synchronization-mode inheritance evidence
- configuration-mode coverage evidence
- per-folder preference inheritance evidence
- temporary rollout scaffold inventory evidence
- scaffold retirement evidence
- baseline scar or carry-forward exception evidence
- highest honest current baseline-assimilated sentence
- strongest blocked stronger baseline-assimilated sentence

## Proof sentence families

The page must support concise summaries such as:

- `the rollout stayed bounded, but baseline assimilation is still blocked for future arrivals`
- `future arrivals are safe only through named lanes; linked-device or Standard-key semantics still block a stronger sentence`
- `temporary rollout scaffolds still carry the safety story, so ordinary-baseline language remains dishonest`
- `the new hardening is now baseline-assimilated for the required arrival surfaces, with the remaining scars explicitly preserved`
- `future-arrival safety collapsed after baseline drift or scaffold reintroduction`

## Stronger-sentence blockers

The page must explicitly name blockers such as:

- future-arrival surface not formally bounded
- linked-device inheritance still unsafe
- Standard-folder or key-based admission unresolved
- default arrival path ambiguous
- synchronization-mode inheritance incomplete
- per-folder preference inheritance too narrow
- config-mode baseline coverage too narrow
- temporary scaffold still required
- scaffold retirement not proven
- evidence basis too weak

## Evidence handling rules

The proof page must never let these substitute for stronger proof:

- one successful bounded rollout without future-arrival evidence
- one default folder path without admission-surface proof
- one linked-device inheritance story without one-way or Standard-key accounting
- one manual detour without scaffold retirement evidence
- one aligned desktop preference without cross-surface baseline proof
