# Remedy-hardening-attestation catastrophe-recovery lineage receipt page — anchor scope, reconstitution class, and blocked stronger sentences

## Purpose

This page is the durable receipt for the strongest honest catastrophe-recovery sentence after reviewing one or more destructive events and recovery paths.
It is the page a later operator opens when they need to know what was lost, what anchors survived, whether the same governed world was reconstituted or replaced, and which stronger sentence remained blocked.

## Required receipt fields

The receipt must preserve:

- catastrophe-recovery identifier
- source durable or regime-shift receipt identifier
- named governed slice
- named catastrophe class
- current catastrophe-recovery class
- bytes retention status
- database-lineage retention status
- key or secret retention status
- identity retention status
- `.sync` capsule retention status
- storage-root retention status
- supported recovery-path status
- forced-regeneration status
- safe successor-world identifier if any
- highest honest catastrophe-recovery sentence
- strongest blocked stronger sentence
- exact blocker summary
- next evidence needed for upgrade
- next evidence that would force downgrade
- issuance timestamp
- issuer identity

## Canonical sentence families

The receipt must support at least these sentence families:

- the target state was previously durable, but catastrophe recovery has not been reviewed
- bytes were recovered for the named slice, but governing continuity remains unproven
- the named catastrophe is recoverable only if the retained keys, database lineage, and other anchors remain available
- the slice is usable again, but `.sync` or instance-capsule loss forced a new synchronization instance
- the catastrophe was answered by safe successor-world re-foundation, not same-world recovery
- the named catastrophe was recovered for the named slice only
- same-world reconstitution is proven for the named slice only
- broader all-catastrophe continuity or universal recoverability is blocked

## Hard rules

- The receipt must never collapse `usable again` into `same world restored`.
- The receipt must never collapse `new instance works` into `old instance survived`.
- The receipt must never collapse `keys existed somewhere` into `all anchor requirements were satisfied`.
- The receipt must never collapse `reinstall and relink succeeded` into `continuity was preserved`.
- The receipt must never collapse `clone did not visibly fail yet` into `supported recovery`.
