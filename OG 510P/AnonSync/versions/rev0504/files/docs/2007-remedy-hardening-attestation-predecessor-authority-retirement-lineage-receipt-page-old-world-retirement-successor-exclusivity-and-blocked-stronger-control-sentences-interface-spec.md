# Remedy-hardening-attestation predecessor authority retirement lineage receipt page — old-world retirement, successor exclusivity, and blocked stronger control sentences

## Purpose

This page is the compact receipt a product can carry forward after reviewing whether the predecessor world can still act.
It exists so downstream users can quote one durable object instead of reconstructing exclusivity from scattered resets, revokes, rotations, and unlink lore.

## Receipt body

Every predecessor-authority-retirement receipt must contain:

- receipt identifier
- predecessor-authority-retirement case identifier
- source successor-reference-rebinding receipt identifier
- predecessor world identifier
- successor world identifier
- governed slice identifier
- current predecessor live-capability class
- current split-world status
- current quarantine scope
- current successor exclusivity class
- highest honest public sentence
- strongest blocked stronger sentence
- specific contradiction set that blocks the stronger sentence
- next evidence needed for upgrade
- downgrade trigger set
- receipt issue time
- receipt expiry or mandatory re-review horizon

## Allowed highest honest public sentences

The receipt may expose sentences such as:

- successor legitimate, predecessor authority not yet reviewed
- successor canonical, predecessor still active
- predecessor authority reduced on named surfaces only
- predecessor quarantined for named slice only
- successor exclusive controller for named slice only
- predecessor actuation extinguished for named slice only, broader universal exclusivity blocked
- off-world predecessor authority unresolved, stronger control claims blocked

## Forbidden upgrades

The receipt must never allow:

- `successor exclusive controller` without a visible scope
- `predecessor retired` without a visible surface or slice
- `control fully transferred` when any contradiction set remains
- `old world gone` when only discovery moved
- `universal exclusivity` when off-world or split-world actuation remains unresolved

## Receipt downgrade triggers

The receipt must automatically become stale or downgraded when:

- any predecessor actor is observed writing, deleting, sharing, or serving again
- an old-key cohort is observed still syncing
- a copied handle is shown to admit new dependents
- a supposedly retired device or world reappears as an active actor
- service-world or rebuilt-instance evidence creates a fresh split-world lane
- new off-world authority evidence appears
