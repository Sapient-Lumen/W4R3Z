# Remedy-hardening-attestation regime-shift proof page — transition matrix, world continuity, and robustness ceiling

## Purpose

This page is the evidence-heavy proof surface for determining whether a durable target state survives one or more named regime shifts.
It proves the exact ceiling on any sentence that tries to say the durable state is not merely stable in the current world, but robust across upgrades, migrations, account changes, storage relocation, or control-surface substitution.

## Required evidence blocks

### 1. Durable basis ledger

Preserve:

- source postcondition-durability receipt
- target postcondition sentence
- governed slice
- current durable class before transition

### 2. Transition matrix ledger

For each named transition preserve:

- transition class
- supported, conditional, blocked, or unsupported status
- exact prerequisites for preserving the prior governing world
- exact reasons the path forks into a new world if it does

### 3. World-continuity ledger

Preserve:

- principal or service-account continuity
- identity continuity
- storage-root continuity
- launch-parameter continuity
- folder-class continuity
- control-surface continuity
- version-family and license-family continuity

### 4. Transition witness ledger

Preserve:

- before-and-after witnesses for the named transition
- surviving slice after transition
- re-share, reconnect, or rebind steps required
- continuity receipts for storage and identity
- contradictions or losses observed after transition

### 5. Unsupported shortcut and collision ledger

Preserve:

- clone or image-copy attempts
- multi-instance twin risks
- unsupported family or install-style transitions
- manual recovery dependencies
- resulting downgrade class

### 6. Claim ceiling

Render:

- highest honest same-world transition sentence
- highest honest named-transition survival sentence
- highest honest transition-set survival sentence
- blocked stronger all-transition sentence and exact blocker

## Evidence classes

The page must distinguish at least:

- pre-transition durability only
- supported path with prerequisites not yet satisfied
- supported path witness missing
- same-user-and-storage-dependent survival only
- service-account or storage-world fork exposure
- config-mode or control-surface override exposure
- folder-class continuity blocked
- unsupported clone-derived transition
- named transition survived for named slice only
- named transition set survived for governed slice
- broader all-transition robustness blocked

## Hard rules

The proof page must never treat:

- a pre-transition durable receipt as proof of post-transition survival by itself
- byte continuity as proof of identity or share continuity
- a new WebUI or service screen as proof that the same governing world persisted
- a cloned instance as if it were a supported continuity witness
- one successful transition class as proof for different transition classes
