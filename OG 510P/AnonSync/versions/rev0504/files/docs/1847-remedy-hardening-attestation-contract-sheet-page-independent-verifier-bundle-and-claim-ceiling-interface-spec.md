# Remedy-hardening-attestation contract sheet page — independent verifier bundle and claim ceiling

## Purpose

This page is the operator's compact contract for whether a case that already achieved recurrence-hardened-retained-change-gated-rollout-bounded-baseline-assimilated-and-bootstrap-reproducible discharge may honestly claim that the same safety posture is independently verifiable from one durable bundle.
It exists so the product can distinguish `the current operator believes the case is safe` from `a later verifier can inspect one exported bundle and confirm the strongest honest sentence without relying on folklore`.

- case identifier
- source remedy-hardening-bootstrap receipt identifier
- triggering cause family

- required verifier cohort
- attestation bundle identifier
- bundle generation time
- evidence freshness horizon
- evidence expiry horizon

- platform and version lane coverage status

- explicit scars and blocked-sentence inclusion status
- highest honest current verifier-ready sentence
- strongest blocked stronger verifier-ready sentence
- next strengthening trigger
- next weakening trigger

## Remedy-hardening-attestation posture rungs

The page must model at least these distinct rungs:

- safe current world only
- bootstrap reproducible but not attested
- evidence bundle partial
- operator-memory-dependent handoff
- verifier-ready for named lanes only
- successor handoff ready with scars preserved
- independently verifier-ready for required cohort
- externally challengeable but still standing
- attestation stale or horizon-expired
- attestation collapsed or revoked

## Required distinctions

The page must keep these truths separate:

- safe claim versus verifier-ready claim
- evidence bundle present versus evidence bundle sufficient
- debug logs collected versus log provenance adequate
- short-window history versus durable attestation lineage
- settings snapshot versus invariants and scars snapshot
- successor handoff ready versus independent third-party verifiable
- named-lane verifier readiness versus required-cohort verifier readiness
- current bootstrap proof versus later attestation freshness

## Operator promises

The contract sheet must let the operator say things like:

- `the case is safe and reproducible, but not yet independently verifier-ready`
- `attestation is honest only for named lanes and within the current freshness horizon`
- `logs exist, but provenance remains too operator-shaped for the stronger sentence`
- `a successor can inherit this case honestly with scars preserved`
- `the case is now independently verifier-ready for the required cohort, with scars and expiry preserved`

## UI behavior

The page must visually scar any blocked stronger sentence with the exact blocker class:

- evidence horizon too short
- history horizon too weak
- log provenance too operator-controlled
- storage snapshot incomplete
- rebuild proof missing
- folder-type or lane coverage incomplete
- operator-memory dependence still present
- scars or blocked stronger sentences omitted from export
