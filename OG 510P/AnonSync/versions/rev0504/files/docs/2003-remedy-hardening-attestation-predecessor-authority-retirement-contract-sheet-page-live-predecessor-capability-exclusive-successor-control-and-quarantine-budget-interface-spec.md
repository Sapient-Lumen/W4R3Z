# Remedy-hardening-attestation predecessor authority retirement contract sheet page — live predecessor capability, exclusive successor control, and quarantine budget

## Purpose

This page is the compact contract for deciding whether a successor world that is already legitimate and discoverable has also become the only actor that may still control, mutate, publish, seed, or revoke for the named slice.
It exists so the product can distinguish `successor legitimate`, `successor canonical`, `predecessor still active`, `predecessor quarantined for named slice`, `exclusive successor control for named slice`, and `broader universal exclusivity still blocked`.

- predecessor-authority-retirement identifier
- source successor-reference-rebinding receipt identifier

- successor-world identifier

- authority rulebook version

- predecessor seed or serve capability status
- predecessor discovery or intake capability status

- predecessor copied-handle actuation status

- disablement or expiry evidence set
- successor exclusivity class
- highest currently safe exclusivity sentence

- next fact that collapses retirement standing now

## Predecessor live capability classes

The page must model at least these distinct classes:

- predecessor capability unreviewed
- predecessor known present, live capability unknown
- predecessor can still write or mutate
- predecessor can still share or admit dependents
- predecessor can still seed, serve, or relay bytes
- predecessor can still revoke or interfere
- predecessor can still attract dependents through copied handles
- predecessor disabled for named surface only
- predecessor quarantined for named slice only
- predecessor actuation extinguished for named slice only
- broader universal retirement blocked

## Authority surface types

The page must preserve at least these distinct surfaces:

- write or delete surface
- rename or replace surface
- permission or membership surface
- share or invite surface
- key or handle distribution surface
- read, seed, or serve surface
- notification or publication surface
- reconnect or rejoin surface
- copied-off-world handle surface
- unknown historical authority surface

## Successor exclusivity classes

The page must support at least these classes:

- successor legitimate, exclusivity unreviewed
- successor canonical, predecessor still active
- successor exclusive for internal governed slice only
- successor exclusive for write surface only
- successor exclusive for publication surface only
- predecessor quarantined but off-world authority unresolved
- split-world still active
- predecessor extinguished for named slice only
- broader universal exclusivity blocked

## Fixed rendering order

Every predecessor-authority-retirement contract sheet must render the same sections in the same order:

1. **Strongest currently safe exclusivity sentence**
2. **Predecessor actor set and live capability inventory**
3. **Quarantine posture, disablement evidence, and split-world state**
4. **Successor exclusive-control scope and blocked stronger sentence**
5. **Next evidence that upgrades or collapses retirement standing**

## Minimum required comparisons

The page must force explicit comparison between:

- successor discoverability and successor exclusivity
- stale handle retirement and live predecessor capability
- local unlink or removal and remote actuation survival
- key rotation and old-key cohort survival
- write disablement and share disablement
- named-slice quarantine and universal retirement

## Hard rules

The page must never silently upgrade:

- `successor canonical` into `predecessor cannot still act`
- `old handles rebound` into `old authorities extinguished`
- `one peer was rotated` into `old-key cohort dead`
- `one device was unlinked` into `all predecessor devices disabled`
- `linked-identity cleanup done` into `off-world remotes cannot still publish or serve`
- `stolen-device reset initiated` into `exclusive successor control already proved`
