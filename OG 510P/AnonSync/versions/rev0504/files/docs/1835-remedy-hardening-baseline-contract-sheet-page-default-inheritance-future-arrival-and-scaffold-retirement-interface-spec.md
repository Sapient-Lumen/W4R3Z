# Remedy-hardening-baseline contract sheet page — default inheritance, future arrival, and scaffold retirement

## Purpose

This page is the operator's compact contract for whether a case that already achieved recurrence-hardened-retained-change-gated-and-rollout-bounded discharge may honestly claim that the hardened behavior is now the safe baseline for future arrivals.
It exists so the product can distinguish `the current rollout stayed bounded` from `new arrivals now inherit the right baseline without depending on temporary rollout scaffolds`.

## Core fields

- case identifier
- source remedy-hardening-rollout receipt identifier
- triggering cause family
- current remedy-hardening-baseline posture rung
- current hardening or change class
- current safe baseline class
- named current protected cohort
- named future-arrival surfaces
- required future-arrival cohort
- linked-device future-arrival inheritance status
- Standard-versus-Advanced future-admission status
- share-link versus key future-admission status
- default path and arrival-binding status
- synchronization-mode inheritance map
- per-folder preference inheritance status
- configuration-mode baseline coverage status
- temporary rollout scaffold inventory
- scaffold retirement status
- baseline scar or carry-forward exception status
- highest honest current baseline-assimilated sentence
- strongest blocked stronger baseline-assimilated sentence
- next strengthening trigger
- next weakening trigger

## Remedy-hardening-baseline posture rungs

The page must model at least these distinct rungs:

- rollout bounded; baseline still provisional
- bounded rollout safe only for current cohort
- default inheritance aligned for named arrival surfaces only
- future-arrival safety blocked by linked-device or Standard-folder semantics
- temporary rollout scaffold still required
- scaffold retirement opened
- scaffold retired but scar still active
- baseline assimilated for required current cohort
- baseline assimilated and future-arrival safe for named required surfaces
- recurrence-hardened-retained-change-gated-rollout-bounded-and-baseline-assimilated discharge achieved
- baseline assimilation collapsed or suspended

## Required distinctions

The page must keep these truths separate:

- bounded rollout versus baseline assimilation
- current protected cohort versus future-arrival cohort
- safe arrival path versus safe future-admission semantics
- remembered approval versus fresh baseline inheritance
- temporary rollout scaffold versus ordinary baseline lane
- scaffold retirement versus scaffold forgotten
- one desktop surface aligned versus required-surface baseline assimilation

## Operator promises

The contract sheet must let the operator say things like:

- `the rollout stayed bounded, but future arrivals would still inherit the wrong baseline`
- `the hardened state is baseline-assimilated for current linked devices only`
- `new arrivals through Standard-key lanes still block the stronger baseline sentence`
- `manual one-way or pilot scaffolds still exist, so ordinary-baseline language stays blocked`
- `future arrivals now inherit the right hardened behavior across the required surfaces without depending on rollout-era scaffolds`

## UI behavior

The page must visually scar any blocked stronger sentence with the exact blocker class:

- linked-device future-arrival inheritance still unsafe
- Standard-folder or key-based admission still bypasses the intended baseline
- default arrival path still weak or ambiguous
- per-folder preference inheritance still desktop-only or partial
- config-mode coverage still too narrow
- synchronization-mode inheritance still incomplete
- temporary rollout scaffold still required
- scaffold retirement evidence too weak
- evidence basis too weak to claim baseline assimilation
