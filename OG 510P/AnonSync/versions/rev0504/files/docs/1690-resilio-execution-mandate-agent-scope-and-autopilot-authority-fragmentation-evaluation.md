# Resilio execution mandate, agent scope, and autopilot-authority fragmentation evaluation

## Claim

Current official Resilio docs are still admirably candid that `identity`, `linked device`, `owner`, `approval`, `automatic folder arrival`, `common folder list`, and `notification` are not one flat execution truth.
That candor is useful.
It is also exactly why AnonSync should not clone the present contract.

The missing product object is now sharper than acknowledgment and assent:

> after the product knows **who was notified, who opened, and who assented in a named capacity**, it still needs one first-class answer to **who may actually carry out the act, whether a human must press go, whether a delegate may execute, whether a linked device or agent may execute automatically, what supervision is required, and what stronger agency sentence remains blocked**.

Current Resilio materials still do not provide one typed execution-mandate object for:

- distinguishing person assent from person execution authority
- distinguishing delegated representative execution from linked-identity convenience action
- distinguishing supervised agent execution from unsupervised autopilot
- distinguishing standing operational ownership from typed fairness-act mandate
- distinguishing fresh execute-now authorization from older trust or owner posture
- preserving when automatic cross-device availability is useful operationally while still too weak for irreversible fairness execution
- proving when a stronger `fully execution-authorized` or `autopilot-authorized` sentence remains blocked

Instead, the operator still has to translate linked-device ownership, any-device approval, automatic folder arrival, synchronized notifications, and remembered settings into execution meaning.

## What current official docs still say

Current official docs still jointly show all of the following:

- `Sync Private Identity & Linking My Devices` still says each installation has a unique certificate, that once a remote user approves a connection they can choose to automatically approve all your linked devices for future sharing, that all Sync folders become available from any linked device, and that folder-access requests can be approved from any device where the folder is present.
- `Sync functionality in detail` still says the folder list is common across linked devices, that a device can be `Disconnected`, `Selective Sync`, or `Synced`, and that you can approve connections from any linked device instead of the specific device that shared the folder initially.
- `Comprehensive guide to syncing (Desktop-Desktop)` still says that linking devices with one identity automates folder sharing and that every folder added on one device becomes available on the others with full read-write access.
- `User Management` still says only Owners can invite new users, and that when you share across your own linked devices all of your devices act as Owners.
- `How to create a Read Only folder while syncing across linked devices?` still says My Devices automatically syncs added folders to linked devices with Owner permission by default, and that you must step outside that flow to force a read-only posture.
- `Resilio Sync change log` still says notifications synchronize across devices and that Sync API v2 is enabled.

This is strong operational candor.
It is not a first-class execution-mandate contract.

## Why this still fragments the decisive answer

One ordinary fairness answer still requires stitching together several docs and surfaces:

- whether assent to an act also authorized execution of that act
- whether a linked-device owner may execute only for sync continuity or for the exact typed fairness effect
- whether automatic folder arrival and full read-write default imply an execution mandate or only an operational convenience default
- whether any-device approval should count as named human execution, delegated execution, supervised agent execution, or merely identity-level continuity
- whether remembered approval or API availability can substitute for a fresh execute-now mandate
- whether an irreversible act needs human-in-the-loop execution even when ownership and connectivity are already settled

That means current official materials can help answer `can this device connect`, `can an owner approve`, `will this folder arrive automatically`, or `can automation touch Sync somehow`.
They still do not directly answer `who may now execute this exact act, through what actor kind, under what supervision, and what stronger autopilot sentence stays blocked?`

That gap is exactly where AnonSync should refuse cloning.

## Hard replacement line for AnonSync

AnonSync should borrow the useful ingredients:

- explicit device identity and certificate modeling
- explicit owner and permission routes
- explicit automatic cross-device arrival behavior where desired
- explicit notifications and searchable trace
- explicit operational APIs and automation hooks where they genuinely exist

But AnonSync should replace the page contract with a first-class **execution mandate** object where each typed act has its own:

- allowed executor class
- human-in-the-loop requirement
- delegate eligibility
- agent / automation eligibility
- linked-device substitution rule
- execute-now freshness rule
- supervision / dual-control requirement
- strongest blocked stronger agency sentence
- execution lineage receipt

## Product decision tightened here

The new design line is:

- **assented act is weaker than execution-mandated act**
- **human execution, delegated representative execution, supervised agent execution, and unsupervised autopilot are different truths**
- **identity-level convenience and linked-device ownership are weaker than typed execution mandate**
- **standing mandate is weaker than fresh execute-now mandate for irreversible effects unless the exact row allows standing execution**
- **execution trace is weaker than valid execution under current mandate**

## Consequence for the non-clone score

Resilio still belongs on the borrow side for identity, owner, automatic sharing, approval, and notification candor.
Resilio remains on the non-clone side for the fairness-critical execution-mandate contract.

The reason is now precise:

> current Resilio docs still expose linked-device ownership, any-device approval, automatic folder arrival, synchronized notifications, and API-era operational capability as separate operational facts rather than one typed execution-mandate object for `who may carry out this exact act now, through what actor class, under what supervision, and with what stronger autopilot sentence still blocked`, so the operator still has to reconstruct whether anyone was actually authorized to execute instead of merely connected, trusted, or notified.
