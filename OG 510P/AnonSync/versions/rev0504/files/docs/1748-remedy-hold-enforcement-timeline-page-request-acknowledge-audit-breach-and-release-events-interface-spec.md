# Remedy-hold-enforcement timeline page — request, acknowledge, audit, breach, and release events

## Purpose

This page orders the lifecycle by which a preservation hold becomes binding, stays credible, weakens, or fails.
It exists so the archive can show when the hold was merely named, when it became acknowledged, when it became enforceable, and when breaches or blind spots entered the story.

## Event classes

The timeline must preserve at least these events:

- hold declared
- hold request sent
- custodian acknowledgment received
- enforcement control applied
- restart required
- restart completed
- cleanup suppression confirmed
- blind spot discovered
- rescan window started
- audit performed
- breach suspected
- breach confirmed
- hold narrowed
- hold extended
- hold released
- enforcement collapsed

## Required chronology rules

- a hold cannot appear as enforced before at least one enforcement control or equivalent confirmed suppression exists
- a hold cannot appear as strongly breach-sensed before the detection lane is named and active
- restart-sensitive changes must stay visibly pending until restart or other activation proof completes
- suspected breach and confirmed breach must remain separate states
- release must preserve whether the hold ended cleanly, expired, or failed under breach

## Timeline summaries

The page header must summarize:

- current enforcement posture
- last successful audit time
- current undetected-breach floor
- next scheduled weakening event
- current strongest blocked stronger sentence
