# Remedy-landing proof page — target-binding evidence, duplicate-path risk, and adoption floor

## Purpose

This page is the case proof that a cure did or did not land as the intended repaired object in the intended operative place.
It exists so later readers can inspect the evidence behind the landing sentence instead of inferring it from visible files or reassuring folder names.

## Proof bundle

The proof page must preserve evidence for:

- intended repair object identity
- intended target path or binding
- actual landing paths
- duplicate-directory creation events
- reconnect-path divergence events
- non-empty-target merge confirmations
- placeholder-only states
- archive-rebind evidence
- encrypted survivorship evidence
- `.sync` continuity evidence
- final-name adoption evidence
- manual adoption actions
- cohort-by-cohort landing verification
- strongest honest landing sentence
- strongest blocked stronger landing sentence

## Proof sentence families

The page must support concise summaries such as:

- `bytes finished, but reconnect created a side-path candidate, so target-bound landing remains unproven`
- `landing is readable and operative for the named desktop cohort, while one required mobile cohort remains placeholder-only`
- `archive hash evidence supports rename rebind, but duplicate-path residue still blocks the stronger all-required-cohort landing sentence`
- `encrypted survivorship preserves remedy substrate, but operative landing remains blocked because readable adoption is absent`
- `the target was non-empty and merged by confirmation, so safe adoption remains weaker than raw bytes-finished success suggests`

## Invariants

- the proof never compresses transfer finish, target binding, and operative adoption into one word
- the proof never hides duplicate-path or side-path risk behind a visible folder name
- the proof never lets placeholders or encrypted survivorship impersonate readable operative landing
- the proof always preserves the blocker that prevented the stronger landing sentence
