# Remedy-hardening-attestation catastrophe-recovery proof page — anchor ledger, rebuild path, and reconstitution ceiling

## Purpose

This page is the evidence-heavy proof surface for determining whether a governed state can be recovered after catastrophic damage, and exactly how strong that recovery sentence may be.
It proves the ceiling on any claim that tries to say the system is not merely usable again, but legitimately continuous with the governed world that existed before the catastrophe.

## Required evidence blocks

### 1. Pre-catastrophe basis ledger

Preserve:

- source durable or regime-shift receipt
- target sentence before catastrophe
- governed slice
- pre-catastrophe continuity class

### 2. Catastrophe-class ledger

For the named catastrophe preserve:

- catastrophe class
- destructive scope
- whether loss touched bytes, anchors, identity, control capsule, or storage world
- whether the event itself already severs same-world continuity

### 3. Anchor-retention ledger

Preserve:

- bytes retained or lost
- storage folder retained or lost
- database lineage retained or lost
- keys or secrets retained or lost
- identity retained or regenerated
- `.sync` capsule retained, corrupted, or recreated
- receipts, proofs, or rulebook anchors retained or lost

### 4. Recovery-path ledger

Preserve:

- supported recovery path or unsupported shortcut
- re-add, relink, reconnect, reshare, or decrypt steps required
- exact anchors consumed by the recovery path
- exact elements regenerated or replaced
- whether the path yields same-world reconstitution or successor-world re-foundation

### 5. Contradiction and downgrade ledger

Preserve:

- clone-like restore exposure
- twin-instance exposure
- regenerated-identity exposure
- new synchronization-instance exposure
- contradictory witnesses after recovery
- resulting downgrade class

### 6. Claim ceiling

Render:

- highest honest bytes-recovered sentence
- highest honest governing-world continuity sentence
- highest honest same-world reconstitution sentence
- blocked stronger sentence and exact blocker

## Evidence classes

The page must distinguish at least:

- bytes recovered only
- supported anchor-dependent path not yet executed
- retained-database and retained-key conditional recovery only
- same-instance continuity blocked
- same-identity continuity blocked
- successor-world re-foundation only
- unsupported clone-derived recovery
- named catastrophe recovered for named slice only
- same-world reconstitution proven for named slice only
- broader all-catastrophe robustness blocked

## Hard rules

The proof page must never treat:

- recovered files as proof of recovered governance
- one surviving anchor as proof that all required anchors survived
- a new working Sync instance as proof of same-instance continuity
- regenerated trust material as proof of preserved trust continuity
- unsupported clone restoration as proof of supported reconstitution
