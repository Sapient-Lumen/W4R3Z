# Baseline-lineage receipt page — anchor, signature, equivalence grade, and blocked stronger sentences

## Receipt purpose

This receipt is the durable answer to:

> what baseline did we compare against, what subject did we really mean, what grade of sameness was proven, and what stronger comparison sentence was intentionally refused?

## Receipt fields

- receipt id
- time
- operator / automation actor
- canonical setting id
- canonical subject id or cohort id
- local label observed at review time
- baseline id and revision
- world id
- normalized governance signature snapshot
- equality grade
- divergence reasons
- realignment action taken or withheld
- activation rung if any mutation occurred
- strongest safe comparison sentence
- blocked stronger sentence

## Mandatory blocked-stronger sentence families

The receipt must explicitly block stronger sentences such as:

- `same label, therefore same subject`
- `same visible value, therefore same governance`
- `same current behavior, therefore same future default adoption`
- `same menu route, therefore same authority lane`
- `same service/config concept, therefore same world`
- `same baseline name, therefore same baseline anchor`

## Compact verdict patterns

- `Visible-value match only; detached override remains.`
- `Governance-signature match proven in current desktop world.`
- `Baseline-conformant after restore-inheritance.`
- `Comparison blocked pending canonical re-anchor.`
- `Cross-world similarity observed; equivalence ceiling remains below baseline conformance.`

## Copy rules

- Prefer canonical ids over labels in the receipt body.
- Preserve the local label only as a witnessed alias.
- If a mutation was withheld, say why.
- If a mutation occurred, say whether it changed value, governance, or both.
- Keep the blocked stronger sentence verbatim enough that future readers know exactly what was refused.
