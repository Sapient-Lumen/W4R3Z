# Residual authority page: already-landed bytes, offline seat, and proof-of-cutoff interface spec

## Purpose

This page answers:

> after I contain or rotate, what still remains outside my immediate control, and what proof do I truly have?

The page exists because future-update cutoff, already-landed bytes, offline seats, and proof of severance are not the same truth.

## Core rule

Every non-trivial compromise response must expose one first-class **Residual authority** page before the incident is allowed to look resolved.
That page owns:

- unrecallable local possession
- future-update cutoff status
- proof already obtained
- proof still pending
- accepted residual risk

## Primary layout

The page always renders the same regions:

1. residual verdict
2. residual-fact families
3. proof-of-cutoff card
4. pending proof and unresolved work
5. final incident receipt

### 1) Residual verdict

Show:

- strongest current statement such as `future updates cut off`, `already-landed bytes remain`, `cutoff not yet proven`, or `rotation pending`
- whether the incident is `contained`, `partially contained`, or `still open`
- strongest accepted residual risk

### 2) Residual-fact families

Separate at least these families:

- **already-landed local bytes** on the suspect seat
- **live authority not yet retired**
- **future updates already cut off**
- **offline uncertainty** because the suspect seat has not yet been observed again
- **reissue debt** such as grants, approvals, or shares still needing new issuance

For each family show:

- what remains
- why it remains
- whether it is expected, temporary, or alarming

The operator must be able to answer: **what exactly is still left over here?**

### 3) Proof-of-cutoff card

Show:

- what evidence currently supports cutoff: revoked grants, rebuilt cohort, changed identity epoch, seat no longer eligible, entitlement re-home, etc.
- whether the proof is direct, inferred, or still pending observation
- what the proof does **not** demonstrate

The operator must be able to answer: **what do I truly know was cut off?**

### 4) Pending proof and unresolved work

Show:

- waiting-for-return-online checks
- waiting-for-reissue tasks
- waiting-for-human confirmation items
- accepted unresolved residue that will not be chased further

The operator must be able to answer: **what still has to happen before this case can honestly close?**

### 5) Final incident receipt

Emit a receipt that preserves:

- containment lane used
- rotation or non-rotation verdict
- cutoff proof obtained
- residual-risk statement
- pending or intentionally abandoned follow-up

## Honest outputs

This page may conclude:

- `future updates cut off; suspect seat may still hold old local bytes`
- `cohort rebuilt; proof of old-seat severance is indirect until next observation`
- `subject-local disconnect complete; already synchronized files remain beyond recall`
- `incident not closed; four grants still need reissue under the new epoch`

It may not collapse these into one generic `resolved` badge.

## Rules

### Rule 1 — possession and authority must remain separate

Having bytes already on the suspect seat and having power to receive or modify future bytes are different residual facts.

### Rule 2 — proof must name its ceiling

The page must say what the current evidence proves and what it cannot yet prove.

### Rule 3 — closure requires an explicit residual statement

No incident may become `done` merely because the operator clicked through the rebuild.

## Acceptance test

This page is good enough when a cautious operator can answer all of the following without leaving it:

- what residual facts remain after containment or rotation
- which of those are possession versus live authority
- what proof of cutoff already exists
- what proof is still pending
- what residual risk the operator is explicitly accepting
