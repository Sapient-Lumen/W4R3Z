# Remedy-hardening-bootstrap proof page — rebuild evidence, migration scope, and reproduction floor

## Purpose

This page is the proof bundle behind the claim that a case which already achieved a future-arrival-safe baseline may let a fresh or rebuilt world inherit the same safety posture.
It exists so later readers can inspect rebuild method, world continuity, version-lane limits, folder-type coverage, and re-proof scars instead of inferring them from installation guidance.

## Proof bundle

The proof page must preserve evidence for:

- source remedy-hardening-baseline result
- triggering cause family
- current hardening or baseline class
- named current world
- named fresh-world target class
- required reproduction cohort
- startup-config reproduction evidence
- migrate-settings evidence
- clean-install reproduction evidence
- service-principal and runtime-mode evidence
- storage-root continuity or fork evidence
- identity carry-forward or rebirth evidence
- linked-device dependence evidence
- Standard-folder reproduction evidence
- Advanced-folder reproduction evidence
- per-folder preference reproduction evidence
- supported platform lane evidence
- supported version lane evidence
- manual rebind or re-share evidence
- highest honest current bootstrap-reproducible sentence
- strongest blocked stronger bootstrap-reproducible sentence

## Proof sentence families

The page must support concise summaries such as:

- `the current world is safe, but a fresh world would not yet reproduce the same hardening`
- `reproduction is honest only through named startup or Standard-folder lanes`
- `service or storage-world rebirth still blocks the stronger bootstrap sentence`
- `version-lane compatibility remains too weak for full fresh-world language`
- `the hardened baseline is now reproducible through the required clean-world and supported-version lanes, with scars preserved`

## Stronger-sentence blockers

The page must explicitly name blockers such as:

- startup recipe too narrow
- clean-install path unresolved
- settings migration not enough
- service principal or storage world not continuous
- linked-device dependence hiding missing reproduction proof
- Standard/Advanced lane mismatch
- per-folder preference reproduction too narrow
- version-lane compatibility blocked
- platform lane not covered
- evidence basis too weak

## Evidence handling rules

The proof page must never let these substitute for stronger proof:

- one current-world baseline receipt without rebuild evidence
- one sync.conf file without lane-coverage evidence
- one migrated service world without invariants re-proved
- one linked-device repopulation event without explicit hardening reproduction evidence
- one supported install path without supported-version and supported-world evidence
