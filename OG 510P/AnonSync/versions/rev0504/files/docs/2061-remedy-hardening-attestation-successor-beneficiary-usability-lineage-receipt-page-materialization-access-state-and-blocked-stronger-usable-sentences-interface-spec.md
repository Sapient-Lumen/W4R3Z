# Remedy-hardening-attestation successor beneficiary-usability lineage receipt page — materialization, access state, and blocked stronger usable sentences

## Purpose

This page is the portable receipt summarizing what can honestly be claimed about whether the named beneficiary can use one landed reviewed result now.
Later pages must cite this receipt instead of improvising `the user has it`, `the file is there`, or `they can use it now` language.

## Receipt header

The header must show:

- receipt identifier
- action identifier
- source outcome-conformance receipt identifier
- named beneficiary identifier
- current beneficiary-usability standing
- current strongest safe sentence
- current blocked stronger sentence

## Mandatory receipt fields

- source outcome-conformance receipt identifier
- source execution-run identifier
- named beneficiary summary
- intended beneficiary action summary
- intended usable-result summary
- current materialization summary
- online-source dependency summary
- shell or handler summary
- access and update posture summary
- lock, path, encoding, and filesystem blocker summary
- source-peer absence or ghost-file summary if any
- contradiction status
- superseding receipt identifier if any

## Standing states

The receipt must support at least these states:

- landed result exists, beneficiary usability still unproven
- visible-only or placeholder-only representation
- source-dependent retrievability only
- local bytes present but ordinary affordance blocked
- local bytes present but access or update posture degraded
- beneficiary can read or open only
- beneficiary can use result as intended for named slice only
- later contradiction narrowed prior beneficiary-usability confidence
- receipt superseded

## Primary sentence classes

The receipt must be able to emit at least these classes:

- `reviewed result landed; beneficiary-usable sentence still blocked`
- `beneficiary currently has placeholder-only or visible-only representation`
- `beneficiary can fetch bytes only while a source peer remains online`
- `beneficiary has bytes locally, but ordinary-use sentence is blocked by affordance or access limits`
- `beneficiary has bytes locally, but live-update posture is degraded`
- `named beneficiary can use result as intended for named slice only`
- `later contradiction narrowed prior beneficiary-usability confidence`
- `stronger beneficiary-usable sentence remains blocked`

## Hard rules

The receipt must never let later pages say:

- the named beneficiary has the result in a usable form
- the beneficiary can use it now without dependency or workaround
- the beneficiary can modify it and still receive intended updates
- the beneficiary has a self-sufficient copy
- beneficiary usability is settled and final

unless the receipt actually carries the corresponding proof state.
