# Remedy-landing contract sheet page — target binding, side-path risk, and operative adoption

## Purpose

This page is the operator's compact contract for whether a cure that was protected strongly enough to finish also landed in the intended logical place.
It exists so the product can distinguish `bytes finished` from `the intended repaired object is now actually where the case needed it to be`.

## Core fields

- case identifier
- source remedy-flight-protection receipt identifier
- current remedy-landing posture rung
- intended repair object identifier
- intended target path or binding
- intended operative cohort
- actual landing cohort
- actual landing locations
- duplicate-path posture
- side-path residue posture
- non-empty-target merge posture
- placeholder-only residue posture
- archive-rebind posture
- encrypted or unreadable landing posture
- `.sync` continuity posture
- final-name adoption posture
- local-only rename caveat posture
- reconnected-path divergence posture
- strongest blocked stronger cure sentence
- next strengthening trigger
- next weakening trigger

## Remedy-landing posture rungs

The page must model at least these distinct rungs:

- landing requested
- bytes finished pending target-bind verification
- landed in duplicate or side path
- landed through merge into pre-existing target
- landed as placeholder-only shell
- landed unreadable or encrypted only
- landed via archive rebind pending adoption
- landed for named cohort
- landed for required cohort
- landing misbound
- landing verification collapsed

## Required distinctions

The page must keep these truths separate:

- bytes finished versus target-bound landing
- target-bound landing versus operative adoption
- visible folder reappearance versus restored original target binding
- placeholder visibility versus readable landed bytes
- archive rebind versus ordinary retransmitted landing
- encrypted survivorship versus readable operative landing
- local folder rename versus globally adopted folder identity
- side-path duplicate creation versus intentional safe migration

## Operator promises

The contract sheet must let the operator say things like:

- `the repair finished, but reconnect proposed a new path and created a duplicate directory candidate, so landing remains pending target-bind verification`
- `the repaired bytes landed for the named desktop cohort, but one required device still exposes only placeholders, so required-cohort landing stays blocked`
- `landing succeeded through Archive-backed rebind, but operative adoption remains blocked until duplicate-path residue is cleared`
- `encrypted backup survivorship proves substrate, but readable operative landing is still absent for the required cohort`
- `the target was non-empty and merge was accepted, so safe landing remains weaker than it looks until foreign-content risk is reviewed`

## UI behavior

The page must visually scar any blocked stronger sentence with the exact blocker class:

- duplicate directory creation
- side-path reconnect
- non-empty target merge
- placeholder-only residue
- archive-only rebind ambiguity
- encrypted or unreadable landing
- `.sync` continuity fragility
- local-only rename caveat
- target mismatch across cohorts
- manual adoption debt

## Invariants

- the page never lets finished transfer impersonate target-bound landing
- the page never lets visible reappearance impersonate operative adoption
- the page never lets placeholder presence impersonate landed content
- the page always states whether landing holds for named cohorts only or all required cohorts
