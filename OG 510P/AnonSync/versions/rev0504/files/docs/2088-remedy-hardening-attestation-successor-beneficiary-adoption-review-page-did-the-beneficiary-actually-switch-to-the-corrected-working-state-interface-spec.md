# Remedy-hardening-attestation successor beneficiary-adoption review page — did the beneficiary actually switch to the corrected working state?

## Purpose

This page is the decisive review for whether the named beneficiary merely noticed a correction or actually changed working behavior for the governed slice.
It exists because `seen`, `acknowledged`, `downloaded`, `opened`, and `adopted` are not the same sentence.

## Review question

The page must force the reviewer to answer:

**did the named beneficiary actually switch to the corrected working state and retire stale reliance for the governed slice, or do we only know that the correction was noticed, acknowledged, fetched, or opened?**

## Required prompts

The review must explicitly ask:

1. What uptake class was actually required here: notice only, acknowledgement, open, adoption, stale retirement, or compliance attestation?
2. What evidence shows the corrected artifact became the active working artifact rather than merely one more downloaded copy?
3. Which stale artifacts, paths, exports, local derivatives, or remembered habits still remain plausible?
4. Is any downstream pointer, bookmark, workflow, template, or operating location still aimed at superseded material?
5. What is the strongest honest sentence that can be said now without pretending that activity evidence equals adoption?

## Minimum evidence blocks

The review page must preserve at least these blocks:

- beneficiary and governed-slice summary
- correction summary
- required uptake class
- acknowledgement evidence block
- download / hydration evidence block
- open / view evidence block
- active working-pointer evidence block
- stale artifact set block
- stale-retirement evidence block
- relapse / contradiction block
- strongest safe sentence preview
- blocked stronger sentence preview

## Required outcomes

The review must be able to end in at least these outcomes:

- `beneficiary noticed the correction; adoption still unproven`
- `beneficiary acknowledged the correction; adoption still unproven`
- `corrected artifact was fetched or opened; working switch still unproven`
- `beneficiary likely switched to corrected working state`
- `working switch likely happened, but stale reliance still remains plausible`
- `stale reliance retired for the governed slice only`
- `broader compliance sentence still blocked`
- `later contradiction narrowed prior adoption confidence`

## Required layout

### Left column — intended uptake contract

Show:

- governed slice
- correction severity
- required uptake class
- corrected working artifact
- stale-retirement requirement
- unacceptable substitute states

### Right column — actual beneficiary-adoption evidence

Show:

- acknowledgement evidence
- fetch/open evidence
- active working-pointer evidence
- stale artifact evidence
- stale-retirement evidence
- relapse or contradiction evidence
- blocker-by-blocker reasoning

### Bottom section — decision worksheet

This section must offer explicit toggles for the reviewer to mark:

- `seen only; adoption unproven`
- `acknowledged; adoption unproven`
- `opened corrected artifact; active switch unproven`
- `working pointer switched; stale artifacts still matter`
- `stale reliance retired for named slice only`
- `evidence too weak for stronger compliance sentence`

Each toggle must immediately update the strongest-honest-sentence preview.

## Hard rules

The review must never let the operator leave without answering:

- what uptake class was actually required
- what evidence shows the corrected artifact became the working artifact
- whether any stale artifact still competes for actual reliance
- whether stale reliance was retired for the governed slice
- what stronger sentence is still blocked
