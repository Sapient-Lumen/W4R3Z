# Resilio remedy hardening attestation successor-world inheritance bridge legitimacy and carry-forward fragmentation evaluation

## What current Resilio gets right

Current official Resilio materials still deserve credit for being candid that `the old world was lost or reset`, `a new usable world exists`, and `the new world legitimately inherits the old world's standing` are not one flat truth.
That candor is useful.

The strongest present ingredients are:

- current `If your device is stolen` docs still say the serious response path breaks the previous instance, regenerates identity, relinks devices, and reshares folders
- current `Service files missing / Cannot identify destination folder` docs still say repair after `.sync` loss creates a new synchronization instance
- current `How do I upgrade my Standard (1.4, or classic) folders to Advanced (2.x) folders?` docs still say there is no upgrade path and operators must remove Standard folders and re-add them as Advanced folders because of architectural differences
- current `Sync Service Troubleshooting on Windows` docs still say switching service execution to Local System creates a new storage folder where no old added folders are visible and the operator must re-add and re-share or reconnect all folders
- current `Running Sync as a service on Windows` docs still say one installation path migrates settings while the clean-install path requires re-sharing folders and reconnecting them to existing peers
- current `Encrypted folders` docs still say same-database continuity matters if you want the encrypted backup peer to remain a valid recovery source, which implies that losing that lineage weakens what can be inherited
- current `Sync Storage folder` docs still say storage contains current configuration, auxiliary settings files, and shares databases, which means successor-world carry-forward depends on which anchors actually crossed the break
- current `Cloning Sync` docs still say cloning is unsupported and may yield multiple instances that do not transfer data to one another, which is exactly the opposite of an explicit inheritance bridge

## Where the current contract still fragments

The problem is not that Resilio lacks successor-world clues.
The problem is that it still does not produce one first-class, case-scoped **inheritance-bridge legitimacy** object.

Today an operator can often infer only weaker truths such as:

- a new instance works, but it may not legitimately inherit the prior instance's standing
- some data and even some peers reconnect, but old receipts, obligations, approvals, or waivers may or may not carry forward
- one migration path preserves visible shares, while another path requires re-share and reconnect, yet the product still leaves inheritance meaning implicit
- a same-database path may preserve more continuity than a regenerated-identity or new-instance path, but the product does not turn that into one explicit carry-forward budget
- architectural conversion by remove-and-re-add may preserve user intention while still severing old-world lineage for some claims
- a safer successor world may deserve partial inheritance of bytes or policy, while stronger authority or trust claims should remain blocked

Those are useful clues.
They are not the same as an explicit answer to `which receipts, obligations, waivers, policy deployments, trust handles, and challenge outcomes legitimately carry forward into this successor world, which stay predecessor-bound, and which stronger continuity sentence must remain blocked?`

## Why that matters for AnonSync

AnonSync needs a stronger sentence than `we recovered something usable after catastrophe`.
It needs to support claims such as:

- the old world is severed, but a named successor world may inherit bytes only
- the successor world may inherit policy and precedent, but not old approvals or trust handles
- a new world may inherit some obligations to notify, remediate, or revoke, even while same-world continuity remains blocked
- carry-forward may be explicitly budgeted and ratified rather than guessed from what happened to reconnect successfully

So AnonSync should not clone Resilio's present contract at this seam.
It should borrow the candor about new-instance repair, identity regeneration, clean-install re-sharing, storage-world forks, architectural replacement, and same-database recovery preconditions, while replacing the fragmented operator story with one first-class family for **successor-world inheritance bridge legitimacy and carry-forward truth**.
