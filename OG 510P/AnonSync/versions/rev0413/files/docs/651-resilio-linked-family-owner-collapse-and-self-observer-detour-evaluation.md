# Resilio linked-family owner collapse, self-observer detour, and seat-role opacity evaluation

## Why this pass exists

The archive already had stronger doctrine for authority mutation, derived rights, non-authority local-edit fate, and seat posture.
What it still lacked was one direct current Resilio evaluation for a narrower but important question:

> when one of my own devices should participate less authoritatively than the rest of my linked family, does the product have one native seat-level role for that, or does it force me to switch subject class, artifact family, and connection ritual just to express `this is still mine, but this seat is intentionally narrower`?

Current official Resilio docs still show a useful, living product, but they also still show that one ordinary answer is spread across several article families at once:

- `Sync Private Identity & Linking My Devices`
- `Sync functionality in detail`
- `User Management`
- `Is one-way synchronization possible?`
- `How to create a Read Only folder while syncing across linked devices?`
- `What's the difference between Standard and Advanced folders?`

## Current official Resilio evidence that matters here

Current official docs still show an active v3 line through `3.1.2.1076`.
They also still say all of the following:

- `Sync Private Identity & Linking My Devices` still says once devices are linked, all folders automatically become available on all linked devices.
- The same linking docs still say approvals can be issued from any linked device where the folder is active.
- `User Management` still says that when data is shared across devices linked to one identity, all of those devices act as Owners.
- `Sync functionality in detail` still repeats that linked devices share one common folder list and that approvals can be handled from any linked device.
- `Is one-way synchronization possible?` still says Advanced folders do not allow Read Only synchronization across linked devices.
- `How to create a Read Only folder while syncing across linked devices?` still says that if you want one of your own linked devices to hold a Read Only copy, you must use a Standard folder with a Read Only key, disconnect the folder if it already connected, manually enter the key, manually choose the location, and accept non-empty-target confirmation if needed.
- `What's the difference between Standard and Advanced folders?` still says Standard and Advanced differ architecturally, that only Advanced supports on-the-fly permission changes and Owner, and that Standard uses keys while Advanced uses PKI/certificates.

So current Resilio still contains a real but scattered answer to `what role does this seat have because it is my linked device, and how do I intentionally narrow it without pretending it is some other share kind?`

## What Resilio still gets right

### 1) It is candid that linked-family convenience is real

The docs do not pretend each personal device is a separate manual sharing project.
They openly say linked devices inherit common visibility and approval convenience.
That is valuable.

### 2) It still admits that seat role can matter operationally

The docs do not hide that a linked device may need `Disconnected`, `Selective Sync`, or `Synced` posture, and they do not hide that a receive-only copy on your own device is a distinct ask.
That honesty matters.

### 3) It still publishes the detour instead of silently failing

The Read Only how-to is awkward, but it is explicit.
Resilio does not merely grey out the idea and leave the user guessing.

## Why this is still a good reason not to clone them

### 1) Identity relationship still collapses seat role into `Owner`

Current docs still make `my linked device` and `Owner` nearly the same default sentence.
That is convenient, but it means the product still lacks one native way to say:

- same personal constellation
- same subject lineage
- intentionally narrower seat authority
- no fake re-share ritual required

AnonSync should not inherit that collapse.

### 2) Self-observer posture still requires a world switch, not a seat-role edit

Current docs still route `make one of my own devices Read Only` through:

- Standard folder instead of Advanced folder
- Read Only key instead of linked-family seat policy
- disconnect/manual connect ritual instead of direct seat-role change
- manual bind and possible non-empty confirmation

That is not just a UI gap.
It means the role change is expressed by changing artifact family and connection path instead of changing seat role directly.

### 3) Relationship basis and authority basis are still too easy to confuse

Current docs still require the operator to reconstruct whether a device is powerful because:

- it is the same linked identity
- it received an explicit folder permission
- it is using a different folder class entirely
- it was manually re-added through a Standard-folder detour

A serious sync product should not let `same person`, `same family`, `same subject`, and `same authority` blur together.

### 4) The strongest safe sentence is still under-owned

Current Resilio still leaves later operators to reconstruct whether the honest sentence is:

- `this seat is an owner because it is linked`
- `this seat is intentionally narrowed within the same subject`
- `this is actually a separate Standard-folder receive-only detour`
- `this seat only looks narrower because the subject class changed`

That sentence should belong to one product-owned page and one durable receipt.

## The tighter AnonSync conclusion

AnonSync should borrow the following from Resilio more boldly:

- candid admission that personal linked-family convenience is useful
- candid admission that one seat may still need a narrower operational role than the rest
- explicit publication of the actual workaround when native self-narrowing is missing

But AnonSync should refuse the exact page contract whenever one ordinary answer still depends on:

- linked-family owner default
- subject-class substitution
- key-family detour
- disconnect/manual-bind ritual
- later memory about whether the narrow seat is really the same subject or a workaround copy

## The replacement pages this evaluation justifies

This pass therefore makes four page-shaped obligations concrete:

1. **Seat role** — what role does this seat currently have for this subject, and why?
2. **Self-narrowing review** — how should one of my own seats become narrower without lying about subject continuity?
3. **Relationship-versus-seat authority** — is this role coming from linked identity, explicit grant, derived ceiling, or a detour artifact?
4. **Seat-role receipt** — what role was requested, what basis actually won, and what is the strongest honest sentence now?

## Bottom line

The tighter no-clone reason is now this:

> Resilio is still good evidence that personal linked-device convenience matters, but it is also current evidence that one ordinary request — `make this one of my own devices intentionally less authoritative` — can still require owner-default folklore, Standard-folder substitution, Read Only keys, disconnect/manual-connect ritual, and later archaeology about whether the result is really the same subject. AnonSync should copy the candor and refuse the owner-collapse contract.
