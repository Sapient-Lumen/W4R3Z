# Resilio interface clone-veto tests and page obligations

## Purpose

The archive already had a borrow/adapt/reject scorecard.
That was necessary, but it still left one pressure question only half answered:

> how do we decide, page by page, whether a Resilio-like interface contract deserves direct inheritance, adaptation, or refusal?

This document gives that answer.
Its goal is not to punish familiarity.
Its goal is to make `do not clone` operational.

## The decision rule

A Resilio-like page should be cloned only if it passes five tests.
If it fails materially, AnonSync should adapt or refuse the page contract even when the underlying product idea is right.

### Test 1 — one ordinary question, one stable page answer

If an ordinary operator question needs help pages, browser chrome, hidden power-user settings, and troubleshooting folklore to reconstruct the answer, the page does not earn cloning.

### Test 2 — degraded states must publish upgrade ladders

If the page can tell the operator `warning`, `failed`, `paused`, or `not ready`, it must also tell the operator the next stronger reachable state and how to get there.

### Test 3 — convenience selectors must not decide orthogonal truths silently

A convenience selector may exist.
But it should not silently decide several materially different truths at once, such as visibility, path adoption, byte materialization, authority widening, or future defaults.

### Test 4 — accelerators must degrade into typed fallbacks

If the fast path fails, the fallback must preserve typed import/review rather than dumping the operator into folklore, generic paste boxes, or raw OS/browser rituals.

### Test 5 — meaningful mutations must leave product-owned receipts

If the operator accepted a trust exception, changed a cap, chose a different intake lane, or crossed from installed to ready, the product should own the receipt instead of outsourcing memory to browser history or support notes.

## Where current Resilio still fails these tests

### A) Control trust

Resilio still earns respect for local-web practicality.
But the current trust story still spans:

- WebUI defaults on Linux and Windows service installs
- self-signed certificate warnings
- proceed-unsafely browser ritual
- HSTS clearing to fall back toward HTTP
- custom certificate replacement through config

That fails Test 1 and Test 2.
The operator question is ordinary, but the answer is still scattered.

### B) Artifact intake

Resilio still earns respect for link, QR, and manual delivery.
But current docs still say:

- browser handoff can fail
- OS/browser registration can be the cause
- WebUI cannot consume the direct-link path
- manual paste becomes the fallback

That fails Test 4 because the fallback is semantically weaker than it should be.

### C) Effective rate truth

Resilio still earns respect for having real rate and schedule controls.
But the current answer still spans:

- ordinary send/receive rates
- a hidden LAN exception preference
- schedule windows
- `Paused` semantics that still allow some state changes
- config-mode declarations

That fails Test 1 and partially Test 5 because the winning answer is still reconstructed.

### D) Install-to-ready bringup

Resilio still earns respect for supporting service-heavy and headless installs.
But current docs still leave the operator to assemble:

- package trust and reputation warnings
- elevation/service registration
- firewall/network consent
- runtime start
- browser reachability

That fails Test 1 and Test 5 because `installed` and `ready` are still too easy to confuse.

## What current Resilio still plainly deserves

The point of these veto tests is not fake differentiation.
Resilio still clearly deserves copying on several lines:

- disconnected / selective / synced byte posture
- link / QR / manual delivery as a triad
- browser/local-web control on Linux-heavy and service-heavy installs
- encrypted custody on an untrusted intermediary
- same-host derivation as a real workflow

The archive should stay honest about that.

## The page obligations this creates for AnonSync

If AnonSync refuses a direct clone, it now owes one explicit replacement page.
This revision therefore treats the following pages as mandatory answers, not optional polish:

1. **Control trust**
2. **Import artifact**
3. **Rate policy**
4. **Finish setup**

Each one exists because a still-ordinary question deserves one stable product-owned page.

## The minimal standard for page-shaped replacement

A replacement page should do at least five things:

1. name the current state in product language rather than browser/OS folklore
2. name the strongest ordinary next action
3. preserve typed consequence preview before mutation
4. preserve a durable receipt after mutation
5. remain projectable in local web, CLI, and API without semantic loss

## Result

The archive can now answer `why are we not cloning this Resilio page?` with something better than taste.

It can say:

> because the underlying product idea is good, but this exact page still fails one of our clone-veto tests, and here is the stronger replacement page we will ship instead.
