# rev0317 governance-tail consolidation audit

## Audit target

The riskiest waste pattern is governance mass that looks important but does not help the next human
act. Rev0316 already moved the startup path toward owner contact plus the teacher/tutor micro-pilot.
Rev0317 audits the governance tail itself so future work can delete, merge, or cold-park surfaces
after a real cycle instead of adding more doctrine.

## Refactor decision

No files are deleted in rev0317 because the release validators and branch-family index still expect
historical paths to remain stable. The refactor is navigational and operational:

- keep the ten-surface re-entry path small;
- add an owner contact send pack so `FT-0181` is no longer only a scratch artifact;
- add a micro-pilot run card and owner plan so pedagogical execution is no longer only a concept;
- treat `portable-*`, `sector-and-*`, old deep-audit, and old risk-burndown files as cold retrieval;
- after the first real owner or micro-pilot readout, retire or merge any cold-tail surface that did
  not change a decision.

## Deletion test for the next real cycle

After an accepted owner packet or completed micro-pilot readout, every candidate governance surface
must answer four questions:

1. Which decision did this surface change?
2. Which harm did it prevent that an existing surface did not already prevent?
3. Which field, command, or owner action depends on it?
4. Would deleting or cold-parking it increase learner harm, privacy risk, access harm, or false
   claims?

If the answer is unclear, merge the surface into an index row or cold archive note. Do not create a
replacement control unless the real cycle exposed a concrete uncovered failure.

## Claim boundary

This audit lowers navigation burden and names deletion candidates. It does not remove historical
obligations, accept evidence, authorize service changes, upgrade claims, or close `FT-0181`.
