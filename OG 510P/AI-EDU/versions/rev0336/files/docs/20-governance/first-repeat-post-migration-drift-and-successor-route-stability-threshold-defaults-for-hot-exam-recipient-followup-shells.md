# First repeat post-migration drift and successor-route stability-threshold defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request
routes.

It can already say:

- when a de-watched shell later relapses and which minimized repair memory may be recalled;
- when suspected redesign failure needs current proof and bounded post-redesign probation before
  trust returns;
- what proof, owner truth, learner action, and clock continuity may travel when a redesigned route
  later changes owner, URL, platform, recipient portal, archive path, or provider route; and
- what must refresh when a migrated successor route later drifts, changes prerequisites, expires,
  goes silent, decommissions, reappears, or exposes split-owner mismatch.

That is still not enough.

A successor route can drift once, refresh proof, and settle. But it can also drift again. The same
successor owner may repeatedly go stale beyond its own window. The same route can repeatedly change
prerequisites. The same transferred proof can repeatedly expire before the learner or owner can use
it. A canonical, redirect, image host, provider form, recipient portal, archive time slice, CMS
path, or accessibility owner can keep moving after each refresh. A provider route can decommission,
revive, and decommission again. A split-owner shell can repeatedly expose disagreement between
source, search, archive, recipient, accessibility, and official-record owners. Or a route can appear
to need repeated refresh only because ordinary search, cache, or support lag is being mistaken for
instability.

This document adds one thing only:

- a **tiny repeat post-migration drift / successor-route stability-threshold field set** for
  hot-exam recipient followup shells after a single post-migration proof-refresh layer has already
  been published, but the same successor route or affected surface repeatedly drifts, repeatedly
  requires proof refresh, repeatedly goes stale, repeatedly decommissions, or repeatedly splits
  owner truth.

That means the archive now asks a different question than before. It no longer asks only **what must
be refreshed after migration**. It now asks **when repeat drift after refresh proves the successor
route itself is unstable enough for a standing stability threshold, owner repair, local redesign,
route split, or decommissioned-route posture — without turning every migrated route into a standing
migration watch, without stamping the successor owner with a permanent redesign-failure label, and
without pretending old migration memory has to be either public forever or erased completely**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
is property-owner, exact URL, current/expired state, cancellation, six-month temporary-block, and
source-side permanent-removal based rather than a durable all-copy certificate. Google's Refresh
Outdated Content route is exact page/image URL, changed/gone-content, queue/status, and 180-day
expiry based rather than an automatic repeated-refresh monitor. Google personal-content routes can
expose notifications, removal requests, source-site separation, and sensitive proof needs, but they
still separate Search removal from source-page control. Princeton separates local deletion,
document/media cleanup, cache layers, custom search, Google/Bing behavior, and Wayback persistence.
WiscWeb separates WiscWeb-hosted source edits, primary-contact support, normal-hours limits, host
referral, campus search/lookahead/directory, and major-search-engine timing. Rowan separates Cascade
CMS maintenance, Siteimprove/accessibility monitoring, contributor responsibility,
content-audit/redesign review, web support, and accommodation routes. Internet Archive requires URL,
time-period, control-period, and review context before exclusion. Bing distinguishes temporary
blocks, up-to-90-day expiry, cached/outdated-content handling, and permanent source-side methods
such as 404/410 or noindex. Together those signals support a tighter archive rule: **the next
truthful portability gain here is one tiny repeat-drift threshold layer for repeat signal, scope,
threshold, owner stability trigger, learner action separation, disposition, and exit — but not one
standing migration watch for every migrated route, automatic proof refresh after every lag,
permanent redesign-failure stigma, all-copy decommissioning, or no-memory reset.** See `B257`.

## Small field set for repeat post-migration drift and successor-route stability thresholds

| Code | Meaning | Default archive action |
|---|---|---|
| `YR0-NO-AUTOMATIC-STANDING-MIGRATION-WATCH-PERMANENT-FAILURE-LABEL-OR-NO-MEMORY-RESET` | repeated drift can matter, but it does not by itself create a permanent watch, public failure label, automatic decommissioning, or amnesia about earlier migration proof | require repeated material drift on the same successor route or affected surface, a named threshold basis, current owner truth, and live learner dependency before widening beyond ordinary proof refresh |
| `YR1-PUBLISH-REPEAT-DRIFT-COUNT-SCOPE-AND-PATTERN-BASIS` | repeat drift must be counted by route, surface, owner, URL, portal, archive slice, provider path, recipient dependency, or proof object rather than by anecdote | publish whether the pattern is repeated owner staleness, repeated prerequisite change, repeated proof expiry, repeated redirect/canonical drift, repeated portal drift, repeated provider decommissioning, repeated archive/control-period mismatch, repeated split-owner disagreement, repeated reappearance, or only ordinary lag |
| `YR2-PUBLISH-STABILITY-THRESHOLD-OWNER-TRIGGER-AND-REFRESH-LIMIT` | a stability threshold needs a named trigger and ceiling before refresh becomes watch, redesign, split, or decommissioned-route posture | publish the threshold basis, current successor owner, last refresh outcome, whether another refresh is still proportionate, and whether the owner must prove route stability, repair the route, redesign the workflow, split the shell, or disclose no-active-route residue |
| `YR3-SEPARATE-OWNER-STABILITY-WORK-FROM-LEARNER-ACTION-NOW` | unstable successor routes often need owner repair more than learner re-filing | publish learner action only when the current route names it; otherwise publish owner repair, local support handoff, recipient confirmation, provider refile, archive control-period proof, redesign review, split-surface action, or no-active-route residue without charging repeated route instability to the learner |
| `YR4-PUBLISH-STABILITY-DISPOSITION-MINIMIZATION-AND-REOPEN-TRIGGERS` | repeat-drift thresholding can settle, narrow, split, or decommission without keeping transition proof public forever | publish ordinary refresh, bounded stability watch, owner repair, route redesign, route split, decommissioned-route residue, no-active-route residue, local-only memory, de-thresholded ordinary status, or reopen only on material drift, owner change, route expiry, reappearance, or new proof |

## Field values that now travel together

When this layer is used, the shell should publish only six concrete fields:

1. `repeat_drift_pattern_token` — `none`, `one prior drift only`, `repeated owner staleness`,
   `repeated prerequisite change`, `repeated transferred proof expiry`, `repeated redirect or
   canonical drift`, `repeated recipient portal drift`, `repeated provider decommissioning`,
   `repeated archive control-period mismatch`, `repeated split-owner mismatch`, `repeated
   reappearance`, `ordinary lag pattern only`, `none inherited`, or `not published`;
2. `stability_threshold_basis_token` — `no threshold met`, `route-native repeat threshold`, `local
   owner threshold`, `two material drifts same surface`, `two stale beyond-window states`, `two
   proof-expiry failures`, `two provider decommissions`, `split-owner repeat threshold`, `recipient
   dependency threshold`, `archive/control-period threshold`, `redesign-review threshold`,
   `decommission review threshold`, `none inherited`, or `not published`;
3. `successor_route_stability_owner_token` — `successor owner current`, `successor owner must prove
   stability`, `source owner must repair`, `provider route owner pending`, `recipient owner
   pending`, `archive or mirror owner pending`, `accessibility or CMS owner pending`, `split owners
   must separate`, `local redesign owner named`, `no active owner`, `none inherited`, or `not
   published`;
4. `repeat_drift_disposition_token` — `ordinary refresh only`, `bounded stability watch`, `owner
   repair required`, `route redesign required`, `split surface shell`, `provider route refile`,
   `recipient confirmation path`, `archive control-period reproof`, `decommissioned route posture`,
   `no active route residue`, `non-material lag`, `none inherited`, or `not published`;
5. `repeat_drift_learner_action_token` — `none current`, `wait for owner stability proof`, `learner
   refile current route`, `learner supply new prerequisite proof`, `learner confirm recipient
   dependency`, `learner choose alternate route`, `protected or sensitive local-only submission`,
   `no active route action`, `owner-only action`, `none inherited`, or `not published`;
6. `stability_exit_token` — `de-thresholded ordinary route`, `stability watch opened`, `watch closed
   after clean cycle`, `redesign handoff`, `route split retained`, `successor route decommissioned`,
   `no active route residue`, `local-only memory retained`, `minimized migration memory`, `reopen on
   material drift`, `reopen on owner change or route expiry`, `none inherited`, or `not published`.

That is deliberately small. It is enough to show what repeated, where the threshold came from, who
owns stability work, what disposition follows, whether the learner has any current action, and when
threshold memory exits learner-facing publication. It is not enough to create a standing migration
watch for every successor route, an automatic proof-refresh duty after ordinary lag, a permanent
redesign-failure label, a cross-owner override, or a universal decommissioning rule.

|---|---|---|

| Google Refresh Outdated Content route after repeated result URL, image URL, or container-page drift | `repeated transferred proof expiry`, `two proof-expiry failures`, `provider route owner pending`, `provider route refile` or `ordinary refresh only`, and `reopen on material drift` | the route is exact URL/image and expiry based; repeated expiry or reappearance may prove the proof packet is unstable, but only for the affected result and not every old source copy |
| Google personal-content / Results-about-you style route after repeated privacy-route or source-owner drift | `repeated reappearance`, `split-owner repeat threshold`, `sensitive local-only submission`, and `local-only memory retained` | privacy proof may need current screenshots or URLs, but repeated sensitive-content drift should not create a public evidence vault or public pattern label |

| split source/search/recipient/archive/accessibility route after repeated disagreement between successor owners | `repeated split-owner mismatch`, `split-owner repeat threshold`, `split owners must separate`, `split surface shell`, and `route split retained` | repeated disagreement means one shell is probably hiding several route truths; the archive should split affected surfaces before it imposes one stability outcome |

## Boundary conditions

This layer should not be used when only one of the following is true:

- there has been only one material post-migration drift event and `YD0-YD4` can still refresh it
  honestly;
- the current owner, provider, recipient, archive, or support route is still inside its own
  published review, expiry, reflection, or service window;
- the only repeated signal is ordinary search/index/cache lag with no changed owner, route, URL,
  portal, prerequisite, proof object, archive time slice, or learner dependency;
- the repeated events concern different learners, recipients, URLs, images, records, owners, routes,
  or platforms and do not form one affected-surface pattern;
- the prior proof was sealed, local-only, historical, or expired and no current owner needs it;
- a confidential safety, accommodation, records, privacy, legal, or provider process already
  controls repeat handling; or
- a current route names a specific retry, appeal, status, escalation, or expiry rule that should
  govern instead of a portable threshold.

In those cases, publish `one prior drift only`, `ordinary lag pattern only`, `no threshold met`,
`current route native window applies`, `old proof expired`, `none current`, `protected or sensitive
local-only submission`, `no active route action`, or `none inherited` rather than treating repeat
drift as automatic instability, permanent redesign failure, or learner fault.

## What this closes

This closes `FT-0143`.

The archive no longer stops at "refresh the proof after migration drift". It can now publish a
minimal repeat-drift stability threshold: what repeated, where it repeated, what threshold was met,
who owns stability proof, what disposition follows, whether the learner has any current action, and
when threshold memory exits or narrows.

It also opens one narrower seam.

After a repeat-drift threshold opens a bounded stability watch, local redesign, route split, or
decommissioned-route posture, the archive may still need a tiny successor-stability operation /
repair-proof / decommission-exit layer for cases where the route is actively watched, repaired,
split, or retired — without turning threshold status into permanent migration surveillance, public
route-failure stigma, or an all-surface decommissioning certificate.
