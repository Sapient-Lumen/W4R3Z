# First post-second-dewatch relapse and renewed-repair memory defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request
routes.

It can already say:

- how repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how a first rewatch operates, proves repair, exits, de-watches, splits, redesigns, retires, or
  becomes residue;
- how a later post-dewatch relapse recalls repaired-route memory;
- how repeated post-dewatch relapse crosses a repaired-route rewatch threshold only on material
  repeat facts; and
- how renewed rewatch operates, refreshes repair, protects learner action, and exits through a
  second dewatch, split, redesign, retirement, or residue state.

That is still not enough.

After a renewed rewatch exits or second-dewatches, a later recurrence creates a new pair of
mistakes. One mistake says: because the route has already relapsed twice, every later signal
automatically reopens renewed rewatch, proves permanent repaired-route instability, and justifies
public proof retention. The opposite mistake says: because the second dewatch closed cleanly, the
shell must forget every prior repair-refresh fact and handle the next recurrence as if no owner,
proof, route, protected-path, recipient, or clock history existed. Both defaults are too blunt. A
repaired route can later reappear only in a search or archive reflection. A recipient correction can
reappear after the second dewatch. A protected route can diverge again while proof must stay local.
A redesign owner can miss a new proof point. A retired-route posture can revive. No-active-route
residue can acquire a current owner. Or repair-refresh proof can age enough that a current learner
dependency needs a limited memory recall, without turning old second-rewatch proof into a public
vault.

This document adds one thing only:

- a **tiny post-second-dewatch relapse / renewed-repair memory field set** for hot-exam recipient
  followup shells after `ZA0-ZA4` has closed renewed rewatch, refreshed repair, minimized proof, or
  completed a second dewatch, but before the archive treats every later recurrence as automatic
  renewed rewatch, permanent repeated-repair stigma, duplicate learner filing, or total fresh-start
  amnesia.

That means the archive now asks a narrower question than before. It no longer asks only **how
renewed rewatch operates and exits**. It now asks **when a later post-second-dewatch recurrence may
recall limited renewed-repair memory, how current proof age and owner status control that recall,
what the learner safely does now, and when the shell closes, reminimizes, opens a threshold
candidate, or routes into protected, recipient, redesign, retired-route, no-active-route, or
split-surface handling**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation,
Google-Search-only, and source-side permanent-removal boundaries rather than a durable all-cycle
renewed-repair memory certificate. Google's Refresh Outdated Content route is exact page/image URL,
changed/gone-content, request-status, additional-URL, and expiry based rather than a permanent
repair-refresh proof vault. Google's personal-content routes keep Search removal, source-page
removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb
separates local source edits, emergency edits, primary-contact follow-up, campus-search and
lookahead ownership, caching, and major-search-engine non-control. Princeton separates local
deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search
handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support,
Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, project
closeout, support tickets, and accommodation routing. Internet Archive asks for URL, time-period,
control-period, and review context before exclusion. Bing distinguishes temporary block,
up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites,
exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals
support a tighter archive rule: **the next truthful portability gain here is one tiny
post-second-dewatch memory layer for second-exit basis, later relapse signal, renewed-repair scope,
scoped memory recall, current proof age, owner status, learner-safe action, disposition,
reminimization, and reopen triggers — but not one automatic third rewatch, one permanent
repeated-repair stigma label, one duplicate-filing duty, one public second-repair proof vault, one
all-surface renewed-repair certificate, or one total amnesia reset.** See `B269`.

   failed`, `same retired route revived`, `same no-active-route residue gained owner`, `split

## Minimal publication sentence

A shell using this layer should be able to publish a sentence no more complicated than:

> `After second dewatch, [exit_basis] is the prior state. The current signal is
[relapse_signal_and_scope]. The shell recalls [renewed_repair_memory] only for [current_dependency].
Current proof and owner status are [proof_age_owner_status]. Learner action now is
[learner_safe_action]. The disposition is [post_second_dewatch_disposition_and_reopen].`

If the shell cannot fill those slots, it should publish `not published`, `none inherited`, `ordinary
downstream lag`, `route-native rule controls`, `protected proof local-only`, or `no learner action
now` rather than imply renewed-repair instability.

## Default interpretation rules

1. **Second dewatch is not amnesia.** A clean second exit can minimize public proof, but it does not
   forbid a later shell from recalling the minimum renewed-repair summary needed for a current
   owner, recipient, proof, clock, protected-route, official-record, appeal, or learner-remedy
   decision.
2. **Later reappearance is not automatic third watch.** A later signal must have a current affected
   scope and live dependency before it becomes anything more than ordinary lag, non-material close,
   or route-native handling.
3. **Scope beats anxiety.** Count only recurrence inside the same repaired route pair, recipient
   portal, protected route, proof object, clock, source/search/archive surface, redesign handoff,
   retired-route residue, no-active-route residue, or split surface.
4. **Current proof outranks old repair confidence.** A second-dewatch closure, old screenshot,
   expired request row, or stale owner claim may explain history, but current source, recipient,
   official-record, protected-route, archive/platform, clock, redesign, or successor-owner proof
   controls action now.
5. **Learner action stays prospective and safe.** If owners or routes disagree after second dewatch,
   publish one safe route, dual-route recognition, clock hold, protected local submission, manual
   support, owner-only repair, or no action before any refiling duty.
6. **Protected proof stays protected.** Repeated recurrence does not move accommodation,
   accessibility, privacy, safety, appeal, or records proof into the public renewed-repair layer.
7. **Memory must dispose of itself.** The shell should close as ordinary lag, non-material close,
   scoped memory recall, proof-refresh request, recipient correction, protected-route retention,
   redesign review, retired-route posture, no-active-route residue, split-surface shell,
   route-native control, threshold candidate, or reminimized false alarm rather than remain a public
   repeated-repair warning forever.

## Worked examples

### Example A — second-dewatched search reflection only

A renewed rewatch second-dewatched after the source page stayed removed, the recipient portal
accepted the repaired route, and the public proof summary was minimized. Three months later, a
search snippet briefly shows the old title while the source, recipient record, official record, and
learner-facing route remain current.

Publish:

- `post_second_dewatch_exit_basis_token = second dewatch completed`;
- `post_second_dewatch_relapse_signal_and_scope_token = same search result family reflection`;
- `renewed_repair_memory_recall_token = public minimized summary only`;
- `current_proof_age_owner_status_token = current source proof`;
- `learner_safe_action_after_second_dewatch_token = none current`; and
- `post_second_dewatch_disposition_and_reopen_token = ordinary lag only` or `reminimized false
  alarm`.

Do not reopen renewed rewatch merely because a downstream search reflection appears without a
current owner, clock, recipient, protected-route, or learner dependency effect.

### Example B — recipient correction reappears after second dewatch

A repaired route second-dewatched after the recipient-of-record corrected its portal and confirmed
that one deadline controlled. In a later cycle, the same recipient portal again accepts the retired
route while the official source and controlling office still publish the repaired deadline.

Publish:

- `post_second_dewatch_exit_basis_token = recipient record corrected`;
- `post_second_dewatch_relapse_signal_and_scope_token = same recipient portal conflict`;
- `renewed_repair_memory_recall_token = recipient correction marker recalled`;
- `current_proof_age_owner_status_token = current official-record proof` or `current
  recipient-of-record proof`;
- `learner_safe_action_after_second_dewatch_token = submit once with dual-route recognition`; and
- `post_second_dewatch_disposition_and_reopen_token = recipient correction reopened` or
  `repeat-relapse threshold candidate`.

Do not convert the reappearing recipient error into duplicate learner filing unless the current
recipient-of-record route expressly requires it and protects the learner from duplicate-clock or
wrong-route harm.

### Example C — protected route conflict reappears

A renewed rewatch closed with a public repaired route and a protected accommodation route retained
locally. Later, the public page again contradicts the protected local route. The proof needed to
resolve the conflict includes sensitive accommodation facts.

Publish:

- `post_second_dewatch_exit_basis_token = protected route retained`;
- `post_second_dewatch_relapse_signal_and_scope_token = same protected route conflict`;
- `renewed_repair_memory_recall_token = protected proof local-only`;
- `current_proof_age_owner_status_token = current protected owner proof`;
- `learner_safe_action_after_second_dewatch_token = protected local-only submission`; and
- `post_second_dewatch_disposition_and_reopen_token = protected route retained` or `local-only
  memory retained`.

Do not publish protected proof or route details merely because a second-dewatched public route
relapsed again.

### Example D — no-active-route residue gains a current owner

A renewed rewatch exited as no-active-route residue after both the old and repaired owner routes
disappeared. A later page identifies a current office and a support ticket route for the same
exam-family record correction, but the office has not yet confirmed whether the old repaired route
still controls.

Publish:

- `post_second_dewatch_exit_basis_token = no-active-route residue`;
- `post_second_dewatch_relapse_signal_and_scope_token = same no-active-route residue gained owner`;
- `renewed_repair_memory_recall_token = public minimized summary only` or `memory unavailable
  residue`;
- `current_proof_age_owner_status_token = current successor owner proof` or `owner changed`;
- `learner_safe_action_after_second_dewatch_token = wait for owner confirmation` or `manual local
  support only`; and
- `post_second_dewatch_disposition_and_reopen_token = repair-refresh proof requested` or
  `no-active-route residue`.

Do not treat newly discovered ownership as proof that learners were previously at fault for using
the only safe route then visible.

### Example E — redesign proof fails again

A renewed rewatch second-dewatched after the redesign owner accepted a corrected route instruction
and a proof point. In the next cycle, the redesigned page again publishes two official-looking paths
and misses its next named proof point.

Publish:

- `post_second_dewatch_exit_basis_token = redesign proof accepted`;
- `post_second_dewatch_relapse_signal_and_scope_token = same redesign handoff failed`;
- `renewed_repair_memory_recall_token = redesign proof marker recalled`;
- `current_proof_age_owner_status_token = current redesign proof` or `proof mismatched`;
- `learner_safe_action_after_second_dewatch_token = use more protective route until resolved` or
  `submit once with dual-route recognition`; and
- `post_second_dewatch_disposition_and_reopen_token = redesign review opened` or `repeat-relapse
  threshold candidate`.

Do not treat a redesign proof miss as proof that every source, search, archive, recipient, protected
route, official record, and learner filing surface failed.

## Non-goals

This layer does **not** create:

- an automatic third rewatch after every later recurrence;
- a permanent repeated-repair instability label;
- a public second-rewatch proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, all-record, or all-engine renewed-repair
  certificate;
- a universal memory-recall window for every route family;
- a no-memory reset after second dewatch; or
- a rule that every later recurrence must be counted toward a new threshold.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about repairing a route once, or even twice. It
is about preventing repair history from becoming either permanent suspicion or unusable memory.

This layer matters because both extreme defaults harm learners and owners. One bad default says a
route that needed renewed repair is forever suspicious, so every later signal justifies watch
status, duplicate filing, and public proof retention. Another bad default says a clean second
dewatch wipes history so completely that owners must rediscover the same proof, protected-route
conflict, recipient correction, redesign miss, retired-route posture, or no-active-route residue
from scratch. The portable answer is narrower: publish the second-exit basis, current signal,
affected renewed-repair scope, limited memory recall, current proof age and owner status,
learner-safe action, and a disposition that closes, reminimizes, asks for proof refresh, corrects
the recipient record, retains protected handling, opens redesign review, revives retired-route
posture, names residue, splits a surface, or marks a threshold candidate on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `ZA0-ZA4` has not already closed renewed rewatch, refreshed repair, minimized proof, or completed
  a second dewatch;
- the current question is still how renewed rewatch operates, proves repair refresh, or
  second-dewatches rather than how a later recurrence recalls memory;
- the later event is unrelated to the repaired route pair or affected surface;
- the later signal is only search, cache, crawler, archive, image, or downstream copy lag with no
  current learner-facing owner, proof, clock, recipient, protected-route, official-record, or live
  dependency effect;
- a route-native process already names post-second-dewatch relapse handling, renewed-repair memory
  recall, current proof age, learner-safe action, disposition, and reopen triggers;
- the only available proof is stale, expired, screenshot-only, owner-claim-only, anecdotal,
  unrelated to a current owner, or unrelated to a learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules
  already control proof handling and should stay local-only; or
- repeated post-second-dewatch recurrence has already crossed a named threshold and the question is
  now threshold operation rather than first memory recall.

In those cases, publish `ordinary lag only`, `unrelated new path`, `route-native rule controls`,
`protected local-only route`, `no learner action now`, `current renewed rewatch still open`, `fresh
first-cycle conflict`, `repeat-relapse threshold already open`, `reminimized false alarm`, or `none
inherited` rather than creating a post-second-dewatch memory layer.

## What this closes

This closes `FT-0155`.

The archive no longer stops at "renewed rewatch operated and second-dewatched". It can now publish a
minimal post-second-dewatch relapse / renewed-repair memory layer: second-exit basis, later relapse
signal, renewed-repair scope, scoped memory recall, current proof age, owner status, learner-safe
action, disposition, reminimization, and reopen triggers when a route later relapses again,
repair-refresh proof ages, minimized second-rewatch memory must be recalled, protected or recipient
corrections reappear, redesign proof fails, retired-route posture revives, no-active-route residue
exposes a current owner, or split-surface recurrence becomes visible.

It also opens one narrower seam.

After later post-second-dewatch relapse has been classified and renewed-repair memory has been
recalled or minimized, the archive may still need a tiny repeat post-second-dewatch relapse /
renewed-repair rewatch-threshold layer for cases where the same route, owner, proof object, clock,
recipient, protected route, redesign handoff, retired-route posture, no-active-route residue,
source/search/archive surface, or official-record dependency recurs again — without making every
recurrence automatic third rewatch, every repeated repair a permanent stigma label, every learner
action duplicate filing, or every second-rewatch proof object a public vault.
