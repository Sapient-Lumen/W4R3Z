# Portable recent-repair sensitivity and accelerated re-cooling defaults for restored ordinary packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance
envelope has cooled locally, regained portable status, survived its watched re-entry cycle, and then
restored ordinary promoted status, can the first now-ordinary cycle itself carry one shared
recent-repair sensitivity / accelerated re-cooling package, or should that post-restoration caution
still remain local even though probation has technically expired?**

The archive's answer is narrower again:

> only maintenance classes whose **first post-restoration ordinary-cycle caution truth** remains
stable across the reuse scope should carry one shared recent-repair sensitivity / accelerated
re-cooling package. In the starter canon, only restored-to-ordinary `PME-LABEL` usually carries one
shared post-restoration caution package; record-owner calendar upkeep, route calendars, and safety
calendars should keep that first ordinary-cycle caution local.

The point is to avoid three opposite errors at once:

- **snap-back normalization** — a service treats restored ordinary status as though all
  recent-repair caution has already expired, even though the very first ordinary cycle after
  probation is still where a repaired portable story can prove too fragile;
- **shadow-caution laundering** — a service publishes one shared restoration package but then runs
  the first ordinary cycle under owner-specific caution, unpublished fast-collapse rules, or hidden
  residue review that the portable story conceals;
- **permanent repair stigma** — a maintenance class whose first restored ordinary cycle really can
  carry one small shared caution package never earns it and therefore has to describe the same
  recent-repair sensitivity locally forever.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI
toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's
current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance
snapshots; Study Mode and related learning surfaces continue to frame the product direction as
guided understanding rather than quick-answer posture; and UNESCO's 2026 teacher and student
competency frameworks keep human agency and AI pedagogy central. See `B11`, `B23`, `B143`, `B146`,
`B149`, `B150`, `B151`.

## Three post-restoration caution portability tiers

The archive now distinguishes three post-restoration caution portability tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `RSC-BOTH` | the restored ordinary envelope carries one shared recent-repair sensitivity floor and one shared accelerated re-cooling trigger family | the fact that the first restored ordinary cycle is still caution-marked, and the trigger family that collapses it back to local cooling faster than an ordinary promoted cycle would | any stricter local reviewer, any extra local checkpoint, and any stronger local publication or challenge route |
| `RSC-FLOOR` | the envelope carries only one shared recent-repair sensitivity floor | the fact that the first restored ordinary cycle is still under bounded recent-repair caution | the actual accelerated re-cooling trigger family and any local caution residue record |
| `RSC-LOCAL` | the envelope carries no shared post-restoration caution package | only the earlier basket / numeric / checkpoint / republication / cumulative-cycle / re-promotion / watched-cycle / restoration tiers | both the recent-repair sensitivity floor and the accelerated re-cooling package |

The archive is deliberately asymmetric again:

> post-restoration caution portability is harder to earn than restoration portability. A class can
carry one shared probation-expiry / ordinary-status package while the truth about the **first
ordinary cycle after restoration** still remains owner-local.

## Five tests for whether first-ordinary-cycle caution truth really travels

A restored-to-ordinary promoted maintenance envelope may harden above `RSC-LOCAL` only when all five
tests hold.

1. **same-first-ordinary-cycle object test** — the first restored ordinary cycle is genuinely the
   same maintenance object across the reuse scope rather than using one owner-specific shell
   cleanup, one calendar reshuffle, or one policy tidy-up to stand in for many different
   post-restoration realities.
2. **same-recent-repair-meaning test** — saying that the first restored ordinary cycle is still
   caution-marked means the same thing across the reuse scope: ordinary promoted status has
   returned, but the service is still treating that first cycle as unusually sensitive to relapse
   from recent repair.
3. **same-accelerated-re-cooling-truth test** — the minimal trigger family for collapsing that first
   ordinary cycle back to local cooling can be described in one reusable way without concealing
   owner-specific relapse logic, unpublished side review, or hidden residue checks.
4. **no-shadow-caution test** — the shared package does not make one owner's local shadow caution or
   unpublished fast-collapse rule look like ordinary portable sensitivity when the real first-cycle
   scrutiny still differs materially by family or object.
5. **same-next-cycle-settling boundary test** — clearing the caution-marked ordinary cycle really
   means the same thing for a subsequent fully settled cycle across the proposed scope rather than
   still depending on local committee sign-off, local freshness tests, or owner-specific
   recent-repair residue.

Failing the first, third, fourth, or fifth test keeps the envelope at `RSC-LOCAL`. Failing only the
third may eventually point to `RSC-FLOOR`, but the starter canon does not yet use that middle tier.

## The starter recent-repair sensitivity package

The archive now names one shared recent-repair sensitivity floor and one shared accelerated
re-cooling package.

| Code | Meaning |
|---|---|
| `RR-1ORDINARY` | the **first ordinary cycle after restoration** still runs as a recent-repair-sensitive ordinary portable cycle rather than as fully settled ordinary trust |
| `RC-ACCEL-LOCAL` | during that recent-repair-sensitive ordinary cycle, any unresolved breach, fresh reset cluster, basket / field-logic expansion, owner-family-conditioned meaning drift, challenge-route weakening, or other caution-cycle failure collapses the path back to local cooling faster than an ordinary promoted cycle would |

The archive does **not** yet create a richer post-restoration caution ladder. The starter canon is
deliberately small:

- no restored-to-ordinary promoted maintenance envelope currently becomes fully settled on the very
  first ordinary cycle after probation expires;
- no restored-to-ordinary promoted maintenance envelope currently carries one shared "two ordinary
  cycles of caution" rule;
- where the archive refuses a shared post-restoration caution package, services must still publish a
  **local** first-ordinary-cycle caution rule, or say plainly that restored ordinary status remains
  under owner-local recent-repair sensitivity.

## The archive's starter post-restoration caution answers

### Restored-to-ordinary `PME-LABEL` usually hardens as `RSC-BOTH` with `RR-1ORDINARY + RC-ACCEL-LOCAL`

Restored-to-ordinary `PME-LABEL` may usually carry **both** one shared recent-repair sensitivity
floor and one shared accelerated re-cooling trigger family across its promoted branch scope.

Why the archive allows this:

- label/plain-language restoration usually means the same thing across the branch scope: a wording
  shell cooled locally, re-entered portability, survived its watched cycle, and has now restored
  ordinary promoted status, but the first ordinary cycle after that restoration is still unusually
  sensitive to fresh shell drift;
- the minimum caution-cycle failure family can usually be described the same way too: new shell
  drift, unresolved breach residue, reset-cluster formation, field-logic expansion, or rights-shell
  weakening means the first ordinary cycle after restoration did not hold strongly enough to keep
  riding ordinary promoted status;
- the boundary to a more fully settled following cycle is still thin but usually truthful here: if
  the first restored ordinary label cycle finishes cleanly without those failures, the path can
  usually stop publishing special recent-repair caution.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, `CFP-BOTH`,
`RXP-BOTH`, `RPW-BOTH`, and `ORS-BOTH`, it may usually also inherit `RSC-BOTH` with `RR-1ORDINARY +
RC-ACCEL-LOCAL`.

What this means in practice:

1. once the watched re-entry cycle closes cleanly and ordinary promoted status is restored, the next
   label-maintenance cycle is ordinary again but still marked as recent-repair-sensitive;
2. that cycle must still publish its own checkpoint / breach / residue truth rather than pretending
   the recent repair no longer matters;
3. only after that first restored ordinary cycle finishes cleanly may the following ordinary cycle
   stop carrying the special post-restoration caution package.

What still collapses `RSC-BOTH` immediately:

- any fresh shell drift, unresolved breach, reset cluster, basket or field-logic expansion,
  owner-family-conditioned meaning drift, or challenge-route weakening during the first restored
  ordinary cycle;
- any attempt to treat the restoration package as though it already exhausted all recent-repair
  caution before that first ordinary cycle has actually closed;
- any effort to smuggle owner-specific shadow caution or unpublished fast-collapse logic underneath
  the portable package.

### Restored-to-ordinary `PME-CALENDAR` for `AF-RECORD` stays `RSC-LOCAL`

Record-owner calendar upkeep should currently keep post-restoration recent-repair sensitivity and
accelerated re-cooling local.

Why:

- even after ordinary promoted status is restored, the meaning of "still unusually sensitive because
  repair was recent" depends too much on local record cadence, issuance windows, or board timing;
- a shared accelerated re-cooling family would therefore overstate how comparable the first
  ordinary-cycle caution truth really is across record regimes;
- some record calendars may genuinely need no extra ordinary-cycle caution, while others may still
  need owner-specific shadow review, which defeats a truthful shared package.

### Restored-to-ordinary `PME-CALENDAR` for `AF-ROUTE` stays `RSC-LOCAL`

Route-case calendar upkeep also keeps post-restoration recent-repair sensitivity local.

Why:

- route calendars already keep restoration-to-ordinary trust local because callback truth, partner
  inventory, and exposure semantics vary too much across regimes;
- the meaning of a "recently repaired but ordinary again" route calendar therefore remains too
  dependent on local route architecture to claim one reusable caution package honestly.

### Restored-to-ordinary `PME-CALENDAR` for `AF-SAFETY` stays `RSC-LOCAL`

Safety/supervisor calendar upkeep remains fully local after restoration.

Why:

- safety calendars are closely coupled to live exposure judgment, duty staging, or safeguarding
  timelines;
- a shared post-restoration caution package would risk hiding meaningful differences in local
  protective review and the seriousness of what a fast-collapse trigger would actually mean.

## What the archive is refusing for now

The archive is intentionally declining four stronger claims:

1. any shared post-restoration caution package that says restored ordinary status is already fully
   settled on the first ordinary cycle after probation expires;
2. any shared post-restoration caution package for record-owner, route, or safety calendar
   envelopes;
3. any shared package that lets a first restored ordinary cycle fail softly under hidden local
   caution rather than publishing an accelerated return to local cooling;
4. any claim that a restoration package alone already tells us when all recent-repair sensitivity
   has expired.

## Why this counted as a real archive gain

The archive already knew which promoted maintenance envelopes can travel, which quantitative and
proof layers sometimes travel with them, which fresh-cycle and cumulative-cycle layers sometimes
travel too, which of those envelopes can regain portable status under one shared monitored re-entry
package, which first re-promoted cycle can carry one shared watched package, and which clean watched
cycles can restore ordinary promoted status. But it still lacked the next tighter answer:

- whether the first ordinary cycle after that restoration can carry one shared recent-repair
  sensitivity package at all;
- and whether the archive should distinguish classes where that post-restoration caution truth
  travels from classes where it still depends too heavily on local repair residue.

This revision now answers that narrower question with one small ratchet:

- three post-restoration caution portability tiers;
- five tests for whether first-ordinary-cycle caution truth really travels;
- one tiny starter package, `RR-1ORDINARY + RC-ACCEL-LOCAL`;
- and a starter judgment that only restored-to-ordinary `PME-LABEL` usually carries it.

That is a real operating gain because it blocks three opposite mistakes at once:

- treating restored ordinary status as fully settled immediately after watched-cycle restoration;
- making post-restoration label maintenance permanently local even when its first ordinary-cycle
  caution story is actually stable enough to travel;
- and using a portable restoration story to conceal shadow caution or unpublished fast-collapse
  rules.

## Current archive bet

The archive's current best guess is that **portable packet maintenance should become harder at each
stage: baskets travel first, then some numeric bands, then some checkpoint / breach packages, then
some fresh-cycle republication and recurrence duties, then at most one shared cumulative-cycle
ceiling and cooling rule, then at most one shared monitored re-promotion package, then at most one
shared watched re-entry package, then at most one shared restoration package, and only after that
may a very small post-restoration recent-repair sensitivity package sometimes travel — with only
restored-to-ordinary label/plain-language maintenance usually carrying one shared `RR-1ORDINARY +
RC-ACCEL-LOCAL` package while record-owner calendar upkeep, route calendars, and safety calendars
keep first ordinary-cycle caution local.**
