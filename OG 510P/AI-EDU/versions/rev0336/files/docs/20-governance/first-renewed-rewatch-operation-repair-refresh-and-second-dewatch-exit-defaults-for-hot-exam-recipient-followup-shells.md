# First renewed rewatch operation, repair-refresh, and second-dewatch-exit defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request
routes.

It can already say:

- how repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how that first rewatch operates, proves repair, exits, de-watches, splits, redesigns, retires, or
  becomes residue;
- how a later post-dewatch relapse recalls repaired-route memory; and
- how repeated post-dewatch relapse crosses a repaired-route rewatch threshold only on material
  repeat facts.

That is still not enough.

Once a repaired-route rewatch threshold has opened after dewatch, the next temptation is to treat
the renewed operation as proof that the route pair now belongs under permanent surveillance. The
opposite error is also dangerous: because the first rewatch already repaired once and dewatched
once, an owner may treat the renewed threshold as a loose status label rather than actual
repair-refresh work. A recipient portal can again accept the retired route. A protected local route
can again diverge while proof remains non-public. A redesign owner can miss a repair-refresh proof
point. A route can move from repaired route pair to split surface, retired-route residue, or
no-active-route residue. Or a second clean cycle can show that renewed rewatch should dewatch again
and minimize proof rather than keep a public repaired-route dossier alive.

This document adds one thing only:

- a **tiny renewed rewatch operation / repair-refresh / second-dewatch-exit field set** for hot-exam
  recipient followup shells after `YZ0-YZ4` has found that repeated post-dewatch relapse crossed a
  repaired-route rewatch threshold, but before the archive treats that threshold as permanent
  surveillance, public route-pair stigma, automatic duplicate learner filing, or an indefinite
  repaired-route proof vault.

That means the archive now asks a narrower question than before. It no longer asks only **when
repeated post-dewatch recurrence crosses a repaired-route rewatch threshold**. It now asks **how
that renewed threshold operates, what repair-refresh proof can close it, what the learner safely
does while owners refresh repair, and when a second dewatch, split, redesign, retirement, residue
state, or reminimization is truthful**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation,
Google-Search-only, and source-side permanent-removal boundaries rather than a durable all-surface
rewatch operation. Google's Refresh Outdated Content route is exact page/image URL,
changed/gone-content, request-status, additional-URL, and expiry based rather than a universal
repair-refresh certificate. Google's personal-content routes keep Search removal, source-page
removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb
separates local source edits, emergency edits, primary-contact follow-up, campus-search and
lookahead ownership, caching, and major-search-engine non-control. Princeton separates local
deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search
handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support,
Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, support
tickets, project closeout, and accommodation routing. Internet Archive asks for URL, time-period,
control-period, and review context before exclusion. Bing distinguishes temporary block,
up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites,
exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals
support a tighter archive rule: **the next truthful portability gain here is one tiny renewed
operation layer for run-state, affected scope, current owner, cadence, repair-refresh proof,
learner-safe action, second-dewatch exit, minimization, and reopen triggers — but not one permanent
repaired-route dashboard, one public route-pair stigma, one duplicate-filing duty, one indefinite
proof vault, or one all-surface repair-refresh certificate.** See `B268`.

## Small field set for renewed rewatch operation, repair refresh, and second dewatch exit

| Code | Meaning | Default archive action |
|---|---|---|
| `ZA0-NO-PERMANENT-REWATCH-DASHBOARD-PUBLIC-STIGMA-DUPLICATE-FILING-OR-INDEFINITE-REPAIR-VAULT` | a repaired-route threshold can open renewed work, but it does not create permanent surveillance, stigma, duplicate learner filing, or a public repair vault | require a run-state, affected scope, current owner, cadence or event trigger, repair-refresh proof, learner-safe action, exit condition, minimization posture, and reopen trigger before extending beyond the threshold shell |
| `ZA1-PUBLISH-RENEWED-REWATCH-RUN-STATE-SCOPE-OWNER-AND-CADENCE-LIMIT` | renewed rewatch must say what is actually operating and who owns it | publish whether the renewed operation is owner reconciliation, route-pair repair refresh, recipient-record correction, protected-route handling, redesign proof review, retired-route posture, no-active-route residue review, split-surface handling, ordinary-lag review, or dewatch-eligible clean cycle, plus the affected route, proof, clock, recipient, protected route, source, search, archive, or record scope |
| `ZA2-PUBLISH-REPAIR-REFRESH-PROOF-PRECEDENCE-AND-OWNER-RECONCILIATION` | a second operation needs current proof, not revived confidence from the first repair | publish current source, search, archive, recipient, official-record, protected-route, redesign, clock, or successor-owner proof; label stale, expired, screenshot-only, owner-claim-only, local-only, pending, or unavailable proof; and state which current owner or precedence rule controls until repair refresh completes |
| `ZA3-SEPARATE-LEARNER-SAFE-ACTION-FROM-OWNER-REFRESH-DUPLICATE-FILING-AND-PROOF-VAULTING` | renewed owner-side repair should not become learner fault or proof reburdening | publish no action, one safe route, dual-route recognition, clock hold, longer current window, protected local submission, manual support, route-native optional refile, or owner-only repair before asking the learner to refile; do not publish protected proof or revive old repair screenshots without current route-native authority |
| `ZA4-PUBLISH-SECOND-DEWATCH-EXIT-SPLIT-MINIMIZATION-AND-REOPEN-TRIGGERS` | renewed rewatch must close, dewatch again, split, redesign, retire, become residue, or minimize on named facts | publish second dewatch, refreshed repaired route, recipient correction, protected route retained, route split retained, redesign proof accepted, retired-route residue, no-active-route residue, renewed rewatch extended, closed without learner action, local-only memory, or material reopen triggers tied to current route, owner, proof, clock, recipient, protected-route, source, search, archive, or official-record facts |

## Practical renewed-rewatch defaults

| Situation | Minimal publication | Why |
|---|---|---|
| repaired-route threshold opens owner reconciliation for the same route pair | `renewed rewatch active` or `owner reconciliation reopened`, affected repaired route pair, current owners, repair-refresh proof state, learner-safe action, and a named second-dewatch condition | repeated threshold status can require owners to refresh repair, but it should not create a permanent public repaired-route watch |
| recipient portal again accepts the wrong or retired route after prior dewatch | `recipient-record correction reopened`, recipient-of-record owner, current route proof, `submit once with dual-route recognition`, and whether the recipient record was refreshed | the live dependency is the recipient or record effect; timely learner action should be preserved while the record owner repairs the mismatch |
| protected accommodation, accessibility, privacy, safety, appeal, or records route relapses during renewed rewatch | `protected-route handling`, protected owner proof, `protected local-only submission`, and `protected route retained` or `route split retained` | sensitive proof should not become a public proof vault merely because the repaired route pair is unstable again |
| source, search, archive, or image surfaces disagree after a repair-refresh claim | `route-pair repair refresh opened`, source owner, provider or archive status, proof age, and `no learner action now` or one safe route | one refreshed source does not prove every downstream surface is refreshed; one lagging downstream surface does not prove the repaired route failed |
| two clocks recur after a prior dewatch | `owner reconciliation reopened`, `same clock or deadline`, route-native clock proof or `repair refresh unresolved`, and `use longer current window until resolved` | adverse clocks should not attach until the current controlling owner and window are visible |
| the same route instructions keep creating renewed relapse | `redesign proof review`, redesign owner, affected proof object or prerequisite, `owner-only repair refresh`, and post-redesign reopen triggers | repeated ambiguity can show that route instructions need renewed redesign proof without forcing all learners to refile or keeping old proof public |
| old route appears only in search, image, archive, or mirror surfaces while source, recipient, and record owners agree | `ordinary-lag review` or `retired-route posture review`, current source / recipient proof, `no learner action now`, and minimized memory | downstream visibility can be documented without treating the old route as current or the repair refresh as failed |
| no current owner can refresh the repair | `no-active-route residue review`, last current proof, `manual local support only` or `no action now`, and material reopen triggers | absence of a repair owner should be published as residue, not silence-as-repair, silence-as-denial, or learner abandonment |
| renewed rewatch completes a clean cycle with current proof | `second dewatch completed`, repair-refresh proof, refreshed repaired route or retained split, minimized memory, and reopen triggers | clean second exit restores ordinary handling without erasing the bounded memory needed for a later material relapse |

## What this layer now makes portable

Hot-exam recipient followup shells may now publish one tiny `ZA0-ZA4` layer after `YZ0-YZ4` when the
archive needs to say not merely that **repeated post-dewatch relapse crossed a repaired-route
rewatch threshold**, but that **renewed rewatch is operating, what repair-refresh proof can close
it, what the learner safely does while owners refresh repair, and how a second dewatch, split,
redesign, residue state, or minimization occurs**.

That means a shell may now truthfully say things like:

- `the repaired-route threshold opened renewed owner reconciliation; submit once and no adverse
  clock runs until conflict-aware notice names the controlling route`;
- `the recipient record is being corrected again; timely action through either named route is
  protected while the recipient owner confirms`;
- `public repair-refresh proof controls, but protected accommodation proof remains local-only and
  the protected route stays split`;
- `the old route appears only in a search or archive surface; keep retired-route residue
  time-slice-specific and do not reopen learner action`; or
- `renewed rewatch closed after one clean repair-refresh cycle; minimize public proof and reopen
  only on material route, owner, clock, recipient, protected-route, source, search, archive, or
  official-record facts`.

It still may not pretend:

- that threshold status creates permanent repaired-route surveillance;
- that a route pair deserves a public instability label forever;
- that repeated owner disagreement is learner fault;
- that learners must duplicate filings while owners refresh repair;
- that old screenshots, expired request rows, or downstream copies prove current failure by
  themselves;
- that owner repair-refresh claims automatically control every source, search, archive, recipient,
  protected-route, and official-record surface; or
- that second dewatch erases all bounded repair memory.

## Non-goals

This layer does **not** create:

- a standing renewed rewatch for every repeated post-dewatch threshold;
- a public repaired-route instability label;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- an indefinite repaired-route proof vault;
- a public repair-refresh certificate for all surfaces;
- a protected-proof publication duty;
- a universal cadence for every renewed rewatch;
- an automatic second dewatch after one owner claim; or
- a no-memory reset after renewed rewatch closes.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about deciding when recurrence crosses a
threshold. It also has to keep the actual repair work bounded, current, and safe for learners once
the threshold opens.

This layer matters because both extreme defaults are harmful. One bad default says repeated
post-dewatch relapse proves permanent repaired-route instability, so every learner-facing shell
becomes a surveillance surface. Another says the first repair already proved enough, so a renewed
threshold can stay an empty label while owners never refresh proof. The portable answer is narrower:
publish the renewed run-state, affected scope, owner, cadence, and current repair-refresh proof;
protect learner action from duplicate-filing and wrong-route fault; then close, dewatch again,
split, redesign, correct the recipient record, retain protected handling, publish residue, or
minimize proof on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `YZ0-YZ4` has not already found that repeated post-dewatch relapse crossed a repaired-route
  rewatch threshold;
- the current question is only whether repetition crosses a threshold rather than how an opened
  renewed operation runs;
- the later signal is unrelated to the repaired route pair or affected surface;
- the repeat is only search, cache, crawler, archive, or downstream copy lag with no current
  learner-facing owner, proof, clock, recipient, protected-route, or live dependency effect;
- a route-native process already names renewed rewatch operation, repair-refresh proof, learner-safe
  action, second-dewatch exit, and memory minimization rules;
- the only available proof is stale, expired, screenshot-only, owner-claim-only, anecdotal, or
  unrelated to a current owner or learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules
  already control proof handling and should stay local-only; or
- no current learner, owner, recipient, proof object, clock, protected route, official-record,
  source, search, archive, or route dependency remains.

In those cases, publish `threshold met but renewed rewatch not opened`, `ordinary lag only`,
`unrelated new path`, `route-native rule controls`, `protected local-only route`, `no learner action
now`, `no active owner`, `repaired-route threshold already closed`, `minimized memory`, or `none
inherited` rather than creating a renewed rewatch operation layer.

## What this closes

This closes `FT-0154`.

The archive no longer stops at "repeated post-dewatch relapse crossed a repaired-route threshold".
It can now publish a minimal renewed rewatch operation / repair-refresh / second-dewatch-exit layer:
run-state, affected scope, current owner, cadence, repair-refresh proof, learner-safe action, exit
disposition, minimization, and reopen triggers when a repaired-route threshold opens owner
reconciliation, route-pair repair refresh, recipient-record correction, protected-route handling,
redesign proof review, retired-route posture, no-active-route residue, or split-surface handling.

It also opens one narrower seam.

After renewed rewatch exits or second-dewatches, the archive may still need a tiny
post-second-dewatch relapse / renewed-repair memory layer for cases where the repaired route later
relapses again, repair-refresh proof ages, minimized second-rewatch memory must be recalled,
protected or recipient corrections reappear, redesign proof fails, retired-route posture revives, or
no-active-route residue exposes a current owner — without making every later recurrence automatic
renewed rewatch, every repeated repair a permanent stigma label, every learner action a duplicate
filing, or every second-rewatch proof object a public vault.
