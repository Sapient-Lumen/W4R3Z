# First rewatch operation, repair-proof, and dewatch-exit defaults for hot-exam recipient followup shells

The archive can now publish one still smaller operating layer for the hottest exam-like
learner-request routes.

It can already say:

- when an activation route-stability operation deconflicts a revived route, replacement route,
  recipient portal, protected route, proof object, clock, source surface, search result, archive
  slice, or official record;
- when that deconflict operation exits and later relapses;
- when minimized deconflict memory may be recalled only for a current named need; and
- when repeated post-deconflict relapse crosses a named rewatch threshold without turning every
  relapse into automatic rewatch, learner fault, public stigma, or a revived proof dossier.

That is still not enough.

A threshold is only useful if the shell can say what the threshold actually opens. It might open a
bounded rewatch. It might require owner reconciliation. It might require repair of a route-pair
instruction, recipient portal, official-record field, protected-route handoff, source page,
search-result family, archive slice, proof object, prerequisite, or clock. It might send the route
pair to redesign. It might split public, protected, recipient, record, source, search, and archive
surfaces. It might close as ordinary lag. Or it might end as retired-route residue or
no-active-route residue because no current owner can repair the affected path.

This document adds one thing only:

- a **tiny rewatch operation / repair-proof / dewatch-exit field set** for hot-exam recipient
  followup shells after `YT0-YT4` has already found a repeat post-deconflict relapse / rewatch
  threshold, but before the archive claims that a bounded rewatch, owner reconciliation, route-pair
  repair, protected-route handling, recipient-record correction, redesign, split, retired-route
  residue, or no-active-route residue is operating or has exited.

That means the archive now asks a different question than before. It no longer asks only **when
repeated relapse crosses a rewatch threshold**. It now asks **what the opened rewatch is doing, what
repair proof is current, what learners can safely do while owners repair or split the route pair,
and how the rewatch exits without permanent surveillance, public route-pair stigma, automatic
duplicate learner filing, or an indefinite proof vault**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
is property-owner, exact-URL, current/expired-history, temporary-removal, cancellation,
about-six-month, Google-Search-only, and source-side-permanent-method based rather than a permanent
rewatch dashboard. Google's Refresh Outdated Content route is exact page/image URL,
changed/gone-content, queue/status, additional-URL, processing, and 180-day-expiry based rather than
a durable repair certificate for every related copy. Google's personal-content routes keep Search
removal, source-page removal, status, notification, sensitive proof, and new-result handling
separate. Princeton, WiscWeb, and Rowan separate local deletion, cache, CMS ownership, accessibility
or accommodation support, search/archive persistence, contributor obligations, redesign, and
support-ticket work. Internet Archive asks for URL, time-period, control-period, and review context
before exclusion. Bing distinguishes temporary blocking, up-to-90-day expiry,
cached/outdated-content handling, extension or permanent-removal prerequisites, exact URL
submission, and source-side 404/410 or noindex methods. Together those signals support a tighter
archive rule: **the next truthful portability gain here is one tiny operating layer for rewatch
run-state, affected scope, owner, cadence or event trigger, repair proof, learner-safe action,
dewatch exit, minimization, and reopen triggers — but not one permanent public dashboard, one
route-pair stigma label, one duplicate-filing duty, one all-surface repair certificate, one
protected-proof publication rule, or one no-memory reset.** See `B265`.

## Small field set for rewatch operation, repair proof, and dewatch exit

| Code | Meaning | Default archive action |
|---|---|---|
| `YV0-NO-PERMANENT-REWATCH-DASHBOARD-PUBLIC-STIGMA-DUPLICATE-FILING-OR-INDEFINITE-VAULT` | a threshold can open bounded rewatch work, but it does not automatically create permanent surveillance, public route-pair stigma, learner duplicate-filing duty, or public proof retention | require current run-state, affected scope, owner, cadence or event trigger, repair-proof basis, learner-safe action, and dewatch exit before widening beyond `YT0-YT4` threshold publication |
| `YV1-PUBLISH-REWATCH-RUN-STATE-SCOPE-OWNER-AND-CADENCE-LIMIT` | an opened rewatch must say what is actually running and how bounded it is | publish whether the threshold opened bounded rewatch, owner reconciliation, route-pair repair, recipient-record correction, protected-route handling, redesign handoff, route split, retired-route residue review, no-active-route residue review, ordinary-lag review, or no operation; name affected route pair, surface, owner, cadence, event trigger, and out-of-scope surfaces |
| `YV2-PUBLISH-REPAIR-PROOF-PRECEDENCE-AND-OWNER-RECONCILIATION` | repair requires current proof and owner reconciliation, not threshold status, owner assertion, stale screenshots, or expired rows alone | publish reciprocal owner confirmation, recipient-of-record correction, official-record correction, protected-route authority, source-owner repair, search/archive/provider status, route-native clock proof, redesign proof, or `repair proof unresolved` with age and scope |
| `YV3-SEPARATE-LEARNER-SAFE-ACTION-FROM-OWNER-REPAIR-DUPLICATE-FILING-AND-PROOF-VAULTING` | repeated owner-side ambiguity should not force learner fault, duplicate filings, or public proof revival | publish learner action only when current route-native authority requires it; otherwise publish no action now, one safe route, submit once with dual-route recognition, use the more protective route, use the longer current window, protected local-only submission, manual support, or owner-only repair work |
| `YV4-PUBLISH-DEWATCH-EXIT-SPLIT-REPAIR-MEMORY-MINIMIZATION-AND-REOPEN-TRIGGERS` | rewatch must close, split, hand back, redesign, become residue, or minimize on named facts | publish ordinary route-pair return, repaired route pair, recipient-record correction, protected route retained, route split retained, redesign handoff, retired-route residue, no-active-route residue, rewatch extended, rewatch closed, minimized memory, local-only memory, or reopen only on material route, owner, proof, clock, recipient, protected-route, source, search, archive, or official-record facts |

   opened`, `protected-route handling`, `redesign handoff running`, `route split operation`,
   `retired-route residue review`, `no-active-route residue review`, `ordinary-lag review`, `repair
   proof under review`, `recurrence during rewatch`, `dewatch eligible`, `dewatch completed`,
   `rewatch closed without repair`, `none inherited`, or `not published`;

   route only`, `recipient portal`, `official-record field`, `protected accommodation or
   accessibility route`, `source page`, `Google result family`, `Bing or partner-search family`,
   `custom search`, `image result`, `archive capture or mirror`, `proof object`, `clock or
   deadline`, `prerequisite requirement`, `multiple affected scopes`, `event-triggered only`, `no
   current owner`, `none inherited`, or `not published`;
3. `rewatch_repair_proof_token` — `reciprocal owners confirmed`, `recipient of record corrected`,
   `official record corrected`, `protected owner proof current`, `source corrected and persisted`,

   or expired cleanly`, `archive or platform review proof`, `route-native clock proof current`,

6. `post_dewatch_memory_and_reopen_token` — `minimized public memory`, `aggregate memory only`,

## Practical rewatch-operation defaults

| Situation | Minimal publication | Why |
|---|---|---|
| repeat relapse threshold opens owner reconciliation for the same route pair | `bounded rewatch active` or `owner reconciliation opened`, affected route pair, current owners, repair proof unresolved, learner-safe action, and a named dewatch condition | threshold status can require owners to repair or reconcile, but it should not create a permanent public route-pair watch |
| recipient portal repeatedly accepts the wrong or retired route after deconflict memory was minimized | `recipient-record correction opened`, recipient-of-record owner, last current route-pair proof, `submit once with dual-route recognition`, and whether recipient record was corrected | the live dependency is the recipient or record effect; timely learner action should be preserved while the record owner repairs the mismatch |
| protected accommodation, accessibility, privacy, safety, appeal, or records route relapses during rewatch | `protected-route handling`, protected owner proof, `protected local-only submission`, and `protected route retained` or `route split retained` | sensitive proof should not become a public rewatch proof vault merely because the public route pair is unstable |
| public source page and search result disagree after a repair claim | `route-pair repair opened`, source owner, search-provider status, proof age, and `no learner action now` or one safe route | one repaired source does not prove search, image, cache, archive, or recipient surfaces are repaired; one lagging result does not prove the source failed |
| two clocks recur after a prior deconflict exit | `owner reconciliation opened`, `clock or deadline`, route-native clock proof or `repair proof unresolved`, and `use longer current window until resolved` | adverse clocks should not attach until the current controlling owner and window are visible |
| route instructions themselves keep causing relapse | `redesign handoff running`, redesign owner, affected proof object or prerequisite, `owner-only repair work`, and post-redesign reopen triggers | repeated ambiguity can prove that the route instructions need redesign, but not that all learners must refile or that old proof stays public |
| old route appears only in search, image, archive, or mirror surfaces while source, recipient, and record owners agree | `ordinary-lag review` or `retired-route residue review`, current source / recipient proof, `no learner action now`, and minimized memory | downstream visibility can be documented without treating the old route as current or the replacement as failed |
| no current owner can repair the route pair | `no-active-route residue review`, last current proof, `manual local support only` or `no action now`, and material reopen triggers | absence of a repair owner should be published as residue, not silence-as-repair, silence-as-denial, or learner abandonment |
| rewatch completes one clean cycle with repair proof | `dewatch completed`, repair proof, ordinary route-pair return or retained split, minimized memory, and reopen triggers | clean exit restores ordinary handling without erasing the bounded repair memory needed for a later material relapse |

## What this layer now makes portable

Hot-exam recipient followup shells may now publish one tiny `YV0-YV4` layer after `YT0-YT4` when the
archive needs to say not merely that **repeated post-deconflict relapse crossed a rewatch
threshold**, but that **a bounded rewatch is operating, what repair proof can close it, what the
learner safely does while owners repair, and how the route-pair memory exits or minimizes after
dewatch**.

That means a shell may now truthfully say things like:

- `repeat relapse met the threshold; owners are reconciling, submit once, and no adverse clock runs
  until conflict-aware notice names the controlling route`;
- `the recipient record is being corrected; timely action through either named route is protected
  while the recipient owner confirms`;
- `public replacement proof controls, but protected accommodation proof remains local-only and the
  protected route stays split`;
- `the old route appears only in a search or archive surface; keep retired-route residue
  time-slice-specific and do not reopen learner action`; or
- `the rewatch closed after one clean repair cycle; minimize public proof and reopen only on
  material route, owner, clock, recipient, protected-route, source, search, archive, or
  official-record facts`.

It still may not pretend:

- that threshold status creates permanent route-pair surveillance;
- that a route pair deserves a public instability label forever;
- that repeated owner disagreement is learner fault;
- that learners must duplicate filings while owners repair;
- that old screenshots, expired request rows, or downstream copies prove current failure by
  themselves;
- that owner assertion alone proves repair, reconciliation, redesign, or dewatch eligibility;
- that protected or sensitive proof must become public to repair a public route pair; or
- that one surface's repair or failure is an all-surface repair certificate.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about detecting repeated failure. It is also
about preventing repair governance from becoming a second harm.

This layer matters because rewatch states are sticky. A threshold can quickly turn into a permanent
warning label, a dashboard that keeps old proof alive, or a duplicate-filing burden that makes
learners absorb owner-side ambiguity. The opposite error is also real: a clean cycle or owner claim
can erase the repair history needed to understand a later material relapse. The portable answer is
narrower: publish **what rewatch is actually running**, **which route pair or surface is affected**,
**who owns repair**, **what current proof controls or remains unresolved**, **what the learner can
safely do without wrong-route or duplicate-filing risk**, **how protected or sensitive proof stays
bounded**, and **how the posture exits, splits, hands back, redesigns, becomes residue, minimizes,
or reopens**.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `YT0-YT4` has not found a repeat post-deconflict relapse / rewatch threshold;
- the visible difference is ordinary search/cache/crawl/archive lag with no learner-facing
  route-choice, owner, proof, clock, recipient, protected-route, official-record, or live dependency
  effect;
- the route-native process already names the rewatch owner, repair proof, learner-safe action, clock
  posture, exit state, memory rule, and reopen rule;
- the only signal is an unrelated mirror, screenshot, archive capture, expired history row, or
  downstream copy with no current owner or learner dependency;
- a protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record process
  already controls proof handling and should stay local-only;
- the threshold was closed as non-material, ordinary lag, or no-active-owner residue without opening
  any rewatch work; or
- a current rule expressly requires a different local repair, duplicate-filing, appeal,
  protected-route, or record-correction posture.

In those cases, publish `no rewatch opened`, `ordinary lag only`, `route-native rule controls`,
`protected local-only route`, `no learner action now`, `no active owner`, `threshold closed`, or
`none inherited` rather than creating a portable rewatch operation.

## What this closes

This closes `FT-0151`.

The archive no longer stops at "repeat post-deconflict relapse crossed a rewatch threshold". It can
now publish a minimal rewatch operation / repair-proof / dewatch-exit layer: run-state, affected
scope, owner, cadence or event trigger, repair proof, learner-safe action, exit disposition,
minimization, and reopen triggers when repeated route-pair relapse opens actual owner
reconciliation, route-pair repair, recipient-record correction, protected-route handling, redesign,
split, retired-route residue, or no-active-route residue.

It also opens one narrower seam.

After a rewatch operation exits, splits, hands back, redesigns, repairs the route pair, retains
protected or recipient-specific handling, retires a route, or becomes no-active-route residue, the
archive may still need a tiny post-dewatch relapse / repaired-route memory layer for cases where the
same route pair later relapses, repair proof ages, minimized rewatch memory must be recalled, a
recipient or protected correction reappears, or no-active-route residue later exposes a current
owner — without making every later recurrence automatic rewatch, permanent stigma, duplicate filing,
or total fresh-start amnesia.
