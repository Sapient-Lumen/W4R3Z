# First child splits for still-live reusable starter override rows

This document closes the archive's next narrower governance gap about **which of the still-live
starter override rows already need named child rows instead of remaining one provisional parent
shell**.

The archive's current bet is:

> keep the parent family shells small, but publish the first child rows where age band, project
stage, or tool ecology already changes the truthful inherited outcome.

The point is to avoid five predictable failures at once:

- **one-row dishonesty** — a single parent row keeps pretending that two or three materially
  different construct situations share one truthful default;
- **anti-access overshoot** — institutions copy the hottest child into cooler contexts where the
  support should remain protected or only lightly bounded;
- **stage collapse** — exploratory help, draft-stage help, and final learner-owned performance get
  treated as one policy moment;
- **tool-ecology confusion** — mathematics or other tool-rich domains silently inherit a no-tool or
  all-tool posture that fits neither classroom practice nor assessment truth;
- **bureaucratic sprawl** — local teams keep inventing ad hoc notes around the same three boundary
  shifts instead of inheriting a small child-row map.

Current public signals point in the same direction. College Board's current AP guidance is
increasingly explicit about **stage-sensitive** and **tool-sensitive** boundaries rather than
universal prohibition or universal permission: AP world-language course projects allow AI for
inquiry and target-language source finding while keeping the final learner-owned presentation
central; AP Computer Science Principles permits AI-assisted coding but still requires students to
understand and explain the code; and the current AP calculator policy continues to distinguish
subjects and even exam parts where calculators are allowed or required from those where they are
not. WIDA's current accessibility manual keeps the accessibility line equally explicit:
accommodations do not change what the test measures, should not invalidate the assessment, and
should be selected only as needed to preserve meaningful participation. NCEO's current reading/TTS
policy work continues to show the same construct boundary pressure, especially where reading the
reading passage aloud changes what is being measured. Together those signals support a tighter
archive rule: when one parent row keeps hiding a stable stage or tool split, the archive should
publish the child rows rather than keep calling the parent “provisional.” See `B195`, `B196`.

## Relationship to the starter-row canon

This document does not replace
[`reusable-starter-override-rows.md`](reusable-starter-override-rows.md) or
[`promotion-splitting-softening-and-retirement-rules-for-reusable-starter-override-rows.md`](promotion-splitting-softening-and-retirement-rules-for-reusable-starter-override-rows.md).

It adds one thing only:

- the **first named child rows** for the starter families that the archive already judged as more
  honest to split than to harden unchanged.

The parent-row canon still answers the first question:

- which repeated construct-sensitive cases deserve a published shared row at all.

The disposition-rule canon answered the second question:

- whether each starter row should harden, split, soften, or retire.

This document answers the next question:

- which **specific child rows** should now replace the still-live one-row shells.

## When the archive publishes a child row instead of leaving a parent shell vague

A still-live parent row should gain named child rows when three conditions hold together:

1. one recurring distinction changes the truthful public outcome (`protected_default`,
   `first_unaided_then_supported`, `ordinary_course_rule`, or
   `live_or_supervised_surface_required`);
2. that distinction is already legible enough to publish without a giant local codebook;
3. publishing the child rows reduces anti-access drift more than it increases table complexity.

The archive's current judgment is that exactly three parent rows now meet that bar: foundational
reading, world-language projects, and symbolic mathematics.

## Child-row notes

### `SR-READ-FOUND-01A` and `SR-READ-FOUND-01B` — stop treating early decoding and later supported reading access as one row

The parent reading row was useful, but too broad. The archive now makes the sharper claim that
**early first-pass decoding** and **later supported access to text where decoding is no longer the
graded claim** should not live under one inherited outcome. WIDA's current manual states that
accommodations do not change what a test measures and must never invalidate the assessment; NCEO's
current reading/TTS policy work continues to show that reading the reading passage aloud remains a
construct-sensitive boundary in many reading settings. That combination supports a two-child
structure: preserve one named decoding surface where decoding itself is the claim, but keep ordinary
access supports on the protected rail once the work has shifted toward comprehension, discussion,
and participation. See `B196`.

### `SR-LANG-PROJ-01A` and `SR-LANG-PROJ-01B` — split inquiry help from final learner-owned target-language performance

The language-project parent row was hiding a stage distinction that College Board now states openly.
Current AP world-language guidance allows AI for topic inquiry and target-language source finding,
while still requiring the student to develop their own presentation in a way that demonstrates their
language abilities and cultural understanding. That means exploratory support and final
learner-owned performance should not share one inherited row. The archive therefore publishes a
cooler child row for inquiry/source-finding and a hotter child row for the final presented product.
See `B196`.

### `SR-MATH-PROC-01A` and `SR-MATH-PROC-01B` — split direct first-pass procedure from tool-integrated application

The mathematics parent row was also doing too much. Current AP calculator policy still separates
subjects and exam parts where calculators are allowed or required from those where they are not,
which is a clean public sign that mathematics assessment does not live on one universal tool
boundary. The archive's AI analogue is not “ban tools everywhere” or “allow executor tools
everywhere.” It is to publish two child rows: one for direct first-pass symbolic procedure and one
for tool-integrated application where interpretation, setup, and transfer remain the real proof
burden. See `B196`.

## What the archive is **not** splitting yet

The archive is still holding back from three wider moves:

- it is **not yet** publishing a high-stakes child split for `SR-WRITE-RHET-01`; the
  protected-access carveout comes first;
- it is **not yet** publishing advanced or safety-critical child rows for `SR-CODE-EXPL-01`; the
  ordinary explanation floor can harden first;
- it is **not yet** publishing professional-subdomain child rows inside `SR-LIVE-PRO-01`; the
  live/supervised floor hardens first while regulatory specifics stay local.

That restraint is deliberate. The goal of this pass is to name the first child rows only where the
parent shells were already visibly lying by compression.

## What institutions should publish when they inherit a child row

When a local or sector owner inherits one of these child rows, publish only five child-specific
extras beyond the ordinary row fields:

1. the child row ID and parent row ID;
2. the split dimension (`literacy_stage`, `project_stage`, or `tool_ecology / task_phase`);
3. the local course or programme scope using that child;
4. the named alternative proof surface or protected-default note now in force;
5. the review point if the child is still marked split-first rather than hardened.

That is enough to make child inheritance legible without turning the override table into a large
taxonomy project.

## What counted as a real archive gain

The archive previously had a compact disposition rule for starter rows, but it still left the next
operational question open: **which of the still-live rows already deserve named child rows right
now?**

This document answers that with six child rows across three parent families. That is a real gain
because it converts “split before harden” from a plausible instruction into actual inheritable row
names and outcomes.

## Current archive bet

The archive's current best guess is that **publishing a very small first child-row layer** will
outperform both extremes:

- keeping `SR-READ-FOUND-01`, `SR-LANG-PROJ-01`, and `SR-MATH-PROC-01` as single provisional shells
  for too long;
- or exploding the starter-row canon into many course-specific local tables before the first obvious
  stage and tool splits are even named.

That claim is now canon, but still live. The next narrower problem is no longer which still-live
parent rows deserve their first child split, but which of these child rows now harden cleanly, where
protected-access carveouts or stakes splits still have to branch further, and where local variance
remains too high for stronger inheritance. See `OQ-0005`.
