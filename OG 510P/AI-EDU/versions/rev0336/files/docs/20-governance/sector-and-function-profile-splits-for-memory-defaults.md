# Sector and function profile splits for memory defaults

This document closes the archive's next governance gap about **which memory defaults should already
split by sector and function before local evidence accumulates, because one generic `M0-M4` ladder
is too blunt for minors, formal assessment, professional gatekeeping, and public-route services**.

The archive's current bet is:

> keep one generic memory ladder as the floor, but publish a second tiny starter profile layer
wherever developmental duty, assessment validity, supervised-practice safety, or benefits-linked
public routing already makes a uniform memory default misleading.

The point is to avoid five predictable failures at once:

- **continuity-to-biography drift** — a service that only needed short continuity quietly
  accumulates longitudinal learner history because persistence is technically easy;
- **child-facing pseudo-relationship memory** — a minor-facing tutor or helper turns remembered
  details into dependence, emotional steering, or secrecy-shaped interaction rather than bounded
  educational support;
- **assessment carry-forward contamination** — candidate history, prior flags, or behavioral traces
  bleed into live proof events that should remain memory-cool and validity-protective;
- **coaching-to-gatekeeping creep** — support memory that was acceptable for simulation or
  remediation quietly becomes readiness, progression, or placement memory;
- **route-memory becoming treatment memory** — public navigation tools move from remembering
  preferences or unfinished steps to shaping eligibility, queue order, or linked-service treatment.

Current public signals point in the same direction. OECD's current education guidance says
generative AI supports learning only when used with pedagogical purpose rather than as generic
performance outsourcing. The UK DfE's current education guidance says teacher-facing use shows more
immediate benefits and fewer risks than pupil-facing use, while pupil-facing use requires stronger
safeguards, careful legal compliance, and openness about automated decision-making and profiling.
The DfE's current product-safety standards make the design boundary sharper: educational AI products
should state intended purpose and target demographic, give meaningful information about profiling
and its consequences, provide formal complaint routes, and avoid manipulative, exploitative, or
secrecy-encouraging interaction patterns. The ICO's current child-data guidance makes the governance
bar sharper still: profiling children or making automated decisions about them is presumptively
high-risk, should not be the norm, and needs human intervention, contestability, intelligible
notice, and strong justification when it materially affects them. FERPA keeps the contractual floor
visible by tying disclosed student data to authorised purpose, written control, and purpose-bounded
redisclosure. UNESCO's current rights-based work sharpens the same floor by tying personalization
claims to privacy, safety, equity, and accountability, while its critique of personalised learning
warns that black-box pathways can sideline learner voice and agency. The EU AI Act then sharpens two
hard boundaries: emotion recognition in educational institutions is prohibited except for medical or
safety reasons, and Annex III education uses that perform profiling remain high-risk rather than
ordinary convenience. See `B11`, `B102`, `B120`, `B122`, `B128`, `B129`, `B136`, `B138`, `B139`.

## Reading the profiles correctly

These profiles are **overlays**, not replacements.

The generic memory ladder still answers the first question:

- what kind of remembered state is this?

This document answers the second question:

- in this sector or function, does the archive already know that some memory classes should begin
  cooler, move earlier onto human-owned rails, or stay capped even when similar memory might be
  tolerated elsewhere?

That means the same underlying model can inherit different memory defaults in different settings:

- an optional adult study helper may still live mostly under the generic memory ladder;
- the same model used in a school-managed learner-facing system for minors belongs under
  `MP-K12-MINORS`;
- a similar system used during controlled assessment belongs under `MP-FORMAL-ASSESS`, where
  candidate-facing memory stays much cooler;
- and the same family of tool used for public-route intake or referral belongs under
  `MP-PUBLIC-ROUTE`, where cross-agency boundaries and no-loss-of-place human paths matter
  immediately.

## The disposition rule: harden, branch, stay provisional, cap, or retreat

The archive now gives these starter profiles a compact disposition rule.

A local inherited memory profile should harden unchanged only when all five of these still travel
together under ordinary conditions:

1. **state fit** — the same kind of remembered state is still enough, rather than the service
   drifting from learner-declared preferences or bounded continuity into inferred traits, risk
   labels, or prescriptive path-setting;
2. **owner fit** — the same human owner and correction path still make sense, rather than the memory
   quietly moving from learner control or current-course handling into support, assessment, or
   institutional treatment;
3. **scope-and-expiry fit** — the same boundaries and expiry still hold, rather than the memory
   expanding across courses, offices, agencies, or time horizons;
4. **treatment fit** — the remembered state still does not materially shape opportunity, candidate
   treatment, progression, queue order, or support intensity beyond the original profile's
   consequence class;
5. **relationship-safety fit** — the interaction still looks like bounded educational assistance
   rather than dependence-building, secrecy-shaped, or manipulation-prone engagement.

When those five do **not** travel together, the archive prefers one of four other dispositions.

### 1. Branch

Branch when a remembered state starts doing a different kind of work than the parent profile
assumed.

Examples:

- minor-facing tutoring memory becomes attendance or wellbeing routing memory;
- assessment accommodation continuity becomes candidate-control or suspicion memory;
- professional coaching memory becomes readiness-signalling or placement memory;
- public navigation memory becomes funded-route prioritisation or cross-agency queue memory.

### 2. Stay provisional

Stay provisional when the remembered state still looks bounded, but ordinary-operating evidence is
not yet strong enough to show that the same controls, expiry, correction path, and human alternative
really hold across cohorts or institutions.

### 3. Cap below `M4`

Cap below `M4` when the apparent value depends on opaque inference, hidden nudging, relational
stickiness, or continuous behavioral modeling rather than on learner-declared preferences, bounded
continuity, or named human-owned records.

### 4. Retreat

Retreat when a hotter predictive or inferred layer is not actually needed. The archive prefers
moving back toward `M1` learner-declared preferences or `M3` human-owned case/record rails whenever
those routes can do the educational job without hidden profile-building.

## The child-branch hardening and retreat rule

The archive now answers the narrower question rev0045 left open: **which of these child branches may
actually harden as inherited defaults, which should harden only as named `M3` rails, and which reuse
claims should never inherit portability at all**.

The compact rule is two-tiered.

1. **cooler support-continuity branches** — `MP-K12-TUTOR`, `MP-ASSESS-ACCESS-RAIL`, `MP-PRO-COACH`,
   and `MP-ROUTE-INFO` may harden unchanged only when the remembered state stays mostly declared or
   directly entered, remains bounded to the same function, keeps the same reset/challenge path, and
   does not change treatment outside that function;
2. **consequence-bearing branches** — `MP-K12-SUPPORT-ROUTE`, `MP-ASSESS-CANDIDATE-CONTROL`,
   `MP-PRO-SIGNAL`, and `MP-ROUTE-QUEUE` should not harden as ordinary service memory. They may
   harden only as named accountable `M3` rails with explicit human owners, or else retreat to
   human-only handling.

In practice, that means the archive now treats three outcomes as knowable in advance:

- some child branches may travel as bounded continuity defaults;
- some may travel only as governed human-owned record rails;
- and some reuse claims should be treated as **non-portable by default**, even when one local
  implementation looked useful.

| `MP-PRO-COACH` | memory stays inside the current supervised block and does not assign readiness or professionalism labels | progression weighting, placement influence, or formal remediation tracking appears | coaching continuity does not inherit portability into gatekeeping, credentialing, or hiring-like signal systems |

| `MP-ROUTE-QUEUE` | only as a named route file with bypass, explanation, and challenge rights | predictive prioritisation, denial, or hidden cross-agency treatment appears | no inherited portability across agencies or functions merely because the same vendor or public stack is involved |

### The five tests for hardening a cooler child branch

A cooler child branch should harden unchanged only when all five of these still travel together
under ordinary conditions:

1. **function fit** — the memory still serves the same child branch rather than drifting into
   support treatment, candidate control, readiness signalling, or queue shaping;
2. **declaration fit** — the branch still depends mainly on learner-declared, teacher-entered, or
   directly observed bounded state rather than inferred traits, risk labels, or behavioural scoring;
3. **owner fit** — the same named adult owner, correction path, and public explanation still make
   sense;
4. **expiry fit** — the memory still expires on the same course, event, placement, or route boundary
   rather than becoming cumulative biography;
5. **no-treatment-portability fit** — the remembered state still does not change treatment in
   another office or function just because it exists.

If one of those tests breaks, the archive does **not** treat the local success as a reason to
inherit portability. It branches hotter, moves onto a named `M3` rail, or retreats to human-only
handling.

### The four child branches that should usually harden only as named `M3` rails

The archive now treats four child branches as presumptively **rail-only**, not service-memory
defaults:

- `MP-K12-SUPPORT-ROUTE`;
- `MP-ASSESS-CANDIDATE-CONTROL`;
- `MP-PRO-SIGNAL`;
- `MP-ROUTE-QUEUE`.

These branches can matter institutionally, but their remembered state already affects support
intensity, candidate treatment, progression, or route order. That means they should harden only
where a named human owner, contestability path, retention boundary, and no-bypass alternative are
visible. Where those cannot be published clearly, the archive prefers human-only handling.

### The reuse claims the archive now treats as non-portable by default

The archive now makes four negative portability judgments explicit. A useful local implementation
does **not** by itself justify inherited reuse from:

1. tutoring memory to attendance, behaviour, wellbeing, or safeguarding treatment;
2. accommodation continuity or assessment administration to suspicion, scrutiny, or score
   interpretation;
3. coaching or remediation support to readiness, progression, placement, credentialing, or
   hiring-adjacent signalling;
4. informational route help to referral priority, funded-seat recommendation, denial, or
   cross-agency queue order.

Those are not “same memory, new office” extensions. They are governance changes that require a
hotter branch judgment, a named `M3` rail, or human-only handling.

## What these child branches change in practice

The archive now makes four tighter judgments explicit:

1. **minor-facing tutoring is not the same branch as minor-facing support routing** — bounded
   practice continuity may sometimes remain at `M1-M2`, while remembered support treatment should
   move earlier onto human-owned rails;
2. **assessment accommodation continuity is not the same branch as candidate control** —
   accessibility-support records outside scoring should not share a memory ceiling with suspicion,
   proctoring, or candidate-handling memory;
3. **professional coaching is not the same branch as readiness signalling** — support for supervised
   learning and memory that shapes access to live practice have materially different consequence
   classes;
4. **informational route help is not the same branch as queue shaping** — a multilingual navigator
   or explainer may deserve a cooler memory rail than a tool that changes referrals, order, or
   funded access.

These branches do not eliminate local judgment. They simply stop the archive from pretending that
remembered support continuity already says enough once support use turns into treatment.

## What the archive now treats as knowable in advance

Local evidence still matters, but the archive now treats five memory facts as knowable **before**
local implementation evidence accumulates.

### 1. Minor-facing continuity and minor-facing profiling are not the same memory class

Remembered accessibility, language, or bounded course preferences may be educationally useful for
minors. Inferred motivation, attention, emotion, vulnerability, or relational stickiness is a
different governance shape.

### 2. Assessment memory and assessment records should not collapse into one rail

A candidate-facing proof event should stay far cooler than the surrounding human-owned record rails
for accommodations, incidents, or appeals.

### 3. Coaching memory and gatekeeping memory are not the same branch

Continuity that helps a learner practice or reflect does not by itself justify readiness,
progression, or placement memory.

### 4. Public-route memory can become treatment memory very quickly

A tool that begins by remembering unfinished steps or language preference may become materially
hotter as soon as it shapes who is prioritised, referred first, or steered toward funded support.

### 5. Cross-function reuse is a governance change even when the vendor surface looks unchanged

When tutoring traces become advising inputs, route-help memory becomes eligibility memory, or
support notes become queue order, the archive treats that as a branch or retreat event, not backend
convenience.

than one generic record bucket.

## Rail-family presumptions no longer all sit at the same level

The archive now adds a small disposition rule inside the function-locked rails too. Their family
presumptions are no longer treated as one undifferentiated middle layer.

| Family presumption shape | Current posture | Archive judgment |
|---|---|---|
| process protections that still travel across sectors inside one rail family | may strengthen as family defaults | `M3-CANDIDATE-CONTROL` pause-before-`L3`, no-finding-from-AI-alone, and `M3-READINESS-SIGNAL` no-silent-label / named evidence-building-route defaults fit here |
| protections whose logic survives but whose operational shape varies by office, stakes, or route | branch before hardening | readiness-block pause posture and queue-loss / timestamp-preservation rules fit here because safety, accreditation, scarcity, and statutory cadence recur too unevenly for one inherited family-wide default |
| protections that turn out to govern every function-locked rail once live consequence-bearing treatment exists | collapse back toward the portable floor | naming the human owner and stated reason for a continuing provisional restriction, and naming urgent exceptions rather than implying them, fit better here than as rail-specific defaults |

When a local system departs from a strengthened or branched family presumption, publish a tiny
rebuttal packet naming the presumption, the reason type, the scope, the substitute protection, and
the expiry or review trigger. That keeps `rebuttable` from collapsing into invisible local
discretion while still leaving law-, accreditation-, and queue-specific residue local.

## Which of those child branches now deserve their own inherited overlays

The archive can now answer the next narrower question too. Not every new child branch needs a
portable clock or legal calendar, but four **event-relative branch overlays** now look stable enough
to inherit:

| Child branch | Inherited review-window band | Inherited substitute-path default | Branch-level publication trigger |
|---|---|---|---|
| `RS-INTERNAL-PROGRESSION` | `RW-CHECKPOINT` | supervised continuation / extra-evidence path before durable internal lock where feasible | remembered state can now produce a reportable defer / no-sign-off / progression hold |
| `RS-EXTERNAL-PRACTICE-ACCESS` | `RW-EXPOSURE` | closest supervised / simulation / evidence-building route when full pause is not presumed | remembered state can now affect live practice access, client contact, or partner-owned placement rights |
| `QS-SCARCE-SEAT` | `RW-FORFEITURE` | reserve / next-offer / anti-penalty handling when a seat cannot simply be held | remembered state can now affect offer order, hold expiry, reserve handling, or ordinary cohort-entry timing |
| `QS-URGENT-DUTY` | `RW-FIRST-STABLE` | minimal-loss route during urgent action plus first ex post review once the immediate duty has passed | remembered state can now trigger urgent rerouting, priority displacement, or access interruption under safeguarding / statutory / imminent-loss duty |

These overlays are deliberately narrow. They do **not** make progression criteria, partner rules,
queue formulas, statutory deadlines, or emergency thresholds portable. They only make three
recurring things harder to hide inside local custom: when review must still happen relative to the
next consequence-bearing step, which substitute path should ordinarily be named, and what event
activates the branch line in the first place.

## What institutions should publish

Where a local memory rule inherits one of these profiles, publish one extra line with only six
additions beyond the generic memory fields:

1. profile identifier (`MP-K12-MINORS` through `MP-PUBLIC-ROUTE` or local equivalent);
2. the highest ordinary memory class the service may use under that profile;
3. which remembered states or triggers force a branch, retreat, or move onto `M3`;
4. whether any memory classes are presumptively capped below routine use under that profile;
5. who owns correction, challenge, reset, and deletion for remembered state under that profile;
6. whether cross-function reuse is prohibited, conditionally governed, or routed only through a
   named human-owned rail.

If a child branch retreats to `M3`, also publish whether that rail uses the archive's
**shared-schema shell** (`M3-SUPPORT-CASE`, `M3-ASSESS-ACCESS`, `M3-ROUTE-CASE`) or a
**function-locked / local-only** map (`M3-CANDIDATE-CONTROL`, `M3-READINESS-SIGNAL`,
`M3-QUEUE-SHAPING`). For the function-locked rails, do not stop at naming the rail: also publish the
local action families in use, whether a live challenge pauses each family, the review point before
any irreversible step, and the interim protection floor while the challenge is live. Where the rail
sits inside one of the new readiness / queue child branches, also publish the inherited
review-window band, substitute-path default, and publication trigger for that branch. If the rail
departs from one of the archive's strengthened or branched family presumptions, add the rebuttal
packet too rather than treating the departure as implicit local custom. If the rail now omits,
weakens, or replaces one of the archive's hardened authority-family pairings or limited anti-penalty
floors, publish the new seven-field departure packet rather than burying the difference in vendor
notes or office lore. If the same departure packet now repeats across independent owners, across
sibling sites, or across the rail's own next review trigger, do not keep classifying it as local
exception handling: apply the archive's repeat-cluster rule and either branch, cool, or reclassify
the inherited default.

This keeps the public layer small while blocking the common failure where an institution publishes
what a tool can answer and what it logs, but never says that minors, formal assessment, professional
gatekeeping, and public-route services already need different default memory rails, different
ceilings, and in some cases a different publication posture once memory becomes record-bearing.

## What counted as a real archive gain

The archive previously knew that persistent memory should default toward learner declaration and
bounded continuity rather than silent predictive profiles. It then added a bounded starter layer, a
compact disposition rule, and a child-branch hardening / retreat rule with explicit non-portable
reuse claims. It still lacked a compact answer to a narrower operational question: **once a hot
child branch retreats to `M3`, when can the rail share one publication/challenge shell and when
should it stay function-locked?**

This revision answered that with a small rail-family map, and then added a tiny local action/timing
floor for the function-locked rails so `local-only` does not become a synonym for unpublished
downstream effects. The archive then added a narrower inheritance rule inside those maps: a portable
rights floor may harden across sectors, a small set of rail-family presumptions may harden only
inside the named rail family, and the rest remains permanently local. This revision closes the next
seam inside that structure by distinguishing which family presumptions can already strengthen, which
need office- or stakes-level branching first, and which should collapse back into the portable
floor, with a tiny rebuttal packet for local departures. It now closes the next seam again by giving
the newly named readiness / queue child branches their first inherited review-window bands,
substitute-path defaults, and publication triggers. The archive keeps the generic `M0-M4` grammar,
but now makes the memory stack more deployable across schools, assessment systems, professional
education, and public-route coordination without pretending all named human-owned rails inherit one
record template, one hidden local action code, one universal due-process template, or one opaque
local timing custom.

## Current archive bet

The archive's current best guess is that a **generic memory ladder plus a tiny sector-and-function
profile layer plus a small shared-schema / function-locked split inside `M3`, plus a tiny
action/timing floor for the function-locked rails, plus a further split between portable floor,
rail-family presumption, and permanently local residue, plus a small promotion-and-split rule for
those presumptions** will outperform both extremes:

- one universal memory rule for all educational-AI services;
- one universal due-process template for all function-locked rails;
- and bespoke service-by-service memory writing with no inherited defaults at all.

That claim is now canon, but still live. The archive has now pushed the portability question one
layer further: `RS-EPA-PARTNER-CAPACITY` and `QS-SS-BATCH-OFFER` may usually travel farther because
scarcity mechanics travel better than authority boundaries, while `RS-EPA-LICENCE-SAFETY` and
`QS-SS-ROLLING-SLOT` should split once publication promises depend on who actually owns lawful
exposure or slot inventory. The archive also now names one urgent-duty regime branch —
`QS-UD-CHILD-SAFETY` — because safeguarding-linked routing sits inside a real multi-agency
protective regime rather than an ordinary queue exception. This revision first hardened a tiny
shared packet across the hottest authority-sensitive branches: branch + authority shape, present
constraint family, non-override statement, earliest meaningful review point, strongest guaranteed
interim path, and challenge / explanation route. It then decided that only some of those fields
travel one level further by authority family: authority shape, non-override, review point, and
challenge route may strengthen into regulator-bar versus host-bar, public-dispatch versus
partner-inventory, or provider-led safeguarding review versus formal multi-agency child-protection
stage, while full reason taxonomies and concrete interim protections still mostly remain local. It
then hardened only a tiny mini-code layer inside those authority families: reusable event-anchor
families such as `EA-REG-RECONSIDER`, `EA-DISPATCH-CYCLE`, and `EA-CP-STAGE`, plus truthful
interim-protection shapes such as `IP-PACKET-PRESERVATION`, `IP-PROTECTED-HANDOFF`, and
`IP-SAFETY-COMPATIBLE-CONTINUITY`, while exact calendars, merits rules, rank effects, and
protective-plan details still remain local. The archive now closes the next seam too by deciding
that only one default pairing, one publication trigger, and one limited anti-forfeiture or
anti-punishment floor travel by authority family, while generic challenge-pause rules, full priority
effects, concrete substitute packages, and legal calendars still stop at local residue. The archive
has now pushed that seam several layers further: material omissions now require a departure packet,
repeated packets now force branch creation, cooling, or office-bound reclassification, downgraded
defaults may recover only when a causal fix, a clean run through the same event family, independent
confirmation at the level of claimed travel, and active monitoring evidence all line up, and
re-hardened defaults now reopen immediately when the same structural reason returns, the
rights-compatible shell is lost, a serious incident / safeguarding-stage escalation attaches to the
same path, monitoring evidence disappears, or a material path change makes the old clean-run
evidence stale. Ordinary local packets still exist, but only while the same anchor, truthful interim
shape, limited floor, and challenge route remain intact. The next problem is narrower again too:
once a recovered path has survived its first relapse screen, the extra sensitivity may now expire on
monitored comparable reuse, but only until a later path-changing event resets the watch. The next
live seam is now even smaller: when several individually non-resetting micro-changes accumulate on
the same recovered path, when should the archive stop calling them harmless maintenance and force a
fresh reset cluster? See `OQ-0023`.
