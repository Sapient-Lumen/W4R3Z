# Hardening, branching, and retreat rules for recovery profiles

This document closes the archive's next governance gap about **when the starter recovery profiles
may really travel unchanged, when they must split further by stakes, modality, or office owner, and
when even the profile floor should cool back toward `RP0` or direct human handback**.

The archive's current bet is:

> keep the generic packet-and-signal rule plus the tiny sector-and-context starter profile layer,
but add one small disposition rule and one small first set of child branches wherever ordinary
support, queue-owned service operation, and consequence-bearing treatment still risk being mistaken
for the same recovery posture.

The point is to avoid five predictable failures at once:

- **profile-travel fiction** — one starter recovery row is treated as portable evidence even when
  repeated use quietly depends on a different owner, modality, or consequence shell;
- **office-owner blur** — course-owned or teacher-owned support recovery quietly becomes programme-,
  welfare-, readiness-, or route-office treatment without a visible branch change;
- **mode-blind hardening** — institutions treat live teacher-present recovery, asynchronous
  shared-queue recovery, and background workflow routing as if they justified the same packet
  ceiling;
- **cool-floor drift** — a profile that should cool back toward `RP0` or direct human handback keeps
  inheriting `RP1` simply because packeting has become operationally convenient;
- **support-to-treatment concealment** — aggregates still look de-identified on paper while real
  downstream treatment is being shaped through standing joins, case queues, or readiness
  interpretation.

Current public signals point in the same direction. OECD's 2026 outlook says GenAI helps most when
tied to clear pedagogical purpose rather than generic output completion. RAND's March 2026 youth
findings then sharpen the demand-side warning: homework use is rising, but concern about
critical-thinking harm is rising too. UNESCO's 2026 teacher and student competency frameworks keep
human agency, AI pedagogy, and responsible use at the centre, which means recovery design matters
rather than sitting outside the learning model. OpenAI's 2026 learning-outcomes work adds the
measurement pressure for longer-run educational evaluation without assuming institutions need
durable learner dossiers to get it. ICO guidance keeps the privacy floor visible by requiring
minimisation, design/default limits on collection and accessibility, and a child-facing presumption
against profiling by default. The DfE's current product-safety standards reinforce the same design
direction by treating manipulation, cognitive-development effects, and emotional/social-development
effects as product-governance questions rather than optional local cautions. See `B11`, `B17`,
`B102`, `B151`, `B152`, `B153`, `B154`, `B155`, `B156`.

## Relationship to the generic recovery rule and starter profile layer

This document does not replace
[`recovery-packets-and-aggregate-dependence-signals.md`](recovery-packets-and-aggregate-dependence-signals.md)
or
[`sector-and-context-profile-splits-for-recovery-defaults.md`](sector-and-context-profile-splits-for-recovery-defaults.md).

It adds two things only:

- a **small disposition rule** for deciding when a starter recovery profile may harden unchanged,
  must branch, should stay provisional, or should retreat;
- a **small first set of child branches** where the parent recovery profiles were still hiding a
  repeated split.

The generic packet-and-signal rule still answers the first question:

- when ordinary interaction should stay inside `IR0-IR2`,
- when `IR3` justifies a temporary `RP1` packet,
- and which `AG1-AG5` views may remain aggregate-only.

The starter profile layer still answers the second question:

- where minors, credit-bearing higher education, professional-practice training, and public
  adult-route services already need cooler, narrower, or earlier-human-owned recovery defaults.

This document answers the third question:

- when those starter profiles are actually stable enough to inherit unchanged,
- when one recurring variation should become a named child branch instead,
- and when even the profile floor is still too hot to remain the ordinary default.

## The disposition rule: harden unchanged, branch, stay provisional, or retreat

| Disposition | What it means | Archive action |
|---|---|---|
| **harden unchanged** | the same profile keeps fitting ordinary contexts without hidden hotter joins, hidden owner shifts, or packet inflation | this profile may now be inherited as written for the named recovery context |
| **branch** | the parent profile remains useful, but one recurring split predictably changes packet truthfulness, aggregate scope, or required human ownership | publish the child branch and stop pretending the parent profile still travels unchanged |
| **stay provisional / local** | implementation is still thin, unusually staffed, or too operationally uneven to know whether the parent really travels | keep the profile as a starter overlay only, not a hardened inherited default |
| **retreat** | the published profile is already too hot or too dossier-like for how the service actually behaves | cool back toward `RP0`, a narrower aggregate-only rule, or direct human handback |

## Five tests before a recovery profile hardens

A starter recovery profile should harden unchanged only when all five tests are substantially met.

### 1. The same packet remains truthful under ordinary use

The same short-lived packet shape must keep describing reality without back-channel side notes,
hidden extra fields, or copied transcripts. If ordinary operators keep needing longer narratives,
wider history, or broader condition labels, the profile has not hardened unchanged.

### 2. The aggregate view remains genuinely aggregate

`AG1-AG5` views must still be minimum-cell or de-identified and used for branch repair, staffing,
training, or service redesign rather than for learner ranking or covert treatment joins.

### 3. The owner and consequence shell stay the same

A course owner, named teacher, supervisor, or route-service owner cannot quietly hand recovery to a
different office while still claiming the same inherited profile. If the real owner has shifted, the
branch has shifted too.

### 4. The modality and tempo still fit the same packet logic

Live teacher-present recovery, asynchronous queue-owned recovery, and background route workflow do
not justify the same packet truthfulness just because they all happen after `IR3`. If response
tempo, queue ownership, or human visibility has materially changed, the profile should branch or
cool.

### 5. Re-entry remains real, not ceremonial

The learner must still have a truthful way back into ordinary support. If packeting mostly feeds
longer monitoring, future treatment, or indefinite special handling, the profile has failed and
should retreat rather than harden.

## What counts as a branch trigger rather than hardening

The archive now treats seven recurring changes as presumptive branch triggers for recovery profiles:

1. **optional use becomes required or default-path use**;
2. **course/teacher ownership becomes programme-, welfare-, readiness-, or route-office ownership**;
3. **the same support surface starts shaping record-bearing treatment**;
4. **live or visible recovery becomes asynchronous shared-queue or workflow-owned recovery**;
5. **aggregates start being joined to academic standing, conduct, safeguarding, aid, eligibility, or
   queue systems**;
6. **packet creation becomes common enough that `RP1` is describing ordinary service friction rather
   than exceptional re-entry help**;
7. **the service repeatedly pushes the same cases onto a hotter rail, showing that the published
   support profile is no longer truthful as the ordinary floor**.

One branch trigger does not always mean the service is bad. It means the parent profile no longer
carries enough information.

The archive keeps this split intentionally small. It does **not** try to map every tutoring or
recovery workflow. It only names the first branch where the parent recovery profiles were still
hiding too much practical difference.

## What these child branches change in practice

The archive now makes four tighter judgments explicit:

1. **optional minor-facing study help is not the same branch as required or support-linked minor
   recovery** — the second branch should usually start cooler and hand off earlier;
2. **course-bound higher-ed recovery is not the same branch as record-adjacent programme or
   central-office treatment** — support packets should not quietly become standing or aid memory;
3. **professional coaching reset is not the same branch as readiness or remediation treatment** —
   supervisor-owned consequence-bearing work should not inherit support recovery ceilings;
4. **informational public-route help is not the same branch as queue or eligibility treatment** —
   route explanation and route allocation should not share one recovery profile.

These branches do not eliminate local judgment. They simply stop the archive from pretending that
one parent recovery profile already says enough once support use turns into treatment.

## What the archive now treats as knowable in advance

Local evidence still matters, but the archive now treats five recovery facts as knowable **before**
local implementation evidence accumulates.

### 1. `RP1` should not become the default description of routine friction

If a service needs packets for ordinary operation rather than for bounded re-entry, the archive
prefers cooler design, tighter answer-release/default changes, or direct human handback rather than
broader packeting.

### 2. Office-owner shifts are not evidence-neutral

A change from teacher/tutor ownership to programme, readiness, welfare, aid, or route-office
ownership is not harmless implementation detail. It is usually a new recovery branch.

### 3. Asynchronous queue ownership is not the same as visible adult recovery

A recovery rule that works with one named adult in view may fail when the same intervention is run
through a shared queue, central service desk, or background workflow.

### 4. Record-bearing and route-bearing effects are not support-neutral

Once recovery starts shaping academic standing, readiness, funded access, queue order, or formal
support treatment, the archive stops treating it as just a more elaborate support packet.

### 5. Some services should cool rather than accumulate more structure

The correct response to repeated packeting is sometimes not a better packet. It is a cooler
interaction default, a narrower aggregate-only signal, a named human route, or a decision that the
service should not own this recovery function at all.

## What institutions should publish

Where a recurring study companion, tutoring surface, or feedback assistant inherits one of these
profiles or child branches, publish only seven additions beyond the generic recovery rule:

1. parent profile identifier and any child-branch identifier in use;
2. whether ordinary recovery prefers `RP0` or allows `RP1`;
3. maximum ordinary expiry for any `RP1` packet;
4. which aggregate signal families (`AG1-AG5`) are actually used there;
5. which office owner may hold the packet or receive the handback;
6. which joins or downstream uses are explicitly prohibited;
7. which trigger moves the case onto a named rail or direct human handback.

That is enough to keep recovery legible without publishing a telemetry manual or a giant local
process annex.

## What counted as a real archive gain

The archive previously had a generic packet-and-signal rule plus a tiny sector-and-context recovery
starter layer. It still lacked a compact answer to a harder operational question: **when do those
starter profiles genuinely travel, when is one parent row hiding a repeated split, and when should
even the profile floor cool back toward no packet at all?**

This document answers that with a bounded disposition rule plus a first child-branch layer. It keeps
the generic recovery grammar and the starter profiles, but it now makes the archive more deployable
across schools, higher education, professional-practice settings, and public adult-route services
without pretending that optional support, queue-owned recovery, and consequence-bearing treatment
share one ordinary packet posture.

## Current archive bet

The archive's current best guess is that a **generic packet-and-signal rule plus starter recovery
profiles plus one tiny harden / branch / retreat layer** will outperform both extremes:

- one universal recovery profile for all learning support;
- and bespoke institution-by-institution recovery writing with no inherited branching rule.

That claim is now canon, but still live. The archive can now close that broader portability question
through

handback, and which should remain permanently local residue. See `OQ-0028`.
