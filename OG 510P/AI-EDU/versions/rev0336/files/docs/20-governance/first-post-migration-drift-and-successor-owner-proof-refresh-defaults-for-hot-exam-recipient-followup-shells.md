# First post-migration drift and successor-owner proof-refresh defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request
routes.

It can already say:

- when post-dewatch relapse should recall minimized repair memory;
- when redesign failure needs current repair proof before trust returns;
- when post-redesign probation exits without permanent stigma; and
- what proof, owner truth, learner action, and clock continuity may travel when a repaired route
  later changes owner, URL, platform, portal, or provider path.

That is still not enough.

A successor owner can later go quiet. A migrated route can change its proof prerequisites. A
transferred proof item can expire or stop matching the affected surface. A redirected URL,
canonical, image host, CMS path, recipient portal, provider form, or archive time slice can drift
again after migration. A search route can require exact current URLs even when the source-side
repair was once proved. A recipient or official-record route can migrate twice, leaving old
confirmation proof attached to the wrong intake path. A provider can decommission the successor
route or split it into a temporary block, outdated-content refresh, personal-content request, or
source-owner method. A split-owner migration can expose a mismatch between source, search, archive,
accessibility, recipient, and record owners. Or a successor owner can remain visible but not answer,
tempting the shell to treat silence as learner abandonment, automatic denial, or fresh
migration-watch duty.

This document adds one thing only:

- a **tiny post-migration drift / successor-owner proof-refresh field set** for hot-exam recipient
  followup shells after successor-owner / route-migration continuity has already been published, but
  the successor route later drifts, becomes stale, changes proof requirements, expires,
  decommissions, reappears, or exposes a new split-owner mismatch.

That means the archive now asks a different question than before. It no longer asks only **what
travels when the route migrates**. It now asks **what must be refreshed after migration when the
successor owner, surface, route, proof, clock, or prerequisite changes — without turning migration
into a perpetual watch, without making proof refresh automatic for every old copy, and without
treating successor silence as learner abandonment**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
is property-owner, URL, current/expired status, cancellation, history-window, Google-Search-only,
and temporary-block based rather than a durable all-surface migration certificate. Google's Refresh
Outdated Content route is exact page/image URL, request queue, status, changed/gone-content, and
expiry based rather than an automatic proof-refresh engine. Google personal-content routes may
expose notifications, removal requests, source-site separation, and sensitive proof needs, but
Search removal still does not remove the source page. Princeton separates local deletion,
media/document cleanup, cache layers, custom search, Google/Bing behavior, and Wayback persistence.
WiscWeb separates WiscWeb ownership, primary-contact support, normal-hours limits, host referral,
campus directory/search/lookahead, and major-search-engine timing. Rowan separates Cascade CMS
maintenance, Siteimprove/accessibility monitoring, contributor training, content-audit/redesign
review, Web Ambassador resolution, support requests, and post-implementation support. Internet
Archive requires URL, time period, control period, and review context before exclusion. Bing
distinguishes temporary blocks, up-to-90-day expiry, content removal, cached/outdated-content
handling, and permanent source-side methods such as 404/410 or noindex. Together those signals
support a tighter archive rule: **the next truthful portability gain here is one tiny post-migration
drift layer for drift signal, successor-owner status, proof-refresh basis, learner action-now truth,
clock status, and refresh exit — but not one perpetual migration watch, automatic proof-refresh
duty, abandonment-by-successor-silence rule, all-copy refresh certificate, or cross-owner
override.** See `B256`.

## Small field set for post-migration drift and successor-owner proof refresh

| Code | Meaning | Default archive action |
|---|---|---|
| `YD0-NO-PERPETUAL-MIGRATION-WATCH-AUTOMATIC-REFRESH-DUTY-OR-ABANDONMENT-BY-SUCCESSOR-SILENCE` | migration continuity can drift, but drift does not create a standing monitoring job, refresh every old proof item, or convert successor silence into learner fault | require a current drift signal, affected surface, successor-owner status, proof-refresh basis, and live learner dependency before reopening or refreshing the migrated shell |
| `YD1-PUBLISH-DRIFT-SIGNAL-SURFACE-SCOPE-AND-LAST-CURRENT-MIGRATION-STATE` | post-migration drift must be tied to a concrete owner, route, URL, portal, archive slice, recipient path, or proof object | publish the last current migration state and whether the new signal is owner silence, route prerequisite change, proof expiry, redirect/canonical drift, provider decommissioning, recipient-portal drift, archive/control-period drift, split-owner mismatch, reappearance, or ordinary lag |
| `YD2-PUBLISH-SUCCESSOR-OWNER-STATUS-AND-REFRESH-PATH` | a successor owner may be current, stale, redirected, changed, partial, or absent; those are different truths | publish whether the successor owner is current, silent within its own window, stale beyond a named window, redirected, disclaiming the affected surface, replaced, split, provider-only, recipient-only, archive-only, or no-active-owner residue |
| `YD3-PUBLISH-PROOF-FRESHNESS-PREREQUISITE-CHANGE-AND-LEARNER-ACTION-NOW` | transferred proof may remain current, need current-source refresh, require exact-URL reproof, require route-prerequisite proof, or expire | publish whether proof is still current, must be refreshed by the owner, must be refiled by the learner, needs recipient confirmation, must stay local-only because sensitive, is mismatched, or is unavailable; publish learner action only prospectively and only against the current route |
| `YD4-PUBLISH-REFRESH-OUTCOME-SPLIT-HANDBACK-MINIMIZATION-AND-REOPEN-TRIGGERS` | proof refresh can settle, split, deny, decommission, or return to residue without keeping migration memory public forever | publish proof refreshed, no-refresh-needed handback, split-surface shell, successor-route denial, decommissioned route, no-active-route residue, local-only memory, or reopen only on material drift, owner change, route expiry, reappearance, or new proof |

## Field values that now travel together

When this layer is used, the shell should publish only six concrete fields:

1. `post_migration_drift_token` — `no drift`, `successor owner silent`, `successor owner changed`,
   `route prerequisite changed`, `route status expired`, `transferred proof expired`, `redirect or
   canonical drift`, `recipient portal drift`, `provider route decommissioned again`, `archive time
   slice drift`, `split owner mismatch`, `surface reappeared after migration`, `ordinary lag only`,
   `none inherited`, or `not published`;
2. `successor_owner_status_token` — `owner current`, `owner silent within route window`, `owner
   stale beyond route window`, `owner redirected request`, `owner disclaims surface`, `owner
   replaced`, `split owners disagree`, `provider owns search surface only`, `source owner owns
   repair`, `recipient owner pending`, `archive or mirror owner pending`, `no active owner`, `none
   inherited`, or `not published`;
3. `proof_refresh_basis_token` — `no refresh needed`, `refresh from current source state`, `refresh
   from current route status`, `fresh exact url proof needed`, `new prerequisite proof needed`,
   `recipient confirmation refreshed`, `archive control period reproof needed`, `sensitive proof
   local only refresh`, `old proof expired`, `old proof mismatched`, `proof unavailable`, `none
   inherited`, or `not published`;
4. `post_migration_action_now_token` — `no learner action`, `owner refresh action`, `learner confirm
   only`, `learner refile current route`, `learner submit fresh proof`, `recipient confirmation
   needed`, `wait route native status`, `local support handoff`, `split shell action`, `no active
   route action`, `none inherited`, or `not published`;
5. `post_migration_clock_token` — `no clock`, `original migration clock still current`, `clock
   paused pending successor response`, `route native window applies`, `fresh clock starts after
   notice`, `provider expiry applies`, `recipient window applies`, `clock expired`, `clock not
   portable`, `none inherited`, or `not published`;
6. `post_migration_exit_token` — `ordinary successor handback`, `proof refreshed`, `route refreshed
   no learner action`, `split surface shell retained`, `successor route denied`, `successor route
   decommissioned`, `no active route residue`, `local only memory`, `reopen on material drift`,
   `reopen on owner change or route expiry`, `none inherited`, or `not published`.

That is deliberately small. It is enough to show what drifted after migration, who currently owns
the successor path, whether transferred proof still matches the live surface, whether the learner
has any current action, whether any clock is route-native and prospective, and when refresh memory
exits learner-facing publication. It is not enough to create a perpetual migration watch, an
automatic proof-refresh duty, an abandonment-by-successor-silence rule, a cross-owner override, or a
universal all-copy refresh certificate.

| Google personal-content / Results-about-you style route after a successor privacy route, notification, or source owner changes | `route prerequisite changed`, `surface reappeared after migration`, or `successor owner changed`; `provider owns search surface only` plus `source owner owns repair`; `sensitive proof local only refresh` or `new prerequisite proof needed`; `learner submit fresh proof` only under the current route; and `local only memory` after closure | sensitive screenshots, addresses, IDs, or safety evidence may be needed for current review, but old privacy proof should not become a public refresh packet |

| Internet Archive / Wayback or mirror-copy route after domain control, owner, URL, or time-slice drift | `archive time slice drift`, `successor owner changed`, or `surface reappeared after migration`; `archive or mirror owner pending`; `archive control period reproof needed`; `learner submit fresh proof` or `no active route action`; and `split surface shell retained` or `no active route residue` | archive exclusion is URL/time/control-period and review-context specific; post-migration drift cannot inherit old domain-control proof for a new time slice or owner period |
| Bing temporary block or permanent-removal route after source URL, provider route, block expiry, or noindex/404 proof changes | `route status expired`, `provider route decommissioned again`, or `redirect or canonical drift`; `provider owns search surface only` plus source owner where visible; `refresh from current source state`, `fresh exact url proof needed`, or `new prerequisite proof needed`; `learner refile current route` only when the route remains live; and `provider expiry applies` | Bing distinguishes temporary blocking from permanent source-side methods; a 90-day or route-specific block does not become durable proof for later URL or owner drift |
| decommissioned provider route, retired campus form, or unsupported successor path after migration continuity | `provider route decommissioned again`; `no active owner`; `proof unavailable`; `no active route action`; `clock not portable`; and `no active route residue` | if the successor route disappears and no current owner or alternate path is named, the truthful state is residue, not learner abandonment or proof-refresh failure |
| split source/search/recipient/archive/accessibility route after one successor owner changes state | `split owner mismatch`; `split owners disagree`; `refresh from current route status` only for the affected surface; `split shell action`; and `split surface shell retained` | one successor owner can drift while others remain settled; the shell should split affected surfaces instead of forcing one owner or one refresh outcome across all copies |

## Boundary conditions

This layer should not be used when only one of the following is true:

- the successor route is still inside its own published review, support, expiry, or reflection
  window;
- the only evidence is ordinary search/index/cache lag with no changed source, owner, route,
  prerequisite, URL, portal, recipient, archive slice, or learner dependency;
- the old proof is historical, sealed, expired, or local-only and no current route needs it;
- the drift affects a different learner, recipient, URL, image, capture, record, owner, or platform
  than the migrated shell;
- the successor owner is rumored but no current owner, route, or status surface is visible;
- sensitive proof can be refreshed locally without learner-facing publication; or
- a legal, records, provider, safety, or accommodation process requires confidential handling rather
  than a portable public field.

In those cases, publish `ordinary lag only`, `owner silent within route window`, `old proof
expired`, `old proof mismatched`, `sensitive proof local only refresh`, `no active owner`, `no
active route residue`, or `none inherited` rather than treating post-migration drift as automatic
proof failure, learner abandonment, or permanent monitoring duty.

## What this closes

This closes `FT-0142`.

The archive no longer stops at "the route migrated". It can now publish a minimal post-migration
drift shell: what drifted, which successor owner is current or stale, what proof must refresh, what
the learner must do now, what clock is live, and how refresh memory exits or splits.

It also opens one narrower seam.

After post-migration proof refresh is published, the archive may still need a tiny repeat-drift /
successor-route stability-threshold layer for cases where the same successor route repeatedly drifts
after refresh, repeatedly changes prerequisites, repeatedly decommissions, or repeatedly splits
owners — without converting every migrated route into a standing watch, permanent redesign-failure
label, or no-memory reset.
