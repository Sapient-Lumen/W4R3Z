# First repeat post-dewatch relapse and repaired-route rewatch-threshold defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request
routes.

It can already say:

- how a repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how that rewatch operates, proves repair, exits, de-watches, splits, redesigns, retires, or
  becomes residue;
- how a later post-dewatch relapse recalls repaired-route memory; and
- how current proof age, learner-safe action, reminimization, and reopen triggers should be
  published after dewatch.

That is still not enough.

Once a post-dewatch relapse has already been classified, the next temptation is to treat the second
or third recurrence as decisive proof that the repaired route pair is permanently unstable. The
opposite error is just as dangerous: because each later event can be explained as search lag,
recipient delay, protected-route residue, redesign handoff noise, or no-active-route churn, the
shell can keep classifying every recurrence as isolated and never admit that the same repaired scope
has crossed a new threshold. A recipient portal can repeatedly accept the retired route after memory
recall. A protected route can repeatedly contradict the public route while its proof must stay
local. A redesign handoff can fail twice without producing a public repair certificate. A retired
route can revive after each dewatch. A no-active-route residue can repeatedly gain and lose a
current owner. Or repeated apparent relapse can still be only downstream reflection with no current
learner action.

This document adds one thing only:

- a **tiny repeat post-dewatch relapse / repaired-route rewatch-threshold field set** for hot-exam
  recipient followup shells after `YW0-YW4` has already classified at least one post-dewatch
  relapse, but before the archive treats repeated recurrence as automatic rewatch, permanent
  route-pair stigma, duplicate filing, public proof-dossier revival, or repeat-by-anecdote.

That means the archive now asks a narrower question than before. It no longer asks only **how a
dewatched route pair recalls repaired-route memory when one later event occurs**. It now asks **when
repeated post-dewatch relapse becomes a named repaired-route rewatch threshold — and when it should
instead remain ordinary lag, fresh handling, local-only protected proof, repaired-route memory
recall, recipient correction, redesign review, no-active-route residue, or reminimized residue**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation,
Google-Search-only, and source-side permanent-removal boundaries rather than an automatic rewatch
rule for every repeated reappearance. Google's Refresh Outdated Content route is exact page/image
URL, changed/gone-content, queue/status, additional-URL, and expiry based rather than a durable
all-copy repeat-relapse monitor. Google's personal-content routes keep Search removal, source-page
removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb
separates local source edits, emergency edits, primary-contact follow-up, campus-search and
lookahead ownership, caching, and major-search-engine non-control. Princeton separates local
deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search
handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support,
Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, support
tickets, project closeout, and accommodation routing. Internet Archive asks for URL, time-period,
control-period, and review context before exclusion. Bing distinguishes temporary block,
up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites,
exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals
support a tighter archive rule: **the next truthful portability gain here is one tiny repaired-route
repeat-threshold layer for repeat count, material scope, threshold source, current owner, proof age,
memory limit, learner-safe action, disposition, minimization, and reopen triggers — but not one
automatic rewatch, one permanent public route-pair stigma, one duplicate-filing duty, one public
repaired-route dossier, or one all-surface relapse certificate.** See `B267`.

## Small field set for repeat post-dewatch relapse and repaired-route rewatch thresholds

| Code | Meaning | Default archive action |
|---|---|---|
| `YZ0-NO-AUTOMATIC-REWATCH-PERMANENT-STIGMA-DUPLICATE-FILING-PUBLIC-DOSSIER-OR-REPEAT-BY-ANECDOTE` | repeated post-dewatch relapse can matter, but repetition alone does not create surveillance, stigma, duplicate learner filing, proof-vault revival, or a threshold by anecdote | require a repeat count, repaired-route scope, current materiality, named threshold source, current owner, memory limit, proof-age label, and learner action-now truth before widening beyond ordinary post-dewatch handling |
| `YZ1-PUBLISH-REPEAT-RELAPSE-COUNT-SCOPE-AND-MATERIALITY` | the shell must say what repeated, where, and why it matters now | publish whether the repeat involves the same repaired route pair, recipient portal, protected route, proof object, clock, source/search/archive surface, redesign handoff, retired route, no-active-route residue, split surface, or only downstream lag, and whether a current learner, owner, recipient, proof, protected-route, or official-record dependency is live |
| `YZ2-PUBLISH-REWATCH-THRESHOLD-SOURCE-OWNER-PROOF-AGE-AND-MEMORY-LIMIT` | a repaired-route rewatch threshold needs a named source and current owner, not accumulated unease | publish whether the threshold comes from a route-native repeat rule, current owner confirmation, recipient-of-record repeat, protected local owner trigger, redesign owner trigger, current owner discovery, repeated proof-age mismatch, or no threshold owner; label which minimized repair memory may be recalled and which proof remains stale, expired, redacted, local-only, unavailable, or public as-of only |
| `YZ3-SEPARATE-OWNER-REWATCH-WORK-FROM-LEARNER-FAULT-DUPLICATE-FILING-AND-PROOF-VAULTING` | repeated owner-side ambiguity is usually owner-stability work before it is learner fault | publish no action, one safe route, dual-route recognition, clock hold, protected local submission, owner-only repair, recipient correction, redesign review, or wait-for-owner-confirmation before asking the learner to refile; do not publish protected proof, revive old repair screenshots, or create adverse wrong-route fault without current route-native authority |
| `YZ4-PUBLISH-THRESHOLD-DISPOSITION-MINIMIZATION-AND-REOPEN-TRIGGERS` | repeated post-dewatch relapse must end, narrow, or open a bounded next posture on named facts | publish below-threshold ordinary handling, repaired-route rewatch opened, repair refresh requested, recipient correction opened, protected route retained, redesign review opened, retired-route watch opened, no-active-route residue, split-surface new shell, reminimized false alarm, or route-native rule controls, plus what proof is minimized and what material new owner, surface, proof, clock, recipient, protected-route, or learner-dependency fact would reopen |

## Field values that now travel together

When this layer is used, the shell should publish only six concrete fields:

1. `repeat_post_dewatch_relapse_count_token` — `first repeat after YW classification`, `second
   material recurrence`, `third or later material recurrence`, `recipient correction repeated`,
   `protected route conflict repeated`, `redesign handoff failed again`, `retired route revived
   again`, `no-active-route owner churn repeated`, `source search or archive reflection repeated`,
   `proof-age mismatch repeated`, `repeat below threshold`, `repeat not material`, `none inherited`,
   or `not published`;
2. `repaired_route_rewatch_scope_token` — `same repaired route pair`, `same recipient portal`, `same
   protected route`, `same proof object`, `same clock or deadline`, `same source page`, `same search
   result family`, `same archive time slice or mirror family`, `same redesign handoff`, `same
   retired route`, `same no-active-route residue`, `split surface only`, `unrelated new path`, `none
   inherited`, or `not published`;
3. `threshold_source_and_owner_token` — `route-native repeat threshold`, `current owner confirmed
   threshold`, `recipient of record threshold`, `protected local owner threshold`, `redesign owner
   threshold`, `successor owner threshold`, `platform status threshold`, `current owner discovered
   after residue`, `local-only threshold`, `no threshold owner`, `threshold denied stale proof`,
   `none inherited`, or `not published`;
4. `proof_age_and_memory_limit_token` — `current proof controls`, `fresh owner proof required`,
   `expired request row as-of only`, `stale screenshot as-of only`, `old dewatch proof aged`,
   `minimized repair summary recall only`, `recipient proof local-only`, `protected proof
   local-only`, `redesign proof pending`, `proof unavailable residue`, `public pointer only`,
   `memory not recalled`, `none inherited`, or `not published`;
5. `learner_safe_action_under_repeat_relapse_token` — `no learner action now`, `use repaired route`,
   `submit once with dual-route recognition`, `clock held during owner repair`, `protected
   local-only submission`, `recipient correction pending no duplicate filing`, `wait for owner
   confirmation`, `owner-only repair`, `route-native refile optional`, `route-native refile required
   with no penalty`, `no adverse wrong-route fault`, `none inherited`, or `not published`;
6. `repeat_post_dewatch_threshold_disposition_token` — `below threshold ordinary handling`,
   `repaired-route rewatch opened`, `repair refresh requested`, `recipient correction opened`,
   `protected route retained`, `redesign review opened`, `retired-route watch opened`,
   `no-active-route residue`, `split-surface new shell`, `route-native rule controls`, `reminimized
   false alarm`, `threshold closed`, `none inherited`, or `not published`.

That is deliberately small. It is enough to show whether a later recurrence has become a repeat
pattern inside the same repaired scope, who owns the threshold, what proof and memory may be used,
what the learner can safely do, and what bounded posture follows. It is not enough to create
permanent surveillance, a public repaired-route dossier, a duplicate-filing duty, an all-surface
relapse certificate, a protected-proof publication duty, or a threshold based only on repeated
anecdotes.

## Minimal publication sentence

A learner-facing or owner-facing shell can usually say the whole thing in one sentence:

> This is `[repeat_post_dewatch_relapse_count_token]` within `[repaired_route_rewatch_scope_token]`.
Threshold source and owner are `[threshold_source_and_owner_token]`. Proof and memory limits are
`[proof_age_and_memory_limit_token]`. Learner action now is
`[learner_safe_action_under_repeat_relapse_token]`. Current disposition is
`[repeat_post_dewatch_threshold_disposition_token]`.

If public publication would expose protected, privacy-sensitive, accommodation, appeal, security,
recipient-record, or route-controlled proof, publish only the owner, action-now truth, and a
redacted or local-only threshold token.

## Default interpretation rules

1. **Repeat is not threshold by itself.** A second or third recurrence matters only when the same
   repaired scope, current owner, proof object, recipient, protected route, clock, surface, or
   learner dependency is materially live.
2. **Thresholds need owners.** A route-native timer, current owner confirmation, recipient-of-record
   trigger, protected local owner, redesign owner, successor owner, or platform status can supply a
   threshold. A stale screenshot, expired request row, rumor, or generic complaint count cannot.
3. **Proof age lowers authority.** Old dewatch proof can be an as-of memory pointer, but it cannot
   create current learner fault, duplicate filing, or public stigma without current route-native
   authority.
4. **Protected repeats may be real and still local.** Accommodation, privacy, appeal, security, or
   protected-route conflicts can cross a local threshold without moving the proof into the public
   repaired-route layer.
5. **Learner action stays prospective and safe.** When owners or routes disagree repeatedly, publish
   one safe route, dual-route recognition, clock hold, protected local submission, owner-only
   repair, or no action before any refiling duty.
6. **The threshold must dispose of itself.** A shell should close as below-threshold ordinary
   handling, bounded repaired-route rewatch, repair refresh, recipient correction, protected-route
   retention, redesign review, retired-route watch, no-active-route residue, split-surface shell,
   route-native control, or reminimized false alarm rather than remain a public repaired-route
   warning forever.

## Worked examples

### Example A — repeated search reflection below threshold

A rewatch dewatched after the source owner removed a retired page and the recipient portal accepted
the repaired route. Two later search snippets briefly show the old URL, but the source remains gone,
the recipient portal stays correct, and no learner action depends on the snippet.

Publish:

- `repeat_post_dewatch_relapse_count_token = source search or archive reflection repeated`;
- `repaired_route_rewatch_scope_token = same search result family`;
- `threshold_source_and_owner_token = no threshold owner`;
- `proof_age_and_memory_limit_token = public pointer only`;
- `learner_safe_action_under_repeat_relapse_token = use repaired route`; and
- `repeat_post_dewatch_threshold_disposition_token = below threshold ordinary handling`.

Do not reopen repaired-route rewatch merely because downstream search reflection repeats without a
current owner, recipient, clock, or learner dependency.

### Example B — recipient correction repeatedly reappears

A rewatch exited after the recipient-of-record confirmed that one route and one clock controlled. A
post-dewatch relapse was handled with dual-route recognition. In the next cycle, the same recipient
portal again accepts the retired route while the official record owner still publishes the repaired
clock.

Publish:

- `repeat_post_dewatch_relapse_count_token = recipient correction repeated`;
- `repaired_route_rewatch_scope_token = same recipient portal`;
- `threshold_source_and_owner_token = recipient of record threshold`;
- `proof_age_and_memory_limit_token = current proof controls`;
- `learner_safe_action_under_repeat_relapse_token = submit once with dual-route recognition`; and
- `repeat_post_dewatch_threshold_disposition_token = repaired-route rewatch opened`.

Do not convert the repeated recipient failure into duplicate learner filing unless the
recipient-of-record currently names that duty and protects the learner against duplicate-clock harm.

### Example C — protected route conflict repeats

A protected accommodation route was retained locally and the public route was repaired. After one
post-dewatch relapse was handled locally, the public page again contradicts the protected local
route. The proof needed to resolve the conflict includes sensitive accommodation facts.

Publish:

- `repeat_post_dewatch_relapse_count_token = protected route conflict repeated`;
- `repaired_route_rewatch_scope_token = same protected route`;
- `threshold_source_and_owner_token = protected local owner threshold`;
- `proof_age_and_memory_limit_token = protected proof local-only`;
- `learner_safe_action_under_repeat_relapse_token = protected local-only submission`; and
- `repeat_post_dewatch_threshold_disposition_token = protected route retained`.

Do not move protected proof into a public repaired-route dossier merely because the protected
conflict repeats.

### Example D — no-active-route residue repeatedly gains and loses an owner

A rewatch exited as no-active-route residue. A later post-dewatch relapse found a new owner and
requested repair refresh. The owner route then disappears, reappears under a different office, and
again becomes silent while learners have a live deadline.

Publish:

- `repeat_post_dewatch_relapse_count_token = no-active-route owner churn repeated`;
- `repaired_route_rewatch_scope_token = same no-active-route residue`;
- `threshold_source_and_owner_token = current owner discovered after residue`;
- `proof_age_and_memory_limit_token = fresh owner proof required`;
- `learner_safe_action_under_repeat_relapse_token = clock held during owner repair`; and
- `repeat_post_dewatch_threshold_disposition_token = repaired-route rewatch opened` or
  `no-active-route residue`.

Do not let owner churn become a learner wrong-route fault or a permanent public stigma label.

### Example E — redesign handoff fails again

A prior rewatch dewatched after a redesign handoff was accepted. The first post-dewatch relapse was
classified as repair refresh requested. The same redesign handoff misses its next named proof point,
and the recipient portal again exposes two official-looking paths.

Publish:

- `repeat_post_dewatch_relapse_count_token = redesign handoff failed again`;
- `repaired_route_rewatch_scope_token = same redesign handoff`;
- `threshold_source_and_owner_token = redesign owner threshold`;
- `proof_age_and_memory_limit_token = redesign proof pending`;
- `learner_safe_action_under_repeat_relapse_token = wait for owner confirmation` or `submit once
  with dual-route recognition`; and
- `repeat_post_dewatch_threshold_disposition_token = redesign review opened`.

Do not treat redesign handoff failure as proof that all related source, search, archive,
protected-route, and recipient surfaces failed.

## Non-goals

This layer does **not** create:

- an automatic rewatch after every repeated post-dewatch event;
- a permanent repaired-route instability label;
- a public repaired-route proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a repeat-by-anecdote threshold;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, or all-engine relapse certificate;
- a universal threshold count that travels across every route family; or
- a duty to monitor every old route pair after dewatch.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about allowing repaired-route memory to survive
dewatch. It is also about deciding when repeated recurrence proves a current stability problem
without turning the learner, the route pair, or the proof object into permanent suspicion.

This layer matters because both extreme defaults are harmful. One bad default says repetition itself
proves the repaired route pair is untrustworthy, so a learner must refile, reprove, or accept
wrong-route fault. Another says every repeat is just another isolated post-dewatch event, so no
owner ever has to admit that the same repaired scope has crossed a new threshold. The portable
answer is narrower: count only material repeats inside a named repaired scope; require a current
threshold source and owner; label proof age and memory limits; protect learner action; and move the
threshold to bounded rewatch, repair refresh, recipient correction, protected-route retention,
redesign review, retired-route watch, no-active-route residue, split surface, route-native control,
or reminimized false alarm on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `YW0-YW4` has not already classified at least one post-dewatch relapse or repaired-route memory
  event;
- the later event is unrelated to the repaired route pair or affected surface;
- the repeat is only search, cache, crawler, archive, or downstream copy lag with no current
  learner-facing owner, proof, clock, recipient, protected-route, or live dependency effect;
- a route-native process already names repeat post-dewatch relapse handling, threshold count, proof
  age, memory limit, learner-safe action, and disposition;
- the only signal is a stale screenshot, expired request row, old status page, anecdote, or
  unrelated mirror without current owner or learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules
  already control proof handling and should stay local-only; or
- a repaired-route rewatch has already opened and the question is now operation, repair refresh, or
  dewatch exit rather than threshold crossing.

In those cases, publish `below threshold ordinary handling`, `ordinary lag only`, `unrelated new
path`, `route-native rule controls`, `protected local-only route`, `no learner action now`, `fresh
first-cycle conflict`, `repaired-route rewatch already open`, `reminimized false alarm`, or `none
inherited` rather than creating a repeat post-dewatch threshold layer.

## What this closes

This closes `FT-0153`.

The archive no longer stops at "post-dewatch relapse classified and repaired-route memory recalled".
It can now publish a minimal repeat post-dewatch relapse / repaired-route rewatch-threshold layer:
repeat count, repaired-route scope, materiality, threshold source, current owner, proof age, memory
limit, learner-safe action, disposition, minimization, and reopen triggers when the same repaired
route pair or affected surface relapses again after memory recall, repair proof repeatedly ages,
protected or recipient corrections repeatedly reappear, redesign handoff repeatedly fails,
retired-route residue repeatedly revives, or no-active-route residue repeatedly gains and loses a
current owner.

It also opens one narrower seam.

After repeated post-dewatch relapse crosses a repaired-route rewatch threshold, the archive may
still need a tiny renewed rewatch operation / repair-refresh / second-dewatch-exit layer for cases
where a threshold opens owner reconciliation, route-pair repair, recipient-record correction,
protected-route handling, redesign proof, retired-route posture, or no-active-route residue —
without turning threshold status into permanent surveillance, public route-pair stigma, automatic
duplicate learner filing, or an indefinite repaired-route proof vault.
