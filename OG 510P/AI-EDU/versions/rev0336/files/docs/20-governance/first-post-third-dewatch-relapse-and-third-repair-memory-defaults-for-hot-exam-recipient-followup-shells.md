# First post-third-dewatch relapse and third-repair memory defaults for hot-exam recipient followup shells

The archive can now publish one still smaller memory layer for the hottest exam-like learner-request
routes.

It can already say:

- how repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how a first rewatch operates, proves repair, exits, de-watches, splits, redesigns, retires, or
  becomes residue;
- how later post-dewatch recurrence recalls repaired-route memory and crosses a repaired-route
  threshold only on material repeated facts;
- how renewed rewatch operates after that threshold, proves repair refresh, and exits through second
  dewatch;
- how post-second-dewatch recurrence recalls renewed-repair memory and crosses a renewed-repair
  rewatch threshold only when the same route, owner, proof, clock, recipient, protected route,
  official record, or affected surface materially repeats; and
- how third rewatch operates after that threshold, refreshes proof again, protects learner action,
  and exits through third dewatch, split, route-native control, redesign, retirement, residue, or
  minimization.

That is still not enough.

A third dewatch is not total amnesia. It may leave a small memory marker: which route was refreshed,
which recipient or official record was corrected, which protected route stayed local, which redesign
proof was accepted, which retired-route or no-active-route residue was named, or which public proof
was minimized. But it is also not a standing fourth-rewatch trigger. A later reflection might be
only search, cache, crawler, archive, mirror, image, or downstream lag. It might be a fresh
unrelated route. It might recall only a sealed local accommodation fact. It might expose a current
owner after a no-active-route residue. It might show an official-record dependency returned. Or it
might be material enough to become a repeat-relapse threshold candidate.

This document adds one thing only:

- a **tiny post-third-dewatch relapse / third-repair memory field set** for hot-exam recipient
  followup shells after `ZD0-ZD4` has already closed third rewatch, refreshed repair, minimized
  proof, or completed a third dewatch, but before the archive treats later recurrence as automatic
  fourth rewatch, permanent serial-repair stigma, duplicate learner filing, a public third-rewatch
  proof vault, or a no-memory fresh start.

That means the archive now asks a narrower question than before. It no longer asks only **how a
third-rewatch threshold operates and exits**. It now asks **what limited third-repair memory may be
recalled after third dewatch, which current fact makes that recall legitimate, what learners can
safely do now, and when the later event should be closed, reminimized, reopened, localized, routed
natively, or queued as a repeat-threshold candidate**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool
exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation,
Google-Search-only, and source-side permanent-removal boundaries rather than a durable all-surface
fourth-rewatch trigger. Google's Refresh Outdated Content route is exact page/image URL,
changed/gone-content, request-status, additional-URL, and expiry based rather than a universal
third-repair memory certificate. Google's personal-content routes keep Search removal, source-page
removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb
separates local source edits, emergency edits, primary-contact follow-up, campus-search and
lookahead ownership, caching, and major-search-engine non-control. Princeton separates local
deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search
handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support,
Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, support
tickets, project closeout, and accommodation routing. Internet Archive asks for URL, time-period,
control-period, and review context before exclusion. Bing distinguishes temporary block,
up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites,
exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals
support a tighter archive rule: **the next truthful portability gain here is one tiny
post-third-dewatch memory layer for exit basis, later signal, affected third-repair scope, scoped
memory recall, current proof age and owner status, learner-safe action, disposition, reminimization,
and reopen triggers — but not one automatic fourth-rewatch trigger, one permanent public
serial-repair stigma label, one duplicate-filing duty, one public third-rewatch proof vault, or one
no-memory reset.** See `B272`.

   downstream lag`, `none inherited`, or `not published`;

## Practical post-third-dewatch memory defaults

| Situation | Publish | Why |
|---|---|---|
| a search or archive reflection reappears after clean third dewatch but the source, recipient, and record remain current | `third dewatch completed`; `ordinary downstream lag`; `public minimized summary only`; `current source proof`; `none current`; `closed as ordinary lag` or `reminimized false alarm` | keeps minimized memory available without turning downstream lag into fourth rewatch |
| the same recipient portal again accepts the old route after third dewatch | `recipient record corrected`; `same recipient portal conflict`; `recipient correction marker recalled`; `current recipient-of-record proof`; `submit once with dual-route recognition`; `recipient correction reopened` | recalls the narrow correction marker needed to protect learners from duplicate filing |
| public route and protected local route diverge again | `protected route retained`; `same protected route conflict`; `protected proof local-only`; `current protected-owner proof`; `protected local-only submission`; `protected route retained` | keeps sensitive proof sealed while preserving the learner's safe route |
| the official record lags behind a refreshed route after third dewatch | `official record corrected`; `same official-record dependency`; `official-record correction marker recalled`; `current official-record proof` or `proof mismatched`; `wait for owner confirmation`; `official-record correction reopened` | names record dependency without claiming that every public or search surface failed |
| a retired route appears again with no current owner | `retired-route residue`; `same retired-route posture revived`; `public minimized summary only`; `owner unavailable`; `manual local support only`; `retired-route posture reviewed` or `no-active-route residue` | prevents owner disappearance from becoming learner wrong-route fault |
| the same redesign handoff fails after third dewatch | `redesign proof accepted`; `same redesign handoff failed`; `redesign proof marker recalled`; `current redesign proof` or `proof mismatched`; `use more protective route until resolved`; `redesign review opened` | treats redesign recurrence as a current proof question, not a public serial-repair stigma |
| the same material route, owner, proof, clock, recipient, protected route, official-record dependency, or split surface recurs again after memory recall | third-exit basis plus current repeat scope; scoped memory recalled; current proof and owner status; no duplicate filing | may become a repeat-relapse threshold candidate only on named current facts |

## Minimal publication sentence

A learner-facing or owner-facing shell can usually say the whole thing in one sentence:

> This post-third-dewatch event follows `[post_third_dewatch_exit_basis_token]` and is
`[post_third_dewatch_relapse_signal_and_scope_token]`. Memory recall is
`[third_repair_memory_recall_token]`. Current proof and owner status is
`[current_post_third_proof_age_owner_status_token]`. Learner action now is
`[learner_safe_action_after_third_dewatch_token]`. Disposition and reopen posture is
`[post_third_dewatch_disposition_and_reopen_token]`.

If public publication would expose protected, privacy-sensitive, accommodation, appeal, security,
recipient-record, or route-controlled proof, publish only the current owner, action-now truth, and a
redacted or local-only memory token.

## Default interpretation rules

1. **Third dewatch is not amnesia.** A clean third dewatch may still leave minimized public memory,
   aggregate memory, local-only proof, recipient or official-record correction markers, redesign
   proof markers, or residue markers when a current dependency needs them.
2. **Third dewatch is also not fourth rewatch.** Later recurrence should not automatically reopen
   serial watch status unless it repeats materially in current route, owner, proof, clock,
   recipient, protected-route, source, search, archive, split-surface, official-record, redesign,
   retired-route, or residue facts.
3. **Current proof controls recall.** Old third-rewatch proof explains memory, but current source,
   recipient, record, protected-owner, route-native, platform, archive, redesign, or successor-owner
   proof controls whether the shell reopens.
4. **Learner action stays bounded.** The default action remains none, wait for owner confirmation,
   one safe route, dual-route recognition, protected local submission, manual support, or
   route-native refile with no penalty; duplicate filing and wrong-route fault are not the default.
5. **Protected proof remains sealed.** Accommodation, privacy, safety, appeal, security, and other
   protected-route proof can support memory recall or local action without becoming a public
   third-rewatch proof vault.
6. **Disposition must reminimize or name a trigger.** The shell should close as ordinary lag,
   reminimize false alarms, retain only scoped memory, reopen a named correction, localize protected
   handling, route natively, become residue, or mark a threshold candidate on named current facts.

## Examples

### Example A — search reflection after clean third dewatch

A route completed third rewatch, the source owner and recipient-of-record confirmed the refreshed
route, and the public proof summary was minimized. Two months later, a search snippet still shows
the old route title, while the source page, recipient portal, official record, and protected local
route remain current.

Publish:

- `post_third_dewatch_exit_basis_token = third dewatch completed`;
- `post_third_dewatch_relapse_signal_and_scope_token = ordinary downstream lag` or `same search
  result family reflection`;
- `third_repair_memory_recall_token = public minimized summary only`;
- `current_post_third_proof_age_owner_status_token = current source proof`;
- `learner_safe_action_after_third_dewatch_token = none current`; and
- `post_third_dewatch_disposition_and_reopen_token = closed as ordinary lag` or `reminimized false
  alarm`.

Do not open fourth rewatch merely because a downstream reflection exists without a current
learner-facing owner, clock, recipient, protected-route, official-record, or route dependency
effect.

### Example B — recipient correction returns after third dewatch

A third rewatch closed when the recipient portal corrected the route and confirmed a single
controlling deadline. In the next cycle, the same portal again accepts the retired route while the
source and official record still publish the refreshed repaired route.

Publish:

- `post_third_dewatch_exit_basis_token = recipient record corrected`;
- `post_third_dewatch_relapse_signal_and_scope_token = same recipient portal conflict`;
- `third_repair_memory_recall_token = recipient correction marker recalled`;
- `current_post_third_proof_age_owner_status_token = current recipient-of-record proof` or `current
  official-record proof`;
- `learner_safe_action_after_third_dewatch_token = submit once with dual-route recognition` or `do
  not duplicate filing`; and
- `post_third_dewatch_disposition_and_reopen_token = recipient correction reopened` or
  `repeat-relapse threshold candidate`.

Do not convert the repeated recipient-side error into learner fault unless a current
recipient-of-record rule expressly requires a no-penalty route-native refile.

### Example C — protected proof stays local after third dewatch

A third rewatch retained a protected accommodation route locally while the public route was
refreshed. Later, the public route again contradicts the protected route, and the proof needed to
resolve it includes sensitive support information.

Publish:

- `post_third_dewatch_exit_basis_token = protected route retained`;
- `post_third_dewatch_relapse_signal_and_scope_token = same protected route conflict`;
- `third_repair_memory_recall_token = protected proof local-only`;
- `current_post_third_proof_age_owner_status_token = current protected-owner proof` or `local-only
  proof`;
- `learner_safe_action_after_third_dewatch_token = protected local-only submission`; and
- `post_third_dewatch_disposition_and_reopen_token = protected route retained`.

Do not publish accommodation, privacy, safety, appeal, or support proof as a public serial-repair
dossier.

### Example D — official-record dependency returns

A third rewatch dewatched after the official record reflected the refreshed repaired route. Later,
the public route and recipient portal remain current, but the official record again shows the old
value for the same learner-facing field.

Publish:

- `post_third_dewatch_exit_basis_token = official record corrected`;
- `post_third_dewatch_relapse_signal_and_scope_token = same official-record dependency`;
- `third_repair_memory_recall_token = official-record correction marker recalled`;
- `current_post_third_proof_age_owner_status_token = current official-record proof` or `proof
  mismatched`;
- `learner_safe_action_after_third_dewatch_token = wait for owner confirmation` or `use more
  protective route until resolved`; and
- `post_third_dewatch_disposition_and_reopen_token = official-record correction reopened`.

Do not treat one official-record relapse as proof that every source, search, archive, recipient,
protected route, redesign handoff, and learner filing surface has failed.

### Example E — no-active-route residue gains a current owner

A third rewatch closed as no-active-route residue because neither the old nor refreshed owner route
remained active. A later support page names a successor office and ticket route for the same route
family, but the office has not confirmed whether the third-repaired route still controls.

Publish:

- `post_third_dewatch_exit_basis_token = no-active-route residue`;
- `post_third_dewatch_relapse_signal_and_scope_token = same no-active-route residue gained owner`;
- `third_repair_memory_recall_token = memory unavailable residue` or `public minimized summary
  only`;
- `current_post_third_proof_age_owner_status_token = successor owner proof current` or `owner
  changed`;
- `learner_safe_action_after_third_dewatch_token = wait for owner confirmation` or `manual local
  support only`; and
- `post_third_dewatch_disposition_and_reopen_token = no-active-route residue` or `material reopen
  trigger named`.

Do not make newly discovered ownership retroactively fault a learner who used the last safe
published route.

## Non-goals

This layer does **not** create:

- an automatic fourth rewatch after every later recurrence;
- a permanent serial-repair stigma label;
- a public third-rewatch proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, all-record, or all-engine third-repair
  certificate;
- a universal memory-recall window for every route family;
- a no-memory reset after third dewatch; or
- a rule that every later recurrence must be counted toward a new threshold.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about repairing routes repeatedly. It is about
preventing repeated repair from becoming either permanent suspicion or unusable memory.

This layer matters because both extreme defaults harm learners and owners. One bad default says any
route that needed third rewatch is forever unstable, so every later signal justifies fourth watch,
duplicate filing, and public proof retention. Another bad default says third dewatch wipes history
so completely that owners must rediscover the same protected-route conflict, recipient correction,
official-record dependency, redesign miss, retired-route posture, or no-active-route residue from
scratch. The portable answer is narrower: publish the third-exit basis, later signal, affected
third-repair scope, scoped memory recall, current proof and owner status, learner-safe action, and a
disposition that closes, reminimizes, reopens a named correction, retains protected handling, opens
redesign review, revives retired-route posture, names residue, routes natively, or marks a
repeat-threshold candidate on current facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `ZD0-ZD4` has not already closed third rewatch, refreshed repair, minimized proof, or completed a
  third dewatch;
- the current question is still how third rewatch operates, proves renewed-repair refresh, or
  third-dewatches rather than how a later event recalls memory;
- the later event is unrelated to the third-repaired route, owner, proof object, clock, recipient,
  protected route, official record, redesign handoff, retired-route posture, no-active-route
  residue, or affected surface;
- the later signal is only search, cache, crawler, archive, image, or downstream copy lag with no
  current learner-facing owner, proof, clock, recipient, protected-route, official-record, or live
  dependency effect;
- a route-native process already names post-third-dewatch relapse handling, third-repair memory
  recall, current proof age, learner-safe action, disposition, and reopen triggers;
- the only available proof is stale, expired, screenshot-only, owner-claim-only, anecdotal,
  unrelated to a current owner, or unrelated to a learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules
  already control proof handling and should stay local-only; or
- repeated post-third-dewatch recurrence has already crossed a named threshold and the question is
  now threshold operation rather than first memory recall.

In those cases, publish `closed as ordinary lag`, `new unrelated path`, `route-native control`,
`protected local-only route`, `none current`, `current third rewatch still open`, `fresh first-cycle
conflict`, `repeat-relapse threshold already open`, `reminimized false alarm`, or `none inherited`
rather than creating a post-third-dewatch memory layer.

## What this closes

This closes `FT-0158`.

The archive no longer stops at "third rewatch operated and third-dewatched". It can now publish a
minimal post-third-dewatch relapse / third-repair memory layer: third-exit basis, later relapse
signal, third-repair scope, scoped memory recall, current proof age, owner status, learner-safe
action, disposition, reminimization, and reopen triggers when a route later relapses again,
repair-refresh proof ages, minimized third-rewatch memory must be recalled, protected or recipient
corrections reappear, official-record dependency returns, redesign proof fails, retired-route
posture revives, no-active-route residue exposes a current owner, or split-surface recurrence
becomes visible.

It also opens one narrower seam.

After later post-third-dewatch relapse has been classified and third-repair memory has been recalled
or minimized, the archive may still need a tiny repeat post-third-dewatch relapse / third-repair
rewatch-threshold layer for cases where the same route, owner, proof object, clock, recipient,
protected route, redesign handoff, official-record dependency, retired-route posture,
no-active-route residue, source/search/archive surface, or split-surface recurs again — without
making every recurrence automatic fourth rewatch, every serial repair a permanent stigma label,
every learner action duplicate filing, or every third-rewatch proof object a public vault.
