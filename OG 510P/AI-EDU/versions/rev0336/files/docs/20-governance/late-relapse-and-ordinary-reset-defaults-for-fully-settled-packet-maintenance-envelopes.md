# Late-relapse and ordinary-reset defaults for fully settled packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance
envelope has cooled locally, regained portable status, survived its watched re-entry cycle, restored
ordinary promoted status, completed its recent-repair-sensitive first ordinary cycle cleanly, and
truthfully rejoined fully settled ordinary status, does it still need one distinct shared
late-relapse / ordinary-reset package after a materially quiet settled cycle, or should later
failures simply fall back to the ordinary promoted canon?**

The archive's answer is narrower one last time:

> a maintenance class that has truthfully rejoined **fully settled ordinary status** should usually
not carry any further special late-relapse / ordinary-reset package. In the starter canon, fully
settled ordinary `PME-LABEL`, record-owner calendar upkeep, route calendars, and safety calendars
all fall back to the ordinary promoted checkpoint / departure / reset canon rather than carrying a
distinct post-settlement relapse layer.

The point is to avoid three opposite errors at once:

- **shadow-probation after settlement** — a service declares that a path is fully settled ordinary
  again but then quietly keeps a hidden “recently repaired” status alive through a distinct
  post-settlement relapse package;
- **duplicate-canon clutter** — a service republishes an ordinary promoted reset rule under a new
  late-relapse label even though the ordinary canon already says everything the post-settlement path
  needs;
- **false closure** — a service claims there is no need for any special post-settlement layer when
  the real problem is that the path never earned truthful fully settled ordinary status in the first
  place.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI
toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's
current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance
snapshots; Study Mode and related learning surfaces continue to frame the product direction as
guided understanding rather than quick-answer posture; and UNESCO's 2026 teacher and student
competency frameworks keep human agency and AI pedagogy central. See `B11`, `B23`, `B143`, `B146`,
`B149`, `B150`, `B151`.

## Three post-settlement relapse tiers

The archive now distinguishes three post-settlement relapse tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `LRO-BOTH` | the fully settled ordinary envelope carries one shared late-relapse trigger family and one shared ordinary-reset rule | the minimum fact that certain later failures count as a special post-settlement relapse and the minimum fact about what reset follows | any stricter local watch, any owner-local review packet, and any stronger local publication or challenge route |
| `LRO-FLAG` | the envelope carries only one shared late-relapse flag floor | the minimum fact that some later failures should be named as post-settlement relapse events | whether those events produce any reset beyond the ordinary promoted canon |
| `LRO-NONE` | the fully settled ordinary envelope carries no special post-settlement relapse layer | only the ordinary promoted checkpoint / departure / reset canon that already governs settled maintenance | both late-relapse labeling and any extra reset package |

The archive is deliberately asymmetric again:

> once a maintenance class has truthfully earned `FS-SETTLED-ORDINARY`, the burden shifts sharply
against any new special layer. A distinct post-settlement relapse package is presumptively evidence
that fully settled ordinary status was overstated or that the ordinary canon is still
under-specified.

## Five tests for whether any post-settlement relapse layer is really needed

A fully settled ordinary promoted maintenance envelope may harden above `LRO-NONE` only when all
five tests hold.

1. **non-duplication test** — the proposed late-relapse layer adds a real truth not already carried
   by the ordinary promoted checkpoint / departure / reset canon.
2. **same-settled-meaning test** — “fully settled ordinary again” really means the same thing across
   the reuse scope rather than some owners quietly preserving a latent repaired-state shadow.
3. **same-late-relapse trigger test** — the kinds of later failures that are supposed to count as a
   special post-settlement relapse can actually be described in one reusable way rather than
   collapsing back into the ordinary breach / departure / reset grammar.
4. **same-reset-consequence test** — once the late-relapse trigger fires, the reset consequence is
   genuinely different from the ordinary promoted canon and remains stable across the reuse scope.
5. **no-shadow-probation test** — the proposed post-settlement layer does not merely smuggle back an
   unpublished probation, recent-repair stigma, or hidden fast-collapse rule underneath the label
   “fully settled ordinary.”

Failing the first, fourth, or fifth test keeps the envelope at `LRO-NONE`. Failing only the fourth
may someday point to `LRO-FLAG`, but the starter canon does not yet use that middle tier.

## The starter post-settlement answer

The archive now makes one compact starter claim:

| Code | Meaning |
|---|---|
| `NO-LRO-LAYER` | once a maintenance path has truthfully earned `FS-SETTLED-ORDINARY`, later failures should fall back to the **ordinary promoted checkpoint / departure / reset canon** rather than carrying any distinct post-settlement relapse package |

The starter canon is deliberately small:

- no fully settled ordinary maintenance envelope currently carries one shared late-relapse trigger
  family beyond the ordinary canon;
- no fully settled ordinary maintenance envelope currently carries one shared ordinary-reset rule
  beyond the ordinary canon;
- if a service believes a later failure still needs a special repaired-state package after supposed
  settlement, the archive treats that as evidence that the path was not yet truthfully fully settled
  ordinary or that the ordinary promoted canon needs repair upstream rather than one more
  post-settlement layer.

## The archive's starter post-settlement answers

### Fully settled ordinary `PME-LABEL` stays `LRO-NONE`

Fully settled ordinary `PME-LABEL` should currently carry **no** distinct late-relapse package.

Why:

- once label/plain-language maintenance has truthfully earned `RSX-CLEAN-1ORDINARY +
  FS-SETTLED-ORDINARY`, the path has already demonstrated that special repair residue has cleared
  and that later failures can be governed honestly through the ordinary promoted canon;
- a special late-relapse layer here would usually duplicate the existing ordinary checkpoint /
  departure / reset logic rather than add a new truthful governance fact;
- if a label-maintenance path still seems to need a distinct “recently repaired” fallback after
  settlement, that is usually evidence that `FS-SETTLED-ORDINARY` was claimed too early.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, `CFP-BOTH`,
`RXP-BOTH`, `RPW-BOTH`, `ORS-BOTH`, `RSC-BOTH`, and `SOS-BOTH`, it should usually fall back to
`LRO-NONE` with `NO-LRO-LAYER` rather than carrying any distinct post-settlement relapse package.

What this means in practice:

1. a later label-shell failure after a materially quiet settled cycle is handled as an ordinary
   promoted breach, departure, or reset event;
2. the service should not revive a hidden repaired-state label merely because the path once passed
   through recovery;
3. any institution that cannot tell that story truthfully should reopen the earlier final-settling
   claim instead of inventing a new post-settlement layer.

### Fully settled ordinary `PME-CALENDAR` for `AF-RECORD` stays `LRO-NONE`

Record-owner calendar upkeep also stays `LRO-NONE`.

Why:

- record-owner calendars never earned a shared final-settling package in the first place, so there
  is no honest shared post-settlement relapse package to add on top;
- where a record-owner calendar has settled locally, later failures are still handled through the
  ordinary local or promoted canon that already governs that owner-bound path.

### Fully settled ordinary `PME-CALENDAR` for `AF-ROUTE` stays `LRO-NONE`

Route-case calendar upkeep likewise stays `LRO-NONE`.

Why:

- route calendars keep final-settling truth local, so a shared post-settlement relapse package would
  only compound a portability claim the archive never made;
- later route-calendar failures should therefore keep using the ordinary route-owned checkpoint /
  departure / reset logic already in force.

### Fully settled ordinary `PME-CALENDAR` for `AF-SAFETY` stays `LRO-NONE`

Safety/supervisor calendar upkeep also stays `LRO-NONE`.

Why:

- safety calendars keep final-settling truth local and remain tightly coupled to live exposure and
  duty staging;
- a distinct shared late-relapse package here would either duplicate ordinary safety-governance
  logic or reintroduce a shadow repaired-state story the archive is trying to avoid.

## What the archive is refusing for now

The archive is intentionally declining four stronger claims:

1. any shared post-settlement relapse package for fully settled ordinary `PME-LABEL`;
2. any shared post-settlement relapse package for record-owner, route, or safety calendar envelopes;
3. any claim that fully settled ordinary status may truthfully coexist with a hidden repaired-state
   or “recently restored” post-settlement layer;
4. any attempt to use a late-relapse package to patch what should really have been a stricter
   earlier final-settling judgment.

## Why this counted as a real archive gain

The archive already knew which recurring maintenance classes can travel, which numeric and
checkpoint layers sometimes travel with them, which renewal, cumulative-cycle, re-promotion,
watched-cycle, restoration, post-restoration caution, and final-settling packages sometimes travel
too. But it still lacked the last tight answer:

- whether any maintenance class that has truthfully rejoined fully settled ordinary status still
  needs one more special layer after settlement;
- and whether a distinct late-relapse package clarifies governance or merely hides that settlement
  was overstated.

This revision now answers that last narrow question with one small closure move:

- three post-settlement relapse tiers;
- five tests for whether any post-settlement relapse layer is really needed;
- one tiny starter rule, `NO-LRO-LAYER`;
- and a starter judgment that every currently named fully settled ordinary maintenance class stays
  `LRO-NONE`.

That is a real operating gain because it blocks three opposite mistakes at once:

- declaring paths fully settled and then quietly keeping a shadow probation alive;
- bloating the archive with a redundant post-settlement reset layer that just restates the ordinary
  canon;
- and hiding an earlier final-settling mistake by papering it over with one more downstream package.

## Current archive bet

The archive's current best guess is that **portable packet maintenance should become harder at each
stage and then stop: baskets travel first, then some numeric bands, then some checkpoint / breach
packages, then some fresh-cycle republication and recurrence duties, then at most one shared
cumulative-cycle ceiling and cooling rule, then at most one shared monitored re-promotion package,
then at most one shared watched re-entry package, then at most one shared restoration package, then
at most one shared post-restoration caution package, then at most one very small final-settling
package, and after truthful settlement later failures should simply fall back to the ordinary
promoted canon rather than spawning a new special relapse layer.**

That claim is now canon, but still revisable. The packet-maintenance chain is provisionally closed
here: it should be reopened only if evidence shows that some class can truthfully be both **fully
settled ordinary** and yet still needs a distinct post-settlement relapse package that is neither
redundant nor a disguised shadow probation.
