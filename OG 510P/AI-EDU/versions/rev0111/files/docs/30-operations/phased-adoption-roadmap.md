# Phased adoption roadmap

The archive's current rollout logic is **sequence matters**.

## Phase 0 — Readiness

Before broad deployment:

- establish privacy, procurement, and rights review;
- decide which uses are low-, medium-, and high-stakes;
- train leaders and early teacher cohorts;
- choose a governed institutional workspace;
- classify the first recurring use cases on the deployment ladder (`D0-D4`);
- identify any student-facing services that already inherit stricter starter profiles because they involve minors, professional-practice progression, credit-bearing pathway support, or benefits-linked public routing;
- identify any institution-facing offices that already inherit stricter starter profiles because they involve minors, professional gatekeeping, or benefits-linked public routing;
- choose the first memory / personalisation defaults for learner-, teacher-, and institution-facing AI use;
- choose the first observability/retention defaults for learner-, teacher-, and institution-facing AI use;
- publish the first failure-escalation owner, manual fallback path, and no-learner-penalty rule for any recurring service;
- publish the first change-classification and fresh-review rule for any recurring service, including live-window freezes and rollback ownership;
- define the first proof metrics;
- and decide how accessibility, accommodation, and multilingual support requests route without forcing public disclosure.

## Phase 1 — Teacher productivity and teacher minimum

Start where upside is visible and risks are manageable:

- lesson adaptation,
- feedback drafting,
- translation/accessibility support,
- administrative compression,
- and teacher AI fluency.

This phase builds staff competence before normalizing student dependence, but it should not be treated as a blank cheque for teacher-side delegation. In parallel, institutions should identify whether teaching minors, running credit-bearing higher-ed courses, supervising live professional practice, or teaching inside public adult-route systems already requires the archive's stricter teacher-facing starter profiles rather than one generic staff-productivity rule. They should also identify whether any internal attendance, registrarial, advising, selection, or public-route offices already need the archive's stricter institution-facing starter profiles rather than one generic operations rule. Institutions should publish where planning help, materials drafting, feedback assistance, marking support, analytics, and communication sit on the deployment ladder before these uses become ordinary workflow, and whether staff see aggregate signals, selected excerpts, or full content for any of those uses. They should also state what the system remembers across sessions, whether that memory is learner-declared or inferred, whether any recurring service already inherits one of the archive's hotter memory starter profiles for minors, formal assessment, professional gatekeeping, or public-route services, and if any branch already sits on `M3`, whether it uses the archive's shared support/access/route rail schema or a function-locked local-only map. For the function-locked rails they should also publish which parts of that map belong to the portable rights floor, which are rail-family presumptions, and which remain permanently local, rather than treating the whole rail as one opaque local code. Where a local system departs from a strengthened or branched family presumption, they should also publish the rebuttal packet with named reason, scope, substitute protection, and expiry or review trigger. Where a function-locked `M3` branch now sits inside `RS-EXTERNAL-PRACTICE-ACCESS` or `QS-SCARCE-SEAT`, they should also publish the named authority / regime sub-branch in use rather than relying on one generic parent overlay; where it sits inside `QS-URGENT-DUTY`, they should publish whether it has entered the named `QS-UD-CHILD-SAFETY` branch or is still using only the first-stable review point plus a regime-local minimal-loss route, rather than implying that ordinary timestamp-preservation or full pause still travels. And for any `RS-EPA-LS-EXTERNAL-BAR`, `QS-SS-RS-CROSS-OWNER`, or `QS-UD-CHILD-SAFETY` branch, they should now publish the archive's tiny authority-sensitive shared packet — branch + authority shape, present constraint family, non-override statement, earliest meaningful review point, strongest guaranteed interim path, and challenge / explanation route — instead of burying cross-owner or multi-agency facts inside local casework notes. Where those branches now use one of the archive's authority-family variants, they should also publish that narrower family shape — regulator-bar versus host-bar, public-dispatch versus partner-inventory, or provider-led safeguarding review versus formal multi-agency child-protection stage — while still keeping detailed merits tests, legal calendars, and concrete interim protections local unless the archive later hardens them. Where the archive now supplies a mini-code for the next review event or interim path, institutions should publish it too — for example `EA-DISPATCH-CYCLE`, `EA-CP-STAGE`, `IP-PROTECTED-HANDOFF`, or `IP-SAFETY-COMPATIBLE-CONTINUITY` — and where the archive now hardens a default pairing they should publish that pairing as a bundle rather than scattering its parts across notices. They should also state the limited effect that travels with the bundle: preserved packet/date integrity, no ordinary penalty for a blocked exposure segment when the substitute path is followed, no learner-borne blame for partner-release delay once the handoff packet is complete, or no disengagement / misconduct label for compliance with a protective route. But they should not invent one shared calendar, one guaranteed queue-rank effect, or one fake substitute package where the archive still says local residue controls. If the same departure packet now recurs across partners, cohorts, or the service's own next review cycle, institutions should escalate from publication to governance change: the archive now expects branch creation, cooling, or office-bound reclassification rather than endless local exception notices. They should also say what happens if the service drifts, fails, or becomes unavailable during live teaching rather than assuming teachers or learners will improvise continuity, publish which changes count as bounded maintenance versus fresh review for those services, and identify whether any minor-facing, assessment-critical, professional-practice, or public-route functions already inherit the archive's stricter failure profiles with faster brakes or change freezes, plus its stricter change profiles where some releases should already classify hotter than ordinary maintenance. ## Phase 2 — Student AI literacy and structured study use

Introduce student-facing AI in clearly bounded ways:

- a minimal literacy spine across grades or sectors,
- study companions,
- practice generation,
- scaffolding,
- guided writing support,
- and tutoring support.

But pair this with explicit rules for disclosure, appropriate delegation, and course-level norms. Institutions should also name one or two mode-tagged subject routines per family so AI literacy becomes visible in ordinary classes rather than only in policy, publish one short shared legend for mode/disclosure expectations, and state which support questions route privately through accessibility/accommodation channels. They should also publish which student-facing uses retain only aggregate signals, which allow selected excerpts, which remembered states stay at `M0-M2`, which inherited memory profile applies where the generic ladder is already too blunt, and which open a stronger human-owned record rail only after a named trigger. Where a learner-facing service becomes approved or routine, institutions should also publish the first substitute path and no-learner-penalty rule for system-caused interruption. The archive's current preferred sequence is: **without AI**, then **with guided educational AI**, then **with general-purpose AI**. When student-facing use becomes institutionally recommended or routinely provisioned rather than merely tolerated, the minimum posture should usually rise to a governed `D2` wrapper rather than unmanaged consumer-chat dependence — but tutoring, advising, accessibility routing, and well-being services should then be checked against the archive's function-family default table and, where relevant, its stricter student-facing sector-and-age profiles rather than assumed to share one generic level. Outside ordinary school or university enrollment, public systems should also stand up low-barrier adult entry points through libraries, community colleges/VET, and workforce navigation rather than assuming that only current students need structured AI learning. ## Phase 3 — Assessment redesign

This phase is often skipped and should not be. Once students have ordinary access to capable AI, institutions need stronger proof surfaces:

- more live tasks,
- more oral explanation,
- more checkpoints,
- more revision visibility,
- and fewer unauthenticated polished artifacts as stand-alone evidence.

The archive's current improvement is to define default **bundle** patterns so this phase is actionable rather than purely rhetorical, to link those bundles to mode-tagged subject routines, to cap their burden through a small proof-intensity/sampling grammar, to publish inherited hotter/cooler starter profiles for recurring course families rather than leaving burden tuning to local drift, to add a tiny sector-and-age overlay so minors, ordinary higher education, professional-practice training, and public adult-route learning do not all inherit the same proof floor, and to pair all of that with an observability rule that prefers selected excerpts over universal raw trace capture, plus a tiny sector-and-function overlay where minors, formal test monitoring, professional gatekeeping, or public-route coordination already need different default rails or stronger modality limits. See [`../40-assessment/proof-of-learning-bundles.md`](../40-assessment/proof-of-learning-bundles.md), [`../40-assessment/bundle-intensity-bands-and-sampling-ceilings.md`](../40-assessment/bundle-intensity-bands-and-sampling-ceilings.md), [`../40-assessment/subject-family-proof-intensity-defaults.md`](../40-assessment/subject-family-proof-intensity-defaults.md), [`../40-assessment/sector-and-age-profile-splits-for-proof-intensity-defaults.md`](../40-assessment/sector-and-age-profile-splits-for-proof-intensity-defaults.md), and [`subject-embedded-exemplar-kernel.md`](subject-embedded-exemplar-kernel.md).

## Phase 4 — Evidence-backed specialized tools

Only after governance, literacy, and assessment have moved should institutions scale more ambitious tools, especially those making personalization, tutoring, advising, or navigation claims. At that stage institutions should be able to say whether “personalisation” means learner-controlled preferences, bounded course continuity, or a hotter inferred learner model rather than using the term as a marketing blur. Public R&D and emerging trials suggest this is where long-run gains may come from, but the evidence bar must remain high, the use case should usually move to `D3` on the deployment ladder rather than resting on bare general-purpose chat, and the service should usually pass through a monitored `RG2` stage before any broad `RG3` approval, with a hotter burden or lower ceiling where the use case falls under the archive's rollout starter profiles for minors, formal assessment, professional gatekeeping, or public-route coordination. When institutions start reusing those starter rollout profiles, they should ask separately whether the same claim, operating model, human route, and infrastructure ceiling still travel; and in the archive's hotter parent profiles they should now also ask whether the service is still in the support branch or has crossed into a consequence-bearing child branch such as candidate-facing assessment control, readiness signalling, or queue-shaping public routing. They should now ask a parallel memory question too: whether the service still only needs learner-declared preferences or bounded continuity, or whether remembered state has crossed into a hotter starter profile that should move onto human-owned rails, branch, or remain capped below `M4`; and in those hotter parents they should now also ask whether the service still belongs in a cooler support-continuity child branch or has crossed into support-routing, candidate-control, readiness-signalling, or queue-shaping memory that should move earlier onto named `M3` rails or remain human-only. The archive now adds one more test: whether the memory claim is portable at all. If the remembered state only worked because it stayed inside one bounded function, institutions should not inherit it into another office or treatment path just because the same vendor surface persists. If a hotter branch does move onto `M3`, institutions should also say whether the rail inherits the archive's shared publication/challenge shell or a function-locked local-only map. For the function-locked rails they should now separate a portable rights floor from any rail-family presumptions and from the permanently local residue, instead of publishing one undifferentiated local map. They should also say whether a given family presumption has genuinely hardened, now belongs in one of the archive's named readiness / queue child branches, still needs a further office- or stakes-level branch, or is being locally rebutted with a published reason, substitute protection, and expiry. Where the service now sits inside one of those named child branches, they should also publish the inherited review-window band, substitute-path default, and publication trigger rather than leaving those as buried implementation detail. Otherwise the archive prefers a child branch, a named `M3` rail, or a governed cap rather than silent hardening. ## Phase 5 — Continuous evaluation and retirement

Institutional AI adoption should include explicit stop conditions. Even after `RG3` scale approval, institutions should keep a live review date, a rollback owner, and a rule for which model, prompt, memory, cohort, or workflow changes would reopen the rollout gate rather than quietly inheriting the old pilot result.

Institutional AI adoption should include explicit stop conditions:

- retire tools that do not produce value,
- demote tools that create dependency without understanding,
- and re-run equity and accessibility checks as use patterns change.

## Compact warning

The failure mode is easy to name:

> institutions adopt AI for convenience before they build literacy, guardrails, and new proof-of-learning surfaces.

That sequence makes cheating panic, brittle policy, and bad pedagogy more likely.


## Cross-cutting public route

Institutions should not wait until perfect school deployment to think about adults and workers. In parallel with the formal phases above, jurisdictions should identify at least one low-cost civic first-contact point, one bridge provider for deeper learning, and one workforce-navigation route so AI education remains a lifelong public pathway rather than a perk of current enrollment. They should also adopt a small shared handoff-and-recognition rule so learners do not restart intake at every node: low-friction entry, warm transfer, learner-controlled portability, recognition before duplication, a tiny machine-readable claim layer, a clear boundary between portable claims and protected local support records, published sector defaults for when outside AI-learning completions should count only for continuity, for waiver of duplicate basics, for review/challenge, or for formal credit, dated standing-equivalency lists for recurring outside cases, a tiny publication profile with review and expiry windows matched to the family of outside learning being recognized, and a no-fault continuity-cost rule so system-caused bridges, challenge steps, and substitute-equivalent routes do not simply become new learner invoices.
