# Portable re-promotion and cooldown-exit defaults for promoted packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance envelope has exceeded its cumulative-cycle ceiling and cooled locally, can portable status ever be regained under one shared monitored re-entry package, or should re-promotion stay fully local even when a cycle ceiling now travels?**

The archive's answer is narrower again:

> only maintenance classes whose **cooldown-exit truth** remains stable across the reuse scope should carry one shared re-promotion package. In the starter canon, only `PME-LABEL` usually carries one shared monitored re-entry package; record-owner calendar upkeep, route calendars, and safety calendars should keep recovery-to-portability local.

The point is to avoid three opposite errors at once:

- **forgiveness laundering** — a service treats one cooled local cycle as though it automatically restores the old promoted trust story even when the real repair evidence is owner-specific or redesign-specific;
- **permanent de-promotion** — a maintenance class whose cooldown-exit truth really is stable enough to travel never earns one small re-entry package and therefore has to re-litigate the same recovery-to-portability logic locally forever;
- **false monitored certainty** — the archive publishes one reusable re-entry package even though the meaning of a "clean repair cycle" or a truthful return to portability still varies materially by owner, regime, or calendar object.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance snapshots; UNESCO's 2026 competency frameworks keep human agency and AI pedagogy central; and ICO guidance keeps challengeable design, privacy by default, and child-facing limits in view. See `B11`, `B23`, `B143`, `B146`, `B149`, `B150`, `B151`.

## Three re-promotion portability tiers

The archive now distinguishes three re-promotion portability tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `RXP-BOTH` | the fatigued promoted envelope carries one shared cooldown-exit floor and one shared monitored re-promotion gate | the minimum cooled local cycle and the minimum clean re-entry evidence needed before portable status is reclaimed | any stricter local cooldown, any extra local reviewer, and any stronger local re-entry notice |
| `RXP-FLOOR` | the fatigued promoted envelope carries only one shared cooldown-exit floor | the minimum fact that portable status may not return immediately after fatigue | the actual evidence bundle, review owner, and re-promotion gate |
| `RXP-LOCAL` | the fatigued promoted envelope carries no shared re-promotion package | only the earlier basket / numeric / checkpoint / republication / cumulative-cycle tiers | both the cooldown-exit floor and the re-promotion gate |

The archive is deliberately asymmetric again:

> re-promotion portability is harder to earn than fatigue portability. A class can carry one shared cycle ceiling and one shared cooling move while the truth about *getting portability back* still remains owner-local.

## Five tests for whether cooldown-exit truth really travels

A fatigued promoted portable maintenance envelope may harden above `RXP-LOCAL` only when all five tests hold.

1. **same-repair-object test** — the cooled local cycle is genuinely repairing the same maintenance object rather than using one local redesign, one office migration, or one wording rewrite to stand in for many different kinds of repair.
2. **same-cooldown-floor test** — the proposed shared cooldown floor means the same thing across the reuse scope: portable status really is absent until at least the same minimal local repair step has occurred.
3. **same-clean-reentry-evidence test** — the minimum evidence for truthful re-promotion can be described in one reusable way without concealing who reviewed the cooled cycle, what remained local, or which breach conditions had to clear.
4. **no-forgiveness-laundering test** — the shared package does not make one merely quiet local cycle look like genuine repair when the maintenance class is still drifting, redesigning, or living on exception handling.
5. **same-first-repromoted-cycle truth test** — the first cycle after re-promotion really starts with the same bounded trust story across the proposed scope rather than with owner-specific probation, conditional approval, or shadow repair that the portable tag would conceal.

Failing the first, fourth, or fifth test keeps the envelope at `RXP-LOCAL`. Failing only the third may eventually point to `RXP-FLOOR`, but the starter canon does not yet use that middle tier.

## The starter cooldown-exit / re-promotion package

The archive now names one shared cooldown-exit floor and one shared monitored re-promotion gate.

| Code | Meaning |
|---|---|
| `CD-1LOCAL` | after exceeding the portable cumulative-cycle ceiling, at least **1 full fresh cycle** must run under local publication before portable status may be claimed again |
| `RG-CLEAN-REPROMOTE` | re-promotion is allowed only after that cooled local cycle closes cleanly: the promised checkpoint has completed, no unresolved breach remains open, no basket/scope/field-logic expansion has occurred, and the next portable cycle is republished as a new re-entry rather than as silent continuation |

The archive does **not** yet create a richer re-entry ladder. The starter canon is deliberately small:

- no fatigued promoted maintenance envelope may currently regain portable status without at least one full cooled local cycle;
- no fatigued promoted maintenance envelope may currently reclaim portable status by elapsed time alone;
- where the archive refuses a shared cooldown-exit or re-promotion package, services must still publish a **local** repair-to-portability path or say plainly that portability has not yet been regained.

## The archive's starter re-promotion answers

### `PME-LABEL` usually hardens as `RXP-BOTH` with `CD-1LOCAL + RG-CLEAN-REPROMOTE`

`PME-LABEL` may usually carry **both** one shared cooldown-exit floor and one shared monitored re-promotion gate across its promoted branch scope.

Why the archive allows this:

- label/plain-language fatigue usually means the same thing across the branch scope: repeated cycles have made the wording shell unstable enough that the portable claim must cool;
- one cooled local cycle usually does real repair work here rather than hiding a different owner, different field logic, or different challenge-route truth;
- the minimum clean re-entry evidence can usually be described the same way too: the local cycle closes, the promised shell checkpoint clears, no unresolved breach or reset cluster remains open, and the next portable cycle is explicitly republished as a fresh re-entry.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, and `CFP-BOTH`, and then cools under `FG-COOL-LOCAL`, it may usually also inherit `RXP-BOTH` with `CD-1LOCAL + RG-CLEAN-REPROMOTE`.

What this means in practice:

1. once a third label-maintenance cycle would otherwise begin, the promoted cumulative-cycle package cools and the next cycle runs locally;
2. that cooled local cycle must still publish its own checkpoint / breach / residue truth rather than pretending the old portable package remains live;
3. only after that cooled local cycle closes cleanly may the following cycle reclaim promoted portable status, and it must republish that claim as a fresh re-entry rather than as continuous coverage from the pre-fatigue period.

What still collapses `RXP-BOTH` immediately:

- any cooled local cycle that changes basket scope, field logic, family-conditioned meaning, review-anchor truth, or challenge-route prominence;
- any unresolved `BR-PME-CORE` breach, packet reset cluster, or local departure that still denies clean shell continuity;
- any attempt to treat a quiet elapsed period, an unreviewed copy cleanup, or an unpublished local workaround as though it were the cooled repair cycle.

### `PME-CALENDAR` for `AF-RECORD` stays `RXP-LOCAL`

Record-owner calendar housekeeping keeps **both** the cooldown-exit floor and the re-promotion gate local in the starter canon.

Why the archive stops here even though `AF-RECORD` already earned narrower portability wins:

- record-owner calendar fatigue is already local at the cumulative-cycle layer, so the truth about what counts as repair after fatigue remains tied to local term structure, record issuance cadence, award-cycle practice, or board timing;
- one local cycle may be enough in one regime but too little or too much in another, which means both the cooldown floor and the evidence for regained portability remain owner-local;
- a shared re-promotion gate would too easily make record-specific cleanup or schedule normalization look like a truthful cross-site portable recovery story when it still depends on local record practice.

### `PME-CALENDAR` for `AF-ROUTE` stays `RXP-LOCAL`

Route-case calendar upkeep also remains fully local after fatigue.

Why:

- route calendars already keep cumulative-cycle handling local because partner inventory, callback truth, and queue or referral meaning vary too much across regimes;
- the evidence that route-calendar drift has really been repaired is still too dependent on local partner practice, exposure commitments, and current route architecture to claim one reusable re-promotion gate honestly.

### `PME-CALENDAR` for `AF-SAFETY` stays `RXP-LOCAL`

Safety/supervisor calendar upkeep remains fully local after fatigue.

Why:

- safety calendars are closely coupled to live exposure judgment, duty staging, or safeguarding timelines;
- a shared cooldown-exit package would risk hiding meaningful differences in local protective review and the seriousness of what a "clean" local cycle would actually need to show.

## What the archive is refusing for now

The archive is intentionally declining four stronger claims:

1. any shared re-promotion package that allows portable status to return with **zero** cooled local cycles;
2. any shared re-promotion package that treats elapsed time alone as sufficient repair evidence;
3. any shared re-promotion package for record-owner, route, or safety calendar envelopes;
4. any claim that a cooled local cycle can regain portable status without explicit republication of the next portable cycle as a fresh re-entry.

## Why this counted as a real archive gain

The archive already knew which promoted maintenance envelopes can travel, which quantitative and proof layers sometimes travel with them, which fresh-cycle duties sometimes travel too, and which of those envelopes can carry one shared cumulative-cycle ceiling with a cooling rule. But it still lacked the next tighter answer:

- whether a cooled portable envelope can ever regain portable status under one shared monitored re-entry path;
- and whether the archive should distinguish classes where that recovery-to-portability truth travels from classes where it still depends too heavily on local repair practice.

This revision now answers that narrower question with one small ratchet:

- three re-promotion portability tiers;
- five tests for whether cooldown-exit truth really travels;
- one tiny starter package, `CD-1LOCAL + RG-CLEAN-REPROMOTE`;
- and a starter judgment that only promoted label/plain-language maintenance usually carries it.

That is a real operating gain because it blocks three opposite mistakes at once:

- treating one cooled local cycle as automatic forgiveness for every fatigued maintenance class;
- making label maintenance permanently local after fatigue even when its repair-to-portability story is actually stable enough to travel;
- and using a portable re-entry claim to conceal unresolved drift, hidden redesign, or owner-specific repair evidence.

## Current archive bet

The archive's current best guess is that **portable packet maintenance should become harder at each stage: baskets travel first, then some numeric bands, then some checkpoint / breach packages, then some fresh-cycle republication and recurrence duties, then at most one shared cumulative-cycle ceiling and cooling rule, and only after that may a very small monitored re-promotion package sometimes travel — with only promoted label/plain-language maintenance usually carrying one shared `CD-1LOCAL + RG-CLEAN-REPROMOTE` package while record-owner calendar upkeep, route calendars, and safety calendars keep recovery-to-portability local.**

That claim is now canon, but still live.
