# Portable recent-repair-expiry and fully settled ordinary-status defaults for post-restoration packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance envelope has cooled locally, regained portable status, survived its watched re-entry cycle, restored ordinary promoted status, and then completed its first recent-repair-sensitive ordinary cycle cleanly, can that clean first ordinary cycle itself carry one shared recent-repair-expiry / fully settled ordinary-status package, or should the final settling boundary still remain local even after the archive has already allowed a shared caution-marked first ordinary cycle?**

The archive's answer is narrower again:

> only maintenance classes whose **final settling truth** remains stable across the reuse scope should carry one shared recent-repair-expiry / fully settled ordinary-status package. In the starter canon, only post-restoration `PME-LABEL` usually carries one shared final-settling package; record-owner calendar upkeep, route calendars, and safety calendars should keep that last settling boundary local.

The point is to avoid three opposite errors at once:

- **premature full settlement** — a service treats a single clean first ordinary cycle as automatic proof that all recent-repair sensitivity has expired everywhere, even where the meaning of “fully settled ordinary again” still depends on owner-local residue review or cadence;
- **shadow-settling drift** — a service publishes one shared recent-repair-sensitive first ordinary cycle but then clears or preserves its residual caution only through unpublished owner-local judgment, leaving the portable story incomplete at the exact point when trust is supposedly normal again;
- **permanent residue stigma** — a maintenance class whose clean first ordinary cycle really does end recent-repair sensitivity in the same way across the reuse scope never earns one small shared settling package and therefore has to keep restating the same already-proven caution residue locally forever.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance snapshots; Study Mode and related learning surfaces continue to frame the product direction as guided understanding rather than quick-answer posture; and UNESCO's 2026 teacher and student competency frameworks keep human agency and AI pedagogy central. See `B11`, `B23`, `B143`, `B146`, `B149`, `B150`, `B151`.

## Three final-settling portability tiers

The archive now distinguishes three final-settling portability tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `SOS-BOTH` | the caution-marked restored ordinary envelope carries one shared recent-repair-expiry floor and one shared fully settled ordinary-status rule | the minimum fact that a clean first ordinary cycle ends special recent-repair sensitivity and the minimum fact that the next eligible cycle is now fully settled ordinary promoted status | any stricter local sign-off, any extra local checkpoint, and any stronger local publication or challenge route |
| `SOS-EXPIRY` | the envelope carries only one shared recent-repair-expiry floor | the minimum fact that a clean first ordinary cycle can end the special recent-repair-sensitive state | the actual rule for when a path is treated as fully settled ordinary again and any owner-local residual caution |
| `SOS-LOCAL` | the envelope carries no shared final-settling package | only the earlier basket / numeric / checkpoint / republication / cumulative-cycle / re-promotion / watched-cycle / restoration / caution tiers | both recent-repair expiry and fully settled ordinary status |

The archive is deliberately asymmetric again:

> final-settling portability is harder to earn than first-ordinary-cycle caution portability. A class can carry one shared recent-repair-sensitive first ordinary cycle while the truth about becoming **fully settled ordinary again** still remains owner-local.

## Five tests for whether final-settling truth really travels

A post-restoration, caution-marked promoted maintenance envelope may harden above `SOS-LOCAL` only when all five tests hold.

1. **same-clean-first-cycle meaning test** — a clean first ordinary cycle really means the same thing across the reuse scope rather than one owner using it as full closure while another treats it only as partial evidence pending hidden residue review.
2. **same-expiry boundary test** — the exact point at which special recent-repair sensitivity expires can be described in one reusable way rather than depending on local committee timing, local callback completion, or owner-specific caution residue.
3. **same-fully-settled meaning test** — saying that the next eligible cycle is now fully settled ordinary again means the same thing across the reuse scope: no special recent-repair caution remains, and failures are now handled by the ordinary promoted / departure canon rather than by accelerated re-cooling.
4. **no-shadow-settling test** — the shared settling package does not conceal owner-specific shadow review, unpublished residue checks, or hidden caution holdbacks that still materially determine whether fully settled ordinary status has actually returned.
5. **same-late-relapse inheritance test** — once fully settled ordinary status is restored, the maintenance path really inherits the same ordinary promoted packet-governance canon across the proposed scope rather than diverging immediately through owner-specific “recently repaired” exceptions or unpublished quick-collapse rules.

Failing the second, third, fourth, or fifth test keeps the envelope at `SOS-LOCAL`. Failing only the third may eventually point to `SOS-EXPIRY`, but the starter canon does not yet use that middle tier.

## The starter recent-repair-expiry / fully settled package

The archive now names one shared recent-repair-expiry floor and one shared fully settled ordinary-status rule.

| Code | Meaning |
|---|---|
| `RSX-CLEAN-1ORDINARY` | a **clean first recent-repair-sensitive ordinary cycle** ends the special post-restoration recent-repair sensitivity only if that cycle closes without unresolved breach residue, fresh reset cluster formation, basket / field-logic expansion, challenge-route weakening, or owner-family-conditioned meaning drift |
| `FS-SETTLED-ORDINARY` | once `RSX-CLEAN-1ORDINARY` is satisfied, the next eligible cycle returns to **fully settled ordinary promoted status** rather than carrying any special post-restoration caution package, while still inheriting the ordinary promoted checkpoint, recurrence, cumulative-cycle, and departure canon |

The archive does **not** yet create a richer settling ladder. The starter canon is deliberately small:

- no caution-marked restored ordinary envelope currently becomes fully settled by elapsed time alone;
- no caution-marked restored ordinary envelope currently carries one shared “two clean ordinary cycles before settlement” rule;
- where the archive refuses a shared final-settling package, services must still publish a **local** rule for when the post-restoration caution truly clears, or say plainly that fully settled ordinary status remains owner-local even after a clean first ordinary cycle.

## The archive's starter final-settling answers

### Post-restoration `PME-LABEL` usually hardens as `SOS-BOTH` with `RSX-CLEAN-1ORDINARY + FS-SETTLED-ORDINARY`

Post-restoration `PME-LABEL` may usually carry **both** one shared recent-repair-expiry floor and one shared fully settled ordinary-status rule across its promoted branch scope.

Why the archive allows this:

- label/plain-language post-restoration caution usually means the same thing across the branch scope: a wording shell cooled locally, re-entered portability, survived its watched cycle, restored ordinary promoted status, and then completed its one recent-repair-sensitive ordinary cycle cleanly without new shell drift or hidden rights-shell loss;
- the minimal settling boundary is usually stable too: once that first ordinary label cycle closes cleanly, the portable story no longer needs a special recent-repair-sensitive overlay and can fall back to the ordinary promoted package honestly;
- late relapse after settlement is already handled truthfully here by the ordinary packet-departure canon, so the archive does not need a separate shadow “recently repaired” rule after settlement.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, `CFP-BOTH`, `RXP-BOTH`, `RPW-BOTH`, `ORS-BOTH`, and `RSC-BOTH`, it may usually also inherit `SOS-BOTH` with `RSX-CLEAN-1ORDINARY + FS-SETTLED-ORDINARY`.

What this means in practice:

1. a clean first restored ordinary label cycle ends the special post-restoration caution package;
2. the next eligible label-maintenance cycle is treated as fully settled ordinary promoted status rather than as “ordinary, but still recently repaired”;
3. any later label drift is handled through the ordinary promoted checkpoint, departure, and reset canon rather than through a permanent shadow caution residue.

What still collapses `SOS-BOTH` immediately:

- any unresolved breach, reset cluster, field-logic expansion, challenge-route weakening, or owner-family-conditioned meaning drift during the caution-marked first ordinary cycle;
- any attempt to treat the path as fully settled before that first ordinary cycle has actually closed cleanly;
- any effort to smuggle owner-specific shadow caution or unpublished fast-collapse logic underneath the shared settling package.

### Post-restoration `PME-CALENDAR` for `AF-RECORD` stays `SOS-LOCAL`

Record-owner calendar upkeep should currently keep recent-repair-expiry and fully settled ordinary-status boundaries local.

Why:

- even after a clean first ordinary cycle, the meaning of “special recent-repair caution has now truly cleared” still depends too much on owner-local record cadence, issuance windows, board timing, or callback residue;
- a shared fully settled rule would therefore overstate how comparable the final settling boundary really is across record regimes;
- some record calendars may genuinely settle after one clean cycle, while others still need owner-local caution residue review, which defeats a truthful shared package.

### Post-restoration `PME-CALENDAR` for `AF-ROUTE` stays `SOS-LOCAL`

Route-case calendar upkeep also keeps final settling local.

Why:

- route calendars already keep restoration-to-ordinary trust and first ordinary-cycle caution local because callback truth, partner inventory, and exposure semantics vary too much across regimes;
- the point at which that caution finally clears is therefore even less likely to travel truthfully.

### Post-restoration `PME-CALENDAR` for `AF-SAFETY` stays `SOS-LOCAL`

Safety/supervisor calendar upkeep remains fully local after a clean first ordinary cycle.

Why:

- safety calendars are tightly coupled to live exposure judgment, duty staging, or safeguarding timelines;
- a shared final-settling package would risk hiding meaningful differences in when recent repair residue is considered fully cleared.

## What the archive is refusing for now

The archive is intentionally declining four stronger claims:

1. any shared final-settling package that says a clean first ordinary cycle always clears recent-repair sensitivity across all maintenance classes;
2. any shared final-settling package for record-owner, route, or safety calendar envelopes;
3. any shared package that lets a maintenance path appear fully settled while unpublished owner-local caution still materially governs the next cycle;
4. any claim that fully settled ordinary status needs a second permanent caution layer after `SOS-BOTH` is earned.

## Why this counted as a real archive gain

The archive already knew which promoted maintenance envelopes can travel, which quantitative and proof layers sometimes travel with them, which fresh-cycle and cumulative-cycle layers sometimes travel too, which of those envelopes can regain portable status under one shared monitored re-entry package, which first re-promoted cycle can carry one shared watched package, which clean watched cycles can restore ordinary promoted status, and which first restored ordinary cycle can still carry one shared recent-repair-sensitive caution package. But it still lacked the next tighter answer:

- whether a clean first ordinary cycle can end that special recent-repair sensitivity in one shared way at all;
- and whether the archive should distinguish classes where that final settling truth travels from classes where it still depends too heavily on local repair residue.

This revision now answers that narrower question with one small ratchet:

- three final-settling portability tiers;
- five tests for whether final-settling truth really travels;
- one tiny starter package, `RSX-CLEAN-1ORDINARY + FS-SETTLED-ORDINARY`;
- and a starter judgment that only post-restoration `PME-LABEL` usually carries it.

That is a real operating gain because it blocks three opposite mistakes at once:

- treating a clean first ordinary cycle as automatic full settlement for every maintenance class;
- making post-restoration label maintenance permanently residually local even when its final settling boundary is actually stable enough to travel;
- and using a portable caution story to conceal shadow-settling or unpublished residue review at the exact point when fully settled ordinary status is being claimed.

## Current archive bet

The archive's current best guess is that **portable packet maintenance should become harder at each stage: baskets travel first, then some numeric bands, then some checkpoint / breach packages, then some fresh-cycle republication and recurrence duties, then at most one shared cumulative-cycle ceiling and cooling rule, then at most one shared monitored re-promotion package, then at most one shared watched re-entry package, then at most one shared restoration package, then at most one shared post-restoration caution package, and only after that may a very small final-settling package sometimes travel — with only post-restoration label/plain-language maintenance usually carrying one shared `RSX-CLEAN-1ORDINARY + FS-SETTLED-ORDINARY` package while record-owner calendar upkeep, route calendars, and safety calendars keep final settling local.**

That claim is now canon, but no longer stands alone: the archive now answers the next question too in [`late-relapse-and-ordinary-reset-defaults-for-fully-settled-packet-maintenance-envelopes.md`](late-relapse-and-ordinary-reset-defaults-for-fully-settled-packet-maintenance-envelopes.md), which refuses any distinct post-settlement relapse layer once a path has truthfully rejoined fully settled ordinary status.
