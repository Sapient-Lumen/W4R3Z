# Portable first-post-repromotion watch and immediate re-cooling defaults for promoted packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance envelope has cooled locally, regained portable status under one shared monitored re-entry package, and then begins its first newly portable cycle, can that first post-repromotion cycle itself carry one shared watch / immediate re-cooling package, or should the relapse handling after re-entry remain local even though portability has technically returned?**

The archive's answer is narrower again:

> only maintenance classes whose **first post-repromotion probation truth** remains stable across the reuse scope should carry one shared watch / immediate re-cooling package. In the starter canon, only `PME-LABEL` usually carries one shared first-post-repromotion watch package; record-owner calendar upkeep, route calendars, and safety calendars should keep first-cycle relapse handling local.

The point is to avoid three opposite errors at once:

- **instant-normalisation drift** — a service treats regained portable status as though it were already ordinary, unmonitored trust even though the first cycle after re-entry is still where fragile repair claims most often fail;
- **probation laundering** — a service publishes one portable re-entry package and then quietly runs the first re-promoted cycle under owner-specific shadow review, unpublished relapse rules, or local re-cooling triggers that the portable story conceals;
- **permanent specialness** — a maintenance class whose first re-promoted cycle really can carry one small shared watch package never earns that portable probation layer and therefore has to describe the same first-cycle caution locally forever.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance snapshots; Study Mode and related learning surfaces continue to frame the product direction as guided understanding rather than quick-answer posture; and ICO guidance keeps privacy by default, profiling-off-by-default for children absent compelling reason, and challengeable design in view. See `B11`, `B23`, `B143`, `B146`, `B149`, `B150`, `B151`.

## Three post-repromotion watch portability tiers

The archive now distinguishes three first-post-repromotion watch portability tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `RPW-BOTH` | the re-promoted envelope carries one shared watched-cycle floor and one shared immediate re-cooling trigger family | the fact that the first newly portable cycle is still probationary, and the trigger family that collapses it back to local cooling before a second portable cycle begins | any stricter local reviewer, any extra local checkpoint, and any stronger local publication or challenge route |
| `RPW-WATCH` | the re-promoted envelope carries only one shared watched-cycle floor | the fact that renewed portable status is still watched for one cycle | the actual relapse / re-cooling trigger family and any local probation record |
| `RPW-LOCAL` | the re-promoted envelope carries no shared first-post-repromotion watch package | only the earlier basket / numeric / checkpoint / republication / cumulative-cycle / re-promotion tiers | both the watched-cycle floor and the immediate re-cooling package |

The archive is deliberately asymmetric again:

> first-post-repromotion watch portability is harder to earn than re-promotion portability. A class can carry one shared cooldown-exit / re-entry gate while the truth about the **first newly portable cycle after re-entry** still remains owner-local.

## Five tests for whether first-post-repromotion probation truth really travels

A re-promoted portable maintenance envelope may harden above `RPW-LOCAL` only when all five tests hold.

1. **same-first-cycle-object test** — the watched cycle is genuinely the same type of maintenance object across the reuse scope rather than using one owner-specific shell cleanup, one office migration, or one calendar reset to stand in for many different post-repromotion realities.
2. **same-probation-meaning test** — saying that the first re-promoted cycle is still watched means the same thing across the reuse scope: portable status is live again, but not yet ordinary, and the service is not quietly claiming full restored trust before this first cycle survives.
3. **same-immediate-re-cooling-truth test** — the minimal trigger family for collapsing the watched cycle back to local cooling can be described in one reusable way without concealing owner-specific relapse logic, unpublished side review, or hidden repair residue.
4. **no-shadow-probation test** — the shared package does not make one owner's local shadow review or unpublished caution look like ordinary portable monitoring when the real first-cycle scrutiny still differs materially by family or object.
5. **same-second-cycle-admission boundary test** — clearing the watched cycle really means the same thing for admission to a second portable cycle across the proposed scope rather than still depending on local committee sign-off, local freshness tests, or local repair residue that the shared package would conceal.

Failing the first, third, fourth, or fifth test keeps the envelope at `RPW-LOCAL`. Failing only the third may eventually point to `RPW-WATCH`, but the starter canon does not yet use that middle tier.

## The starter first-post-repromotion watch package

The archive now names one shared watched-cycle floor and one shared immediate re-cooling package.

| Code | Meaning |
|---|---|
| `PW-1REPROMOTED` | the **first cycle after portable status returns** runs as a watched portable cycle rather than as ordinary restored trust |
| `RC-IMMEDIATE-LOCAL` | during that watched cycle, any unresolved breach, fresh reset cluster, basket / field-logic expansion, owner-family-conditioned meaning drift, challenge-route weakening, or other watched-cycle failure immediately collapses the path back to local cooling before a second portable cycle may begin |

The archive does **not** yet create a richer watched-cycle ladder. The starter canon is deliberately small:

- no re-promoted portable maintenance envelope currently becomes fully ordinary again on the same cycle that portable status returns;
- no re-promoted portable maintenance envelope currently carries one shared "second-chance inside the watched cycle" rule;
- where the archive refuses a shared first-post-repromotion watch package, services must still publish a **local** watched-cycle or post-re-entry relapse rule, or say plainly that renewed portable status remains owner-local after re-entry.

## The archive's starter first-post-repromotion watch answers

### `PME-LABEL` usually hardens as `RPW-BOTH` with `PW-1REPROMOTED + RC-IMMEDIATE-LOCAL`

`PME-LABEL` may usually carry **both** one shared watched-cycle floor and one shared immediate re-cooling trigger family across its promoted branch scope.

Why the archive allows this:

- label/plain-language re-entry usually means the same thing across the branch scope: a wording shell that was cooled locally has already completed one clean local repair cycle and is now back under portable publication, but still has one first-cycle probation before ordinary trust is restored;
- the minimum watched-cycle failure family can usually be described the same way too: new shell drift, unresolved breach residue, reset-cluster formation, field-logic expansion, or rights-shell weakening means the watched cycle did not hold and must cool locally again before another portable cycle can begin;
- the admission boundary to a second portable cycle is still thin but usually truthful here: if the first re-promoted label cycle finishes cleanly without those watched failures, the archive can at least say the probation layer has been survived.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, `CFP-BOTH`, and `RXP-BOTH`, and then re-enters portable status under `CD-1LOCAL + RG-CLEAN-REPROMOTE`, it may usually also inherit `RPW-BOTH` with `PW-1REPROMOTED + RC-IMMEDIATE-LOCAL`.

What this means in practice:

1. after a fatigued promoted label envelope completes one clean cooled local cycle and regains portable status, the **next** cycle runs as portable but still watched;
2. that watched cycle must still publish the same portable checkpoint / breach / recurrence / fatigue shell it already promised, rather than relying on unpublished local shadow review;
3. if the watched cycle picks up unresolved breach residue, a fresh reset cluster, basket expansion, field-logic drift, or rights-shell weakening, portable status collapses back to local cooling immediately rather than rolling into a second portable cycle;
4. only a clean watched cycle can even begin to support the archive's later question about when renewed portability becomes ordinary again.

### Record-owner calendar upkeep stays `RPW-LOCAL`

Record-owner calendar upkeep should currently keep first-post-repromotion watch and immediate re-cooling local.

Why the archive does **not** promote a shared watch package here:

- even where a record-owner calendar envelope can honestly carry a shared `QC-2` cap and a shared breach family, the meaning of a *watched first re-promoted cycle* still varies materially with term objects, callback anchors, and owner-specific tolerance for slippage inside the calendar shell;
- one owner may treat the first post-re-entry cycle as ordinary if the checkpoint closes, while another still requires local sign-off around overlap, notice timing, or inherited claimant expectations;
- a shared immediate re-cooling family would therefore overstate how comparable the watched-cycle failure truth really is.

The archive therefore keeps calendar post-re-entry relapse handling local even when earlier cycle-fatigue and re-promotion steps already publish some reusable calendar structure.

### Route and safety calendars stay `RPW-LOCAL`

Route calendars and safety-owner calendars should also stay `RPW-LOCAL`.

The reasons are even stronger than for record-owner calendars:

- post-re-entry relapse handling is still tightly entangled with local protective review, callback guarantees, safeguarding exposure, and authority-specific challenge duties;
- the difference between "portable status returned but is still watched" and "portable status returned only for shell publication while underlying caution remains local" is not yet stable enough to travel;
- a shared watched-cycle package here would risk making owner-specific protective review look like ordinary portable reuse.

## What this changes in the packet-governance line

The archive now makes three things explicit that it had only implied before.

1. **Re-promotion is not yet ordinary trust.** Even where a portable re-entry package exists, the first newly portable cycle may still need a named probation layer.
2. **Probation portability is a new claim, not a free rider on re-promotion portability.** A class that earns `RXP-BOTH` does not automatically earn `RPW-BOTH`.
3. **Immediate re-cooling is sometimes portable.** For label/plain-language maintenance, the archive now thinks the watched-cycle failure family itself is stable enough to travel with the first re-promoted cycle.
