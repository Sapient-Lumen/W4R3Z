# First repeat post-second-dewatch relapse and renewed-repair rewatch-threshold defaults for hot-exam recipient followup shells

The archive can now publish one still smaller layer for the hottest exam-like learner-request routes.

It can already say:

- how repeated post-dewatch relapse crosses a repaired-route rewatch threshold;
- how renewed rewatch operates, refreshes repair, protects learner action, and exits through a second dewatch, split, redesign, retirement, or residue state;
- how a later post-second-dewatch recurrence recalls renewed-repair memory without turning proof back into a public vault; and
- how current proof age, owner status, learner-safe action, reminimization, and reopen triggers should be published after renewed rewatch has closed or second-dewatched.

That is still not enough.

Once a post-second-dewatch relapse has already been classified, the next error is to treat the next recurrence as automatic proof that the route now deserves a third rewatch, a permanent repeated-repair warning, duplicate learner filing, and revived public proof. The opposite error is to keep treating every later recurrence as an isolated post-second-dewatch memory event even when the same route, owner, proof object, clock, recipient, protected route, redesign handoff, retired-route posture, no-active-route residue, source/search/archive surface, or official-record dependency has recurred again after memory recall or reminimization. A search reflection can repeat while the source and recipient route remain fixed. A recipient correction can reappear in the same portal after a second dewatch. A protected route can repeatedly diverge while its proof must stay local. A redesign handoff can miss another proof point after renewed repair. A retired-route posture can revive again. No-active-route residue can repeatedly gain and lose a current owner. Or an official-record dependency can recur even though public source proof has not failed. Repetition matters only when it is material, scoped, owned, and tied to current learner action or current owner work.

This document adds one thing only:

- a **tiny repeat post-second-dewatch relapse / renewed-repair rewatch-threshold field set** for hot-exam recipient followup shells after `ZB0-ZB4` has already classified at least one post-second-dewatch renewed-repair memory event, but before the archive treats repeated recurrence as automatic third rewatch, permanent repeated-repair stigma, duplicate learner filing, public second-rewatch proof-vault revival, all-surface renewed-repair certification, or repeat-by-anecdote.

That means the archive now asks a narrower question than before. It no longer asks only **how a later recurrence after second dewatch recalls renewed-repair memory**. It now asks **when repeated post-second-dewatch recurrence becomes a named renewed-repair rewatch threshold — and when it should instead remain ordinary lag, scoped memory recall, protected local handling, recipient correction, redesign review, retired-route posture, no-active-route residue, official-record correction, split-surface handling, or reminimized false alarm**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation, Google-Search-only, and source-side permanent-removal boundaries rather than an automatic third-rewatch rule for every repeated reappearance. Google's Refresh Outdated Content route is exact page/image URL, changed/gone-content, request-status, additional-URL, and expiry based rather than a durable all-cycle renewed-repair monitor. Google's personal-content routes keep Search removal, source-page removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb separates local source edits, emergency edits, primary-contact follow-up, campus-search and lookahead ownership, caching, and major-search-engine non-control. Princeton separates local deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support, Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, project closeout, support tickets, and accommodation routing. Internet Archive asks for URL, time-period, control-period, and review context before exclusion. Bing distinguishes temporary block, up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites, exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals support a tighter archive rule: **the next truthful portability gain here is one tiny repeat-threshold layer for post-second-dewatch recurrence count, renewed-repair scope, threshold source, current owner, proof age, memory limits, learner-safe action, threshold disposition, minimization, and reopen triggers — but not one automatic third rewatch, one permanent repeated-repair stigma label, one duplicate-filing duty, one public second-rewatch proof vault, one all-surface renewed-repair certificate, or one repeat-by-anecdote threshold.** See `B270`.

## Field values that now travel together

When this layer is used, the shell should publish only six concrete fields:

1. `repeat_post_second_dewatch_recurrence_count_token` — `first repeat after ZB classification`, `second material post-second-dewatch recurrence`, `third or later material post-second-dewatch recurrence`, `recipient correction repeated again`, `protected route conflict repeated again`, `redesign handoff failed again after second dewatch`, `retired-route posture revived again`, `no-active-route owner churn repeated again`, `source search or archive reflection repeated`, `official-record dependency recurred`, `proof-age mismatch repeated after second dewatch`, `repeat below threshold`, `repeat not material`, `none inherited`, or `not published`;
2. `renewed_repair_rewatch_scope_token` — `same renewed repaired route pair`, `same current owner`, `same proof object`, `same clock or deadline`, `same recipient portal`, `same protected route`, `same source page`, `same search result family`, `same archive time slice or mirror family`, `same redesign handoff`, `same retired route posture`, `same no-active-route residue`, `same official-record dependency`, `split surface only`, `unrelated new path`, `none inherited`, or `not published`;
3. `renewed_repair_threshold_source_owner_token` — `route-native repeat threshold`, `current owner confirmed threshold`, `recipient of record threshold`, `protected local owner threshold`, `redesign owner threshold`, `successor owner threshold`, `official-record owner threshold`, `platform or archive status threshold`, `current owner discovered after residue`, `local-only threshold`, `no threshold owner`, `threshold denied stale proof`, `none inherited`, or `not published`;
4. `second_rewatch_proof_age_memory_limit_token` — `current renewed-repair proof controls`, `fresh owner proof required`, `second-dewatch proof aged`, `expired request row as-of only`, `stale screenshot as-of only`, `minimized second-rewatch summary recall only`, `recipient proof local-only`, `protected proof local-only`, `redesign proof pending`, `official-record proof pending`, `proof unavailable residue`, `public pointer only`, `memory not recalled`, `none inherited`, or `not published`;
5. `learner_safe_action_under_post_second_repeat_token` — `no learner action now`, `use current repaired route`, `submit once with dual-route recognition`, `clock held during owner repair`, `protected local-only submission`, `recipient correction pending no duplicate filing`, `official-record confirmation pending`, `wait for owner confirmation`, `manual local support only`, `owner-only repair`, `route-native refile optional`, `route-native refile required with no penalty`, `no adverse wrong-route fault`, `none inherited`, or `not published`;
6. `repeat_post_second_dewatch_threshold_disposition_token` — `below threshold ordinary handling`, `third rewatch threshold opened`, `renewed repair refresh requested`, `recipient correction reopened`, `protected route retained`, `redesign review reopened`, `retired-route posture watch opened`, `no-active-route residue`, `official-record dependency reopened`, `split-surface new shell`, `route-native rule controls`, `reminimized false alarm`, `threshold closed`, `none inherited`, or `not published`.

That is deliberately small. It is enough to show whether a recurrence has repeated inside the same renewed-repair scope, who owns the threshold, what proof and memory may be used, what the learner can safely do, and what bounded posture follows. It is not enough to create permanent serial surveillance, a public second-rewatch proof vault, a duplicate-filing duty, an all-surface renewed-repair certificate, a protected-proof publication duty, or a threshold based only on repeated anxiety.

## Minimal publication sentence

A learner-facing or owner-facing shell can usually say the whole thing in one sentence:

> This is `[repeat_post_second_dewatch_recurrence_count_token]` within `[renewed_repair_rewatch_scope_token]`. Threshold source and owner are `[renewed_repair_threshold_source_owner_token]`. Proof and memory limits are `[second_rewatch_proof_age_memory_limit_token]`. Learner action now is `[learner_safe_action_under_post_second_repeat_token]`. Current disposition is `[repeat_post_second_dewatch_threshold_disposition_token]`.

If public publication would expose protected, privacy-sensitive, accommodation, appeal, security, recipient-record, or route-controlled proof, publish only the owner, action-now truth, and a redacted or local-only threshold token.

## Default interpretation rules

1. **Repeat is not threshold by itself.** A second or third post-second-dewatch recurrence matters only when the same renewed-repair scope, current materiality, threshold source, and owner can be named.
2. **Threshold source must be current.** Old second-dewatch proof, expired request rows, stale screenshots, or prior owner claims cannot open a renewed-repair threshold without a current route-native, owner, recipient, protected-route, official-record, platform, archive, or redesign basis.
3. **Memory recall stays scoped.** Second-rewatch proof can support a threshold only as a minimized summary, local-only marker, or current proof pointer; it does not become a public proof vault merely because recurrence repeats.
4. **Protected proof stays local.** Accommodation, privacy, safety, appeal, security, and other protected routes may trigger or deny a threshold without moving proof into the public renewed-repair layer.
5. **Learner action stays prospective and safe.** When owners or routes disagree repeatedly after second dewatch, publish one current safe route, dual-route recognition, clock hold, protected local submission, owner-only repair, manual support, or no action before any refiling duty.
6. **The threshold must dispose of itself.** A shell should close as below-threshold ordinary handling, bounded third rewatch, renewed repair refresh, recipient correction, official-record confirmation, protected-route retention, redesign review, retired-route posture watch, no-active-route residue, split-surface shell, route-native control, or reminimized false alarm rather than remain a public repeated-repair warning forever.

## Worked examples

### Example A — repeated search reflection stays below threshold

A renewed rewatch second-dewatched after the source owner and recipient portal accepted the current repaired route. One later post-second-dewatch memory event was classified as ordinary search lag. In the next cycle, the same search family briefly reflects the old title again, while the source page, recipient route, official record, and learner-facing deadline remain correct.

Publish:

- `repeat_post_second_dewatch_recurrence_count_token = source search or archive reflection repeated`;
- `renewed_repair_rewatch_scope_token = same search result family`;
- `renewed_repair_threshold_source_owner_token = no threshold owner`;
- `second_rewatch_proof_age_memory_limit_token = public pointer only`;
- `learner_safe_action_under_post_second_repeat_token = use current repaired route`; and
- `repeat_post_second_dewatch_threshold_disposition_token = below threshold ordinary handling` or `reminimized false alarm`.

Do not open a third rewatch merely because downstream search reflection repeats without a current owner, recipient, clock, official-record, protected-route, or learner dependency effect.

### Example B — recipient correction repeats after renewed-repair memory recall

A renewed rewatch exited after the recipient-of-record corrected its portal and accepted one controlling route. A post-second-dewatch relapse later recalled the recipient correction marker and used dual-route recognition. In the following cycle, the same recipient portal again accepts the retired route while the current source and official record still publish the repaired clock.

Publish:

- `repeat_post_second_dewatch_recurrence_count_token = recipient correction repeated again`;
- `renewed_repair_rewatch_scope_token = same recipient portal`;
- `renewed_repair_threshold_source_owner_token = recipient of record threshold`;
- `second_rewatch_proof_age_memory_limit_token = current renewed-repair proof controls`;
- `learner_safe_action_under_post_second_repeat_token = submit once with dual-route recognition`; and
- `repeat_post_second_dewatch_threshold_disposition_token = third rewatch threshold opened` or `recipient correction reopened`.

Do not convert the repeated recipient failure into duplicate learner filing unless the current recipient-of-record route expressly requires it and protects the learner against duplicate-clock or wrong-route harm.

### Example C — protected route conflict repeats again

A public route was repaired twice, but a protected accommodation route stayed local. After second dewatch, one protected-route recurrence was handled through local-only memory recall. Later, the public page again contradicts the protected local route, and the proof needed to resolve it includes sensitive accommodation facts.

Publish:

- `repeat_post_second_dewatch_recurrence_count_token = protected route conflict repeated again`;
- `renewed_repair_rewatch_scope_token = same protected route`;
- `renewed_repair_threshold_source_owner_token = protected local owner threshold`;
- `second_rewatch_proof_age_memory_limit_token = protected proof local-only`;
- `learner_safe_action_under_post_second_repeat_token = protected local-only submission`; and
- `repeat_post_second_dewatch_threshold_disposition_token = protected route retained`.

Do not move protected proof into a public second-rewatch dossier or public threshold certificate merely because the protected conflict repeats.

### Example D — no-active-route residue churns again

A renewed rewatch second-dewatched into no-active-route residue after both the retired and repaired owner routes disappeared. A later recurrence found a current owner and requested renewed repair refresh. The owner route then disappears, reappears under a different office, and again becomes silent while learners have a live deadline.

Publish:

- `repeat_post_second_dewatch_recurrence_count_token = no-active-route owner churn repeated again`;
- `renewed_repair_rewatch_scope_token = same no-active-route residue`;
- `renewed_repair_threshold_source_owner_token = current owner discovered after residue` or `successor owner threshold`;
- `second_rewatch_proof_age_memory_limit_token = fresh owner proof required`;
- `learner_safe_action_under_post_second_repeat_token = clock held during owner repair` or `manual local support only`; and
- `repeat_post_second_dewatch_threshold_disposition_token = third rewatch threshold opened` or `no-active-route residue`.

Do not let repeated owner churn become learner wrong-route fault or a permanent public repeated-repair stigma label.

### Example E — official-record dependency recurs after redesign handoff

A renewed rewatch second-dewatched after a redesign owner accepted a corrected instruction and an official-record owner confirmed the learner-facing record field. A later post-second-dewatch event recalled the redesign proof marker. In the next cycle, the same redesign handoff misses its proof point again and the official-record dependency reappears.

Publish:

- `repeat_post_second_dewatch_recurrence_count_token = official-record dependency recurred` or `redesign handoff failed again after second dewatch`;
- `renewed_repair_rewatch_scope_token = same official-record dependency` or `same redesign handoff`;
- `renewed_repair_threshold_source_owner_token = official-record owner threshold` or `redesign owner threshold`;
- `second_rewatch_proof_age_memory_limit_token = official-record proof pending` or `redesign proof pending`;
- `learner_safe_action_under_post_second_repeat_token = official-record confirmation pending` or `submit once with dual-route recognition`; and
- `repeat_post_second_dewatch_threshold_disposition_token = official-record dependency reopened` or `redesign review reopened`.

Do not treat one official-record dependency as proof that every source, search, archive, recipient, protected-route, and learner-filing surface has failed.

## Non-goals

This layer does **not** create:

- an automatic third rewatch after every repeated post-second-dewatch event;
- a permanent repeated-repair instability label;
- a public second-rewatch or renewed-repair proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a repeat-by-anecdote threshold;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, all-record, or all-engine renewed-repair certificate;
- a universal threshold count that travels across every route family; or
- a duty to monitor every old repaired route after second dewatch.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about avoiding amnesia after repair. It is also about deciding when repeated recurrence after renewed repair proves a current stability problem without turning the learner, the route pair, or the proof object into permanent suspicion.

This layer matters because both extreme defaults are harmful. One bad default says a route that needed renewed repair twice is forever unstable, so every later recurrence justifies third rewatch, duplicate filing, public proof retention, or learner fault. Another says every recurrence after second dewatch is merely another memory event, so no owner ever has to admit that the same renewed-repair scope has crossed a new threshold. The portable answer is narrower: count only material repeats inside a named renewed-repair scope; require a current threshold source and owner; label proof age and memory limits; protect learner action; and move the threshold to bounded third rewatch, renewed repair refresh, recipient correction, official-record confirmation, protected-route retention, redesign review, retired-route posture watch, no-active-route residue, split surface, route-native control, or reminimized false alarm on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `ZB0-ZB4` has not already classified at least one post-second-dewatch relapse or renewed-repair memory event;
- the later event is unrelated to the renewed repaired route, owner, proof object, clock, recipient, protected route, official record, or affected surface;
- the repeat is only search, cache, crawler, archive, image, or downstream copy lag with no current learner-facing owner, proof, clock, recipient, protected-route, official-record, or live dependency effect;
- a route-native process already names repeat post-second-dewatch recurrence handling, threshold count, proof age, memory limit, learner-safe action, and disposition;
- the only signal is a stale screenshot, expired request row, old status page, anecdote, or unrelated mirror without current owner or learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules already control proof handling and should stay local-only; or
- a renewed-repair rewatch threshold has already opened and the question is now operation, repair refresh, or third dewatch exit rather than threshold crossing.

In those cases, publish `below threshold ordinary handling`, `ordinary lag only`, `unrelated new path`, `route-native rule controls`, `protected local-only route`, `no learner action now`, `fresh first-cycle conflict`, `third rewatch threshold already open`, `reminimized false alarm`, or `none inherited` rather than creating a repeat post-second-dewatch threshold layer.

## What this closes

This closes `FT-0156`.

The archive no longer stops at "post-second-dewatch relapse classified and renewed-repair memory recalled". It can now publish a minimal repeat post-second-dewatch relapse / renewed-repair rewatch-threshold layer: repeat count, renewed-repair scope, materiality, threshold source, current owner, proof age, memory limit, learner-safe action, threshold disposition, minimization, and reopen triggers when the same route, owner, proof object, clock, recipient, protected route, redesign handoff, retired-route posture, no-active-route residue, source/search/archive surface, or official-record dependency recurs again after memory recall or reminimization.

It also opens one narrower seam.

After repeated post-second-dewatch recurrence crosses a renewed-repair rewatch threshold, the archive may still need a tiny third rewatch operation / renewed-repair-refresh / third-dewatch-exit layer for cases where the threshold opens owner reconciliation, renewed repair refresh, recipient-record correction, protected-route handling, redesign proof, retired-route posture, no-active-route residue, official-record dependency, or split-surface handling — without turning threshold status into permanent serial surveillance, public repeated-repair stigma, automatic duplicate learner filing, or an indefinite second-rewatch proof vault.
