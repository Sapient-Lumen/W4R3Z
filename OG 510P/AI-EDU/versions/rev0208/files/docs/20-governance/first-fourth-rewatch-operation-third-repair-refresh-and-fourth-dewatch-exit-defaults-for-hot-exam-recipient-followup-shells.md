# First fourth rewatch operation, third-repair refresh, and fourth-dewatch-exit defaults for hot-exam recipient followup shells

The archive can now publish one still smaller operating layer for the hottest exam-like learner-request routes.

It can already say:

- how repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how first and renewed rewatch operations prove repair, exit, de-watch, split, redesign, retire, or become residue;
- how post-second-dewatch and post-third-dewatch recurrence recalls repaired-route, renewed-repair, or third-repair memory without reviving public proof vaults; and
- how repeated post-third-dewatch recurrence crosses a third-repair threshold only when the same route, owner, proof object, clock, recipient, protected route, official record, retired-route posture, no-active-route residue, source/search/archive surface, or split surface materially repeats.

That is still not enough.

An opened fourth-rewatch threshold is not yet proof that a permanent serial-watch regime is justified. It is also not a loose warning label that can sit on a learner, route, owner, or proof object without operating work. The threshold might open owner reconciliation. It might require a current third-repair refresh from a source, recipient, archive, search provider, official-record owner, protected-route owner, redesign owner, or successor owner. It might need only a bounded owner-confirmation check. It might split a public source surface from a protected local route. It might show that the route is genuinely retired, that no active route exists, that the official record now controls, or that only ordinary downstream lag remains. Or it might prove a clean enough cycle for fourth dewatch and proof minimization.

This document adds one thing only:

- a **tiny fourth rewatch operation / third-repair-refresh / fourth-dewatch-exit field set** for hot-exam recipient followup shells after `ZF0-ZF4` has already found that repeated post-third-dewatch recurrence crossed a third-repair rewatch threshold, but before the archive treats that threshold as permanent serial surveillance, public serial-repair stigma, automatic duplicate learner filing, route-pair punishment, or an indefinite third-rewatch proof vault.

That means the archive now asks a narrower question than before. It no longer asks only **when repeated post-third-dewatch recurrence crosses a third-repair threshold**. It now asks **how that opened fourth-rewatch threshold operates, what current third-repair-refresh proof can close it, what learners can safely do while owners repair or split the route, and when fourth dewatch, split, redesign, retirement, residue, route-native control, or minimization is truthful**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation, Google-Search-only, and source-side permanent-removal boundaries rather than a durable all-surface serial-rewatch operation. Google's Refresh Outdated Content route is exact page/image URL, changed/gone-content, request-status, additional-URL, and expiry based rather than a universal third-repair-refresh certificate. Google's personal-content routes keep Search removal, source-page removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb separates local source edits, emergency edits, primary-contact follow-up, campus-search and lookahead ownership, caching, and major-search-engine non-control. Princeton separates local deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support, Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, support tickets, project closeout, and accommodation routing. Internet Archive asks for URL, time-period, control-period, and review context before exclusion. Bing distinguishes temporary block, up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites, exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals support a tighter archive rule: **the next truthful portability gain here is one tiny fourth-operation layer for run-state, affected scope, current owner, cadence, current third-repair-refresh proof, learner-safe action, fourth-dewatch exit, minimization, and reopen triggers — but not one permanent serial-rewatch dashboard, one public serial-repair stigma label, one duplicate-filing duty, one indefinite third-rewatch proof vault, one all-surface serial-repair certificate, or route-pair punishment.** See `B274`.

## Small field set for fourth rewatch operation, third-repair refresh, and fourth dewatch exit

| Code | Meaning | Default archive action |
|---|---|---|
| `ZG0-NO-PERMANENT-FOURTH-REWATCH-DASHBOARD-PUBLIC-SERIAL-REPAIR-STIGMA-DUPLICATE-FILING-OR-INDEFINITE-THIRD-REWATCH-VAULT` | a third-repair threshold can open fourth-rewatch work, but it does not create permanent serial surveillance, public serial-repair stigma, duplicate learner filing, route-pair punishment, or a standing third-rewatch proof vault | require a fourth-rewatch run-state, affected scope, current owner, cadence or event trigger, current third-repair-refresh proof, learner-safe action, exit condition, minimization posture, and reopen trigger before widening beyond the threshold shell |
| `ZG1-PUBLISH-FOURTH-REWATCH-RUN-STATE-SCOPE-OWNER-AND-CADENCE-LIMIT` | an opened fourth rewatch must say what is actually operating and how bounded it is | publish whether the fourth operation is owner reconciliation, third-repair refresh, recipient-record correction, protected-route handling, redesign proof review, retired-route posture review, no-active-route residue review, official-record dependency review, split-surface handling, ordinary-lag review, or dewatch-eligible clean cycle, plus the affected route, proof, clock, recipient, protected route, source, search, archive, record, or split-surface scope |
| `ZG2-PUBLISH-CURRENT-THIRD-REPAIR-REFRESH-PROOF-PRECEDENCE-AND-OWNER-RECONCILIATION` | fourth rewatch needs current proof, not threshold status, revived third-rewatch proof, stale screenshots, or owner assertion alone | publish current source, search, archive, recipient, official-record, protected-route, redesign, clock, successor-owner, or reciprocal-owner proof; label stale, expired, screenshot-only, owner-claim-only, local-only, pending, redacted, unavailable, or route-native proof; and state which current owner or precedence rule controls while refresh completes |
| `ZG3-SEPARATE-LEARNER-SAFE-ACTION-FROM-OWNER-FOURTH-REWATCH-REPAIR-DUPLICATE-FILING-AND-PROOF-VAULTING` | repeated owner-side repair work should not become learner fault, duplicate filing, or public proof reburdening | publish no action, one safe route, dual-route recognition, clock hold, longer current window, protected local submission, manual support, route-native optional refile, route-native required refile with no penalty, formal appeal only, or owner-only repair before asking the learner to refile; do not publish protected proof or revive old third-rewatch screenshots without current route-native authority |
| `ZG4-PUBLISH-FOURTH-DEWATCH-EXIT-SPLIT-RESIDUE-MINIMIZATION-AND-REOPEN-TRIGGERS` | fourth rewatch must close, dewatch again, split, redesign, retire, become residue, or minimize on named facts | publish fourth dewatch, refreshed third-repaired route, recipient correction, protected route retained, route split retained, redesign proof accepted, retired-route residue, no-active-route residue, official-record correction, route-native control, fourth rewatch extended, closed without learner action, local-only memory, or material reopen triggers tied to current route, owner, proof, clock, recipient, protected-route, source, search, archive, split-surface, or official-record facts |

## Field values that now travel together

When this layer is used, the shell should publish only six concrete fields:

1. `fourth_rewatch_operation_state_token` — `none`, `threshold met but fourth rewatch not opened`, `fourth rewatch active`, `owner reconciliation reopened`, `third-repair refresh opened`, `recipient-record correction reopened`, `protected-route handling`, `redesign proof review`, `split-surface operation`, `retired-route posture review`, `no-active-route residue review`, `official-record dependency review`, `ordinary-lag review`, `third-repair-refresh proof under review`, `recurrence during fourth rewatch`, `fourth dewatch eligible`, `fourth dewatch completed`, `fourth rewatch closed without repair`, `none inherited`, or `not published`;
2. `fourth_rewatch_scope_owner_and_cadence_token` — `same third repaired route pair`, `same current owner`, `same recipient portal`, `same protected route`, `same proof object`, `same clock or deadline`, `same source page`, `same search result family`, `same archive time slice or mirror family`, `same official-record dependency`, `same redesign handoff`, `same retired route`, `same no-active-route residue`, `split surface only`, `event-triggered only`, `one clean-cycle check`, `owner-confirmation check`, `no current owner`, `none inherited`, or `not published`;
3. `third_repair_refresh_proof_token` — `current source proof`, `current recipient-of-record proof`, `current official-record proof`, `protected owner proof current`, `search-provider request state current`, `archive or platform review proof`, `route-native clock proof current`, `redesign proof current`, `successor owner proof current`, `reciprocal owners confirmed`, `source corrected and persisted`, `third-rewatch proof still stale`, `screenshot-only proof`, `owner assertion only`, `proof pending`, `proof unavailable residue`, `local-only proof`, `proof redacted`, `none inherited`, or `not published`;
4. `learner_safe_action_during_fourth_rewatch_token` — `no learner action now`, `use current safe route`, `use more protective route until resolved`, `submit once with dual-route recognition`, `do not duplicate filing`, `clock held`, `longer current window controls`, `protected local-only submission`, `manual local support only`, `wait for owner confirmation`, `recipient correction pending no penalty`, `route-native optional refile`, `route-native required refile no penalty`, `formal appeal only`, `owner-only repair`, `none inherited`, or `not published`;
5. `fourth_dewatch_exit_disposition_token` — `fourth dewatch completed`, `refreshed third-repaired route controls`, `recipient record corrected`, `official record corrected`, `protected route retained`, `split surface retained`, `redesign proof accepted`, `retired-route residue`, `no-active-route residue`, `route-native rule controls`, `ordinary lag only`, `fourth rewatch extended once`, `closed without learner action`, `local-only memory`, `threshold met but no operation`, `none inherited`, or `not published`; and
6. `post_fourth_dewatch_memory_and_reopen_token` — `minimized fourth-rewatch memory`, `third-repair-refresh proof minimized`, `protected proof sealed`, `recipient correction marker retained`, `official-record correction marker retained`, `redesign proof marker retained`, `retired-route marker retained`, `no-active-route residue marker retained`, `source-search-archive split marker retained`, `reopen on owner change`, `reopen on proof mismatch`, `reopen on recipient recurrence`, `reopen on protected-route recurrence`, `reopen on official-record recurrence`, `route-native reopen only`, `no reopen without material new facts`, `none inherited`, or `not published`.

These fields should travel together because each one limits the others. A fourth-rewatch state without proof tells the learner nothing. Proof without safe action can become a duplicate-filing trap. A current owner without exit disposition can become permanent surveillance. And a dewatch exit without minimization can become a public serial-repair vault.

## Examples

### Example A — owner reconciliation opens after the third-repair threshold

A route was repaired, rewatched, repaired again, second-dewatched, rewatched a third time, third-dewatched, and later crossed a third-repair threshold because the same owner and proof object failed again. The threshold opens a fourth rewatch. The public source owner and recipient-of-record owner disagree about which route now controls, but no learner deadline has yet been harmed.

Publish:

- `fourth_rewatch_operation_state_token = owner reconciliation reopened` or `fourth rewatch active`;
- `fourth_rewatch_scope_owner_and_cadence_token = same third repaired route pair`;
- `third_repair_refresh_proof_token = proof pending` or `reciprocal owners confirmed` once reconciled;
- `learner_safe_action_during_fourth_rewatch_token = wait for owner confirmation` or `use more protective route until resolved`;
- `fourth_dewatch_exit_disposition_token = refreshed third-repaired route controls` or `fourth rewatch extended once`; and
- `post_fourth_dewatch_memory_and_reopen_token = minimized fourth-rewatch memory` or `reopen on proof mismatch`.

Do not label the learner, route pair, or owner as permanently suspect merely because a fourth operation opened.

### Example B — recipient record correction reopens during fourth rewatch

A recipient portal again accepts the retired route while the source and official record now publish the refreshed third-repaired route. The third-repair threshold was already opened, but the learner has not filed twice and should not have to start over.

Publish:

- `fourth_rewatch_operation_state_token = recipient-record correction reopened`;
- `fourth_rewatch_scope_owner_and_cadence_token = same recipient portal`;
- `third_repair_refresh_proof_token = current recipient-of-record proof` or `current official-record proof`;
- `learner_safe_action_during_fourth_rewatch_token = submit once with dual-route recognition` or `do not duplicate filing`;
- `fourth_dewatch_exit_disposition_token = recipient record corrected`; and
- `post_fourth_dewatch_memory_and_reopen_token = recipient correction marker retained`.

Do not convert recipient-side repair into duplicate learner filing unless a current recipient-of-record rule expressly requires it and preserves no-penalty treatment.

### Example C — protected-route handling stays local during fourth rewatch

A public route and a protected accommodation route diverge again after third dewatch. The facts needed to resolve the conflict include sensitive support information, and the protected local owner can confirm that the learner should use the protected route while the public route is repaired.

Publish:

- `fourth_rewatch_operation_state_token = protected-route handling`;
- `fourth_rewatch_scope_owner_and_cadence_token = same protected route`;
- `third_repair_refresh_proof_token = protected owner proof current` or `local-only proof`;
- `learner_safe_action_during_fourth_rewatch_token = protected local-only submission`;
- `fourth_dewatch_exit_disposition_token = protected route retained`; and
- `post_fourth_dewatch_memory_and_reopen_token = protected proof sealed`.

Do not publish accommodation, privacy, safety, appeal, or protected support proof as a public serial-repair vault.

### Example D — no-active-route residue appears during the operation

A fourth-rewatch threshold opens because no-active-route residue repeatedly gained and lost a current owner after third repair. During the operation, the successor owner disappears from the public page and the recipient portal remains silent while learners still have a live deadline.

Publish:

- `fourth_rewatch_operation_state_token = no-active-route residue review`;
- `fourth_rewatch_scope_owner_and_cadence_token = same no-active-route residue` or `no current owner`;
- `third_repair_refresh_proof_token = proof unavailable residue`;
- `learner_safe_action_during_fourth_rewatch_token = manual local support only` or `use longer current window until resolved`;
- `fourth_dewatch_exit_disposition_token = no-active-route residue`; and
- `post_fourth_dewatch_memory_and_reopen_token = reopen on owner change`.

Do not let missing owner proof become adverse wrong-route fault against a learner who followed the last safe published route.

### Example E — redesign proof and official-record dependency split

A redesign owner accepts a refreshed instruction, but the official-record owner has not yet reflected the changed learner-facing field. The fourth-rewatch threshold opened on repeated redesign handoff failure, and now the public page, recipient portal, and official record disagree.

Publish:

- `fourth_rewatch_operation_state_token = redesign proof review` or `official-record dependency review`;
- `fourth_rewatch_scope_owner_and_cadence_token = same redesign handoff` or `same official-record dependency`;
- `third_repair_refresh_proof_token = redesign proof current` or `current official-record proof` once confirmed;
- `learner_safe_action_during_fourth_rewatch_token = submit once with dual-route recognition` or `wait for owner confirmation`;
- `fourth_dewatch_exit_disposition_token = redesign proof accepted` or `official record corrected`; and
- `post_fourth_dewatch_memory_and_reopen_token = redesign proof marker retained` or `official-record correction marker retained`.

Do not let one official-record dependency imply that every public, protected, recipient, source, search, archive, and learner-filing surface has failed.

## Non-goals

This layer does **not** create:

- permanent serial rewatch after every opened threshold;
- a public serial-repair instability label;
- a public third-rewatch or fourth-rewatch proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, all-record, or all-engine third-repair-refresh certificate;
- a universal fourth-rewatch cadence that travels across every route family;
- a duty to monitor every old repaired route after fourth dewatch; or
- a rule that every route reaching fourth rewatch must be redesigned, retired, or permanently watched.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about remembering repeated repair. It is also about preventing repeated repair from becoming a permanent identity for a learner, route, owner, proof object, or protected route.

This layer matters because both extreme defaults are harmful. One bad default says a route that has crossed a fourth-rewatch threshold must stay under public serial surveillance forever, so every later signal becomes proof of learner fault, duplicate filing, or permanent route instability. Another says that because fourth rewatch sounds exceptional, the shell can carry the label without current proof, owner reconciliation, learner-safe action, exit, or minimization. The portable answer is narrower: publish the operating run-state, affected scope, current proof, safe action, exit disposition, and memory posture; then close, split, redesign, retire, localize, route-native-control, residue, or dewatch on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `ZF0-ZF4` has not opened a third-repair rewatch threshold;
- the later event is unrelated to the third repaired route, owner, proof object, clock, recipient, protected route, official record, or affected surface;
- the issue is only search, cache, crawler, archive, image, or downstream copy lag with no current owner, recipient, protected-route, official-record, proof, clock, or learner dependency effect;
- a route-native process already names fourth-rewatch operation, proof requirements, learner action, exit, and minimization;
- the only signal is a stale screenshot, expired request row, old status page, anecdote, or unrelated mirror without current owner or learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules already control proof handling and should stay local-only; or
- fourth rewatch has already dewatched or closed and the question is now later relapse or fourth-repair memory rather than operation.

In those cases, publish `threshold met but fourth rewatch not opened`, `ordinary lag only`, `route-native rule controls`, `protected local-only route`, `no learner action now`, `fresh unrelated path`, `fourth dewatch completed`, `closed as route-native control`, `no-active-route residue`, or `none inherited` rather than creating a fourth-rewatch operation layer.

## What this closes

This closes `FT-0160`.

The archive no longer stops at "repeat post-third-dewatch recurrence crossed a third-repair threshold". It can now publish a minimal fourth rewatch operation / third-repair-refresh / fourth-dewatch-exit layer: run-state, scope, owner, cadence, current refresh proof, learner-safe action, exit disposition, minimization, and reopen triggers when the threshold opens owner reconciliation, recipient correction, protected-route handling, redesign proof review, retired-route posture, no-active-route residue, official-record dependency, split-surface handling, route-native control, or a clean fourth-dewatch cycle.

It also opens one narrower seam.

After a fourth rewatch operation closes or fourth-dewatches, the archive may still need a tiny post-fourth-dewatch relapse / fourth-repair memory layer for cases where a later route, owner, proof, clock, recipient, protected route, source, search, archive, official-record dependency, redesign handoff, retired-route posture, or no-active-route residue reappears — without making every later recurrence automatic fifth rewatch, permanent serial-repair stigma, duplicate learner filing, a public fourth-rewatch proof vault, or total fresh-start amnesia.
