# First third rewatch operation, renewed-repair refresh, and third-dewatch-exit defaults for hot-exam recipient followup shells

The archive can now publish one still smaller operating layer for the hottest exam-like learner-request routes.

It can already say:

- how repeated post-deconflict relapse crosses a bounded rewatch threshold;
- how a first rewatch operates, proves repair, exits, de-watches, splits, redesigns, retires, or becomes residue;
- how later post-dewatch recurrence recalls repaired-route memory and crosses a repaired-route threshold only on material repeated facts;
- how renewed rewatch operates after that threshold, proves repair refresh, and exits through second dewatch; and
- how post-second-dewatch recurrence recalls renewed-repair memory and crosses a renewed-repair rewatch threshold only when the same route, owner, proof, clock, recipient, protected route, official record, or affected surface materially repeats.

That is still not enough.

An opened third-rewatch threshold is not yet proof that a permanent serial-watch regime is justified. It is also not a loose warning label that can sit on a learner, route, or proof object without operating work. The threshold might open owner reconciliation. It might require another repair refresh from a current source, recipient, archive, search, official-record, protected-route, redesign, or successor owner. It might only need a bounded owner-confirmation check. It might split a public surface from a protected local route. It might show that the route is genuinely retired, that no active route exists, or that only ordinary downstream lag remains. Or it might prove a clean enough cycle for third dewatch and proof minimization.

This document adds one thing only:

- a **tiny third rewatch operation / renewed-repair-refresh / third-dewatch-exit field set** for hot-exam recipient followup shells after `ZC0-ZC4` has already found that repeated post-second-dewatch recurrence crossed a renewed-repair rewatch threshold, but before the archive treats that threshold as permanent serial surveillance, public repeated-repair stigma, automatic duplicate learner filing, or an indefinite second-rewatch proof vault.

That means the archive now asks a narrower question than before. It no longer asks only **when repeated post-second-dewatch recurrence crosses a renewed-repair threshold**. It now asks **how that opened third-rewatch threshold operates, what current repair-refresh proof can close it, what learners can safely do while owners repair or split the route, and when third dewatch, split, redesign, retirement, residue, route-native control, or minimization is truthful**.

Current official signals support a deliberately narrow answer. Google Search Console's Removals tool exposes property-owner, exact-URL, current/expired-history, temporary-removal, cancellation, Google-Search-only, and source-side permanent-removal boundaries rather than a durable all-surface serial-rewatch operation. Google's Refresh Outdated Content route is exact page/image URL, changed/gone-content, request-status, additional-URL, and expiry based rather than a universal repair-refresh certificate. Google's personal-content routes keep Search removal, source-page removal, screenshot proof, notifications, new-result handling, and sensitive proof separate. WiscWeb separates local source edits, emergency edits, primary-contact follow-up, campus-search and lookahead ownership, caching, and major-search-engine non-control. Princeton separates local deletion, document/media cleanup, access control, cache behavior, Google/Bing/custom-search handling, and Wayback persistence. Rowan separates CMS ownership, Web Services support, Siteimprove/accessibility monitoring, contributor training, content-audit/redesign work, support tickets, project closeout, and accommodation routing. Internet Archive asks for URL, time-period, control-period, and review context before exclusion. Bing distinguishes temporary block, up-to-90-day expiry, cached/outdated-content handling, extension or permanent-removal prerequisites, exact URL submission, and source-side methods such as 404/410 or noindex. Together those signals support a tighter archive rule: **the next truthful portability gain here is one tiny third-operation layer for run-state, affected scope, current owner, cadence, current repair-refresh proof, learner-safe action, third-dewatch exit, minimization, and reopen triggers — but not one permanent serial-rewatch dashboard, one public repeated-repair stigma label, one duplicate-filing duty, one indefinite second-rewatch proof vault, or one all-surface serial-repair certificate.** See `B271`.

## Practical third-rewatch operation defaults

| Situation | Minimal publication | Why |
|---|---|---|
| renewed-repair threshold opens owner reconciliation for the same route pair | `third rewatch active`; `same renewed repaired route pair`; `reciprocal owners confirmed` or `repair refresh unresolved`; one learner-safe route | shows that the threshold is operating as bounded owner work, not as serial learner suspicion |
| recipient portal accepts a retired route again after second dewatch | `recipient-record correction reopened`; `same recipient portal`; `current recipient-of-record proof`; `submit once with dual-route recognition` | keeps recipient correction current without forcing duplicate filing or public proof revival |
| public route and protected local route diverge again | `protected-route handling`; `same protected route`; `protected owner proof current` or `local-only proof`; `protected local-only submission` | protects sensitive proof and keeps public-route repair separate from accommodation or accessibility handling |
| redesigned route misses its proof point during third rewatch | `redesign proof review`; `same redesign handoff`; `redesign proof current` or `proof mismatched`; `wait for owner confirmation` | treats redesign as a current proof question rather than a permanent repair-failure label |
| route owner disappears after a threshold opened | `no-active-route residue review`; `same no-active-route residue`; `proof unavailable residue`; `manual local support only` | prevents a missing owner from becoming learner wrong-route fault |
| only search, cache, crawler, or archive lag repeats without current dependency | `ordinary-lag review`; `split surface only`; `search-provider request state current` or `archive or platform review proof`; `none current` | avoids reopening all route surfaces when only downstream reflection remains |
| third rewatch completes a clean owner-confirmed cycle | `third dewatch completed`; `one clean-cycle check`; `current source proof` and any recipient or record proof; `minimized third-rewatch memory` | closes the operation and minimizes proof rather than retaining an indefinite second-rewatch vault |

## Minimal publication sentence

A learner-facing or owner-facing shell can usually say the whole thing in one sentence:

> This threshold is `[third_rewatch_operation_state_token]` for `[third_rewatch_scope_owner_and_cadence_token]`. Current refresh proof is `[renewed_repair_refresh_proof_token]`. Learner action now is `[learner_safe_action_during_third_rewatch_token]`. Exit disposition is `[third_dewatch_exit_disposition_token]`. Memory and reopen posture is `[post_third_dewatch_memory_and_reopen_token]`.

If public publication would expose protected, privacy-sensitive, accommodation, appeal, security, recipient-record, or route-controlled proof, publish only the current owner, action-now truth, and a redacted or local-only proof token.

## Default interpretation rules

1. **Third rewatch is operating work, not a status stigma.** A shell should not carry `third rewatch active` unless it can name the affected scope, current owner or no-owner residue, cadence or event trigger, proof basis, and learner-safe action.
2. **Current proof controls over old threshold confidence.** Second-rewatch proof, old screenshots, expired provider rows, or prior owner claims may explain why the threshold opened, but they cannot close third rewatch without current source, recipient, record, protected-route, redesign, platform, archive, or route-native proof.
3. **Learner action stays bounded.** The default learner action is no action, one safe route, dual-route recognition, clock hold, local protected route, or manual support until current route-native authority requires a refile and protects against duplicate-clock or wrong-route harm.
4. **Protected proof stays local.** Accommodation, privacy, safety, appeal, security, and other protected-route proof can support third rewatch, block public proof publication, or keep a route local-only without becoming a public repeated-repair certificate.
5. **Exit must name a posture.** Third rewatch should exit into third dewatch, refreshed repaired route, recipient correction, official-record correction, protected route retained, redesign accepted, split surface retained, retired-route residue, no-active-route residue, route-native control, ordinary lag, or closed-without-learner-action; it should not linger as a public open-ended serial watch.
6. **Memory minimization follows exit.** After third dewatch or closure, proof should reduce to minimized public memory, aggregate memory, local-only markers, sealed protected proof, official-record or recipient correction markers, or no reopen trigger unless a material current route, owner, proof, clock, recipient, protected-route, source, search, archive, split-surface, or record fact returns.

## Examples

### Example A — owner reconciliation opens after the renewed-repair threshold

A route was repaired, rewatched, repaired again, second-dewatched, and later crossed a renewed-repair threshold because the same owner and proof object failed again. The threshold opens a third rewatch. The public source owner and recipient-of-record owner disagree about which route now controls, but no learner deadline has yet been harmed.

Publish:

- `third_rewatch_operation_state_token = owner reconciliation reopened` or `third rewatch active`;
- `third_rewatch_scope_owner_and_cadence_token = same renewed repaired route pair`;
- `renewed_repair_refresh_proof_token = repair refresh unresolved` or `reciprocal owners confirmed` once reconciled;
- `learner_safe_action_during_third_rewatch_token = wait for owner confirmation` or `use more protective route until resolved`;
- `third_dewatch_exit_disposition_token = refreshed repaired route controls` or `third rewatch extended once`; and
- `post_third_dewatch_memory_and_reopen_token = minimized third-rewatch memory` or `reopen on proof mismatch`.

Do not label the learner or the route pair as permanently suspect merely because a third operation opened.

### Example B — recipient record correction reopens during third rewatch

A recipient portal again accepts the retired route while the source and official record now publish the refreshed repaired route. The renewed-repair threshold was already opened, but the learner has not filed twice and should not have to start over.

Publish:

- `third_rewatch_operation_state_token = recipient-record correction reopened`;
- `third_rewatch_scope_owner_and_cadence_token = same recipient portal`;
- `renewed_repair_refresh_proof_token = current recipient-of-record proof` or `current official-record proof`;
- `learner_safe_action_during_third_rewatch_token = submit once with dual-route recognition` or `do not duplicate filing`;
- `third_dewatch_exit_disposition_token = recipient record corrected`; and
- `post_third_dewatch_memory_and_reopen_token = recipient correction marker retained`.

Do not convert recipient-side repair into duplicate learner filing unless a current recipient-of-record rule expressly requires it and preserves no-penalty treatment.

### Example C — protected-route handling stays local during third rewatch

A public route and a protected accommodation route diverge again after second dewatch. The facts needed to resolve the conflict include sensitive support information, and the protected local owner can confirm that the learner should use the protected route while the public route is repaired.

Publish:

- `third_rewatch_operation_state_token = protected-route handling`;
- `third_rewatch_scope_owner_and_cadence_token = same protected route`;
- `renewed_repair_refresh_proof_token = protected owner proof current` or `local-only proof`;
- `learner_safe_action_during_third_rewatch_token = protected local-only submission`;
- `third_dewatch_exit_disposition_token = protected route retained`; and
- `post_third_dewatch_memory_and_reopen_token = protected proof sealed`.

Do not publish accommodation, privacy, safety, appeal, or protected support proof as a public serial-repair vault.

### Example D — no-active-route residue appears during the operation

A third-rewatch threshold opens because no-active-route residue repeatedly gained and lost a current owner. During the operation, the successor owner disappears from the public page and the recipient portal remains silent while learners still have a live deadline.

Publish:

- `third_rewatch_operation_state_token = no-active-route residue review`;
- `third_rewatch_scope_owner_and_cadence_token = same no-active-route residue` or `no current owner`;
- `renewed_repair_refresh_proof_token = proof unavailable residue`;
- `learner_safe_action_during_third_rewatch_token = manual local support only` or `use longer current window until resolved`;
- `third_dewatch_exit_disposition_token = no-active-route residue`; and
- `post_third_dewatch_memory_and_reopen_token = reopen on owner change`.

Do not let missing owner proof become adverse wrong-route fault against a learner who followed the last safe published route.

### Example E — redesign proof and official-record dependency split

A redesign owner accepts a repaired instruction, but the official-record owner has not yet reflected the changed learner-facing field. The third-rewatch threshold opened on repeated redesign handoff failure, and now the public page, recipient portal, and official record disagree.

Publish:

- `third_rewatch_operation_state_token = redesign proof review` or `official-record dependency review`;
- `third_rewatch_scope_owner_and_cadence_token = same redesign handoff` or `same official-record dependency`;
- `renewed_repair_refresh_proof_token = redesign proof current` or `current official-record proof` once confirmed;
- `learner_safe_action_during_third_rewatch_token = submit once with dual-route recognition` or `wait for owner confirmation`;
- `third_dewatch_exit_disposition_token = redesign proof accepted` or `official record corrected`; and
- `post_third_dewatch_memory_and_reopen_token = redesign proof marker retained` or `official-record correction marker retained`.

Do not let one official-record dependency imply that every public, protected, recipient, source, search, archive, and learner-filing surface has failed.

## Non-goals

This layer does **not** create:

- permanent serial rewatch after every opened threshold;
- a public repeated-repair instability label;
- a public second-rewatch or third-rewatch proof dossier;
- a duplicate-filing duty for learners;
- an adverse wrong-route fault rule;
- a protected-proof publication duty;
- an all-source, all-search, all-archive, all-recipient, all-record, or all-engine renewed-repair certificate;
- a universal third-rewatch cadence that travels across every route family;
- a duty to monitor every old repaired route after third dewatch; or
- a rule that every route reaching third rewatch must be redesigned, retired, or permanently watched.

## Why this matters for the larger archive

The archive's education-with-AI program is not only about remembering repeated repair. It is also about preventing repeated repair from becoming a permanent identity for a learner, route, owner, proof object, or protected route.

This layer matters because both extreme defaults are harmful. One bad default says a route that has crossed a third-rewatch threshold must stay under public serial surveillance forever, so every later signal becomes proof of learner fault, duplicate filing, or permanent route instability. Another says that because third rewatch sounds exceptional, the shell can carry the label without current proof, owner reconciliation, learner-safe action, exit, or minimization. The portable answer is narrower: publish the operating run-state, affected scope, current proof, safe action, exit disposition, and memory posture; then close, split, redesign, retire, localize, route-native-control, residue, or dewatch on named facts.

## Boundary conditions

This layer should not be used when only one of the following is true:

- `ZC0-ZC4` has not opened a renewed-repair rewatch threshold;
- the later event is unrelated to the renewed repaired route, owner, proof object, clock, recipient, protected route, official record, or affected surface;
- the issue is only search, cache, crawler, archive, image, or downstream copy lag with no current owner, recipient, protected-route, official-record, proof, clock, or learner dependency effect;
- a route-native process already names third-rewatch operation, proof requirements, learner action, exit, and minimization;
- the only signal is a stale screenshot, expired request row, old status page, anecdote, or unrelated mirror without current owner or learner dependency;
- protected accommodation, privacy, safety, legal, records, appeal, or recipient-of-record rules already control proof handling and should stay local-only; or
- third rewatch has already dewatched or closed and the question is now later relapse or third-repair memory rather than operation.

In those cases, publish `threshold met but third rewatch not opened`, `ordinary lag only`, `route-native rule controls`, `protected local-only route`, `no learner action now`, `fresh unrelated path`, `third dewatch completed`, `closed as route-native control`, `no-active-route residue`, or `none inherited` rather than creating a third-rewatch operation layer.

## What this closes

This closes `FT-0157`.

The archive no longer stops at "repeat post-second-dewatch recurrence crossed a renewed-repair threshold". It can now publish a minimal third rewatch operation / renewed-repair-refresh / third-dewatch-exit layer: run-state, scope, owner, cadence, current refresh proof, learner-safe action, exit disposition, minimization, and reopen triggers when the threshold opens owner reconciliation, recipient correction, protected-route handling, redesign proof review, retired-route posture, no-active-route residue, official-record dependency, split-surface handling, route-native control, or a clean third-dewatch cycle.

It also opens one narrower seam.

After a third rewatch operation closes or third-dewatches, the archive may still need a tiny post-third-dewatch relapse / third-repair memory layer for cases where a later route, owner, proof, clock, recipient, protected route, source, search, archive, official-record dependency, redesign handoff, retired-route posture, or no-active-route residue reappears — without making every later recurrence automatic fourth rewatch, permanent serial-repair stigma, duplicate learner filing, a public third-rewatch proof vault, or total fresh-start amnesia.
