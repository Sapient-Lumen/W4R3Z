# Portable probation-expiry and ordinary-status restoration defaults for re-promoted packet maintenance envelopes

This document closes the archive's next packet-governance gap: **once a promoted packet maintenance envelope has cooled locally, regained portable status under one shared monitored re-entry package, and then survived its first watched post-repromotion cycle cleanly, can that clean watched cycle itself carry one shared probation-expiry / ordinary-status restoration package, or should the meaning of "ordinary again" still remain local even after portable re-entry has already survived one monitored reuse?**

The archive's answer is narrower again:

> only maintenance classes whose **end-of-probation truth** remains stable across the reuse scope should carry one shared probation-expiry / ordinary-status restoration package. In the starter canon, only `PME-LABEL` usually carries one shared restoration package; record-owner calendar upkeep, route calendars, and safety calendars should keep restoration-to-ordinary trust local.

The point is to avoid three opposite errors at once:

- **premature normalization** — a service treats any clean watched re-entry cycle as automatic proof that ordinary portable trust has returned, even where the real meaning of "ordinary again" still depends on owner-specific sign-off, cadence, or protective review;
- **shadow-restoration drift** — a service publishes one watched-cycle package but then restores ordinary status only through unpublished owner-local discretion, hidden residue checks, or opaque approvals;
- **permanent probation** — a maintenance class whose clean watched cycle really does mean the same thing across the reuse scope never earns one portable restoration rule and therefore remains artificially probationary forever.

Current public signals support this thinner move. OECD's 2026 outlook keeps pressing educational AI toward pedagogically purposeful design rather than convenience-first task completion; OpenAI's current learning-outcomes work emphasizes longitudinal measurement instead of one-off performance snapshots; Study Mode and related learning surfaces continue to frame the product direction as guided understanding rather than quick-answer posture; and ICO guidance keeps privacy by default, profiling-off-by-default for children absent compelling reason, and challengeable design in view. See `B11`, `B23`, `B143`, `B146`, `B149`, `B150`, `B151`.

## Three restoration portability tiers

The archive now distinguishes three probation-expiry / restoration portability tiers.

| Tier | Meaning | What travels | What stays local |
|---|---|---|---|
| `ORS-BOTH` | the re-promoted-and-watched envelope carries one shared probation-expiry floor and one shared ordinary-status restoration rule | the minimum clean watched-cycle condition that ends probation and the minimum fact that the next eligible cycle returns to ordinary promoted status | any stricter local sign-off, any extra local checkpoint, and any stronger local publication or challenge route |
| `ORS-EXPIRY` | the envelope carries only one shared probation-expiry floor | the minimum fact that a clean watched cycle can end special probation | the actual rule for when ordinary status is restored and what lingering local residue still matters |
| `ORS-LOCAL` | the envelope carries no shared restoration package | only the earlier basket / numeric / checkpoint / republication / cumulative-cycle / re-promotion / watch tiers | both probation-expiry and ordinary-status restoration |

The archive is deliberately asymmetric again:

> restoration portability is harder to earn than watched-cycle portability. A class can carry one shared first-cycle probation package while the truth about becoming **ordinary again** still remains owner-local.

## Five tests for whether end-of-probation truth really travels

A re-promoted-and-watched portable maintenance envelope may harden above `ORS-LOCAL` only when all five tests hold.

1. **same-clean-watch-meaning test** — a clean watched cycle really means the same thing across the reuse scope rather than one owner treating it as a bounded shell pass while another treats it only as provisional evidence pending local approval.
2. **same-probation-expiry boundary test** — the exact point at which probation ends can be described in one reusable way, rather than depending on local committee timing, local callback completion, or owner-specific caution residue.
3. **same-ordinary-status meaning test** — saying that the next eligible cycle is now ordinary again means the same thing across the reuse scope: no special watched-cycle warning remains, and the path falls back to the ordinary promoted package rather than to unpublished shadow probation.
4. **no-shadow-restoration test** — the shared restoration package does not conceal local shadow review, unpublished holdbacks, or stronger owner-specific evidence burdens that still materially determine whether ordinary trust has actually returned.
5. **same-post-restoration inheritance test** — once ordinary status is restored, the maintenance path really inherits the same baseline packet-governance canon across the proposed scope rather than diverging immediately through owner-specific recent-repair sensitivity or hidden accelerated re-cooling rules.

Failing the second, third, fourth, or fifth test keeps the envelope at `ORS-LOCAL`. Failing only the third may eventually point to `ORS-EXPIRY`, but the starter canon does not yet use that middle tier.

## The starter probation-expiry / ordinary-status restoration package

The archive now names one shared probation-expiry floor and one shared ordinary-status restoration rule.

| Code | Meaning |
|---|---|
| `PE-CLEAN-WATCH` | a **clean watched re-entry cycle** closes probation only if the published watched-cycle package completed without unresolved breach residue, fresh reset cluster formation, basket / field-logic expansion, or challenge-route weakening |
| `OR-RETURN-ORDINARY` | once `PE-CLEAN-WATCH` is satisfied, the next eligible cycle returns to the envelope's ordinary promoted status rather than carrying re-entry probation again, while still inheriting all ordinary checkpoint, recurrence, cumulative-cycle, and future departure rules |

The archive does **not** yet create a richer restoration ladder. The starter canon is deliberately small:

- no re-promoted-and-watched portable maintenance envelope currently restores ordinary status before the watched cycle closes cleanly;
- no re-promoted-and-watched portable maintenance envelope currently restores ordinary status by elapsed time alone;
- where the archive refuses a shared restoration package, services must still publish a **local** end-of-probation / restoration rule, or say plainly that renewed portable status remains under owner-local caution even after a clean watched cycle.

## The archive's starter restoration answers

### `PME-LABEL` usually hardens as `ORS-BOTH` with `PE-CLEAN-WATCH + OR-RETURN-ORDINARY`

`PME-LABEL` may usually carry **both** one shared probation-expiry floor and one shared ordinary-status restoration rule across its promoted branch scope.

Why the archive allows this:

- label/plain-language watched re-entry usually means the same thing across the branch scope: a wording shell that cooled locally, re-entered portability, and then survived one fully published watched cycle without fresh shell drift, unresolved breach, reset-cluster formation, field-logic expansion, or rights-shell weakening;
- the point at which probation ends is usually describable in one reusable way too: once that watched cycle closes cleanly under the already-published package, there is no extra hidden owner step that changes whether label maintenance is still special or ordinary;
- the meaning of "ordinary again" is relatively thin and therefore portable here: the path does **not** become exempt from ordinary cycle ceilings, checkpoint duties, or future repair obligations, but it does stop carrying the special watched-cycle flag.

The starter default is therefore:

> when `PME-LABEL` has already earned `PMT-BRANCH`, `PQT-BOTH`, `PCP-BOTH`, `RRP-BOTH`, `CFP-BOTH`, `RXP-BOTH`, and `RPW-BOTH`, and then completes its watched re-entry cycle cleanly under `PW-1REPROMOTED + RC-IMMEDIATE-LOCAL`, it may usually also inherit `ORS-BOTH` with `PE-CLEAN-WATCH + OR-RETURN-ORDINARY`.

What this means in practice:

1. after a re-promoted label envelope survives the watched cycle cleanly, the special re-entry probation ends at cycle close;
2. the next eligible cycle does **not** need to republish the watched-cycle flag or carry a hidden restoration review;
3. ordinary promoted status returns, but only the ordinary promoted status already defined elsewhere — basket, quantitative, checkpoint, recurrence, cumulative-cycle, and future departure rules still govern the path;
4. any later breach, fresh reset cluster, or future fatigue event is handled by the ordinary packet-governance canon rather than by pretending the path is forever stuck in re-entry probation.

### Record-owner calendar upkeep stays `ORS-LOCAL`

Record-owner calendar upkeep should currently keep probation-expiry and ordinary-status restoration local.

Why the archive does **not** promote a shared restoration package here:

- even where a record-owner calendar envelope can honestly carry a shared `QC-2` cap and a shared breach family, the meaning of a clean watched re-entry cycle still varies materially with local record-review practice, notice timing, callback completion, and whether one owner treats the next cycle as truly ordinary or still specially supervised;
- one owner may consider ordinary status restored once the watched cycle closes, while another still requires local review around calendar adjacency, claimant expectations, or inherited timeline residue;
- a shared restoration package would therefore overstate how comparable the end-of-probation boundary really is.

The archive therefore keeps calendar restoration-to-ordinary trust local even when earlier numeric, breach, and watched-cycle layers already publish some reusable structure.

### Route and safety calendars stay `ORS-LOCAL`

Route calendars and safety-owner calendars should also stay `ORS-LOCAL`.

The reasons are even stronger than for record-owner calendars:

- the difference between "watched re-entry survived" and "ordinary trust is fully back" is still tightly entangled with owner-specific protective review, callback guarantees, safeguarding exposure, and local challenge duties;
- a shared restoration package here would risk making local protective caution disappear behind the phrase "ordinary again";
- the truth about when recent repair history stops mattering is not yet portable enough to harden.

## What this changes in the packet-governance line

The archive now makes three things explicit that it had only implied before.

1. **A clean watched cycle can sometimes end specialness.** For label/plain-language maintenance, the archive now thinks a clean watched re-entry cycle is stable enough to carry one shared end-of-probation rule.
2. **Ordinary restoration is a new claim, not a free rider on watched-cycle portability.** A class that earns `RPW-BOTH` does not automatically earn `ORS-BOTH`.
3. **Ordinary again still means bounded ordinary.** Restoring ordinary status does not erase cycle ceilings, future breach handling, or later fatigue logic; it only ends the special re-entry probation layer.
