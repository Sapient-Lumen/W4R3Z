# Roadmap (rev1000)

This is the current outcome roadmap. Historical revision detail belongs in
`docs/revision-index.json`; durable policy belongs in
`docs/41-decisions-log.md`.

## North star

Micromax is building a calm editor for understandable least-authority end-user
automation. Configuration, macros, and plugins share one small language; effects
remain explicit, attributable, bounded, recoverable, and inspectable without
curses. Product order is trust, then taste, then flow.

## Compact headless truth — current foundation

The current product foundation includes boring recoverable startup, exact
discard consent, collision-safe buffers, durable review-first save recovery,
permission continuation, restricted plugin generations, explicit lifecycle and
authority, bounded host work, finite process/worker owners, a compact screen
contract, exact search/query-replace/multicursor geometry, sparse history,
retained-text budgets, first-write grouped rollback, one-payload synchronous
save, framed recovery authority, and an exact-byte release configuration.

Rev1000 does not replace those owners. It corrects project-level truth:

- release-manifest presence, source/test currency, internal consistency,
  completeness, pass state, counts, digest, and issues are separately visible;
- partial checkpoints remain useful without becoming full-suite claims;
- package metadata, CLI help/greeting, editor/package docstrings, the README, and
  tutorial describe the current editor instead of a future prototype; and
- the mission audit measures coordinator/evidence growth and makes product proof
  the next default priority.

## Now — product reality

Run five sustained sessions before another long trust-hardening sequence:

1. clean environment, install/run, open help, make and save the first edit;
2. ordinary multi-file project work with repeated open/switch/find/edit/save;
3. restricted startup and plugin inspection/approval;
4. forced interruption, recovery review, continued edit, and save; and
5. one session by a person who did not author the relevant subsystem.

Record the real task, friction, workaround, trust/taste/flow category, headless
reproduction, and smallest correction. Ship no more than three product changes
from the evidence. Likely candidates are a restrained shared-model first-run
hint, a clearer one-action help loop, and a small repeated-navigation or prompt
friction correction. Do not create a telemetry or onboarding subsystem by
anticipation.

## In parallel — execute publication evidence

The highest-risk release gap is execution, not more workflow design:

1. run the exact tag/manual hosted lane;
2. retain and download the wheel, run receipt, release receipt, and revision ZIP;
3. verify repository, workflow, ref/event, commit, signer identity, and subject
   digests from a consumer context;
4. compare downloaded files with embedded source/receipt identities;
5. complete or honestly retain the short-window full-suite checkpoint; and
6. add Windows/macOS claims only through equivalent executed receipts.

A configured workflow, attestation action, or partial manifest is not current,
complete, passed, or consumer-verified evidence.

## Then — reduce one real seam

Choose one coordinator extraction only when it satisfies all of these:

- a second real consumer or independently testable owner exists;
- authority and lifetime become narrower and easier to state;
- complete product journeys remain unchanged;
- direct `Editor` responsibility, methods, or state decline; and
- the new seam deletes more coordinator code than it adds.

A file move, façade, generic owner registry, or one-method wrapper is not a
refactor outcome. A broad rewrite is also unauthorized.

## Later — public contract and platform semantics

After product and release evidence are real:

1. define a compact versioned extension “world” of buffers, edits, commands,
   prompts, messages, resources, effects, limits, and receipts;
2. prove it with a second consumer before evaluating process or Wasm isolation;
3. specify extended-grapheme movement/deletion/selection and terminal-cell width
   across the headless contract and at least two consumers;
4. publish a named filesystem and sudden-power-loss support matrix;
5. define archive revision, package version, and host API version relationships;
   and
6. choose a distinct public name after search and legal review.

## Product and architecture rules

- Evidence supports the lived editor loop; it is not the product.
- Every new mechanism names the user journey or release claim it protects.
- Presence, currency, consistency, completeness, pass state, platform, and
  consumer verification are separate evidence facts.
- Keep one immutable coordinate space and one visible boundary for multi-location
  editing.
- Treat recovery as text plus authority and rendering as free of filesystem
  discovery.
- Capture inverse data at the narrowest witnessed mutation boundary.
- Keep eager/flat paths as executable references, not accidental product paths.
- Prefer one durable contract plus one machine row over another permanent essay.
- Select a text representation, watcher, async owner, shared-memory transport,
  process/Wasm host, or broader registry only from reproduced product pressure
  and a smaller public contract.

## Deliberate non-goals

- no hostile-code sandbox claim for the Python host or helpers;
- no full-suite, hosted, public-release, or cross-platform claim from a configured
  lane or partial checkpoint;
- no generic owner/transaction/recovery/release/transport registry by symmetry;
- no rope, piece tree, background index, watcher, async save, or worker pool by
  anticipation;
- no extension isolation that exports the internal Python object graph; and
- no public launch under a name that has not passed basic identity review.
