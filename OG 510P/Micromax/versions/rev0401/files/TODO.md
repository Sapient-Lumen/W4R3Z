## Next up (high leverage)

The current editor framing is **taste, trust, and flow**.

- **Taste** = the editor looks calm, intentional, and visually coherent.
- **Trust** = startup, save/open, replace, plugins, and errors feel boringly honest.
- **Flow** = file movement, navigation, editing, and recovery loops keep the user moving.

The detailed product note is `docs/269-editor-goals-taste-trust-flow.md`. The short version is: prioritize **trust first**, then **taste**, then **flow**.

1. **Trust first**: reduce startup/plugin weirdness, make degraded-mode behavior explain itself, improve bulk-edit confidence (`replace`/`replaceall`/`qreplace` previews and clearer progress), and keep file/save/readonly/encoding behavior visibly honest. The repo already has a lot of the right substrate — capability gates, inspectable status/prompt/screen models, grouped plugin cleanup, readonly/protected-buffer paths, and portability discipline — so the next wins should mostly make that existing safety model feel human rather than implicit.
2. **Taste second**: keep iterating on picker/TUI readability, but now as one coherent visual system rather than a pile of isolated cues. The editor already has a strong inventory of tiny affordances (`hlsearch`, `cursorline`, `ruler`, `relativeruler`, `scrollmargin`, `hltrailingws`, `hltaberrors`, `colorcolumn`, `scrollbar`, `matchbrace`, overflow markers, `$(bufpos)`, `keymenu`, `infobar`, `constantshow`, `screen_model(...)`, `display_rows_model(...)`, `viewport_cues_model(...)`, and the shared prompt/status/panel/layout models); the next job is to curate defaults, previews, and hierarchy so the surface feels designed rather than merely featureful.
3. **Flow third**: keep making navigation and edit loops cheaper once trust/taste are sturdier. That means better file/project movement, better jump/return/orientation loops, continued picker scan-speed improvements, safer/faster repetitive editing, and later multi-buffer/split-aware workflows once the single-window interaction model feels settled.
4. **Docs browser polish**: keep adding small markdown affordances only when they improve real docs usage or sharpen the shared inspectable docs/help models. That lane stays valuable, but it should compete against taste/trust/flow rather than automatically outranking them.
5. **Portability discipline**: keep expanding the portable corpus / cross-host validation story as the VM surface grows, because long-term trust in Micromax as a language/runtime still depends on replayable semantics across future non-Python hosts too.
6. **Safety boundaries**: keep expanding capability-gated surfaces (jobs, filesystem, UI integration) while keeping defaults safe and degraded modes explicit.
