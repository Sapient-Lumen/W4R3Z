# Promotion dispatch budgets

VHK now models a separate promotion question from shipping/startup/recovery/proof: **what dispatch posture should own user-perceived latency for this surface?**

## Postures

- `edge-resident`: the trigger path should stay at the input edge and avoid launcher/runner startup.
- `service-resident`: the surface should already be warm in a user/system service and dispatch repeatedly without paying cold-start costs.
- `daemon-warm`: helper-backed flows may pay setup cost once but should reuse a warm daemon afterward.
- `session-resume`: portal/session-shaped helpers may need a session/bootstrap step, but steady-state dispatch should avoid rebuilding that session every time.
- `launch-cold`: a launcher/hub can honestly stay cold and pay startup at invocation time.
- `review-budget`: the planner cannot yet make a stronger claim and wants review.

## Why separate this from activation routes?

Startup routes answer **who wakes the surface up**. Dispatch budgets answer **which path must be warm when the user expects AHK-like immediacy**. Those are related, but not identical. A surface can start through a launcher yet still depend on a warm helper afterward, or start as a service while still having a review-only first-use path.

## Intended follow-up

The next product step is to let export/setup/runtime-pack generation consume these postures directly so the repo can default more aggressively toward the Linux-native lane each promoted surface actually needs.
