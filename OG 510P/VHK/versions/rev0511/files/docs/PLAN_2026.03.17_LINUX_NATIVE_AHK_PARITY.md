## New planning thread: release authority handoffs

The repo now needs one more Linux-native honesty rule: every setup/release artifact should keep the same owner model that planner/install/service work already learned. A release lane is not fully specified if it says how to ship and verify it but still hides whether the lane is session-userland, desktop-mediated, remapper-edge owned, or helper-daemon dependent after release.

That means setup guides, release-lane docs, deploy snippets, and stage payload READMEs should all preserve the same authority story instead of drifting back into generic package/deploy prose.

## New planning thread: authority-aware installs

The repo now treats native-install and session-service generation as an authority problem, not only a packaging problem. A Linux-native AHK competitor has to say which layer owns a surface after install: launcher/session userland, desktop portal/session mediation, or adjacent privileged helper/remapper.

Immediate direction:
- keep the native app tree opinionated about docs/runtime/launcher ownership
- keep session services opinionated about resident user-session ownership
- keep remapper/helper lanes adjacent and reviewable instead of pretending the app install owns them
- keep portal lanes catalog/session shaped rather than relabeling them as generic hotkey support

# VHK plan — Linux-native AHK parity without pretending Linux is Windows

This plan treats VHK as two products at once:

1. a fast local automation runner for Linux desktop workflows
2. a proof-driven export/planning system that keeps target-lane claims honest

## Product stance

VHK should not chase a fake “generic Linux” abstraction.
Instead it should:

- keep one authoring model
- support multiple desktop lanes explicitly
- prefer native or near-native trigger/injection paths for each lane
- surface proof gaps early when a project is being evaluated on the wrong host

## Explicit spec direction

### 1) Trigger plane is lane-specific

VHK should continue to model trigger ownership as a lane choice, not one global
backend:

- portal-session lanes for stable reviewed action catalogs on GNOME/KDE-style Wayland sessions
- remapper/helper-first lanes for wlroots/Hyprland/sway-style reviewed sessions
- WM/native bindings for X11/i3 and desktop-native integrations
- WM mode/submap lanes for grouped action families on X11/i3-class, sway, and Hyprland targets
- reviewable X11 adapter packs (AutoKey-class) when text/hotkey workflows benefit from an existing shell without giving up VHK as the authoring/runtime core
- launcher/text-expander fallbacks when global trigger authority is weak
- service-bus lanes when a desktop domain already exposes a standard contract, such as MPRIS for media transport and metadata
- thin adapter packs when a planner-recognized lane should become a concrete reviewed handoff (for example `vhk gen-playerctl-pack` for MPRIS/playerctl routes, `vhk gen-kitty-pack` for kitty remote-control text routes, `vhk gen-wezterm-pack` for WezTerm pane-text routes, `vhk gen-mpv-pack` for mpv JSON IPC control routes, and `vhk gen-qutebrowser-pack` for qutebrowser userscript routes)


### 1.5) Portal shortcuts are catalog-shaped, not default-shaped

VHK should keep learning one sharper Wayland lesson: a portal shortcut session is
not the automatic owner of every hotkey just because the backend is Wayland.

It is strongest when:

- actions are predeclared and reviewable
- shortcut ids stay stable across sessions
- launcher/native-bind fallbacks remain available for hotter or helper-sensitive
  routes

That means planner evidence should separate stable portal-catalog candidates
from dynamic/helper-sensitive trigger candidates instead of flattening them into
one Wayland hotkey bucket.


### 1.6) WM modes/submaps are a real middle layer

VHK should also keep learning from i3/Hyprland/sxhkd-class trigger ergonomics:
there is a useful middle lane between flat globals and launcher menus.

It is strongest when:

- a project has several related actions that should share one entry chord
- reset/escape behavior is explicit and reviewable
- the bind layer stays thin while VHK still owns macro logic

That means planner output should surface WM modal/submap lanes explicitly for
X11/i3-class, sway, and Hyprland targets instead of burying them as exporter
implementation details.

### 1.7) Picker-native chooser protocols are a real Linux control surface

VHK should keep learning from rofi/fuzzel/wofi-class picker tools too: many
prompted or chooser-heavy workflows do not want a bespoke GUI and do not belong
behind another global hotkey either.

They are strongest when:

- workflows are preset-rich or prompt-heavy
- searchable chooser entry is more natural than memorizing another bind
- one stable action catalog can feed palette rows, launcher scripts, and
  desktop entries

That means planner output should surface picker-native chooser lanes explicitly
instead of treating launcher/palette wording as sufficient.

### 1.8) App-native control protocols are a real Linux-native lane

VHK should keep learning another Linux lesson that Windows-style macro tools often
blur together: some target apps already expose better control contracts than
replayed input.

This is strongest when:

- the project is clearly pointed at protocol-rich apps like kitty, WezTerm, mpv,
  or qutebrowser
- selectors or bindings can prove which app the flow belongs to
- VHK can keep the adapter thin and reviewable while still owning the broader
  macro semantics

That means planner output should surface app-native protocol lanes explicitly
instead of pretending every terminal/media/browser flow should start with text,
vision, or pointer replay.

### 1.9) Voice command lanes should stay adapter-shaped

VHK should keep learning from Talon and Dragonfly too: Linux voice control is
healthiest when recognition, grammar activation, and app/title contexts stay on
the speech-tool side while VHK keeps the action catalog and runtime semantics.

This is strongest when:

- authors have curated literal spoken phrases or scoped `voice_when` contexts
- one VHK command id can be exported into multiple voice packs without copying
  macro logic
- phrase/context review stays visible as generated artifacts instead of hidden
  recognizer state

That means planner output should surface voice adapter lanes explicitly instead
of leaving Dragonfly/Talon export as a hidden packaging trick.

### 1.10) Desktop notifications are a real feedback lane

VHK should keep learning from the Linux notification stack too: passive status,
replaceable alerts, and operator-facing progress are not the same thing as modal
prompts.

This is strongest when:

- a project already emits `Notify` steps or wants repeated status updates
- notification-daemon signals such as action or close events matter to the flow
- the desktop/session already has a shared notification service rather than a
  bespoke app-specific tray UI

That means planner output should surface notification feedback lanes explicitly
instead of burying them inside generic prompt/UI language.

That same lesson should now reach runtime semantics too: `Notify` should be able
to carry app/category/icon/timeout metadata, notification ids for
replace/update flows, progress hints, and optional daemon-owned action ids so
progress/status toasts and passive choices do not degenerate into a pile of
duplicate one-shot popups or bespoke shell glue.


### 1.11) Authority envelopes are a real Linux product axis

VHK should keep learning one more Linux-native lesson from text expanders,
portal APIs, remappers, and uinput helpers: startup speed and actual authority
are different questions.

This is strongest when:

- a surface looks warm but still depends on portal consent or backend routing
- a helper is installed but `/dev/uinput`, socket policy, or service placement
  still decide whether it truly owns injection authority
- a user-session service owns repeated behavior without implying privileged
  control or broad app-context authority

That means planner and promotion-facing review output should surface authority
envelopes explicitly instead of letting launch, dispatch, or packaging language
stand in for who actually holds power on the host.

### 2) Proof context is a first-class contract

Any command that probes the live session/host must preserve:

- the live host snapshot
- the selected evidence lane
- the resulting host-fit/witness posture

If any pack drops that context, VHK can accidentally turn a host-specific review
into a generic support claim.

### 2.5) X11 adapter lanes should stay explicit

VHK should keep a clear distinction between:

- fast text/package lanes (Espanso-class)
- reviewable X11 shell adapters (AutoKey-class)
- low-latency remap ownership (keyd/Kanata/KMonad/xremap-class)

Those are related but not interchangeable.

### 3) Helper ownership must stay reviewable

For Linux-native operation, VHK should keep helper/service boundaries explicit:

- remapper ownership
- raw-input/uinput policy
- portal routing truth
- service lifecycle expectations
- packaging/bootstrap choices

### 4) Session-fit and host-contract are not documentation fluff

These packs are the maintainer-facing control surface for deciding whether a box
is believable evidence for a shipping lane. They should remain small, direct,
and rerunnable.

## 2026-03-17 addendum — typed-text fast paths must stay narrow on Wayland

VHK should now treat Wayland text lanes with the same honesty it already applies
to triggers and remappers:

- package/clipboard-driven text automation is the broad reviewable lane
- `wtype`-class virtual-keyboard typing is a narrow fast path only when the
  session/compositor evidence supports it
- uinput/helper-daemon typing remains a separate fallback lane with lifecycle
  and permission costs

This means the planner should not present `wtype` as the generic Wayland text
answer by default. It should only elevate that lane when the project shape wants
fast typed-text playback and the target host/session makes the protocol path
believable.


## 2026-03-17 addendum — helper daemons should be planned, not discovered late

The repo now also has enough evidence to treat daemon-backed helper lanes as an
explicit design surface:

- repeated Wayland text/pointer playback often becomes a daemon/socket story
  (`dotoold`/`dotoolc`, `ydotoold`) rather than a clean one-shot CLI story
- that means service generation, socket placement, and `/dev/uinput` policy are
  part of the first-class deployment contract
- VHK should therefore surface a persistent helper lane during planning instead
  of leaving it buried in setup recipes and host-contract packs

This is creatively important because it lets VHK act more like a Linux-native
product strategist: not just “what helper binary exists,” but “what repeatable
operator-owned lane can actually survive deployment?”


## 2026-03-17 addendum — accessibility is a lane, not a checkbox

VHK should also keep learning a sharper structured-UI lesson from Linux
accessibility tooling:

- AT-SPI is a separate bus/contract, not a side effect of ordinary window
  metadata
- inspector-style tooling (Accerciser-class) is part of making semantic targets
  reviewable
- automation wrappers (dogtail-class) show that structured widget targeting can
  be a real lane without pretending every application exposes a good tree

That means planning output should keep an explicit accessibility/structured-UI
lane visible and pair it with desktop-metadata plus vision fallbacks instead of
flattening everything into either “window support” or “image automation.”


## 2026-03-17 addendum — input truth should be grouped by workload, not helper names

The repo now has enough Linux-specific evidence that planning and audit output
should stop forcing operators to mentally translate helper inventories into real
deployment lanes. The important product questions are workload-shaped:

- is this mostly long/structured text that wants a clipboard/text-surface lane?
- is this a narrow literal text burst where `wtype`-class virtual-keyboard
  support is worth using as a fast path?
- is this repeated pointer/key playback that really wants a daemon-backed
  uinput lane?
- is this a permissioned portal/libei-style experiment where session consent is
  part of the contract?
- or is this an X11-native replay case where helper complexity buys little?

That means VHK should expose one workload-oriented input lane dossier during
planning and capability review, instead of making operators infer product shape
from scattered `wtype`/`ydotool`/`dotool`/portal helper mentions.

It should also carry that truth forward into project-level shipping decisions
through a `promotion_input_lane_plan`, so text packages, remapper exports,
helper dossiers, and launcher/service surfaces can say which lane actually owns
the shipped experience instead of only naming an export format.

That same shipping work also needs a `promotion_activation_route_plan`, because
startup/service/session ownership is a separate Linux truth from the input lane
itself. Promotion-pack docs should render both plans directly, so operators can
review shipping-lane ownership and startup ownership in the same artifact where
they review waves, backlog, and evidence.


### 1.8) App-native terminal adapters need real match builders

VHK should also learn one narrower lesson from kitty-class terminal control: app-native adapters become genuinely useful only when the exporter can generate a match expression that remains reviewable outside the current session.

That means the first concrete terminal adapter should stay conservative:

- prefer explicit title/title-regex evidence that can become a stable kitty `--match` expression
- export thin helpers around kitty's own remote-control transport instead of pretending VHK itself is now the terminal multiplexer
- record class/app_id-only routes as skipped until VHK grows a richer inspector/match builder for kitty window metadata

### 1.12) WezTerm pane control is adapter-shaped, not generic typing

VHK should also learn the narrower WezTerm lesson explicitly: pane-aware terminal control is most useful when the exported helper stays honest about how it finds the pane.

It is strongest when:

- a route already has explicit pane identity (`WEZTERM_PANE_ID` / `WEZTERM_PANE`)
- otherwise the project has reviewable title or title-regex evidence that can drive `wezterm cli list --format json` lookup
- the helper keeps `send-text` / `get-text` ownership on the WezTerm side instead of pretending VHK is now the terminal multiplexer

That means concrete WezTerm exports should fail loudly on ambiguous pane resolution and stay reviewable instead of silently targeting an arbitrary pane.


## 2026-03-17 addendum — runtime route choice should reuse planner truth

The repo has now crossed an important product threshold: helper/protocol truth
is not only a planning concern.

- doctor/readiness can prove a daemon lane is inactive, a socket is missing, or
  a Wayland protocol is absent
- runtime should reuse that truth instead of rescanning `PATH` and pretending
  the lane is still equally believable
- uncertainty should remain soft, but explicit disproof should change the live
  route decision

This is a subtle but important AHK-parity lesson for Linux: reliability comes
from making route choice **stateful and honest**, not merely from supporting a
long list of helper binaries.


That same promotion story also needs an explicit recovery lane. Linux-native surfaces do not just differ by how they ship or wake up; they also differ by how operators get back to safety after a bad config, dead session, permission drift, or backlog/overflow surprise. A text package usually wants a service-restart lane, a remapper often wants a rollback-first lane, a portal helper wants a session-recreate lane, and a launcher mostly wants a regenerate-plus-smoke-test lane. `plan-project`, promotion docs, operator docs, and capability-audit review should surface that directly through a `promotion_recovery_plan` instead of burying rollback/re-entry steps in long prose.

One more layer sits underneath startup, recovery, and verification: dispatch budget ownership. Linux-native automation that wants to feel AHK-fast cannot talk about every surface as if “it starts somehow” were enough. A text expander wants a service-resident warm path, a remapper wants an edge-resident path that never detours through launcher latency, a portal/helper flow may accept session-resume or daemon-warm first use, watcher services want resident event pipelines, and a launcher surface may honestly stay launch-cold. `plan-project` and the promotion/capability/operator packs should surface that through a `promotion_dispatch_budget_plan` so cold-start, first-use, and steady-state expectations stay explicit in the product story instead of hiding behind generic startup prose.

Promotion review also needs an explicit verification lane. Linux-native shipping is full of artifacts that can be generated successfully while the real surface is still dead: text packages that are exported but not active, remapper configs that render but still fail under live input, portal sessions that exist but never activate, and watcher services that are up but do not actually deliver events. `promotion_verification_plan` should keep one smoke/proof loop per promoted surface visible in planner, audit, promotion, and operator docs so release language is anchored to real observed behavior, not only to generated files.

- Promotion planning now needs an explicit performance-envelope layer: text/package surfaces should own throughput, remapper surfaces should own low-latency edge paths, helper/portal surfaces should distinguish warm-daemon versus consent-bound latency, and watcher/launcher surfaces should say what “fast enough” means in resident event or wake-up terms.


## New planning thread: session activation sync

- Service handoffs should stop assuming `environment.d` is enough for graphical-session startup.
- Explicitly sync reviewed display/session variables into D-Bus + `systemd --user` activation environments before autostarted VHK-owned services start.
- Keep this variable set narrow and reviewable instead of importing whole login shells wholesale.

## New planning thread: startup handoff ownership

- Service handoffs should stop installing multiple startup owners for the same VHK-owned lane by default.
- Prefer one primary startup owner (graphical-session-bound systemd unit when available) and keep XDG autostart as an explicit fallback.
- Ship a small probe/doc lane that catches duplicate-start risk early, especially on session managers that already translate autostart entries into systemd-managed startup behavior.


## New planning thread: session readiness guards

VHK had already learned to describe authority, warm-path ownership, activation
sync, graphical-session lifetime, and startup ownership. The next Linux-native
truth was subtler but operationally important: **is the live session actually
ready for this lane right now?**

A user unit can be present, enabled, and still be launched in the wrong
context—missing `XDG_RUNTIME_DIR`, missing display identity, inactive graphical
session target, or stale login-time environment. `gen-service-compose-pack` now
ships a concrete readiness probe and uses an `ExecCondition=` gate for the
VHK-owned unit so wrong-session startup can be skipped cleanly instead of
looking like an ordinary daemon crash.


## New planning thread: session readiness evidence

VHK now knows how to guard a user unit with session readiness, but a Linux-native
AHK-like system also needs to **remember what happened** when that guard was
consulted. Rehearsal and dossier lanes should therefore capture one compact
readiness verdict, the probe output that produced it, and the nearby user-unit
state so operators can tell the difference between a healthy install, a skipped
start, and a real runtime fault.

## New planning thread: installed-lane readiness status

VHK now knows how to guard session startup and preserve that evidence in
rehearsal/dossier output, but a Linux-native AHK-like lane also needs one
lighter-weight answer for daily operator use: **what does the installed lane say
about itself right now?**

That means the native launcher status/report surface should capture the same
readiness truth directly, and the support pack should ask for that installed
status bridge before it assumes a full support packet is necessary.


## New planning thread: installed-lane runtime health verdicts

Readiness alone is not enough. A Linux-native AHK-like product also needs a
compact answer to **what is the owned lane doing right now?**

That means installed status/support surfaces should preserve one runtime-health
verdict that can say the lane is healthy, skipped because the session is not
ready, stopped, missing, unavailable, or actively degrading through restart
churn/failure. The point is not to replace deeper dossier evidence, but to make
lightweight operator truth good enough to answer the first round of support
questions without log archaeology.

## New planning thread: installed-lane startup ownership truth

VHK now knows whether the session is ready and whether the owned lane looks
healthy, but Linux-native operator truth still needed one more answer: **who
actually owns startup for this installed lane right now?**

That means installed status/support surfaces should preserve one startup-handoff
verdict that can say the lane is owned by an enabled user unit, currently
depends on an XDG autostart fallback, risks duplicate starts because both are
present, or has no valid startup owner at all. The point is not to replace the
existing service-pack startup policy, but to keep the installed lane honest
when the live host drifts away from the reviewed default.



## New planning thread: installed-lane startup handoff drift

One snapshot of startup ownership is useful, but Linux-native operator truth also
needs to answer whether startup ownership is **staying put**. That means the
installed lane should keep a small local history of startup-owner snapshots and
report whether ownership is stable, recently changed, recovered, chronically
duplicate, chronically missing, or flapping. Rehearsal and dossier surfaces
should inherit that summary so startup drift stops disappearing between support
runs.


## New planning thread: installed-lane runtime health drift

One snapshot of runtime health is useful, but Linux-native operator truth also
needs to answer whether health is **staying good, recovering, or repeatedly
falling apart**. That means the installed lane should keep a small local
history of runtime-health snapshots and report whether health is stable,
recently changed, recovered to healthy, chronically restart-churning,
chronically failed, chronically inactive/missing, or flapping. Support,
rehearsal, and dossier surfaces should inherit that summary so runtime drift
stops disappearing between support runs.


## New planning thread: installed-lane incident signatures

Readiness, runtime health, runtime drift, startup ownership, and startup-owner
drift are all useful, but Linux-native operator truth still benefits from one
more compact question: **what kind of recent incident actually happened?**

That means the installed lane should preserve an incident-signature verdict
that can say the lane was cleanly session-skipped, skipped by some other
condition, pushed into start-limit churn, hit by a real process failure, or
missing units entirely. When `journalctl --user` is available, that verdict
should also carry a small journal sample so support can escalate from summary
into evidence without jumping straight to full dossier collection.

## Incident drift follow-through (rev0313)

The installed lane now has enough signal to classify the current incident, but
Linux support still benefits from one more small truth surface: whether that
incident class is stable, chronic, flapping, or already recovering. That means
the launcher should keep a short local history of incident-signature snapshots
and surface one drift verdict directly in installed status, support, rehearsal,
and dossier artifacts.
