# Note — authority-aware installs and service scope

This note captures the product rule behind revision 0300: VHK should never let a local install or a user-session service imply broader Linux authority than it actually owns.

## Core rule

- launcher links, desktop entries, bundled docs, and embedded runtimes are **userland packaging surfaces**
- session services are **resident user-session orchestration surfaces**
- portal/global-shortcut routes are **desktop-mediated session surfaces**
- remappers and uinput helpers are **adjacent privileged surfaces** unless VHK explicitly owns and verifies their lifecycle

## Why this matters

AHK on Windows could often hide OS boundary lines because the platform exposed a more unified automation surface. Linux does not. If VHK wants to feel equally capable without becoming dishonest, it has to make those ownership lines visible in the shipped artifacts, not only in design notes.

## What revision 0300 implements

- native-install plans/docs now carry `authority_policy`
- native app trees ship `VHK_AUTHORITY_OVERVIEW.md`
- desktop entries expose an authority quick action
- service-composition plans/docs now carry `authority_scope` plus authority-policy context
- service packs can say which surfaces are session-owned versus merely adjacent
