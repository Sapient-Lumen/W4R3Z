# Note — release authority handoffs

This note captures the product rule behind revision 0301: VHK should not let setup or release packs sound more universal than the Linux lane they are actually shipping.

## Core rule

- setup output should explain which surfaces stay in plain user-session ownership
- release-lane output should explain when a lane is desktop-mediated, session-userland, helper-daemon-privileged, or input-edge-privileged
- release-deploy output should keep deployment style separate from authority ownership
- release-stage payloads should preserve the same ownership story so a staged handoff does not regress into generic install prose

## Why this matters

Linux automation tools keep teaching the same lesson in different ways: portal shortcuts are session/consent objects, text expansion is often a user service, and low-latency input ownership often belongs to a remapper or helper daemon rather than to the authoring app itself. A Linux-native AHK pseudoclone can still be creative, but it has to keep those owners visible when it ships.

## What revision 0301 implements

- centralized authority-policy derivation in `authority_policy.py`
- setup guides now render explicit authority boundaries
- release-lane plans/docs now carry per-lane authority stories and summary counts
- release-deploy docs now include authority handoff sections alongside install/deploy choices
- release-stage docs and per-lane READMEs now preserve that same authority story
