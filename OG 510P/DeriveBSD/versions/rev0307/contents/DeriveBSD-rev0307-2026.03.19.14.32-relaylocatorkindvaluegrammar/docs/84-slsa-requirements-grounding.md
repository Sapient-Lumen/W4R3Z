# SLSA requirements grounding (use as policy vocabulary)

DeriveBSD uses SLSA not as “compliance theater” but as a vocabulary:
- to express build provenance expectations
- to map policy knobs to recognizable guarantees

SLSA publishes:
- “levels” / tracks describing security postures
- detailed “requirements” for each level

References in `docs/32-curated-references.md`.

## DeriveBSD mapping (tight)

- Provenance exists and is signed → baseline for all channels.
- Provenance is generated by the build system (not hand-authored) → required for official channels.
- Build isolation / hermeticity → required for “high assurance zones”.

DeriveBSD policy should be able to express:
- required SLSA-ish level (or subset of requirements)
- which target kinds must meet it (host vs microVM vs wasm)
- what evidence is acceptable (attestations, transparency inclusion)

This doc is a pointer; see `docs/76-slsa-levels-and-derivebsd-goals.md` for the roadmap view.
