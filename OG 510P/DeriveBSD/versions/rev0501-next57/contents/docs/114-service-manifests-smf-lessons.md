# Service manifests as derived graphs (SMF lessons)

Illumos/Solaris SMF treats services as first-class objects with explicit dependencies and deep introspection.
Even if DeriveBSD keeps `rc.d` as an activation backend, the **graph** is the real lesson.

References:
- SMF overview (`smf(7)`). https://smartos.org/man/7/smf
- SmartOS SMF quick reference (manifests + tooling pointers). https://docs.smartos.org/smf-quick-reference/

## DeriveBSD direction

Derive an explicit **service graph manifest** from the Plan + host/workload intent:
- service instances
- dependencies
- restart policies
- which jail/microVM they live in
- which resources/pf anchors they require

This enables:
- `derive diff --blast-radius` to include *service-level* authority changes
- `derive explain service <name>` to answer why it exists and what it depends on
- conformance testing: ensure activation matches the manifest

## Keep the v1 footprint small

- Don’t invent a full SMF clone.
- Start with a single JSON manifest output (generated by activation planning).
- Activation backends (rc.d, service-jails, maybe later something else) must be able to consume it.

SMF also has a useful operational lesson: services become inspectable objects with explicit dependency
edges and failure states (e.g., “offline/maintenance”), which can inform DeriveBSD’s health gating.

See RFC-0082.


## State vocabulary (operator UX)

Even if activation is `rc.d`-backed, the *meaning* of “service health” should be consistent.
Borrow SMF’s vocabulary (and semantics) as a stable interface:

- `uninitialized` — not yet evaluated by a restarter
- `offline` — enabled but not running/available
- `online` — running/available
- `degraded` — running/available with reduced capacity
- `maintenance` — requires operator action / repeated failure
- `disabled` — explicitly disabled

This gives health-gated updates a clear signal beyond “booted once”.

## Restarters + failure ownership

SMF’s other key lesson: failures are owned by a **restarter** that:
- observes a service’s lifecycle
- applies restart policy with backoff/limits
- enters `maintenance` deterministically when failure persists

DeriveBSD should implement the *data model* first:
- `svcdb` (compiled service database)
- `svc.snapshot` (runtime state)
- `svc.event` (transitions + crashes)

See: `docs/214-service-supervision-health-as-evidence.md` and RFC-0149.

## “Contracts” (optional, but high leverage)

Illumos process contracts provide a clean way to define a *fault boundary* around a service’s whole process tree.
DeriveBSD can use a contract-like mechanism (or jail/microVM boundaries) to avoid orphan subprocesses and make restarts reliable.

See: https://smartos.org/man/5/process
