# 2026-03-01 (07) — reproducibility, proc-macro sandboxing, and i18n foundations

## Signals (with sources)
- **Reproducible `cargo package` archives are still an open pain point** (bit-for-bit identical `.crate` archives across machines).  
  Source: cargo issue “Reproducible crate builds” — https://github.com/rust-lang/cargo/issues/8612
- **Deterministic build order & metadata emission have been asked for repeatedly** (helps benchmarking and reproducibility tooling).  
  Source: cargo issue “Deterministic build order of crates” — https://github.com/rust-lang/cargo/issues/2607
- **Proc-macro execution model remains a reproducibility + security hazard**, and the compiler team is actively exploring WebAssembly as a sandbox mechanism.  
  Source: compiler-team issue “WebAssembly for procedural macros” — https://github.com/rust-lang/compiler-team/issues/876
- **There is persistent demand for i18n/localization ergonomics in Rust apps**, with toolchains like cargo-i18n and ICU4X being common points of reference.  
  Sources:
  - https://users.rust-lang.org/t/internationalization/77011
  - https://github.com/unicode-org/icu4x
  - (example of typed-token design concerns) https://github.com/zed-industries/zed/discussions/43592

## Candidate gaps that feel “crate-sized”
1. **Reproducible packaging & verification**: normalize timestamps, file order, and archive metadata; provide CI-friendly verification.
2. **Proc-macro sandbox readiness kit**: help crates prepare for a Wasm-based proc-macro future (tooling + constraints + test harness).
3. **I18n “batteries included” that go beyond message lookup**: typed tokens + ICU-backed formatting for numbers/dates/plurals, without pulling a whole framework.
