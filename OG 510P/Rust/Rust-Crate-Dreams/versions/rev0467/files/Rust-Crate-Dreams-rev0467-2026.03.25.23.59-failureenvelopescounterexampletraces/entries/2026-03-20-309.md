# Entry 309 — channel-surface-contract-kit added for capacity posture, overflow policy, delivery obligation, and shutdown/drain truth

This pass added a new top-level proposal: **P-0529 Channel Surface Contract Kit**.

## Why this lane earned a slot

The archive already had better answers for:

- resource saturation,
- lifecycle/shutdown aftermath,
- observability delivery truth,
- generic capability contracts,
- feature/config/MSRV support truth,
- and crate selection / upgrade support.

It still lacked one receiver-facing answer to a common concurrency question:

> “What does this channel actually promise when it fills, when receivers lag, when a send succeeds, and when shutdown begins?”

Current Rust channel substrate now makes that absence concrete enough to justify a dedicated lane.

## What moved this time

The main planning move was to treat **channel choice as a support contract layer**, not as raw implementation detail or benchmark trivia.

This pass therefore promoted four review objects to first-class status:

1. **capacity-posture truth** — bounded, unbounded, zero-capacity, latest-only, overwrite, or priority-bounded;
2. **overflow-policy truth** — wait/backpressure, reject, drop-oldest, lag-error, or retain-latest behavior;
3. **delivery-obligation truth** — whether send success means enqueued, receivable by one, cloned to all current subscribers, or merely visible as latest state;
4. **shutdown/drain truth** — what close/drop does to buffered work and what clean-shutdown recipe really exists.

## Why this matters

Without those objects, the ecosystem still permits a common shortcut:

- Tokio `mpsc`, Tokio `broadcast`, Tokio `watch`, `crossbeam`, Embassy, `async-channel`, `flume`, and domain wrappers can all truthfully say “channel”,
- maintainers can truthfully say “bounded” or “supports clean shutdown”,
- and a downstream team can still have no compact answer for:
  - whether a sender blocks or drops,
  - whether intermediate messages are preserved,
  - whether lag is explicit or silent,
  - whether send means enqueue or full observation,
  - and what buffered work does during close.

That is not just API detail.
It is supportiveness.

## Main judgment after the pass

A worthy channel-support contribution for Rust should now provide more than a crate choice, one benchmark chart, or a prose docs section.
It should provide:

- one explicit **capacity-posture receipt**,
- one explicit **overflow-policy receipt**,
- one explicit **delivery-obligation report**,
- and one honest **shutdown-drain receipt**.
