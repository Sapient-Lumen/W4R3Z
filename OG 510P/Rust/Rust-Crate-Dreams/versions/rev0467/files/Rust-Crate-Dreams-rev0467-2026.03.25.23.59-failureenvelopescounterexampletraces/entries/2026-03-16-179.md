- **generic lint-fix orchestration**, and
- **lower-level Cargo phase / plumbing receipts**.

That produced two focal crates:

- **P-0507 Cargo Fix Campaign Kit**
- **P-0432 Cargo Plumbing Interop Kit**

## Why these moved now

Several official signals now line up unusually well.

### 1. `cargo fix` is important, but its current workflow is still thin

The Cargo docs and Edition Guide make clear that:

- `cargo fix` runs the equivalent of `cargo check`,
- it may need multiple passes,
- and edition migration often needs separate target/feature runs.

That means real maintenance work already looks like a **campaign**, not one command.

### 2. The `cargo-fixit` prototype exposed a real missing layer

The Rust project’s own summaries say the existing architecture is limited by speed, limited lint-selection control, and a locking-heavy rustc-proxy design.
The alternative `cargo-fixit` prototype instead lets the top-level tool:

- decide which build targets are safe to fix in a pass,
- coordinate suggestions,
- remove the locking-heavy architecture,
- and open the door to interactive mode.

That is a strong signal that a worthy crate opportunity exists **above** `cargo fix` itself.

### 3. Cargo plumbing is real enough to matter, but still compromised enough to need receipts

The official plumbing goal already framed build work as discrete stages.
The GSoC plumbing prototype implemented seven candidate subcommands, but it also documented blocker-driven compromises such as re-reading manifests from disk instead of consuming caller-edited state directly.

That means a downstream crate is needed to capture:

- phase outputs,
- phase-input intent,
- reread-versus-consumed behavior,
- and blocker notes.
