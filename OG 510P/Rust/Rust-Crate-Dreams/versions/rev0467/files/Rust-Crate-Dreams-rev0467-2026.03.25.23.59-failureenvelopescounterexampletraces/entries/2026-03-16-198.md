# Entry 198 — crate-authored guidance packs promoted as a receiver-facing ecosystem-supportiveness lane

This pass added a new top-level proposal: **P-0512 Crate Guidance Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing crate choice, producer-side capability claims, shared interop profiles, generic diagnostic rendering, and crate-authored guidance into one fake “supportiveness tooling” story.

## Why this moved now

Several current official Rust signals line up unusually well.

### 1. The ecosystem frontier needed a receiver-facing lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**, and
- **shared ecosystem profile contracts** via **P-0511**.

But it still lacked a good answer to:

- “Once a user has chosen a crate and hit a common failure path, what guidance does the crate actually provide?”

That left the archive with better answers for **selection** and **support claims** than for **failure recovery**.

### 2. Official vision-doc guidance now names supportive interfaces from crates directly

The December 2025 vision-doc post says Rust should “double down on extensibility” and specifically calls for **better diagnostics and guidance from crates**.
It argues that crates currently do not benefit from the same supportive surfaces Rust provides natively through compiler messages and lints.

That is a surprisingly explicit statement of a missing-crate opportunity.

### 3. The compiler hook substrate exists, but the maintainer workflow does not

Rust 1.78 stabilized the `#[diagnostic]` namespace and `#[diagnostic::on_unimplemented]`.
The Reference now documents those hooks and also lists `diagnostic::do_not_recommend`.
RFC 3368 exists because some trait-heavy crates emit large, hard-to-understand errors and crate authors need better control.

But those pieces still do **not** give maintainers one boring workflow for:

- declaring common failure modes,
- verifying them against fixtures,
- attaching recovery recipes,
- and diffing the support surface across releases.

### 4. Survey evidence says support surfaces matter because docs and code are still the main learning path

The 2025 State of Rust survey says online documentation is still the preferred canonical reference and the code itself is the next thing people study.
That means crate supportiveness is not just a “nice extra”; it is part of how people actually learn and recover.

## Current judgment

The worthy crate here is not:

- another ranking engine,
- another support-claims schema,
- another interop profile pack,
- or another renderer for already-existing diagnostics.

The worthy crate is the boring supportiveness layer that can hand other people:

1. one **guidance pack**,
2. one **compile-guidance receipt**,
3. one **recovery-recipe manifest**,
4. one **guidance-check report**,
5. one **support-surface diff**,
6. and one explicit **manual-review boundary** when the guidance is still advisory.
