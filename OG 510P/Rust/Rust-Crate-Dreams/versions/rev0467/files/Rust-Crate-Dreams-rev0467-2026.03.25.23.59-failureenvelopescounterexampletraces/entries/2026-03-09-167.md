# Entry 167 — local-first fixture pack restored and transport/bootstrap truth tightened

This pass again chose **not** to add another narrow proposal.

The better move was to fix a repo-memory mismatch and use that repair to sharpen one of the archive’s broad top-tier bets.

`Entry 165` already claimed that **P-0076 Local-first Sync Kit** had a full fixture pack.
But the extracted archive did not actually contain `fixtures/localfirst-sync-kit/`.
That is exactly the kind of archive drift this repository is supposed to resist.

So this pass did two things together:

1. restored the missing fixture pack,
2. and made the proposal more operationally honest about **transport**, **relay behavior**, and **bootstrap material**.

## Main judgment

The sharper local-first crate in Rust is not:

- another CRDT engine,
- another vague sync abstraction,
- or a claim that “peer connected” means everything is fine.

It is a crate that can hand another person a small, reviewable set of artifacts saying:

- which repo/profile was in play,
- which sync assumptions were relied on,
- whether the session was direct or relay-backed,
- how peers initially found each other,
- which membership epoch was current,
- and why the outcome was convergence, drift, rejection, or manual-review-only.

That is a much stronger planning target than a generic “local-first platform”.

## Why these changes were the right ones

### 1. The archive needed to match its own memory surface
A research repo that says a fixture pack exists when it does not is training future humans and LLMs on the wrong shape of the frontier.
Restoring the missing pack was therefore not busywork; it was part of the archive’s epistemic hygiene.

### 2. Transport truth is part of the missing crate
The current substrate makes this unusually clear:

- Automerge sync assumes a **reliable in-order stream**,
- iroh makes **protocol routing**, **relay fallback**, and **bootstrap handles** explicit,
- public relays are not the same operational story as dedicated relays,
- and tickets are useful bootstrap material but not durable identity.

That means a worthy local-first crate should export session receipts that preserve those distinctions.

### 3. Bootstrap convenience needed to be separated from authorization truth
A common design mistake in peer-to-peer systems is to treat the thing that gets two peers talking as the same thing that proves who should still be allowed to talk.
That is not a safe or supportable assumption.

The updated proposal and fixtures now say more clearly that:

- tickets / invites / endpoint handles are **bootstrap**,
- replica/member IDs are **durable identity**,
- membership ledgers and epochs are **authorization truth**,
- and support bundles should normally carry only **redacted summaries** of bootstrap material.

### 4. The fixture pack now has a cleaner first profile split
The restored scenarios make the planning surface more credible:

- `offline_fork_then_reconnect` covers the same-user multi-device happy path,
- `revoked_device_after_key_epoch` covers the collaboration/membership failure path.

That keeps the proposal grounded in both product ergonomics and security honesty.

## New planning stance

For the next few passes, the archive should prefer:

- treating **P-0076** as a boring coordination kit above strong substrate,
- keeping bootstrap material separate from durable identity,
- keeping direct vs relay path visible in receipts,
- and treating redaction/comparability as first-class support truths.

It should **not** drift into:

- another CRDT engine proposal,
- another fake “all local-first problems solved” platform,
- or a story where tickets, identities, and authorization all quietly become the same thing.
