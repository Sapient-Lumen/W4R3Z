# Entry 307 — crate-observability-surface-pack-kit sharpened around delivery posture, completeness class, and exit-sensitive route truth

This pass returned to **P-0518 Crate Observability Surface Pack Kit** because the archive still left one ordinary operational shortcut too cheap:

> a team could truthfully say “this crate emits logs / traces / metrics to that route” while still leaving other teams unable to tell whether the route is blocking, lossy, sampled, periodically aggregated, or dependent on clean shutdown / `force_flush`.

## What moved this time

Several current Rust and OpenTelemetry surfaces make that blur more expensive now than it used to be:

- `tracing_appender::non_blocking` still runs a dedicated background thread, defaults to **lossy** mode, and exposes dropped-line counters instead of pretending complete delivery;
- `WorkerGuard` still exists because buffered logs/events may not be written on abrupt process termination;
- `SdkTracerProvider` and `SdkLoggerProvider` still expose explicit `force_flush` / shutdown semantics for remaining buffered spans/logs;
- OpenTelemetry sampling docs are explicit that unsampled traces/spans are not processed or exported;
- `tracing-opentelemetry` now includes a metrics layer, but metrics are still exported as aggregated telemetry rather than one raw downstream event per measurement;
- and OpenTelemetry’s Rust instrumentation-library docs still make the library/app boundary a real support boundary rather than a solved default.

## Main planning move

This pass promoted two more first-class review objects for **P-0518**:

1. **delivery posture truth** — whether a signal family is blocking, backpressure-buffered, lossy-buffered, batch-exported, periodically exported, sampled, or still manual-review territory;
2. **completeness class truth** — whether another team should interpret that family as `attempted_all_events`, `best_effort_buffered`, `representative_sample`, `aggregated_window`, `exit_sensitive`, or `manual_review_required`.

## Why this matters

Without those objects, the archive still permits an ordinary lie:

- a maintainer can truthfully point at a `fmt` route,
- another maintainer can truthfully point at an OTLP trace route,
- a platform team can truthfully see metrics in a backend,
- and nobody has one compact answer for whether those are complete event streams, sampled representatives, periodic aggregates, or exit-sensitive buffered paths.

That is not just backend trivia.
It is the difference between:

- “the route exists,”
- “the route usually works,”
- and “this is the kind of delivery/completeness claim another team may honestly rely on.”

## Main judgment after the pass

A worthy observability-support contribution for Rust should now provide more than a signal list, activation recipes, route receipts, and redaction notes.
It should also provide:

- one explicit **delivery-posture receipt**,
- one explicit **completeness-class report**,
- and one honest separation between **route existence** and **delivery/completeness claims**.
