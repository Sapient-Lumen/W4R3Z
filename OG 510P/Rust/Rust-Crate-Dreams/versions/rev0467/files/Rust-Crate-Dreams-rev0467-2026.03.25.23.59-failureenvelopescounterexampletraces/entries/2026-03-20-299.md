# Entry 299 — cargo-package-review-kit sharpened around packaged-surface authority, archive basis, and extraction-state truth

This pass returned to **P-0470 Cargo Package Review Kit** because the archive still left one ordinary release-review shortcut too cheap:

> a team could say “we reviewed the package” while meaning three different surfaces — the authored working tree, the packaged `.crate` archive, or the extracted verification tree Cargo creates after packaging.

## What moved this time

Several current Cargo signals make that blur more expensive now than it used to be:

- `cargo package` still treats the `.crate` tarball as the canonical packaged source bundle, rewrites and normalizes `Cargo.toml`, removes `[patch]`, `[replace]`, and `[workspace]` sections, includes `Cargo.lock` by default, flattens symlinks, extracts the tarball again, rebuilds it from scratch, and checks that build scripts did not modify source files;
- the unstable `cargo package --list --message-format json` surface now makes path lineage materially more reviewable by exposing packaged paths plus whether a file was `copy` or `generate`, including the `Cargo.toml.orig` / generated `Cargo.toml` pair;
- Cargo explicitly says `.cargo_vcs_info.json` is only a best-effort snapshot and not verified provenance;
- Rust 1.93.1 says maintainers should use `cargo package` rather than depending on `cargo publish` to leave `.crate` tarballs lying around as durable artifacts;
- Cargo’s changelog now says generated files in package tarballs should have deterministic timestamps, and that Cargo updates mtimes for generated files after unpacking `.crate` source tarballs;
- and long-running tooling pain around `.cargo-ok` and modified extracted trees shows that “what Cargo unpacked for verification” is still not the same thing as “what was originally uploaded”.

## Main planning move

This pass promoted three more first-class review objects for **P-0470**:

1. **packaged surface truth** — what exact archive paths and bytes were actually reviewed, and whether they were copied or generated during packaging;
2. **archive authority truth** — which surface is authoritative for hash/review/signoff claims: authored tree, raw `.crate`, JSON path listing, or extracted verification tree;
3. **extraction mutation truth** — what Cargo changed after unpacking for verification, such as `.cargo-ok`, normalized manifest replacement, or mtime adjustments.

## Why this matters

Without those objects, the archive still permits a very ordinary lie:

- a maintainer can truthfully inspect an extracted tree,
- another reviewer can truthfully diff the authored workspace,
- Cargo can truthfully verify the unpacked package,
- and nobody has one compact answer for which of those surfaces is the authority for the release review itself.

That is not just tooling trivia.
It is the difference between “we reviewed something package-like” and “another team can inspect one honest receipt that says which bytes were authoritative, which paths were generated, and which extraction-time mutations happened only during verification.”

## Main judgment after the pass

A worthy pre-publish package-review contribution for Rust should now provide more than:

- a packaged path list,
- one normalized-manifest summary,
- or one VCS snapshot caveat.

It should also provide:

- one explicit **packaged-surface receipt**,
- one explicit **archive-authority report**,
- one explicit **extraction-mutation report**,
- and one honest way to keep “authored tree”, “raw archive”, and “verification extraction” from masquerading as one review surface.
