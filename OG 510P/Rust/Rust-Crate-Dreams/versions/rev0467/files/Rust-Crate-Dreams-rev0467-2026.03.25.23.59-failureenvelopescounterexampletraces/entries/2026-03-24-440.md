# Entry 440 — supportive surfaces, first-release bundles, and hard-domain adoption ladders

This pass again chose **deepen over append**.

The archive already has many missing-crate candidates and a wide sector map.
What it still needed was a sharper answer to three planning questions:

1. what a worthy crate should provide **other people on day one**,
2. how the leading control-plane crates should expose **supportive surfaces** instead of just outputs,
3. and how those crates should scale their claims when the audience is not just a hobby project but an **air-gapped, embedded, mixed-language, or safety-critical** team.

## Main judgment

Three repo moves were worth making now.

### 1. Add a supportive-surface discipline for epic crates

The December 2025 Vision Doc write-up on what people love about Rust makes two important claims:
- crates are good at building safe, efficient abstractions,
- but Rust still lacks enough tools that make crates **supportive** for users.

That matters here.
A worthy missing crate should not just be a wrapper, ranking table, or clever API.
It should export a **supportive surface** another person can actually use in review, support, or operations.

The new supportive-surface note therefore says a serious crate should usually publish five distinct surfaces:
1. **orientation** — who this is for and under what task constraints,
2. **evidence** — receipts, reports, manifests, and witnesses,
3. **review** — short human-facing briefs and manual-review triggers,
4. **machine** — schemas and importable structured outputs,
5. **drift/refusal** — freshness rules, revisit triggers, and explicit non-claims.

That model is the archive’s new default filter for “what should the crate provide other people?”

### 2. Make pathfinder review packets more operational

The archive already knew that **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit** should emit decision packs.
What it still lacked was a stronger mapping from those packs to concrete receiver workflows.

The new pathfinder review-packet note therefore frames `cargo pathfinder` as a crate that must serve at least four workflows:
- **solo or team lead selection**,
- **architecture / ADR review**,
- **CI / pre-merge drift watch**,
- **periodic re-evaluation** for long-lived stacks.

It also tightens the first packet family:
- `decision-brief.md`
- `starter-set.bundle.json`
- `candidate-elimination.receipt.json`
- `manual-review.note.md`
- `revisit-trigger.policy.json`
- `adoption-checklist.md`

That is now a better `0.1` target than “a recommendation engine.”

### 3. Add a hard-domain adoption ladder instead of pretending one support level fits all

Current Rust sources still say that safety-critical, embedded, GUI, and unevenly served domains experience the ecosystem differently.
At the same time, docs remain the preferred canonical reference, docs.rs publishes machine-usable rustdoc JSON, and Cargo/tooling work is increasingly aimed at evidence and witness-style tooling.

That combination suggests a stronger repo rule:
- a crate may be useful at **explore** level,
- still not be ready for **team default**,
- still not be ready for **air-gapped or regulated** use,
- and still need extra evidence before it deserves a high-support claim.

The new hard-domain adoption ladder makes that explicit across these tiers:
1. **explore**
2. **team default**
3. **shipping baseline**
4. **restricted / offline / mixed-language**
5. **regulated / safety-critical evidence-heavy**

It then maps the current frontier crates against those tiers so future passes stop flattening “works for me” into “worthy ecosystem support.”

## Main practical consequence

This pass still does **not** justify a major salience rerank.
The top frontier remains centered on:
- **P-0509 Pathfinder**,
- **P-0486 Debuggability Support**,
- **P-0538 Concurrency Contract**,
- **P-0472 Docs.rs Build Parity**,
- **P-0535 Dependency Lifecycle Transition**,
- **P-0489 Cargo Build-Dir Consumer Transition**,
- **P-0484 Toolchain & Target Support**,
- **P-0536 Crate Knowledge Pack**.

But it **does** justify a sharper practical queue:

1. **P-0509** — review-packet workflows and scenario packs
2. **P-0536** — pinned, cited, importable knowledge packs paired to those packets
3. **P-0486** — debug capability packets for the same receiver workflows
4. **P-0472** — docs.rs parity doctor and hosted/local gap bundles
5. **P-0489** — build-dir transition support for tooling consumers
6. **P-0535** — dependency transition and off-ramp packets
7. **P-0484** — target/toolchain truth for harder-domain adoption tiers
8. **P-0058** — native prerequisites / ABI provenance for offline and mixed-language cases

Interpretation:
- the repo now treats **knowledge-pack work** as closer to the front because pathfinder packets need pinned, cited, machine-usable support to stay trustworthy;
- supportive surfaces and hard-domain ladders are now part of what makes a crate “epic,” not extra polish;
- future passes should deepen those packet families before promoting more new sector lanes.

## Variety consequence

This pass also widened the practical scenario mix without widening the top frontier.
New pathfinder scenario stubs were added for:
- **safety-critical boundary selection**,
- **air-gapped enterprise registry + native support**,
- **robotics control-loop vs ops split**,
- **data/lakehouse open-table stack**.

These are intentionally broad and weird enough to keep the archive honest about the ecosystem’s real breadth.
But they remain subordinate to the horizontal control-plane queue unless they reveal a distinct evidence seam the frontier cannot absorb.

## What this pass says a worthy crate should provide other people

A serious crate should now usually provide:
- a **decision surface**,
- an **evidence surface**,
- a **review surface**,
- a **machine surface**,
- and a **drift / refusal surface**.

If it cannot say what those are, it is probably still too fuzzy to promote.
