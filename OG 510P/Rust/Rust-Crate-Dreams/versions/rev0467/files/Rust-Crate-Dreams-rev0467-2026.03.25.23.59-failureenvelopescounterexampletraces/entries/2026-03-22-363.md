# Entry 363 — trait-solver drift deepened around solver-lane truth, obligation classes, and minimization lineage for P-0442

This pass deepened **P-0442 Trait Solver Drift Witness Kit** instead of adding another general compile-fail harness, another nightly-only tracing workflow, or another semver-specific witness helper.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the active next-solver goal is explicitly about stabilization work for `-Znext-solver=globally`, expanding usage in lints and rustdoc, and publicly asking for testing;
- stable Rust 1.84 already enabled the next-generation trait solver for coherence, which means the ecosystem is already living with a mixed-lane transition instead of a clean future flip;
- the rustc dev guide now documents major behavioral and diagnostic differences in the new solver, including canonicalization-heavy evaluation, fixpoint handling of nested goals, and proof-tree-driven diagnostics;
- nightly/compiler docs still expose concrete lane differences such as overflow behavior under `-Znext-solver`;
- and the GSoC witness-generation work for `cargo-semver-checks` proved that generating witness programs and letting rustc decide hard type-level questions is now practical substrate, not pure theory.

Together these make one conclusion stronger: the worthy crate here is not just “run old and new rustc and diff stderr”.
It is a crate that helps other people inspect **which solver lane actually ran, what kind of obligation changed, whether the drift is semantic or only diagnostic, and how a minimized repro relates back to the original corpus**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still **not** another corpus runner.
It is a **stable support-contract layer** above corpus runners, generated witnesses, and future compiler substrate.

This pass promotes six P-0442 review objects into first-class status:

1. **comparison-lane receipt** — which solver lane actually ran (`legacy_only`, `coherence_default_only`, `global_preview`, or `mixed_unknown`);
2. **corpus-authority receipt** — where the case came from and what kind of expectation is authoritative;
3. **obligation-class report** — what category of trait-system question changed;
4. **diagnostic-normalization receipt** — what transforms were applied before declaring a difference diagnostic-only;
5. **minimization-lineage receipt** — how a reduced witness maps back to the source corpus and what context got dropped;
6. **solver-support-bundle manifest** — the compact handoff artifact joining those truths.

## Why these objects matter

Current Rust solver substrate is finally concrete enough that the archive should stop flattening solver-transition investigations:

- a stable result on 1.84 may already include next-solver behavior in coherence without proving full global-next-solver parity;
- a message-shape change can be real but still remain a diagnostic-only drift once normalization rules are recorded;
- witness-generation style cases can be invaluable without being the same authority class as imported `ui_test` or `trybuild` corpora;
- and a reduced repro can be perfect for issue filing while still needing explicit lineage back to the original case.

## New archive-level stance

For trait-system transition work, the archive should now prefer this layering:

1. **P-0442** for solver-lane truth, obligation classes, diagnostic normalization, and minimized witness lineage;
2. **P-0446** for Polonius / borrowck outcome drift;
3. **P-0244** and public-API readiness lanes for SemVer/public-surface witness use;
4. raw `ui_test` / `trybuild` / `compiletest_rs` for corpus execution substrate;
5. optional rustc tracing / proof-tree substrate as imported evidence rather than as the whole product.

That keeps the portfolio from minting another crate that merely says “nightly changed something” without clarifying what lane changed or how trustworthy the comparison was.

## What should count as a worthy crate contribution after this pass

A worthy trait-solver drift contribution should now be able to answer all of these cleanly:

1. **Which solver lane actually ran for this result?**
2. **What class of obligation changed?**
3. **Is the drift semantic, diagnostic, or scope-only?**
4. **What normalization happened before that verdict?**
5. **How does this minimized witness map back to the original source corpus?**

If a candidate crate cannot answer those questions, the archive should usually treat it as solver folklore rather than a serious support contract.
