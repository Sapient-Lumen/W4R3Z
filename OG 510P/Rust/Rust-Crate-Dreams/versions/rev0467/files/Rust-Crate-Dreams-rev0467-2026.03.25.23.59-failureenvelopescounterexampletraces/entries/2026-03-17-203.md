# Entry 203 — crate performance envelopes promoted as the performance-support lane

This pass added a new top-level proposal: **P-0517 Crate Performance Envelope Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing configuration scenarios, generic benchmarking, profiling evidence, hosted CI performance services, and receiver-facing performance contracts into one fake “better benchmark tooling” story.

## Why this moved now

Several current Rust signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good performance-support lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- **successor / off-ramp support** via **P-0515**,
- and **setup/configuration scenarios** via **P-0516**.

But it still lacked a good answer to:

- “Once a team already chose and configured a crate, what exactly does the crate hand them so they can understand the real performance tradeoff they are buying?”

That left the archive with better answers for **choice**, **setup**, **interop**, **failure**, and **migration** than for **performance expectations**, which is strange for Rust.

### 2. Official Cargo substrate makes this a packaging problem, not a missing-knobs problem

`cargo bench` already provides benchmark targets, custom harness support, and a stable command surface.
Cargo profiles already make optimization/debugging choices a first-class product surface, and the docs explicitly warn that surprising results are common enough that people should experiment and reevaluate over time.
The Cargo team also explicitly says plugins matter because Cargo cannot be everything to everyone.

That means the sharper question is no longer “how do we benchmark in Rust at all?” but “what receiver-facing artifact should sit above today’s benchmark and profile substrate?”

### 3. The current performance tool ecosystem is real but fragmented

Criterion provides statistically grounded wall-time benchmarking.
Iai-Callgrind provides instruction/cache-oriented measurement that remains useful in virtualized CI and can emit differential outputs.
Divan provides another modern stable benchmarking surface.
CodSpeed compatibility layers show teams are already trying to connect local suites to CI-hosted measurement without rewriting everything.

What is still missing is the boring pack that can say:

- these are the named workloads we care about,
- this is the metric you should trust for each one,
- these are the environment assumptions and caveats,
- these numbers are representative budgets,
- and this is how the crate’s performance envelope changed across releases.

### 4. Rust’s current official messaging makes “supportive performance surfaces” more plausible than before

The vision-doc work explicitly recommends more **supportive interfaces from crates**.
The 2025 survey says docs and source remain the main learning surfaces, while resource-usage and debugging issues remain visible productivity limits.
That combination makes it more credible to treat benchmark meaning, workload honesty, and measurement caveats as part of the crate’s product surface rather than as off-repo folklore.

## Current judgment

The worthy crate here is not:

- another benchmark runner,
- another profiler,
- another hosted regression service,
- another screenshot-heavy “perf dashboard”,
- or another generic config-scenario crate with some numbers attached.

The worthy crate is the boring receiver-facing performance layer that can hand other people:

1. one **perf pack**,
2. one **perf-surface receipt**,
3. one **perf-scenario report**,
4. one **perf-recipe manifest**,
5. one **perf-check report**,
6. one **perf-budget report**,
7. one **perf diff**,
8. and one explicit **manual-review boundary** when hardware noise or workload drift makes automation dishonest.
