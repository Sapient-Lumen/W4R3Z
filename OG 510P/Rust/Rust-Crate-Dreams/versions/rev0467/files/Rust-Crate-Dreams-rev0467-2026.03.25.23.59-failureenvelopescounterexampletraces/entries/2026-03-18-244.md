# Entry 244 — NuGet native interop shipkit deepening around RID coverage, loader routes, and deployment posture

This pass did **not** invent a brand-new .NET lane.
It sharpened **P-0499 NuGet Native Interop ShipKit** into a more believable shipping-contract crate.

## Why this moved now

The NuGet / .NET / Rust substrate is now real enough that the missing value is no longer just “please make Rust callable from C# somehow.”
The sharper gap is a **boring package and support contract above already-working authoring tools**:

- NuGet already documents native assets under `runtimes/<rid>/native`, and the SDK flattens directory structure under that path when copying to output. That means package layout is a real contract surface rather than folklore.
- Microsoft’s RID catalog keeps platform-asset naming explicit, and .NET 8 guidance now says the host determines RID-specific assets more strictly and recommends portable RIDs for package restore.
- The unmanaged library loading algorithm is explicit about resolver hooks, `AssemblyLoadContext`, and probing; plugin-host guidance now makes `AssemblyDependencyResolver` a first-class substrate rather than a niche trick.
- Native AOT already has its own interop rules, and .NET 10 changed single-file native-library search behavior, so “works in one ordinary app” no longer settles the shipping promise for special deployment modes.
- `.NET` interop best-practice guidance now prefers `LibraryImport` where possible, which means binding-generation truth and runtime-loading truth should stay joined rather than being treated as unrelated.
- `csbindgen` already provides real Rust→C# binding substrate, so the missing crate is no longer “a generator exists” but “what exact package and host promise are we making above it?”

So the gap is not “there is no Rust .NET interop tooling.”
The gap is that maintainers still rarely get one **reviewable NuGet bundle** that says:

- which RID assets actually shipped,
- what loader route downstream users are expected to take,
- and what deployment posture the package really has for ordinary runtime, plugin hosts, single-file publish, and Native AOT.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another binding generator, not another MSBuild helper, and not a giant cross-host .NET build platform.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-built native libraries published into NuGet packages and consumed from .NET**,
- above today’s NuGet native-asset layout, RID guidance, `csbindgen`, P/Invoke / `LibraryImport`, and .NET loading / deployment substrate,
- with three first-class review objects that were previously still too implicit:
  1. **RID coverage**
  2. **loader route**
  3. **deployment posture**

## Main judgment after the pass

A worthy NuGet-native shipkit should now provide not only a package layout, but also:

- explicit **RID-coverage truth** (`portable_rid_matrix_complete`, `rid_asset_gap`, `legacy_rid_graph_assumption`, etc.),
- explicit **loader-route truth** for default probing, custom `SetDllImportResolver`, and isolated plugin-host / `AssemblyDependencyResolver` paths,
- explicit **deployment-posture truth** for ordinary runtime, single-file publish, and Native AOT,
- and a compact review bundle that another person can inspect without recreating the whole MSBuild / NuGet / runtime pipeline.

That is a much sharper and more believable contribution than “yet another Rust-to-C# helper.”
