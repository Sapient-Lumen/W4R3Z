# Entry 335 — Service Readiness & Drain Contract Kit added for activation gates, readiness surfaces, health channels, shutdown triggers, drain policy, and in-flight fate

This pass added **P-0534 Service Readiness & Drain Contract Kit** instead of another web framework, another probe-endpoint helper, or another generic graceful-shutdown crate.

## Why this lane earned a serious pass

The archive already had better answers for:

- task supervision and restart,
- crate lifecycle surfaces,
- channel semantics,
- async runtime assurance,
- and runtime-handoff / incident-bundle work.

What it still lacked was a build-shaped answer to the service-transition question:

> “When is this service actually safe to advertise, how does it drain, and what happens to work that is already in flight?”

Current substrate is now strong enough to make that precise:

- Tower `Service` makes admission readiness concrete via `poll_ready` and warns that calling without readiness can error or panic;
- hyper explicitly defines graceful shutdown as stopping new requests while allowing in-flight requests to complete;
- axum exposes a `WithGracefulShutdown` serve future, proving the server-level hook is now ordinary substrate;
- tonic-health proves a concrete gRPC health surface exists, but not that it is the same as HTTP readiness or startup completion;
- Tokio’s graceful-shutdown guidance plus `TaskTracker` make stop/wait coordination concrete for async applications;
- `tokio-graceful-shutdown` proves there is appetite for structured shutdown trees and timeouts in real Tokio services.

That means a worthy crate here should not merely say “supports health checks and graceful shutdown.”
It should say **when traffic may begin, which readiness/health surfaces exist, what starts drain, how drain behaves, and what in-flight work can expect**.

## What moved this time

The main planning move was to stop treating “ready” or “healthy” as one blob.

This pass elevated six review objects into first-class status for **P-0534**:

1. **activation gate** — listener bound, dependency warmup, stable background work, manual flip, or composite;
2. **readiness surface** — internal admission readiness versus external ready/not-ready exposure;
3. **health channel** — HTTP/gRPC/admin/internal channels and their audiences;
4. **shutdown trigger** — signal, admin command, subsystem failure, deploy hook, or manual review;
5. **drain policy** — refusal posture, grace budget, keepalive behavior, and timeout aftermath;
6. **in-flight fate** — accepted request fate during drain and after timeout.

## Why this matters now

The ecosystem evidence is now sharp enough that the missing layer is no longer vague:

- `poll_ready` does not answer whether a load balancer should send traffic;
- a readiness endpoint does not prove dependency warmup or background-consumer stability;
- gRPC health does not automatically answer HTTP admission truth;
- graceful shutdown enablement does not automatically tell another team what timeout aftermath means;
- and shutdown triggers still vary between signals, admin commands, supervisor failures, and deployment hooks.

That means a worthy crate should not let one green “service ready” bit silently over-claim startup completion, probe meaning, or in-flight request fate.

## Main judgment after the pass

A worthy service-support contribution for Rust should now provide more than probe routes, signal handlers, or serve-with-graceful-shutdown helpers.
It should also provide:

- one explicit **activation-gate receipt**,
- one explicit **readiness-surface receipt**,
- one explicit **health-channel receipt**,
- one explicit **shutdown-trigger receipt**,
- one explicit **drain-policy receipt**,
- one explicit **in-flight-fate report**,
- plus the already-needed summary/diff/support-bundle surface.
