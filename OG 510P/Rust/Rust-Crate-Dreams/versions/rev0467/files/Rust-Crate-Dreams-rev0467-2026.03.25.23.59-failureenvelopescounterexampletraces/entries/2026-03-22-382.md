# Entry 382 — trusted-publishing tooling deepened around registry-policy imports, workflow-route identity, and authorization drift

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another generic supply-chain helper, CI OIDC wrapper, or provenance dashboard.

The lane chosen here was **P-0175 Trusted Publishing Tooling Kit**.
The archive already had a strong thesis, provider-capability matrices, claim-basis receipts, trigger reports, publish-mode receipts, rehearsal reports, drift diffs, and compact support-bundle vocabulary.
What it still lacked was a sharper answer to a harder downstream question:

> when somebody says “this crate publishes through crates.io trusted publishing”, what exactly should another maintainer receive so **registry-side policy**, **workflow route identity**, and **authorization drift** do not get flattened into one vague “OIDC is configured” story?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official crates.io, RFC, GitHub, GitLab, and Rust Infrastructure sources still converge on the same pressure point:

- RFC 3691 still defines the trusted-publishing model as an OIDC exchange that yields short-lived crates.io access tokens instead of long-lived API tokens;
- the January 2026 crates.io development update says trusted publishing now supports **GitLab CI/CD** in addition to GitHub Actions, but still only on **GitLab.com** rather than self-hosted GitLab;
- that same update says crates can now enforce **Trusted Publishing Only Mode** and that `pull_request_target` and `workflow_run` are blocked GitHub triggers for trusted publishing;
- current GitHub OIDC docs make `id-token: write` mandatory, distinguish caller workflow identity from reusable-workflow identity, and document `job_workflow_ref` / customized `sub` claim routes;
- current GitLab docs make `aud` explicit, keep `sub` configurable, expose `ci_config_ref_uri`, `ref_path`, runner/environment claims, and make host scope part of issuer identity;
- and the Rust Infrastructure Team’s January 2026 update shows Rust-project trusted-publishing settings being moved into **Infrastructure as Code**, which makes imported registry policy and repo-declared route policy more important to compare rather than assume are the same thing.

That combination makes one archive lesson sharper:

**A worthy trusted-publishing crate is not just “inspect some JWT claims and see whether the workflow passed.”**
**It is a reviewable contract for what the registry is configured to trust, what CI route identity was actually observed, what changed between two release paths, and what one portable bundle another maintainer can review without secrets.**

## Main repo judgment from this pass

The strongest next move for **P-0175** was to make three more receiver-facing review objects first-class:

1. **`registry-publisher-state.import.json`** — records what crates.io-side trusted-publisher configuration was imported for the package set: provider family, host scope, registered repository/project/workflow/environment tuple, TP-only posture, and observation source.
2. **`workflow-identity-route.receipt.json`** — records what release route identity was actually observed in CI: direct or reusable workflow, `id-token: write` posture, caller-vs-called workflow route, environment context, issuer/audience, and any provider-specific route claims such as `job_workflow_ref` or `ci_config_ref_uri`.
3. **`publish-authorization-drift.report.json`** — records what changed between two trusted-publishing bundles: registry state, provider/host scope, workflow route, subject/audience shape, trigger class, environment guard, TP-only posture, and whether the change remains compatible, blocked, or manual-review-only.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0492** still owns broader registry auth diagnosis;
- **P-0477** still owns post-publish receipt joining;
- **P-0015** still owns provenance/attestation publication;
- but **P-0175** owns the receiver-facing workflow for **trusted-publisher policy import, workflow-route identity, preflight/rehearsal coherence, and publish-authorization drift**.

That separation matters.
Otherwise the archive would quietly confuse “OIDC exists”, “the registry is configured”, “the workflow had some token claims”, “the run was rehearsed once”, and “this release path is reviewably authorized” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One imported registry-state receipt** that says what crates.io is actually configured to trust for the package set.
2. **One workflow-route receipt** that says what CI identity route actually ran, including reusable-workflow or config-file route when relevant.
3. **One claim-basis receipt** that keeps issuer/audience/subject facts visible without exporting secrets.
4. **One trigger verdict** that says why the release event is allowed, blocked, unsupported, or manual-review-only.
5. **One publish-mode receipt** that keeps TP-only, mixed-mode, and manual/token fallback distinct.
6. **One rehearsal report** that keeps observational facts separate from inferred policy coherence.
7. **One authorization-drift report** for release review so registry state, workflow route, claim shape, or TP-only posture changes can be compared over time.
8. **One portable trusted-publish support bundle** that another maintainer can archive, diff, and inspect without replaying secrets-bearing CI.

If a crate idea in this territory cannot supply those review objects, it is still probably just a CI OIDC helper, registry-auth doctor, provenance tool, or publish workflow template rather than the missing support layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **registry-side trust configuration** into **repo-local policy files**, or **some observed claim set** into **an honest workflow-route receipt**, or **one successful rehearsal** into **stable release authorization**.

Future passes should therefore keep asking:

1. what the registry is configured to trust,
2. what workflow route actually ran,
3. which provider-specific claims matter for that route,
4. what changed compared with the last good publish path,
5. and what one portable bundle another maintainer should receive.

That is a better use of repo time than inventing another JWT inspector, YAML linter, or supply-chain UI that still cannot hand someone an honest trusted-publishing support witness.
