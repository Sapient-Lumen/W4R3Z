# Entry 291 — text-input-kit sharpened around web edit-path truth, selection geometry, and accessibility mirrors

This pass returned to **P-0027 text-input-kit** because the lane had already become implementation-shaped around IME transactions, selection contracts, backend capability receipts, and replayable evidence — but it still left one dangerous blur available:

> a toolkit could claim that “text input works on native and web” while saying almost nothing about **which editing path is active**, how IME/candidate geometry is synchronized, or whether a canvas-backed editable surface still owes an explicit accessibility mirror.

## What moved this time

Several fresh ecosystem signals made that blur harder to tolerate:

- fresh `winit` issue traffic in March 2026 shows that even native IME behavior still needs normalization and explicit receipts across Windows, X11, and macOS;
- the active Web/WASM IME issue in `winit` still says canvas-based IME support currently falls back to hidden-input forwarding because the canvas cannot receive composition events directly;
- the issue itself now points at the **EditContext API** as the plausible long-term web route, but only once browser support is broader;
- MDN’s EditContext docs now make explicit that custom editable regions owe the OS text service **selection changes**, **text-location / bounds updates**, and — for canvas-backed content — a separate accessibility representation;
- AccessKit already has text-position and text-selection vocabulary, so the archive can no longer pretend that “a11y later” is an honest default for custom editors;
- current field reporting on Rust GUI libraries still reads like an ecosystem where IME provisional states, candidate-window placement, and screen-reader-visible text often vary sharply by toolkit.

That combination means the missing crate is no longer only “a shared transaction/selection engine.”
It is also a **shared edit-path / geometry / mirror honesty layer** above today’s event, layout, and accessibility substrate.

## Main planning move

This pass promoted two more review objects to first-class status for **P-0027**:

1. **web-edit-path truth** — whether the active path is native-window IME, web hidden-input fallback, experimental EditContext, toolkit-native bridge, or something else, and which route actually owns focus/composition state,
2. **selection-geometry truth** — whether caret/selection/character bounds are being synchronized precisely enough for IME candidate windows and composition UI, whether provisional text is rendered inline or detached, and whether an accessibility mirror is present when the visible surface is custom-rendered.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a canvas or GPU text surface can receive committed text somehow,
- a toolkit can truthfully say that users can type,
- and yet candidate UI still appears in the corner, provisional text still renders detached or not at all, fullscreen behavior still degrades, or assistive technology still cannot inspect the text that sighted users see.

That is not secondary polish.
It is the difference between “characters eventually land in the widget” and “this text system is reviewably usable.”

## Main judgment after the pass

A worthy text-input crate contribution for Rust should now provide more than transactions, selections, and one generic capability badge.
It should provide:

- one explicit **web-edit-path receipt**,
- one explicit **selection-geometry report**,
- one explicit statement of whether provisional text and candidate anchoring are **inline, approximate, detached, or manual-review-only**,
- and one explicit statement of whether a custom-rendered editor still owes an **offscreen / parallel accessibility mirror**.

That is a better answer to the current ecosystem than either:

- “the toolkit has a text box,”
- “winit exposes IME APIs,”
- or “Web text input works because the hidden-input fallback eventually commits text.”
