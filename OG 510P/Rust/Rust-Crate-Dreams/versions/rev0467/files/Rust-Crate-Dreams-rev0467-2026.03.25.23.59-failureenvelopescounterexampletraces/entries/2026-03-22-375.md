# Entry 375 — debuggability support deepened around backend observations, source-material handoff, and portable debug-support bundles

This pass continued the archive’s current strategy of **deepening one high-value support-contract lane until it looks genuinely buildable** instead of opening another debugger launcher, symbol portal, or IDE integration lane.

The lane chosen here was **P-0486 Debuggability Support Contract Kit**.
The archive already had a solid thesis, posture vocabulary, artifact handoff, backend-coverage boundaries, and source-lookup impact reporting.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when a team says “this release is debuggable,” what exactly should another engineer receive so artifact richness, checked debugger lanes, source lookup, and portable handoff do not get flattened into one vague claim?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Rust sources still pull in the same direction:

- the 2026 debugging survey says Rust is not yet where it should be on multi-debugger support, visualizers, async debugging, or Rust expression evaluation, and explicitly notes that debugging can regress across debugger versions and Rust internal changes;
- the March 2026 Rust challenges write-up says debugging remains a domain-scaled pain point, especially where optimized builds, cross targets, or long iteration cycles complicate ordinary workflows;
- current Cargo profile docs keep `debug`, `split-debuginfo`, and `strip` explicit and warn that Cargo and `rustc` still differ in `split-debuginfo` defaults;
- current `rustc` codegen docs keep the platform split concrete (`pdb`, `dSYM`, `dwo`, `dwp`) and say `strip = debuginfo` may preserve backtraces while still making interactive debugging ineffectual;
- the Rust Reference keeps `#[debugger_visualizer]` a stable language surface;
- Cargo’s build-cache docs and the Build Dir Layout v2 call-for-testing keep reinforcing that final-artifact location, intermediate layout, and handoff discipline are related but not identical truths.

That combination makes one archive lesson sharper:

**A worthy debuggability crate is not just “discover symbols” or “launch a debugger.”  
It is a reviewable contract for what broad support posture a build has, which debugger lanes were actually checked, what source material is needed for lookup, what sidecars and visualizers are required, and how that story changed across revisions.**

## Main repo judgment from this pass

The strongest next move for **P-0486** was to make three more receiver-facing review objects first-class:

1. **`backend-observation.receipt.json`** — record exact debugger family / OS / version / capability observations instead of letting artifacts imply universal backend support.
2. **`source-material.manifest.json`** — record what source archive, sysroot source pack, or remapped-path context is needed for lookup after privacy-oriented path changes.
3. **`debug-support-bundle.manifest.json`** — give another engineer one compact pack for posture, sidecars, backend evidence, source materials, share posture, and manual-review gaps.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0491** still owns visualizer compatibility work;
- **P-0493** still owns source-path / lookup diagnosis;
- **P-0101** still owns crash-artifact and symbolication workflows;
- but **P-0486** owns the receiver-facing workflow for **broad posture, checked debugger lanes, source-material handoff, and portable review bundles**.

That separation matters.
Otherwise the archive would quietly confuse “the build contains debug-rich artifacts” with “another reviewer can now tell what this release honestly supports.”

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One broad support-posture verdict** that does not over-read narrower evidence.
2. **One exact backend-observation receipt** saying which debugger family / version / capability lane was really checked.
3. **One symbol and visualizer handoff map** that keeps required sidecars explicit.
4. **One source-material manifest** that says what lookup material exists, where it lives, and whether it is safe to share.
5. **One source-lookup impact report** that keeps privacy/path changes separate from overall debugger posture.
6. **One portable debug-support bundle** that another reviewer can archive, diff, or hand to downstream users.

If a crate idea in this territory cannot supply those review objects, it is still probably a launcher, a symbol helper, or raw debugger substrate rather than the missing contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **artifact richness** into **portable debuggability support**.

Future passes should therefore keep asking:

1. what broad posture is actually promised,
2. which backend lane was really checked,
3. what source material is needed for lookup,
4. what can be safely shared,
5. and whether the exported bundle preserves those truths.

That is a better use of repo time than inventing another debugger launcher, symbol browser, or “debug metadata dashboard.”
