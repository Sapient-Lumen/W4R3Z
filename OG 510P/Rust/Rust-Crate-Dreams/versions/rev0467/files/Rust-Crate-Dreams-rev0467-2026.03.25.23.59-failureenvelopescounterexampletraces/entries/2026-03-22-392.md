# Entry 392 — build-observability deepening promoted cargo-event-stream into a real support-contract lane

This pass stayed focused.
It did **not** add another broad ecosystem rerank or a spray of new proposal IDs.
Instead it deepened one older but increasingly justified lane:

**P-0042 cargo-event-stream**.

## Why this lane earned a serious refresh now

Fresh primary signals make the build-observability seam much sharper than it used to be:

- the Cargo 1.93 development-cycle notes explicitly name **structured logging** as an active project-goal direction;
- the build-analysis goal says Cargo wants to record build metadata across invocations and expose `cargo report` commands for timing and rebuild reasons;
- the March 2026 build-dir-layout-v2 testing call says many projects still rely on unspecified Cargo details because features are missing;
- Cargo’s external-tools docs still warn that `--message-format=json` only controls Cargo and rustc output and does **not** control arbitrary output from procedural macros or other tools;
- Cargo’s command docs now make rendering-policy choices like `json-render-diagnostics` explicit.

Together those sources say the missing value is no longer “invent a secret better JSON mode for Cargo.”
The missing value is a stable crate-level handoff for:

1. native Cargo/rustc JSON events,
2. foreign output that contaminates the stream,
3. rendering-policy truth,
4. session identity and provenance,
5. portable redacted bundles that another tool or reviewer can consume.

## Main judgment after the refresh

**P-0042 cargo-event-stream** is now stronger as a **support contract above evolving upstream build logging** than as a raw wrapper around `cargo build`.

That means the proposal should own:

- event-envelope normalization,
- foreign-output containment,
- session manifests,
- rendering-policy receipts,
- redaction receipts,
- and portable stream bundles.

It should **not** try to own:

- Cargo’s future built-in structured logging recorder,
- historical trend warehouses,
- support-grade rebuild-cause bundles,
- or whole-run replay containers.

## What should count as a worthy crate contribution in this lane now

A worthy build-event crate should hand other people:

1. **one stable event envelope** for build-session tooling,
2. **one honest foreign-output story** instead of broken NDJSON folklore,
3. **one rendering-policy receipt** instead of guessing whether diagnostics were embedded or Cargo-rendered,
4. **one session manifest** that says what command, toolchain, target, and workspace lane produced the stream,
5. **one portable bundle** that another tool can inspect after redaction.

If a candidate crate cannot do those things, the archive should usually treat it as a parser helper or wrapper utility, not an epic ecosystem contribution.
