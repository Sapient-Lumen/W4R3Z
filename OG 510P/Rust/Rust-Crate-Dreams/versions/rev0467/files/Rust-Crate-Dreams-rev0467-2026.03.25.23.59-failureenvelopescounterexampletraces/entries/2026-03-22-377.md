# Entry 377 — rebuild-causality work deepened around comparison scope, artifact-route drift, and portable support bundles

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another generic Cargo performance helper.

The lane chosen here was **P-0469 Cargo Rebuild Explanation Kit**.
The archive already had a strong thesis, baseline-authority receipts, exactness reporting, evidence-source imports, reverse-impact reporting, and a stable bundle story above Cargo’s newer build-analysis substrate.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when somebody says “this build rebuilt because of X”, what exactly should another engineer receive so **comparison scope**, **artifact-route drift**, **adjacent tool-only context**, and **portable support bundles** do not get flattened into one vague explanation?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Cargo and Rust sources still converge on the same pressure point:

- the 2025 State of Rust survey still reports resource usage, especially compile time and storage use, among the biggest productivity problems;
- the March 2026 Rust challenges write-up again calls out build times as persistent friction;
- current unstable Cargo docs now document persisted build-analysis sessions plus `cargo report sessions`, `cargo report timings`, and `cargo report rebuilds`;
- the Cargo 1.94 development-cycle update makes those reports feel more like a real user-facing substrate than an internal experiment;
- the `Relink don’t Rebuild` goal explicitly says reverse dependencies still rebuild after edits that would not trigger that fanout in languages with stricter interface separation;
- the build-dir-layout goal and the March 2026 Build Dir Layout v2 testing call both emphasize that build-dir / target-dir shape and finer-grained locking are active upstream concerns;
- Cargo’s build-cache docs now keep final artifacts in `target-dir` and intermediate artifacts in `build-dir` as first-class separate routes;
- and rust-analyzer still documents a separate `cargo.targetDir` escape hatch that avoids locking at the cost of duplicated artifacts.

That combination makes one archive lesson sharper:

**A worthy rebuild-explanation crate is not just “show me the reason a crate rebuilt.”  
It is a reviewable contract for whether two sessions are in scope to compare at all, how build and target routes changed, what adjacent tool-only context should be imported rather than over-read, and what one portable bundle another reviewer should actually receive.**

## Main repo judgment from this pass

The strongest next move for **P-0469** was to make three more receiver-facing review objects first-class:

1. **`comparison-scope.receipt.json`** — records whether the candidate and baseline are comparable across command family, profile, targets, workspace selection, wrappers, and artifact routes.
2. **`artifact-route-drift.report.json`** — records when `build-dir`, `target-dir`, rust-analyzer target-dir, wrapper hash lanes, or final-vs-intermediate routes changed and how that should constrain reuse claims.
3. **`rebuild-support-bundle.manifest.json`** — gives another engineer one compact pack for rebuild receipt, unit causes, comparison scope, route drift, evidence sources, exactness, baseline authority, reverse-impact, and imported adjacent-lane context.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0494** still owns compile-time-deps / editor / tool-surface parity as a primary problem;
- **P-0490** still owns blocked progress and lock-wait truth;
- **P-0035** still owns historical warehousing;
- but **P-0469** owns the receiver-facing workflow for **comparison-scope gating, artifact-route drift, and one portable rebuild-causality bundle**.

That separation matters.
Otherwise the archive would quietly confuse “different command lane”, “different cache route”, “tool-only context”, and “real rebuild cause” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One comparison-scope receipt** that says whether the compared sessions actually belong to the same explanatory lane.
2. **One artifact-route drift report** that says whether build-dir / target-dir / wrapper / tool-owned route changes may have altered reuse context.
3. **One baseline-authority receipt** that still explains why this comparison was chosen.
4. **One unit-rebuild explanation surface** that keeps observed causes and conservative inference separate.
5. **One reverse-impact report** that keeps fanout separate from proven interface change.
6. **One portable rebuild-support bundle** that another reviewer can archive, diff, or attach to CI and issue reports.
7. **One manual-review zone** whenever command-family drift, artifact-route drift, or imported tool-only context outruns what the bundle can honestly prove.

If a crate idea in this territory cannot supply those review objects, it is still probably a profiler, warehouse, contention witness, or tool-parity import lane rather than the missing support-contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **comparison scope** into **baseline choice**, or **artifact-route drift** into **observed rebuild cause**, or **adjacent tool-only context** into **proof**.

Future passes should therefore keep asking:

1. are these two sessions really in scope to compare,
2. which build/target/tool routes changed,
3. what came from an adjacent lane rather than this one,
4. what one portable bundle another reviewer should receive,
5. and where manual review still begins.

That is a better use of repo time than inventing another timing dashboard, cache cleaner, or Cargo wrapper that cannot export a reviewable explanation contract.
