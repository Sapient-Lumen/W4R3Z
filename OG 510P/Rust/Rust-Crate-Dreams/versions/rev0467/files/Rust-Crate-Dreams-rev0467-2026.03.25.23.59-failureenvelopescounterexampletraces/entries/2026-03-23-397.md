# Entry 397 — safety-contract consumption now needs authority receipts, consumer-coverage matrices, and semantic-lane honesty

This pass focuses on one safety-critical / verification lane that already had strong motivation but still lacked a tight artifact contract.
It deepens:

**P-0453 Safety Contract Consumer Kit**.

## Why this lane earned a serious refresh now

The repo already had the right instinct: Rust’s emerging contract substrate should produce portable snapshots, diffs, and runtime-check receipts.
What it still left too vague was the hardest review question:

> “Which contracts came from what authority, which downstream tools actually consumed which parts of that contract surface, and under what semantic lane or caveats?”

Current sources make this question much sharper than before:

- the std-contracts project goal still says contracts should support **opt-in runtime checks** and also provide a **compiler interface for external tools** to retrieve annotated contracts;
- the same goal reports roughly **200 functions** already annotated and verified in the `verify-rust-std` fork;
- `verify-rust-std` is explicitly **tool agnostic** and currently accepts **Flux, GOTO Transcoder (ESBMC), Kani, and VeriFast**;
- Kani’s current contract docs show a concrete consumer lane in which verified contracts can replace function bodies via `stub_verified`, and recent Kani releases keep expanding contract support;
- other accepted or adjacent tools clearly work in different semantic styles: Flux as refinement typing, Creusot as deductive verification via Why3, and VeriFast as modular separation-logic symbolic execution for unsafe Rust.

Together these say the sharper missing crate is not “one contract format to rule them all” and not “translate every verifier into one semantic truth”.
It is a **reviewable consumer layer** for:

- **contract authority**,
- **consumer coverage**,
- **semantic-lane posture**,
- and **portable contract-consumption bundles**.

## Main judgment after the refresh

**P-0453** is now stronger as a **contract-consumption honesty lane**.

That means a worthy crate in this lane should explicitly own:

- `contract-authority.receipt.json`,
- `consumer-coverage.matrix.json`,
- `semantic-lane.report.json`,
- plus bundles that keep extraction authority, runtime-check results, downstream-tool consumption, and semantic caveats separate.

It should **not** try to own:

- the contract language itself,
- all proof obligations inside every downstream verifier,
- or a fictional claim that runtime checks, bounded model checking, refinement typing, and separation-logic proofs are interchangeable.

## What should count as a worthy crate contribution in this lane now

A worthy safety-contract crate should now hand other people:

1. **one authority receipt** that says which contract clauses came from compiler-native attributes, imported snapshots, manual annotations, or tool-specific substrate,
2. **one consumer-coverage matrix** that says which tools or modes consumed which clauses fully, partially, abstractly, or not at all,
3. **one semantic-lane report** that says whether the current result came from runtime checks, bounded model checking, deductive verification, refinement typing, separation logic, or another lane,
4. **one runtime-check / proof / export bundle** that keeps those lanes separate instead of silently merging them,
5. **one portable bundle** another team can reopen later without reverse-engineering contract folklore from compiler PRs, verifier docs, and issue threads.

If a candidate crate cannot do those things, the archive should usually treat it as verifier substrate, proof tooling, or project-specific glue — not the missing epic consumer layer.
