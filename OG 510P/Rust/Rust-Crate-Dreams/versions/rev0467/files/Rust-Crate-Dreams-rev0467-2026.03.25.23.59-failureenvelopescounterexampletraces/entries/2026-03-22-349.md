# Entry 349 — build-script delegation deepened around unit topology, output lanes, override authority, and delegation drift for P-0508

This pass deepened **P-0508 Cargo Build Script Delegation Kit** instead of adding another native-probe helper, another generic `build.rs` wrapper, or another “declarative builds someday” note.

## Why this lane earned another pass now

Fresh official Cargo signals line up unusually well:

- build-script docs already make order-sensitive directives, `OUT_DIR`, metadata passing, and `links`-override behavior explicit;
- Cargo external-tools docs already expose machine-readable build observations;
- unstable Cargo now documents **metabuild**, **multiple build scripts**, and **any build script metadata**;
- the 2025 GSoC work explicitly says the route toward reusable delegated build logic runs through multiple-build-scripts, deterministic unit ordering, and separate output directories;
- Cargo 1.93’s development notes say any future artifact-dir build-script bridge must reason about collision checking and concurrent safety;
- and Cargo is explicitly trying to reduce the need for users to write build scripts at all.

Together these make one conclusion stronger: a worthy ecosystem contribution here is not just “help me write `build.rs`.” It is a crate that helps other people inspect **which build units existed, which unit owned each output lane, whether live execution or an override was authoritative, what bridge posture was really in play, and what drifted across revisions**.

## Main judgment after the pass

The strongest near-term contribution in this lane is **not** another build helper.
It is a **delegated-build support contract layer** above handwritten `build.rs`, metabuild, multi-script packages, `links` overrides, and future artifact-bridge substrate.

This pass promotes six P-0508 review objects into first-class status:

1. **unit-topology receipt** — what build units exist and in what order;
2. **output-lane receipt** — which metadata/env/generated files/artifacts each unit owns;
3. **override-authority receipt** — whether live execution, config override, or delegate package policy was authoritative;
4. **delegate-bridge report** — where unstable artifact or bridge posture still blocks strong support claims;
5. **delegation-drift diff** — what changed across revisions or toolchains;
6. **build-script support bundle manifest** — the portable review bundle joining those facts.

## Why these objects matter

Current Cargo substrate is finally specific enough that the archive should stop flattening it:

- a build can succeed while still leaving **unit ownership** of outputs ambiguous;
- a distro or workspace can skip live probing with a `links` override while support docs still incorrectly talk as if `build.rs` ran;
- a multi-script package can export distinct `OUT_DIR` surfaces while downstream users still only see “the crate has a build script”;
- and an artifact-staging experiment can appear to work locally while still lacking **collision authority** strong enough for a receiver-facing support claim.

## New archive-level stance

For delegated build-time work, the archive should now prefer this layering:

1. **P-0508** for unit topology, output-lane ownership, override authority, bridge posture, and drift;
2. **P-0046** for build-script diagnostics and human-scale summaries;
3. **P-0059** for hermetic replay/testing of buildscript behavior;
4. **P-0484** when the hard problem is host-vs-target support truth rather than delegated build ownership;
5. native dependency / artifact lanes when the hard problem is downstream packaging or probe policy rather than delegated build execution.

That keeps the portfolio from minting another crate that merely says “uses delegated build scripts” without clarifying what actually ran or who authored the authoritative outputs.

## What should count as a worthy crate contribution after this pass

A worthy delegated-build contribution should now be able to answer all of these cleanly:

1. **What build units exist, and what deterministic ordering basis do they rely on?**
2. **Which metadata/env/generated files/artifacts belong to which unit?**
3. **Did a live build-script run produce the authority, or did config/delegate policy replace it?**
4. **Which support claims depend on unstable bridge substrate or unresolved collision authority?**
5. **Can another engineer compare the delegated-build story across revisions without reverse-engineering every log by hand?**

If a candidate crate cannot answer those questions, the archive should usually treat it as delegated-build folklore rather than a serious support contract.
