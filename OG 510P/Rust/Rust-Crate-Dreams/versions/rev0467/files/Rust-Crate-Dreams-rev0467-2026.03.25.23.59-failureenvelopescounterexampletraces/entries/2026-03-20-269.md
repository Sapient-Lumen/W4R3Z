# Entry 269 — crate upgrade support sharpened around native import truth and fixup posture

This pass came from a deeper donor read rather than from trying to mint more upgrade hazards.
The best transfers were the ones that made the lane **less willing to fake certainty**.

## What moved this time

Two unrelated datacubes kept pointing at the same missing discipline inside **P-0514 Crate Upgrade Pack Kit**:

- **Rust-Needs-and-Dreams / Cargo Report Kit** made the strongest case that native tool/report imports should stay visibly separate from later normalization and prose summary, especially when stable and unstable Cargo lanes coexist.
- **GlassTTY** made the strongest case that “a tool can perform an edit” and “the lane permits unattended execution” are different truths and need different artifacts.

Both moves apply directly to release-to-release upgrade support.

## Main planning move

The previous passes already established:

- **hazard authority**,
- **source lineage**,
- **hazard arbitration**,
- **package-scope truth**,
- and **active follow-through state**.

This pass adds two sharper review objects above them:

1. **native import truth** — which upgrade facts came from machine-native tool/report surfaces, how they were consumed, and whether the underlying lane was stable, unstable, external, or mixed;
2. **fixup posture truth** — whether an observed fix is manual-only, suggestion-only, approval-required, or eligible for some bounded autonomous step.

## Why this matters

Without **native import truth**, the crate can accidentally flatten:

- verbatim `cargo semver-checks` output,
- normalized `cargo fix` or `rustfix` extraction,
- `cargo metadata` workspace/package truth,
- future Cargo-native report replay,
- and maintainer-authored release prose

into one fake “imported evidence” blob.
That is the wrong shape.
A downstream reviewer should be able to tell **what was natively imported**, **what was normalized later**, and **what stayed advisory-only**.

Without **fixup posture truth**, the crate can accidentally flatten:

- “a source rewrite exists,”
- “the rewrite was observed once under review,”
- “manifest/docs/config follow-through still remains,”
- and “the lane permits only a bounded or approval-gated sequence”

into one polished “automation available” claim.
That is also the wrong shape.
Sometimes the right answer is **approval-required single action** or **manual-only**, even when automation substrate exists.

## Main judgment after the pass

A worthy upgrade-support crate should now provide **more than hazard classes, source lineage, package scope, and fix receipts**.
It should also provide:

- **import receipts** that keep native tool/report truth separate from later normalization and summary,
- **fixup posture reports** that say whether a fix is manual-only, approval-required, or narrowly auto-runnable,
- and explicit downgrade rules when uncertain or partial state appears.

That makes the lane more honest in two places where migration support usually starts lying:
summary replaces native import, and automation existence gets mistaken for permission to run.
