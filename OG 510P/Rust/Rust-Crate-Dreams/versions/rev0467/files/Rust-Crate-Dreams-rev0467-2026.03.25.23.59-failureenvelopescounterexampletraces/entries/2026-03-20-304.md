# Entry 304 — schema-compatibility-workbench-kit sharpened around comparison-basis, compatibility-profile, finding-strength, and policy-decision truth

This pass returned to **P-0124 Schema Compatibility Workbench Kit** because the archive still left one familiar and costly blur too available:

> a team could truthfully say “no breaking schema changes” while meaning several very different things — that Buf passed under one category, that oasdiff found only warnings below the fail threshold, that current instances validated against a new JSON Schema, or that a registry subject accepted a latest-only compatibility check.

## What moved this time

Several current schema and Rust signals make that blur harder to excuse:

- Buf’s breaking docs now make Protobuf compatibility a formal review surface with distinct categories like `FILE`, `PACKAGE`, `WIRE_JSON`, and `WIRE`;
- oasdiff is explicit that some findings are definite breaking changes (`ERR`) while others are only potential (`WARN`), and that ignore files plus fail thresholds shape the final gate result;
- Rust’s `jsonschema` crate now gives fast standards-aware validation and structured output across multiple drafts, but that is still validation substrate rather than one universal compatibility semantics;
- Confluent’s compatibility docs and API are explicit that results depend on the subject/global mode, latest-only versus transitive history, optional normalization, and optional verbose reasons;
- Schemars says generated schemas should match Serde/`serde_json` serialization meaning, which means generated-schema checks already have a non-trivial basis story;
- the Rust `schema-registry-compatibility` crate already proves there is real native compatibility substrate, including seven compatibility modes, but still not one shared receiver-facing review contract above it.

That combination means the missing crate is no longer best described as “some schema diff tooling”.
It is better described as a **reviewable schema-compatibility contract** above today’s validators, diff engines, and registry checks.

## Main planning move

This pass promoted four first-class review objects for **P-0124**:

1. **comparison-basis truth** — what exact old/new surfaces were compared, from where, with what normalization and history scope;
2. **compatibility-profile truth** — which engine/profile/category/mode defined compatibility for this run;
3. **finding-strength truth** — whether a result is mechanically definite, only potential, witness-backed, validation-only, or still manual-review territory;
4. **policy-decision truth** — which ignore lists, waivers, thresholds, or review choices produced the final gate result.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “Buf passed”,
- another maintainer can truthfully say “the registry compatibility API accepted the candidate schema”,
- a reviewer can truthfully say “current examples validate under the new JSON Schema”,
- and a downstream team can still be unable to tell whether the result was latest-only instead of transitive, wire-only instead of generated-source-sensitive, warning-bearing instead of definite, or green only because certain findings were ignored.

That is not a wording nit.
It is the difference between “schema tooling exists” and “another team can review the actual compatibility claim they are being asked to trust”.

## Main judgment after the pass

A worthy schema-compatibility contribution for Rust should now provide more than diff output and a green CI badge.
It should also provide:

- one explicit **comparison-basis receipt**,
- one explicit **compatibility-profile receipt**,
- one explicit **finding-strength report**,
- and one honest **policy-decision report**.
