# Entry 376 — toolchain/target support deepened around imported authority, public docs surface, and portable support bundles

This pass continued the archive’s current strategy of **deepening one top-ranked support-contract lane until it looks genuinely buildable** instead of opening another cross-target bootstrapper, installer wrapper, or CI matrix helper.

The lane chosen here was **P-0484 Toolchain & Target Support Contract Kit**.
The archive already had a strong thesis, support-class vocabulary, target-readiness receipts, prerequisite manifests, exercise-scope reports, artifact-route receipts, and host/target topology reporting.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when a project says “we support this toolchain/target lane”, what exactly should another engineer receive so **upstream authority**, **project-local support promises**, **public docs surface**, and **portable handoff** do not get flattened into one vague claim?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Rust sources still pull in the same direction:

- the January 2026 safety-critical write-up explicitly asks for target-focused readiness checklists that translate target-tier facts into practical adoption guidance;
- the March 2026 Rust challenges write-up says cross-compilation friction, `no_std` ecosystem gaps, and other domain-specific maturity issues remain real pain points for experienced teams;
- rustup 1.29.0 makes environment shape more concrete again by adding official Solaris hosts and improving `rust-analyzer` PATH fallback behavior;
- rustup’s override docs remain explicit that `path` toolchains ignore `components`, `targets`, and `profile`;
- current Cargo docs keep `target-dir` and `build-dir` separate and configurable, which matters for artifact routes and host/target interpretation;
- docs.rs metadata/build docs make explicit target lists, default-target behavior, sandbox limits, and hosted-build constraints concrete;
- and the October 2025 docs.rs default-target change proved that a project’s visible public docs surface can drift even when the project never wrote explicit target metadata.

That combination makes one archive lesson sharper:

**A worthy toolchain/target support crate is not just “show me supported targets.”  
It is a reviewable contract for what came from upstream authority, what the project itself promises, what docs.rs is publicly exposing, and what one portable bundle another engineer should archive or review.**

## Main repo judgment from this pass

The strongest next move for **P-0484** was to make three more receiver-facing review objects first-class:

1. **`upstream-support-authority.import.json`** — record imported facts from Rust-project target tiers, rustup-supported hosts, docs.rs defaults, and Cargo path/config rules instead of letting those facts silently masquerade as project-local promises.
2. **`public-docs-surface.receipt.json`** — record what docs.rs is actually exposing, whether defaults were implicit, and which hosted limits shaped that surface.
3. **`toolchain-support-bundle.manifest.json`** — give another engineer one compact pack for local support contract, imported authority, docs posture, target-readiness, prerequisites, topology, route, and manual-review gaps.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0472** still owns docs.rs parity and hosted-build reproduction;
- **P-0036** still owns MSRV policy activation and command-family floor truth;
- lock-contention and linker-lane work still own blocked progress and native-build failure diagnosis;
- but **P-0484** owns the receiver-facing workflow for **imported support authority, project support class, public docs surface, and portable toolchain/target support bundles**.

That separation matters.
Otherwise the archive would quietly confuse “officially available”, “publicly documented”, and “project-supported”.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One imported-authority receipt** that says which support-shaping facts came from Rust-project policy, rustup, docs.rs, or Cargo docs.
2. **One local support contract** that says what the project itself promises after interpreting those imported facts.
3. **One public-docs-surface receipt** that keeps hosted docs visibility separate from runtime/test/device support.
4. **One target-readiness report** that still keeps tier, prerequisites, tested environment, blockers, and exercise scope explicit.
5. **One portable support bundle** that another reviewer can archive, diff, or hand to downstream integrators.
6. **One manual-review zone** whenever upstream availability, docs exposure, and project-local support diverge.

If a crate idea in this territory cannot supply those review objects, it is still probably a matrix visualizer, bootstrap helper, or raw upstream substrate rather than the missing contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **upstream authority** into **project support**, or **public docs surface** into **target readiness**.

Future passes should therefore keep asking:

1. what upstream fact was imported,
2. what the project actually promises,
3. what docs.rs is publicly exposing,
4. what one portable bundle another reviewer should receive,
5. and where manual review still begins.

That is a better use of repo time than inventing another target matrix, target installer wrapper, or hosted support dashboard.
