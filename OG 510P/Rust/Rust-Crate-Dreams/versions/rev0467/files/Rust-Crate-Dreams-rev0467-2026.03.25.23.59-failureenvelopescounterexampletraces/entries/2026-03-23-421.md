# Entry 421 — compile-iteration deepened around activation boundaries, stale-code residency, and explicit handoff truth

This pass chose to **deepen P-0537 Compile Iteration Feedback Kit** again instead of opening another watcher, dev-server, or “Rust hot reload” lane.

The sharper question was:

> once a dev-loop bundle says an edit was patch-eligible and names the reload surface, how does it also say **when the new code actually becomes active**, **what old code may continue running anyway**, and **whether continuity came from true persistence, explicit handoff, or simple wishful thinking**?

## Why this deepening pass earned a full revision

Fresh sources made the next missing layer concrete:

- the March 2026 Rust challenges write-up still treats compile time as a universal productivity tax and explicitly names hot reloading and faster linking as high-leverage mitigations;
- the active **Relink don’t Rebuild** goal still shows that even implementation-only edits often fail to stay on the strongest fast path today;
- Dioxus hot-reload docs now distinguish RSX reload, asset reload, and experimental Rust hotpatching, and explicitly say Subsecond currently only tracks the “tip” crate;
- current `subsecond` docs say globals/statics/thread-locals have important limits, including thread-local reset risk in the tip crate and no supported struct hot-reload when layout changes;
- current `chaud` docs say hot-reloaded code only becomes active once a `#[chaud::hot]` function is called and that old code can continue via function pointers or trait objects;
- current `hot-lib-reloader` docs say dynamic-library reloads need careful handling for signatures, layout-shared types, global state, and `TypeId`-sensitive systems, and they explicitly expose reload events plus serialize/deserialize handoff patterns.

That means the next worthy move for **P-0537** is not merely stronger “state continuity.”
It is to make **activation boundaries** and **stale-code residency** first-class review artifacts.

## Main judgment after this pass

The top frontier still begins:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But **P-0537** is stronger now because the archive no longer stops at:

- reload surface,
- restart ceiling,
- latency budget,
- edit scope,
- fast-path barriers,
- and coarse state continuity.

It now has a clearer product shape for:

- **activation-boundary reports**,
- **stale-code-risk reports**,
- **reload-event / handoff honesty**,
- **entrypoint-gated activation vs global switch distinctions**,
- and portable bundle inventory that keeps route truth, continuity truth, and live-code truth separate.

## What should count as a worthy crate contribution in this lane now

A worthy compile-iteration crate should now provide other people:

1. **one activation-boundary report** that says whether fresh code is live immediately, only at a reloadable entrypoint, only after a manual handoff, or only after restart;
2. **one stale-code-risk report** that says whether old code can linger in function pointers, trait objects, already-running tasks, thread-local copies, or type-identity-sensitive stores;
3. **one explicit handoff story** so “state survived reload” is not over-read when it was really serialized, rebuilt, rebound, or reinitialized;
4. **one separation between patch route and activation route** so a successful rebuild or dylib swap is not mistaken for a completed code takeover;
5. **one separation between continuity and live-code truth** so “the state is still there” does not imply that every call path now hits fresh code;
6. **one portable bundle** that keeps edit scope, barrier class, state continuity, activation boundary, stale-code risk, and restart fallback distinct.

That is closer to an ecosystem-worthy crate than another watcher, benchmark chart, or framework-specific dev loop wrapper.
