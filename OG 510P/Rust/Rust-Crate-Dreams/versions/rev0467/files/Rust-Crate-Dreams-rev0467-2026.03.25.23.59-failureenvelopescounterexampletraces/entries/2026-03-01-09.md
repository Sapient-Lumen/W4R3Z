# 2026-03-01 (09) — Cargo build-analysis, structured output, and build signatures

## Signals (with sources)

- **Cargo build-analysis is actively being prototyped**: the 2025H2 Rust Project Goal describes persistent storage of build metadata (potentially SQLite/JSON blobs) plus new commands like `cargo report rebuild-reasons` and `cargo report timing`.  
  Source: Rust Project Goals “Prototype Cargo build analysis” — https://rust-lang.github.io/rust-project-goals/2025h2/cargo-build-analysis.html

- **Today’s official timing output is HTML-only**, which is useful for humans but awkward for tooling and regression tracking.  
  Source: Cargo Book “Reporting build timings” — https://doc.rust-lang.org/cargo/reference/timings.html

- **Tooling still lacks a clean, stable “Cargo event stream”**: Cargo has a long-running request to emit its own messages as JSON, and the discussion explicitly raises questions about wrapping “non-JSON pollution” (proc-macros/build scripts) and including build script warnings.  
  Source: Cargo issue “Provide Cargo messages as JSON messages” — https://github.com/rust-lang/cargo/issues/8283

- **Proc-macros can break `--message-format=json` consumers by printing to stdout**, causing tools like rust-analyzer / cargo-metadata / jq to fail parsing.  
  Source: Cargo issue “Proc macros can cause non-json output … despite message-format=json” — https://github.com/rust-lang/cargo/issues/8179

- **IDEs also want “human output + JSON output” simultaneously** (not “run Cargo twice”), which suggests a missing “multiplexed output protocol.”  
  Source: Cargo issue “Allow to get both JSON output from Cargo and human …” — https://github.com/rust-lang/cargo/issues/3855

- **There is user demand for a “build signature” / list of input files** used by `cargo build`, for caching and reproducibility verification.  
  Source: r/rust “Get a list of all input files used by cargo build” — https://www.reddit.com/r/rust/comments/z0jtlc/get_a_list_of_all_input_files_used_by_cargo_build/

- **Reproducible `.crate` archives are still a concrete pain point**: users want `cargo package` to be bit-for-bit identical across machines when using the same Cargo version.  
  Source: Cargo issue “Reproducible crate builds” — https://github.com/rust-lang/cargo/issues/8612

- **“Precompiled artifacts” remain contentious but real**, and multiple discussions point to the need for deterministic build systems and trust/provenance if any such workflows exist.  
  Source: Rust Internals “Add some form of precompiled artifact support to cargo” — https://internals.rust-lang.org/t/add-some-form-of-precompiled-artifact-support-to-cargo/22871

- **Cargo’s JSON message format is treated as stable-with-additions**, and the ecosystem expects evolution via additive fields or a future `json-v2` if needed.  
  Source: users.rust-lang.org “How stable is cargo's message-format=json?” — https://users.rust-lang.org/t/how-stable-is-cargos-message-format-json/15662

- **Rust is explicitly investing in verification and mirroring** (TUF/chain-of-trust) with experimental infrastructure and tooling goals.  
  Sources: 2025H1 “verification and mirroring” goal — https://rust-lang.github.io/rust-project-goals/2025h1/verification-and-mirroring.html ; Rust Foundation 2025 year in review — https://rustfoundation.org/2025/

- **Reproducible-build tooling is shipping as cargo subcommands**, e.g. `cargo-reproduce` (2025), which affects our “repro” proposals: integrate, don’t reinvent.  
  Source: crates.io `cargo-reproduce` — https://crates.io/crates/cargo-reproduce

## Repo implications

- Update proposal: **P-0042 cargo-event-stream** to explicitly cover (1) multiplexed human+JSON output and (2) “dirty stream” wrapping for proc-macro/build-script output.
- Add proposal: **P-0045 cargo-input-manifest** — a build signature + input manifest artifact (files/env/toolchain) to support reproducibility and caching.
- Add proposal: **P-0046 buildscript-ux-kit** — structured capture/summary of build-script directives and stderr/stdout, with CI-friendly outputs and optional warning policies.
