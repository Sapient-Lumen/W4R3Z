# Entry 301 — crate-test-surface-pack-kit sharpened around isolation-class and reset-capability truth

This pass returned to **P-0523 Crate Test Surface Pack Kit** because the archive still left one ordinary downstream-testing shortcut too cheap:

> a crate could publish official fixtures, fake backends, deterministic seams, and witness artifacts, yet still leave downstream users unable to tell whether those helpers are actually isolated under the runner they use and whether state truly becomes clean again afterward.

## What moved this time

Several current official and ecosystem-standard surfaces make that blur more expensive now than it used to be:

- Rust's own testing docs still say `cargo test` runs tests in parallel by default and warn against shared state such as files or environment variables;
- `std::env::set_var` is now unsafe in multi-threaded non-Windows programs, which makes environment mutation a real isolation/support fact;
- nextest explicitly uses process-per-test isolation and documents why this does **not** transfer back to `cargo test`;
- `wiremock` documents that each `MockServer` is isolated and should not be shared between tests;
- `testcontainers` documents self-contained isolated integration tests with scope-based cleanup;
- and `tempfile` distinguishes OS-owned cleanup from destructor-dependent cleanup.

## Main planning move

This pass promoted two more first-class review objects for **P-0523**:

1. **isolation-class truth** — whether a helper is fresh per call, fresh per test, process-shared, externally shared, or only honest under a runner-specific isolation model;
2. **reset-capability truth** — whether cleanup/reset comes from the OS, from Drop, from an explicit reset API, from best-effort external teardown, or not at all.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “we publish a fake backend and deterministic seams,”
- a downstream team can truthfully say “the tests still flake or contaminate one another under cargo test,”
- another team can truthfully say “it is fine under nextest,”
- and nobody has one compact answer for whether the support contract was **per-test fresh**, **runner-isolated-only**, **process-shared**, or merely **usually cleaned up on Drop**.

That is not cosmetic.
It is the difference between:

- “a helper exists,”
- “a helper is contamination-safe under my runner,”
- and “a helper usually cleans up if nothing interrupts Drop.”

## Main judgment after the pass

A worthy crate test-surface contribution for Rust should now provide more than a fixture catalog and scenario witnesses.
It should also provide:

- one explicit **isolation-class receipt**,
- one explicit **reset-capability receipt**,
- and one honest way to keep runner assumptions, contamination risk, and cleanup mechanism from masquerading as the same support claim.
