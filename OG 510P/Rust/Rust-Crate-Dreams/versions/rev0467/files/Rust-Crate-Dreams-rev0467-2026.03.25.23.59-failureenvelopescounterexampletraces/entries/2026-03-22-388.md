# Entry 388 — Doctest runtool support deepened around runner-route provenance, execution basis, and portable support bundles for P-0481

This pass deepened **P-0481 Doctest Runtool Profile Kit** in a more review-critical direction: **runner-route provenance, execution basis, and portable support bundles**.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- rustdoc’s current command-line docs make `--test-runtool` and `--test-runtool-arg` explicit, including wrapper argument order and the fact that the doctest executable path is passed to the wrapper;
- Cargo’s current unstable-features docs say doctest cross-compilation is now unconditionally enabled starting in Rust 1.89 and that `cargo test` doctests honor `--target`;
- current release notes now keep three related ideas simultaneously official: cross-compiled doctests, target-specific `ignore-*` doctest attributes, and stable `--test-runtool` / `--test-runtool-arg`;
- Cargo’s config docs still make `target.<triple>.runner`, `target.<cfg>.runner`, and `CARGO_TARGET_<triple>_RUNNER` first-class execution routes, with `<triple>` precedence over `<cfg>`;
- Cargo’s `cargo test` docs still warn that the execution model of doctests is not guaranteed and may change;
- those same docs also say doctest compilation happens with `rustdoc` invoked from the workspace root while the runtime working directory for each doctest is the package root and is controlled through `rustdoc`’s `--test-run-directory` option;
- Rust-for-Linux’s tooling goal still explicitly wants stable rustdoc features to extract and customize doc tests for special environments;
- and rustdoc’s `--persist-doctests` support is still unstable, which means persisted binaries can be useful evidence but not yet the stable support contract itself.

Together these sharpen one conclusion: a worthy crate here is not “another emulator helper”.
It is a crate that helps other people inspect **how the effective runner route was selected, what execution basis actually applied to a target lane, and what exact artifact bundle should travel in review or support handoff**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still a **stable support-contract layer** above rustdoc/Cargo execution substrate.
But that support contract now needs three additional review objects:

1. **runner-route receipt** — whether execution came from explicit `rustdoc --test-runtool`, Cargo target-runner config, environment override, direct execution, or a manual review-only route;
2. **execution-basis receipt** — what target/support class/ignore policy/compile-vs-run directories actually governed the lane;
3. **doctest-runtool support bundle** — one portable manifest that keeps route, basis, results, and imported adjacent receipts separate.

## Why these objects matter

Current substrate is now concrete enough that the archive should stop flattening doctest runner support:

- two green runs can both say “cross-target doctests passed” while one used explicit rustdoc wrapper flags and the other inherited a Cargo target runner from config or environment;
- two target lanes can both say “ignored” while one is a documented target-specific policy choice and the other is effectively unreviewed drift;
- a runner wrapper can be entirely correct while still assuming the wrong working directory or path basis for assets;
- and persisted doctest binaries can be useful imports without becoming the stable support contract by themselves.

## New archive-level stance

For documentation-example execution work, the archive should now prefer this layering:

1. **P-0455** for extraction-basis truth, manifests, rewrite lineage, grouping comparability, support class, and portable doctest-support bundles;
2. **P-0481** for runner-route provenance, execution basis, target/emulator policy, ignore audit posture, and portable runtool-support bundles;
3. **P-0472** for docs.rs hosted parity;
4. **P-0476** for docs-example coverage / debt review;
5. broader emulator frameworks or docs portals only after the runtool-support bundle stays honest on its own.

That keeps the portfolio from minting another crate that merely says “QEMU doctests work” without clarifying whether the relevant lane was explicit rustdoc routing, inherited Cargo runner config, target-specific ignore policy, or a manual reconstruction.

## What should count as a worthy crate contribution after this pass

A worthy doctest-runtool contribution should now be able to answer all of these cleanly:

1. **What exact route selected the effective runner?**
2. **What target and support class was the lane actually claiming?**
3. **Which ignore policy was active and why?**
4. **What compile and runtime working-directory assumptions applied?**
5. **What evidence came from adjacent lanes like P-0455 rather than direct runner observation?**
6. **What exact portable bundle can another maintainer inspect?**

If a candidate crate cannot answer those questions, the archive should usually treat it as runner folklore rather than a serious support contract.
