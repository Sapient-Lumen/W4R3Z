# Entry 373 — Async runtime assurance work deepened around qualification basis, runtime drift, and portable runtime-support bundles

This pass continued the archive’s current strategy of **deepening one high-value support-contract lane until it looks genuinely buildable** instead of opening another async helper, benchmark suite, or runtime abstraction layer.

The lane chosen here was **P-0532 Async Runtime Assurance Profile Kit**.
The archive already had a solid thesis, a product sketch, and starter fixtures for `runtime-profile.receipt.json` plus `shutdown-behavior.report.json`.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when a team says “we use Tokio”, “this target uses Embassy”, or “RTIC is part of the concurrency story”, what exactly should another engineer receive and compare?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official and current ecosystem signals still pull in the same direction:

- the March 2026 Rust challenges post says async remains a pain point, that many developers avoid it, and that runtime lock-in is still a real ecosystem problem;
- the January 2026 safety-critical write-up says teams looking at async through an ISO 26262 lens need runtimes with appropriate quality and process artifacts and explicitly recommends defining what a safety-case-friendly async runtime should mean;
- the 2026 flagships page keeps “Just Add Async” on the main forward-looking agenda, which strengthens language/library substrate but does not itself produce a receiver-facing runtime-support contract;
- Tokio’s current runtime docs make shutdown aftermath unusually explicit: timed shutdown can unblock the caller while spawned work continues, started `spawn_blocking` jobs cannot really be aborted once running, and I/O resources bound to the runtime stop functioning after runtime drop;
- Tokio and `tokio-metrics` now expose enough runtime/task metrics surface that “documentation only” and “documentation plus instrumentation” can be kept separate as evidence classes;
- Embassy’s current executor docs make no-`alloc`, static task allocation, linker-detected RAM fit, fairness, integrated timer queues, and optional multi-priority execution concrete enough to classify;
- and RTIC’s current docs keep single-shared-stack execution, compile-time deadlock-freedom, hardware scheduling, generated async executors, and timer-queue semantics concrete enough that the archive should stop flattening RTIC into “just another executor”.

That combination makes one archive lesson sharper:

**A worthy async-runtime crate is not just “name the runtime” or “collect a few metrics.”
It is a reviewable contract for which runtime model is actually in play, what evidence class backs the claim, how runtime posture drifted, and what compact bundle another reviewer can inspect without flattening hosted Tokio, embedded Embassy, and RTIC concurrency into one fake story.**

## Main repo judgment from this pass

The strongest next move for **P-0532** was to make three more receiver-facing review objects first-class:

1. **`qualification-basis.receipt.json`** — claims about runtime choice should stay explicit about whether they are docs-derived, metrics-derived, target-measured, imported from external assurance work, or still manual-review-only.
2. **`runtime-profile-diff.report.json`** — runtime changes should be diffable when scheduler model, allocation posture, timer authority, blocking posture, or evidence class changes.
3. **`runtime-assurance-bundle.manifest.json`** — another team should be able to receive one compact pack joining runtime profile, shutdown behavior, qualification basis, and any host/target split notes without pretending those surfaces all mean the same thing.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0520** still owns broader lifecycle/shutdown support surfaces above the runtime layer;
- **P-0521** still owns resource/budget topology;
- **P-0484** still owns toolchain/target support posture;
- and broader system assurance still belongs to **P-0503** rather than being smuggled into runtime-selection prose.

That separation matters.
Otherwise the archive would quietly confuse “the ecosystem is improving async language support” with “another team can now review the runtime assumptions of this shipped product.”

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One runtime-profile receipt** that says what class of runtime/concurrency model is actually in use.
2. **One shutdown-behavior report** that says what stopping really means for async tasks, blocking tasks, timeouts, and bound resources.
3. **One qualification-basis receipt** that says whether the claim is docs-only, metrics-backed, on-target measured, or imported from an assurance artifact.
4. **One runtime-profile drift report** that says whether the team changed runtime model, only evidence basis, or both.
5. **One portable assurance bundle** that keeps host/test/runtime notes, target/runtime notes, and manual-review gaps separate.
6. **One conservative review boundary** so Tokio, Embassy, RTIC, and mixed host/target stacks stop collapsing into one fake “supports async runtime X” verdict.

If a crate idea in this territory cannot supply those review objects, it is still probably substrate, instrumentation, or a framework adapter rather than the missing contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **runtime names** into **runtime support truth**.

Future passes should therefore keep asking:

1. what runtime model is actually in play,
2. what evidence class backs the claim,
3. what changed across revisions,
4. and how host/runtime versus target/runtime lanes remain separate in the exported bundle.

That is a better use of repo time than inventing another async tutorial crate, generic benchmark harness, or runtime-neutral abstraction layer.
