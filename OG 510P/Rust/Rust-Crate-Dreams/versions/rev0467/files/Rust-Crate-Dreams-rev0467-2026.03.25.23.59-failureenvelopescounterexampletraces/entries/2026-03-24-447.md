# Entry 447 — add adjudication and carry-forward so packet disagreement becomes reviewable instead of silently normalized

This pass again chose **deepen over append**.

The archive already had a much better answer for:
- how a team compares plausible crates,
- how it freezes a basis,
- how it imports and materializes support packets,
- and how later triggers reopen review.

What it still lacked was a clean answer to the next operational question:

> when two packets, surfaces, or later signals disagree, how does a worthy crate help people **adjudicate the conflict** and then **carry the decision forward** without rewriting the original basis?

That seam matters now because the official Rust substrate is increasingly packet-friendly but still route-sensitive and time-sensitive:
- Cargo explicitly frames future “plumbing” around programmatic phases rather than one monolithic porcelain command;
- Cargo build analysis is about persisting build metadata across invocations, which means later comparison/adjudication is a first-class workflow;
- `cargo metadata` still requires `--format-version` and the registry index still differs in subtle ways from both the Publish API and `cargo metadata`;
- Cargo JSON streams distinguish `compiler-artifact` messages from `build-script-executed` messages and note that build-script output may be cached even when the script was not rerun;
- docs.rs `latest` / semver routes and download archives are convenient import surfaces, but they must be resolved into a pinned basis and keep offline/static-asset caveats visible;
- crates.io now exposes more trust and timing surfaces (`pubtime`, Trusted Publishing settings, Security tab), but these still do not settle task fit or local policy.

## Main judgment

A worthy crate in the practical core should now publish not only:
- compare packets,
- basis locks,
- intake/materialization receipts,
- recheck tickets,
- revalidation packets,
- and transition packets,

but also a credible **adjudication workbench**.

That means it should provide:
1. one compact disagreement ledger,
2. one adjudication session showing which claims conflicted and why,
3. one carry-forward receipt that says what changed and what stayed inherited,
4. one visible unresolved/manual-review zone list,
5. and one narrow path for reopening the same question later without erasing the old decision.

## Practical consequence

This pass still does **not** justify a major salience rerank.

But it sharpens the first practical slice again:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, intake/materialization, adjudication sessions, carry-forward receipts, trigger intake, and recheck tickets
2. **P-0486** — debug witness bundles that can later enter the same adjudication flow
3. **P-0496** — restricted-delivery/source-parity packets that reuse the same disagreement/carry-forward honesty
4. **P-0472** — docs.rs parity bundles that explicitly separate hosted facts, local replay, and adjudicated support posture

Interpretation:
- the front door is no longer just “choose, freeze, intake, materialize, watch, and reopen honestly”; it is now also “**adjudicate and carry forward honestly**”.
- the sharpest missing product layer is no longer more scoring or more crawling; it is a small **decision workbench** above current packet families.

## What this pass says a worthy crate should provide other people

A worthy crate in the practical core should now answer **fifteen** operational questions:

1. compare — what are the plausible choices now?
2. freeze — what exact basis did the chosen answer stand on?
3. watch — which surfaces are being watched later?
4. trigger — what exact event opened review?
5. intake — what imported material was actually consumed?
6. materialize — what can be made portable or offline-friendly?
7. conflict — which claims disagree and on which route or time basis?
8. adjudicate — what decision was made about that disagreement, by whom, and under what policy?
9. carry forward — which old claims remain inherited and which became superseded?
10. ticket — what review packet should be opened next?
11. refresh — what later facts changed and which did not?
12. revalidate — does the old choice still stand under the same task and policy?
13. transition — if not, what posture follows now?
14. degrade — what became partial, unresolved, or manual-review-only?
15. ceiling — what still requires manual judgment even after the workbench runs?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
