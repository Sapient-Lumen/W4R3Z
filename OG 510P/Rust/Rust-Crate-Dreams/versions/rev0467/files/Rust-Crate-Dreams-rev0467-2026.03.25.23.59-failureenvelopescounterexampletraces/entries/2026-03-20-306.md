# Entry 306 — secrets-kit sharpened around revelation path, persistence posture, memory posture, and export posture

This pass returned to **P-0037 secrets-kit** because the archive still left one familiar and costly blur too available:

> a team could truthfully say “we use `secrecy`, `zeroize`, and a secure store” while still leaving another team unable to tell how the secret was actually revealed, whether test mode silently switched to a mock, whether in-process handling was merely zeroize-on-drop or truly protected memory, and whether serialization or explicit export paths had been reopened.

## What moved this time

Several current Rust signals make that blur harder to excuse:

- `secrecy` is explicit that it aims for explicit secret access, debug redaction, and zeroize-on-drop, while also explicitly **not** providing `mlock(2)` / `mprotect(2)`-style advanced memory protection;
- `secrecy` is also explicit that deserialization can create intermediate plaintext and that callers must clean up the unparsed input path carefully;
- `zeroize` now gives a very clear promise — reliable zeroing that will not be optimized away — while equally clearly refusing to masquerade as a complete memory-protection story;
- `keyring` now gives a clearer cross-platform substrate with explicit store features, BYO store builders, and a documented mock store that provides **no persistence**;
- `secrets` gives materially stronger protected-memory behavior (`mprotect`, guard pages, `mlock`, zero-on-drop), which makes the zeroize-only versus protected-memory boundary concrete.

That combination means the missing crate is no longer best described as “some provider chain plus typed secrets”.
It is better described as a **reviewable secret-handling contract** above today’s wrappers, stores, and memory-protection substrate.

## Main planning move

This pass promoted four newly first-class review objects for **P-0037**:

1. **revelation-path truth** — what source class revealed the secret and whether plaintext intermediates were part of the path;
2. **persistence-posture truth** — whether the backend is persistent, session-bound, ephemeral, mock-only, or externally managed;
3. **memory-posture truth** — whether the runtime promise is ordinary heap, zeroize-only, protected memory, hybrid, or manual-review-only;
4. **export-posture truth** — whether debug, display, serde, clone, and explicit reveal helpers widen the export surface.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “we do not print secrets in debug output”,
- another maintainer can truthfully say “we store secrets in the keyring”,
- a reviewer can truthfully say “we wrap values in `SecretBox<T>` and zeroize them on drop”,
- and a downstream team can still be unable to tell whether tests use a non-persistent mock, whether the value first passed through an env `String`, whether protected memory is actually in use, or whether a `serde` opt-in reopened export paths.

That is not a wording nit.
It is the difference between “the app uses secret-related crates” and “another team can review the secret-handling contract they are being asked to trust”.

## Main judgment after the pass

A worthy secret-handling support contribution for Rust should now provide more than a provider chain, a wrapper type, and a generic redaction claim.
It should also provide:

- one explicit **revelation-path receipt**,
- one explicit **persistence-posture receipt**,
- one explicit **memory-posture receipt**,
- and one honest **export-posture report**.
