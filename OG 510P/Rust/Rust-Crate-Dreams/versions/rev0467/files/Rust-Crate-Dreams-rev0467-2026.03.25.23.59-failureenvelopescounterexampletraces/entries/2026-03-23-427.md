# Entry 427 — concurrency-contract deepened around delivery audience, claim semantics, and fanout honesty

This pass chose to **deepen P-0538 Concurrency Contract Kit** again instead of opening another channel wrapper, pub/sub helper, or actor-adjacent abstraction.

The sharper question was:

> once a concurrency surface can describe reentrancy, fairness, cancellation, context legality, locality, liveness, delivery memory, and backlog pressure, how does it also say **who is actually eligible to observe a given wake/value/message** and **whether one observer taking it prevents other observers from seeing it**?

## Why this deepening pass earned a full revision

Fresh primary sources made the next missing layer concrete:

- the March 2026 Rust challenges write-up still says async complexity is part of the current Rust pain picture;
- Tokio `broadcast` documents that each sent value is seen by **all consumers** / **all active receivers** in order;
- Tokio `watch` documents that each `Receiver` independently tracks the last value seen by its caller, which is a different audience/claim shape from queue delivery;
- Tokio `Notify::notify_waiters` documents waking **all waiting tasks** but storing **no** future permit;
- Tokio `mpsc` documents a multi-producer, **single-consumer** queue;
- `async-channel` documents MPMC delivery where each message can be received by **only one** of the existing consumers;
- Flume documents that cloning a receiver does **not** turn the channel into a broadcast channel and each message is still received by only one receiver;
- Tokio `oneshot` documents a single-message producer/consumer pair.

That means the next worthy move for **P-0538** is not just broader “channel behavior.”
It is to make **delivery-audience** and **consumption-claim** first-class review artifacts.

## Main judgment after this pass

The top frontier still begins:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But **P-0538** is stronger now because the archive no longer stops at:

- reentrancy scope,
- progress/fairness class,
- wait-cancellation semantics,
- recovery posture,
- execution-context boundaries,
- mobility / affinity,
- driver-liveness,
- delivery memory,
- backlog pressure.

It now has a clearer product shape for:

- **delivery-audience reports**,
- **consumption-claim reports**,
- **single-consumer versus all-active-receiver versus current-waiter-only honesty**,
- **exclusive-claim versus fanout-clone versus independent-seen-state distinctions**,
- and portable bundle inventory that keeps audience and claim semantics separate from memory, pressure, fairness, cancellation, or context legality.

## What should count as a worthy crate contribution in this lane now

A worthy concurrency-contract crate should provide other people:

1. **one delivery-audience report** that says whether a send/notify targets one waiter, all current waiters, one consumer, all active receivers, or independent per-receiver latest-state observers;
2. **one consumption-claim report** that says whether observation is a non-consuming wake, an exclusive single-receiver claim, a clone-per-receiver fanout, an independent seen-state mark, or a single-use transfer;
3. **one explicit separation between “many observers may exist” and “each message is still claimed by only one observer”**;
4. **one explicit separation between “every active receiver gets a clone” and “every receiver only sees the latest shared state”**;
5. **one portable bundle** that keeps delivery audience and claim semantics separate from delivery-memory, pressure, fairness, cancellation, recovery, context, locality, and liveness.

That is closer to an ecosystem-worthy crate than another queue helper, notification wrapper, or “which channel should I use?” article.
