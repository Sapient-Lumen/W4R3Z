# 2026-03-01 (06) — Update policies, build analysis, MSRV workflows, secrets ergonomics

This entry captures new evidence signals that suggest **high-leverage missing crates** in Cargo/workspace tooling and application plumbing.

## Signals & sources

### Cargo wants “gradual rollouts” and safer dependency update workflows
- The Cargo team explicitly called out interest in *gradual rollouts* driven by **publish time (“pubtime”)** so users can require versions to be “old enough” before upgrading. See the `pubtime` section in the Cargo 1.93 dev-cycle update.  
  Source: https://blog.rust-lang.org/inside-rust/2026/01/07/this-development-cycle-in-cargo-1.93/
- There is a concrete Cargo issue proposing **adding release date to the registry index format** to enable delaying updates (including as a mitigation against fast-moving supply-chain attacks).  
  Source: https://github.com/rust-lang/cargo/issues/15491
- In Cargo’s own design discussions around `-Zminimal-versions` and version-req updating, participants explicitly mention a future “hold/forbid updates” mechanism and time-based limits (e.g., “only update to versions from 3 months ago”).  
  Source: https://internals.rust-lang.org/t/zminimal-versions-cargo-update-and-cargo-upgrade/21335

### Cargo build performance tooling is shifting toward persisted, queryable build metadata
- A Rust Project Goal proposes **persisting build metadata across invocations** and adding `cargo report ...` commands for historical timing and rebuild reasons; it notes `--timings` exists mostly as HTML and is not well-suited for machine analysis.  
  Source: https://rust-lang.github.io/rust-project-goals/2025h2/cargo-build-analysis.html
- A design proposal sketch exists for `cargo report timings` and `cargo report rebuild-reasons`, including JSONL parsing and run IDs.  
  Source: https://hackmd.io/K5-sGEJeR5mLGsJLXqsHrw
- Cargo still lacks structured JSON for Cargo’s own messages (#8283), which blocks richer external tooling and IDE integrations.  
  Source: https://github.com/rust-lang/cargo/issues/8283

### MSRV-aware resolution is real, but the UX and “mixed MSRV workspace” workflow is still rough
- Cargo has a documented MSRV resolver RFC, but real workspaces report surprising/suboptimal behavior when MSRVs differ across workspace members.  
  Sources:
  - https://rust-lang.github.io/rfcs/3537-msrv-resolver.html
  - https://github.com/rust-lang/cargo/issues/14414
- Maintainers still ask for an **automated way to infer a minimum required Rust version** for a crate/workspace.  
  Source: https://users.rust-lang.org/t/whats-the-automated-way-to-find-out-minimum-required-rust-version-with-cargo/110274
- The Rust API guidelines discussion on MSRV policies highlights the need for clearly documenting MSRV and testing it in CI.  
  Source: https://github.com/rust-lang/api-guidelines/discussions/231

### Secrets storage remains confusing across desktop/mobile/server contexts
- People still ask “what’s the recommended crate” for storing DB credentials (server context) and note tooling churn / staleness.  
  Source: https://users.rust-lang.org/t/recommended-crate-for-storing-keys-for-web-site-database/133305
- For client apps, developers report frustration that popular keyring approaches don’t cover Android.  
  Source: https://www.reddit.com/r/rust/comments/1qgb3rq/recommended_way_to_store_secrets_securely_in/
- A modern Vault client exists and is actively maintained, but application-level *composition* (Vault + env + file + keyring + redaction + typed config) is still ad hoc.  
  Source: https://github.com/michaelklishin/vault-client-rs

## Candidate proposal directions
- `cargo-update-policy` (pubtime/holds/forbid versions; safer rollouts)
- `cargo-build-insights` (parse & query persisted build analysis; insights + privacy-respecting reports)
- `msrv-workspace-lab` (mixed MSRV workspace planning + CI automation + inference helpers)
- `secrets-kit` (provider chain + typed secrets + redaction + platform gaps)
