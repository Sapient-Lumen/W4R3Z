# Entry 267 — crate upgrade support sharpened around hazard authority, workspace scope, and follow-through coverage

This pass did **not** invent another release bot, another changelog generator, or another generic codemod framework.
It deepened **P-0514 Crate Upgrade Pack Kit** into a more implementation-ready product.

## Why this moved now

The ecosystem’s release/upgrade substrate is better than it was even two days ago in the archive, but it still leaves a conspicuous downstream hole.

- The Rust vision-doc work explicitly argues that crates need more **supportive interfaces**, not just more raw power.
- The 2025 State of Rust survey still says **online documentation** and **code** remain the main learning surfaces, which means upgrade support still lands largely through maintainer-authored artifacts.
- The Cargo SemVer reference remains a useful compatibility baseline, but it is still only one slice of the migration problem.
- `cargo-semver-checks` is mature enough to be real release substrate, but its own docs still say it depends on unstable rustdoc JSON and only guarantees support for current stable/beta Rust versions.
- `release-plz update` now explicitly integrates `cargo-semver-checks` when available, but it also explicitly warns that `cargo-semver-checks` does **not** catch every SemVer violation.
- `cargo release` clearly automates validation/version/tag/publish chores, but it is still a producer-side release flow, not a downstream migration artifact.
- `cargo fix` clearly applies rustc suggestions to **source code**, while `rustfix` itself is a low-level suggestion applier over compiler JSON rather than a manifest/config/docs migration system.
- Cargo’s external-tools and `cargo metadata --format-version` surfaces are now stable enough that a workspace-aware upgrade-support crate can import package structure without scraping ad hoc output.
- Cargo workspaces remain common and first-class, which makes “the library lane passed” versus “the example binary lane was not checked” a real distinction, not an edge case.
- The July 2025 `hint-mostly-unused` call for testing made the language around **feature flags as stable interface** unusually explicit, which means feature/default-policy shifts belong inside upgrade hazard modeling, not outside it.

That combination makes the sharper missing value clearer than before.
The ecosystem does **not** mainly lack one more way to publish or one more way to summarize commits.
It lacks one reviewable artifact that can say:

- **where each upgrade hazard came from**,
- **which workspace/package/example lanes were actually checked**,
- and **which surfaces were truly machine-fixed versus still requiring manifest/config/docs follow-through**.

## Main planning move

This pass promoted three review objects to first-class status for **P-0514**:

1. **hazard authority** — whether a given hazard comes from SemVer/public-API evidence, feature/default-policy drift, config/runtime policy drift, observed behavior checks, or maintainer-authored notes,
2. **package-scope truth** — which workspace members and scenario classes were actually exercised, and which lanes remain outside the witnessed bundle,
3. **follow-through coverage** — whether an observed machine fix touched only Rust source or truly covered the full migration surface.

That matters because the archive already had good pieces:

- hazard classes,
- fixup capability receipts,
- lane-fidelity reports,
- and recipe manifests.

But it still did not cleanly separate:

- “SemVer/public-API evidence found a break,”
- “a feature/default policy changed even though the public API diff stayed green,”
- “`cargo fix`/`rustfix` repaired source code only,”
- and “the workspace release PR updated several packages but only one published lane was actually witnessed.”

This pass fixes that.

## Main judgment after the pass

A worthy upgrade-support crate should now provide **more than hazards + recipes**.
It should provide:

- explicit **hazard-authority truth**,
- explicit **workspace/package-scope truth**,
- explicit **follow-through coverage truth**,
- explicit **manual-review boundary truth**,
- and one compact **upgrade bundle** another maintainer can inspect without reverse-engineering release bots, compiler suggestions, changelogs, and workspace CI.

That is a stronger and more believable product than any of the nearby substitutes:

- “SemVer checks passed, so the upgrade is easy”,
- “release-plz opened a PR, so the lane is covered”,
- “cargo fix succeeded, so the migration is automated”,
- or “the changelog already tells people what changed”.
