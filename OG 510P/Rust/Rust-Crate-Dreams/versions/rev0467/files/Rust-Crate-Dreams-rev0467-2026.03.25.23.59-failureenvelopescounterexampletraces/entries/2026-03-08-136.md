# Entry 136 — buildscript UX implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded **P-0046 buildscript-ux-kit** from a strong native-build-frontier idea into a more implementation-ready crate plan.

## Main judgment

Cargo already has enough real substrate here that the archive should stop speaking about build-script UX in vague terms.

The current upstream story already has:

- documented `cargo::warning` / `cargo::error` behavior,
- documented visibility asymmetry for warnings from non-path dependencies,
- `build-script-executed` JSON output in Cargo’s external-tools surface,
- cached build-script values appearing in JSON even when the script was not run,
- and unstable direction toward `metabuild` / `multiple-build-scripts` rather than one permanent handwritten-script worldview.

So the missing value is not “invent a new build-script protocol.”
It is the **receiver-facing support bundle** above those surfaces.

## New planning stance

**P-0046** should now be read as a crate that hands other people:

- one redaction-aware `buildscript-report.json`,
- one concise `buildscript-summary.txt`,
- one `policy-gate.report.json`,
- optional `notes.md`,
- and explicit semantics for **capture origin** plus **message visibility**.

That is a much sharper contract than “structured build-script diagnostics.”

## Archive-level lesson

When Cargo exposes more machine-readable substrate, a worthy crate often becomes *smaller* and more honest.

The right move here was not to add another native-build proposal. It was to make the strongest one more conservative about provenance, more explicit about what users actually saw, and more concrete about the support bundle it hands to someone else.
