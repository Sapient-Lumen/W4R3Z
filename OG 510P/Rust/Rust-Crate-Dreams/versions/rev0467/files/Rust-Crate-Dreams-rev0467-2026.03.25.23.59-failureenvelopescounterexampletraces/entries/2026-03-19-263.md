# Entry 263 — crate observability support sharpened around bridge routes, activation truth, and sensitivity boundaries

This pass did **not** add another subscriber, another exporter, another schema linter, or another observability backend.
It sharpened **P-0518 Crate Observability Surface Pack Kit** into a more implementation-ready support crate.

## Why this moved now

Rust’s observability story is no longer missing substrate.
That changes the shape of the missing value.

- The December 2025 Rust vision-doc work explicitly says crates need more **supportive interfaces**.
- The 2025 State of Rust survey still says online docs and code remain the main learning surfaces, while resource usage and debugging remain visible pain points.
- Tokio’s tracing topic still presents `tracing` as structured event-based diagnostics with downstream routes including OpenTelemetry export, Tokio Console, logging, and profiling.
- `EnvFilter` now makes a subtle but important truth explicit: filters may be global or per-layer, field-value matching can use regex, and regex matching should be disabled for potentially untrusted input.
- `console-subscriber` still makes the runtime recipe explicit: Tokio `tracing` support and `tokio_unstable` are required on the Tokio path.
- `tracing-opentelemetry` still makes another boundary explicit: it can export traces and metrics, but **not logs**.
- OpenTelemetry’s Rust docs still mark traces, metrics, and logs as **beta** in Rust.
- OpenTelemetry’s Rust libraries page still says the docs team does not know of any Rust library with OpenTelemetry natively integrated by default.
- OpenTelemetry schema docs still tie semantic meaning to versioned schema URLs.
- OpenTelemetry’s sensitive-data guidance still says implementers remain responsible for understanding and reviewing emitted data, including instrumentation-library output.

That combination means the missing crate is no longer “Rust needs telemetry tooling”.
The sharper missing crate is a **crate-authored observability contract** above today’s tracing, filtering, console, exporter, and semantic-convention substrate.

## Main planning move

This pass promoted five review objects to first-class status for **P-0518**:

1. **signal stability** — which names and fields are stable enough for queries and alerts,
2. **activation truth** — which features, filters, layers, runtimes, or cfgs are actually required,
3. **bridge-route truth** — which routes actually carry which signals to stdout/fmt, console, traces, metrics, or logs,
4. **schema posture** — which semantic-convention / schema URL claims are being made,
5. **sensitivity boundaries** — which fields are safe, payload-derived, hashed, dropped, or manual-review territory.

That move matters because the archive had already named the lane, but it had not yet made the boundary between **"a signal exists in code"** and **"a downstream team can actually see it through the route they think they are using"** concrete enough.
This pass fixes that.

## Main judgment after the pass

A worthy observability-support crate contribution for Rust should now provide **more than signal names**.
It should provide:

- explicit **signal-stability truth**,
- explicit **activation-truth**,
- explicit **bridge-route truth**,
- explicit **schema-posture truth**,
- explicit **sensitivity-boundary truth**,
- and one compact **observability-surface diff** another maintainer can inspect without reconstructing the story from `RUST_LOG`, exporter layers, console wiring, and backend assumptions.

That is more believable and more ecosystem-multiplying than either:

- “just use `tracing`”,
- “just add OpenTelemetry”,
- “just call `console_subscriber::init()`”,
- or “just inspect the dashboards” with no receiver-facing support contract attached.
