# Entry 293 — crate-lifecycle-surface-pack sharpened around shutdown phases, stop budgets, and timeout aftermath truth

This pass stayed with **P-0520 Crate Lifecycle Surface Pack Kit** again because the archive had already become much clearer about **shutdown barriers** and **escape paths**, but it still left one dangerous blur intact:

> a crate or framework could now tell you what its graceful-shutdown barrier covers, yet still leave you unable to answer **which phase shutdown actually reached before a time budget expired**, whether the program merely **stopped waiting**, and what work may still be running after the timeout returned control to the caller.

## What moved this time

Several current ecosystem signals make that blur hard to excuse:

- Tokio’s graceful-shutdown guide still frames shutdown as **figure out when to shut down, tell tasks to shut down, and wait for them to shut down**. That already implies a phased model rather than one magical “done” bit.
- `tokio_util::task::TaskTracker` still says `wait()` completes only when the tracker is **both closed and empty**, which is a real phase boundary, not merely a signal-delivery event.
- Tokio maintainer guidance from March 2025 makes another common trap explicit: putting a `JoinHandle` under `timeout` and then timing out only drops the handle; it does **not** cancel the task unless you also `abort` it.
- Tokio’s `spawn_blocking` docs now state that started blocking tasks cannot be aborted, and runtime shutdown will wait indefinitely for them unless `shutdown_timeout` is used.
- Tokio’s runtime docs go further: once the timeout is reached, outstanding work and threads are **leaked**, the initiating thread is unblocked, and the work continues until its own stopping conditions are met.
- `hyper-util`’s graceful-shutdown docs say `shutdown()` completes once all **watched connections** have shut down, which is useful but still narrower than “the whole service is now quiescent.”
- Live issue traffic still shows both kinds of confusion in the wild: axum WebSocket upgrade work can outlive the server graceful-shutdown future, while SSE work can keep that future pending indefinitely.

That combination means the lifecycle lane now needs two more first-class review objects.

## Main planning move

This pass promoted:

1. **shutdown-phase truth** — which step of shutdown was actually reached (`signal_sent`, `accepting_stopped`, `tracked_tasks_drained`, `protocol_close_attempted`, `protocol_drains_finished`, `runtime_wait_abandoned`, `manual_review_required`),
2. **timeout-aftermath truth** — what remains true after a timeout or dropped wait path returns (`wait_stopped_only`, `task_still_running`, `blocking_thread_survives`, `resource_handles_invalidated`, `manual_abort_still_required`, `manual_review_required`).

## Why this matters

Without those objects, the archive still permits another ordinary lie:

- a maintainer can clearly name the shutdown barrier,
- a framework can truthfully say graceful shutdown completed,
- a runtime can honestly report that timeout returned,
- and a user can still walk away believing the program is *quiescent* when all that really happened is that **waiting stopped**.

That difference matters for:

- background workers still flushing or retrying,
- blocking threadpool work that survives runtime timeout,
- upgraded protocol tasks outside the main server barrier,
- and any support story that needs to answer “what is still alive right now?” rather than merely “which future resolved?”

## Main judgment after the pass

A worthy lifecycle-support crate for Rust should now provide more than:

- background-work maps,
- stop-verb truth,
- shutdown-barrier truth,
- and escape-path receipts.

It should also provide:

- one explicit **shutdown-phase report**,
- one explicit **timeout-aftermath receipt**,
- one explicit answer to whether a timeout stopped **work** or merely stopped **waiting**,
- and one explicit answer to whether the caller is seeing **quiescence**, **barrier completion only**, or **budget exhaustion with surviving work**.

That is a much stronger answer than either:

- “Tokio already has cancellation tokens,”
- “the server has graceful shutdown,”
- or “timeout returned, so we’re done.”
