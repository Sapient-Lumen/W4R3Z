# Entry 404 — build-dir consumer transition now needs consumer-need reports, adapter-authority receipts, windowed viability matrices, and rehearsal bundle manifests

This pass deepens an already-promising Cargo migration lane instead of adding another cache manager, path abstraction helper, or filesystem wrapper.
It sharpens:

**P-0489 Cargo Build-Dir Consumer Transition Kit**.

## Why this lane earned another serious refresh now

The archive already had a stronger story for:
- consumer inventories,
- layout snapshots,
- consumer audits,
- path contracts,
- adapter plans,
- adapter-viability windows,
- and transition receipts / diffs.

What it still left too easy to flatten was a sharper operational question:

> “What job was this consumer actually trying to do, what source really authorizes the replacement advice, and in which Cargo/layout window does that advice honestly hold?”

Current primary Cargo sources make that split unusually concrete:

- the March 2026 call for testing says the build-dir layout is internal-only, but many projects still rely on unspecified details because Cargo is missing features;
- the same post asks people to run tests, release processes, and anything else touching build-dir / target-dir under `-Zbuild-dir-new-layout`;
- the post names concrete failure modes rather than vague breakage, including inferring a `[[bin]]` path from a `[[test]]` path, build scripts recovering target-dir from their binary or `OUT_DIR`, and user-requested artifact lookup from rustc-oriented locations;
- the build-cache docs keep the split explicit: final artifacts live in target-dir while intermediate artifacts are internal to Cargo and rustc and live in build-dir;
- Cargo build docs explicitly document `CARGO_BIN_EXE_<name>` for integration-test binary lookup;
- and Cargo’s external-tools docs still say `--message-format=json` only controls Cargo/rustc output, not arbitrary tool or proc-macro output.

Together those sources say the missing crate contribution is no longer just “audit path scraping” or even “name a safer adapter.”
It is a reviewable migration layer for **consumer need truth**, **adapter authority truth**, **windowed viability truth**, and **portable rehearsal-bundle truth**.

## Main judgment after the refresh

**P-0489** is stronger when it owns four more receiver-facing truths:

1. **consumer need truth** — whether a workflow actually needs an integration-test binary, build-script-owned output, a final artifact, dep-info, or only a guessed workspace/topology path;
2. **adapter authority truth** — whether the suggested fix comes from stable Cargo docs, a version-windowed official post, release notes, unstable docs, or only a local heuristic / issue-thread workaround;
3. **windowed viability truth** — which Cargo channel / version / layout mode combinations are documented, conditional, nightly-only, fallback-required, or still manual-review-only;
4. **portable rehearsal-bundle truth** — how a team hands around one compact bundle for legacy layout, custom `build.build-dir`, and `-Zbuild-dir-new-layout` rehearsal without collapsing evidence into one fake “migration supported” verdict.

That means a worthy crate in this lane should now explicitly own:

- `consumer-need.report.json`,
- `adapter-authority.receipt.json`,
- `windowed-viability.matrix.json`,
- and `rehearsal-support-bundle.manifest.json`

above the earlier inventory / audit / contract / adapter-plan / transition-receipt lane.

It should **not** try to become:
- a universal stable filesystem API for Cargo internals,
- another cache manager,
- a Cargo-as-a-library reimplementation,
- or a magical source rewriter that claims all migrations are automatic.

## What should count as a worthy crate contribution in this lane now

A worthy build-dir-consumer transition contribution should now hand other people:

1. **one consumer-need report** that says what the workflow was really trying to accomplish instead of just which path it scraped;
2. **one adapter-authority receipt** that says which official source class actually justifies the replacement advice and where scope conditions still apply;
3. **one windowed-viability matrix** that makes Cargo-version, stable-vs-nightly, fallback, and layout-mode truth explicit;
4. **one rehearsal-support bundle manifest** that joins those facts with the older inventory / audit / transition artifacts for issue reports, CI migrations, and upgrade rehearsals.

If a candidate crate cannot do those things, the archive should usually treat it as path folklore, a one-off migration note, or a local helper script — not the missing reviewable transition-contract layer.
