# Entry 419 — concurrency-contract deepened around task locality, mobility/affinity, and driver-liveness truth

This pass chose to **deepen P-0538 Concurrency Contract Kit** again instead of opening another executor abstraction, spawn helper, or runtime-comparison lane.

The sharper question was:

> once a concurrency surface says whether it is fair, cancel-safe, or legal in some broad context, how does it also say **where the task is allowed to live, what thread or executor it is tied to, and what has to keep driving the system for that task to make progress**?

## Why this deepening pass earned a full revision

Fresh sources made the next missing layer concrete:

- the March 2026 challenges write-up still says async complexity is a major expert-facing pain and ties that pain to fragmentation and lock-in;
- community wish-list discussion still explicitly asks for better documentation around forward progress guarantees and reentrancy;
- Tokio `spawn_local` documents that spawned tasks stay on the calling thread and that the API panics outside a `LocalSet` or `LocalRuntime`;
- Tokio runtime docs explicitly say a `LocalSet` only runs when it is awaited or otherwise driven, and current-thread runtimes only execute tasks when a thread is provided via `Runtime::block_on`;
- Tokio `Handle::block_on` explicitly warns that on a `current_thread` runtime it does **not** drive I/O or timer drivers;
- Tokio `LocalRuntime` is still unstable, explicitly thread-bound, and explicitly incompatible with `LocalSet`;
- `async_executor::LocalExecutor` and `glommio` both expose meaningful thread-local / local-executor behavior, showing that portability here is possible without flattening everything to Tokio;
- executor-abstraction crates like `async_executors` and `executor-core` already exist, which strengthens the case that the missing value is **support-contract truth**, not another abstraction layer.

That means the next worthy move for **P-0538** is not just broader “execution-context boundaries.”
It is to make **mobility/affinity** and **driver-liveness** first-class review artifacts.

## Main judgment after this pass

The top frontier still begins:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But **P-0538** is stronger now because the archive no longer stops at:

- reentrancy scope,
- progress/fairness class,
- wait-cancellation semantics,
- recovery posture,
- and broad execution-context boundaries.

It now has a clearer product shape for:

- **mobility-affinity reports**,
- **driver-liveness reports**,
- **same-thread / local-context spawn requirements**,
- **non-driving handle warnings**,
- and portable bundle inventory that keeps locality truth separate from fairness, cancellation, or panic posture.

## What should count as a worthy crate contribution in this lane now

A worthy concurrency-contract crate should provide other people:

1. **one mobility/affinity receipt** that says whether tasks, executors, or handles are movable across threads, fixed to a thread, fixed to a local context, or manual-review-only;
2. **one driver-liveness report** that says what actually has to keep running for progress to happen;
3. **one explicit separation between “can spawn locally” and “will make progress here”**;
4. **one warning for non-driving handles and half-valid contexts** so “it compiled” is not over-read as “timers and I/O are driven”;
5. **one portable bundle** that keeps mobility, liveness, fairness, cancellation, and recovery in distinct review lanes.

That is closer to an ecosystem-worthy crate than another executor wrapper or runtime-agnostic facade.
