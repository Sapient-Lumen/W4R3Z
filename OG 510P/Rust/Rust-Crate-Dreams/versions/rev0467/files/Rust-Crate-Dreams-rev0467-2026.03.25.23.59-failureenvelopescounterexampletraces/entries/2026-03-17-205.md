# Entry 205 — crate authority surfaces promoted as the sandbox/offline/determinism-support lane

This pass added a new top-level proposal: **P-0519 Crate Authority Surface Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing capability APIs, sandbox runtimes, static authority scans, and receiver-facing crate authority support into one fake “better security tooling” story.

## Why this moved now

Several current Rust and ecosystem signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good host-authority lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- **successor / off-ramp support** via **P-0515**,
- **setup/configuration scenarios** via **P-0516**,
- **performance envelopes** via **P-0517**,
- and **observability surfaces** via **P-0518**.

But it still lacked a good answer to:

- “Once a team chose a crate, what exactly does the crate hand them so they can understand its ambient authority, determinism posture, and sandboxability?”

That left the archive with better answers for **choice**, **setup**, **migration**, **failure**, **perf**, and **telemetry** than for **host-authority posture**, which is strange for a language heavily used in servers, CLIs, embedded systems, WASI, plugins, and constrained environments.

### 2. Official substrate makes this a contract problem, not a missing-building-blocks problem

The project-goals page for sandboxed build scripts already frames file-system and network access plus determinism as real design seams.
Cargo already documents environment variables and build scripts with arbitrary tasks.
`getrandom` already supports opt-in and custom backends.
Capability-oriented crates like `ambient-authority`, `cap-std`, and `wasi-cap-std-sync` already exist.

That means the sharper question is no longer “can Rust express capability-oriented or sandboxed code at all?” but “what portable artifact should sit above today’s substrate so a crate can tell downstream users what it actually touches or assumes?”

### 3. Current capability/sandbox tooling is real but still fragmented at the crate boundary

`cap-std` gives a capability-oriented API.
`ambient-authority` makes ambient use explicit.
`rustix` explicitly says it does not restrict ambient authorities.
Build-sandbox tools and goals focus on compile-time execution.
What is still missing is the boring pack that can say:

- these are the authority kinds we intentionally require,
- these ones are optional or profile-specific,
- these dependencies are injectable rather than ambient,
- this recipe verifies offline or deterministic operation,
- and this is how the authority surface changed across releases.

### 4. Rust’s current official messaging makes “authority support surfaces” more plausible than before

The vision-doc work explicitly recommends more **supportive interfaces from crates**.
The 2025 survey says docs and source remain the main learning surfaces.
That combination makes authority maps, determinism notes, and sandbox recipes more credible as part of a crate’s product surface rather than as private maintainers’ lore.

## Main judgment after the pass

The worthy crate here is not another sandbox.
It is the boring contract layer that can hand other people:

- one **authority pack**,
- one **authority-surface receipt**,
- one **authority-profile report**,
- one **determinism-surface report**,
- one **capability-injection report**,
- one **sandbox-recipe manifest**,
- one **authority-check report**,
- and one **authority diff**.
