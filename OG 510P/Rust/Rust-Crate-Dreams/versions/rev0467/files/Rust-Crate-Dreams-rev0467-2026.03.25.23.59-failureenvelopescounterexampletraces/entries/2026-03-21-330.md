# Entry 330 — Trusted Publishing Tooling Kit deepened for provider scope, claim basis, trigger policy, and publish-mode truth

This pass deepened **P-0175 Trusted Publishing Tooling Kit** instead of adding another provenance lane, another registry-auth doctor, or another generic CI OIDC helper.

## Why this lane earned another serious pass

The archive already knew crates.io trusted publishing mattered.
What it still lacked was a build-shaped answer for *which truths actually belong in one reviewable trusted-publishing support contract*.

Current substrate is now strong enough to make that precise:

- RFC 3691 already defines crates.io trusted publishing as an OIDC-based short-lived token flow with workflow claims;
- crates.io now supports **GitHub Actions** and **GitLab CI/CD**, but GitLab support is explicitly **GitLab.com-only** today;
- crates can now enable **trusted-publishing-only mode**, so migration/fallback posture is no longer background detail;
- crates.io now blocks especially risky GitHub triggers like `pull_request_target` and `workflow_run` from trusted publishing;
- GitHub’s OIDC docs now make reusable-workflow routing and `job_workflow_ref` visible enough that “the workflow filename matched” is no longer a sufficient identity story;
- GitLab’s ID-token docs now make `aud`, `sub`, and environment/ref-sensitive subject context explicit enough that GitLab claim basis cannot be hand-waved as “same as GitHub, but different YAML”.

That means a worthy crate here should not simply say “supports trusted publishing”.
It should say **which provider host is supported, which claim route defines the trusted publisher, which triggers are allowed, which publish mode is in force, and what the rehearsal actually proved**.

## What moved this time

The main planning move was to stop treating “trusted publishing” as one blob.

This pass elevated five review objects into first-class status for **P-0175**:

1. **provider-scope truth** — GitHub Actions, GitLab.com, self-hosted/manual-review, or future provider;
2. **claim-basis truth** — issuer, audience, repository/project, workflow route, reusable-workflow route, ref, and environment context;
3. **trigger-policy truth** — eligible, blocked, unsupported, or manual-review-only;
4. **publish-mode truth** — trusted-publishing-only, mixed migration, token fallback, or manual publish;
5. **rehearsal-result truth** — what was observed, inferred, blocked, or still needs human review.

## Why this matters now

The ecosystem evidence is now sharp enough that the missing layer is no longer vague:

- GitHub’s OIDC flow now clearly requires `id-token: write` and exposes reusable-workflow identity claims;
- GitLab ID tokens expose a different claim model with configurable `aud` and `sub` posture;
- crates.io’s current GitLab.com-only support means host/issuer scope is now a real support boundary instead of trivia;
- trusted-publishing-only mode means “OIDC exists” and “this release path is allowed” are no longer the same truth.

That means a worthy crate should not let “OIDC release configured” quietly over-claim provider support, workflow route identity, or migration completeness.

## Main judgment after the pass

A worthy trusted-publishing crate should now provide more than one rehearsal command and a vague policy file.
It should also provide:

- one explicit **provider-capability matrix**,
- one explicit **claim-basis receipt**,
- one explicit **trigger-policy report**,
- one explicit **publish-mode receipt**,
- one explicit **rehearsal report**,
- one explicit **provider drift diff**,
- and one conservative rule for when useful CI/OIDC facts are still too host-specific, too mixed-mode, or too incomplete to bluff a universal green result.
