# Entry 241 — Wasm component shipkit deepening around tooling lineage, world locks, and composition closure

This pass did **not** invent a brand-new Wasm lane.
It sharpened **P-0206 Wasm Component Artifact + Conformance Kit** into a more believable shipping-contract crate.

## Why this moved now

The Wasm component substrate is now real enough that the missing value is no longer just “please make Rust build a component somehow.”
The sharper gap is a **stable artifact and review layer above shifting tooling paths**:

- the current Rust component-model docs now say that while `cargo-component` used to be recommended, it is **being deprecated** because native tooling can be used directly; that means ordinary teams need a contract above a moving build path rather than another forever-builder wrapper. [Sources: component-model Rust docs; cargo-component repo/release state]
- Rust’s 2026 project goals explicitly call out **Wasm Components** as a flagship area, including work to improve and stabilize component targets. [Sources: Rust project goals 2026]
- the composition docs say tooling is still early and warns that tools are inconsistent about **interface-version inference/injection**, so package/world/version truth cannot stay implicit. [Sources: component-model composing docs]
- Wasmtime already supports **running components with custom exports** through `wasmtime run --invoke`, so components increasingly have a real exercise surface that should be captured rather than rediscovered. [Sources: Wasmtime CLI/component-model docs]
- the `wasm32-wasip3` target already exists, outputs a **component** rather than a core module, and remains explicitly transitional in the rustc book, which means target/runtime posture must stay visible. [Sources: rustc platform support docs]
- Wasmtime also had a February 2026 security advisory around the now-default `component-model-async` path, which is a reminder that runtime/exercise posture should stay explicit rather than hidden behind “component built successfully.” [Sources: Wasmtime security advisory + release notes]

So the gap is not “no one can build components.”
The gap is that teams still lack a **boring, reviewable component bundle** that states:

- how the component was built,
- what exact world/package/version contract it carries,
- whether imports are fully closed or still host-supplied,
- and how another person can actually exercise it.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another runtime, not another universal builder, and not a replacement for Cargo, `cargo-component`, WAC, `wasm-tools`, or Wasmtime.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-built Wasm components and their WIT/composition contract**, 
- above today’s native `wasm32-wasip2`/`wasm32-wasip3`, `cargo-component`, WAC, and Wasmtime substrate,
- with three first-class review objects that were previously still too implicit:
  1. **tooling lineage**
  2. **world lock**
  3. **composition closure**

## Main judgment after the pass

A worthy Wasm-component shipkit should now provide not only a bundle format, but also:

- explicit **tooling-lineage truth** (`native_target_build`, `cargo_component_transitional`, `native_plus_wac_compose`, etc.),
- explicit **world-lock truth** for package/world/interface/version matching,
- explicit **composition-closure truth** for bundled, host-supplied, or transitively-open imports,
- and a compact review bundle that another person can exercise with Wasmtime or a custom host without reconstructing the whole build path.

That is a much sharper and more believable contribution than “yet another Wasm helper crate.”
