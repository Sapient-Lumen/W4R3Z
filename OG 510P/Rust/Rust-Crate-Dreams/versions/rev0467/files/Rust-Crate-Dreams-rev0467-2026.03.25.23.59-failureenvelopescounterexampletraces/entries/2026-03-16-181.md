# Entry 181 — workspace tool manifests and install-policy cooldowns promoted into a first-class lane

This pass did not add a new proposal.
It upgraded two early archive ideas that had become much more important than their original drafts suggested:

- **P-0055 Cargo Workspace Toolchain Manifest Kit**
- **P-0056 Cargo Install Policy & Cooldown Kit**

## Why these moved now

Several official signals now line up unusually well.

### 1. Cargo still does not offer a first-class workspace tool dependency model

The Cargo docs make several important facts explicit:

- `cargo install` is a user/system-level command,
- its install root follows a specific precedence order,
- local project config is ignored for ordinary install flows,
- and Cargo external subcommands still depend on executable discovery through PATH / `$CARGO_HOME/bin`.

That means the missing value is no longer “how do we install binaries at all?”
The missing value is a **workspace manifest + lock + runner + receipt** layer above installer substrate.

### 2. Install defaults and install policy are still meaningfully under-specified for real teams

The `cargo install` docs are still explicit that:

- packaged lockfiles are ignored by default unless `--locked` is used,
- `--no-track` disables Cargo’s install tracking and concurrent-install protection,
- and install roots are a real decision surface.

That is already enough to justify an install-policy crate.

### 3. `pubtime` made cooldown policy much more real

The crates.io development update says index entries now include `pubtime`, and explicitly names future Cargo cooldown periods as a supported use case.

That is a strong reason to rewrite the old install-policy idea as a crate for:

- lockfile stance,
- cooldown gates,
- waiver ledgers,
- and install receipts.

### 4. Cargo’s plugin ecosystem is still first-class enough to deserve boring support layers

The Cargo 1.94 development-cycle update again highlights external plugin crates because Cargo cannot be everything to everyone.

That makes a workspace-managed runner/receipt layer more plausible, not less.

## Current judgment

The worthy crates here are not:

- a magical replacement for rustup,
- a vague “dev environment manager”,
- or another ad hoc wrapper around `cargo install`.

The worthy crates are the boring, layered artifacts above today’s substrate:

1. a **workspace tool manifest / lock / runner receipt** crate, and
2. an **install policy / cooldown / waiver / receipt** crate.

That feels more strategically honest than inventing another generic setup tool.
