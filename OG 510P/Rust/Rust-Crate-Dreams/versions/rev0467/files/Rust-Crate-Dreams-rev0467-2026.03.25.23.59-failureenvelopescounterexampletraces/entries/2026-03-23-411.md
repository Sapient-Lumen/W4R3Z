# Entry 411 — compile-iteration deepened around framework-route splits, restart ceilings, and latency-budget truth

This pass chose to **deepen** the current top frontier instead of adding another new lane.

The archive re-read the latest revision, checked fresh official and primary-source signals again, and then asked a narrower question:

> if **P-0537 Compile Iteration Feedback Kit** is really worthy, what does it have to provide other people in practice across UI, web, desktop, mobile, and long-running-process workflows?

The answer was that the lane still needed three things to become more implementation-ready:

1. **framework-route clarity** — the repo needed a sharper lattice for Dioxus-style RSX/asset/hotpatch routes, Tauri-style Rust-reload plus frontend-devserver flows, and Trunk / cargo-leptos style immediate CSS-visible updates;
2. **restart ceilings** — the repo needed an explicit artifact for when a framework can feel fast while still requiring restart or full rebuild for some edit classes;
3. **budget truth** — the repo needed a compact way to distinguish “instant visual update” from “Rust logic is ready” and from “the process restarted and is usable again”.

## Why this deepening pass earned a full revision

Fresh current sources make the distinction sharper than it was yesterday:

- the March 2026 Rust challenges note still frames compile time as the universal productivity tax and explicitly says hot reloading and faster linking can have outsized leverage;
- the 2025 compiler-performance survey still treats incremental rebuilds after small changes as one of the most important workflows and says the build experience differs wildly across users and workflows;
- Dioxus 0.7 now explicitly documents **three forms** of hot reloading — RSX, assets, and Rust hot reloading — while also spelling out edit classes that still require a full rebuild unless `--hotpatch` is enabled;
- Tauri’s current CLI docs join “hot-reloading for the Rust code” with a `build.devUrl` / `beforeDevCommand` route that usually starts a frontend dev server, which means a crate should not flatten frontend HMR and Rust iteration into one surface;
- and current Leptos ecosystem docs still make immediate CSS/browser updates via `trunk` / `cargo-leptos` visible enough that “the page changed instantly” can be true while the stronger “Rust logic feedback loop is solved” is still unproven.

That combination means **P-0537** is strongest when it owns one boring, reviewable answer to:

- what route actually changed the running program or page,
- which edit classes still require rebuild or restart,
- what “ready” means for the latency budget being measured,
- and where framework marketing or user delight stops being a stronger support claim.

## Main judgment after this pass

The top frontier does **not** need to change again.
It should still begin:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But P-0537 is now stronger because the repo no longer only says “hot reload is important.”
It now has a clearer artifact path for **reload surface**, **restart fallback**, and **latency budget** across several real framework families.

## What should count as a worthy crate contribution in this lane now

A worthy compile-iteration crate should provide other people:

1. **one reload-surface report** that says whether the change was markup, CSS/static asset, frontend HMR, Rust logic hotpatch, or only rebuild/restart;
2. **one restart-ceiling artifact** that says which edit classes still force a rebuild or restart even when the framework is generally pleasant;
3. **one latency-budget report** that says what “ready” meant: visual change, logic ready, or restarted app ready;
4. **one cross-framework vocabulary** that can compare Dioxus, Tauri, Trunk/cargo-leptos, plain watcher loops, and future relink workflows without pretending they are the same thing;
5. **one portable support bundle** that another engineer can inspect later without re-running the exact setup.

If a candidate crate cannot produce those artifacts, it is probably still one of these instead:

- a framework-local dev server,
- a watcher wrapper,
- a linker experiment,
- a runtime hotpatch engine,
- or a benchmark anecdote.

Useful, yes.
But not the full support-contract layer this archive now thinks is missing.
