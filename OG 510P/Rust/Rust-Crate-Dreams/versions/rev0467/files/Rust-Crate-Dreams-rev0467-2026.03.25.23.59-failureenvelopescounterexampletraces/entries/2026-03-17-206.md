# Entry 206 — crate lifecycle surfaces promoted as the background-work / shutdown-truth lane

This pass added a new top-level proposal: **P-0520 Crate Lifecycle Surface Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing structured-concurrency substrate, graceful-shutdown frameworks, and receiver-facing lifecycle support into one vague “better async UX” story.

## Why this moved now

Several current Rust and ecosystem signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good lifecycle lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profiles** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- **successor / off-ramp support** via **P-0515**,
- **setup/configuration scenarios** via **P-0516**,
- **performance envelopes** via **P-0517**,
- **observability surfaces** via **P-0518**,
- and **authority surfaces** via **P-0519**.

But it still lacked a good answer to:

- “Once a team chose a crate, what exactly does the crate hand them so they can understand background work, cancel safety, and shutdown/drain obligations?”

That left the archive with better answers for **choice**, **setup**, **failure**, **migration**, **perf**, **telemetry**, and **authority** than for **steady-state task and shutdown behavior**, which is strange for a language and ecosystem that lean heavily on async runtimes and long-lived services.

### 2. Official and ecosystem substrate now make this a contract problem, not a primitives problem

Tokio’s graceful-shutdown docs already frame shutdown as a three-step discipline.
`CancellationToken` and `TaskTracker` already provide signal-and-wait substrate.
`JoinHandle`, `AbortHandle`, and `AbortOnDropHandle` already make detaching versus aborting explicit.
Tokio’s I/O docs already show that some operations are cancel-safe, some preserve partial progress, and some are not cancel-safe.

That means the sharper question is no longer “can Rust model async lifecycle at all?” but “what portable artifact should sit above today’s substrate so a crate can tell downstream users what it promises?”

### 3. Current lifecycle tools are useful but fragmented at the crate boundary

`async_shutdown` and `tokio-graceful-shutdown` help implement graceful stop flows.
`task_scope` and `moro` show demand for structured concurrency and cancellation propagation.
What is still missing is the boring pack that can say:

- these components do background work,
- these handles detach on drop,
- these operations are cancel-safe or partially-progressing,
- this shutdown sequence is mandatory to avoid loss,
- and this is how the lifecycle surface changed across releases.

### 4. Rust’s current messaging makes lifecycle support surfaces more plausible than before

The vision-doc work explicitly recommends more **supportive interfaces from crates**.
The 2025 survey says docs and source remain the main learning surfaces.
That combination makes lifecycle packs feel like product support artifacts rather than maintainers’ private notes.

## Main judgment after the pass

The worthy crate here is not another runtime.
It is the boring contract layer that can hand other people:

- one **lifecycle pack**,
- one **background-work receipt**,
- one **cancellation-surface report**,
- one **shutdown-obligation report**,
- one **drain-recipe manifest**,
- one **race/retry-safety report**,
- one **lifecycle-check report**,
- and one **lifecycle diff**.
