# Entry 164 — assurance cases become review-contract-first

This pass again chose **not** to add another narrow proposal.

The better move was to make **P-0503 Assurance Case Workbench Kit** much more handoff-ready.
The archive already knew that Rust’s safety-critical direction is getting more serious.
What it still under-specified was the missing review layer above the newly stronger bundle and verification substrate.

## Main judgment

The sharper missing crate here is not “a Rust assurance-case editor”.
It is a boring workbench that can answer:

> what claims are being made, which evidence currently supports them, what is still assumption or manual review, and what materially changed since the last assurance pack?

That sounds close to the earlier proposal, but the missing details mattered.
The old version still behaved too much like a standards-export essay.
The revised version is much more explicit about:

1. **evidence import**,
2. **conservative claim status**,
3. **change-impact diffing**, and
4. **export lanes as optional compatibility surfaces**.

## Why these changes were the right ones

### 1. P-0503 needed a first-class evidence index

The archive previously talked about “linking evidence to claims”, but that was still too vague.
The revised version now freezes a much sharper receiver-facing contract:

- imported artifact ID,
- evidence class,
- provenance,
- freshness,
- trust level,
- claim linkage,
- and automation/manual status.

That is much closer to something another team could really implement.

### 2. The proposal needed to separate internal status from export notation

A good assurance crate cannot treat GSN or SACM export as the primary truth.
It needs an internal Rust-friendly model that can still say:

- this claim is `partial`,
- this one is `blocked`,
- this evidence is `stale`,
- and this top-level result still requires manual review.

That is now explicit in the schemas and scenarios.

### 3. The repo needed a memory aid for upper-layer boundaries

The new meta note records another reusable stack rule:

- evidence producers,
- bundle/profile substrate,
- assurance-case assembly and review,
- optional standards-shaped exports,
- and separate organization-specific certification workflows.

That should reduce future drift toward vague “safety certification platform” language.

### 4. P-0503 needed fixture-first planning

The proposal now has a much better answer to:

> what concrete files should another maintainer, customer, or assessor receive?

The new fixture pack gives it:

- an assurance profile,
- a claim graph,
- an evidence index,
- a claim-status report,
- an assurance-diff report,
- and a review-pack manifest.

That is a lot closer to something another builder could actually start implementing.

## New planning stance

For the next few passes, the archive should prefer:

- treating **P-0503** as a conservative upper-layer review/import crate,
- reusing **P-0256** for bundle semantics,
- importing **P-0485** and **P-0264** outputs without flattening them,
- and keeping GSN/SACM/editor surfaces as optional compatibility lanes.

It should **not** drift into:

- another decorative diagram-first assurance idea,
- a fake “push button certification” story,
- or a crate that silently owns regulator- or company-specific lifecycle workflows.
