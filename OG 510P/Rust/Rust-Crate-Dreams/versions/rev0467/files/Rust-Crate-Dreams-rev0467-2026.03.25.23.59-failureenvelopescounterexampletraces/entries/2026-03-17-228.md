# 2026-03-17 (228) — crate upgrade-pack productization pass

This pass did **not** add a new lane.
It sharpened **P-0514 Crate Upgrade Pack Kit** into a more implementation-ready `0.1` shape.

## Main judgment

The missing value is still **not** another semver checker, another changelog generator, another release bot, or a universal codemod platform.
The sharper missing layer is a **maintainer-facing upgrade contract** that records:

- what kind of upgrade hazards exist between `from -> to` lanes,
- what machine-fix capability was actually observed and where it applies,
- which feature/target/runtime/package combinations were really checked,
- and where a downstream user still needs explicit behavior review or manual migration.

## Why this lane looks sharper now

- Rust’s current vision work explicitly argues that crates need more **supportive interfaces**, not just powerful abstractions.
- The 2025 State of Rust survey still says **online documentation** and **studying the code** are the main learning surfaces, which raises the value of structured migration artifacts over changelog prose alone.
- The cargo-semver-checks project-goal work makes the publish-path evidence story more real, which makes the missing layer increasingly the downstream-facing artifact above raw verdicts.
- `cargo fix`, edition migration, rustc JSON diagnostics, and `rustfix` make machine-fix capture and applicability boundaries concrete enough that the missing value is increasingly the joined receipt, not the bare substrate.
- Release automation tools such as release-plz and cargo-release keep getting better at versioning and publishing, but that still does not tell a downstream user which upgrade lane was checked and where behavior review begins.

## What to keep separate

- Keep **P-0514** separate from SemVer/public-API evidence (**P-0244** / **P-0483**).
- Keep **P-0514** separate from compile-time guidance (**P-0512**) and runtime handoff (**P-0513**).
- Keep **P-0514** separate from release automation / changelog tooling.
- Keep **P-0514** separate from domain-specific migration workbenches.

## Preferred proving grounds

- crates with renamed APIs where `cargo fix` or rustfix can repair source but not manifest/docs/config changes
- crates whose default feature or backend policy changes without a simple source rewrite
- framework crates where a minor release keeps API shape compatible but shifts runtime or behavior defaults
- workspaces where the checked migration lane only covers a library member while binaries/examples remain higher-touch
- widely used crates that already run SemVer checks and release bots but still answer upgrade questions manually in issues or release notes
