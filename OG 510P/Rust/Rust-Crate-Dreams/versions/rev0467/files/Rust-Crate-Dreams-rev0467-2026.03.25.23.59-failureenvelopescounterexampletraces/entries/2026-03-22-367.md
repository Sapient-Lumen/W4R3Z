# Entry 367 — Cargo script work deepened around frontmatter authority, discovery scope, invocation interpretation, cache residency, and export lineage for P-0435

This pass deepened **P-0435 Cargo Script Workbench Kit** instead of adding another script runner, another “shareable snippet” helper, or another generic repro template.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the Cargo script goal explicitly treats single-file Cargo packages as a way to reduce friction for bug reports, educational material, prototyping, and small utilities;
- Cargo’s unstable docs now pin down concrete single-file-package semantics: no auto-discovery, embedded frontmatter, inferred/defaulted manifest fields, disallowed manifest fields, a hashed default target-dir under Cargo home, and lockfile placement in that target-dir;
- the same docs distinguish `cargo <path>` from `cargo run --manifest-path <path>` by config-root choice and default verbosity;
- the Cargo 1.94 development-cycle post says Cargo script is intentionally **starting with workspace auto-discovery disabled** while broader workspace/config discovery remains an active design seam;
- and the goals page makes rustfmt, rust-analyzer, rustc frontmatter behavior, and improved Cargo diagnostics part of the stabilization path.

Together these make one conclusion stronger: the worthy crate here is not just “run `.rs` files with dependencies”.
It is a crate that helps other people inspect **what frontmatter was authoritative, what discovery rules applied, how the invocation was interpreted, where the cache and lock actually lived, and how to export the script into a normal package without losing provenance**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still **not** another launcher.
It is a **stable support-contract layer** above Cargo’s single-file-package substrate.

This pass promotes six P-0435 review objects into first-class status:

1. **frontmatter-authority receipt** — what manifest content was explicit, inferred, defaulted, or rejected;
2. **discovery-scope receipt** — what workspace/config discovery rules were in or out of scope;
3. **invocation-interpretation receipt** — whether the run used manifest-command or subcommand semantics and what that changed;
4. **cache-residency receipt** — where `CARGO_TARGET_DIR`, lockfile, and derived build products actually lived;
5. **export-lineage plan** — how to materialize a normal package while preserving semantic provenance and human-choice points;
6. **script support-bundle manifest** — the compact handoff artifact joining those truths.

## Why these objects matter

Current substrate now makes several mistakes easier to commit unless the archive models them explicitly:

- a reviewer can confuse **explicit frontmatter** with **Cargo-inferred defaults**;
- “workspace auto-discovery disabled” can be mistaken for “no parent configuration mattered”;
- `cargo <path>` can be treated as equivalent to `cargo run --manifest-path <path>` even though Cargo documents different config-root and verbosity behavior;
- a script can look local and disposable while actually writing its lockfile into a hashed Cargo-home target-dir lane;
- and “export this to a real package” can sound trivial until file layout, package naming, edition/default migration, and manifest lift-out decisions must be preserved.

## New archive-level stance

For single-file Cargo package work, the archive should now prefer this layering:

1. **P-0435** for frontmatter authority, discovery scope, invocation interpretation, cache residency, and export lineage;
2. **P-0489** for broader build-dir / path-consumer migration when internal Cargo layouts become the question;
3. **P-0490** for lock-contention incidents once shared-root waiting becomes the question;
4. Cargo script / single-file-package docs and the stabilization goal for the moving upstream substrate.

That keeps the portfolio from minting another crate that merely says “Cargo can run scripts now” without clarifying what was inferred, what discovery was disabled, what config still mattered, and how to hand the result to someone else.

## What should count as a worthy crate contribution after this pass

A worthy Cargo script-facing contribution should now be able to answer all of these cleanly:

1. **What frontmatter was explicit, inferred, defaulted, or rejected?**
2. **What discovery scope applied, and what stayed deliberately out of scope?**
3. **Was the invocation interpreted as a manifest-command lane or a subcommand lane?**
4. **Where did cache and lock state actually reside?**
5. **What would need to change to export this into a normal package?**
6. **Which facts are hard Cargo semantics versus advisory portability guidance?**

If a candidate crate cannot answer those questions, the archive should usually treat it as script convenience rather than a serious support contract.
