# Entry 319 — cargo-build-dir-consumer-transition deepened for adapter-viability windows, Cargo-version floors, and dual-support honesty

This pass deepened **P-0489 Cargo Build-Dir Consumer Transition Kit** instead of opening another generic migration helper or output-path abstraction.

## Why this lane earned another serious pass

The sharper missing value is no longer just “which local helper scrapes Cargo internals?”
Cargo's March 2026 **Build Dir Layout v2** testing post now names concrete breakage families and even gives some **version-sensitive** adapter advice.
That means a worthy crate in this lane should not stop at consumer audits and adapter names.
It should also publish whether a suggested adapter is actually:

- documented and stable now,
- documented only above a Cargo version floor,
- nightly-only,
- heuristic-only,
- or still blocked on upstream.

## What moved this time

This pass promoted **adapter-viability windows** into a first-class review object for **P-0489**.

The archive already had sharper answers for:

- which consumer family a break belongs to,
- which path contract is probably wanted,
- and which adapter name seems most plausible.

What it still needed was a disciplined answer to:

> “How strong is that adapter claim in *this* Cargo window, and do we still need fallback or dual-layout support?”

## Main judgment after the pass

A worthy build-dir transition contribution should not stop at:

- one consumer inventory,
- one path contract,
- and one list of suggested adapters.

It should also provide:

- one explicit **adapter-viability report**,
- one honest **Cargo-version floor / availability class** when advice is version-windowed,
- and one conservative **fallback / dual-support** story when migrations must temporarily tolerate old and rehearsed layouts together.
