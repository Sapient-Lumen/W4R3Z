# Entry 155 — resolver why-bundles also need feature-origin and weak-forwarding truth

This pass again did **not** add another top-level proposal.

Instead, it sharpened **P-0468 Cargo Resolver Explanation Kit** where the archive still had unusually high leverage: the crate now has a clearer plan for **feature origin, hidden optional-dependency aliases, and weak dependency forwarding preconditions** above today’s mixed Cargo surfaces.

## Main judgment

The important missing crate is not another feature browser.
It is a **receiver-facing resolver bundle** that can tell another person:

- whether a feature name is explicit, implicit, hidden by `dep:`, or not really a public feature at all,
- whether a dependency-feature clause activated the optional dependency directly,
- whether a dependency-feature clause only forwarded a feature if some other path already activated that dependency,
- and whether the answer is directly observed, conservative, or still manual-review-required.

## New planning stance

**P-0468** should now be read as a crate that hands other people:

- one `resolve-why.lock`,
- one `feature-causes.json`,
- one `version-choices.json`,
- one `duplicate-builds.json`,
- one `lane-partition.report.json`,
- one `platform-coverage.report.json`,
- one `unification-scope.report.json`,
- one `feature-intent.report.json`,
- one `dependency-origin.report.json`,
- one `feature-origin.report.json`,
- one `resolver-choice.receipt.json`,
- and one `resolution-diff.report.json` that is allowed to say when the surprise came from hidden aliases or weak forwarding preconditions, not just from coarse feature-state changes.

That is a sharper contract than “Cargo feature explanation tool”.
