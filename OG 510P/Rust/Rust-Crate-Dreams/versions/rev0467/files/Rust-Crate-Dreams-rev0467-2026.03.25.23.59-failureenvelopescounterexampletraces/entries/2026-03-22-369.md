# Entry 369 — Crate knowledge pack work deepened around authority, hosted-doc truth, example lineage, slice policy, and cross-sector territory mapping

This pass continued the broad “what is still truly missing in Rust crates?” work, but chose **productization over proliferation**.

The archive already had enough evidence to justify **P-0536 Crate Knowledge Pack Kit**.
What it did not yet have was an implementation-ready plan that makes the lane precise enough to build without it turning into:

- another docs portal,
- another rustdoc JSON wrapper,
- another docs coverage percentage tool,
- or another “chat with your crate” gimmick.

So this pass did three things:

1. deepened **P-0536** into a more buildable `0.1` shape,
2. added schema/fixture scaffolding for the first receiver-facing artifacts,
3. and added a **cross-sector opportunity map** so future archive passes keep extreme breadth without opening redundant lanes.

## Why this lane deserved more work now

Fresh official signals still pull in the same direction:

- the 2025 State of Rust survey says online documentation remains the preferred canonical reference, code study remains a major learning route, and some learning activity appears to be moving toward LLM tooling;
- the March 2026 challenges write-up says ecosystem pain does not disappear with expertise — it shifts into async complexity, embedded maturity gaps, certification friction, and other domain-specific support problems;
- docs.rs now documents hosted rustdoc JSON, hosted README behavior, docs.rs-specific build metadata, sandbox/resource ceilings, and hosted cross-compilation posture more concretely than many downstream tools reflect;
- Cargo/rustdoc still keep JSON output behind an unstable path, which makes **imported provenance** and **version-aware normalization** especially important for any reusable crate-side handoff format;
- and the Rust Foundation’s 2026–2028 strategy keeps infrastructure and sustainable maintenance first-class, which argues for boring, reusable support artifacts over clever one-off integrations.

Together that means the archive should not merely say “knowledge packs sound good.”
It should say **what exact bundle another person receives**, **which facts are authoritative**, **which ones are inferred**, and **what machine consumers are and are not allowed to treat as canonical**.

## Main repo judgment from this pass

The worthy move here is **not** inventing more proposals.
It is making the strongest ones look like real crates.

For **P-0536**, the real product promise should now be:

- one compact, provenance-aware pack for a crate’s public API, official examples, and hosted documentation truth;
- one small slice format for support/search/assistant consumers;
- one explicit split between rustdoc/docs.rs authority and local inference;
- one visibility map for feature / target / `cfg`-sensitive surfaces;
- one diff object for reviewing release-to-release knowledge drift.

If a crate idea in this area cannot supply those things to other people, it is still probably substrate or wrapper work.

## New frontier lesson

The archive now has a clearer answer to “what should a worthy crate provide other people?”:

1. **a compact receiver-facing artifact**, not just library internals;
2. **explicit authority classes**, not one flattened verdict;
3. **imported upstream truth before guessed truth**;
4. **small slices for real workflows** (support, search, review, assistant ingestion);
5. **diffable drift objects** for release review;
6. **tight lane boundaries** that prevent “one mega crate” sprawl.

That answer scales across many sectors.
The new cross-sector map makes a broad but disciplined claim:

- the archive is already rich in domain-specific interoperability workbenches;
- the still-underpriced opportunities remain ecosystem support contracts for docs, build friction, stewardship, evidence, and adoption risk;
- and future broad passes should usually connect sector-specific needs **back into those shared support layers** instead of opening fresh duplicates.
