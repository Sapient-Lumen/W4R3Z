# Entry 240 — Python wheel/free-threading shipkit deepening around ABI target class, thread-support declarations, and variant horizon

This pass did **not** invent a brand-new Python lane.
It sharpened **P-0466 Python Wheel ABI & Free-Threading ShipKit** into a more believable shipping-contract crate.

## Why this moved now

The Python/Rust substrate is now strong enough that the missing value is no longer “somehow build Rust for Python.”
The sharper missing layer is a **maintainer-facing release contract** above existing substrate:

- PyO3 already documents real packaging and multi-version distribution paths, including `abi3`. citeturn324357view5turn539480search1
- PyO3 now treats free-threaded support as a first-class concern; in current docs it defaults to assuming thread-safe modules and lets crates opt out with `gil_used = true`. citeturn377112view1turn790458view2
- Python 3.14 made free-threaded CPython officially supported rather than experimental. citeturn404209view3
- But Python’s own extension docs still say the free-threaded build does **not currently** support the Limited C API / Stable ABI, so projects need distinct `t` wheels today. citeturn790458view1
- maturin already has real free-threading support and specific policy changes for `3.13t`/`3.14`, but it also still has an open March 2026 issue to add `abi3.abi3t` wheel support for accepted PEP 803. citeturn324357view2turn790458view3turn596666view1turn404209view2
- cibuildwheel now treats free-threaded support as ordinary enough that `3.14+` wheels do not require the old experimental opt-in, while `3.13` still does. citeturn324357view3turn790458view4
- Python packaging is also moving toward **wheel variants**, which means a serious shipkit should not hard-code a forever-frozen assumption that wheel tags end at today’s axes. citeturn404209view0turn404209view2

So the gap is no longer “PyO3 and maturin do not exist.”
The gap is that teams still lack a **boring, reviewable, future-aware release artifact** for what exact Python compatibility promise they are making.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another binding generator, not another package uploader, and not another universal Python build backend.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-backed Python extension modules**,
- built on top of **PyO3 + maturin + wheel tooling** rather than replacing them,
- with three first-class review objects that were previously still too implicit:
  1. **ABI target class**
  2. **thread-support declaration**
  3. **variant horizon**

## Main judgment after the pass

A worthy Python-extension shipkit should now provide not only a wheel matrix, but also:

- explicit **ABI target-class truth** (`version_specific`, `abi3`, split free-threaded, `abi3t` horizon),
- explicit **thread-support declarations** (`gil_used`, PyO3 assumptions, manual-review zones),
- explicit **variant-horizon honesty** for `abi3t` and wheel-variant futures,
- and a compact release bundle that reviewers can sign off on without reverse-engineering CI.

That is a much sharper and more believable contribution than “yet another PyO3 helper.”
