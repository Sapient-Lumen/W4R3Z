# 2026-03-17 (230) — crate interop-profile productization pass

This pass did **not** add a new lane.
It sharpened **P-0511 Crate Interop Profile Pack Kit** into a more implementation-ready `0.1` shape.

## Main judgment

The missing value is still **not** another ranking engine, another producer-side support contract, another semver checker, or another domain-specific conformance suite.
The sharper missing layer is a **shared ecosystem boundary contract** that records:

- which shared profile is actually in view,
- what kind of profile it is,
- which public surfaces and coupling rules it requires,
- which adapters or bridge obligations are part of fitting the profile,
- how much of pairwise compatibility is static versus witnessed,
- and where manual review still begins.

## Why this lane looks sharper now

- Rust’s current vision work explicitly argues that users need help navigating crates **and** that Rust needs smoother interop between libraries.
- The 2025 State of Rust survey still says **online documentation** and **studying the code** are the main learning surfaces, which raises the value of stable shared-profile artifacts over folklore.
- The EII goal and evolving-traits work both strengthen the case for explicit, evolvable ecosystem customization points.
- Current ecosystem substrate is already real — `http`, `tower-service`, `tower`, `futures-core`, and Serde all define reusable shared boundaries.
- Current framework docs like `axum` show that shared middleware and protocol-agnostic reuse are already possible when crates meet at the same boundary.

## What to keep separate

- Keep **P-0511** separate from task-first decision packs (**P-0509**).
- Keep **P-0511** separate from producer-side capability contracts (**P-0510**).
- Keep **P-0511** separate from trait-evolution / customization-point planners (**P-0449** / **P-0452**).
- Keep **P-0511** separate from SemVer/public-API slice tools.
- Keep **P-0511** separate from domain-specific conformance or certification workbenches.

## Preferred proving grounds

- async libraries that use Tokio internally but want runtime-neutral public APIs
- middleware/service ecosystems built around `tower-service` + `http`
- framework families that rely on shared middleware reuse across crates
- Serde model crates that want to stay format-neutral rather than silently becoming transport-specific
- releases that look semver-compatible while quietly tightening ecosystem lock-in
