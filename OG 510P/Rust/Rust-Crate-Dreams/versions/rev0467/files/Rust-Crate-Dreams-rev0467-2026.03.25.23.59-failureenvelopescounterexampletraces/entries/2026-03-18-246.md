# Entry 246 — JAR/JNI native shipkit deepening around classifier dialect, native-access posture, and loader residency

This pass did **not** invent a brand-new Java interoperability lane.
It sharpened **P-0500 JAR/JNI Native ShipKit** into a more believable shipping-contract crate.

## Why this moved now

The Java / JVM / Rust substrate is now real enough that the missing value is no longer just “please make Rust callable from Java somehow.”
The sharper gap is a **boring package and support contract above already-working authoring tools**:

- current JDK docs now say `System.loadLibrary`, `System.load`, and native method binding are restricted/native-access surfaces rather than invisible runtime details;
- current JDK migration guidance makes `--enable-native-access` posture explicit for named modules versus `ALL-UNNAMED` class-path consumers;
- Maven already supports attached classifier artifacts and Sonatype Central now supports explicit Maven-plugin publication through the Central Publisher Portal;
- `os-maven-plugin` / `osdetector` have become a de-facto classifier dialect for JVM native dependencies, which means classifier **naming** is now part of the support contract rather than just a packaging afterthought;
- `jni` / `jni-rs` already provide serious Rust-side authoring substrate, so the sharp missing value is not raw JNI bindings.

So the gap is not “there is no Rust JVM tooling.”
The gap is that maintainers still rarely get one **reviewable JVM-native bundle** that says:

- whether classifier names are standard enough for ordinary downstream intake,
- what loader residency the package actually assumes,
- what native-access posture a modern JDK consumer must adopt,
- and how Central/Maven artifacts relate to those runtime claims.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another JNI wrapper, not another Gradle plugin set, and not another Maven publisher helper.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-built JVM native libraries published as Maven artifacts and consumed from Java/Kotlin**,
- above today’s JDK native-loading rules, Maven/Central publication substrate, `os-maven-plugin` conventions, and `jni-rs`,
- with three first-class review objects that were previously still too implicit:
  1. **classifier dialect**
  2. **native-access posture**
  3. **loader residency**

## Main judgment after the pass

A worthy JAR/JNI shipkit should now provide not only a classifier matrix, but also:

- explicit **classifier-dialect truth** (`os_detector_aligned`, `classifier_mapping_required`, etc.),
- explicit **native-access-posture truth** linking class-path or module-path loader shape to modern JDK runtime flags,
- explicit **loader-residency truth** for `java.library.path`, absolute loads, extraction-first flows, and manual-install stories,
- and a compact review bundle that another person can inspect without replaying Maven, Gradle, Central publication, and JVM loader code by hand.

That is a much sharper and more believable contribution than “yet another Rust-to-Java helper.”
