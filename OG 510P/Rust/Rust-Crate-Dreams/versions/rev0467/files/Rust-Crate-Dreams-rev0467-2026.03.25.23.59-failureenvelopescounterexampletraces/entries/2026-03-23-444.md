# Entry 444 — make comparison, refresh, and transition packets first-class, and move dependency lifecycle deeper into the practical core

This pass again chose **deepen over append**.

The archive already had:
- a stronger front-door pairing between **P-0509 Pathfinder** and **P-0536 Crate Knowledge Pack**,
- replayable basis locks,
- and sharper first-usable-release thinking.

What it still lacked was a clean answer to the next practical question:

> what happens **after** a team freezes a crate decision and the world changes underneath it?

That is where many real Rust users actually live:
- a new release appears,
- a docs surface shifts,
- a new advisory lands,
- an alternate registry or offline mirror enters the story,
- a Rust floor or target filter changes,
- or a once-acceptable dependency now needs a containment or replacement plan.

## Main judgment

Three repo moves were worth making now.

### 1. Treat **comparison**, **refresh**, and **transition** as separate packet families

The archive already had a good front-door story for choosing a starter set.
It still needed a stronger story for what happens next.

A worthy crate in the leading lanes should stop acting like one packet solves the whole lifecycle.
It should separate:
- the **comparator packet** used to choose,
- the **refresh / revalidation packet** used to decide whether a previous choice still stands,
- and the **transition packet** used when a dependency must be pinned harder, contained, replaced, forked, vendored, or retired.

That distinction is now practical because the official substrate keeps getting better at machine-readable replay and drift analysis:
- Cargo plumbing work is explicitly about more programmatic surfaces,
- Cargo build analysis is explicitly about historical build metrics and future replay/debugging uses,
- libtest JSON work exists because programmatic test output was already relied upon,
- and Cargo semver-checks work is explicitly about getting stronger breaking-change discipline onto the publish path.

### 2. Pull **P-0535 Dependency Lifecycle Transition Kit** forward in the practical queue

The archive had already identified lifecycle and off-ramp work as important.
This pass makes the planning sharper.

The Rust signals now point to a stronger need for a crate that helps teams answer:
- what is still acceptable to keep,
- what needs review,
- what needs containment,
- and what needs transition planning.

That conclusion is supported by multiple current signals at once:
- the challenges write-up says users still struggle with crate choice, trust, and domain maturity;
- the safety-critical post says many teams use crates early, then narrow or replace them later, and that stability is operational rather than abstract;
- crates.io now imports more trust surfaces, but those surfaces still do not settle architecture or lifecycle posture;
- malicious-crate notification policy is now intentionally more selective, which means teams need their own recurring refresh discipline instead of depending on high-noise public alerts;
- and the March 2026 Cargo advisory shows dependency acquisition and registry path assumptions are still part of the real risk surface, especially for alternate registries.

### 3. Add stronger archive rules so future passes do not silently rewrite frozen judgments

If the repo is going to keep describing packets, it needs stronger repo-level discipline too.

A future pass should not be allowed to silently overwrite:
- an old comparator packet,
- an old freeze-time basis,
- or a transition exception that has gone stale.

Instead it should append a refresh/revalidation layer and say why a previous answer still stands, or why it no longer does.
That is the point of the new archive promotion/freeze note.

## Salience consequence

This pass still does **not** justify a dramatic frontier rerank.
The front-door pair stays first.

But it does justify a practical change:
- **P-0535 Dependency Lifecycle Transition Kit** now belongs closer to the top implementation slice,
- because comparison alone is not enough for real adopters with long-lived systems, restricted delivery, or rising assurance demands.

## Practical queue consequence

The practical queue now reads best as:

1. **P-0509 + P-0536** — comparator packets and review packets with frozen basis locks
2. **P-0535** — refresh, revalidation, and transition packets for changing dependency posture
3. **P-0486** — debug capability packets with witness bundles
4. **P-0496** — source-parity / restricted-delivery packets
5. **P-0472** — docs.rs parity doctor and issue bundles
6. **P-0489** — build-dir dual-support transition
7. **P-0484** — target/support truth for hard domains
8. **P-0058** — native prerequisites and ABI provenance

Interpretation:
- pathfinder still gets a team to a reviewable starting point,
- knowledge packs still freeze the basis,
- but lifecycle transition is now what keeps that answer honest over time.

## What this pass says a worthy crate should provide other people

A worthy crate now needs a cleaner answer to **nine** practical questions:

1. **compare** — how do I choose among plausible options today?
2. **freeze** — what exact basis did that choice stand on?
3. **refresh** — what later facts changed and which did not?
4. **revalidate** — does the old choice still stand under the same task and policy?
5. **transition** — if it no longer stands, what next posture is being adopted?
6. **anchor** — what lock, patch, mirror, fork, or local override currently makes the posture hold?
7. **sharedness** — is that anchor team-shared or merely local?
8. **schema** — can downstream consumers survive evolution of the packet family?
9. **ceiling** — what still requires manual review?

If a proposal cannot answer those, it may still be interesting, but it is not ready for the practical core.
