# Entry 207 — crate resource surfaces promoted as the capacity / saturation-truth lane

This pass added a new top-level proposal: **P-0521 Crate Resource Surface Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing queues, caches, pools, rate limits, runtime knobs, and receiver-facing capacity truth into one vague “better performance and backpressure” story.

## Why this moved now

Several current Rust and ecosystem signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good capacity / saturation lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profiles** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- **successor / off-ramp support** via **P-0515**,
- **setup/configuration scenarios** via **P-0516**,
- **performance envelopes** via **P-0517**,
- **observability surfaces** via **P-0518**,
- **authority surfaces** via **P-0519**,
- and **lifecycle surfaces** via **P-0520**.

But it still lacked a good answer to:

- “Once a team chose a crate, what exactly does the crate hand them so they can understand queue depth, buffer growth, pool size, cache bounds, worker counts, and overload behavior?”

That left the archive with better answers for **choice**, **setup**, **failure**, **migration**, **telemetry**, **authority**, and **shutdown** than for **steady-state resource posture**, which is strange for a language used heavily for clients, services, pipelines, and long-lived processes.

### 2. Official and ecosystem substrate now make this a contract problem, not a primitives problem

Tokio already distinguishes bounded versus unbounded channels.
Tokio runtime builders already expose worker counts and thread-stack sizes.
`spawn_blocking` already documents the “spawn until a limit, then queue” behavior.
Reqwest already exposes pool sizing knobs.
Tower and Governor already expose concurrency, rate, burst, and replenish parameters.
Moka already exposes explicit capacity and weighted sizing.
Runtime metrics already expose queue depth and alive-task observations.

That means the sharper question is no longer “can Rust express resource limits at all?” but “what portable artifact should sit above today’s substrate so a crate can tell downstream users what it promises?”

### 3. Current tools are useful but fragmented at the crate boundary

The ecosystem has many excellent implementation and monitoring tools, but they still leave maintainers to assemble support truth by hand.
What is still missing is the boring pack that can say:

- these are the resource classes this crate uses,
- these are bounded versus effectively unbounded,
- this is what happens at saturation,
- these are the knobs that matter,
- these are the metrics worth watching,
- and this is how the resource surface changed across releases.

### 4. Rust’s current messaging makes resource support surfaces more plausible than before

The vision-doc work explicitly recommends more **supportive interfaces from crates**.
The 2025 survey says docs and source remain the main learning surfaces and that resource-usage pain remains visible.
That combination makes resource packs feel like product support artifacts rather than maintainers’ private tuning notes.

## Main judgment after the pass

The worthy crate here is not another queue.
It is the boring contract layer that can hand other people:

- one **resource pack**,
- one **resource-surface receipt**,
- one **capacity-profile manifest**,
- one **saturation-behavior report**,
- one **reclaim-obligation report**,
- one **resource-budget report**,
- one **resource-check report**,
- and one **resource diff**.
