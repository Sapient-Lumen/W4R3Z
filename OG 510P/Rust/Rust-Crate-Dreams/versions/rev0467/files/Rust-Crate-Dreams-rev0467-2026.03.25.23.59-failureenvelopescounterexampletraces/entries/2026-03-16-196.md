# Entry 196 — crate capability contracts promoted as a producer-side interop-truth lane

This pass added a new top-level proposal: **P-0510 Crate Capability Contract & Interop Profile Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing producer-side support claims, task-first crate choice, item-level availability truth, whole-project support contracts, and slice-specific API/MSRV/security tools into one fake metadata story.

## Why this moved now

Several current official Rust signals line up unusually well.

### 1. The new pathfinder lane exposed a second missing layer

The archive’s new **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit** gave the repo a stronger answer to the consumer-side question: “which crates fit this task?”

But that immediately exposes the producer-side weakness:
there is still no shared, machine-readable way for crate authors to publish their own runtime-coupling, `no_std`/`alloc` posture, docs posture, native obligations, or interop exports.

That makes “crate choice” and “crate support truth” adjacent but distinct missing crates.

### 2. Official vision-doc guidance now pressures both navigation and interop

The December 2025 vision-doc work says Rust should help users navigate the crates.io ecosystem and enable smoother interop between libraries.
That is a powerful hint that a worthy crate here is not just another ranking layer.
It is also a contract layer that lets libraries describe their own compatibility and interop posture in a more reusable way.

### 3. Today’s official metadata surfaces are real, but still too fragmented

Cargo’s docs give crate authors:

- tiny manifest metadata such as `keywords`, `categories`, `rust-version`, `build`, and `links`,
- a generic `package.metadata` table for external tools,
- docs.rs metadata for custom documentation builds,
- and rustdoc JSON as a machine-readable API substrate.

Meanwhile, crates.io now exposes security advisories, SLOC, and `pubtime` more directly.
Those are good building blocks.
But they still do **not** add up to one shared producer-side support/interop contract.

### 4. Slice tools exist, but the joined contract is still missing

Cargo’s `rust-version` docs explicitly point users to third-party tools like `cargo-msrv`.
The archive also already tracks real slice tools and goals around dependency policy, public API, and semver analysis.

That means the gap is no longer “there are no tools.”
The sharper gap is the boring **joined contract** above them.

## Current judgment

The worthy crate here is not:

- another registry frontend,
- another “best crates” list,
- another badge-only metadata pack,
- or another health/trust score.

The worthy crate is the boring producer-side contract layer that can hand other people:

1. one **capability contract**,
2. one **observed capabilities receipt**,
3. one **interop export map**,
4. one **profile conformance report**,
5. one **capability diff**,
6. and one explicit **manual-review boundary** when the support story still depends on human judgment.
