# Entry 260 — Crate persistence support sharpened around publication target, identity retention, and witnessed recovery

This pass did **not** add another serializer, another migration engine, another async file wrapper, or another embedded database.
It sharpened **P-0522 Crate Persistence Surface Pack Kit** into a more implementation-ready support crate.

## Why this moved now

The current Rust persistence story is no longer empty.
That changes the shape of the missing value.

- The December 2025 Rust vision-doc work explicitly says crates need more **supportive interfaces**.
- The 2025 State of Rust survey still says online docs and code remain the main learning surfaces.
- `std::fs::File` still distinguishes `sync_all` from `sync_data`, and still documents that close errors are ignored on drop.
- `std::fs::rename` still only works on the same mount point and has platform-specific replace behavior.
- `tempfile::NamedTempFile::persist` still says replacement is atomic, but also says neither file contents nor the containing directory are synchronized on return.
- `atomic-write-file` now documents a stronger no-intermediate-state overwrite path, but it also documents that symlink handling and metadata retention are real boundaries.
- `tokio::fs` still runs ordinary file operations via `spawn_blocking`, which helps ergonomics but does **not** create a stronger durability contract.
- redb still documents automatic recovery from crashes / power loss and a separate integrity-check / repair path for suspected external modification.

That combination means the missing crate is no longer “Rust needs file persistence primitives”.
The sharper missing crate is a **crate-authored persisted-state contract** above today’s substrate.

## Main planning move

This pass promoted five review objects to first-class status for **P-0522**:

1. **publication target** — which path object is replaced or committed, including symlink-versus-target truth,
2. **identity retention** — which metadata classes survive replacement and which may drift,
3. **durability boundary** — what success actually means at return time,
4. **compatibility authority** — why a format-stability claim should be trusted,
5. **recovery witness** — whether recovery/repair claims were merely declared or actually exercised.

That move matters because the archive had already named the lane, but it had not yet made the most surprising **publication / replacement / retention** boundaries concrete enough to survive real product planning.
This pass fixes that.

## Main judgment after the pass

A worthy persistence-support crate contribution for Rust should now provide **more than “format is stable”**.
It should provide:

- explicit **publication-target truth**,
- explicit **identity-retention truth**,
- explicit **durability-boundary truth**,
- explicit **compatibility-authority truth**,
- explicit **recovery-witness truth**,
- and one compact **persistence-surface diff** another maintainer or downstream user can inspect without reconstructing durable-byte behavior from serializer docs, storage-engine docs, and incident folklore.

That is more believable and more ecosystem-multiplying than either:

- “just use temp-file replacement”,
- “just say the wire format is stable”,
- or “just trust the backend” with no receiver-facing support contract attached.
