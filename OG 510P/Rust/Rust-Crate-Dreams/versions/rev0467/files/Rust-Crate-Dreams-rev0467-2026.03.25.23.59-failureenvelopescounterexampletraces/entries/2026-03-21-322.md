# Entry 322 — error-surface-contract-kit added for stable error identity, audience modes, remediation receipts, and sensitivity posture

This pass added a new top-level proposal: **P-0533 Error Surface Contract Kit**.

## Why this lane earned a slot

The archive already had better answers for:

- diagnostic rendering and span UX,
- CLI surface/output/exit posture,
- first-diagnosis and self-check support,
- secrets/redaction policy in the broad,
- and crate guidance / onboarding support.

It still lacked one receiver-facing answer to a common cross-cutting question:

> “What does this crate or application actually promise about its errors across codes, reports, JSON payloads, docs, hints, and sensitive detail?”

Current Rust error substrate now makes that absence concrete enough to justify a dedicated lane.

## What moved this time

The main planning move was to treat **error handling as a support contract layer**, not as derive-macro choice or renderer aesthetics.

This pass therefore promoted four review objects to first-class status:

1. **error-identity truth** — which code/class is actually stable enough for downstream automation or docs;
2. **audience-mode truth** — whether a surface is for end users, operators, developers, or machine readers;
3. **remediation-surface truth** — whether hints, retry guidance, and docs routes are authoritative or merely helpful;
4. **sensitivity-posture truth** — whether backtraces, attachments, snippets, or context objects are safe to expose.

## Why this matters

Without those objects, the ecosystem still permits a common shortcut:

- `thiserror` can truthfully say a public error type is easy to maintain,
- `anyhow` can truthfully say context layering is ergonomic,
- `miette` and `ariadne` can truthfully say diagnostics are rich and friendly,
- `error-stack` and `snafu` can truthfully say reports, attachments, chains, and backtraces are available,
- while a downstream consumer still has no compact answer for:
  - which error identities are actually stable,
  - which surface is safe to automate against,
  - whether “helpful” text is a real fix or retry guarantee,
  - and whether a rich report is safe to show outside an operator/debug context.

That is not just polish.
It is supportiveness.

## Main judgment after the pass

A worthy error-support contribution for Rust should now provide more than a derive macro, a context wrapper, or a polished renderer.
It should provide:

- one explicit **error-identity receipt**,
- one explicit **audience-mode receipt**,
- one honest **remediation-surface report**,
- and one conservative **sensitivity-posture receipt**.
