# Entry 320 — async-runtime-assurance-profile-kit added for runtime choice, shutdown truth, and qualification-basis evidence

This pass opened **P-0532 Async Runtime Assurance Profile Kit** instead of doing another Cargo-adjacent refinement.

## Why this lane earned a slot now

The current official Rust writing now says the quiet part out loud:

- the March 2026 Rust challenges post says async remains painful and that runtime lock-in is still a real ecosystem problem;
- the January 2026 safety-critical post says async is attractive for event-driven systems, but the runtime and qualification story is not settled at higher integrity levels;
- that same post explicitly recommends defining requirements for a **safety-case friendly async runtime**;
- and the 2026 project flagships keep safety-critical evidence on the main agenda while async language work continues separately.

That combination makes a new missing-crate lane viable.
The missing value is not another runtime implementation.
It is one boring crate that can publish:

- what runtime family a project actually chose,
- what allocation/scheduling/preemption assumptions come with that choice,
- what shutdown really means,
- and what evidence exists for any stronger support or qualification claim.

## Main judgment after the pass

A worthy contribution in this lane should not try to erase runtime differences.
It should instead make them reviewable.

The useful product is a compact pack that can honestly say:

- this project is relying on a Tokio-like hosted I/O runtime,
- or an Embassy-style cooperative embedded executor,
- or an RTIC-style interrupt-priority scheduler,
- and here is what that means for allocation, timing, shutdown, and evidence posture.

That is more valuable than another benchmark, another runtime abstraction layer, or another “async best practices” guide.
