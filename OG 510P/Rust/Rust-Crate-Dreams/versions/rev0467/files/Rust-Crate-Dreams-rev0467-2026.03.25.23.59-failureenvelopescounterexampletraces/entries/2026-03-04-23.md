# 2026-03-04 (late): structured concurrency, telemetry batteries, reproducible rebuilders

This entry adds a few “epic crate” candidates where the ecosystem has *pieces*, but not yet a **coherent, boring, production-friendly kit**.

## Added proposals

### P-0077 — OTel Batteries Kit (Rust observability that feels “standard library”)
Rust’s `tracing` + OpenTelemetry bridge works, but the “just do it right” path still involves lots of fiddly choices and unstable/experimental feature gates in practice (and the Rust OTel project is still actively graduating features).  
**Goal:** one crate (and companion cargo subcommand) that makes *good* observability the default across services, CLIs, and libraries.

Evidence / motivation:
- OpenTelemetry Rust has multiple features still behind experimental/spec-unstable flags as of Feb 2026.  
  https://github.com/open-telemetry/opentelemetry-rust/issues/3376
- Standard “getting started” guidance exists, but it’s still easy to end up with partial coverage or mismatched conventions across crates.  
  https://opentelemetry.io/docs/languages/rust/getting-started/
- The `tracing-opentelemetry` layer exists, but configuration + conventions + propagation + export pipelines remain fragmented across projects.  
  https://docs.rs/tracing-opentelemetry

What it should provide other people:
- **One-line bootstrap** that selects sensible defaults (resource attrs, env var config, propagators, exporters).
- **Semantic conventions helpers**: consistent spans/metrics/log attributes for HTTP, DB, messaging, gRPC, background jobs.
- **Library-grade APIs**: helpers that *do not* impose a global subscriber unless asked; opt-in “app bootstrap” module.
- **Zero-surprise performance controls**: sampling knobs, span limits, aggregation temporality; ship profiles (dev, staging, prod).
- **Compliance and debug UX**: “why is my trace missing?” doctor; diagnostics for context propagation.
- **Interop fixtures**: golden tests for OTLP payloads and context propagation.

Design notes:
- Treat “observability as a contract”: explicit versioning of conventions, plus an upgrade guide.
- Include “integration packs” behind features: `axum`, `tower`, `hyper`, `sqlx`, `tonic`, `reqwest`, `tokio`, `rdkafka`.
- Include a `cargo otel doctor` command that inspects dependencies and suggests the right feature flags.

### P-0078 — Structured Concurrency Standard Kit (runtime-agnostic nurseries + cancellation contracts)
Structured concurrency is a recurring need in async Rust: scopes/nurseries that guarantee task lifetime & cancellation correctness.  
There are promising experiments and crates (e.g., `moro` for async scopes, `futures-concurrency` for structured ops), but the ecosystem lacks a **unified contract** that libraries can target.

Evidence / motivation:
- `futures-concurrency` explicitly positions itself as “structured concurrency operations” and focuses on cancellation correctness (Jan 2026).  
  https://crates.io/crates/futures-concurrency
- `moro` explores async scopes to spawn jobs that can borrow stack data (scope-style spawning).  
  https://github.com/nikomatsakis/moro
- A common complaint in async Rust is that correctness is mostly about *concurrency structure* and cancellation semantics, not raw speed.  
  https://kobzol.github.io/rust/2025/01/15/async-rust-is-about-concurrency.html

What it should provide other people:
- A **portable nursery trait** that runtimes can implement (Tokio, async-std, smol, custom).
- **Cancellation + timeout algebra** with explicit guarantees:
  - cancellation propagation direction
  - “must-join” semantics (no detached tasks unless explicit)
  - panic policy + error aggregation
- **Borrow-friendly scoped spawn** (like `std::thread::scope`) where possible, with a clear “soundness frontier.”
- **Task tree introspection hooks** so tools (console/otel) can visualize scope structure.
- **Interoperability adapters**: convert between runtime join handles and the standard kit’s handles.
- A strong test suite: cancellation edge cases, drop order, panic races; include Miri/loom-friendly modes.

Design notes:
- Treat it like `Iterator`: minimal core traits + rich combinators layer.
- Provide “opinionated helpers” (nursery macros, structured `select`/`join` forms) without forcing them on libraries.

### P-0079 — Rebuilder Network Kit (reproducible build verification as a first-class workflow)
Cargo gives repeatable dependency resolution, but “independent parties can rebuild and verify identical artifacts” remains hard in practice.  
There’s long-running Rust community interest in reproducible builds for rustc itself, and modern supply-chain posture increasingly assumes provenance + rebuild verification.

Evidence / motivation:
- Rust internals has discussed “verifying rustc releases with reproducible builds” since 2016.  
  https://internals.rust-lang.org/t/verifying-rustc-releases-with-reproducible-builds/4502
- Newer threads continue to explore the scope/complexity of reproducible builds work (Mar 2025).  
  https://internals.rust-lang.org/t/reproducible-builds-for-rustc-gsoc-25-idea/22532
- SLSA frames provenance and its relation to SBOM/reproducible builds; this remains a moving ecosystem standard.  
  https://slsa.dev/spec/v1.1/faq

What it should provide other people:
- A **standard “rebuild capsule” format**:
  - pinned toolchain + env
  - dependency graph snapshot
  - build script I/O capture policy
  - deterministic timestamp/source date support
- A **rebuild runner** that can execute capsules hermetically (Docker/Podman/Nix/VM backends as plugins).
- A **verifier** that compares outputs and emits a signed “rebuild attestation” (linkable to provenance).
- A **registry-friendly story**: attach/host capsules and attestations (crates.io, GitHub releases, OCI registries).
- **Human-centered UX**: “why did this differ?” diffing of env vars, build script outputs, file ordering, timestamps.

Design notes:
- Don’t try to solve full reproducibility in one go: ship incremental “repro levels” with crisp guarantees.
- Integrate with existing policy tooling (e.g., `cargo vet`-style workflows) as an optional gate.
