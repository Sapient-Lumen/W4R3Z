# Entry 383 — dependency lifecycle transition deepened around override authority, signal freshness, and exception reevaluation

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another dependency scorecard, vendoring wrapper, or source-policy dashboard.

The lane chosen here was **P-0535 Dependency Lifecycle Transition Kit**.
The archive already had a strong thesis, lane snapshots, boundary reports, seam receipts, replacement-readiness reports, transition-plan manifests, exception ledgers, imported-signal receipts, lifecycle drift diffs, and support-bundle vocabulary.
What it still lacked was a sharper answer to a harder downstream question:

> when somebody says “we use this crate for now, but we have it contained, reviewed, and on a path toward replacement,” what exactly should another maintainer receive so **override visibility**, **signal freshness**, and **exception status** do not get flattened into one vague “dependency policy exists” story?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Rust/Cargo/Foundation sources still converge on the same pressure point:

- the January 2026 safety-critical write-up explicitly says teams often **use crates early, track carefully, shrink dependencies for higher-criticality parts**, and at higher criticality either avoid third-party crates or hide them behind abstraction layers for later replacement;
- the March 2026 Rust challenges write-up says ecosystem maturity is uneven across domains and that a layer of tacit knowledge still shapes crate choice, which increases the value of compact, explicit lifecycle artifacts;
- Cargo’s current config docs say `[patch]` can live in `.cargo/config.toml`, but those files are **not usually checked into source control**, should generally yield to `Cargo.toml` for shared builds, and config patches override manifest patches when both exist;
- Cargo’s source-replacement docs say replacement assumes the **same source code** and is therefore the wrong tool for patching divergence or proving private-fork progress;
- Cargo’s metadata docs say the output format is versioned, source IDs are opaque, and imports should be treated like captured receipts rather than permanent semantic truth;
- Cargo’s lockfile guide keeps `Cargo.toml` as broad declaration and `Cargo.lock` as the exact realized graph, which matters when a transition is declared more loosely than it is currently realized;
- and the Rust Foundation’s 2026–2028 strategy keeps **Stable Infrastructure** and **Sustainable Maintenance** as core pillars, reinforcing boring review artifacts over another score or dashboard.

That combination makes one archive lesson sharper:

**A worthy dependency-lifecycle crate is not just “graph + seam + waiver.”**
**It is a reviewable contract for where the transition is declared, whether imported context is still fresh enough to trust, whether a waiver is still alive, and what one portable bundle another maintainer can inspect without oral history.**

## Main repo judgment from this pass

The strongest next move for **P-0535** was to make three more receiver-facing review objects first-class:

1. **`override-authority.receipt.json`** — records what kind of override or source route is actually in play, where it is declared, whether it is repo-visible or local-only, and what that means for shared reviewability.
2. **`signal-freshness.report.json`** — records which imported ecosystem facts were captured, when they were captured, what refresh window they carry, and whether they are still fresh enough to support the current transition story.
3. **`exception-reevaluation.report.json`** — records which typed exceptions are still active, nearing review, stale, expired, exit-ready, or manual-review-only.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0496** still owns mirror/vendor/source-parity truth;
- **P-0017** still owns broader trust/risk signal interpretation;
- **P-0011** still owns stewardship/support continuity;
- **P-0515** still owns crate-offramp planning;
- but **P-0535** owns the receiver-facing workflow for **criticality lanes, seams, transition posture, override authority, signal freshness, exception reevaluation, and lifecycle drift**.

That separation matters.
Otherwise the archive would quietly confuse “there is a local patch”, “we vendored it”, “the crate has good imported signals”, “an exception exists”, and “the replacement path is still healthy” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One lane snapshot** that shows where third-party crates are allowed to live.
2. **One seam receipt** that names the actual replacement boundary instead of promising “we can swap it later.”
3. **One transition plan** that says whether the next move is pinning, containment, vendoring, forking, internalization, or removal.
4. **One override-authority receipt** that says whether the current transition is declared in checked-in policy, local config, generated config, or some manual side path.
5. **One signal-freshness report** that says whether imported ecosystem context is still current enough to support the plan.
6. **One exception-reevaluation report** that says whether a waiver is still active, stale, or ready to close.
7. **One lifecycle drift artifact** so a release cannot quietly widen or normalize a temporary dependency posture.
8. **One support bundle** that a reviewer, downstream integrator, or safety lead can read without spelunking local config, CI, and folklore.

If a crate idea in this territory cannot supply those review objects, it is still probably a graph helper, source-parity lane, trust dashboard, or off-ramp pack rather than the missing support layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten:

1. **shared checked-in transition policy** and **local-only override state**,
2. **imported positive signals** and **fresh enough imported signals**,
3. **an exception ledger entry** and **an honestly reevaluated exception**,
4. **a vendored or mirrored source route** and **architectural replacement progress**.

Future passes should therefore keep asking:

- where is the transition actually declared,
- who can see it,
- when were the imported signals last refreshed,
- when must the exception be reevaluated,
- and what one portable lifecycle bundle another maintainer should receive.

That is a better use of repo time than inventing another dependency score, source helper, or “secure dependency policy” dashboard that still cannot hand someone an honest lifecycle witness.
