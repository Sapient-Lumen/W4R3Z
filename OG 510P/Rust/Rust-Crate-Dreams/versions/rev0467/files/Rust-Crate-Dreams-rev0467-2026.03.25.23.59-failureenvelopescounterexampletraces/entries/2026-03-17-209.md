# Entry 209 — crate test surfaces promoted as the downstream-testing-support lane

This pass added a new top-level proposal: **P-0523 Crate Test Surface Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing test frameworks, mock servers, property generators, containerized integration helpers, and receiver-facing crate test support into one vague “better testing” story.

## Why this moved now

Several current Rust and ecosystem signals line up unusually well.

### 1. The crate-supportiveness frontier still lacked a good downstream-testing lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profiles** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- **successor / off-ramp support** via **P-0515**,
- **setup/configuration scenarios** via **P-0516**,
- **performance envelopes** via **P-0517**,
- **observability surfaces** via **P-0518**,
- **authority surfaces** via **P-0519**,
- **lifecycle surfaces** via **P-0520**,
- **resource surfaces** via **P-0521**,
- and **persistence surfaces** via **P-0522**.

But it still lacked a good answer to:

- “Once a team adopts a crate, what exactly does the crate hand them so they can write deterministic, supported tests for code built on top of it?”

That left the archive with better answers for production setup, telemetry, shutdown, and storage than for the most ordinary downstream task of all: **testing code that depends on a crate**.

### 2. Official and ecosystem substrate now make this a contract problem, not a primitives problem

Rust already has clear unit/integration test structure.
Tokio already documents paused time and publishes dedicated testing helpers.
`rstest` already offers fixtures.
`proptest` already offers canonical strategy substrate.
`wiremock` already offers HTTP mocking.
`testcontainers` already offers isolated integration environments.
`assert_cmd`, `tempfile`, and `insta` already cover important slices of the space.

That means the sharper question is no longer “can Rust test these things at all?” but “what portable artifact should sit above today’s tooling so a crate can tell downstream users how it expects to be tested?”

### 3. Current tools are useful but fragmented at the crate boundary

The ecosystem has many useful ingredients, but maintainers still assemble testing support by hand.
What is still missing is the boring pack that can say:

- these fixtures and fakes are official,
- these scenario corpora are representative,
- these deterministic seams exist,
- these integration topologies are supported,
- and this is how the crate’s testing support changed across releases.

### 4. Rust’s current messaging makes test-support surfaces more plausible than before

The vision-doc work explicitly recommends more **supportive interfaces from crates**.
The 2025 survey says docs and source remain the main learning surfaces.
That combination makes test-surface packs feel like product-support artifacts rather than private maintainer notes.

## Main judgment after the pass

The worthy crate here is not another test runner.
It is the boring contract layer that can hand other people:

- one **test-surface pack**,
- one **fixture-catalog receipt**,
- one **fake-backend report**,
- one **scenario-corpus manifest**,
- one **property-strategy report**,
- one **deterministic-seam report**,
- one **snapshot-normalization report**,
- one **integration-topology manifest**,
- one **test-support check report**,
- and one **test-surface diff**.
