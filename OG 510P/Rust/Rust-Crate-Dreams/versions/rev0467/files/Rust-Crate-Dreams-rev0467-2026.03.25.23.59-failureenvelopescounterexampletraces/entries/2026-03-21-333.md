# Entry 333 — Task Supervision & Restart Kit deepened for topology truth, restart-policy truth, health/readiness basis, state-reset honesty, shutdown escalation, and failure bundles

This pass deepened **P-0095 Task Supervision & Restart Kit** instead of adding another actor framework, another retry helper, or another vague async-resilience note.

## Why this lane earned another serious pass

The archive already had stronger answers for:

- runtime assurance and qualification posture,
- lifecycle / shutdown support contracts,
- async replay/debugging bundles,
- and channel/resource contracts.

What it still lacked was a build-shaped answer for the supervision question:

> “If this task fails, hangs, or times out during shutdown, what exactly restarts, what state resets, and what artifact explains what happened?”

Current substrate is now strong enough to make that precise:

- the Rust project still identifies async complexity and runtime lock-in as live ecosystem problems;
- Tokio gives task-group and graceful-shutdown substrate, but not a shared supervision contract;
- `task-supervisor` proves demand for restart, dead-task detection, and runtime task control;
- `spry` proves startup/readiness state matters;
- `ractor-supervisor` proves strategy choice and meltdown windows matter.

That means a worthy crate here should not merely say “supports supervised tasks”.
It should say **which restart topology exists, which failure classes trigger restart, what state survives restart, what timeout really means, and what bundle another team can inspect**.

## What moved this time

The main planning move was to stop treating “restart tasks on failure” as one blob.

This pass elevated six review objects into first-class status for **P-0095**:

1. **supervision topology** — membership shape, dependency/order basis, and restart blast radius;
2. **restart policy** — restart class, trigger classes, backoff, and meltdown windows;
3. **health / readiness basis** — stable-start criteria, liveness basis, and unresponsive-task action;
4. **state reset basis** — template clone, fresh factory, shared external state, or persisted rehydrate;
5. **shutdown escalation** — stop signal, graceful phase, timeout aftermath, and blocking-work posture;
6. **failure bundle** — the receipts and attachments exported when the policy is exercised.

## Why this matters now

The ecosystem evidence is now sharp enough that the missing layer is no longer vague:

- task groups and shutdown helpers do not answer restart blast radius;
- restart helpers do not automatically answer state-reset or timeout-aftermath truth;
- actor supervisors prove strategy and meltdown semantics matter, but they still do not give a portable supervision contract for other teams;
- clone-based restarts can silently drop in-memory state while leaving shared `Arc` state alive.

That means a worthy crate should not let one green “auto restart” bit silently over-claim restart safety, retained state, or shutdown semantics.

## Main judgment after the pass

A worthy task-supervision contribution for Rust should now provide more than task groups, watchdog loops, or actor-specific restart helpers.
It should also provide:

- one explicit **supervision-topology receipt**,
- one explicit **restart-policy receipt**,
- one explicit **health-source receipt**,
- one explicit **state-reset receipt**,
- one explicit **shutdown-escalation receipt**,
- one explicit **supervision-failure-bundle manifest**,
- plus the already-needed summary/diff/support bundle surface.
