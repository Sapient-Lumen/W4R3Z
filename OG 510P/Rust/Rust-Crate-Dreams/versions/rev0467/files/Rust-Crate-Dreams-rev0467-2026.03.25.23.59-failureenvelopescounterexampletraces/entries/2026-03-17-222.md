# 2026-03-17 (222) — crate resource-surface productization pass

This pass did **not** add a new lane.
It sharpened **P-0521 Crate Resource Surface Pack Kit** into a more implementation-ready `0.1` shape.

## Main judgment

The missing value is still **not** another queue, another cache, another rate limiter, another runtime metrics dashboard, or another profiler.
The sharper missing layer is a **maintainer-facing resource contract** that records:

- what can accumulate or stay alive,
- what kind of bound that resource actually has,
- what happens at saturation,
- and which signals or receipts prove pressure is building.

## Why this lane looks sharper now

- Tokio’s docs now make bounded/unbounded channel posture, worker-thread posture, blocking-thread queueing, and runtime queue metrics concrete enough that the missing value is increasingly the contract above them;
- reqwest’s pool docs make it explicit that a crate can expose connection reuse and idle-pool defaults without making the receiver-facing resource story obvious;
- Moka’s capacity docs make “bounded by entries” and “bounded by weighted size” materially different support stories;
- and Tower / governor provide real limit substrate without automatically publishing one crate’s backlog, saturation, and pressure-signal contract.

## What to keep separate

- Keep **P-0521** separate from performance envelopes (**P-0517**).
- Keep **P-0521** separate from observability contracts (**P-0518**).
- Keep **P-0521** separate from lifecycle / shutdown truth (**P-0520**).
- Keep **P-0521** separate from queue/cache/limiter substrate itself.

## Preferred proving grounds

- SDK or client crates with internal pools and idle/default resource posture
- async libraries with bounded and unbounded work queues
- runtime bridge crates using `spawn_blocking`
- caches where entry-count and weighted-size bounds differ materially
- service crates that compose concurrency limits with external queues or admission paths
