# Entry 449 — add policy profiles and evidence floors so the same packet stack can serve different adopters honestly

This pass again chose **deepen over append**.

The archive already had much better answers for:
- compare,
- freeze,
- watch,
- trigger,
- intake,
- materialize,
- adjudicate,
- exception,
- carry forward,
- and reopen review.

What it still lacked was a clean answer to the next operational question:

> when two teams ask the same crate-choice question but live under **different evidence and assurance expectations**, how does a worthy crate avoid handing both of them the same shallow answer?

That seam matters now because the current Rust substrate already contains **real profile fragments**, but they remain scattered and tool-local:

- the Rust challenges write-up says users still struggle with crate choice and that some domains remain immature;
- the 2025 survey says resource usage and debugging are still live productivity problems while online docs remain the preferred canonical reference;
- the 2026 goals explicitly emphasize secure supply chain, safety-critical evidence, SBOM, Wasm Components, async, and cargo plumbing;
- the safety-critical work calls for ecosystem-wide MSRV conventions, target-readiness checklists, and reusable dependency-lifecycle playbooks;
- Cargo Vet already supports custom criteria, configurable policies for different dependency subtrees, and multiple sets of criteria;
- cargo-deny already lets teams scope checks by target and configure ignored advisories, bans, and license exceptions;
- Cargo, docs.rs, and the registry index already expose enough structured/versioned machine surfaces to support profile-aware review packets.

## Main judgment

A worthy crate in the practical core should now publish not only:
- decision packets,
- basis locks,
- intake/materialization receipts,
- adjudication sessions,
- exception receipts,
- expiry tickets,
- and recheck tickets,

but also a credible **policy profile pack**.

That means it should provide:
1. named adopter profiles with stable IDs,
2. explicit evidence floors per profile,
3. clear pass / conditional / fail / manual-review outcomes for each profile,
4. typed mappings from tool-local policy facts into shared packet language,
5. explicit non-claims for what a profile does **not** certify,
6. and profile diffs so teams can see what changed when they move from “explore” to “enterprise offline” to “safety onramp”.

## Practical consequence

This pass still does **not** justify a major salience rerank.

But it sharpens the first practical slice again:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, profile packs, profile-satisfaction reports, adjudication sessions, policy-exception receipts, carry-forward receipts, expiry tickets, and recheck tickets
2. **P-0486** — debug witness bundles that should also evaluate against named adopter profiles instead of one vague “supported” story
3. **P-0496** — restricted-delivery/source-parity bundles that become profile-gated requirements for air-gapped and mirror-heavy adopters
4. **P-0472** — docs.rs parity bundles that can satisfy some visibility floors without pretending hosted docs settle safety, offline, or target truth

Interpretation:
- the front door is no longer just “choose, freeze, adjudicate, and reopen honestly”;
- it is now also “**answer according to the adopter’s evidence floor honestly**”.

## What this pass says a worthy crate should provide other people

A worthy front-door crate should now answer **seventeen** operational questions:

1. compare — what are the plausible choices now?
2. freeze — what exact basis did the chosen answer stand on?
3. profile — which adopter profile is asking?
4. floor — what evidence is minimally required for that profile?
5. watch — which surfaces are being watched later?
6. trigger — what exact event opened review?
7. intake — what imported material was actually consumed?
8. materialize — what can be made portable or offline-friendly?
9. conflict — which claims disagree and on which route or time basis?
10. adjudicate — what decision was made about that disagreement, by whom, and under what policy?
11. exception — what temporary relief was granted, to whom, for which scope, and why?
12. carry forward — which old claims remain inherited and which became superseded?
13. ticket — what review packet should be opened next?
14. refresh — what later facts changed and which did not?
15. revalidate — does the old choice still stand under the same task and profile?
16. transition — if not, what posture follows now?
17. ceiling — what still requires manual judgment even after the workbench runs?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
