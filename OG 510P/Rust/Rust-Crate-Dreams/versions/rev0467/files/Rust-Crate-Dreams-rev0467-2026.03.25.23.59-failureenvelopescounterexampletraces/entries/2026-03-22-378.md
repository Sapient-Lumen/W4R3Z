# Entry 378 — lock-contention work deepened around package-cache lock modes, residual contention, and mitigation-outcome honesty

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another generic Cargo performance or cache helper.

The lane chosen here was **P-0490 Cargo Lock Contention Witness Kit**.
The archive already had a strong thesis, root authority receipts, actor command lanes, wait windows, exactness reporting, mitigation-cost reporting, and a compact support-bundle story.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when somebody says “Cargo was blocked by another process, and we fixed it by changing target dirs / build dirs / workflow shape”, what exactly should another engineer receive so **package-cache lock modes**, **residual contention surfaces**, and **before/after mitigation outcomes** do not get flattened into one vague diagnosis?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Cargo and rust-analyzer sources still converge on the same pressure point:

- rust-analyzer still explicitly says it and Cargo can compete over the build lock, and that using a different target directory trades blocking relief for duplicated artifacts;
- rust-analyzer’s configuration docs still make the base `cargo check` command, per-workspace vs once invocation strategy, override commands, wrappers, and target-dir separation concrete;
- Cargo’s build-cache and config docs now keep `target-dir` and `build-dir` separate with explicit authority routes;
- Cargo’s unstable docs still say the new build-dir layout is meant to unblock caching and locking improvements;
- the March 2026 call for testing build-dir-layout v2 says teams should test anything that touches `build-dir` or `target-dir`, and notes that simply separating `build-dir` may already expose failures;
- the Cargo 1.94 development-cycle update says target-dir locking remains trickier than it first looked, with easy-to-overlook but significant residual contention around proc-macros, build scripts, and some non-workspace-member cases;
- and Cargo’s current internal `cache_lock` docs now make package/index-cache lock modes unusually explicit: `DownloadExclusive`, `Shared`, and `MutateExclusive`, with the important caveat that `DownloadExclusive` does **not** interfere with `Shared`.

That combination makes one archive lesson sharper:

**A worthy lock-contention crate is not just “show me the wait and recommend a different target dir.”  
It is a reviewable contract for what lock mode was actually relevant, what contention surfaces remain after a mitigation, and what one honest before/after bundle another reviewer should receive.**

## Main repo judgment from this pass

The strongest next move for **P-0490** was to make three more receiver-facing review objects first-class:

1. **`package-cache-lock-mode.receipt.json`** — records whether the relevant package-cache behavior was `download_exclusive`, `shared_read`, `mutate_exclusive`, or `unknown`, what that mode can interfere with, and how exact the claim is.
2. **`residual-contention.report.json`** — records which contention surfaces remain even after a mitigation or topology change, such as package-cache serialization, proc-macro/build-script overlap, non-workspace-member lock sharing, or upstream-volatility/manual-review zones.
3. **`mitigation-outcome.diff.json`** — compares a before/after witness pair and classifies what actually changed: shared roots, lock mode, wait class, residual surfaces, artifact duplication, or only confidence/exactness.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0436** still owns lease/coordination and cleanup policy for shared caches;
- **P-0480** still owns Cargo-home inventory, retention, and garbage-collection policy;
- **P-0469** still owns rebuild causality;
- but **P-0490** owns the receiver-facing workflow for **lock-mode truth, residual contention after mitigation, and one portable before/after witness bundle**.

That separation matters.
Otherwise the archive would quietly confuse “same package cache root”, “actually conflicting lock mode”, “residual proc-macro/build-script collision”, and “we changed something so the symptom moved” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One package-cache lock-mode receipt** that says whether package-cache activity should actually conflict with the observed build lane.
2. **One root/topology report** that still says which roots were shared and how those root paths were determined.
3. **One wait-window receipt** that bounds the observed stall without bluffing about blocker identity.
4. **One residual-contention report** that says what still remains after a mitigation or topology change.
5. **One mitigation-outcome diff** that compares before/after evidence without pretending the mitigation universally solved contention.
6. **One portable contention-support bundle** that another reviewer can archive, diff, or attach to CI/IDE setup docs.
7. **One manual-review zone** whenever upstream locking work, older Cargo behavior, or ambiguous observation outruns what the bundle can honestly prove.

If a crate idea in this territory cannot supply those review objects, it is still probably a lease/policy tool, a cache-governance tool, a rebuild-explanation tool, or a generic wrapper rather than the missing support-contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **shared package cache roots** into **conflicting lock modes**, or **mitigation applied** into **contention solved**, or **residual proc-macro/build-script collisions** into **same as the original wait**.

Future passes should therefore keep asking:

1. what lock mode was actually relevant,
2. whether that lock mode could interfere with the observed actor,
3. which residual contention surfaces remained after the mitigation,
4. what changed before vs after in a portable diff,
5. and where manual review still begins.

That is a better use of repo time than inventing another cache-helper, generalized scheduler, or Cargo wrapper that cannot export an honest contention witness.
