# Entry 139 — debugger visualizer activation/external-lane refresh

This pass again did **not** add another top-level proposal.

Instead, it tightened **P-0491 Debugger Visualizer Compatibility Kit** so the crate contract is more honest about what it can actually prove.

## Main judgment

The important archive-level correction is:

- **embedded asset present**,
- **backend will activate/load it**,
- and **backend is actually supported**

are three different claims.

The official docs now make that distinction concrete enough to encode directly:

- Rust documents embedded NatVis and GDB assets,
- Rust narrows NatVis embedding to `-windows-msvc`,
- Rust warns that embedded GDB printers are not auto-loaded by default,
- GDB documents the safe-path trust model behind that warning,
- and LLDB’s formatter model is documented as summaries/filters/synthetic children plus Python-backed routes rather than a Rust-embedded visualizer lane.

That means the worthy crate here is a **compatibility receipt**, not a vague debugger platform.

## New planning stance

**P-0491** should now be read as a crate that hands other people:

- one `visualizer-policy.toml`,
- one `visualizer-assets.manifest.json`,
- one `backend-matrix.receipt.json`,
- one `render-golden.report.json`,
- one `embed-vs-external.report.json`,
- optionally one `visualizer-drift.diff.json`,
- and one compact `notes.md`.

But the backend matrix must keep three facts separate:

1. asset bytes discovered,
2. activation/trust/config conditions,
3. and actual support verdict.

## Archive-level lesson

When upstream docs expose awkward boundaries clearly enough, the repo should not smooth them over.

For visualizers especially, the missing value is often **not** new formatter syntax.
It is the boring artifact that tells another human whether the asset was present, whether the debugger would even activate it, and whether support was embedded, external, or only manually reviewable.
