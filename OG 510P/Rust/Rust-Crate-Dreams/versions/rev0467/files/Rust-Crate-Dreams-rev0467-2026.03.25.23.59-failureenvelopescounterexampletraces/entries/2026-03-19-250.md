# Entry 250 — text-input-kit deepened around IME transactions, selection truth, and backend capability receipts

This pass did **not** open another vague “Rust GUI needs polish” lane.
It sharpened **P-0027 text-input-kit** into a more believable, implementation-ready product.

## Why this moved now

The current Rust GUI/text stack is no longer empty.
That changes the shape of the missing value.

- **winit** now has explicit IME APIs (`set_ime_allowed`, `Ime` events, candidate-window positioning) for native targets, but it still documents **Web as unsupported** for IME events and positioning.
- **Fresh upstream bugs** still show that even when the API exists, event truth is not yet boring: on Windows, a March 2026 report says keyboard input can still leak while IME is allowed during preedit.
- **Web/WASM IME** is still an active open seam in `winit`; the current issue explicitly says the canvas cannot receive `CompositionEvent`, and points to hidden-input forwarding as a hacky workaround.
- **Parley** and **cosmic-text** show that Rust now has real layout/editing substrate.
- **AccessKit** already has **TextPosition** and **TextSelection** types, which means text-selection semantics can be exported once the input/editing layer is honest.
- At the same time, current field reporting on Rust GUI libraries still reads like an ecosystem where ordinary text-input polish varies widely, and **Slint** issue discussion shows text-input accessibility exposure is still a major design challenge.

That combination means the missing crate is no longer “yet another text stack”.
The sharper missing crate is a **shared text-input engine plus adapter/replay/receipt layer** above today’s layout and accessibility substrate.

## Main planning move

This pass made the crate more concrete by promoting three first-class review objects that were still too implicit in the older proposal:

1. **IME transaction report** — what preedit/commit/cancel/replacement truth the engine actually saw and applied,
2. **selection contract report** — what caret/selection behavior the engine claims for graphemes, words, lines, and replacement ranges,
3. **backend capability receipt** — what the active adapter can really support on this platform/runtime, and where manual review or fallback behavior begins.

That move matters because the archive had already separated:

- **P-0027** as the lower-level text-input substrate lane,
- **P-0197** as the text layout/shaping correctness lane,
- **P-0087** as the authoring-side accessibility doctor lane,
- **P-0092** as the broader GUI regression lane.

But `P-0027` still lacked a tight `0.1` shape.
This pass fixes that.

## Main judgment after the pass

A worthy text-input crate contribution for Rust should now provide not merely “some editor state” but:

- explicit **IME transaction truth** for preedit, replacement-range, commit, cancel, and dedup behavior,
- explicit **selection/caret truth** for grapheme-safe deletion, cursor movement, anchor/head stability, and replacement semantics,
- explicit **backend-capability truth** for native versus web adapters, candidate-window anchoring, dead-key handling, and fallback/manual-review boundaries,
- and one compact replayable artifact another maintainer can inspect without reverse-engineering toolkit internals.

That is a sharper and more believable contribution than “just another text widget”, “yet another layout engine”, or “a vague IME helper crate”.
