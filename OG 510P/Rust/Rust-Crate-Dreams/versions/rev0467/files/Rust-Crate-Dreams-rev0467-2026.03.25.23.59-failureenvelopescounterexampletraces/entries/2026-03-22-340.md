# Entry 340 — toolchain/target frontier deepening via artifact-route truth and host-target topology for P-0484

This pass deliberately doubled back to **P-0484 Toolchain & Target Support Contract Kit** because the latest official signals keep making the same support gap more concrete.

## Why this lane earned another serious pass

The support story is getting sharper, not fuzzier:

- the March 2026 “Rust challenges” write-up again names **cross-compilation** and `no_std` gaps as practical friction, especially for embedded teams;
- the January 2026 safety-critical write-up again asks, in effect, for target-readiness answers that another team could responsibly bet on;
- the March 2026 Cargo build-dir-layout-v2 call-for-testing says many projects rely on **unspecified build-dir details** because Cargo is still missing features they need;
- the October 2025 docs.rs target change reminds us that public target posture can shift even if a crate author never touched their manifest;
- and the 2025 target demotions show that Rust-project tier/support facts can move while binaries continue to ship.

Together these push the same conclusion: a worthy crate here is still not another cross tool, linker helper, or docs.rs wrapper. It is a **reviewable support contract** that tells other people not only *what* a project claims to support, but *how that claim is evidenced and located*.

## Main judgment after the pass

The existing P-0484 artifacts were already strong on:

1. override lineage,
2. requested versus effective components,
3. support classes,
4. exercise scope,
5. external prerequisites,
6. docs posture,
7. target readiness.

This pass promotes two more objects into first-class status:

8. **artifact route** — how a workflow actually finds the build/docs/test artifact it relies on, and whether that route uses stable interfaces or brittle Cargo-internal layout assumptions;
9. **host-target topology** — which phases really happen on the host, which produce target artifacts, which require runners/devices/emulators, and which “cross-target” claims still secretly depend on host-only helpers.

## Why these two objects matter

Current substrate is specific enough that the archive should stop flattening it:

- rustup target installation only adds the Rust stdlib for a target, not the linker/SDK story;
- rustup overrides, profiles, and component availability still mean requested state and effective state can differ;
- Cargo is actively changing internal build-dir layout and explicitly says many tools depend on unspecified details;
- docs.rs default-target behavior is documented and can influence a crate’s public surface without meaning runtime support;
- target tiers can be demoted while distribution continues, so “downloads exist” is weaker than “tested and maintained.”

A crate can therefore truthfully say “supports target X” while still hiding:

- whether CI locates outputs through stable Cargo message JSON or by spelunking `target/` or build-dir internals;
- whether proc macros and build scripts succeeded only on the host while the target lane was compile-only;
- whether tests require a runner, board, emulator, Rosetta, or a hosted docs surface;
- and whether the project support class stayed in sync with official tier movement.

## New archive-level stance

For toolchain/target-heavy work, the archive should now prefer this layering:

1. **P-0484** for support-contract truth,
2. **P-0036** for MSRV policy/lockfile floors,
3. docs.rs parity or native-build diagnosis lanes for deeper replay/debug work,
4. shipkits or platform packages only after the support contract is already explicit.

That keeps the archive from minting another tool that “helps cross compilation” while still failing to say which phases are host-only and which artifact paths are brittle.

## What should count as a worthy crate contribution after this pass

A worthy support-contract crate should now be able to answer all of these cleanly:

1. **Which toolchain/targets/components were requested, and which actually won?**
2. **What support class is being claimed for each host/target lane?**
3. **Which scopes were really exercised?**
4. **Which external prerequisites still exist outside Rustup/Cargo?**
5. **How are artifacts actually discovered, and is that discovery path stable?**
6. **Which steps are host-only even in a supposedly cross-target lane?**
7. **Did any official docs.rs or target-tier movement change the support story?**

If a candidate crate cannot answer those questions, the archive should usually treat it as incomplete support folklore rather than a serious platform contribution.
