# Entry 451 — add evidence-gap campaigns so stage-aware packet stacks can close missing proof without pretending to be a workflow platform

This pass again chose **deepen over append**.

The archive already had much better answers for:
- compare,
- freeze,
- profile,
- stage,
- progress,
- adjudicate,
- except,
- carry forward,
- reopen,
- and exit.

What it still lacked was a compact answer to the next operational question:

> when a stage or profile answer comes back as **conditional**, **hold**, or **manual review required**, how does a team close the missing evidence in a reviewable way without rewriting the frozen basis or turning the crate into a full workflow platform?

That seam matters now because the current Rust substrate increasingly exposes **bounded evidence routes** rather than only prose:

- the Rust challenges write-up still says users struggle with crate choice and uneven domain maturity;
- the 2025 survey still reports resource usage and debugging as meaningful productivity pain while online docs remain the preferred canonical reference;
- 2026 flagships still emphasize supply chain, SBOM, safety-critical work, async, and cargo plumbing;
- Cargo plumbing work explicitly decomposes Cargo into programmatic phases;
- Cargo build-analysis is explicitly about recording build metadata across invocations for later explanation;
- docs.rs now exposes hosted build posture, configurable metadata, rustdoc JSON, download archives, and a public queue/rebuild queue;
- crates.io now exposes Security-tab data, Trusted Publishing improvements, and `pubtime`;
- Cargo Vet already distinguishes backlog, suggestions, exemptions, imported audits, trusted publishers, and expiring renewals.

## Main judgment

A worthy control-plane crate in the practical core should now publish not only:
- profile packs,
- stage runbooks,
- adjudication sessions,
- exceptions,
- progression reports,
- and recheck tickets,

but also a credible **gap-closure layer**.

That means it should provide:
1. a machine-readable `evidence-gap.report`,
2. a bounded `evidence-campaign.plan`,
3. a `gap-closure.receipt` that says what actually changed,
4. explicit source/authority routes for each campaign item,
5. automation classes and manual-review ceilings,
6. and stop conditions that prevent a campaign from pretending to solve what still requires judgment.

## Practical consequence

This still does **not** justify a major salience rerank.

But it sharpens the first practical slice again:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, profile packs, profile-satisfaction reports, decision-program runbooks, adjudication sessions, policy-exception receipts, progression reports, evidence-gap reports, evidence-campaign plans, gap-closure receipts, expiry tickets, and recheck tickets
2. **P-0486** — debug support bundles should also export gap reports when support is conditional rather than collapsing into one vague “not fully supported” message
3. **P-0496** — restricted-delivery/source-parity work should be consumable as one campaign item inside enterprise-offline and safety-adjacent stages
4. **P-0472** — docs.rs parity should be one importable gap source, not a fake whole-program answer
5. **P-0484** — target/support truth should also open bounded campaign items instead of one giant “more testing needed” bucket

Interpretation:
- the front door is no longer only “answer under a profile honestly”;
- it is now also “**show the smallest bounded plan for closing what is still missing**”.

## What this pass says a worthy crate should provide other people

A worthy front-door crate should now answer **twenty-three** operational questions:

1. compare — what are the plausible choices now?
2. freeze — what exact basis did the chosen answer stand on?
3. profile — which adopter profile is asking?
4. floor — what evidence is minimally required for that profile?
5. watch — which surfaces are being watched later?
6. trigger — what exact event opened review?
7. intake — what imported material was actually consumed?
8. materialize — what can be made portable or offline-friendly?
9. conflict — which claims disagree and on which route or time basis?
10. adjudicate — what decision was made about that disagreement, by whom, and under what policy?
11. exception — what temporary relief was granted, to whom, for which scope, and why?
12. carry forward — which old claims remain inherited and which became superseded?
13. stage — which named decision-program stage is active now?
14. gate — what evidence must exist to enter or leave that stage?
15. progress — what exactly moved from explore to team-default or enterprise-offline?
16. exit — did the program end in keep, hold, split-boundary, replace-later, or stop?
17. gap — which specific gate still fails and why?
18. campaign — what smallest bounded plan would close that gap?
19. route — which authority surface or import route should that plan use?
20. close — what changed when one gap was actually closed?
21. ticket — what review packet should be opened next?
22. refresh — what later facts changed and which did not?
23. ceiling — what still requires manual judgment even after the workbench runs?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
