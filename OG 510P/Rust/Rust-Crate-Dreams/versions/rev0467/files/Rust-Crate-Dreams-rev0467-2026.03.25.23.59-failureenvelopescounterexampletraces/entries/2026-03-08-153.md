# Entry 153 — resolver why-bundles also need feature-intent and suppression truth

This pass again did **not** add another top-level proposal.

Instead, it sharpened **P-0468 Cargo Resolver Explanation Kit** where the archive still had unusually high leverage: the crate now has a clearer plan for **positive feature requests, negative feature intent, and subject-scope truth** above today’s mixed Cargo surfaces.

## Main judgment

The important missing crate is not another dependency graph explorer.
It is a **receiver-facing resolver bundle** that can tell another person:

- what the explanation subject actually was (`-p`, `--bin`, workspace root, or equivalent),
- who explicitly asked for a feature,
- who explicitly asked for defaults to stay off,
- whether another selected or participating package still kept that feature active,
- and whether the answer is directly observed, conservative, or still manual-review-required.

## New planning stance

**P-0468** should now be read as a crate that hands other people:

- one `resolve-why.lock`,
- one `feature-causes.json`,
- one `version-choices.json`,
- one `duplicate-builds.json`,
- one `lane-partition.report.json`,
- one `platform-coverage.report.json`,
- one `unification-scope.report.json`,
- one `feature-intent.report.json`,
- one `resolver-choice.receipt.json`,
- and one `resolution-diff.report.json` that is allowed to distinguish policy, selection, and intent changes.

That is a sharper contract than “Cargo feature explanation tool”.
