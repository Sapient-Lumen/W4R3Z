# Entry 292 — crate-lifecycle-surface-pack sharpened around shutdown barriers and escape-path truth

This pass returned to **P-0520 Crate Lifecycle Surface Pack Kit** because the lane had already become fairly concrete around activation boundaries, stop semantics, blocking-work caveats, teardown evidence, and drain recipes — but it still left one dangerous blur available:

> a crate or framework could say that it supports “graceful shutdown” while never making clear **what completion event actually counts as the shutdown barrier**, which work is covered by that barrier, which tasks or upgraded connections can escape it, and which pending components can block it indefinitely.

## What moved this time

Several live ecosystem signals made that blur harder to tolerate:

- Tokio’s graceful-shutdown guide still frames shutdown as **signal + propagate + wait**, which means the waiting boundary is part of the contract, not just an implementation detail.
- `tokio_util::task::TaskTracker` now states that `wait()` completes only when the tracker is **both closed and empty**, and it also states that dropping a `TaskTracker` does **not** abort tasks.
- Tokio’s `JoinHandle` docs still say that dropping the handle **detaches** the task.
- Tokio’s `JoinSet` docs now keep three materially different paths explicit: dropping the set aborts tasks, `shutdown()` aborts and then waits, and `detach_all()` removes tasks that continue running in the background.
- Tokio maintainer guidance in March 2025 makes another ordinary trap explicit: putting a `JoinHandle` under `timeout` and then timing out only drops the handle; it does **not** cancel the task unless you also `abort` it.
- Current axum issue traffic gives two sharp real-world failure modes: a WebSocket upgrade task can sit **outside** the server graceful-shutdown future, while an SSE endpoint with a pending upstream stream can keep the graceful-shutdown barrier **blocked** until some other event arrives.
- axum’s 0.8.4 changelog also recently fixed a separate leaked Tokio task in `serve` without graceful shutdown, which reinforces that task ownership and shutdown coverage are still easy to misread from surface APIs alone.

That combination means the missing crate is no longer only “a lifecycle support bundle.”
It is also a **shutdown-barrier / escape-path honesty layer** above today’s cancellation tokens, task trackers, task handles, and framework-level graceful-shutdown hooks.

## Main planning move

This pass promoted two more review objects to first-class status for **P-0520**:

1. **shutdown-barrier truth** — what event actually counts as completion (`signal_sent_only`, `listener_stopped`, `tracked_tasks_closed_and_empty`, `protocol_drains_finished`, or `manual_review_required`),
2. **escape-path truth** — which work is outside that barrier or needs a different stop route (`detached_task`, `upgraded_connection_task`, `pending_stream_dependency`, `blocking_worker`, or `external_worker`).

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a crate can expose a cancellation token,
- a framework can expose a graceful-shutdown future,
- and a maintainer can truthfully say that they “wait for shutdown”
- while upgraded tasks, detached background work, pending streams, or timeout-dropped task handles still escape the user’s mental model of what finished.

That is not a wording nit.
It is the difference between:

- “the stop signal was sent”,
- “the listener stopped accepting new work”,
- “the tracked tasks finished”,
- and “the user-visible protocol work is actually gone.”

## Main judgment after the pass

A worthy lifecycle-support crate for Rust should now provide more than task maps and shutdown recipes.
It should provide:

- one explicit **shutdown-barrier report**,
- one explicit **escape-path receipt**,
- one explicit statement of whether a timeout or dropped handle merely stopped *waiting* versus actually stopped *work*,
- and one explicit statement of whether a graceful-shutdown completion event covers only the listener, the tracked task set, or the full user-visible protocol surface.

That is a better answer to today’s ecosystem than either:

- “Tokio has cancellation tokens,”
- “the framework has graceful shutdown,”
- or “we close the server and that’s basically the same as everything finishing.”
