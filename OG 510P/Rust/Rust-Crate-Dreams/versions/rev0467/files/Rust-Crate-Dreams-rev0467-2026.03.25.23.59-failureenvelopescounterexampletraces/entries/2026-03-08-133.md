# Entry 133 — Cargo resolver explanation implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded **P-0468 Cargo Resolver Explanation Kit** from a good abstract idea into a more implementation-ready crate plan.

## Main judgment

Cargo resolver explainability is now a much cleaner frontier than it was when this proposal first landed.

The current ecosystem already has:

- official resolver and feature docs,
- concrete troubleshooting guidance via `cargo tree`,
- stable graph context via `cargo metadata`,
- unstable richer imports via `--unit-graph` and `resolver.feature-unification`,
- and third-party graph/simulation prior art via `guppy` and `cargo hakari`.

So the missing value is not “finally query Cargo graphs.”
It is the **receiver-facing explanation bundle** above those surfaces.

## New planning stance

**P-0468** should now be read as a crate that hands other people:

- one feature-cause report,
- one version-choice receipt,
- one duplicate-build grouping,
- one graph-diff report,
- and one receipt telling them where every claim came from.

That is a much sharper contract than “Cargo graph tooling.”

## Archive-level lesson

When upstream docs and adjacent ecosystem tools become clearer, one of the best repo moves is often not adding more ideas.
It is tightening the boundary between **existing substrate** and the actually missing **support artifact**.
