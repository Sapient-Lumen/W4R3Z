# Entry 348 — in-place initialization deepened around placement topology, constructor lanes, address commit, and failure cleanup for P-0447

This pass deepened **P-0447 In-Place Initialization Adoption Kit** instead of adding another pinning macro, another generic unsafe checker, or another language-design summary.

## Why this lane earned another pass now

Fresh official and substrate signals line up unusually well:

- the 2026 Rust flagship themes explicitly keep **Beyond the `&`** focused on field projections, reborrow traits, and **design alignment on in-place initialization**;
- the 2025H2 in-place-initialization goal names five concrete drivers: avoiding stack overflow for large heap values, C++ interop, pinned C out-pointer constructors, async fn in dyn trait, and self-referential types;
- the goal also explicitly says the ecosystem already has multiple external-crate experiments and that Rust should learn from them rather than pretend the problem is theoretical;
- `moveit` documents safe in-place construction of Rust and C++ objects and says its `New` trait writes into `Pin<&mut MaybeUninit<T>>` where address stability matters;
- `pin-init` already documents safe initialization of pinned data structures, `PinUninit`, pointer-init traits, and `Rc::pin_with` / `Arc::pin_with` helpers;
- Crubit `ctor.rs` explicitly compares itself against `moveit`, `pin-init`, and the upstream in-place-init proposal, while noting that it only allows pinned initialization;
- and the latest pin-init material shows concrete cases for large values, out-pointers, fallible init, embedded pinned fields, and generated pin projections.

Together these make one conclusion stronger: a worthy ecosystem contribution here is not just “offer some init macros.” It is a crate that helps other people inspect **where initialization actually happened, which constructor family was in play, when the final address became authoritative, how failure cleanup behaved, and what changed across revisions**.

## Main judgment after the pass

The strongest near-term contribution in this lane is **not** another initialization engine.
It is an **in-place initialization adoption contract layer** above `pin-init`, `moveit`, Crubit `Ctor`, local out-pointer adapters, and future language support.

This pass promotes six P-0447 review objects into first-class status:

1. **placement-topology receipt** — where bytes were first written and where the final allocation lives;
2. **constructor-lane report** — whether the case is by-value Rust, pinned-init, C out-pointer, `moveit`, Crubit `Ctor`, or a provisional future-language lane;
3. **address-commit receipt** — when the final address becomes authoritative and moves become forbidden;
4. **failure-cleanup report** — what can fail, what may be partially initialized, and who owns rollback;
5. **init-transition diff** — what changed across revisions;
6. **init-support bundle manifest** — the portable review bundle joining those facts.

## Why these objects matter

Current substrate is finally specific enough that the archive should stop flattening it:

- a crate can claim “constructed on the heap” while still stack-bouncing a large temporary first;
- a wrapper can return a pinned handle while leaving unclear when the real address-commit moment happened;
- a C out-pointer path can look successful while leaving error cleanup or partial initialization under-specified;
- and a C++ constructor lane can be very different from Rust’s ordinary move semantics even if the public API shape looks similar.

## New archive-level stance

For in-place-init-facing work, the archive should now prefer this layering:

1. **P-0447** for placement topology, constructor-lane comparison, address commit, failure cleanup, and transition drift;
2. **P-0440** when the hard problem is projection/reborrow semantics and aliasing witnesses rather than construction topology;
3. **P-0460** when the hard problem is field-carried invariants after construction;
4. **P-0121** when the hard problem is broader FFI boundary truth rather than constructor placement.

That keeps the portfolio from minting another crate that merely says “supports pinned initialization” without clarifying where construction happened or what the address/failure contract really is.

## What should count as a worthy crate contribution after this pass

A worthy in-place-initialization contribution should now be able to answer all of these cleanly:

1. **Where were the first writes performed, and where does the final allocation live?**
2. **Which constructor family / move semantics are in play?**
3. **When does the final address become authoritative and movement become forbidden?**
4. **Which failure paths may partially initialize state, and who owns cleanup?**
5. **Can another engineer compare the initialization story across revisions without reverse-engineering every unsafe adapter by hand?**

If a candidate crate cannot answer those questions, the archive should usually treat it as initialization folklore rather than a serious adoption contract.
