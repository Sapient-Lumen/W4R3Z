# Entry 187 — artifact sidecar contracts promoted into a fixture-first shipping-policy lane

This pass did not add a new proposal.
It upgraded **P-0479 Cargo Artifact Sidecar Contract Kit** into a more implementation-shaped lane with schema files, scenario packs, and a sharper statement of what the crate should actually hand other people.

## Why this moved now

Several official signals now line up unusually well.

### 1. Cargo already exposes enough artifact substrate to support a sidecar contract layer

Cargo external-tools JSON emits `compiler-artifact` messages with produced filenames plus package/target/profile context.
That means a downstream crate can freeze association evidence instead of forcing every consumer to rediscover artifact ownership from scratch.

### 2. Cargo has explicit output-shape help because artifact lookup is genuinely painful

The unstable `--artifact-dir` feature exists because the exact location and naming of outputs are otherwise annoying for downstream tools to consume predictably.
That is exactly the kind of seam where a contract crate can add value.

### 3. Sidecars are real now, not speculative

Cargo’s unstable `sbom` feature emits `<artifact>.cargo-sbom.json` files beside executable and linkable outputs and exposes `CARGO_SBOM_PATH`.
That means the ecosystem now has a concrete, first-party sidecar family worth designing around.

### 4. The sidecar-adjacent contract is still moving in ways that justify downstream receipts

Cargo’s changelog recently clarified that SBOM package IDs are fully qualified.
That is good progress upstream, but also a reminder that downstream tools still need explicit schema/version and exactness receipts instead of treating all sidecar facts as timeless truth.

## Current judgment

The worthy crate here is not:

- just another artifact manifest,
- just another SBOM emitter,
- or just another build-output scanner.

The worthy crate is the boring shared layer that can hand other people:

1. a **sidecar contract lock**,
2. an **artifact-sidecar index**,
3. a **schema/stability report**,
4. an **attachment policy receipt**,
5. an **association exactness receipt**,
6. and a **diffable sidecar-surface bundle**.
