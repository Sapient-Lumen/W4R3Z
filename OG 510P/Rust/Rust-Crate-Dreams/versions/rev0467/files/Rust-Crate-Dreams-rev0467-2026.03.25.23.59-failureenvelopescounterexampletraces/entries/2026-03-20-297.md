# Entry 297 — msrv-workspace-lab sharpened around policy activation, command-family floors, and lockfile-authoring truth

This pass returned to **P-0036 MSRV Workspace Lab** because the archive still left one costly simplification on the table:

> a workspace could honestly publish one `rust-version`, or even pass one pinned build lane, while still leaving reviewers without one compact answer to **whether the intended resolver policy was active**, **which command families really work at that floor**, and **whether lockfile authoring/update quietly requires a newer toolchain**.

## What moved this time

Several current Cargo/MSRV signals make that blur more expensive now than it used to be:

- Cargo’s `rust-version` docs now explicitly recommend choosing a support policy and say Cargo allows **multiple policies within one workspace**;
- those same docs warn that shared dependencies may be forced down to lowest-common versions and that, under `fallback`, one package’s Rust version can affect dependency versions chosen for another;
- the Rust 2024 edition guide says `edition = "2024"` implies resolver v3 and `fallback`, but also says the resolver is a **global workspace setting** and that a **virtual workspace still needs `[workspace] resolver = "3"`** to opt in;
- Cargo 1.83 made lockfile format v4 the default for creating/updating a lockfile and notes that toolchains 1.78+ support it;
- Rust 1.85’s release notes say Cargo now **respects `rust-version` when generating the lockfile**;
- Cargo’s FAQ still treats `Cargo.lock` as a deterministic snapshot that helps verify an older MSRV, which is useful but also means “builds from the committed lockfile” is not the same promise as “can keep authoring/updating that lockfile on the same floor”;
- a fresh Cargo issue shows a concrete case where `cargo run` works while `cargo metadata` breaks because an inactive target edge drags in a newer edition under `fallback`;
- and `cargo-msrv` continues to improve, but its center of gravity is still **finding or verifying a minimum version**, not publishing a reviewable workspace support contract.

## Main planning move

This pass promoted three more first-class review objects for **P-0036**:

1. **policy activation truth** — was the intended MSRV-aware resolver policy actually active at the workspace root?
2. **command-family floor truth** — which command families are supported at the policy floor, and which require something newer?
3. **lockfile-authoring truth** — what floor is required to read/write/update the lockfile path, and is that higher than the supported build floor?

## Why this matters

Without those objects, the archive still permits a very ordinary lie:

- a maintainer can truthfully say the crate supports Rust `X`,
- a reviewer can truthfully see a green `cargo build`,
- a workspace can truthfully contain edition-2024 members,
- and yet the intended `fallback` policy may not actually be active for the root, `cargo metadata` or `cargo package` may require more than the build lane, or `cargo update` may silently write a lockfile that older support lanes cannot read.

That is not just wording drift.
It is the difference between “we found a number once” and “another team can review the ongoing support posture of this workspace.”

## Main judgment after the pass

A worthy MSRV-support contribution for Rust should now provide more than:

- one inferred minimum compiler,
- one declared `rust-version`,
- or one green build receipt.

It should also provide:

- one explicit **policy-activation receipt**,
- one compact **command-family floor report**,
- one explicit **lockfile-floor receipt**,
- and one blame surface explaining whether the mismatch came from workspace coupling, inactive target edges, edition floors, or ongoing lockfile-authoring behavior.

That is a better answer to today’s Cargo ecosystem than either:

- “cargo-msrv found a version,”
- “edition 2024 means fallback is on,”
- or “the pinned lockfile still builds, so our MSRV promise is fine.”
