# Entry 303 — ffi-boundary-conformance-kit sharpened around ownership-transfer, unwind-posture, callback-execution, and binding-coverage truth

This pass returned to **P-0121 FFI Boundary & Bindings Conformance Kit** because the archive still left one familiar but costly blur too available:

> a Rust crate could truthfully say it exposes a C ABI, uses UniFFI or Diplomat, catches panics, supports callbacks or async, and generates several foreign-language bindings while still leaving another team unable to tell **who owns what**, **what may unwind**, **where callbacks execute**, and **which surfaces are actually checked**.

## What moved this time

Several current Rust and ecosystem signals make that blur harder to excuse:

- the 2024 Edition now requires `unsafe extern` blocks, making boundary obligations explicit rather than folkloric;
- the Reference and RFC 2945 keep unwinding and non-unwinding ABI families distinct instead of treating “FFI panic behavior” as one fuzzy story;
- `catch_unwind` still gives a real containment tool, but only for unwinding Rust panics;
- the Nomicon still states that asynchronous callbacks targeting Rust objects must stop before those objects are destroyed, which is an explicit teardown contract, not a style preference;
- UniFFI now exposes concrete runtime surfaces for buffers, handles, callbacks, and future poll/cancel/free flows;
- UniFFI’s callback-interface docs also admit that callback interfaces are soft-deprecated and conceptually thread-safe outside Rust’s own enforcement;
- Diplomat, `cxx`, `cbindgen`, and `wit-bindgen` each prove the ecosystem has serious substrate, but none of them publish one shared boundary contract for ownership, unwind posture, callback execution, and check strength.

That combination means the missing crate is no longer best described as “another generator” or “a release helper for bindings”.
It is better described as a **reviewable FFI boundary contract** above today’s generators and bridges.

## Main planning move

This pass promoted four first-class review objects for **P-0121**:

1. **ownership-transfer truth** — whether a value is borrowed, copied, opaque-handle-based, explicit-free, or otherwise runtime-managed;
2. **unwind-posture truth** — whether a Rust panic is caught and translated, forced to abort, intentionally allowed via an unwind ABI, or still implicit;
3. **callback-execution truth** — whether callbacks run inline, on foreign threads, or through continuation/future machinery, and what teardown rule is required;
4. **binding-coverage truth** — whether each surface is directly checked, generated-only, packaging-only, docs-only, or still manual-review-only.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “we generate Swift/Kotlin/Python bindings,”
- another maintainer can truthfully say “we also expose a plain C header or C++ bridge,”
- a reviewer can truthfully see `catch_unwind` or async machinery in one place,
- and a downstream team can still be unable to tell whether a returned buffer is explicit-free, whether a callback may arrive after object destruction, whether `extern "C"` versus `C-unwind` was chosen intentionally, or whether any given language surface was actually exercised in CI.

That is not a wording nit.
It is the difference between “there is FFI substrate” and “another team can review the actual boundary contract they are being asked to trust.”

## Main judgment after the pass

A worthy FFI-support contribution for Rust should now provide more than generated bindings and release glue.
It should also provide:

- one explicit **ownership-transfer receipt**,
- one explicit **unwind-posture receipt**,
- one explicit **callback-execution report**,
- and one honest **binding-coverage report**.
