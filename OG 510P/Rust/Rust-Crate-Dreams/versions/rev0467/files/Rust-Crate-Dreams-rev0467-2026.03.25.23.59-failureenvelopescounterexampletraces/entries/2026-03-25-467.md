# Entry 467 — 2026-03-25

## Theme
**falsification / failure-envelope / counterexample-trace pass**

## Why this pass exists

The archive already had strong layers for:
- evidence bundles,
- conformance tiers,
- interchange profiles,
- policy packs,
- review packets,
- renewal programs,
- delta handling,
- and assurance cases.

What it was still missing was a sharper answer to:

**how should a worthy crate help another team see where a claim fails, which scenario disproved it, what guarantee must be withdrawn, and what smaller claim still survives without reconstructing the whole basis by hand?**

This pass answers with:
- one shared **failure envelope** for every bounded claim family,
- one portable **counterexample trace** that names the disproving witness and scenario,
- one **disproof summary** that tells a reviewer what broke and what still stands,
- one **degraded-claim surface** for smaller surviving guarantees,
- one **repair hint note** that points to the next honest rerun or replay slice,
- and one **refutation bridge** so later cases can inherit, clear, or supersede earlier failures instead of burying them.

## Main judgment

### 1. The next missing layer is not stronger assurance prose; it is falsification discipline

The archive already knew how a worthy crate might emit receipts, support tiers, policy verdicts, review packets, renewal ledgers, delta bundles, and assurance cases.
What it still lacked was a durable **negative-evidence structure**.

A worthy crate should increasingly provide downstream teams with:
- **which scenario falsifies a claim**,
- **which witness is decisive**,
- **which narrower claim still survives**,
- **what exact guarantee is withdrawn**,
- **what cheapest replay or rerun could clear the failure**,
- and **whether the failure supersedes, downgrades, or merely challenges the prior case**.

That is a stronger answer to “what should the crate provide other people?” than one more green report.

### 2. The strongest falsification-first lane is the support-envelope ring, with the decision front door right behind it

For the falsification lens, the strongest immediate build slice is now:
1. **P-0472 + P-0484**
2. **P-0509 + P-0536 + minimal P-0535**
3. **P-0486**
4. **P-0431 + P-0496 + P-0125**
5. **P-0537**
6. **P-0538**

This does **not** overthrow the archive’s broad frontier.
It changes the next practical question.

The support-envelope ring rises because that is where failure evidence is naturally born:
- docs that pass locally but fail on docs.rs,
- target assumptions that drift under hosted defaults,
- hosted metadata that shows scope but not runtime qualification,
- or witnesses that are real but insufficient.

The decision front door remains close behind because another team still needs the failure carried into a usable recommendation, degraded claim, or refusal.
Debugger support rises because it is one of the clearest matrix-heavy places where a counterexample tuple matters more than a broad positive slogan.

### 3. A worthy crate should ship a failure envelope, not only a success packet

A stronger crate promise is not only:
- “here is the packet,”
- “here is the verdict,”
- or “here is the assurance case.”

It is also:
- **here is the scenario that broke the claim**,
- **here is the decisive disproving witness**,
- **here is the smaller claim that still survives**,
- **here is the guarantee we now refuse to imply**,
- **here is the cheapest honest replay slice**,
- and **here is how this failure relates to the prior case**.

That matters especially where support claims are subtle or expensive:
- docs.rs local-vs-hosted mismatches,
- debugger and OS/version variance,
- build-script capability boundaries,
- target-tier and default-target drift,
- semver checks with visible overrides,
- and safety-critical or long-lived adoption.

### 4. The archive itself now deserves a machine-readable failure memory file

The repo already had `archive-state.json`, `suite-topologies.json`, `conformance-kits.json`, `interchange-profiles.json`, `policy-packs.json`, `review-packets.json`, `renewal-programs.json`, `delta-programs.json`, and `assurance-cases.json`.
This pass adds **`failure-envelopes.json`** so later human/LLM passes can see:
- the current failure vocabulary,
- the default artifact family for counterexample traces,
- which lanes are strongest under the falsification lens,
- and which lane should define shared degraded-claim and repair-hint semantics first.

This is repo hygiene, not a crate proposal.

## Practical lesson from this pass

A worthy Rust crate contribution should often provide other people with:
- one **failure envelope**,
- one portable **counterexample trace**,
- one **disproof summary**,
- one **degraded-claim note**,
- one explicit **repair-hint / replay-slice note**,
- and one clear **refutation / supersession bridge**.

That is how a crate gives another team something they can not only run and believe, but also **disprove cleanly, downgrade honestly, and repair cheaply**.
