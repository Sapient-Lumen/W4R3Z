# Entry 302 — i18n-icu-kit sharpened around message-argument schema, locale-data profile, formatter-coverage, and fallback-witness truth

This pass returned to **P-0039 i18n-icu-kit** because the archive still left one ordinary product-localization bluff too cheap:

> a Rust crate could truthfully say it uses ICU4X, Fluent, compile-time checked messages, embedded assets, and locale fallback, yet still leave another team unable to tell what argument contract is promised, what locale data is actually shipped, which rich formatter families are really available, and what fallback path actually resolves at runtime.

## What moved this time

Several current official and ecosystem-standard surfaces make that blur more expensive now than it used to be:

- ICU4X’s current README explicitly supports both compiled-data constructors and explicit provider-backed constructors, including runtime-updateable blob providers and locale fallback adapters;
- ICU4X’s current data-management tutorials make locale-data footprint selection and runtime loading explicit integration choices;
- ICU4X’s locale fallback APIs expose different fallback priorities instead of one magical default path;
- `fluent` still documents `FluentBundle` as a low-level container and says higher-level APIs should build above it;
- `fluent-templates` and the `fluent-rs` workspace prove there is demand for high-level lifecycle helpers, but they do not publish one shared support contract;
- and `typed-i18n`, `rust-i18n`, `i18n-embed`, and `i18n-embed-fl` each prove demand for some combination of type safety, embedding, fallback, and compile-time checks, while still leaving those truths fragmented.

## Main planning move

This pass promoted four more first-class review objects for **P-0039**:

1. **message-argument schema truth** — whether public messages have generated/checked argument names and kinds or only ad hoc interpolation assumptions;
2. **locale-data profile truth** — whether support comes from ICU4X compiled defaults, a baked subset, runtime providers, or a mixed profile;
3. **formatter-coverage truth** — whether the stack offers plain substitution, Fluent-only selection, or ICU4X-backed number/date/list/relative-time coverage;
4. **fallback-witness truth** — whether locale resolution is merely promised in prose or actually recorded as a reviewable witness.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “we use ICU4X and typed messages,”
- a downstream adopter can still discover that only a tiny locale subset is really shipped,
- another adopter can still discover that “formatted values” really means plain string interpolation,
- and nobody has one compact answer for whether fallback came from Fluent resource selection, ICU4X locale fallback, app-specific negotiation, or all three.

That is not cosmetic.
It is the difference between:

- “the app is localized somehow,”
- “the message contract is typed and rich-format capable for the locales we claim,”
- and “the support story still depends on implicit wiring and hopeful README reading.”

## Main judgment after the pass

A worthy localization-support contribution for Rust should now provide more than one ergonomic macro, one syntax, or one bundling path.
It should also provide:

- one explicit **message-argument schema receipt**,
- one explicit **locale-data profile receipt**,
- one explicit **formatter-coverage report**,
- and one honest **fallback-witness report**.
