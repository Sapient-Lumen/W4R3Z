# Entry 237 — toolchain/target support deepening around override lineage, component availability, and exercise scope

This pass did **not** promote a new lane.
It sharpened **P-0484 Toolchain & Target Support Contract Kit** into a more reviewable shape.

## Why this moved now

The archive had already made P-0484 believable as a `0.1` candidate, but three important support questions were still too easy to blur together:

1. **Which selector actually made this the active toolchain?**
   A repository pin, a directory override, `RUSTUP_TOOLCHAIN`, and `cargo +toolchain` do not carry the same meaning.

2. **Were the requested components actually available on the effective toolchain?**
   A requested profile or component list is not the same as installed reality, especially on nightly where missing components can trigger a fallback to an older nightly.

3. **What scope was really exercised?**
   Compile success, docs.rs visibility, runner-backed testability, and host build-script / proc-macro behavior are materially different support slices.

Current Rust and ecosystem substrate makes that split timely rather than speculative:
- rustup explicitly documents override precedence and proximity behavior;
- `path` toolchains ignore `components`, `targets`, and `profile`;
- rustup profiles and nightly component availability already create real drift between requested and effective state;
- Cargo documents target-specific `linker` / `runner` config, `build.target`, and the split where `--target` keeps `rustflags` off host-built build scripts and proc macros;
- Cargo’s target model already distinguishes library/bin/example/test/bench surfaces;
- docs.rs metadata and builds docs spell out both the public target posture and hosted sandbox limits;
- and the target-tier policy explicitly expects build/test documentation and baseline-expectation documentation.

## Main planning move

This pass made three more review objects explicit:

- **override lineage** — which rustup selector actually won, what it shadowed, and whether the repository pin was really in force;
- **component availability** — requested versus effective toolchain/component state, including nightly fallback when components are missing;
- **exercise scope** — whether a lane is supported for compile/docs/run/test/bench and whether host helper scopes were actually exercised.

Those are the pieces that make the difference between “we support this target” and “we publish a reviewable whole-project support contract somebody else can trust”.

## Main judgment after the pass

A worthy `0.1` toolchain/target support crate should now publish not just a support class, evidence report, and prerequisite manifest, but also:

- **which selector actually made the effective toolchain active**,
- **whether requested components were really available on the effective toolchain**,
- and **which scopes were truly exercised instead of merely inferred**.

The sharper move, for now, is still to deepen **P-0484** rather than open another neighboring linker, docs, CI, or MSRV-only crate.
