# Entry 202 — crate configuration scenarios promoted as the setup-support lane

This pass added a new top-level proposal: **P-0516 Crate Configuration Scenario Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing task-first crate choice, support claims, shared profiles, setup scenarios, compile-time guidance, runtime handoff, upgrade/off-ramp work, generic Cargo config provenance, feature-matrix testing, and feature-doc rendering into one fake “better crate setup docs” story.

## Why this moved now

Several current Rust signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good “how do I set this crate up?” lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- **release-to-release migration** via **P-0514**,
- and **successor / off-ramp support** via **P-0515**.

But it still lacked a good answer to:

- “Once a team already chose this crate, what exactly does the crate hand them so they can pick the right feature/profile/env recipe?”

That left the archive with better answers for **selection**, **interop**, **debugging**, **upgrades**, and **sunsets** than for **first real adoption/setup**.

### 2. Official Cargo substrate makes configuration a real product surface, not a detail

Cargo features are a real manifest surface.
Cargo’s feature docs explicitly say features should usually be additive, and they discuss what to do when mutually exclusive choices appear.
`cargo build` and `cargo doc` already treat `required-features` as a first-class way to expose configuration-dependent targets.
Cargo also has a stable, versioned `cargo metadata` format that tools can import.

That combination means the ecosystem no longer lacks knobs; it lacks a joined receiver-facing artifact over those knobs.

### 3. Docs.rs and feature metadata deepen the need for named scenarios rather than raw toggles

Docs.rs metadata lets maintainers configure feature sets and `cfg` assumptions for documentation builds.
RFC 3416 exists because feature descriptions, visibility, and deprecation still need stronger structured metadata.
The Inside Rust 1.93 development-cycle post shows feature metadata and related work are still active.

That makes the missing value sharper: not “Cargo needs more features”, but “users need named, checked scenarios above feature soup.”

### 4. Existing tools cover slices of the problem, not the joined scenario contract

`cargo-hack` and `cargo-feature-combinations` can exercise many feature combinations.
`document-features` can render feature documentation from `Cargo.toml`.
`cargo tree --edges features` and resolver docs help explain why a feature got enabled.

What is still missing is the boring artifact that can hand users:

- named scenarios,
- the minimal recipe for each one,
- checked setup receipts,
- explicit conflict classes,
- and a diff when the crate’s setup surface changes.

## Current judgment

The worthy crate here is not:

- another generic Cargo config explainer,
- another feature-powerset runner,
- another docs.rs helper,
- another feature-doc renderer,
- or another raw metadata wrapper.

The worthy crate is the boring receiver-facing setup layer that can hand other people:

1. one **scenario pack**,
2. one **config-surface receipt**,
3. one **scenario-profile report**,
4. one **scenario-recipe manifest**,
5. one **scenario-check report**,
6. one **scenario-conflict report**,
7. one **scenario diff**,
8. and one explicit **manual-review boundary** when the crate’s intended setup lanes are less clean than the docs imply.
