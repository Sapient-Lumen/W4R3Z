# Entry 308 — cargo-feature-surface-contract-kit added for public feature maps, activation profiles, and unification-risk truth

This pass added a new top-level proposal: **P-0528 Cargo Feature Surface Contract Kit**.

## Why this lane earned a slot

The archive already had better answers for:

- crate choice,
- capability contracts,
- cfg/item availability,
- Cargo config truth,
- MSRV policy activation,
- upgrade support,
- and resolver explanation.

It still lacked one receiver-facing answer to a common adoption question:

> “What does enabling this feature really mean, which combinations are supported, and where can Cargo’s unification/default behavior still surprise us?”

Current Cargo substrate now makes that absence concrete enough to justify a dedicated lane.

## What moved this time

The main planning move was to treat **Cargo feature support as a contract layer**, not as a raw manifest dump.

This pass therefore promoted four review objects to first-class status:

1. **feature-surface truth** — which names are public policy versus grouped dependency wiring or hidden plumbing;
2. **activation-profile truth** — which named combinations are supported, sampled, recipe-only, or unsupported;
3. **conflict-policy truth** — whether features compose, are exclusive, or deliberately choose one winner;
4. **unification-risk truth** — where default leakage, resolver-v2 splits, or workspace unification can still change what a downstream user effectively gets.

## Why this matters

Without those objects, the ecosystem still permits a common shortcut:

- Cargo can truthfully show a feature graph,
- a maintainer can truthfully say “we support `serde`, `tokio`, and `rustls`, ”
- CI can truthfully pass `--all-features`,
- and a downstream team can still have no compact answer for:
  - which feature names are actually part of the public contract,
  - which combinations were truly exercised,
  - whether backend toggles are exclusive,
  - and whether workspace/build/target unification altered the effective surface.

That is not just manifest trivia.
It is supportiveness.

## Main judgment after the pass

A worthy feature-support contribution for Rust should now provide more than a raw feature list or a combo runner.
It should provide:

- one explicit **feature-surface receipt**,
- one explicit **activation-profile report**,
- one explicit **conflict-policy receipt**,
- and one honest **unification-risk report**.
