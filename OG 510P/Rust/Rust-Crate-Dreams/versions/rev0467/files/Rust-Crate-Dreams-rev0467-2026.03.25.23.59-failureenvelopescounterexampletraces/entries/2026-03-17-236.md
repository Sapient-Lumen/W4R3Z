# Entry 236 — crate persistence-surface deepening sharpened around compatibility authority, atomicity scope, and recovery witnesses

This pass did **not** promote a new lane.
It sharpened **P-0522 Crate Persistence Surface Pack Kit** into a more reviewable shape.

## Why this moved now

The archive had already made P-0522 believable as a `0.1` candidate, but three important persistence questions were still too easy to blur together:

1. **Why should anyone trust the compatibility claim?**
   A stable external wire spec, a schema snapshot kept under version control, revision-history metadata, and “Serde probably keeps working” are not the same authority level.

2. **What kind of atomicity is actually being claimed?**
   No-intermediate-state replacement, same-mount destination swap, data sync, directory-entry sync, and full local durable publish are materially different.

3. **Was the recovery path merely documented, or actually witnessed?**
   A storage engine can document crash recovery or repair tooling, but a receiver-facing persistence contract is stronger when it records whether recovery was exercised on the current surface.

Current Rust and ecosystem substrate makes that split timely rather than speculative:
- `std::fs::File` distinguishes `sync_data` and `sync_all`, while `Drop` ignores close errors.
- `std::fs::rename` replaces an existing destination and does not work across mount points.
- `tempfile::NamedTempFile::persist` warns that neither the file contents nor the containing directory are synchronized when it returns.
- `atomic-write-file` documents no-intermediate-state overwrite semantics.
- `serde-reflection`, Postcard, and `revision` provide different kinds of compatibility evidence.
- redb documents automatic recovery plus an explicit integrity-check/repair boundary.

## Main planning move

This pass made three more review objects explicit:

- **compatibility authority** — is the promise backed by a stable external spec, a guarded schema snapshot, revision-history metadata, engine docs, or only a best-effort Serde shape?
- **atomicity scope** — does the write path guarantee only “no intermediate state”, same-mount replacement, synced data without a durable directory entry, or a stronger local publish boundary?
- **recovery witness** — is recovery/repair declared only, or was it actually observed on a representative surface?

Those are the pieces that make the difference between “this crate persists state” and “this crate publishes a reviewable persistence support contract somebody else can trust”.

## Main judgment after the pass

A worthy `0.1` persistence-support crate should now publish not just a surface inventory and write-path/failure-model summary, but also:

- **why a compatibility promise is authoritative**,
- **what exact atomicity scope the save path reaches**,
- and **whether recovery or repair paths are declared-only or actually witnessed**.

The sharper move, for now, is still to deepen **P-0522** rather than open another neighboring serializer, journaling, or “durable config” crate.
