# 2026-03-17 (223) — crate performance-envelope productization pass

This pass did **not** add a new lane.
It sharpened **P-0517 Crate Performance Envelope Pack Kit** into a more implementation-ready `0.1` shape.

## Main judgment

The missing value is still **not** another benchmark runner, another profiler, or another hosted regression service.
The sharper missing layer is a **maintainer-facing performance contract** that records:

- which workloads matter,
- which metric is actually authoritative,
- how faithful the measured environment is,
- and what kind of trust class the result deserves.

## Why this lane looks sharper now

- Cargo’s benchmark/profile docs now make it very clear that target model, harness choice, and profile choice are real parts of the measurement story;
- Cargo’s 1.84 development-cycle notes make the tension explicit between bench-profile convenience and release/profiling fidelity;
- Criterion, Iai-Callgrind, Divan, and CodSpeed compatibility layers now make the substrate concrete enough that the missing value is increasingly the review artifact above them;
- and the CodSpeed compatibility docs make it explicit that “the same suite still runs” is not identical to “the same benchmark semantics are supported”.

## What to keep separate

- Keep **P-0517** separate from setup/configuration scenarios (**P-0516**).
- Keep **P-0517** separate from observability contracts (**P-0518**).
- Keep **P-0517** separate from profiling evidence bundles and generic benchmark frameworks.
- Keep **P-0517** separate from hosted CI perf services.

## Preferred proving grounds

- CLI crates with cold-start and binary-size posture
- parser/serializer crates with tiny-input latency versus throughput tradeoffs
- crates using Iai-Callgrind for CI-stable instruction budgets
- crates layering CodSpeed on top of Criterion or Divan benches
- frameworks whose default profile or adapter choice changes what users should trust
