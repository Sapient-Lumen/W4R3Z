# Entry 396 — async runtime assurance now needs deployment topology and guarded capability matrices

This pass stays inside an already-high-value lane.
It deepens:

**P-0532 Async Runtime Assurance Profile Kit**.

## Why this lane earned another serious refresh now

The previous pass made runtime family, service topology, capability routes, and bridge debt explicit.
That still left one important way to overclaim support:

> “It works with Tokio/Embassy/RTIC.”

Current sources make it clear that this sentence is often too coarse to review.

Fresh signals that sharpen the problem:

- the March 2026 Rust challenges post still identifies async complexity and runtime lock-in as live ecosystem pain;
- the January 2026 safety-critical post still says teams need requirements for safety-case-friendly async runtimes;
- Tokio’s current signal docs split Unix and Windows surfaces into different modules and feature gates;
- Tokio’s current `AsyncFd` docs are Unix-specific and register against the current reactor, which means even within one runtime family some capabilities are lane-scoped rather than global;
- Tokio’s I/O and timer docs still say some surfaces require runtime context or enabled drivers;
- Embassy’s current book says the same ecosystem can run `std` examples on a PC while also targeting microcontrollers, and Embassy executor docs still emphasize static-task / no-`alloc` posture;
- RTIC’s current book still makes dispatchers, priorities, and timer queues target- and priority-scoped rather than one flat runtime surface.

Together these say the sharper missing question is no longer only:

> “Which runtime family did you choose, and what services does it have?”

It is also:

> “Which deployment lane are we talking about, which capabilities are available in that lane, and what cfg/feature/context guards fence those claims?”

## Main judgment after the refresh

**P-0532** is now stronger as a **deployment-topology and guarded-capability matrix lane**.

That means a worthy crate in this lane should explicitly own:

- `runtime-deployment-topology.receipt.json`,
- `capability-availability.matrix.json`,
- `surface-guard.report.json`,
- plus bundles that keep runtime family, service topology, deployment lanes, and guarded capability claims separate.

It should **not** try to own:

- all target-compilation/toolchain support truth,
- every cfg and feature interaction in the project,
- or a universal runtime-neutral portability layer.

## What should count as a worthy crate contribution in this lane now

A worthy async-runtime crate should now hand other people:

1. **one deployment-topology receipt** that says which host/dev/CI/target lanes exist and what runtime family each lane actually uses,
2. **one capability-availability matrix** that says which async capabilities are supported, unsupported, or guarded in each lane,
3. **one surface-guard report** that says which cfg/feature/runtime-context/provider guards fence the public support story,
4. **one service-topology receipt** that still records where time, I/O, signals, blocking, or dispatcher services come from,
5. **one portable bundle** another team can reopen later without reconstructing platform scope from docs, examples, and tribal memory.

If a candidate crate cannot do those things, the archive should usually treat it as substrate, adapter, or convenience glue — not the missing epic support-contract layer.
