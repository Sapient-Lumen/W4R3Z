# Entry 201 — crate off-ramp packs promoted as the deprecation/successor-support lane

This pass added a new top-level proposal: **P-0515 Crate Off-Ramp Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing crate health metadata, task-first crate choice, compile-time guidance, runtime handoff, release-to-release upgrades, advisory detection, and publish/yank mechanics into one fake “better deprecation tooling” story.

## Why this moved now

Several current Rust signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a good “leave this crate” lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- **runtime failure handoff** via **P-0513**,
- and **release-to-release migration** via **P-0514**.

But it still lacked a good answer to:

- “Once a team already depends on this crate, what exactly does the crate hand them when it wants them to stop?”

That left the archive with better answers for **adoption**, **support**, **debugging**, and **upgrades** than for **sunsets, successors, and emergency exits**.

### 2. Official Rust guidance already points toward successor planning, but only in fragments

The December 2025 vision-doc post says Rust should “double down on extensibility” and explicitly calls for **better diagnostics and guidance from crates**.
The 2025 survey says online documentation remains the preferred canonical reference, followed by studying the code itself.
The warn-by-default lint docs say deprecations should usually include a note on what to use instead.
Cargo’s SemVer guidance explicitly treats added deprecations as part of the update experience.

That combination makes structured off-ramp support feel like a first-class design problem, not just a docs footnote.

### 3. Cargo and crates.io own important pieces, but not the maintainer-authored exit artifact

Cargo’s yank docs are very clear: yanking removes a version from new resolution but does **not** delete it.
`cargo update` tells users to try a non-yanked version or seek help from maintainers.
crates.io now exposes a Security tab with affected version ranges from RustSec, and the 2026 malicious-crate policy update says RustSec advisories remain the always-on notification path.

Those are real building blocks, but they still do **not** tell a downstream user:

- which successor to adopt,
- whether the recommendation is a real replacement or a temporary stopgap,
- which exit recipes were checked,
- and where manual redesign is still required.

### 4. Existing ecosystem tools detect risk or staleness, not checked successor paths

`cargo-audit` can tell you a dependency is vulnerable.
`cargo-deny` can enforce bans or advisory policy.
`cargo-outdated` can tell you a newer version exists.
Some crates, like `sello`, publish hand-written rename instructions on docs.rs.

What is still missing is the joined, boring artifact that can hand users:

- a successor map,
- deprecation/advisory/yank receipts,
- checked off-ramp recipes,
- compatibility classifications,
- and explicit manual-review boundaries.

## Current judgment

The worthy crate here is not:

- another advisory client,
- another outdated-version checker,
- another dependency-ban policy layer,
- another deprecation-note helper,
- or another publish/yank wrapper.

The worthy crate is the boring receiver-facing exit layer that can hand other people:

1. one **off-ramp pack**,
2. one **successor-map report**,
3. one **deprecation-surface receipt**,
4. one **off-ramp recipe manifest**,
5. one **successor-compat report**,
6. one **sunset-check report**,
7. one **off-ramp diff**,
8. and one explicit **manual-review boundary** when there is no honest drop-in successor.
