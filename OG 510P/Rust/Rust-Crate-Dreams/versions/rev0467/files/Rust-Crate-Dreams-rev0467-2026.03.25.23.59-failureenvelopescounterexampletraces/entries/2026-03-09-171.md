# Entry 171 — passkey lab upgraded into capability receipts and comparability truth

This pass again avoided adding more proposal count.

The stronger move was to make **P-0200 WebAuthn & Passkeys Interop + Device Lab Kit** much more explicit about what another maintainer should receive when a passkey run fails.

## Main judgment

The next important missing value is **not** another passkey SDK.
It is a compact artifact contract for separating:

- scenario truth,
- runner-capability truth,
- ceremony evidence truth,
- comparability truth,
- and imported certification or device evidence.

Without that separation, too many future passkey diffs collapse into fake stories like “browser X failed WebAuthn”.

## Why these changes were the right ones

### 1. The proposal still under-specified lane honesty
The earlier pass made **P-0200** directionally strong.
But it still did not fully answer a receiver-facing question:

> when a passkey run differs, did the scenario differ, did the lane differ, or did the lane simply fail to earn a strong comparability claim?

This pass makes that much more explicit.

### 2. Current ecosystem signals support a lab layer above real substrate
Recent ecosystem signals make capability receipts and comparability rules more important, not less:

- WebAuthn Level 3 is a current W3C Candidate Recommendation Snapshot.
- WPT documents virtual-authenticator and SPC automation commands.
- Selenium documents a practical virtual-authenticator surface.
- geckodriver still warns that virtual-authenticator endpoints are currently unreliable.
- `webauthn-rs` and `passkey-rs` make Rust-only and mixed-lane planning increasingly plausible.
- FIDO certification and conformance tooling already exist outside Rust.

That means a strong Rust crate here should preserve lane provenance instead of burying it.

### 3. The archive needed capability receipts, not another auth framework proposal
The repo already had enough prose about passkeys.
What it lacked was the artifact split that makes future revisions smaller and more honest.

## New planning stance

For the next few passes, the archive should prefer:

- treating `scenario-profile` and `runner-capability.receipt` as first-class public artifacts,
- forcing `manual-review-required` and `not-comparable` outputs when runner truth warrants it,
- keeping certification and conformance imports distinct from local automation results,
- and treating overlay APIs like SPC as explicit overlays rather than as silent core behavior.

The archive should **not** drift back into a single-file story where scenario truth, automation scope, device reality, and certification truth are all implied instead of stated.
