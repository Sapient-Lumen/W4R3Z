# Entry 200 — crate upgrade packs promoted as the release-to-release supportiveness lane

This pass added a new top-level proposal: **P-0514 Crate Upgrade Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing SemVer evidence, public-API review, release automation, changelog generation, compile-time guidance, runtime handoff, and release-to-release migration support into one fake “better release tooling” story.

## Why this moved now

Several current Rust signals line up unusually well.

### 1. The ecosystem-supportiveness frontier still lacked a release-to-release lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- **compile-time / early-failure guidance** via **P-0512**,
- and **runtime failure handoff** via **P-0513**.

But it still lacked a good answer to:

- “Once a team already depends on this crate, what exactly does the crate hand them when they try to upgrade?”

That left the archive with better answers for **adoption**, **support claims**, and **failure recovery** than for **ongoing release-to-release maintenance**.

### 2. Official Rust guidance now names crate supportiveness while docs/code remain the main learning surfaces

The December 2025 vision-doc post says Rust should “double down on extensibility” and specifically calls for **better diagnostics and guidance from crates**.
The 2025 survey says online documentation is still the preferred canonical reference, followed by studying the code itself.

That combination makes crate-authored upgrade support a first-class design problem rather than a docs afterthought.

### 3. The Rust project is improving compatibility evidence, but not yet the downstream migration artifact

The 2025H2 project goal for `cargo-semver-checks` says accidental SemVer violations are common enough that the tool is on a path toward the `cargo publish` workflow.
That is a huge improvement for judging **whether** a release is compatible.

But it still does **not** tell a downstream user:

- which hazards matter for the upgrade they are attempting,
- which feature/runtime/config lanes were checked,
- whether any edits are machine-applicable,
- and what the smallest working after-upgrade recipe looks like.

### 4. Rust already proved suggestion-backed migrations can work

`cargo fix`, the edition-migration flow, `rustc` JSON diagnostics, and `rustfix` together show a concrete upgrade pattern that Rust already knows how to do:

- capture structured findings,
- apply machine-applicable suggestions when possible,
- re-check,
- and keep manual work explicit.

What is still missing is the maintainer-facing crate that packages those ideas for ordinary crate upgrades.

### 5. Existing release tools solve adjacent maintainer problems, not this receiver-facing one

`release-plz` and `cargo-release` help with version bumps, changelogs, tags, and publishing.
That is useful, but it is a different lane from:

- stable upgrade hazards,
- machine-fix receipts,
- checked before/after recipes,
- and explicit manual-review boundaries.

## Current judgment

The worthy crate here is not:

- another semver checker,
- another public-API report,
- another release bot,
- another changelog generator,
- or a universal codemod framework.

The worthy crate is the boring release-to-release supportiveness layer that can hand other people:

1. one **upgrade pack**,
2. one **upgrade-hazards report**,
3. one **fixup-hints receipt**,
4. one **migration-recipe manifest**,
5. one **upgrade-check report**,
6. one **upgrade diff**,
7. and one explicit **manual-review boundary** when the migration cannot be honestly automated.
