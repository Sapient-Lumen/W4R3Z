# Entry 141 — linker-lane support is its own missing layer

This pass **did** add a new top-level proposal.

The archive already knew a lot about toolchains, native dependencies, Cargo performance, and cross-target support.
What it did **not** yet isolate cleanly was the linking layer itself.

## Main judgment

The missing value is not another linker wrapper.
It is the **linker-lane contract and diagnosis layer** above today’s wrappers and flags.

That means the right contribution here is:

- not another linker implementation,
- not another “zero setup” cross tool,
- not a benchmark suite,
- but a conservative crate that can capture one intended or observed linker lane, classify failures and drift, and emit a portable review bundle.

## New planning stance

Read this frontier as a stack:

1. target/toolchain support posture,
2. native dependency and SDK probing,
3. linker lane selection/configuration substrate,
4. observed link-attempt receipts,
5. diagnosis and lane-switch review bundles.

**P-0504** occupies layers 4–5.
It should import from lower layers, not absorb them.

## Archive-level lesson

Once an ecosystem has multiple credible lane-specific tools, the next missing crate may be the one that makes those lanes **comparable and reviewable**.

Future passes should resist the temptation to keep proposing another wrapper when the sharper need is one compact, boring artifact for linker-lane intent, observations, failures, and diffs.
