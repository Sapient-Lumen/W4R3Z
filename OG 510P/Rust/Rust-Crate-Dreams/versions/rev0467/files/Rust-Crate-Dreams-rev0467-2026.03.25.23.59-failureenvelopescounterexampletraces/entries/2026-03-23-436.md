# Entry 436 — deepen the repo around the contribution bar, docs.rs issue-flow planning, and build-dir transition dual-support

This pass again chose **deepen** over **append**.

The archive already contains more candidate crates than one team can reasonably digest.
What it needed next was a sharper answer to three questions:

1. what should count as a genuinely **worthy / epic** crate contribution,
2. which currently live ecosystem seams deserve the next concrete product-planning passes,
3. and how should the archive itself resist drift, repetition, and vague rewording on future LLM refreshes.

## Main judgment

The archive should now treat the following as the **practical implementation queue** for the next repo-building passes:

1. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
2. **P-0486 Debuggability Support Contract Kit**
3. **P-0472 Docs.rs Build Parity & Evidence Kit**
4. **P-0489 Cargo Build-Dir Consumer Transition Kit**
5. **P-0535 Dependency Lifecycle Transition Kit**
6. **P-0484 Toolchain & Target Support Contract Kit**
7. **P-0536 Crate Knowledge Pack Kit**
8. **P-0537 Compile Iteration Feedback Kit**

This is not a claim that the older control-plane frontier was wrong.
It is a claim that current official Rust signals now make **docs/build/support-truth** lanes unusually actionable:

- the 2025 State of Rust survey keeps compile times, debugging, and dependency/version pressure live,
- the Rust debugging survey says debugging quality still varies a lot across debugger/back-end/platform combinations,
- docs.rs now publishes its sandbox limits and explicitly recommends `cargo docs-rs` in CI while warning it is not a perfect replica,
- docs.rs metadata and rustdoc JSON surfaces are real enough that a serious parity/evidence crate can now be narrow and practical,
- Cargo is actively asking users to rehearse `-Zbuild-dir-new-layout` and report which tools still depend on internals,
- Cargo build-analysis work and relink/build-layout work show upstream is creating substrate but not the receiver-facing bundle layer,
- crates.io now exposes more support/security/trust context without solving crate choice or migration planning,
- and safety-critical writeups keep asking for stronger MSRV, target, dependency, and boundary evidence.

That combination means the strongest next contribution to the repo is not “invent ten more sectors.”
It is to make the top horizontal lanes look more like **things a maintainer could actually build in `0.1`**.

## New portfolio stance

### 1. “Epic crate” now has a stricter bar

A worthy contribution is now presumed to be a crate that gives **other people** one or more of the following:

- a portable review bundle,
- a decision pack,
- a capability/support contract,
- a migration receipt,
- a target / toolchain / docs / debug evidence artifact,
- or a small stable substrate that can be checked, diffed, and handed off.

That means the archive should resist over-promoting:

- wrappers with thin behavioral novelty,
- parser/client bridges without receiver-facing workflow value,
- generic “smart assistant” shells,
- scoreboards without an exported evidence seam,
- and sector-specific ideas that are really downstream consequences of a sharper horizontal gap.

### 2. Docs.rs parity deserves promotion into the near-term build queue

The docs.rs substrate is now concrete enough that the missing work is no longer “some docs helper.”
The missing work is an **issue/review/evidence workflow** that records:

- effective docs.rs metadata,
- fidelity class,
- hosted-vs-local drift,
- target/feature/rustdoc assumptions,
- and the smallest honest issue bundle a maintainer can attach upstream.

### 3. Build-dir transition deserves more than generic migration advice

Cargo’s March 2026 testing call makes the lane much sharper.
The missing receiver-facing crate now needs to track:

- what the consumer was really trying to accomplish,
- whether there is a stable replacement surface,
- what Cargo/toolchain/layout window that replacement really covers,
- and whether the right operational answer is “migrate now”, “support both layouts”, or “blocked on upstream”.

### 4. The archive itself now needs a stricter refresh loop

Future refreshes should not silently repeat broad summaries.
They should:

1. inspect the latest entry,
2. state whether the pass is **deepen**, **re-rank**, or **append**,
3. name the exact lanes being changed,
4. record which files were added/updated,
5. preserve what did **not** change,
6. and update memory/hygiene notes whenever the working rules changed.

## Why this matters for missing-crate planning

The repo is strongest when it treats a proposed crate less like a pitch and more like a **product with boundaries**.
For each serious proposal, the archive should now keep asking:

- what artifact does this crate export,
- who can inspect it later,
- what workflows does it replace or simplify,
- what claims does it refuse to make,
- what supporting upstream substrate does it import rather than reimplement,
- what does the first lovable `0.1` actually ship,
- and what would make the crate boring, trusted, and cheap to keep alive.

That is the standard this pass applied to docs.rs parity and build-dir transition, and it should become the default standard for future high-salience lanes.
