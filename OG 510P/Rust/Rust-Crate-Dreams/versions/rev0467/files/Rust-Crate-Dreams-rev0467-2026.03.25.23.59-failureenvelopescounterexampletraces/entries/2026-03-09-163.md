# Entry 163 — verification campaigns become policy-first and lane-honest

This pass again chose **not** to add another narrow proposal.

The better move was to make **P-0485 Verification Campaign Workbench Kit** much more handoff-ready.
The archive already knew that Rust has several serious verification tools.
What it still under-specified was the missing shared layer above them.

## Main judgment

The sharper missing crate here is not “a dashboard for proof tools”.
It is a boring campaign workbench that can answer:

> what obligations were checked, by which lane, under which trust assumptions, under which green-policy, and how did that posture drift?

That sounds close to the earlier proposal, but the missing details mattered.
The old version still behaved too much like a good tool list.
The revised version is much more explicit about:

1. **lane semantics**,
2. **campaign policy**, and
3. **comparability**.

## Why these changes were the right ones

### 1. P-0485 needed a first-class Verus lane

The archive previously treated Rust verification as mostly Miri/Kani/Creusot/Prusti/Flux-shaped.
That was already incomplete.

A more current reading needs **Verus** as a first-class lane, because the Rust verification frontier is no longer just dynamic checking plus one bounded prover plus one deductive tool.
That matters strategically because the sharper missing crate is now even more clearly the **campaign layer above multiple semantically different lanes**.

### 2. The proposal needed to separate raw results from green-policy

A campaign is not useful enough if it only says:

- here are some proof receipts,
- here are some dynamic findings,
- and here are some trusted functions.

It also needs to say:

- which obligations are blocking,
- what evidence classes count for each,
- whether a new trust item blocks sign-off,
- and why the campaign is green, yellow, or red.

That is now explicit in the proposal and in the new fixture schemas.

### 3. The repo needed a memory aid for comparability

The new meta note records another reusable rule:

- tool-local receipt,
- campaign obligation/trust model,
- policy gate,
- shared bundle substrate,
- optional assurance import.

That should reduce future drift toward vague “proof dashboard” language or toward dishonest diffs between materially different campaigns.

### 4. P-0485 needed fixture-first planning

The proposal now has a much better answer to:

> what concrete files should another maintainer or reviewer receive?

The new fixture pack gives it:

- a campaign manifest,
- obligation records,
- a trust ledger,
- lane results,
- a policy-evaluation report,
- and a comparability-aware diff report.

That is a lot closer to something another builder could actually start implementing.

## New planning stance

For the next few passes, the archive should prefer:

- treating **verification campaigns as a shared substrate** above existing tools,
- freezing lane-semantics and policy vocabulary before widening adapter count too much,
- reusing **P-0256** for bundle semantics,
- and letting **P-0503** consume campaign bundles conservatively rather than flattening them.

It should **not** drift into:

- another “one tool to rule them all” verifier idea,
- a dashboard that cannot be handed to another person,
- or a fake diff that ignores trust-surface or policy-version drift.
