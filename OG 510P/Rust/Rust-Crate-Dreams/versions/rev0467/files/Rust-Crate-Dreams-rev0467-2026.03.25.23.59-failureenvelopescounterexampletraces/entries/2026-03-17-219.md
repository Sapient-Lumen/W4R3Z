# Entry 219 — crate observability-surface planning sharpened into an implementation-ready v0.1 shape

This pass did **not** promote a new lane.
It sharpened **P-0518 Crate Observability Surface Pack Kit** into a more buildable shape.

## Why this moved now

The archive had already promoted crate observability surfaces as one of the stronger missing receiver-facing support lanes.
The sharper move now was **not** to add another adjacent tracing/exporter/dashboard idea, but to make P-0518 believable enough that someone could start `0.1` work this week.

Several current Rust and ecosystem signals make that move unusually well-timed:

1. **Supportive crate interfaces are now a live strategic theme.**
   The December 2025 Rust vision-doc work explicitly argues that crates still lack good tools for supportive interfaces.

2. **Docs and code are still the main learning surfaces.**
   The 2025 State of Rust survey says online documentation remains the preferred canonical reference, followed by studying the code itself.
   That means observability support should not stay trapped in README fragments, subscriber snippets, and tribal ops knowledge.

3. **The substrate is real, but fragmented.**
   `tracing`, `tracing-subscriber`, `EnvFilter`, tokio-console / `console-subscriber`, `tracing-opentelemetry`, and OpenTelemetry semantic conventions/schemas already cover big slices of the problem.
   But they still do **not** add up to one crate-authored contract for which signals are official, what it takes to see them, and which naming/sensitivity claims are stable.

## Main planning move

This pass made three previously fuzzy things explicit:

- **signal stability policy** — is a signal `stable_query_surface`, only `supported_but_evolving`, strictly `debug_only`, or still `manual_review_required`?
- **activation recipe truth** — does a signal require a feature flag, `RUST_LOG` / `EnvFilter` directive, a named layer, runtime support, or an exporter bridge before a downstream user can actually see it?
- **schema / convention posture** — does the signal family follow OpenTelemetry semantic conventions under a specific schema URL, mix custom extensions, or remain crate-local?

Those are the pieces that make the difference between “this crate emits telemetry” and “this crate publishes a reviewable observability support contract”.

## Main judgment after the pass

A worthy `0.1` here is a **small cargo subcommand plus library** centered on:

- `init`
- `capture`
- `check`
- `doctor`
- `summary`
- `diff`
- `pack`

with explicit artifacts for:

- `signal-stability.policy`
- `activation-recipe.receipt`
- `schema-convention.profile`

The key repo-memory lesson is that future passes should not mistake any of the following for proof that a *new* crate lane is needed:

- missing stability-class vocabulary,
- missing activation-recipe vocabulary,
- missing schema-URL or semconv posture,
- missing import adapters for `EnvFilter`, tokio-console, or `tracing-opentelemetry`,
- or missing doctor warnings around overclaimed query stability.

The sharper move, for now, is to keep making **P-0518** more buildable and more falsifiable.
