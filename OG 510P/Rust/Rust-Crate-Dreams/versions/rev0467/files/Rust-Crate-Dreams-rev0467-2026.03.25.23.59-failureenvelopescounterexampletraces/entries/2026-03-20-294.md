# Entry 294 — open-table-format-kit sharpened around table-surface truth, capability profiles, and integration coupling

This pass returned to **P-0028 open-table-format-kit** because the archive had long recognized the strategic importance of a common Rust lakehouse layer, but the original proposal still left one dangerous blur available:

> a crate could say it “supports Iceberg, Delta, and Hudi” while saying almost nothing about **what table surface is actually exposed**, whether that surface is **live or pinned**, which operations are really wired, or how tightly the integration is coupled to specific DataFusion / binding paths.

## What moved this time

Several current ecosystem signals make that blur much harder to excuse:

- `iceberg_datafusion` now documents **two distinct provider shapes**: a catalog-backed provider with automatic metadata refresh and a static provider for a specific snapshot;
- `iceberg-rust` 0.9.0 shipped large integration changes, including storage refactors, DataFusion 52 upgrades, and a higher MSRV;
- `deltalake` now exposes a broad public support matrix across storage backends and operations such as `merge`, `update`, `optimize`, and constraints;
- `hudi-rs` documents a meaningfully different public surface centered on snapshot, time-travel, and incremental reads plus DataFusion integration;
- DataFusion’s own maintainers say third-party table-provider integrations are painful when Rust applications must match the **exact DataFusion version** across `delta-rs`, `iceberg`, and other providers;
- DataFusion Python’s foreign-table-provider FFI helps in one coupling lane, while real issues such as the March 2026 Iceberg GCS Python-binding gap show that underlying storage support and binding wiring can still diverge.

That combination means the missing crate is no longer best described as “one universal trait for open table formats.”
It is better described as a **reviewable table-surface / capability / coupling kit** above today’s serious but still asymmetric format implementations.

## Main planning move

This pass promoted three first-class review objects for **P-0028**:

1. **table-surface truth** — whether a subject is catalog-backed with live refresh, a static snapshot, a time-travel pin, an incremental window, or some other narrower surface,
2. **capability-profile truth** — which reads, writes, maintenance actions, and engine registrations are honestly supported for the exact adapter/binding in view,
3. **integration-coupling truth** — whether the subject is native-only, exact-version-coupled to DataFusion, FFI-exposed, wrapped through another language binding, or otherwise carrying compatibility debt.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say that a format has a Rust crate,
- a query engine can truthfully say it can register a table provider,
- a binding can truthfully say a storage backend exists somewhere below it,
- and a downstream team can still be unable to answer whether they are looking at a **live catalog table**, a **pinned snapshot**, a **read-only adapter**, a **write-capable surface**, or a **version-coupled integration seam** that will break the moment one dependency upgrades first.

That is not a wording nit.
It is the difference between “Rust has lakehouse crates now” and “another team can review what they are actually depending on.”

## Main judgment after the pass

A worthy open-table-format contribution for Rust should now provide more than common read traits and more than another adapter demo.
It should provide:

- one explicit **table-surface receipt**,
- one explicit **capability-profile report**,
- one explicit **integration-coupling receipt**,
- and one compact way to diff those artifacts across format adapters, bindings, and release upgrades.

That is a better answer to the current ecosystem than either:

- “just wrap all three crates behind one trait,”
- “just expose TableProviders,”
- or “just list supported operations in docs and hope the rest is obvious.”
