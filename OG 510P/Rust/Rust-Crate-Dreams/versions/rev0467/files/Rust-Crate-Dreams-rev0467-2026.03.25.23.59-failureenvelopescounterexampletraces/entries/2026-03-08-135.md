# Entry 135 — Cargo build-dir consumer transition implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded **P-0489 Cargo Build-Dir Consumer Transition Kit** from a good abstract idea into a more implementation-ready crate plan.

## Main judgment

Cargo build-dir transition is now a cleaner frontier than it was when this proposal first landed.

The current upstream story already has:

- stable `build.build-dir`,
- build-cache docs that explicitly say intermediate layout is internal,
- release notes warning that tools relying on build-dir internals may break and should proactively test,
- project-goal docs that explicitly call for a transition path for tooling,
- Cargo JSON output for build-script execution and produced artifacts,
- and narrower safer surfaces like `OUT_DIR` and `CARGO_BIN_EXE_<name>`.

So the missing value is not “prove Cargo internals may change.”
It is the **receiver-facing transition bundle** above those surfaces.

## New planning stance

**P-0489** should now be read as a crate that hands other people:

- one consumer inventory,
- one layout snapshot,
- one consumer audit,
- one path contract,
- one adapter plan,
- one transition receipt,
- optionally one diff,
- and one compact notes file.

That is a much sharper contract than “Cargo output migration tooling.”

## Archive-level lesson

When official docs get clearer, a mature repo often benefits more from **freezing a smaller artifact contract** than from adding more idea count.
A worthy crate can get stronger by becoming more boring, more conservative, and easier to attach to a real migration review.
