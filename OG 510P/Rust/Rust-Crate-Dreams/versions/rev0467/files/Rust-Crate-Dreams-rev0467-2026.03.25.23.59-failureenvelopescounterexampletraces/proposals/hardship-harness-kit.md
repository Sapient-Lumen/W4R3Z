# Problem

Distributed systems testing in Rust still tends to be:
- slow (needs real deployments),
- flaky (time/network nondeterminism),
- and hard to *share* (bugs aren’t reproducible outside the author’s machine).

Tokio’s **turmoil** demonstrates a powerful direction: deterministic multi-host execution in a single thread with controlled hardship (network perturbations). citeturn1search2turn1search6  
But most teams don’t adopt it because the missing “product” is not just a crate—it’s a **workflow**: profiles, artifact capture, and a way to integrate with various async stacks and protocols.

# What it provides

1. **A standard deterministic test harness contract**
   - hosts, simulated time, seeded RNG, network links (drop/hold/delay), optional filesystem hardship
   - “scenario DSL” that can be generated by property tests

2. **Artifact-first failure bundles**
   - `*.hardship.zip`: scenario seed + event log + network schedule + minimal reproducer + optional packet transcript
   - `hardship replay`: deterministic replay command; fails identically if the system is deterministic under the harness

3. **Conformance profiles**
   - “TCP-ish”, “HTTP-ish”, “gossip-ish” profiles (latency distributions, partitions, clock skew)
   - a published “hardship matrix” so results are comparable across projects

4. **Interop adapters**
   - a thin compatibility layer so you can run:
     - Tokio-based systems directly (turmoil backend),
     - plus an adapter story for non-Tokio runtimes where possible (even if only partial at first)

# Users & user stories

- **Maintainer of a consensus or replication lib:** “I want a deterministic harness with published scenarios so regressions are caught early.”
- **App developer:** “I want to reproduce a production deadlock as a single zip bundle.”
- **Researcher:** “I need comparable benchmark/hardship suites.”

# Prior art (and why it’s insufficient)

- Turmoil provides deterministic multi-host execution and hardship controls, but teams still need repeatable scenario bundles, replay tooling, and standardized profiles to make it a default workflow. citeturn1search10turn1search2turn1search6

# Design goals

- **Deterministic by construction:** the harness owns time and the network schedule.
- **Minimal reproduction:** always output a replayable bundle on failure.
- **Comparability:** publish profiles and scenario sets that multiple projects can reuse.
- **Incremental adoption:** allow embedding into existing test harnesses.

# Non-goals

- Replacing full integration tests; this complements them.
- Perfect runtime agnosticism on day 1.

# Architecture & API sketch

Crates:
- `hardship-core`: scenario types, event log, bundle format
- `hardship-runner`: CLI + replay
- `hardship-backend-turmoil`: backend built on turmoil
- `hardship-profiles`: curated profiles + scenario corpora

API sketch:
- `Scenario { seed, topology, steps }`
- `Harness::run(scenario, test_fn) -> RunReport`
- `RunReport` includes deterministic event log and minimal reproduction metadata

# Security / safety model

- Bundles are untrusted: validate sizes and decompress limits.
- Optional redaction for payload logs (PII).

# Maintenance & governance plan

- Keep core bundle schema versioned and tiny.
- Treat profiles/corpora like “standards”: reviewed with changelog + compatibility notes.

# Milestones

- **MVP:** turmoil backend + bundle schema + replay CLI.
- **v0.5:** curated hardship profiles + minimization (shrink scenario steps).
- **v1:** publish “hardship matrix” and a starter corpus adopted by 3+ projects.

# Open questions

- Best common abstraction for packet-level vs message-level simulation.
- How much filesystem hardship is necessary vs optional.
