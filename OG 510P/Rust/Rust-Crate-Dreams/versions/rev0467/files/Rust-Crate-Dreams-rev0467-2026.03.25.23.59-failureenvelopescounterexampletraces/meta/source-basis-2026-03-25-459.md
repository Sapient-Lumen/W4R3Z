# Source basis note — 2026-03-25 (459)

This pass was a **suite-topology and package-boundary** pass.
It did not aim to prove that brand-new top-ranked lanes exist.
It aimed to check whether current Rust ecosystem signals justify planning the current leaders as small crate families instead of single-package blobs.

## Facts imported directly

1. Rust users still report substantial pain around resource usage, debugging, and crate-choice/productivity questions.
2. The March 2026 challenges post still highlights embedded, GUI, and safety-critical realities where support and tooling boundaries matter a lot.
3. crates.io now exposes stronger trust/publication surfaces including security-tab data, Trusted Publishing modes, SLOC, and `pubtime`.
4. crates.io malware communication policy is now more advisory-centered and less blog-post-centered.
5. Cargo’s March 2026 advisory explicitly distinguishes crates.io from alternate-registry protection stories.
6. docs.rs exposes configurable build metadata, hosted rustdoc JSON, downloadable archives, target/default-target behavior, and hosted build caveats.
7. The project-goals system now has a 2026 annual slate and still includes work around open namespaces, public/private dependencies, build analysis, and libtest JSON.
8. Web, geospatial, local-first, and GUI all show meaningful ecosystem substrate already, even though they remain uneven.

## Main inferences from those facts

1. The archive still does **not** need a fresh umbrella frontier reset.
2. Current official substrate increasingly rewards crates that can export **stable machine-readable packets** and isolate **fast-moving adapters**.
3. Because different receivers need different surfaces, many worthy contributions are more honestly planned as **small crate families**.
4. Package seams should track receiver/stability/substrate boundaries more than implementation convenience.

## Open questions kept open

- Which shared packet/schema concepts should be standardized across top lanes versus left lane-specific?
- When should a suite gain a dedicated adapter crate rather than a feature-flagged module?
- Does `suite-topologies.json` provide enough machine-readable planning memory, or should the archive later track per-lane release-stage manifests?
