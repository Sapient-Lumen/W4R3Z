# Source basis note — 2026-03-25 (entry 463)

This pass adds a **review-packet / signoff-rail / maintenance-memory** layer.
It is based primarily on current official Rust project sources and a few highly relevant official docs.rs pages.

## Official sources used most heavily

### Ecosystem pain / maintenance / receiver reality
- 2025 State of Rust Survey results — continued signals around resource usage, debugging pain, and documentation as the canonical reference.
- What is maintenance, anyway? — strong argument that maintenance and reviewer-enablement are multiplicative and often invisible.
- What we heard about Rust’s challenges — cross-domain signal that embedded, safety-critical, GUI, and debugging pain remain real.
- Rust debugging survey 2026 — concrete matrix burden for debugger support.
- What does it take to ship Rust in safety-critical? — strong evidence that higher-assurance work needs explicit evidence, interop clarity, upgrade explainability, and bounded dependency posture.

### Machine-usable substrate
- crates.io development update — Trusted Publishing only mode, blocked risky triggers, SLOC, and `pubtime` surfaces.
- docs.rs metadata / builds / download / rustdoc JSON — clear evidence that docs/build/target/API surfaces are now importable in machine form.
- cargo-semver-checks goal — explicit model where a check may block by default but still allow an override path.
- public/private dependencies goal — clearer future substrate for API boundary reasoning.
- open namespaces goal — more multi-team coordination and ownership semantics in package families.
- cargo build analysis goal — useful future substrate, but still prototype-grade and explicitly unstable.
- sandboxed build scripts goal — more pressure toward reviewable execution and bounded permissions.
- StableMIR goal — evidence that more durable tooling interfaces are becoming realistic.

## Main inference this pass

The archive already had enough support for evidence bundles, claim tiers, interchange profiles, and policy packs.
What the sources additionally support is a stronger conclusion:

**a worthy missing Rust crate often needs to provide a durable human review object, not just more machine output.**

That inference is not stated verbatim by any single source.
It arises from combining:
- the maintenance post’s emphasis on invisible reviewer/maintainer work,
- the safety-critical post’s emphasis on evidence, upgrades, and interop over time,
- the semver-checks goal’s explicit override path,
- the docs.rs/crates.io substrate becoming increasingly machine-usable,
- and build-analysis still being unstable enough that reviewed packets should sit above raw prototype data.

## Confidence and limits

High confidence:
- a review/handoff layer is now justified as repo doctrine;
- the leading practical front still favors receiver-facing control-plane crates;
- the decision front door remains the best first place to define shared review packets.

Medium confidence:
- the exact signoff-state vocabulary may still change;
- whether `pathfinder-review` should be a separate package or just a CLI surface may change;
- later lanes may want narrower packet variants than the shared default.

Low confidence / open questions:
- whether the archive should later add signed attestations instead of plain signoff ledgers,
- how much organization-local workflow semantics should live in shared review packets,
- and whether review-packets.json is enough machine memory or should later be joined by reusable approval fixtures.
