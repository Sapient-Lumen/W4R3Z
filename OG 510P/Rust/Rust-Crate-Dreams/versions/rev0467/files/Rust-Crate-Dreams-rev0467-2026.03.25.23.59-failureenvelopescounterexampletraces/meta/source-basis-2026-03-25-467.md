# Source basis note — 2026-03-25 (entry 467)

This pass adds a **falsification / failure-envelope / counterexample-trace** layer.
It is based primarily on current official Rust project sources and official docs.rs pages.

## Official sources used most heavily

### Ecosystem pain / review burden / negative-case pressure
- 2025 State of Rust Survey results — continued signals around debugging, resource usage, and crate-selection friction.
- Rust debugging survey 2026 — explicit reminder that support claims vary across debuggers, operating systems, versions, and async scenarios.
- What is maintenance, anyway? — strong argument that invisible review and enablement work is real labor worth reducing.
- What does it take to ship Rust in safety-critical? — strong evidence that higher-assurance adoption depends on explicit boundaries, upgrade explainability, and credible failure handling.

### Machine-usable substrate and failure-signal surfaces
- crates.io development update — stronger trust surfaces (`Security`, Trusted Publishing, SLOC, `pubtime`) make downgrade and route-specific failure packets more actionable.
- crates.io malicious-crate policy update — advisory-first posture reinforces the need for durable reviewable failure packets rather than memory by blog post.
- Cargo security advisory — crates.io posture and alternate-registry posture can diverge, so inherited trust can be refuted by route.
- docs.rs changed default targets — concrete example where the support-relevant basis can shift even when a crate’s source is unchanged.
- docs.rs metadata / builds / download / rustdoc JSON — clear evidence that docs/build/API/target surfaces are importable and inspectable in machine form, and that hosted builds can diverge from local expectations.
- sandboxed build scripts goal — clear reminder that capability boundaries and determinism matter, so failure envelopes should be able to say when a script’s assumptions exceed the intended execution model.
- cargo-semver-checks goal — explicit model where checks can fail and still expose a visible override path.
- cargo build analysis goal — stronger basis for causal failure explanations and smallest honest replay slices.
- build-dir-layout goal — concrete motivation for slicing build-state problems into smaller units rather than flattening them.
- StableMIR goal and target-tier policy — stronger case that analysis tools can stand on durable interfaces while still representing support ceilings and degraded states honestly.

## Main inference this pass

The archive already had enough support for conformance kits, policy packs, review packets, renewal programs, delta bundles, and assurance cases.
What the sources additionally support is a stronger conclusion:

**a worthy missing Rust crate often needs to export a failure envelope beside its positive case, so another team can see exactly what disproved a claim, what smaller claim still survives, and what repair slice is honest.**

That inference is not stated verbatim by any single source.
It arises from combining:
- continued ecosystem pain around choosing and trusting crates,
- debugger and target support being matrix- and profile-sensitive,
- hosted-vs-local build/documentation mismatches being normal enough to document explicitly,
- maintainer/reviewer labor being expensive and multiplicative,
- and the growing availability of machine-usable docs/build/API/trust substrate.

## Confidence and limits

High confidence:
- a falsification layer is now justified as repo doctrine;
- the broad frontier still favors receiver-facing control-plane crates;
- the support-envelope ring is the best first place to define shared counterexample and degraded-claim semantics;
- the decision front door is the best second place to make those failures human-usable.

Medium confidence:
- the exact degraded-claim vocabulary will vary by lane;
- debugger lanes may need tuple-specific failure semantics that are not ideal for simpler support rings;
- route/advisory refutation bridges may overlap with delta-program semantics more than currently planned.

Low confidence / open questions:
- whether `withdrawn-guarantee.md` should later become machine-readable,
- how much repair-hint vocabulary should be standardized across lanes,
- and whether later passes should add reusable counterexample fixtures beside `failure-envelopes.json`.
