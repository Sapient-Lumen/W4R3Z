# Source basis note — 2026-03-25 (entry 465)

This pass adds a **delta-program / change-class / rerun-slice** layer.
It is based primarily on current official Rust project sources and official docs.rs pages.

## Official sources used most heavily

### Ecosystem pain / maintenance / receiver reality
- 2025 State of Rust Survey results — continued signals around crate choice, debugging, and resource usage.
- What is maintenance, anyway? — strong argument that recurring reviewer and maintainer labor is real work that should be reduced, not hidden.
- What does it take to ship Rust in safety-critical? — strong evidence that upgrades, replacement paths, interop, and change explanation matter as much as first approval.

### Machine-usable substrate and change-semantics signals
- crates.io development update — stronger trust surfaces make change review more actionable.
- Cargo security advisory — alternate registries and older Cargo versions can diverge, so carry-forward cannot be assumed from crates.io posture alone.
- build-dir layout v2 call for testing — explicit reminder that many tools depend on internal build-dir details and need a way to explain partial invalidation when substrate shifts.
- docs.rs changed default targets — concrete example where support-relevant basis changes without the crate’s source code necessarily changing.
- docs.rs metadata / builds / download / rustdoc JSON — clear evidence that docs/build/target/API surfaces are importable and diffable in machine form.
- relink-don't-rebuild goal — explicit upstream effort to avoid blast radius when public interface did not change.
- cargo build analysis goal — explicit upstream effort to explain why rebuilds happened.
- cargo-semver-checks goal — explicit model where a change can trigger a default check and still allow a visible override path.
- public/private dependencies goal — stronger future substrate for distinguishing internal change from public-boundary change.
- StableMIR goal — stronger case that more durable compiler-facing analysis surfaces can support change explanation.
- sandboxed build scripts goal — stronger pressure for deterministic, reviewable change handling rather than opaque side effects.

## Main inference this pass

The archive already had enough support for review packets, renewal programs, and stewardship loops.
What the sources additionally support is a stronger conclusion:

**a worthy missing Rust crate often needs to provide a delta contract above those layers, so another team can tell what changed, what still carries forward, and what exact slice must be replayed.**

That inference is not stated verbatim by any single source.
It arises from combining:
- maintenance work being real and expensive,
- safety-critical and long-lived adoption needing change explanations,
- upstream work to avoid unnecessary rebuild blast radius,
- upstream work to explain why rebuilds happened,
- docs.rs and Cargo substrate shifts that selectively invalidate old assumptions,
- and the growing availability of machine-usable docs/build/API data.

## Confidence and limits

High confidence:
- a delta/carry-forward layer is now justified as repo doctrine;
- the broad frontier still favors receiver-facing control-plane crates;
- the continuity ring is the best first place to define shared change classes;
- the decision front door remains the best place to consume those classes for actual downstream use.

Medium confidence:
- the exact change-class vocabulary may still change;
- some lanes may need fewer or more classes than the shared default;
- the boundary between `policy-only` and `unknown-manual-review` may need refinement later.

Low confidence / open questions:
- whether `confidence-reset.json` should later be merged with review or renewal state,
- how much of supersession-diff semantics should be standardized across all top lanes,
- and whether later passes should add reusable `delta-corpus` fixtures beside `delta-programs.json`.
