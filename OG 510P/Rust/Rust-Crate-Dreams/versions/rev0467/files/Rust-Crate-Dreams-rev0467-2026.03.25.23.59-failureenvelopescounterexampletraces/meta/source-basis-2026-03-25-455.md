# Source basis note — 2026-03-25 (entry 455)

## Scope of this pass

This pass did not try to find a brand-new domain frontier.
It asked whether the top archive lanes needed a better theory of what they should provide after initial adoption.

## Facts imported directly from sources

- The 2025 State of Rust survey still reports challenges around resource usage, debugging, async, and ecosystem choice.
- The March 2026 challenges post repeats crate-choice, async, compile-time, embedded, safety-critical, and GUI pain as major themes.
- The debugging survey explicitly describes debugger/version/OS variance, async debugging, visualizers, and expression evaluation as key gaps.
- crates.io now exposes Security-tab data, Trusted Publishing enhancements, SLOC, and `pubtime`.
- the February 2026 malicious-crate policy update makes RustSec advisories the default notification path for most malicious-crate removals.
- the March 2026 Cargo advisory distinguishes crates.io protection from alternate-registry exposure.
- docs.rs exposes build metadata, download archives, and rustdoc JSON with important caveats.
- the October 2025 docs.rs target update changed the default target set.
- Cargo/report and related goal work continues around build analysis, semver checks, libtest JSON, and other machine-usable surfaces.
- the 2026 goal slate includes build-std, cross-workspace cache, verifiable mirroring, public/private dependencies, sanitizers, Cargo SBOM precursor, and Wasm Components.
- safety-critical reporting continues to emphasize evidence, tooling maturity, and ecosystem thinness at higher criticality levels.
- community hubs across web, GUI, game, IDE, geospatial, and local-first work show active sectors rather than empty ecosystems.

## Main inferences made in this pass

1. The archive’s strongest missing crates are still mostly horizontal control-plane and evidence/contract kits rather than fresh giant sector umbrellas.
2. Because more ecosystem substrate is machine-usable and more post-adoption risk is visible, the sharper missing layer is now **continuity**.
3. That makes **P-0535 + P-0496 + P-0431 (+ P-0125 where relevant)** a stronger practical ring than the archive had been naming explicitly.
4. Debug/support work remains highly salient, but continuity should now be planned more explicitly before widening support claims.

## Open questions

- How much of the continuity ring should be one crate family versus several narrowly joined crates?
- Should SBOM precursor carry-forward remain a supporting lane or move into the continuity core?
- How much alternate-registry and mirror behavior can be described portably without overfitting to specific enterprise setups?
- Which parts of public-boundary drift should depend on witness programs versus rustdoc JSON alone?

## Claim-level changes in this pass

- No major salience reset.
- One practical upgrade: the archive now explicitly recognizes a **continuity ring**.
- One hygiene upgrade: the archive now uses a clearer **claim-upgrade discipline**.
