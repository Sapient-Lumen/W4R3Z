# Source basis note — 2026-03-25 (entry 457)

## Scope of this pass

This pass did not try to discover a brand-new top-ranked fantasy crate.
It asked a more practical question:

**What should a worthy crate provide other people as a bounded product offer, and what broad domain scan still justifies keeping the control-plane frontier in front?**

## Facts imported directly from sources

- The 2025 State of Rust survey still reports broad productivity issues and keeps online documentation important as the canonical reference.
- The March 2026 Rust challenges post says users still struggle to know which crates they need, which crates they can trust, and notes that some industries remain immature for Rust support.
- That same post explicitly calls out embedded resource constraints and says safety-critical developers still lack mature certification tooling.
- The debugging survey says debugging quality varies substantially across debuggers, operating systems, versions, and async scenarios.
- crates.io now supports Trusted Publishing with GitLab.com, Trusted Publishing-only mode, blocked unsafe GitHub triggers, SLOC display, and `pubtime` in the index.
- docs.rs builds docs in a nightly sandbox, exposes configurable build metadata, hosts rustdoc JSON with `format_version` caveats, and stores downloadable ZIP archives with offline caveats.
- Current project-goals work includes build analysis, build-dir rework, public/private dependency support, semver-check improvements for cargo integration, verifiable mirroring work, StableMIR publication, and open namespace support.
- The 2026 goals slate has 66 annual goals.
- Community ecosystem hubs still show active centers of gravity in web, GUI, game development, IDE tooling, geospatial, and local-first software.

## Main inferences made in this pass

1. The strongest missing value is still mostly a cross-cutting receiver-facing control plane, not a fresh umbrella framework for each domain.
2. The sharper missing layer after operating models is a **promise bundle** or **support envelope**: the thing another team actually receives.
3. Broad domain activity argues for comparison, evidence, and continuity crates more than it argues for a new one-true sector framework.
4. The archive itself now benefits from a machine-readable navigation spine (`llms.txt`) because the repo is large enough that later passes could otherwise lose the newest memory layer.

## Open questions

- How much of the promise bundle should be standardized across top lanes versus left lane-specific?
- Should the first reusable packet family center on `P-0509 + P-0536`, or should docs/target support packets be standardized first?
- How much service-level vocabulary should be formalized before it becomes burdensome?
- Should the repo add a second machine-facing navigation file (`AGENTS.md` or similar), or is `llms.txt` sufficient for now?

## Claim-level changes in this pass

- No broad frontier reset.
- One practical clarification: a worthy crate is now expected to provide a **promise bundle / support envelope** to downstream users.
- One archive-hygiene upgrade: the repo now includes an explicit machine-facing navigation file.
