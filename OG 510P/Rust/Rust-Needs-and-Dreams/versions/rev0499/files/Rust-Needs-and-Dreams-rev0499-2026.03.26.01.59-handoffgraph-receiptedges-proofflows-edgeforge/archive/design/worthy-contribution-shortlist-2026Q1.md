# Design: Worthy contribution shortlist (2026 Q1)

## Goal
Turn the archive's broader territory map into an **execution-oriented shortlist**.
This note exists for the narrower question:

> if a serious Rust team, lab, or funder can only build **one** or **a few** ecosystem contributions, what should they actually build, and what should those contributions look like in practice?

This is deliberately different from:
- the archive's **broad ladder**;
- the archive's **active specialist frontier**;
- the archive's **next maintained public-lane candidate**;
- or the archive's **meta-hygiene** work.

A good portfolio answer should keep those layers separate instead of pretending one vivid frontier or one recent source settled everything.

## Ranking discipline
When someone asks what a worthy or even epic contribution should be, answer in five layers instead of one:
1. **one-project winner**;
2. **multi-project portfolio answer**;
3. **active specialist frontier**;
4. **operationally urgent seam**;
5. **hidden multiplier / enabling substrate**.

A candidate rises when it wins on most of these questions:
- does it reduce a recurring pain rather than a niche annoyance?
- does official Rust/Cargo/crates.io/Foundation movement already pull in that direction?
- can it emit reviewable artifacts rather than screenshots and lore?
- can a v0 ship as a thin companion layer?
- can it stay current without a permanent curation empire?

## The shortlist

### 1) Build-State Evidence is still the best single-project answer
If one serious team can only build **one** thing, the archive should still say:
**build Build-State Evidence.**

Why it wins:
- it matches one of Rust's broadest recurring pains;
- Cargo is already building native substrate for this story;
- it helps local loops, CI, editors, and large workspaces at the same time;
- and it composes with many other archive seams instead of competing with them.

A worthy v0 should look like:
- one `build-state-pack/v0` family;
- capture / explain / diff / doctor style commands or equivalent workflows;
- imports from Cargo-native evidence (`cargo report`, plan/build-dir/build-cache context, structured outputs) instead of terminal scraping;
- distinct artifacts for **subject**, **rebuild reason**, **timing/resource evidence**, **cache/contention evidence**, and **human-readable diagnosis**.

The blueprint is now explicit:
- treat the public shape as **portable build review**, not “faster builds” in the abstract;
- preserve **observed facts**, **imported facts**, **derived judgments**, and **hypothetical opportunities** as separate truths;
- and prove the project first on editor/CLI contention, private-change churn, workspace/CI cache posture, and build-dir-layout migration lanes.

Do **not** accidentally build:
- another cache-wrapper empire;
- another build-health score;
- another daemon that becomes the unofficial Cargo control plane.

## Outside-the-box portfolio answer
If a serious lab or funder can build **more than one** contribution, the archive should not answer with five unrelated products.
It should answer with a **shared artifact-conventions portfolio**:

1. **Build-State Evidence** for build reality.
2. **Semantic Context** for semantic authority and machine-usable queries.
3. **Migration Truth + Public API** for release/change correctness.
4. **Package Intake Gateway** for local package ingress and extraction truth.

Why this portfolio is stronger than four disconnected tools:
- these four seams reinforce each other;
- they all benefit from thin artifact families with explicit subject / authority / partiality / handoff boundaries;
- and they create better downstream inputs for Adoption Navigation, Native Edge, canonical learning consumers, CI, and assistants.

Shared conventions across the portfolio should include:
- this shared grammar is now specified in `design/portfolio-artifact-conventions-2026Q1.md`;
- a common pack header pattern (`subject`, `scope`, `authority`, `freshness`, `partiality`, `attachments`, `handoff`);
- common `capture / explain / diff / verify / doctor` verbs where they genuinely fit;
- explicit machine-vs-human and canonical-vs-derived boundaries;
- and assistant slices that are always downstream from captured truth.

This should **not** be treated as a new mega-seam or a universal schema empire.
It is a disciplined execution strategy for the archive's already-high-ranked control planes.

## Practical build order
If the archive had to recommend a realistic order for a strong ecosystem team:
1. build **Build-State Evidence** first;
2. build **Semantic Context** second;
3. build **Migration Truth + Public API** third;
4. build **Package Intake Gateway** fourth;
