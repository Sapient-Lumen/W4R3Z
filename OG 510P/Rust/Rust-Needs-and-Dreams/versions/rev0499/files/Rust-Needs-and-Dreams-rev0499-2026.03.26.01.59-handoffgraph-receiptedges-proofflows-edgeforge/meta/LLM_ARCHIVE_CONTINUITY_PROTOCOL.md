# LLM archive continuity protocol

## Goal
Keep future archive revisions from drifting into private folklore, silent ranking rewrites, stale citations, or one-pass brainstorming canon.

This note is about **how the archive should be edited**, not about which Rust seam is best.
It exists because the repo is now large enough that a good answer can still become a bad revision if the assistant forgets what changed, why it changed, or which claims were still tentative.

Read with:
- `AGENTS.md`
- `INDEX.md`
- `PRIORITIES.md`
- `STRATEGIC_FRONTIER.md`
- `RESEARCH_LOG.md`
- `meta/REVISION_OPERATING_PROTOCOL.md`
- `meta/AMNESIA_RESISTORS.md`
- `meta/CANONICAL_WORKING_SET.md`
- `meta/CANONICAL_RENEWAL_QUEUE.md`
- `atlases/portfolio-source-atlas-v0/sources.json`

## Default revision rule
A revision is only healthy if it leaves behind enough structure that a different assistant can later answer:
- what changed,
- what did not change,
- which sources carried the change,
- which files were touched,
- which claims remain tentative,
- and which future refresh should revisit the decision.

If those answers are missing, the archive should assume the revision is **lossy** even if the prose is good.

## Required moves for any non-trivial revision

### 1) Start from the latest canon, not from memory
Before rewriting ranking or synthesis, re-read at least:
- `AGENTS.md`
- `INDEX.md`
- `PRIORITIES.md`
- `STRATEGIC_FRONTIER.md`
- `RESEARCH_LOG.md`
- the directly relevant design note(s)
- `meta/REVISION_OPERATING_PROTOCOL.md`
- `meta/AMNESIA_RESISTORS.md`

### 2) Declare the revision type explicitly
Every non-trivial revision should state which of these it is:
- **deepening** — sharper execution answer, no ladder rewrite;
- **ranking refresh** — ordering changed or became more explicit;
- **folding** — ideas merged beneath a stronger parent seam;
- **frontier promotion** — rare, should be explicit;
- **meta-hygiene** — archive-operating behavior changed.

Never let a ranking change masquerade as mere prose cleanup.

### 3) Carry freshness anchors with exact source dates
When a revision relies on live or recent ecosystem facts, record the exact source dates and authority lane in the research log or source atlas.
Do not leave “latest survey”, “recent Cargo work”, or “current roadmap” hanging without anchors.

### 4) Keep stable claims, changed claims, and speculative claims separate
A healthy revision says three things separately:
- **unchanged canon** — what still stands;
- **changed interpretation** — what moved and why;
- **speculative watch points** — interesting but not-yet-canonical bets.

Do not let an attractive future possibility silently promote itself into canon.

### 5) Leave a changed-files ledger in prose
The research log entry for the revision should include a concise changed-files ledger.
Not because file names are sacred, but because the next assistant should not have to diff the whole repo mentally.

Minimum ledger classes:
- new files;
- refreshed canon files;
- refreshed meta files;
- refreshed atlas or evidence files;
- maintenance actions such as manifest or doctor refresh.

### 6) Update routing if the answer surface changed
If the best answer to a class of question changed, update the routing layer:
- `AGENTS.md`
- `INDEX.md`
- `PRIORITIES.md`
- `STRATEGIC_FRONTIER.md`
- `meta/CANONICAL_WORKING_SET.md`

### 7) Update memory rails if the failure mode is predictable
If the revision discovered a recurrent archive failure mode, encode it in:
- `meta/AMNESIA_RESISTORS.md`
- `meta/REVISION_OPERATING_PROTOCOL.md`
- or a dedicated meta note like this one.

### 8) Refresh the atlas when sources become load-bearing
If a new source family becomes important enough to support repeated future claims, add or refresh a source-atlas card instead of hiding it only in narrative prose.

### 9) Regenerate maintenance artifacts at the end
For revisions that change archive structure or canon, refresh:
- `meta/ARCHIVE_MANIFEST.md`
- archive mirrors under `archive/`
- doctor / hygiene outputs when appropriate.

## Prohibited drift patterns

### Silent canon rewrite from one brainstorm
One assistant run may discover a better framing.
It may not silently replace long-held ranking without saying that a ranking refresh occurred and why.

### Source laundering through archive prose
Do not cite the archive to prove the world.
Use the archive to remember prior reasoning, but refresh live external claims against external sources.

### Flattening unlike truths into one summary
Do not let one summary paragraph impersonate the whole evidence stack when the archive already distinguishes:
- subject truth
- evidence truth
- claim truth
- handoff truth
- drift or freshness truth
- speculative or watch posture

### Deleting friction history
If a revision folds or eliminates an idea, preserve the reason.
Future assistants should be able to tell whether the idea was rejected as wrong-shaped, superseded, premature, or merely unowned.

### Treating assistant context as canon
Derived prompts, summaries, or assistant-context slices are consumers.
They are never the canonical owner of the archive's claims.

## Preferred revision paragraph shape
When a revision matters, prefer leaving behind a paragraph that can answer all of this in one place:
- why now,
- what changed,
- what stayed the same,
- which files were touched,
- which sources mattered,
- and which future refreshes should watch for drift.

That is the archive's best defense against amnesia, over-interpretation, and duplicate work.
