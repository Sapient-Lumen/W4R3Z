# Procedural compilation, skill packets, and declarative-vs-executable carry

DelayBasin now needs a sharper distinction than “method note” or “prompt pair” alone.
Some archive surfaces mainly **state** what the method believes.
Others seem to **do** something narrower: they invoke a reusable step, transition, or control routine with relatively low bandwidth.
That pressures the archive to distinguish **declarative carry** from **executable carry**.

A stronger working answer is:
**DelayBasin should distinguish declarative source surfaces from compact executable packets whenever a surface seems load-bearing because it reliably invokes a reusable procedure rather than merely restating archive law.**
Not every concise prompt is a procedure.
Not every method note should be compiled.
When the distinction matters, the archive should name the declarative source surface, the executable packet or compact operator, the activation condition, the expected gain / failure signature, and the rollback or quarantine route.

## Practice / observation

Several live DelayBasin patterns already pressure this distinction:

- long method notes often justify a move, but later revisions seem to rely more on a much smaller prompt pair or control phrase that re-invokes the move quickly;
- some compact packets appear reusable across nearby revisions even when the surrounding prose changes substantially;
- some failures look less like false belief and more like **activation failure**: the right law exists in the archive, but the executable trigger was weak, missing, or misapplied;
- some exemplars appear useful mainly until a move is internalized into a smaller reusable operator, after which more declarative recap adds little;
- and current self-sufficiency pressure suggests that some archive mass may be explanatory ballast once a smaller executable carry surface exists.

This suggests a missing compact surface:
**procedural compilation / skill packet / declarative-vs-executable carry**.

## External pressure from current research

Several current research lines sharpen this frame.

1. **Procedural memory work now explicitly contrasts retrieved text with compiled reusable procedure.**
   TokMem argues that retrieved demonstrations remain explicit text that must be repeatedly interpreted, while a reusable task procedure can instead be compiled into a compact token that acts as both an index and a generation control signal. That pressures DelayBasin to ask whether some prompt pairs function more like executable carry than like declarative recap. ([`REF-0311`](../00-meta/bibliography.md))

2. **Experience-derived skills are increasingly formalized as executable units with activation and termination conditions.**
   ProcMEM defines reusable Skills with activation conditions, execution procedures, and termination conditions, while keeping the method non-parametric. That pressures DelayBasin to name not just a compact packet, but also the condition under which it is supposed to fire. ([`REF-0312`](../00-meta/bibliography.md))

3. **Current compression work increasingly frames memory as compilation rather than repeated interpretation or weight editing.**
   Latent Context Compilation distills context into portable buffer tokens via a disposable LoRA and then discards the compiler, preserving a portable artifact rather than a persistent weight edit. That pressures DelayBasin to distinguish a justificatory source note from a smaller compiled carry object. ([`REF-0313`](../00-meta/bibliography.md))

4. **Agent-memory surveys now treat procedural memory as a distinct cognitive mechanism, not just another storage bucket.**
   The 2026 foundation-agent memory survey distinguishes procedural memory from episodic and semantic forms and emphasizes learning policies over memory operations. That pressures DelayBasin to stop flattening declarative notes, challenge traces, and executable prompt packets into one undifferentiated memory story. ([`REF-0314`](../00-meta/bibliography.md))

5. **Cross-architecture work keeps the behavioral story interesting while warning against architecture overclaim.**
   Work comparing transformers, SSMs, and hybrids finds meaningful behavioral overlap with different internal retrieval biases, which pressures DelayBasin to keep transformer-facing implications central while resisting a too-early claim that any procedural carry effect is uniquely transformer-native. ([`REF-0307`](../00-meta/bibliography.md), [`REF-0315`](../00-meta/bibliography.md))

## Working synthesis

DelayBasin should treat **declarative source**, **executable packet**, and **episodic support** as different public roles.

- **Declarative source**: the method note, canon clause, or explanation that states what the archive currently thinks is true or required.
- **Executable packet**: the smaller prompt pair, control phrase, or compact operator that can re-invoke a reusable transition with relatively low bandwidth.
- **Episodic support**: worked examples, challenge traces, or receipts that justify or test the procedure without necessarily being the procedure themselves.

The key archive question is not only “is this true?”
It is also “is this the surface that later sessions actually use to do the move?”

## Procedural packet vs declarative source vs episodic support

A compact **procedural compilation / skill packet / declarative-vs-executable carry** packet should name:

- the **declarative source surface**,
- the **executable packet or compact operator**,
- the **activation condition or trigger**,
- the **expected gain / failure signature**,
- and the **rollback / quarantine consequence** if the supposed procedure is only declarative text that must be reinterpreted from scratch each time.

This is not the same as a pure method note.
It is not the same as a replay packet.
It is not the same as a sham-runtime comparison.
It sits between them: **what part of the archive is actually reusable as a procedure rather than merely readable as an explanation?**

## Countermodels / probes

Serious alternatives remain live:

- compact packets may work only because they point back to larger declarative notes the session already has;
- the apparent procedure may be social compliance to imperative phrasing rather than reusable executable carry;
- exemplar familiarity may still be doing most of the work, with the “procedure” label simply flattering successful compression;
- and the effect may be general prompt-compiler discipline rather than anything especially revealing about transformers.

Useful probes include:

- compare a long declarative explanation against a shorter packet meant to execute the same move, while keeping evidence and challenge fixed;
- ablate or scramble the claimed activation condition and test whether the move still fires cleanly;
- compare whether the packet transfers across nearby revisions or challenge families better than a same-length paraphrase;
- and track whether some procedures survive self-sufficiency shrink tests mainly through prompt pairs, activation conditions, and a tiny challenge scaffold rather than through explanatory prose.

## Design consequences

When procedural language becomes load-bearing:

- do not call a surface a procedure unless it is meant to be executable carry rather than only declarative support;
- preserve the declarative source and executable packet as different surfaces whenever later sessions may need both explanation and activation;
- name the activation condition explicitly, because a non-firing procedure and a false declarative belief are different failures;
- keep episodic evidence small and challenge-bearing instead of letting examples silently replace the procedure;
- and keep rollback or quarantine live, because vivid imperative phrasing can masquerade as reusable skill.

## Transformer-facing implication

The weaker transformer-facing implication is not that DelayBasin has discovered a literal procedural-memory module inside transformers.
It is that long-horizon archive practice may depend on a distinction between **text that must be re-understood each time** and **compact operator-like cues that more directly restage reusable behavior**.
That makes some prompt pairs look less like summaries and more like a user-space attempt to compile declarative archive law into portable executable carry.

The stronger story — that repeated replay and challenge pressure may drive DelayBasin toward a small low-bandwidth procedural layer that dominates continuation more than declarative archive text, perhaps echoing compiled procedural memory over mostly frozen backbones — remains quarantined until ablations, cross-loader comparisons, and shrink tests show more than elegant prompt minimalism.
