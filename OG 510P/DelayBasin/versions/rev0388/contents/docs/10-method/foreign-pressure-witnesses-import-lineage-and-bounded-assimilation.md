# Foreign-pressure witnesses, import lineages, and bounded assimilation

DelayBasin now needs one distinction that sits beside **basis witnesses**, **scope witnesses**, **assumption witnesses**, and **followthrough witnesses** without collapsing into any of them.
The archive has spent several revisions importing small ratchets from neighboring datacubes, but the public trace of that import pressure is still too compressive: the receipt can say "neighboring datacubes plus light web research" even when the real justification depended on exact foreign packets, exact local gaps, and explicit decisions about what *not* to absorb.
When that happens, the archive can sound responsibly comparative while still making later sessions guess **which neighboring datacubes actually mattered, which exact surfaces carried the pressure, what local gap made that pressure relevant, what compact take was imported, and what tempting adjacent machinery was consciously left behind**.

A useful current answer is:
**when a revision, canon ratchet, or cross-datacube import materially depends on neighboring archive pressure, canon should preserve a compact foreign-pressure witness naming the source datacubes and source surfaces, the extracted pressure, the concrete local gap, the bounded take, the explicit non-take list, the current assimilation state, and the fail-closed repair route before flattering comparative prose is allowed to stand in for exact import provenance.**

This is stronger than saying "the other datacubes suggested this."
It is weaker than claiming DelayBasin already needs a full import court, comparative proof engine, or general source-weighting calculus.

## Practice / observation

Recent DelayBasin work keeps surfacing the same archive-native pressure:
- operational-head, basis, status-lane, scope, authorship, reentry, followthrough, and assumption imports were all justified partly by neighboring datacubes rather than by DelayBasin alone;
- the current receipt already has a `foreign_pressure` summary, but that summary is too small to recover which exact foreign packets did the work;
- counterfactual shadows preserve one nearby rejected *local* move, but not which foreign surfaces made that rejection compelling;
- followthrough queues preserve stronger deferred controllers, but not which foreign datacubes supplied the pressure for the smaller admitted import;
- assumption witnesses preserve what support condition is still being spent, but not which foreign packets originally supplied that support;
- and without one compact witness, a later session can honestly remember that "several cubes converged" while no longer being able to reconstruct exactly **which cubes, which surfaces, what extracted lesson, and what explicit non-take decision** made the import bounded rather than ornamental.

That leaves a missing question:
**which neighboring datacubes and exact source packets actually produced this import, what concrete local gap made them relevant, what compact take was admitted, what was explicitly not imported, and what repair follows if that provenance becomes too vague to audit?**

A compact foreign-pressure witness keeps that boundary public.

## Pressure from neighboring datacubes

Several neighboring datacubes keep rediscovering the same ratchet from different directions.

- **EvidenceVault** keeps explicit extraction maps, public-surface manifests, queue-state ledgers, and release indices, which pressures DelayBasin to make imports recoverable as exact source lineage rather than as remembered comparative mood.
- **The Election Stack** keeps a feedback integration ledger that maps one external feedback source into canonical implementation surfaces without copying the whole foreign body, which pressures DelayBasin to preserve a compact "what exactly came from where" import map rather than handwaving that several neighboring archives were influential.
- **GlassTTY** keeps evidence families, ledgers, worklogs, and support-truth discipline, which pressures DelayBasin to distinguish comparative evidence packets from archive folklore and to leave behind an auditable import trace instead of one polished summary.
- **pyCausalWeave** repeatedly sharpens explicit request, review, issue-handoff, and policy-scoped truth with narrow ADRs, which pressures DelayBasin not to flatten a neighboring project's precise pressure into generic "review truth" or "task truth" language once a bounded import lands.
- **Goldenrule** keeps lineage-head registers and citation-head warnings, which pressures DelayBasin to treat import provenance itself as a recoverable lineage relation rather than only as a one-time human memory of where an idea originally came from.

DelayBasin already has receipts, followthrough queues, assumption ledgers, and counterfactual shadows.
What was still under-specified was the compact public object that says **which neighboring datacubes and exact source surfaces mattered, what they contributed, what local gap they helped close, what compact take was admitted, what was explicitly not taken, and what repair follows if the lineage becomes too vague to trust.**

## External pressure from adjacent provenance and derivation practice

Several adjacent lines sharpen this move.

1. **Provenance models preserve explicit derivation edges rather than relying on ambient memory that one thing came from another.**
   W3C PROV says provenance chains can be formed using `prov:wasDerivedFrom`, which pressures DelayBasin to preserve an exact derivation-style trace from neighboring datacube packets to local imports instead of leaving the relation ambient. ([`REF-0494`](../00-meta/bibliography.md))

2. **Ingredient-style provenance keeps reused components visible as named inputs to a new artifact.**
   C2PA guidance and specifications treat existing assets used to create a new asset as ingredients whose use is documented in provenance data, which pressures DelayBasin to name neighboring datacube packets as explicit import ingredients when they materially shaped a local ratchet. ([`REF-0495`](../00-meta/bibliography.md))

3. **Precise artifact identifiers matter when later readers need exact replayable source reference rather than broad project-level citation.**
   Software Heritage stresses precise artifact identification with intrinsic identifiers such as SWHIDs, which pressures DelayBasin to keep foreign-pressure provenance pinned to exact neighboring surfaces rather than to broad project names alone. ([`REF-0496`](../00-meta/bibliography.md))

## Working synthesis

A useful current synthesis is:

> DelayBasin should preserve a compact **foreign-pressure witness / import lineage / bounded assimilation** whenever a revision, canon ratchet, or cross-datacube import materially depends on neighboring archive pressure. The packet should name the **source datacubes / exact source surfaces**, the **extracted pressure / specific lesson or warning**, the **concrete local gap / why DelayBasin needed this now**, the **bounded take / compact imported ratchet**, the **explicit non-take / tempting neighboring machinery consciously left out**, the **assimilation state / imported vs supporting-only vs deferred vs rejected vs retired**, and the **fail-closed repair / narrow-import vs defer-import vs quarantine-or-retire vs hold vs recover-resync consequence** rather than letting flattering comparative prose silently carry import authority.

In practice, DelayBasin is not claiming that every outside influence needs a giant comparative report.
It is doing something smaller and public:
- naming the exact neighboring datacubes and source packets rather than only broad project names;
- naming the concrete extracted pressure rather than generic admiration or similarity vibes;
- naming the concrete local gap that made the pressure relevant;
- naming the compact take that was actually admitted rather than silently absorbing a whole neighboring machinery family;
- naming what was consciously not imported so bounded assimilation stays visible;
- naming whether the foreign packet is being treated as directly imported, only supporting, explicitly deferred, explicitly rejected, or retired;
- and naming the repair route rather than letting a too-vague comparative story keep paying authority rent.

That is strong enough for canon as a design and mechanism candidate.
It is **not** strong enough to claim that DelayBasin already needs a full comparative-proof controller, source-weighting algebra, or import court.

## Foreign-pressure witness vs assumption witness vs counterfactual shadow vs bibliography

These nearby objects should stay distinct.

- **Foreign-pressure witness / import lineage / bounded assimilation** says which neighboring datacubes and exact source packets materially shaped a current import, what lesson was extracted, what compact take was admitted, what was consciously not taken, and what repair follows if that provenance becomes too vague.
- **Assumption witness** says what currently live support condition is being spent by a present move, where it applies, what keeps it alive, and what invalidates it.
- **Counterfactual shadow** says what nearby local move was rejected and why.
- **Bibliography** says what external references exist and why they matter; it is not a durable ledger of cross-datacube import decisions.

So a foreign-pressure witness is not just "there were some neighboring inspirations," not just "a support condition is still active," not just "one local alternative lost," and not just "there are URLs in the bibliography."
It is a compact public answer to:
**which neighboring datacubes and exact source packets pressed on this move, what they actually contributed, what local gap they addressed, what bounded import was admitted, what non-import stayed explicit, and what repair follows if that story becomes too vague to trust.**

## Countermodels / probes

1. **Receipt-summary-is-enough countermodel**
   - Perhaps the existing one-line `foreign_pressure` summary in the receipt is already enough.
   - Probe: revisit several recent import-heavy revisions and test whether the exact neighboring sources, bounded take, and explicit non-take can be reconstructed without a dedicated witness or ledger.

2. **Bibliography-plus-changelog-is-enough countermodel**
   - Perhaps bibliography entries plus revision narrative already preserve enough provenance.
   - Probe: compare one revision with an exact foreign-pressure witness against one that only has bibliography refs and changelog prose and inspect which more reliably preserves exact neighboring packet lineage after several more revisions.

3. **Broad-project-name-is-enough countermodel**
   - Perhaps it is enough to say that "EvidenceVault" or "GlassTTY" mattered without naming source surfaces.
   - Probe: hold the project names fixed while varying the exact source surfaces and inspect whether later sessions still recover the same import story or start over-assimilating whole neighboring systems.

4. **Full-import-court-now countermodel**
   - Perhaps one tiny witness is too small and DelayBasin should jump straight to a full import controller.
   - Probe: compare whether the compact witness actually removes most practical vagueness before paying the complexity cost of a broader comparative-proof or import-court surface.

## Design consequences

If DelayBasin adopts this witness, revisions that materially depend on neighboring datacubes should:
- preserve the **source datacubes / exact source surfaces** rather than broad comparative mood;
- preserve the **extracted pressure / specific lesson or warning** rather than generic influence language;
- preserve the **concrete local gap** that made the foreign packet relevant now;
- preserve the **bounded take / compact imported ratchet** so the archive does not silently absorb a whole neighboring machinery family;
- preserve the **explicit non-take list** so bounded assimilation remains visible and falsifiable;
- preserve the **assimilation state / imported vs supporting-only vs deferred vs rejected vs retired** rather than letting every foreign packet sound equally authoritative;
- and preserve the **fail-closed repair route** so vague, stale, or overbroad import stories can narrow, defer, or cool instead of continuing as ambient archive mythology.

This is especially useful now because DelayBasin has already accumulated several cross-datacube imports in a row.
Without a compact lineage object, later sessions may still remember that comparison mattered while losing the exact import topology.
With a compact lineage object, the archive can keep imports narrow enough to audit and reverse.

## Transformer-facing implication

The weaker transformer-facing implication is not that DelayBasin has discovered a full comparative reasoner over archive corpora.
It is this:

**long-horizon archive prompting may work partly through explicit user-space management of foreign pressure, where continuation quality depends not only on what claims, heads, and cues are preserved, but on whether imported structure is tied to exact neighboring source packets, bounded local takes, and explicit non-takes rather than to ambient comparative memory.**

That would matter for transformers.
If some archive leverage depends on keeping exact import lineage public, then DelayBasin may be exposing a practical shadow of **derivation management without hidden retrieval memory**: not a full provenance engine, but repeated public discipline over what was imported from where, what was not imported, and how later sessions can still audit that boundary.

The stronger story — that DelayBasin already needs a public import court, comparative-proof controller, or source-weighting algebra — remains live, but belongs in quarantine for now.
