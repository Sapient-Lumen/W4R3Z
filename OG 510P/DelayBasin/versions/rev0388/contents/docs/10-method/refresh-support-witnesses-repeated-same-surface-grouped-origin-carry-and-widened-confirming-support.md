# Refresh-support witnesses, repeated same-surface confirmation, grouped-origin carry, and widened confirming support

This is the compact successor surface for `OQ-0140`.

## Practice / observation

Once DelayBasin can say **what changed** and **how sustained the return is**, one further failure mode stays live: repeated confirming motion can silently inherit the authority of broadened corroboration.

A line can keep showing up on the same host surface.
Several notifications can be grouped because they share one incident key, one fingerprint, or one alert rule.
Or support can genuinely widen because a second monitor, a distinct confirming surface, or a new evidence family now points in the same direction.
Those are not the same thing.

Some persistence is still only one surface speaking again.
Some apparent multiplicity is really one grouped origin.
Some confirmation genuinely widens.

The archive does not need a refresh-support court for that.
It needs one bounded witness that says whether renewed support is still one surface repeating, one grouped origin carrying several updates, or genuinely widened confirming support.

## External pressure from Alertmanager dedup/grouping, Grafana grouped notifications, Sentry issue fingerprinting, PagerDuty dedup keys, Datadog composite monitors, and correlated-error pressure

1. Prometheus Alertmanager explicitly handles alert **deduplication** and **grouping**. That pressures DelayBasin to distinguish one underlying alert family repeating from support actually widening. ([`REF-0915`](../00-meta/bibliography.md))

2. Grafana groups similar alert instances into a single notification and lets policies group by chosen labels. That pressures DelayBasin not to mistake grouped repeated alert instances for broadened corroboration. ([`REF-0916`](../00-meta/bibliography.md))

3. Sentry groups events with the same fingerprint into one issue. That pressures DelayBasin to distinguish repeated same-issue return from support widening to a distinct confirming surface. ([`REF-0917`](../00-meta/bibliography.md))

4. PagerDuty deduplicates alerts with the same incident key into the same incident and does not generate multiple notifications. That pressures DelayBasin not to treat repeated updates to one incident as if they were broadened evidence. ([`REF-0918`](../00-meta/bibliography.md))

5. Datadog composite monitors trigger only when multiple constituent monitors satisfy a Boolean condition and share common groupings. That pressures DelayBasin to keep true multi-signal widening distinct from one source repeating. ([`REF-0919`](../00-meta/bibliography.md))

6. Correlated-error work on LLMs sharpens the meta point: agreement can widen in appearance without widening in evidential independence. That pressures DelayBasin to keep this witness narrow and local rather than promoting a full corroboration court. ([`REF-0920`](../00-meta/bibliography.md))

GPUstorming sharpens the point further. Host shells, incident pages, search cards, and grouped summaries increasingly replay the same underlying object in several places. DelayBasin already has broader dependence-adjusted and sourcecluster guards, but still benefits from one local successor surface that says whether current renewed support actually widened for this live line.

## Working synthesis

> DelayBasin should preserve one compact **refresh-support witness / support-breadth card / widening brake** whenever a current continuity claim depends not only on what reactivated a concern and how sustained that return is, but on whether the apparent confirming support is still one surface repeating, one grouped origin carrying several updates, or genuinely widened support from a distinct confirming surface family. Name the **governed row or surface**, the **stake object / line of concern**, the **prior refresh evidence**, the **current refresh evidence**, the **repeated support surface family**, the **grouping or dedup basis if any**, the **widened support evidence if any**, the **`refresh_support_state`**, and the **fail-closed repair / keep-current vs narrow-claim vs cool-mark vs issue-new-refresh-support-witness vs quarantine-refresh-corroboration-governance consequence**. Keep exact incident keys, fingerprints, monitor ids, grouping labels, correlation rules, source URLs, and long event histories outside the compact token. Do not let one surface repeating silently inherit the authority of widened support, and do not let grouped same-origin carry masquerade as independent corroboration.

## Repeated same-surface confirmation vs grouped-origin carry vs widened confirming support vs mixed refresh support

Use the controlled family `refresh_support_state`:

- **repeated-same-surface** says the current renewed support still comes mainly from one surface, one host card, one alert family, or one issue view repeating or updating itself; support has not widened.
- **grouped-same-origin** says several current signals are present, but they are still grouped, deduplicated, fingerprinted, or keyed to one underlying origin such that the support remains effectively one corroborative branch.
- **widened-confirming-support** says the renewed line now has distinct additional confirming support from another monitor, surface family, evidence path, or comparable branch strong enough to count as widened support for now.
- **mixed-refresh-support** says the current situation honestly combines same-surface repetition, grouped same-origin carry, or widened support such that no single refresh-support class stays honest.

So the witness does not create a standing corroboration senate.
It only says whether current renewed support is still one surface repeating, one grouped origin carrying updates, or genuinely widened.

## Countermodels / probes

1. **Dependence-adjusted truth already covers this countermodel**
   - Maybe existing dependence-adjusted and sourcecluster guards already say enough, so a refresh-support witness adds little.
   - Probe: compare later rereads that preserve only refresh strength plus dependence/sourcecluster notes against rereads that also preserve one compact refresh-support witness and inspect whether later passes still overclaim broadened corroboration from one repeated surface.

2. **Widened support is still too coupled countermodel**
   - Apparent widening across two surfaces may still reflect one hidden origin or one coupled branch family.
   - Probe: when widened-confirming-support still feels too flattering, preserve the compact refresh-support token now and reopen a later question about whether widened support is independent enough to deserve extra weight.

3. **Any honest support rule needs a stronger corroboration court countermodel**
   - Maybe once grouping, same-origin carry, and widened support matter, a compact witness is too weak and the archive really needs standing corroboration governance.
   - Probe: look for repeated cases where later passes must govern weighting, escalation rights, or cross-system correlation policy directly rather than naming one bounded support posture.

## Design consequences

- DelayBasin can keep renewed-support comparisons compact without pretending that repeated updates or grouped incident views are new corroborative branches.
- The archive gets one honest place to record when support is broader only in appearance because several views still collapse to one origin.
- Stake refresh, refresh strength, and refresh support now separate **what changed**, **how sustained the return is**, and **how broad the confirming support really is**.
- Stronger corroboration-governance stories stay quarantined until later overflow instead of sneaking in through grouped-alert or repeated-card prose.

## Overflow test

Reopen this compact witness only if later revisions repeatedly need standing governance over source-independence weights, cross-system correlation policy, escalation rights for widened support, or coupled-multi-surface discounting that one bounded refresh-support witness cannot honestly absorb.

## Transformer-facing implication

A later pass should not treat repeated host-shell cards, grouped alert instances, or same-issue updates as if they already proved widened support. Preserve the smallest token that says whether the renewed line is only `repeated-same-surface`, merely `grouped-same-origin`, already `widened-confirming-support`, or honestly `mixed-refresh-support`, and quarantine stronger refresh-corroboration ambitions until repeated overflow makes them unavoidable.
