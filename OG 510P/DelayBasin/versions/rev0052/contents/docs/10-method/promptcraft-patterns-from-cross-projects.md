# Promptcraft patterns from cross-project examples

Status: `inferred`

This doc extracts method patterns from the provided prompt-pair examples across Micromax, VisualHotKey, Hyperepo, Toolkit, GlassTTY, EvidenceVault, Anonymity, Ithkuil translation, 0opschan, Golden Rule, Overseer, Election Stack, and Radical Governance.

## Repeated pattern 1: canon declaration

The stronger prompt pairs do not merely say “continue.”
They say:
- read the latest archive,
- treat it as source of truth,
- reopen from canon rather than old drift,
- name exact must-read files when available.

This appears load-bearing because it reduces ambiguity about which past state is authoritative.

## Repeated pattern 2: non-negotiable surface

The stronger prompt pairs name a small set of constraints that must not degrade.
Examples across the corpus include:
- singlefile/offline invariants,
- no ambient authority,
- one-tex-file-per-paper,
- host-native bounded execution,
- archive size discipline,
- explicit trust posture.

This appears load-bearing because it transforms vague mission into basin walls.

## Repeated pattern 3: per-iteration ratchet

The better prompts require at least one concrete ratchet per run:
- one refactor,
- one guardrail,
- one integrated feature,
- one high-leverage paper architecture improvement,
- one careful implementation pass.

This appears load-bearing because it prevents pleasant but non-cumulative motion.

## Repeated pattern 4: archive luxury for future LLMs

The prompts often explicitly ask for:
- clean handoff docs,
- worklogs,
- context packs,
- memory files,
- wiring/discovery surfaces,
- reproducible release bundles.

This is not merely comfort. It treats future re-entry as a product surface.

## Repeated pattern 5: honest testing

Strong prompts ask for real tests or explicit honesty about what could not be run.
This prevents the archive from drifting into pseudo-implementation theater.

## Repeated pattern 6: continuation compression

The continuation half of the pair is usually much shorter than the bootstrap half.
This suggests a theory:
- the first prompt pair builds the basin,
- later prompts need mainly to reactivate and slightly steer it.

## Design consequence for DelayBasin

DelayBasin prompt pairs should usually include:
1. canon declaration,
2. invariant declaration,
3. ratchet obligation,
4. honesty/testing requirement,
5. packaging discipline,
6. and explicit permission for risky but quarantinable speculation.
