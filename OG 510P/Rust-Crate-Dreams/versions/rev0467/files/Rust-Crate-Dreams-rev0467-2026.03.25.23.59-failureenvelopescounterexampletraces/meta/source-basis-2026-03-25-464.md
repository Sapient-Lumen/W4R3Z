# Source basis note — 2026-03-25 (entry 464)

This pass adds a **renewal-program / freshness-budget / stewardship-loop** layer.
It is based primarily on current official Rust project sources and a few highly relevant official docs.rs pages.

## Official sources used most heavily

### Ecosystem pain / maintenance / receiver reality
- 2025 State of Rust Survey results — continued signals around debugging, resource usage, and documentation as the canonical reference.
- What we heard about Rust’s challenges — cross-domain signal that embedded and safety-critical adoption still runs into sharper support/tooling constraints.
- What is maintenance, anyway? — strong argument that reviewer/maintainer enablement is real work and should be made easier, not assumed away.
- What does it take to ship Rust in safety-critical? — strong evidence that stability is operational: upgrades, target policies, interop, and dependency posture must remain explainable over time.

### Machine-usable substrate and churn signals
- crates.io development update — Trusted Publishing only mode, blocked risky triggers, SLOC, and `pubtime` surfaces.
- malicious crate notification policy update — stronger signal that downstream systems should track durable advisory channels and not depend on noisy blog-post cadence.
- Cargo security advisory — alternate registries and older Cargo versions complicate carry-forward and renewal posture.
- docs.rs metadata / builds / download / rustdoc JSON — clear evidence that docs/build/target/API surfaces are now importable in machine form.
- build-dir layout v2 call for testing — explicit reminder that many tools still depend on Cargo internals and need help identifying breakage when those internals shift.
- cargo-semver-checks goal — explicit model where checks and overrides interact over time, not just once.
- public/private dependencies goal — clearer future substrate for API-boundary-aware renewal.
- open namespaces goal — more multi-team coordination and ownership semantics in crate families.
- cargo build analysis goal — useful future substrate, but still prototype-grade and explicitly unstable.
- sandboxed build scripts goal — stronger case for bounded review cost and deterministic reruns.
- StableMIR goal — evidence that more durable tooling interfaces are becoming realistic.

## Main inference this pass

The archive already had enough support for evidence bundles, claim tiers, interchange profiles, policy packs, and review packets.
What the sources additionally support is a stronger conclusion:

**a worthy missing Rust crate often needs to provide a bounded renewal contract, not just a strong initial review object.**

That inference is not stated verbatim by any single source.
It arises from combining:
- the maintenance post’s emphasis on review and contributor-enablement work,
- the safety-critical post’s emphasis on operational stability, dependency drift, and upgrade explainability,
- the build-dir testing post’s reminder that tool assumptions drift when substrate changes,
- the malicious-crate policy update’s shift toward durable advisory channels over noisy incident posts,
- the crates.io/docs.rs substrate becoming increasingly machine-usable,
- and build-analysis still being unstable enough that renewal logic should sit above raw prototype data.

## Confidence and limits

High confidence:
- a renewal/stewardship layer is now justified as repo doctrine;
- the leading practical front still favors receiver-facing control-plane crates;
- the decision front door remains the best first place to define shared renewal contracts;
- the continuity ring should rise when the question is “what forces renewal?” rather than “what creates evidence?”.

Medium confidence:
- the exact renewal-state vocabulary may still change;
- whether the renewal queue should be a first-class package or remain a CLI/data surface may change;
- some lanes may need narrower renewal semantics than the shared default.

Low confidence / open questions:
- whether `renewal-ledger.jsonl` should later be joined by signed attestations,
- how much organization-local queueing semantics should live inside shared renewal schemas,
- and whether later passes should add a dedicated `freshness-corpus` fixture set alongside `renewal-programs.json`.
