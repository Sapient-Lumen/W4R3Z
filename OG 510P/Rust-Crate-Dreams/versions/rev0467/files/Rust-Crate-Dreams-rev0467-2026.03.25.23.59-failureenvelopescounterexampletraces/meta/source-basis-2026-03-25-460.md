# Source basis note — 2026-03-25 (460)

This pass was a **conformance-kit and promise-tier** pass.
It did not aim to prove that a brand-new top-ranked lane exists.
It aimed to check whether current Rust ecosystem signals justify making **tiered support claims** a first-class planning layer for the current leaders.

## Facts imported directly

1. Rust users still report substantial pain around resource usage, debugging, and crate-choice/productivity questions.
2. Official Rust debugging material explicitly emphasizes debugger / operating-system / version variance and async gaps.
3. crates.io now exposes stronger trust/publication surfaces including Trusted Publishing-only mode, blocked risky triggers, and SLOC.
4. crates.io malware communication now routes most cases through RustSec advisories rather than individual blog posts.
5. Cargo’s March 2026 advisory explicitly warns alternate-registry users to verify their posture with their registry vendor.
6. docs.rs exposes build metadata, custom build configuration, downloadable rustdoc output archives, and hosted rustdoc JSON.
7. docs.rs default target behavior changed in October 2025, which demonstrates that hosted defaults are real but moving substrate.
8. Rust’s official target tiers distinguish meaningful support levels rather than a single binary support state.
9. Cargo and rustdoc/project-goals work continues around build analysis, libtest JSON, public/private dependencies, semver checks, namespaces, and StableMIR.
10. Safety-critical adoption emphasizes long-lived evidence-friendly stacks and stable boundary handling, not only “does it compile?”.

## Main inferences from those facts

1. The archive still does **not** need a fresh umbrella frontier reset.
2. The current substrate increasingly rewards crates that can export **bounded, tiered support claims** rather than vague support language.
3. The support-envelope ring is the cleanest first place to define shared conformance vocabulary.
4. The pathfinder / knowledge front door should increasingly import and freeze conformance claims rather than inventing support rhetoric itself.
5. The archive itself benefits from a machine-readable conformance memory layer.

## Open questions kept open

- Should the claim-tier vocabulary be shared verbatim across support, debugger, and continuity lanes, or should some lanes specialize it?
- When does a domain-specific “qualified” tier deserve shared semantics rather than local semantics?
- Should later revisions add per-lane conformance manifests, or is `conformance-kits.json` enough for now?
