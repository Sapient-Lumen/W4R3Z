# Source basis note — 2026-03-25 (entry 466)

This pass adds an **assurance-case / claim-traceability / witness-chain** layer.
It is based primarily on current official Rust project sources and official docs.rs pages.

## Official sources used most heavily

### Ecosystem pain / review burden / trust needs
- 2025 State of Rust Survey results — continued signals around debugging, resource usage, and crate-selection friction.
- Rust debugging survey 2026 — explicit reminder that support claims vary across debuggers, operating systems, versions, and async scenarios.
- What is maintenance, anyway? — strong argument that invisible review and enablement work is real labor worth reducing.
- What does it take to ship Rust in safety-critical? — strong evidence that higher-assurance adoption depends on traceable evidence, upgrade explainability, and bounded claims.

### Machine-usable substrate and claim-trace signals
- crates.io development update — stronger trust surfaces (`Security`, Trusted Publishing, SLOC, `pubtime`) make claim packets more actionable.
- crates.io malicious-crate policy update — advisory-first posture reinforces the need for durable reviewed packets rather than memory by blog post.
- Cargo security advisory — crates.io posture and alternate-registry posture can diverge, so inherited assurance cannot be assumed blindly.
- docs.rs changed default targets — concrete example where the support-relevant basis can shift even when a crate’s source is unchanged.
- docs.rs metadata / builds / download / rustdoc JSON — clear evidence that docs/build/API/target surfaces are importable and inspectable in machine form.
- cargo-semver-checks goal — explicit model where a claim can be checked, surfaced, and still allow a visible override path.
- cargo build analysis goal — stronger basis for causal claims about why builds changed.
- relink-don't-rebuild goal — stronger basis for minimizing blast radius when public consequences did not change.
- StableMIR goal — stronger case that analysis tools can stand on a more durable compiler-facing interface.
- open namespaces and target-tier policy — clearer substrate for package-family boundaries and support-scope semantics.

## Main inference this pass

The archive already had enough support for conformance kits, policy packs, review packets, renewal programs, and delta bundles.
What the sources additionally support is a stronger conclusion:

**a worthy missing Rust crate often needs to export an assurance case above those layers, so another team can trace a claim back to named witnesses, warrants, open challenges, and inheritance/supersession state.**

That inference is not stated verbatim by any single source.
It arises from combining:
- continued ecosystem pain around choosing and trusting crates,
- debugger and target support being matrix- and profile-sensitive,
- maintainer/reviewer labor being expensive and multiplicative,
- safety-critical and long-lived adoption needing explicit traceability,
- and the growing availability of machine-usable docs/build/API/trust substrate.

## Confidence and limits

High confidence:
- an assurance-case layer is now justified as repo doctrine;
- the broad frontier still favors receiver-facing control-plane crates;
- the decision front door is the best first place to make claim/witness/warrant/challenge structure human-usable;
- the support-envelope ring is the best witness supplier for that structure.

Medium confidence:
- the exact warrant vocabulary will likely vary by lane;
- some lanes may want smaller or larger challenge registers than the shared default;
- inheritance-bridge semantics may overlap with delta-program semantics more than currently planned.

Low confidence / open questions:
- whether `non-claims.md` should later become machine-readable,
- how much of warrant vocabulary should be standardized versus lane-specific,
- and whether later passes should add reusable assurance-case fixtures beside `assurance-cases.json`.
