# Cargo Package Review Kit product plan — 2026-03-20

This note turns **P-0470 Cargo Package Review Kit** into a more implementation-ready crate plan.
The sharper job is no longer merely “show what is in the `.crate`.”
It is to make one review bundle answer three receiver-facing questions:

1. **Which surface is authoritative for review and hashing?**
2. **Which packaged paths were copied versus generated during packaging?**
3. **Which mutations happened only after unpacking for verification?**

## Product judgment

A buildable `0.1` should be a **small cargo subcommand plus library** that helps maintainers publish one boring answer to:

- what exact `.crate` archive or archive-derived path listing was captured,
- whether key packaged files came from authored bytes or Cargo-generated bytes,
- what Cargo normalized, copied in, flattened, or stripped,
- whether the extracted verification tree differs in review-relevant ways from the archive,
- and which surface should be used for hashing, signoff, or downstream inspection.

It should **not** become:

- a new packager,
- a registry client,
- a provenance verifier,
- or a post-publish receipt joiner.

## What the crate should provide other people

For downstream reviewers, distro intake teams, and release stewards, the crate should provide:

1. **A packaged-surface receipt** instead of “we looked at the tarball somehow”.
2. **Archive-authority honesty** about whether the authoritative surface is the raw `.crate`, an extracted tree, Cargo’s JSON path report, or only a local authored tree approximation.
3. **Generated/copied lineage** for key packaged files such as `Cargo.toml`, `Cargo.toml.orig`, external readme/license copy-ins, and flattened symlink targets.
4. **An extraction-mutation report** that keeps `.cargo-ok`, normalized-manifest replacement, and mtime adjustments from silently borrowing the authority of the archive itself.
5. **A small diffable bundle** for CI, PR review, compliance intake, or publish rehearsal.
6. **A conservative failure mode** whenever the crate cannot honestly say which surface is authoritative.

## Recommended `0.1` command surface

### `cargo package-review capture`
Run one packaging capture.
This should:

- call `cargo package` / `cargo package --list` as the primary substrate,
- record the exact archive path or inability to retain one,
- import JSON path lineage when available,
- summarize manifest normalization and copy-in facts,
- and emit packaged-surface / authority / mutation receipts.

### `cargo package-review explain <path>`
Render a short summary for one packaged path.
This should answer:

- whether the path was copied or generated,
- what authored or external source it came from,
- whether it only exists in the extracted verification tree,
- and whether hashing that path is safe for archive-level claims.

### `cargo package-review diff <old> <new>`
Compare two review bundles and classify:

- `packaged_path_added`
- `packaged_path_removed`
- `path_lineage_changed`
- `authority_basis_changed`
- `extraction_mutation_changed`
- `manual_review_required`

### `cargo package-review pack`
Emit one compact archive for PR review, release signoff, or downstream intake.

## Suggested artifact set for `0.1`

Keep the existing review bundle, but make these three files first-class:

- `packaged-surface.receipt.json`
- `archive-authority.report.json`
- `extraction-mutation.report.json`

### `packaged-surface.receipt.json`
Should record:

- archive digest and capture route,
- packaged paths,
- whether each key file is `copy` or `generate`,
- authored-origin pointers for generated paths like `Cargo.toml` → `Cargo.toml.orig`,
- and whether a file is only present after extraction.

### `archive-authority.report.json`
Should record:

- review basis (`raw_archive`, `json_listing_plus_archive`, `extracted_verification_tree`, `authored_tree_only`, `mixed_manual_review`),
- what claims are allowed on that basis,
- what claims are forbidden,
- and whether the basis is strong enough for hashing/signoff.

### `extraction-mutation.report.json`
Should record:

- `.cargo-ok` introduction,
- normalized manifest replacement,
- mtime-only mutation versus content mutation,
- extraction-time generated metadata,
- and whether mutation is review-benign, hash-benign, or authority-breaking.

## Workspace / crate split

A good implementation shape would be:

- `cargo_package_review_model`
- `cargo_package_review_capture`
- `cargo_package_review_manifest`
- `cargo_package_review_authority`
- `cargo_package_review_pack`
- `cargo-package-review`

Optional adapters should stay optional:

- JSON listing import from unstable Cargo output,
- CI artifact emitters,
- tarball diff/render helpers.

## Proving-ground scenarios

A worthy `0.1` should survive at least these fixtures:

1. **Authored manifest vs generated packaged manifest**
   - `Cargo.toml.orig` versus generated `Cargo.toml`
   - raw-archive review basis stays explicit
2. **Extraction-only mutation after unpack**
   - `.cargo-ok`
   - mtime adjustments for generated files
3. **External readme/license copy-in**
   - copied file inside archive is distinct from authored path outside package root
4. **Workspace interdependent package set**
   - package set and authority basis remain stable across several crates
5. **Generated asset budget warning**
   - accidental package bloat is still reviewable without confusing origin or authority

## Good failure modes

Preferred failures:

- raw archive missing and only extracted tree present → `authority_basis = extracted_verification_tree`, `manual_review_required`
- JSON path lineage unavailable → keep packaged-path review, but downgrade origin confidence
- extracted tree differs only by `.cargo-ok` and mtime → report mutation, but keep archive authority
- extracted tree content differs beyond known mutation classes → `authority_basis = mixed_manual_review`

## Why this still looks worth building

Cargo now exposes just enough substrate that this no longer looks like “invent your own package model.”
The official docs now say:

- `cargo package` creates the canonical `.crate`,
- normalizes `Cargo.toml`,
- verifies by rebuilding from an extracted pristine state,
- checks build scripts did not modify source files,
- exposes copy/generate lineage through JSON listing,
- and still leaves extracted-tree mutation and authority classification to downstream tools.

That is exactly the sort of seam a worthy crate should close.
