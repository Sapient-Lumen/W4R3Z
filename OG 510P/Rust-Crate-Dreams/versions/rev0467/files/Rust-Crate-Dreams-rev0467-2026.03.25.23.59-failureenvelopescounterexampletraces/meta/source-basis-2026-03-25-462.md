# Source basis note — 2026-03-25 (462)

This pass was a **policy-pack and explainable-verdict** pass.
It did not aim to prove that a brand-new top-ranked lane exists.
It aimed to check whether current Rust ecosystem signals justify making **reviewable decision packs** a first-class planning layer for the current leaders.

## Facts imported directly

1. Rust users still report substantial pain around crate choice, resource usage, and debugging, while official online documentation remains the preferred canonical reference.
2. crates.io now exposes stronger trust and publication surfaces including a Security tab, Trusted Publishing Only mode, blocked risky GitHub Actions triggers, SLOC metrics, and `pubtime` in the index.
3. Rust target support is already expressed in bounded tiers rather than a binary supported / unsupported claim.
4. `cargo-semver-checks` is broadly adopted, and the cargo team is interested in integrating SemVer checks into `cargo publish` with an override flag.
5. Cargo build analysis is intentionally opt-in and prototype-grade for now, with schema evolution and no user-facing stability guarantees during the prototyping phase.
6. StableMIR aims to provide a reliable interface for tool developers that is insulated from compiler internals and versioned through crates.io.
7. Public/private dependencies aim to help users tell tooling what is private and better identify what constitutes an API.
8. The Rust Project Goals process for 2026 continues to position goals as the front door for turning contributor ideas into real ecosystem work.

## Main inferences from those facts

1. The archive still does **not** need a fresh umbrella frontier reset.
2. The current substrate increasingly rewards crates that can turn reviewed evidence bundles into **reviewable, explainable verdicts**.
3. The decision front door is now the cleanest first place to define a reusable policy-pack and verdict doctrine.
4. The support-envelope ring should remain the main evidence supplier, not the first owner of organization-local policy semantics.
5. Continuity, parity, and boundary lanes are especially important as **policy recheck triggers**.
6. The archive itself benefits from one more machine-readable memory layer for policy packs and verdict vocabulary.

## Open questions kept open

- Should the core verdict vocabulary stay exactly `allow / warn / block / manual-review / waived / expired`, or do some lanes need one extra universal state?
- Where should the line sit between shared core policy semantics and organization-local overlays?
- Should future passes add reusable policy fixtures and override examples, or is `policy-packs.json` enough machine-readable memory for now?
