# P-0535 — Dependency Lifecycle Transition Kit: override authority, signal freshness, and exception reevaluation (2026-03-22)

This note deepens **P-0535 Dependency Lifecycle Transition Kit** around three practical weak points that still make many dependency-transition stories too fuzzy to review:

1. **override authority** — where the transition is actually declared and who can see it,
2. **signal freshness** — whether imported ecosystem facts are still current enough to lean on,
3. **exception reevaluation** — whether a waiver is still alive, stale, or ready to close.

## Main judgment

A worthy next pass for **P-0535** should promote three more first-class review objects:

- `override-authority.receipt.json`
- `signal-freshness.report.json`
- `exception-reevaluation.report.json`

Those objects make the lane more honest in theory and in practice.
They tell another maintainer whether a dependency transition is:

- declared in checked-in policy,
- only present in local or generated config,
- based on fresh imported context,
- and still covered by an exception that has not quietly gone stale.

## Why this layer matters now

Current official Rust/Cargo sources make these gaps unusually concrete.

### 1. Cargo overrides have different visibility and authority classes

Cargo’s config docs say `[patch]` can be expressed in `.cargo/config.toml`, but those files are **not usually checked into source control** and Cargo recommends preferring `Cargo.toml` where possible so other developers can reproduce the build.
The same docs say config-file patches override manifest-file patches when both exist.

That means “we are currently on a fork/path override” is not one honest fact.
A lifecycle review needs to know whether the route is:

- shared and checked in,
- generated by an external build tool,
- local-only,
- or shadowing a checked-in manifest declaration.

### 2. Source replacement is not the same as patching or forking

Cargo’s source-replacement docs explicitly assume the replacement source contains **the exact same code** as the original source.
So a vendored mirror can be a legitimate source posture, but it is not proof of local fork progress or replacement readiness.

That means P-0535 should record source-route posture without pretending to prove source parity or architectural readiness by itself.

### 3. Imported signals age, while exceptions get sticky

Crates.io now exposes richer imported context like Trusted Publishing Only Mode, SLOC, and `pubtime`, and broader Rust/Foundation work keeps maintenance and sustainable infrastructure central.
Those imported facts are useful, but they can go stale relative to a long-lived transition plan.
At the same time, typed exceptions can quietly become permanent if the archive does not publish explicit reevaluation status.

So the lane should not stop at “we imported a few signals” or “we wrote an exception once.”
It should say whether the imported evidence is still fresh enough, and whether the exception still has an honest path forward.

## Proposed review objects

### `override-authority.receipt.json`

Purpose: capture **where** a dependency transition is actually declared and how reviewable it is.

Suggested fields:
- `dependency`
- `override_kind` — `manifest_patch`, `config_patch`, `source_replacement`, `vendor_source`, `path_override`, `owned_fork_git`, `manual_process`, `none`
- `declaration_surface` — checked-in manifest, checked-in config, generated config, local config, CI-only config, external tool, manual
- `visibility_class` — `shared_repo_visible`, `generated_shared`, `local_only`, `ci_only`, `manual_review_required`
- `source_posture` — `registry`, `mirror`, `vendor_subset`, `fork`, `path_checkout`, `internal_source`
- `shared_reviewability`
- `notes`

### `signal-freshness.report.json`

Purpose: show whether imported ecosystem signals are still timely enough to support the current transition story.

Suggested fields:
- `dependency`
- `freshness_verdict`
- `signals[]` with:
  - `source`
  - `signal_kind`
  - `imported_at`
  - `expected_refresh_window`
  - `status` — `fresh`, `aging`, `stale`, `superseded`, `manual_review_required`
  - `notes`
- `notes`

### `exception-reevaluation.report.json`

Purpose: keep exceptions from silently becoming permanent folklore.

Suggested fields:
- `crate`
- `entries[]` with:
  - `dependency`
  - `lane`
  - `exception_class`
  - `reevaluation_verdict` — `active`, `approaching_review`, `expired`, `stale_context`, `exit_ready`, `manual_review_required`
  - `review_due`
  - `blocking_reasons`
  - `notes`
- `notes`

## Suggested workflow

### `cargo dep-lifecycle capture`
Emit the existing lane/seam/transition artifacts plus:
- `override-authority.receipt.json`
- `signal-freshness.report.json`
- `exception-reevaluation.report.json`

### `cargo dep-lifecycle doctor`
Flag:
- local-only or CI-only overrides that masquerade as shared policy,
- source-replacement routes that are being overread as fork progress,
- imported signals beyond their review window,
- exceptions whose review dates are near or past due,
- and transition plans whose imported context no longer matches current reality.

### `cargo dep-lifecycle diff`
Compare two bundles and classify:
- `override_became_local_only`
- `override_became_repo_visible`
- `signal_became_stale`
- `exception_expired`
- `exception_became_sticky`
- `manual_review_required`

## Receiver-facing value

### For maintainers
It becomes easier to say whether a fork/path/vendor move is real shared posture or just local/testing state.

### For reviewers
It becomes easier to separate “good imported signals” from “fresh enough imported signals” and to tell whether a waiver is still honestly temporary.

### For downstream adopters
They get one portable answer to whether the dependency transition they are depending on is visible, current, and still governed.

## MVP boundaries

### Include
- override visibility and authority
- imported-signal freshness
- exception reevaluation status
- portable bundle inventory

### Exclude
- proving source equivalence
- deciding replacement priority automatically
- vulnerability scanning replacement
- mirrored-registry correctness proofs

## Good proving grounds

1. a local `.cargo/config.toml` patch used for a fork test that should not count as shared lifecycle posture,
2. a vendored mirror or source-replacement route that still does not imply architectural fork progress,
3. a restricted-lane exception whose imported trust/support context has aged past the review window,
4. a portable support bundle that keeps override visibility, signal freshness, and exception reevaluation separate.
