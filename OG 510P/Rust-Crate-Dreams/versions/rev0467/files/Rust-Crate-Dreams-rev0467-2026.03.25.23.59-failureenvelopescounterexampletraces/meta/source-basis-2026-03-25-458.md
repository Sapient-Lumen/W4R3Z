# Source basis note — 2026-03-25 (458)

This pass was a **product-blueprint and maturity-ladder** pass.
It did not aim to prove that brand-new top-ranked lanes exist.
It aimed to check whether current Rust ecosystem signals justify turning the existing top lanes into more concrete build programs.

## Facts imported directly

1. The 2025 Rust survey still shows significant pain around resource usage / compile time / debugging / crate choice and documents the survey size and timing.
2. The March 2026 challenges post still highlights async difficulty, safety-critical tooling maturity issues, and other ecosystem pain.
3. The debugging survey explicitly states that debugging quality varies across debuggers and operating systems.
4. crates.io now exposes stronger trust and publication controls, including Trusted Publishing Only Mode.
5. docs.rs exposes build metadata, rustdoc JSON, and build behavior caveats; docs.rs default targets changed in October 2025.
6. The 2026 goals slate includes work such as public/private dependencies, Cargo SBOM precursor stabilization, cargo-semver-checks integration work, verifiable mirroring, libtest JSON, open namespaces, and build-related work.
7. Community ecosystem hubs still show that web and geospatial have meaningful centers of gravity, GUI remains more fragmented, and local-first has credible active substrate.

## Main inferences from those facts

1. The archive still does **not** need a fresh umbrella frontier reset.
2. Current official substrate is now strong enough that the leading control-plane lanes deserve **clearer product blueprints**.
3. The most practical missing contribution is still often a crate that packages evidence into reviewable acceptance packets, not a crate that tries to replace an entire domain ecosystem.
4. A new archive-level maturity ladder is warranted because “important” and “ready for `1.0` semantics” are different questions.

## Open questions kept open

- How much of the acceptance-packet vocabulary should be shared across lanes versus left lane-specific?
- Is a separate repo-level `archive-state.json` enough for machine-memory hygiene, or will the archive later need a richer manifest/index layer?
