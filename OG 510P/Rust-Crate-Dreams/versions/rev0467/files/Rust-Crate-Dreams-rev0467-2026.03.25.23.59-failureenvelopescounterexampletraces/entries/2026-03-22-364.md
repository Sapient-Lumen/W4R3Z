# Entry 364 — MC/DC coverage evidence deepened around decision authority, construct support, and independence-pair lineage for P-0433

This pass deepened **P-0433 MC/DC Coverage Workbench Kit** instead of adding another general coverage dashboard, another `cargo-llvm-cov` wrapper, or another assurance-case shell.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the Rust 2026 flagship themes now explicitly include **implement MC/DC coverage support** in the Safety-Critical Rust milestone set;
- the rustc book already documents a real source-based coverage workflow via `-C instrument-coverage`, but still routes detailed mode selection through unstable `-Z coverage-options`;
- `cargo-llvm-cov` already exposes `--branch` and `--mcdc`, but still labels them unstable;
- and Rust’s own branch-coverage limitations issue now publishes a concrete construct taxonomy, including unsupported or caveat-heavy cases such as individual `match` arms, or-patterns, `?`, `.await`, and macro-generated branches.

Together these make one conclusion stronger: the worthy crate here is not just “run coverage and export percentages”.
It is a crate that helps other people inspect **what decisions were actually in scope, which construct classes were supported, whether independence pairs were really demonstrated, and what evidence lineage backs that claim**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still **not** another runner.
It is a **stable support-contract layer** above coverage runners, LLVM reports, and future upstream MC/DC maturation.

This pass promotes seven P-0433 review objects into first-class status:

1. **decision-authority receipt** — what decision inventory was authoritative;
2. **construct-support matrix** — which branching forms were supported, unsupported, or excluded;
3. **independence-pair report** — whether each condition has witnessed independence evidence;
4. **caveat-basis receipt** — which unstable/toolchain/known-limitation facts constrained the result;
5. **evidence-lineage receipt** — which concrete runs and merged profiles back the conclusion;
6. **MC/DC drift diff** — what changed across revisions/toolchains/policies;
7. **MC/DC support-bundle manifest** — the compact handoff artifact joining those truths.

## Why these objects matter

Current Rust coverage substrate is finally concrete enough that the archive should stop flattening MC/DC-facing investigations:

- a source-based coverage run can be real without proving full MC/DC support;
- a branch-coverage result can still leave key decision families out of scope;
- a tool can expose `--mcdc` while still needing an explicit caveat basis because the lane remains unstable or partial;
- and an independence verdict is weaker if it cannot be traced back to concrete tests and merged profile data.

## New archive-level stance

For safety-critical coverage work, the archive should now prefer this layering:

1. **P-0433** for decision authority, construct support, independence evidence, caveat basis, and lineage;
2. runner/workflow tools such as `cargo-llvm-cov` for practical execution substrate;
3. rustc/LLVM coverage for instrumentation and report generation substrate;
4. broader verification-campaign or assurance-case lanes only after the MC/DC support bundle stays honest on its own.

That keeps the portfolio from minting another crate that merely says “coverage ran” without clarifying what support class or decision inventory the result actually had.

## What should count as a worthy crate contribution after this pass

A worthy MC/DC-facing contribution should now be able to answer all of these cleanly:

1. **What decision inventory was authoritative?**
2. **Which construct classes were supported, unsupported, or excluded?**
3. **Which conditions have witnessed independence pairs?**
4. **What caveat basis constrained the result?**
5. **What concrete run lineage backs the verdict?**

If a candidate crate cannot answer those questions, the archive should usually treat it as coverage folklore rather than a serious support contract.
