# Entry 313 — crate resource support deepened for budget topology, clone sharing, and aggregate-bound honesty

This pass deepened **P-0521 Crate Resource Surface Pack Kit** rather than opening another adjacent queue, pool, or metrics lane.

## Why this lane earned another serious pass

The archive already had sharper answers for:

- where admission happens first,
- who owns backlog,
- what can shrink effective capacity,
- and what callers experience at the boundary.

What still needed a more disciplined answer was the topology question:

> “Does this limit apply per clone, per client family, per host, per connection, per runtime, or to the whole process?”

Current Rust crate docs now make that question concrete enough to build around.

## What moved this time

The key planning move was to stop treating “a numeric bound exists” as sufficient resource truth.

This pass elevated four review objects more explicitly:

1. **budget topology** — where the visible bound actually lives;
2. **sharing behavior** — whether clones share one budget or multiply it;
3. **multiplication axis** — which deployment/runtime dimension scales total retained state;
4. **aggregate-bound posture** — whether the crate can state a true total or only a per-scope bound.

## Main judgment after the pass

A worthy crate-authored resource contract should not only say that something is “bounded”.
It should also say:

- whether clones share or multiply the waiting room,
- whether the number is per host or per connection,
- which deployment axis scales total retained state,
- and when an aggregate process-wide bound is honestly unknowable without extra topology facts.
