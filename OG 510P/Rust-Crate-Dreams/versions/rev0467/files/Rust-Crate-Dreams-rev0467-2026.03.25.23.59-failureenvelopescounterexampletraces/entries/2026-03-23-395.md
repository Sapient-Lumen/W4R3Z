# Entry 395 — async runtime assurance deepened into a service-topology and capability-route lane

This pass stayed inside an already-important frontier rather than opening another proposal family.
It deepened:

**P-0532 Async Runtime Assurance Profile Kit**.

## Why this lane earned another serious refresh now

Fresh primary signals make the seam sharper than a generic “runtime choice” story:

- the March 2026 Rust challenges post still says async complexity and runtime lock-in are real ecosystem pain points;
- the January 2026 safety-critical post explicitly says teams need requirements for a safety-case-friendly async runtime;
- Tokio’s current runtime docs distinguish the scheduler from **resource drivers**, say hand-configured runtimes do **not** enable I/O/time drivers by default, and document that some types such as `Sleep` and `TcpStream` require a runtime context;
- Embassy’s current docs keep the executor, integrated timers, and HAL-provided time-driver route meaningfully separate;
- RTIC’s current book says hardware scheduling and software-task async executors are generated separately, with dispatchers and timer-queue behavior tied to priority levels and target constraints;
- `async-compat` and `async_executors` prove that bridge/adaptation demand is real, but their own docs also show that many bridges are about **context** or **trait** compatibility rather than erasing runtime-capability dependencies;
- and `async-std` now explicitly recommends migrating to `smol`, which is a good reminder that runtime branding is not a stable portability guarantee by itself.

Together those sources say the missing value is no longer just:

> “Which runtime family did you choose?”

It is now:

> “Which async services are actually present, where do they come from, how are they activated, and what bridge debt remains if you cross runtime families?”

## Main judgment after the refresh

**P-0532** is now stronger as a **service-topology and capability-route support lane** than as a generic runtime profile note.

That means the proposal should explicitly own:

- `runtime-service-topology.receipt`,
- `capability-route.receipt`,
- `compatibility-bridge.report`,
- and runtime bundles that keep runtime family, service providers, activation routes, and bridge debt separate.

It should **not** try to own:

- all async portability abstractions,
- all library-level async trait compatibility,
- all target-support/toolchain truth,
- or a universal runtime-neutral execution layer.

## What should count as a worthy crate contribution in this lane now

A worthy async-runtime crate should hand other people:

1. **one runtime profile** that says what runtime family and shutdown/evidence posture are in play,
2. **one service-topology receipt** that says where spawning, time, I/O, blocking, or signal services actually come from,
3. **one capability-route receipt** for each support-sensitive async capability a downstream crate depends on,
4. **one compatibility-bridge report** that says what an adapter actually bridges and what lock-in remains,
5. **one portable bundle** another team can reopen later without reconstructing runtime folklore from docs and issue threads.

If a candidate crate cannot do those things, the archive should usually treat it as substrate, adapter, or convenience glue — not the missing epic support-contract layer.
