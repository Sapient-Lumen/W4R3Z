# Entry 311 — cli-surface-contract-kit added for command surface, output modes, terminal posture, and exit semantics

This pass added a new top-level proposal: **P-0531 CLI Surface Contract Kit**.

## Why this lane earned a slot

The archive already had better answers for:

- example / first-success support,
- test snapshots and CLI assertion substrate,
- guidance/error-channel support,
- diagnosis / self-check bundles,
- and desktop / TUI / text-input product engineering.

It still lacked one receiver-facing answer to a common tooling question:

> “What does this command actually promise on stdout, stderr, JSON mode, color, prompts, progress, and exit codes?”

Current Rust CLI substrate now makes that absence concrete enough to justify a dedicated lane.

## What moved this time

The main planning move was to treat **CLI behavior as a support contract layer**, not as parser setup or snapshot-test folklore.

This pass therefore promoted four review objects to first-class status:

1. **command-surface truth** — the command/subcommand/flag surface, stability notes, and shell-doc coverage;
2. **output-mode truth** — human versus machine-readable modes, framing, and stdout/stderr ownership;
3. **terminal-posture truth** — TTY detection, color policy, progress visibility, prompting, and editor/pager handoff;
4. **exit-semantics truth** — success/failure classes and what nonzero outcomes actually mean.

## Why this matters

Without those objects, the ecosystem still permits a common shortcut:

- `clap` can truthfully say “polished CLI experience” with help, color, completions, and value hints,
- `anstream` can truthfully adapt styled output to terminal capabilities and color env vars,
- `indicatif` can truthfully hide progress bars on non-terminals,
- `dialoguer` can truthfully provide confirmation/input/editor prompts,
- and `trycmd` / `snapbox` / `assert_cmd` can truthfully snapshot or assert CLI behavior,
- while a downstream automation or operator still has no compact answer for:
  - which output mode is stable for scripts,
  - whether progress or prompts contaminate stdout,
  - what changes when a TTY disappears,
  - and what each exit code class actually means.

That is not just UX detail.
It is supportiveness.

## Main judgment after the pass

A worthy CLI-support contribution for Rust should now provide more than a parser, a progress bar, or snapshot tests.
It should provide:

- one explicit **command-surface receipt**,
- one explicit **output-mode receipt**,
- one explicit **terminal-mode receipt**,
- and one honest **exit-semantics receipt**.
