# Entry 168 — async determinism stack clarified and simulation kit made fixture-first

This pass again chose **not** to add another narrow proposal.

The better move was to repair an underbuilt, high-leverage frontier that was starting to blur together several different ideas:

- deterministic async/distributed simulation,
- shared-memory schedule exploration,
- hardship/profile suites,
- record/replay debugger workflows,
- and game rollback/state-hashing determinism.

The archive already had proposals in all of those areas.
What it lacked was a cleaner stack story and a more buildable version of **P-0104 Deterministic Simulation Kit**.

## Main judgment

The sharper missing crate here is **not** “a universal deterministic runtime for all Rust async code”.

It is a crate that gives another person a compact answer to:

- which deterministic ingredients were actually controlled,
- which backend produced the run,
- which fault/scenario plan materially shaped the result,
- what transcript or schedule token was captured,
- and whether the failure can be replayed or minimized honestly.

That is a more plausible and more ecosystem-shaped contribution than another backend experiment.

## Why these changes were the right ones

### 1. The proposal had become both important and underbuilt
`P-0104` was already pointing at a real gap, but it still looked more like a good sketch than a handoff-ready crate.
It also still contained stale UI citation markup in durable markdown, which is exactly the sort of repo-memory leak this archive is supposed to resist.

This pass rewrote it into a more honest artifact-first proposal.

### 2. Current Rust substrate makes the missing value clearer
The ecosystem signals are now stronger than they were when this proposal first landed:

- Tokio has real paused-time support.
- `tokio-rs/simulation` still demonstrates the low-level architecture of deterministic time/scheduling/network lanes.
- `turmoil` provides deterministic single-thread multi-host hardship.
- `madsim` demonstrates deeper deterministic-runtime control, but also shows the cost of runtime replacement and crate patching.
- `shuttle` and `loom` prove that replayable schedule exploration matters, while also showing that this is not the same layer as async multi-host simulation.

That means the sharper crate opportunity is now the **portable profile / receipt / transcript / bundle layer above backend diversity**.

### 3. The archive needed stack boundaries, not more blur
Without a boundary note, future revisions were likely to keep mixing together:

- permutation testing,
- simulation backends,
- hardship suites,
- replay debuggers,
- and rollback determinism.

That would make the archive larger while making the ideas less implementable.
The new note should help resist that drift.

### 4. The fixture pack now answers a receiver-facing question
The strongest recent passes in this archive have made proposals concrete by freezing the artifacts they would hand to another person.
This pass brings the async determinism frontier closer to that standard.

The new minimal pack is now explicit:

- simulation profile,
- backend capability receipt,
- fault plan,
- schedule transcript,
- minimization report,
- and simrun bundle manifest.

## New planning stance

For the next few passes, the archive should prefer:

- treating **P-0104** as the cross-backend deterministic simulation **artifact and adapter** story,
- treating **P-0114** as the curated hardship/profile suite story above that substrate,
- treating **P-0073** as the observed-execution replay/debugger story,
- and treating **P-0066** as the game rollback/state-hashing determinism story.

It should **not** drift back into a fuzzy “one crate solves deterministic async” framing.
