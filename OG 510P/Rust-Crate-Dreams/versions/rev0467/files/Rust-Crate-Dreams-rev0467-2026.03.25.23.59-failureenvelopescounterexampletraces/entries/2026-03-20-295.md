# Entry 295 — spiffe-identity-kit sharpened around identity-source truth, trust-domain policy, peer-identity handoff, and rotation-state evidence

This pass returned to **P-0134 spiffe-identity-kit** because the archive had long recognized workload identity as strategically important, but the original proposal still left one dangerous blur available:

> a crate could say it “supports SPIFFE/SPIRE” while saying almost nothing about **where identity comes from**, which **trust domains are really accepted**, whether the **application can see peer identity**, or how **rotation/failure posture** actually behaves at runtime.

## What moved this time

Several current ecosystem signals make that blur much harder to excuse:

- official SPIFFE docs now point Rust users to `spiffe` for Workload API access and `spiffe-rustls` for TLS/mTLS integration;
- the `spiffe` crate now exposes high-level `X509Source` and `JwtSource` watchers with automatic reconnection and rotation handling;
- `spiffe-rustls` builds live `rustls` client/server configs from `X509Source`, so new handshakes can pick up rotated SVIDs and bundles without restart;
- `spiffe-rustls` also keeps trust-domain policy and peer-ID authorization explicit, including federation-aware bundle selection rules;
- `spiffe-rustls-tokio` now returns `(TlsStream, PeerIdentity)` after successful handshakes;
- `spire-api` now covers SPIRE’s Delegated Identity API for constrained environments;
- and the SPIFFE Workload API and federation specs keep source basis and trust-domain scope as separate truths rather than one generic “mTLS works” claim.

That combination means the missing crate is no longer best described as “a Rust SPIFFE client” or “a simpler rustls adapter.”
It is better described as a **reviewable workload-identity contract** above today’s serious but still fragmented substrate.

## Main planning move

This pass promoted four first-class review objects for **P-0134**:

1. **identity-source truth** — whether a subject is a live Workload API X.509/JWT identity, a delegated SPIRE identity, or a static/dev identity,
2. **trust-domain-policy truth** — whether verification accepts any bundle-set domain, a bounded allowlist, or local-only trust,
3. **peer-identity handoff truth** — whether the application receives a peer SPIFFE ID or whether identity remains verifier-only,
4. **rotation-state truth** — whether new handshakes use updated material and what posture remains when the identity source becomes unavailable.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say that the service uses SPIFFE,
- a TLS demo can truthfully show mutual authentication,
- a platform team can truthfully say rotation is supported somewhere,
- and a downstream team can still be unable to answer whether they are looking at a **live agent-backed identity**, a **delegated/constrained identity path**, a **static bootstrap identity**, a **bundle-set-wide federation stance**, or an **application-visible peer identity handoff**.

That is not a wording nit.
It is the difference between “Rust has workload identity crates now” and “another team can review what identity and trust posture they are actually depending on.”

## Main judgment after the pass

A worthy workload-identity contribution for Rust should now provide more than protocol correctness and more than one working TLS adapter.
It should provide:

- one explicit **identity-source receipt**,
- one explicit **trust-domain-policy receipt**,
- one explicit **peer-identity receipt**,
- one explicit **rotation-state report**,
- and one compact way to diff those artifacts across deployment modes and release upgrades.

That is a better answer to the current ecosystem than either:

- “just use the SPIFFE crates,”
- “just wire rustls to the agent,”
- or “just state the trust domain in docs and hope the rest is obvious.”
