# Entry 332 — OpenAPI 3.1 / JSON Schema toolchain kit deepened for dialect identity, ref-resolution route, projection policy, compatibility profile, and semantic-diff authority

This pass deepened **P-0224 OpenAPI 3.1 + JSON Schema 2020-12 Toolchain Kit** instead of adding another parser crate, another generator wrapper, or another vague API-governance note.

## Why this lane earned another serious pass

The archive already knew OpenAPI 3.1 and JSON Schema 2020-12 mattered.
What it still lacked was a build-shaped answer for *which truths belong in one reusable Rust support contract* rather than being scattered across parsers, validators, code-first emitters, and generator-specific scripts.

Current substrate is now strong enough to make that precise:

- OpenAPI 3.1 now publishes its own Schema Object dialect layered on JSON Schema Draft 2020-12;
- JSON Schema Draft 2020-12 now makes bundling guidance, dynamic references, and vocabulary posture much more explicit;
- `openapiv3_1` and `oas3` show that Rust now has real 3.1 parser/model substrate;
- `jsonschema` gives Rust real validator and external-ref substrate;
- `utoipa` shows code-first OpenAPI 3.1 emission is real, but still not the same thing as a reviewable post-emission contract.

That means a worthy crate here should not merely say "supports OpenAPI 3.1".
It should say **which dialect it assumed, how refs were resolved, what projection it produced, which compatibility profile it checked, and whether a diff is merely descriptive or policy-backed**.

## What moved this time

The main planning move was to stop treating "OpenAPI toolchain support" as one blob.

This pass elevated five review objects into first-class status for **P-0224**:

1. **dialect identity** — OpenAPI Schema Object dialect, JSON Schema base, and vocabulary posture;
2. **ref-resolution route** — entry document, base URI, fetch policy, mirror/cache path, and refusal-to-fetch facts;
3. **bundle / projection policy** — review bundle vs codegen/docs/gateway projection;
4. **compatibility profile** — named downstream consumer expectations separate from structural validity;
5. **semantic-diff authority** — descriptive change facts separate from policy verdicts.

## Why this matters now

The ecosystem evidence is now sharp enough that the missing layer is no longer vague:

- OpenAPI 3.1 itself and its dialect docs make Schema Object dialect identity explicit;
- JSON Schema 2020-12 makes bundling and dynamic-reference posture explicit;
- Rust parser/model and validator crates are now good enough that the next missing value is not "can we parse this at all?";
- the practical gap is now whether another team can review, reproduce, and compare toolchain decisions without guessing what happened.

That means a worthy crate should not let one green "valid" bit silently over-claim dialect fidelity, consumer compatibility, or breaking-change authority.

## Main judgment after the pass

A worthy OpenAPI 3.1 / JSON Schema toolchain crate should now provide more than parsing and generic validation.
It should also provide:

- one explicit **dialect-profile receipt**,
- one explicit **ref-resolution receipt**,
- one explicit **bundle-projection report**,
- one explicit **compatibility-profile receipt**,
- one explicit **semantic-diff report**,
- plus the already-needed manifest, normalized document, and portable review bundle.
