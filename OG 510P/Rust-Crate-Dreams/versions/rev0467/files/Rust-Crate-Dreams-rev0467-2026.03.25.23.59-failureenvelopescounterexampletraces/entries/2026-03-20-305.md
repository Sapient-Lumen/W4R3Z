# Entry 305 — cargo-config-layer-receipt-kit sharpened around invocation-basis and replayability truth

This pass returned to **P-0474 Cargo Config Layer Receipt Kit** because the archive still left one familiar and costly blur too available:

> a team could show another team a merged effective Cargo config and an origin trace, while still leaving them unable to tell whether it came from one real invocation or a later reconstruction — and whether the exported bundle was actually replayable after redaction.

## What moved this time

Several current Cargo and Rust signals make that blur harder to excuse:

- Cargo’s config reference now explicitly documents hierarchical probing, merging, env overrides, `--config` overrides, include graphs, and distinct path roots for env / CLI values versus config-file values;
- Cargo 1.94 stabilized the top-level `include` key, making shared config graphs and optional per-user includes a stable operational surface rather than a nightly-only curiosity;
- Cargo’s docs are explicit that `--config` values take precedence over env, and env takes precedence over config files;
- Cargo’s path rules are explicit that env and `--config KEY=VALUE` paths are relative to the current working directory, while config-file paths are relative to the config-definition root;
- Cargo’s credentials model explicitly treats tokens as sensitive credentials-file data, while credential-provider aliases and provider commands add even more redaction-sensitive context;
- nightly `cargo config get` exists, but still as inspection substrate rather than one durable replayable review artifact.

That combination means the missing crate is no longer best described as “some better Cargo config viewer”.
It is better described as a **reviewable per-invocation Cargo config contract** above today’s config inspection substrate.

## Main planning move

This pass promoted two newly first-class review objects for **P-0474**:

1. **invocation-basis truth** — what exact command context, cwd, explicit `--config` fragments, and observed env overrides were part of the described config surface;
2. **replayability truth** — whether the exported bundle is actually replayable, merely inspectable, local-only, or redaction-broken once secret-bearing and path-bearing facts are removed.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “here is the effective config and the origin trace”,
- another maintainer can truthfully say “the bundle is redacted and safe to attach”,
- a reviewer can truthfully say “the config graph includes project, user, and optional include files”,
- and a downstream team can still be unable to tell whether the key winner came from `--config`, whether a path was cwd-relative instead of config-root-relative, whether a secret-bearing provider alias was essential to replay, or whether the bundle was reconstructed after the fact.

That is not a wording nit.
It is the difference between “Cargo config can be inspected” and “another team can review the actual invocation/config claim they are being asked to trust”.

## Main judgment after the pass

A worthy Cargo config support contribution for Rust should now provide more than an effective-config dump, an origin trace, and a redaction pass.
It should also provide:

- one explicit **invocation-basis receipt**,
- one explicit **replayability report**,
- and one honest separation between **inspectable support bundles** and **replayable config bundles**.
