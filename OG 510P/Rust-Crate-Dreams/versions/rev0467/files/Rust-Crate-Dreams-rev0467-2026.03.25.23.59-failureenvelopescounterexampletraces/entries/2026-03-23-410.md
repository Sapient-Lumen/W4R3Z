# Entry 410 — broad rerank adds a concurrency-contract lane for reentrancy, progress/fairness, cancellation safety, and execution-context truth

This pass went broad again instead of only deepening the current top lane.
It re-read the latest archive, checked fresh official/community Rust signals, and asked a stricter question across a wide spread of domains:

> what still looks missing enough — and useful enough to other people — to deserve real crate-shaped attention?

The strongest new answer was a lane the archive had not yet named sharply enough:

**P-0538 Concurrency Contract Kit**.

## Why this lane earned entry now

Fresh signals make one cross-cutting support gap harder to ignore:

- the March 2026 challenges note still says async complexity remains one of the major expert-facing Rust pain points;
- the 2025 State of Rust survey still lists resource usage / compile times among the biggest pain points and keeps debugging in the top tier of complaints, which matters because concurrency mistakes are often discovered late and under poor tooling conditions;
- the February 2026 Rust debugging survey still treats async debugging, visualizers, and broader debugger capability as unfinished work;
- current community discussion explicitly asks for better documentation around **forward progress guarantees** and **reentrancy**, while also calling out async cancellation safety and production observability gaps;
- Tokio documents fairness and cancellation behavior for `Mutex`, `RwLock`, `Semaphore`, and `select!`, but those guarantees are lane-specific and easy to misremember;
- `parking_lot` documents eventual fairness, `ReentrantMutex`, and deadlock detection experiments, but that vocabulary does not map cleanly onto Tokio or `std` by itself;
- and `std` still exposes blocking and poisoning semantics for `Mutex`, while re-entrant locking in the standard library remains nightly-only experimental.

Taken together, that evidence says the missing value is not another lock implementation, another runtime abstraction, or another generic async helper.
It is a **receiver-facing concurrency support contract** that helps maintainers and integrators answer:

- is this surface re-entrant,
- what progress or fairness class does it actually promise,
- what does cancellation do to waiters,
- which execution contexts are legal or illegal,
- and where the claim ceiling stops.

## Main judgment after the refresh

**P-0538** should be treated as a new top-frontier lane, but not the new number one.

The archive should currently rank the frontier roughly like this:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**
6. **P-0453 Safety Contract Consumer Kit**
7. **P-0011 Crate Health Contract Kit**
8. **P-0121 FFI Boundary Conformance Kit**
9. **P-0532 Async Runtime Assurance Profile Kit**
10. **P-0484 Toolchain & Target Support Contract Kit**

That ranking says:

- compile-iteration, pathfinding, lifecycle transition, and crate-knowledge still remain the strongest broad opportunities,
- but concurrency-contract work now deserves to sit in the next cluster because it cuts across async, sync, services, GUI, data, CLI, runtime choice, and library adoption.

## What should count as a worthy crate contribution in this lane now

A worthy crate contribution here should give other people:

1. **one reentrancy answer** instead of “probably don’t do that,”
2. **one progress/fairness class** instead of folklore about FIFO, starvation, or eventual fairness,
3. **one wait-cancellation report** instead of hand-wavy “abort-safe” claims,
4. **one execution-context boundary report** instead of hidden panic/block/deadlock traps,
5. **one portable support bundle** that can be attached to docs, CI, bug reports, or reviews,
6. **one import vocabulary** that channel, resource, runtime, debugging, and docs-support lanes can reuse without silently replacing them.

If a candidate crate cannot export those sorts of artifacts, it is more likely to be:

- a primitive implementation crate,
- a runtime wrapper,
- a deadlock detector,
- a model-checking harness,
- or docs prose.

Those may still be useful, but they are not the missing support-contract layer this pass found.
