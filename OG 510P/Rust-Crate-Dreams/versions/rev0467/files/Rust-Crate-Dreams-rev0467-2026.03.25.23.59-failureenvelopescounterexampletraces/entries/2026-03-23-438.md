# Entry 438 — apply the epic scorecard, keep the practical queue honest, and deepen async support around scenario labs plus archive freshness discipline

This pass again chose **deepen** over **append**.

The archive already has plenty of candidate crates.
What it still needed was a sharper way to answer three repo-level questions:

1. which of the leading proposals still look strongest after applying the archive’s own epic-crate bar,
2. what one theory-heavy proposal now deserves more implementation-shaped planning rather than more abstract praise,
3. and what repo hygiene will keep future LLM passes from drifting, handwaving freshness, or reranking everything every time.

## Main judgment

Three repo moves were worth making now.

### 1. Apply the epic scorecard to the current frontier

The archive already had an epic-crate bar.
It did **not** yet have a compact applied scoring pass over the current leaders.

That gap mattered because the repo now has enough strong proposals that “sounds important” is no longer a sufficient promotion rule.
A serious pass should say:
- which crates win on **receiver-facing value**,
- which ones win on **portable artifacts and review surfaces**,
- which ones win on **cross-domain leverage**,
- and which ones are strong in principle but still less immediate to ship.

The new scorecard application keeps the broad judgment intact:
- **Pathfinder** is still a top ecosystem need because the March 2026 challenges post again says users need help knowing which crates do what they need, which crates they can trust, and which are best for them.
- **Debuggability** remains near the top because debugging has dedicated official survey work and still shows up as a meaningful productivity pain.
- **Concurrency Contract** belongs back near the very top of the *salience* board because current Rust challenges and 2026 goals keep async as a front-line ecosystem difficulty.
- **Docs.rs parity**, **dependency lifecycle**, **build-dir transition**, **toolchain/target support**, and **crate knowledge packs** remain the strongest adjacent control-plane lanes.

But the scorecard also helps keep one subtle distinction explicit:

- **salience rank** is not identical to
- **practical next-build queue**.

That matters because some crates are extraordinarily important but still more schema- and fixture-heavy than immediate cargo-plugin candidates.

### 2. Give P-0538 a scenario-lab build plan, not just more semantic categories

The repo had already given **P-0538 Concurrency Contract Kit** a rich vocabulary.
What it still lacked was a compact answer to:

> what should a buildable `0.1` give another engineer besides schema files?

The next missing layer is a **scenario lab**.
Not another channel wrapper.
Not another async helper.
A scenario lab with portable bundles showing how concurrency claims survive across:
- wake-only permits,
- latest-value state,
- bounded work queues,
- lagging fanout,
- local-only execution contexts,
- blocking bridges,
- and sync lock recovery postures.

That is a much more credible route to a worthy crate contribution than adding another “best async primitive” explainer.

### 3. Add explicit freshness discipline for future archive passes

The repo is now large enough that future work needs a tighter rule for how current web facts get imported.
Without that, it becomes too easy for later passes to:
- silently reuse stale assumptions,
- browse too broadly without preserving what changed,
- or treat one fresh blog post as if it automatically reranks the whole frontier.

The new freshness policy adds a small **core watch set** and a lightweight refresh contract:
- record what volatile sources were checked this pass,
- separate evergreen docs from fast-moving signals,
- preserve **salience** and **shipability** as separate judgments,
- and only rerank when new sources actually changed the decision basis.

That is archive hygiene, not crate design, but it is worth repo space because this archive is now a multi-pass research instrument.

## What the new planning says a worthy crate should provide other people

This pass strengthens one repo-wide rule:

A serious crate should provide **another person** at least one of these:
- a decision receipt,
- a support/capability contract,
- a migration adapter plan,
- a diffable evidence bundle,
- a scenario pack that travels across issue triage and release review,
- or a machine-usable knowledge artifact with clear claim ceilings.

If it only exports one nicer API, one ranking page, or one vague assistant shell, it probably still belongs below the current control-plane frontier.
