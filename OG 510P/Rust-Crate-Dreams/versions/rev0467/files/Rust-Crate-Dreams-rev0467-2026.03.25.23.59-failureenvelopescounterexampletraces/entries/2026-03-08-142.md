# Entry 142 — host/target config scope is its own missing layer

This pass **did** add a new top-level proposal.

The archive already had strong proposals for broader target support, linker-lane diagnosis, compile-time-deps parity, and build-script UX.
What it still did **not** isolate cleanly was the question:

> which config applied to host artifacts, which applied to target artifacts, and when did that change only because command shape or Cargo scope rules changed?

## Main judgment

The missing value is not another linker wrapper and not another generic cross-compilation helper.
It is the **host/target config scope contract and diagnosis layer** above Cargo’s existing config knobs.

That means the right contribution here is:

- not another config generator,
- not a sandbox runner,
- not a docs.rs clone,
- but a conservative crate that can capture intended scope, record observed scope, classify scope drift, and emit a portable review bundle.

## New planning stance

Read this frontier as a stack:

1. broader toolchain and target support posture,
2. tool-only / editor-oriented compile surfaces,
3. linker-lane choice and diagnosis,
4. host/target config scope intent and observation,
5. mixed-build drift and support bundles.

**P-0505** occupies layers 4–5.
It should import from adjacent layers, not absorb them.

## Archive-level lesson

Once Cargo’s docs start making a confusing behavior explicit, the next missing crate may be the one that turns that behavior into a **portable contract, receipt, and diff** rather than another wrapper or another explainer blog post.

Future passes should resist collapsing toolchain posture, compile-time-deps parity, linker lanes, rustdoc quirks, and host/target scope into one fuzzy “Cargo build doctor” story.
