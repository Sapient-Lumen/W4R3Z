# Entry 314 — debuggability-support-contract-kit deepened for backend coverage, capability ceilings, and manual-review honesty

This pass deepened **P-0486 Debuggability Support Contract Kit** rather than opening another adjacent debugger frontend, crash backend, or IDE integration lane.

## Why this lane earned another serious pass

The archive already had sharper answers for:

- build/profile posture,
- symbol sidecar layout,
- visualizer asset presence,
- artifact handoff/retention,
- and source-lookup / path-hygiene consequences.

What still needed a more disciplined answer was the backend question:

> “Which debugger families, operating systems, versions, and capability classes were actually checked, and which claims are still only inferred from artifacts?”

Current Rust signals now make that question concrete enough to build around.

## What moved this time

The key planning move was to stop treating “symbols exist” or “a NatVis/GDB visualizer was embedded” as sufficient debuggability truth.

This pass elevated three review objects more explicitly:

1. **debugger-family coverage truth** — which debugger/OS/version lanes were directly observed, artifact-inferred only, declared only, unsupported, or still manual-review-only;
2. **capability ceiling truth** — whether a backend claim covers only basic symbol loading, or also type visualizers, async debugging, and Rust expression evaluation;
3. **portable-claim ceiling truth** — what the crate can honestly claim across backends without pretending one successful artifact posture proves uniform debugger support.

## Main judgment after the pass

A worthy debuggability-support crate should not stop at symbol discovery, `pdb` / `dSYM` / `dwo` handoff, or visualizer assets.
It should also provide:

- one explicit **debugger-backend-coverage report**,
- one honest **capability ceiling** per debugger family,
- and one conservative **portable claim ceiling** when some backends or advanced capabilities still require manual review.
