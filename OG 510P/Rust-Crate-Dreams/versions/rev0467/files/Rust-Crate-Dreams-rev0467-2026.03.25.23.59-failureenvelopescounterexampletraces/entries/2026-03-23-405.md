# Entry 405 — compile-time containment now needs ambient-input receipts, sanitization-mode receipts, and launcher-route honesty

This pass deepens an already-promising containment lane instead of adding another backend-specific sandbox wrapper, another proc-macro-only helper, or another generic supply-chain scanner.
It sharpens:

**P-0107 Cargo Sandbox & Capability Policy Kit**.

## Why this lane earned another serious refresh now

The archive already had a stronger story for:
- policy authority,
- actor capability scope,
- enforcement mode,
- exception ownership,
- and policy drift.

What it still left too easy to flatten was a different operational question:

> “Even if a compile-time actor did not get obvious filesystem or network grants, what ambient inputs still flowed in, how were they sanitized, and what wrapper/launcher route actually stood between that actor and the host?”

Current primary sources make that split unusually concrete:

- the sandboxed-build-scripts goal still treats file, network, and process access as the visible permission surface, but explicitly ties sandboxing to determinism and future caching work;
- Cargo’s own env/config docs still say a very large environment surface exists and that `RUSTFLAGS` / `build.rustflags` are shared with build scripts and proc macros unless `--target` is used;
- Cargo’s permanently-unstable `--compile-time-deps` flag confirms that build scripts and proc macros form a meaningful compile-time-only lane;
- Cargo’s long-standing env-sanitization issue says inherited parent env vars hurt reproducibility because it is not obvious which ones build scripts actually use;
- the long-standing host-config issue says target-oriented flags like sanitizers and coverage can accidentally leak into host-built build scripts;
- old-but-still-relevant release notes record that build scripts lost `env!("OUT_DIR")` because that value was wrong at build time under cross-compilation;
- `cargo-sandbox` now shows a real launcher/interceptor route, explicitly refuses project-local config, warns about project-local `rust-toolchain.toml` auto-install, and still documents inherited `PATH` / system-file access plus route-mutability limitations;
- and `cackle` proves real value in sandboxing build scripts separately while still admitting proc-macro sandboxing is routed through shared `rustc` and is therefore not granular.

Together those sources say the sharper missing crate is no longer just a policy-and-capability ledger.
It is a reviewable layer for **ambient-input truth**, **sanitization truth**, and **launcher-route truth** above today’s and tomorrow’s sandbox runners.

## Main judgment after the refresh

**P-0107** is stronger when it owns three more receiver-facing truths:

1. **ambient-input truth** — which parent env keys, Cargo-set env keys, path search roots, toolchain selectors, wrappers, and build-script-emitted env channels were actually in play for a compile-time actor or lane;
2. **sanitization truth** — whether those inputs were inherited wholesale, allowlisted, rewritten, deny-by-default, or only partially controlled, and whether project-local opt-out or auto-install routes still remained;
3. **launcher-route truth** — whether the actor ran directly, through a rustc wrapper, through a preload/interceptor route, via a dedicated runner, or only via a shared host lane whose meaning can be mutated by earlier compile-time actors.

That means a worthy crate in this lane should now explicitly own:

- `ambient-input.receipt.json`,
- `sanitization-mode.receipt.json`,
- and `launcher-route.receipt.json`

above the earlier policy-authority / actor-capability / enforcement / exception / drift lane.

It should **not** try to become:
- another OS sandbox runtime,
- a universal proc-macro isolation redesign,
- a full Cargo execution reimplementation,
- or a magical “secure build” badge that hides inherited ambient state.

## What should count as a worthy crate contribution in this lane now

A worthy compile-time containment contribution should now hand other people:

1. **one ambient-input receipt** that says what env/path/toolchain/wrapper channels were actually visible to a compile-time actor instead of pretending only explicit capability grants matter;
2. **one sanitization-mode receipt** that says whether those channels were inherited, allowlisted, rewritten, or deny-by-default and whether project-local opt-out / toolchain auto-install remained possible;
3. **one launcher-route receipt** that says how the actor was actually wrapped, how granular the route really was, and whether earlier build-time actors could still perturb later proc-macro or rustc lanes;
4. **one portable support bundle** that joins those facts with the older authority / capability / enforcement / exception / drift artifacts.

If a candidate crate cannot do those things, the archive should usually treat it as a runner backend, a partial sandbox helper, or a local policy file — not the missing reviewable support-contract layer.
