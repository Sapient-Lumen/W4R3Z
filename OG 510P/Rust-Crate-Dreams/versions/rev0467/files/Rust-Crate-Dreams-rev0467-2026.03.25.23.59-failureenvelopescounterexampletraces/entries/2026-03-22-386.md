# Entry 386 — Debugger visualizer compatibility deepened around activation route, formatter origin, and portable support bundles for P-0491

This pass deepened **P-0491 Debugger Visualizer Compatibility Kit** again, but in a narrower, more review-critical direction: **activation route, formatter origin, and portable bundle completeness**.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the Rust Reference still keeps `#[debugger_visualizer]` stable, allows multiple visualizer files, and still says embedded NatVis support is limited to `-windows-msvc` targets;
- the rustc dev guide now documents `rust-gdb`, `rust-lldb`, and `rust-windbg.cmd` as support scripts that locate toolchain visualizer scripts and launch debuggers with the right preload arguments;
- that same dev-guide page says `#![debugger_visualizer]` currently works for **GDB and NatVis**, while **LLDB is not currently supported** through that embedded Rust lane and instead points toward separate formatter mechanisms;
- GDB’s current manual still makes `auto-load safe-path` a security gate and says declined files are not loaded when the path is not trusted;
- LLDB’s current formatter architecture still treats formats, summaries, filters, and synthetic children as its own subsystem rather than as Rust-embedded visualizer parity;
- and the 2026 Rust debugging survey still calls out cross-debugger support and high-quality visualizers as active needs, while warning that the debugging experience can regress as debugger versions and Rust internals change.

Together these make one conclusion sharper: a worthy crate here still is not “collect more pretty printers”.
It is a crate that helps other people inspect **what visualizer assets existed, how they were expected to become active, what artifact actually provided the formatter behavior, and what changed between releases**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still a **stable support-contract layer** above debugger assets, launcher scripts, debugger config, and backend-version drift.
But that support contract now needs three additional review objects:

8. **activation-route receipt** — how a visualizer was expected to become active for a backend lane;
9. **formatter-origin receipt** — which asset, wrapper, or debugger-local config is actually the effective formatter source for that lane;
10. **visualizer-support bundle** — one portable manifest that keeps policy, assets, activation, origin, backend verdicts, and drift separate.

## Why these objects matter

Current substrate is now concrete enough that the archive should stop flattening debugger-visualizer support:

- two lanes can both say “visualizer support exists” while one is repo-embedded and the other depends on a toolchain launcher;
- a GDB lane can fail to activate while the asset itself remains present and valid;
- a crate can ship NatVis and GDB assets without that proving anything about LLDB-family formatting;
- and release-to-release drift can come from launcher/origin changes rather than from asset bytes alone.

## New archive-level stance

For debugger-visualizer work, the archive should now prefer this layering:

1. **P-0491** for asset inventory, activation route, formatter origin, backend verdicts, tiny goldens, drift, and support-bundle shape;
2. **P-0486** for broader debuggability posture, sidecars, source materials, and backend capability classes;
3. debugger/toolchain substrate (Rust reference, rustc support scripts, debugger manuals) for the raw platform facts;
4. broader debugger UX or doctor ideas only after the visualizer support bundle stays honest on its own.

That keeps the portfolio from minting another crate that merely says “visualizers are supported” without clarifying whether the effective lane was embedded, script-routed, trust-blocked, or debugger-local.

## What should count as a worthy crate contribution after this pass

A worthy debugger-visualizer contribution should now be able to answer all of these cleanly:

1. **What assets exist and where did they come from?**
2. **Which backend/target lanes are intended?**
3. **How was the visualizer supposed to become active?**
4. **What artifact is actually the formatter origin for that lane?**
5. **What conservative backend verdict was observed?**
6. **What tiny render goldens back the claim?**
7. **What changed between releases or debugger/toolchain versions?**
8. **What exact portable bundle can another maintainer inspect?**

If a candidate crate cannot answer those questions, the archive should usually treat it as debugger folklore rather than a serious support contract.
