# 2026-03-01-15 — Native deps, build.rs quality, OpenAPI glue, and Rust robotics gaps

This entry captures recurring “missing crate” signals in four areas that cut across many real-world Rust projects.

## 1) Native/system dependencies remain underspecified (especially cross-platform)

- The ecosystem still leans on imperative `build.rs` copies that probe `pkg-config`/`vcpkg`, which tends to be error-prone and untested; declarative alternatives like `system-deps` are explicitly discussed as a possible standard, but adoption is uneven.  
  - https://github.com/gdesmott/system-deps/issues/97  
  - https://crates.io/crates/system-deps
- `vcpkg` exists as a Rust build helper and explicitly documents a `cargo vcpkg` workflow, but there isn’t a unified “doctor + policy + cross-compile story” across `pkg-config`, `vcpkg`, and vendoring patterns.  
  - https://docs.rs/vcpkg  
  - https://crates.io/crates/pkg-config
- Windows/MSVC + `pkg-config` availability has been a recurring pain point for a long time, and it still surfaces when `-sys` crates hard-require `pkg-config`.  
  - https://users.rust-lang.org/t/cargo-windows-pkg-config-and-build-dependencies/4595

**Opportunity:** treat native dependency discovery/installation as a first-class workflow with a shared manifest, standardized overrides, and test fixtures.

## 2) build.rs interop is still “folklore”: metadata passing is confusing and brittle

- Cargo’s `DEP_*` and `cargo::metadata` mechanisms are powerful, but documentation clarity and end-user ergonomics are repeatedly questioned.  
  - https://github.com/rust-lang/cargo/issues/7846  
  - https://doc.rust-lang.org/cargo/reference/build-scripts.html
- Users still get stuck trying to pass values across build scripts and crates in practice (even after reading the docs).  
  - https://users.rust-lang.org/t/cant-get-cargo-metadata-work-in-build-scripts/116263
- “build.rs is clunky” stories recur, especially for FFI and platform-specific builds.  
  - https://internals.rust-lang.org/t/build-rs-use-cases-and-stories-sought/9534

**Opportunity:** raise the quality bar for build scripts by making them testable, lintable, and easier to reason about (without waiting for upstream changes).

## 3) Cargo’s build cache & build analysis work suggests new tool substrate

- Cargo explicitly recognizes that `target/` layout complicates caching and that users rely on assumptions; a goal proposes reworking the build dir layout to make caching and CI saner.  
  - https://rust-lang.github.io/rust-project-goals/2025h2/cargo-build-dir-layout.html
- Cargo 1.93 cycle notes structured logging/build analysis goals, reinforcing that a stable(ish) “build session data” substrate is coming.  
  - https://blog.rust-lang.org/inside-rust/2026/01/07/this-development-cycle-in-cargo-1.93/

**Opportunity:** “kits” that consume build-session artifacts and keep CI caching/tools stable across Cargo changes.

## 4) OpenAPI and robotics both show “almost there” ecosystems with missing glue

### OpenAPI
- Longstanding complaints: some generators produce non-idiomatic or weakly typed Rust clients (e.g., futures versioning, typed returns).  
  - https://github.com/OpenAPITools/openapi-generator/issues/6178
- There are serious Rust-native projects (`progenitor`, `paperclip`) but users still ask “what’s the recommended workflow,” suggesting the ecosystem lacks a default, well-lit path.  
  - https://github.com/oxidecomputer/progenitor  
  - https://paperclip-rs.github.io/paperclip/

**Opportunity:** a conformance-focused intermediate representation + compatibility/test harness so codegen outputs are trustworthy and upgrade-friendly.

### Robotics (ROS 2 + Rust)
- Rust remains a second-class citizen in ROS 2 ecosystems in practice; users report missing functionality and churn.  
  - https://users.rust-lang.org/t/i-was-tired-of-ros2-so-i-rewrote-it-in-rust/135139  
  - https://github.com/ros2-rust/ros2_rust/issues/465

**Opportunity:** a “quality kit” that fills the most painful missing pieces (actions/executors/launch ergonomics) with test fixtures and packaging guidance.
