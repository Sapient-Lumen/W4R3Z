# Entry 345 — documentation-example support deepened around doctest manifests, execution modes, and example-support reports for P-0455

This pass deepened **P-0455 Doctest Extraction & Support Contract Kit** instead of adding another docs portal, another docs-quality dashboard, or another “examples are tested” badge.

## Why this lane earned another pass now

Fresh official Rust signals line up unusually well:

- the 2025 State of Rust survey says **online documentation remains the preferred canonical reference** for learning and working with Rust;
- the Rust-for-Linux tooling goal explicitly asks for stable rustdoc features to **extract and customize rustdoc tests**;
- rustdoc already exposes an unstable `--output-format=doctest` mode that emits machine-readable JSON for extracted doctests;
- recent Rust release notes say rustdoc now has stable `--test-runtool` / `--test-runtool-arg` support and target-specific `ignore-*` attributes for doctests;
- and the merged-doctests goal plus current rustdoc flags make execution grouping a real semantic detail rather than invisible implementation trivia.

Together these make one conclusion stronger: a worthy ecosystem contribution here is not just “run `cargo test --doc` in CI.” It is a crate that helps other people understand **which documentation examples exist, what got rewritten, how they were executed, what support class each example actually has, and how that changed over time**.

## Main judgment after the pass

The strongest near-term documentation contribution is **not** another docs renderer and **not** another prose-only docs checker.
It is a **documentation-example support contract** above rustdoc, Cargo, custom runners, and docs.rs.

This pass promotes five P-0455 review objects into first-class status:

1. **doctest manifest** — what rustdoc extracted, where it came from, and how code blocks were classified;
2. **rewrite lineage** — what harness injections, hidden setup shims, or environment-specific rewrites were applied after extraction;
3. **execution mode** — whether an example was standalone, merged, compile-only, ignored, or wrapper-executed, under what runner basis;
4. **docs-example support report** — what other people can actually rely on for each example across host, target, and docs-facing surfaces;
5. **docs-example drift diff** — what changed across toolchains, branches, targets, or policy revisions.

## Why these objects matter

Current substrate is finally specific enough that the archive should stop flattening it:

- docs being canonical reference material does **not** mean the examples are runnable in the environments readers care about;
- docs.rs success is a rendering / build truth, not a doctest-execution truth;
- wrapper/emulator execution via `--test-runtool` changes the meaning of “this example ran” and must stay visible;
- merged doctests can change grouping, failure ownership, and performance characteristics without changing the prose itself;
- and `ignore-*`, `no_run`, `compile_fail`, `cfg(doc)`, and hidden setup lines all affect what a reader may safely infer.

A crate can therefore truthfully say “our examples are tested” while still hiding:

- whether the examples were extracted in a machine-readable way,
- whether custom rewrites were injected for a special environment,
- whether a target-specific ignore posture left a platform effectively unexercised,
- whether success came from render-only/docs.rs posture instead of execution,
- and whether a toolchain change altered grouping or support class.

## New archive-level stance

For documentation-facing work, the archive should now prefer this layering:

1. **P-0455** for the shared documentation-example contract layer,
2. **P-0481** when the hard part is the target-aware runner / emulator / VM profile,
3. **P-0472** when the hard part is docs.rs hosted-build parity and local-vs-hosted drift,
4. **P-0476** when the hard part is coverage / public-API docs debt rather than example support truth.

That keeps the portfolio from minting another crate that merely says “docs are tested” without clarifying extraction, rewrites, execution basis, or support class.

## What should count as a worthy crate contribution after this pass

A worthy docs-example contribution should now be able to answer all of these cleanly:

1. **What examples exist, and exactly where did each one come from?**
2. **What was rewritten or injected after extraction, and why?**
3. **Did an example run, compile only, get ignored, or merely render? Under what runner / grouping mode?**
4. **Which support claims belong to host execution, target execution, docs.rs rendering, or manual-review-only posture?**
5. **Can another engineer compare docs-example posture across revisions without re-deriving the whole setup by hand?**

If a candidate crate cannot answer those questions, the archive should usually treat it as incomplete docs folklore rather than a serious support contract.
