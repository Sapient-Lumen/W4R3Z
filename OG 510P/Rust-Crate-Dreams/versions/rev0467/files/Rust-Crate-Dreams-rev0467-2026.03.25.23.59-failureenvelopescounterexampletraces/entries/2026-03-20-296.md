# Entry 296 — cfg-availability-ledger sharpened around docs-visible versus compile-usable versus doctest-usable truth

This pass returned to **P-0451 Cfg Availability Ledger Kit** because the archive still left one familiar but costly blur available:

> a crate could make an item look available in docs, or even in hosted docs.rs defaults, without giving reviewers one compact answer to whether that same item is actually **compile-usable downstream**, **doctest-usable**, or merely **docs-visible**.

## What moved this time

Several current Rust signals make that blur harder to excuse:

- the Rust project’s 2025H2 `doc_cfg` goal is explicitly about making conditions of item availability more visible to readers;
- RFC 3631 is equally explicit that rendered markers solve the “I can see it but cannot use it” problem only at the **visual-marker** layer, not by duplicating every inactive configuration in docs;
- rustdoc’s advanced-features docs still say `#[cfg(doc)]` can make an item appear in docs even when dependent crates cannot use it the same way, and that this cfg is **not passed to doctests**;
- Cargo’s doctest model is still a separate execution/compilation path driven by rustdoc;
- docs.rs now both hosts rustdoc JSON and warns that `format_version` matters, while also documenting hard hosted-build limits;
- and the October 2025 docs.rs default-target change means the *default visible docs surface* can move even when a maintainer did not change the crate’s public support promise.

That combination means the missing crate is no longer best described as “an availability matrix for targets and features.”
It is better described as a **reviewable conditional-API usability ledger** above today’s rustdoc/docs.rs/Cargo substrate.

## Main planning move

This pass promoted two more first-class review objects for **P-0451**:

1. **usability witness truth** — whether a slice is merely docs-visible, or also same-crate-compilable, doctest-usable, and downstream-compile-usable;
2. **default-surface drift truth** — whether a change in docs.rs defaults or hosted assumptions changed what users see *by default* without proving any new support commitment.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say an item appears in docs,
- a reviewer can truthfully see a `doc(cfg)`-style marker,
- a hosted docs.rs page can truthfully show that item on the default surface,
- and a downstream user can still be unable to compile against it on their target, or fail to use it from doctests, or misread a hosted default-target shift as new real support.

That is not a minor wording issue.
It is the difference between “the documentation has a visibility story” and “another team can review which audience can actually use this API.”

## Main judgment after the pass

A worthy conditional-API contribution for Rust should now provide more than:

- an item-by-item target/feature matrix,
- a displayed gate label,
- or one docs.rs-oriented capture.

It should also provide:

- one explicit **usability witness receipt**,
- one explicit **default-surface drift report**,
- and one compact way to diff “docs-visible”, “doctest-usable”, and “downstream-usable” truth without collapsing them together.

That is a better answer to the current ecosystem than either:

- “rustdoc will show the gate now,”
- “the item is in docs so users can probably use it,”
- or “docs.rs default targets are just presentation details.”
