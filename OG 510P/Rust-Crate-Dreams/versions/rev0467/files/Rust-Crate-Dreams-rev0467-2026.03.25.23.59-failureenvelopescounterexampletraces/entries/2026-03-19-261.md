# Entry 261 — crate test support sharpened around witness lineage, topology honesty, and fixture support levels

This pass did **not** add another test runner, another mock server, another snapshot framework, or another container helper.
It sharpened **P-0523 Crate Test Surface Pack Kit** into a more implementation-ready support crate.

## Why this moved now

The current Rust testing story is no longer empty.
That changes the shape of the missing value.

- The December 2025 Rust vision-doc work explicitly says crates need more **supportive interfaces**.
- The 2025 State of Rust survey still says online docs and code remain the main learning surfaces.
- Tokio already documents paused time for async tests, but it also makes the runtime boundary explicit: paused time requires the `current_thread` runtime, and `start_paused` requires `test-util`.
- `cargo-nextest` now documents recorded runs, replay, and self-contained portable recordings that can be created in CI and replayed locally.
- `assert_cmd` already makes CLI binary testing easier, but its Cargo-binary helpers still only work in integration tests and only with binaries built by `cargo test`.
- `wiremock` already provides isolated mock servers, and its docs explicitly say mock servers should not be shared across tests.
- `testcontainers` already provides isolated integration environments, but its docs also make Docker-API-compatible runtime requirements explicit and note that alternative setups are not equally exercised.
- `trybuild` already covers compile-fail / diagnostic contracts.
- `insta` already supports redactions and sorted redactions for deterministic snapshots.

That combination means the missing crate is no longer “Rust needs testing tools”.
The sharper missing crate is a **crate-authored downstream testing contract** above today’s runners, fixture helpers, mocks, record/replay substrate, compile-fail harnesses, and snapshot tools.

## Main planning move

This pass promoted four review objects to first-class status for **P-0523**:

1. **support level** — whether a fixture or recipe is actually `officially_supported`, merely illustrative, or still manual-review territory,
2. **topology honesty** — which scenarios are really in-process, loopback, containerized, credentialed, or otherwise host-dependent,
3. **witness lineage** — whether a scenario witness came from a direct local run, a compile-fail harness, a portable CI recording, or some weaker/imported source,
4. **normalization boundary** — which snapshot stabilizers help determinism and which ones risk hiding semantics users should still review.

That move matters because the archive had already named the lane, but it had not yet made the **origin of scenario evidence** or the **boundary between official recipe and imported witness** concrete enough to survive real product planning.
This pass fixes that.

## Main judgment after the pass

A worthy test-support crate contribution for Rust should now provide **more than a list of helpers**.
It should provide:

- explicit **support-level truth**,
- explicit **topology-honesty truth**,
- explicit **witness-lineage truth**,
- explicit **normalization-boundary truth**,
- and one compact **test-surface diff** another maintainer or downstream user can inspect without reconstructing support promises from helper modules, CI YAML, and example code.

That is more believable and more ecosystem-multiplying than either:

- “just use `cargo nextest`”,
- “just show a `wiremock` or `assert_cmd` example”,
- or “just point at the tests directory” with no receiver-facing support contract attached.
