# Entry 243 — Apple XCFramework shipkit deepening around slice coverage, package alignment, and trust posture

This pass did **not** invent a new mobile-platform lane.
It sharpened **P-0467 Apple XCFramework & SwiftPM ShipKit** into a more believable shipping-contract crate.

## Why this moved now

The Apple/Rust substrate is now real enough that the missing value is no longer just “please make Rust callable from Swift somehow.”
The sharper gap is a **boring Apple SDK release contract above already-working binding and packaging tools**:

- UniFFI still documents Swift/Xcode integration directly, which means the binding path is real substrate rather than hypothetical.
- `cargo swift` now exists as a current package-building helper in the UniFFI ecosystem, which means release assembly is no longer purely bespoke script work.
- the `xcframework` crate now exists as explicit Rust packaging substrate for Apple XCFramework output.
- Swift Package Manager still treats binary targets as an explicit package boundary with URL/path and checksum semantics for Apple-platform binary artifacts.
- Apple’s own distribution docs still center **XCFramework** bundles for Swift-package binary distribution.
- Apple’s current docs/support surfaces also keep **origin verification**, **privacy manifests**, and in important binary-dependency cases **signatures** visible enough that “the zip was published” is no longer the whole story.

So the gap is not “Rust cannot ship Apple SDKs.”
The gap is that teams still rarely get one **reviewable Apple release bundle** that says:

- which Apple slices actually shipped,
- whether the SwiftPM wrapper and binary target really match the XCFramework inside,
- and what trust posture the release really has around signatures, origin, and privacy-manifest inclusion.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another binding generator, not another Xcode project generator, and not a full notarization or mobile CI platform.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-built Apple SDK releases distributed as XCFrameworks and/or SwiftPM binary targets**,
- above today’s UniFFI / `cargo swift` / `xcframework` / Xcode / SwiftPM substrate,
- with three first-class review objects that were previously still too implicit:
  1. **slice coverage**
  2. **package alignment**
  3. **trust posture**

## Main judgment after the pass

A worthy Apple shipkit should now provide not only a bundle format, but also:

- explicit **slice-coverage truth** (`complete_declared_matrix`, `declared_platform_gap`, `wrapper_claim_exceeds_bundle`, etc.),
- explicit **package-alignment truth** for module names, wrapper/binary-target metadata, zip checksum posture, and deployment-claim drift,
- explicit **trust-posture truth** for signature/origin expectations, privacy-manifest inclusion, and manual-review boundaries,
- and a compact review bundle that another person can inspect without recreating the entire Xcode or CI pipeline.

That is a much sharper and more believable contribution than “yet another Rust-to-Swift helper crate.”
