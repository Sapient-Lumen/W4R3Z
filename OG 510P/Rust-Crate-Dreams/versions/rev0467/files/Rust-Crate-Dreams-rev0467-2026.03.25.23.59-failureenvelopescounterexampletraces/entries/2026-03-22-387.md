# Entry 387 — Doctest extraction/support deepened around extraction basis, grouping comparability, and portable support bundles for P-0455

This pass deepened **P-0455 Doctest Extraction & Support Contract Kit** in a more review-critical direction: **extraction basis, grouping comparability, and portable support bundles**.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the 2025 State of Rust survey still says online documentation is Rust’s preferred canonical reference, even as some learning traffic shifts toward LLM tooling;
- the Rust-for-Linux tooling goal explicitly asks for stable rustdoc features to **extract and customize doc tests**;
- rustdoc’s current unstable-features docs expose `--output-format doctest` JSON with an explicit `format_version`, computed doctest attributes, original code, rewritten code, and wrapper structure;
- the rustdoc docs keep preprocessing rules explicit: hidden lines, crate injection, wrapper insertion, and `#[cfg(doctest)]` all change what gets compiled;
- the Rust 2024 edition guide and current rustdoc doctest docs make merged doctests a real semantic mode, with `standalone_crate` needed for some line-sensitive examples;
- Cargo’s current `cargo test` docs still warn that doctest execution details are not guaranteed and may change, which weakens naive trend claims;
- and current release notes keep cross-compiled doctests, target-specific `ignore-*`, and stable `--test-runtool` / `--test-runtool-arg` in the official substrate.

Together these make one conclusion sharper: a worthy crate here still is not “another docs tool”.
It is a crate that helps other people inspect **what authority produced the docs-example inventory, whether two runs are honestly comparable, and what exact artifacts should travel together in review or support handoff**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still a **stable support-contract layer** above rustdoc extraction, wrapper execution, target-specific ignores, runner imports, and hosted-doc adjacencies.
But that support contract now needs three additional review objects:

6. **extraction-basis receipt** — what exact authority and output format produced the manifest;
7. **grouping-comparison report** — whether two bundles are actually comparable given edition, grouping, target, and attribute drift;
8. **doctest-support bundle** — one portable manifest that keeps basis, rewrites, execution mode, support reports, and imports separate.

## Why these objects matter

Current substrate is now concrete enough that the archive should stop flattening documentation-example support:

- two inventories can list similar-looking examples while one came from first-party rustdoc doctest JSON and the other from a fallback Markdown scrape;
- two green runs can both say “doctests passed” while one is edition-2024 merged and the other is standalone-heavy;
- a cross-target or wrapper-executed run can be valuable without proving the same thing as a local host run;
- and docs.rs rendering can still be relevant while remaining a separate import rather than execution proof.

## New archive-level stance

For documentation-example work, the archive should now prefer this layering:

1. **P-0455** for extraction-basis truth, doctest manifests, rewrite lineage, execution mode, support-class reporting, grouping comparability, drift, and bundle shape;
2. **P-0481** for runner / emulator / `--test-runtool` profile truth;
3. **P-0472** for docs.rs hosted parity;
4. **P-0476** for docs-example coverage / debt review;
5. broader docs portals or search layers only after the doctest-support bundle stays honest on its own.

That keeps the portfolio from minting another crate that merely says “examples are tested” without clarifying whether the authority was nightly rustdoc JSON, a fallback reconstruction, a merged 2024 run, a standalone carve-out, or a wrapper-imported target lane.

## What should count as a worthy crate contribution after this pass

A worthy documentation-example contribution should now be able to answer all of these cleanly:

1. **What exact authority produced the example inventory?**
2. **What did rustdoc rewrite versus what did the environment rewrite?**
3. **What execution mode actually produced the observed result?**
4. **What support class was observed for each example?**
5. **Are two bundles actually comparable or only superficially similar?**
6. **What exact portable bundle can another maintainer inspect?**

If a candidate crate cannot answer those questions, the archive should usually treat it as docs folklore rather than a serious support contract.
