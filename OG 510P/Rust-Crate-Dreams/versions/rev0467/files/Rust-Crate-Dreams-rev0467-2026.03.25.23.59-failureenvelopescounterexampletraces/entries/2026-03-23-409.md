# Entry 409 — rustdoc JSON support now needs source-route receipts, format-window matrices, and normalization-loss honesty

This pass deepens an older but increasingly central machine-consumable docs lane instead of adding another parser wrapper, another docs portal, or another semver-specific adapter.
It sharpens:

**P-0051 Rustdoc JSON Support Contract Kit**.

## Why this lane earned another serious refresh now

The archive already knew that rustdoc JSON mattered for API tooling.
What it did **not** yet make reviewable enough was the difference between:

- where the JSON came from,
- which `format_version` / toolchain windows a consumer really supports,
- and which facts a normalized model still loses.

Current primary sources make that split much more concrete:

- rustdoc still documents `--output-format json` as an **experimental** format behind unstable options;
- Cargo still documents `output-format` for rustdoc as an **unstable** feature;
- docs.rs now hosts rustdoc JSON directly, warns consumers to inspect `format_version`, keeps older format versions around after rebuilds, and notes that releases before 2025-05-23 may not have downloadable JSON until rebuild coverage reaches them;
- the cargo-semver-checks goal explicitly says rustdoc JSON remains nightly-only and unstable, but also demonstrates that one tool can support a **range of formats** at once;
- that same goal also documents real blind spots: target-package rustdoc JSON alone does not settle foreign reexports, and manifest-only SemVer questions require substrate beyond rustdoc JSON;
- and the 2025 State of Rust survey says online documentation is still the preferred canonical reference, which raises the value of machine-consumable docs substrate that is honest about its limits.

Together those sources say the sharper missing crate is not just a parser or cache.
It is a support-contract layer for **source route**, **format-window support**, **normalization loss**, and **portable rustdoc JSON handoff**.

## Main judgment after the refresh

**P-0051** is stronger when it owns four additional receiver-facing truths:

1. **source-route truth** — whether a JSON blob came from local nightly generation, docs.rs download, rustup `rust-docs-json`, or manual file import;
2. **format-window truth** — which `format_version` values and toolchain windows are actually supported, and whether support is native, translated, legacy-only, or unsupported;
3. **normalization-loss truth** — which edges, fields, or semantic classes are unresolved, omitted, downgraded, or outside scope;
4. **bundle truth** — which artifacts another consumer can reopen later without pretending bundle membership implies universal query support.

That means a worthy crate in this lane should now explicitly own:

- `source-route.receipt.json`
- `format-window.matrix.json`
- `normalization-loss.report.json`
- `rustdoc-json-support-bundle.manifest.json`

It should **not** try to become:

- another raw type crate,
- another docs.rs parity runner,
- another full semver engine,
- or a fake promise that “normalized rustdoc JSON” means every downstream claim is safe.

## What should count as a worthy crate contribution in this lane now

A worthy rustdoc JSON support crate should hand other people:

1. **one source-route receipt** that says exactly how the JSON was obtained,
2. **one format-window matrix** that says what versions/toolchain windows are actually supported,
3. **one normalization-loss report** that says what the stable IR still cannot prove,
4. **one portable bundle manifest** another tool can reopen later,
5. **one exactness story** instead of pretending parse success and downstream support are the same thing.

If a candidate crate cannot do those things, the archive should usually treat it as a parser, downloader, consumer-specific adapter, or local script — not the missing ecosystem-level support-contract layer.
