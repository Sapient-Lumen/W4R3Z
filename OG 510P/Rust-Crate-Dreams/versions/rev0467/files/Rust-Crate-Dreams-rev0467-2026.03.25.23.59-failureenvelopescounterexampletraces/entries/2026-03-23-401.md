# Entry 401 — publish-receipt work now needs registry-capability receipts, protection-scope reports, and bundle honesty

This pass deepens an existing release / registry / supply-chain lane instead of opening another generic release helper or another trust-score detour.
It sharpens:

**P-0477 Cargo Publish Receipt Join Kit**.

## Why this lane earned another serious refresh now

The archive already had a good story for joining local package facts, index confirmations, publish identity, and public-visibility lag.
What it still left too easy to flatten was a more operational question:

> “Which protections and enrichments were really present on *this* registry lane, and which of those were crates.io-specific rather than portable truths about publishing in Rust?”

Current Cargo and Rust infrastructure sources make that split more urgent than before:

- Cargo’s registries docs say alternate registries can be published to with `cargo publish --registry`, but only if the registry supports the needed web API access.
- The crates.io January 2026 update says crates can now enforce Trusted Publishing Only mode, trusted publishing supports GitLab CI/CD in addition to GitHub Actions, blocked GitHub triggers are enforced for TP, and index entries now expose `pubtime`.
- The February 2026 malicious-crate policy update says the crates.io team will always publish a RustSec advisory when a crate is removed for containing malware, while broader blog/social signaling remains policy-driven rather than universal.
- The March 21, 2026 Cargo advisory says crates.io deployed an upload-side mitigation on March 13 and audited all previously published crates, but it also says alternate-registry users need to verify exposure with their registry vendor and that older Cargo on alternate registries may remain vulnerable even after Rust 1.94.1 ships.

Together those sources say the missing crate contribution is no longer just “capture a post-publish receipt.”
It is a reviewable publish-support layer for **registry capability**, **protection scope**, and **portable bundle inventory** above local package review, index observation, identity receipts, and visibility lag.

## Main judgment after the refresh

**P-0477** is stronger when it owns three more receiver-facing truths:

1. **registry capability** — what this registry lane actually exposes for publish receipts: index fields, trusted-publishing support, docs coupling, notifications, and relevant caveats;
2. **protection scope** — which protective claims were actually in scope for this registry and client lane, and where mitigation or advisory coverage stops;
3. **bundle honesty** — one portable manifest that keeps local bytes, identity, registry capability, protection scope, and visibility distinct instead of collapsing into “publish succeeded.”

That means a worthy crate in this lane should now explicitly own:

- `registry-capability.receipt.json`,
- `protection-scope.report.json`,
- and `publish-join-bundle.manifest.json`

above the earlier local-package / capture-basis / registry-accept / identity / authority / visibility lane.

It should **not** try to become:

- a registry implementation,
- a malware-moderation system,
- a universal multi-registry abstraction that pretends all registries expose crates.io-equivalent facts,
- or a full provenance / attestation platform.

## What should count as a worthy crate contribution in this lane now

A worthy publish-receipt / registry-review contribution should now hand other people:

1. **one registry-capability receipt** that states what the selected registry actually exposes and what remains crates.io-specific or unknown;
2. **one protection-scope report** that keeps upload blocking, post-hoc audits, advisory channels, client-version caveats, and alternate-registry exposure distinct;
3. **one portable bundle manifest** that inventories exactly which local, registry, identity, and visibility artifacts make up the joined release story;
4. **one conservative explanation** of why a release is reviewable for this registry lane without pretending that all Rust registries share the same operational or security posture.

If a candidate crate cannot do those things, the archive should usually treat it as adjacent release automation, trust scoring, registry moderation, or provenance tooling — not the missing joined publish-support layer.
