# 2026-03-17 (233) — crate diagnosis-surface deepening pass

This pass did **not** add a new lane.
It sharpened **P-0525 Crate Diagnosis Surface Pack Kit** into a more reviewable troubleshooting contract.

## Main judgment

The missing value is still **not** another telemetry stack, another debugger helper, another hosted support portal, or another magical root-cause engine.
The sharper missing layer is a **crate-authored diagnosis contract** that records:

- what a symptom class actually means,
- where each triage step came from,
- which signals are first-inspection surfaces rather than implementation noise,
- whether a support bundle is actually safe to attach,
- and where diagnosis support ends and manual review begins.

## Why this lane looks sharper now

- Rust’s current vision work still points toward **supportive interfaces from crates**.
- The 2025 State of Rust survey still says **online documentation** and **code** are the main learning surfaces while debugging remains a real pain point.
- The February 2026 debugging survey still highlights uneven debugger support, async gaps, and expression-evaluation issues.
- Tokio’s tracing docs and `console-subscriber` make it clear that good async diagnosis already has substrate, but that substrate still needs crate-authored troubleshooting contracts above it.
- `metrics`, `tokio-metrics`, and `miette` now make symptom signals and diagnosis-entry points concrete enough that the missing value is increasingly the reviewable layer above them.

## Preferred proving grounds

- async client crates where tokio-console is documented but instrumentation is incomplete
- SDK/client crates with vague timeout symptoms that should split into separate triage paths
- CLI tools with bounded doctor commands and secret-safe support bundles
- queue/worker crates where backlog growth and starvation need explicit first-inspection signals
- embedded/device-aware crates with board-only or manual-review-only diagnosis honesty
