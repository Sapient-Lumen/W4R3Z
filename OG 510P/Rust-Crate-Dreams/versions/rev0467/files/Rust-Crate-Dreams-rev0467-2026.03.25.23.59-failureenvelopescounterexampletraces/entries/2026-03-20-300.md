# Entry 300 — cargo-future-incompat-triage-kit sharpened around latent-debt visibility and suppression-basis truth

This pass returned to **P-0478 Cargo Future-Incompat Triage Kit** because the archive still left one ordinary release-review shortcut too cheap:

> a team could treat “the build looked clean” as proof that no future-incompat debt existed, even though Cargo and rustc can preserve findings that are only visible in a full report, only visible in a different recall surface, or suppressed in user-facing output while still present in machine-readable capture.

## What moved this time

Several current official surfaces make that blur more expensive now than it used to be:

- Cargo's future-incompat report chapter still treats the full report as a first-class object that can be shown later by id or by rerunning with `--future-incompat-report`;
- `cargo report future-incompat` can narrow recall to a specific package, which means the visible surface can shrink without the original workspace report becoming false;
- Cargo config still lets teams suppress terminal notifications entirely with `[future-incompat-report].frequency = "never"`;
- rustc's JSON output says future-incompat diagnostics can still be emitted even when the warning was suppressed by `#[allow]` or `--cap-lints`;
- Cargo's changelog has already needed fixes for duplicate saved reports, which reinforces that replay/review surfaces need explicit posture rather than folklore;
- and Rust release notes continue adding new lints to the future-incompat surface, so a “clean-looking build” can drift further away from the full debt surface across toolchain eras.

## Main planning move

This pass promoted two more first-class review objects for **P-0478**:

1. **finding visibility truth** — whether a finding was terminal-visible, report-visible-only, suppressed-but-recorded, package-filter-hidden, or otherwise visibility-limited;
2. **suppression basis truth** — why that posture exists, such as `allow_attribute`, `cap_lints`, `report_frequency_never`, or `package_filtered_recall`, and what gate meaning still remains honest.

## Why this matters

Without those objects, the archive still permits one ordinary lie:

- a maintainer can truthfully say “CI looked clean”,
- another maintainer can truthfully recall a full report and find debt,
- a release gate can truthfully fail on a latent blocker,
- and nobody has one compact answer for whether the blocker was actively shown, merely recallable, suppressed-but-recorded, or hidden by a narrower package-filtered view.

That is not cosmetic.
It is the difference between:

- “no one saw a warning,”
- “no warning existed,”
- and “the warning existed, but the reviewed surface was narrower than the debt surface.”

## Main judgment after the pass

A worthy future-incompat triage contribution for Rust should now provide more than capture locks, owner maps, waivers, and release gates.
It should also provide:

- one explicit **finding-visibility report**,
- one explicit **suppression-basis receipt**,
- and one honest way to keep “warning was visible”, “warning was recallable”, and “warning was latent but recorded” from masquerading as the same thing.
