# Entry 437 — deepen the repo around delivery cards, native-build implementation planning, and receiver-facing support bundles

This pass again chose **deepen** over **append**.

The archive already has a lot of proposals.
What it still needed was a sharper answer to two practical questions:

1. for the top-ranked crates, **what exactly should they provide other people**,
2. and which cross-cutting adoption seam is still under-specified even after the recent docs.rs, build-dir, pathfinder, and debuggability passes.

## Main judgment

Two repo moves were worth making now.

### 1. Add explicit delivery cards for the top frontier

A proposal is not ready just because it sounds important.
A serious crate in this archive should now be explainable with one compact card that names:

- who the crate is for,
- the problem it solves for them,
- the concrete `0.1` artifacts it exports,
- the workflows it replaces or shortens,
- and the claims it must explicitly refuse to make.

That turns the archive from “interesting ideas” into a more credible **product portfolio**.

### 2. Promote the native-build support stack into the practical queue

The current Rust/Cargo/docs.rs signals still point to a broad adoption seam around build scripts and native dependencies:

- the 2025 State of Rust survey still puts resource usage near the center of real-world pain,
- online docs remain the preferred canonical learning source,
- Cargo still warns that build scripts rerun conservatively unless authors narrow change detection,
- docs.rs builds in a read-only, network-blocked sandbox with concrete resource limits,
- Cargo is actively asking people to test the build-dir layout transition,
- older `OUT_DIR` assumptions have already broken once in Cargo release behavior,
- safety-critical and mixed-language adopters still call out long-lived FFI and interop pain,
- `system-deps` proves declarative native dependency metadata is viable,
- `vcpkg` proves Windows/MSVC-native discovery is viable,
- but neither becomes a boring, receiver-facing support contract on its own.

That means the sharper missing seam is not another FFI wrapper or another sys crate helper in isolation.
It is a stack of crates that publish **build-script explanation**, **fixture-tested behavior**, and **native dependency resolution receipts**.

## New practical queue update

The archive should now treat the following as the best near-term repo-building order:

1. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
2. **P-0486 Debuggability Support Contract Kit**
3. **P-0472 Docs.rs Build Parity & Evidence Kit**
4. **P-0489 Cargo Build-Dir Consumer Transition Kit**
5. **P-0046 Buildscript UX Kit**
6. **P-0058 Native Deps Kit**
7. **P-0535 Dependency Lifecycle Transition Kit**
8. **P-0484 Toolchain & Target Support Contract Kit**
9. **P-0536 Crate Knowledge Pack Kit**
10. **P-0537 Compile Iteration Feedback Kit**

This is a **practical queue**, not a claim that the broader control-plane ranking changed wholesale.
The point is that native-build support has now become implementation-shaped enough to deserve real repo space again.

## Portfolio consequences

### Delivery-card discipline should now be normal

Before another crate is promoted, the archive should be able to answer in plain terms:

- what the crate exports,
- what review artifact travels across teams,
- what doctor or CI mode it gives maintainers,
- what evidence it preserves for future humans or tools,
- and what kinds of questions it still cannot answer honestly.

If the archive cannot do that yet, the proposal is probably still too vague.

### Native build should stay a stack, not a blob

The build/native frontier gets weaker when these are collapsed into one thing:

- **P-0046 Buildscript UX Kit** — failure explanation and support bundles,
- **P-0059 Buildscript Testkit** — fixture and drift-testing bundles,
- **P-0058 Native Deps Kit** — declared native contract, backend attempts, and doctor reports.

The right move is to let them share vocabulary while keeping their user promises distinct.

### What these crates should provide other people

The archive’s native-build lane should now aim for three handoff bundles:

- one bundle answering **“why did `build.rs` fail and what should I try next?”**
- one bundle answering **“did the build script still emit the contract we expected?”**
- one bundle answering **“what native support was promised, what probe path was tried, and how do I satisfy it here?”**

That is the level of practical usefulness a worthy crate contribution should now reach.
