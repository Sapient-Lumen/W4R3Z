# Entry 389 — Debugger visualizer compatibility deepened around probe surface, comparison basis, and portable support bundles for P-0491

This pass deepened **P-0491 Debugger Visualizer Compatibility Kit** in a more review-critical direction: **probe surface, comparison basis, and portable support bundles**.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the 2026 Rust debugging survey says stellar debugging support requires several versions of different debuggers across multiple operating systems, strong visualizers, and continued resilience as debugger versions and Rust internals change;
- the Rust compiler dev guide says Rust supports three major debuggers — GDB, LLDB, and CDB — and that the CDB engine also powers WinDbg, KD, the Microsoft C/C++ extension for VSCode, and part of the Visual Studio debugger;
- the same dev-guide material on debugger visualizers says LLDB is not currently supported through the Rust-embedded visualizer lane and instead points at a separate formatter-bytecode direction;
- LLDB’s current `lldb-dap` docs explicitly split responsibilities among LLDB itself, `lldb-dap`, and IDE integrations;
- Microsoft’s current NatVis docs say Visual Studio can load NatVis from multiple locations, including `.pdb` embedding, project files, VSIX registration, and user/system visualizer directories, with a defined precedence order;
- those NatVis docs also say embedded `.pdb` NatVis cannot be updated live during a debugging session, while project-backed files can refresh in-place;
- GDB’s current pretty-printer guidance recommends versioned Python package names so multiple library versions can coexist and be registered against the right objfile;
- and the Rust compiler’s own compiletest debuginfo docs still treat debugger/version choice as a first-class axis with distinct `min-*` and `ignore-*` directives for CDB, GDB, and LLDB lanes.

Together these sharpen one conclusion: a worthy crate here is not just “visualizer asset present”.
It is a crate that helps other people inspect **which debugger surface was actually observed, whether two observations are comparable at all, and what exact bundle should travel in review or support handoff**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still a **stable support-contract layer** above Rust’s debugger-visualizer substrate.
But that support contract now needs two additional review objects:

1. **probe-surface receipt** — the observed backend family, frontend surface, version, operating-system class, asset-delivery route, and command surface used for a probe;
2. **comparison-basis receipt** — whether two visualizer observations are comparable, partially comparable, or non-comparable across engine version, frontend surface, asset-delivery route, and formatter-origin assumptions.

## Why these objects matter

Current substrate is now concrete enough that the archive should stop flattening visualizer support:

- two green observations can both say “NatVis works” while one came from an embedded `.pdb` lane inside Visual Studio and another came from a solution-loaded `.natvis` file with hot-reload behavior;
- two GDB observations can both say “printer loaded” while one depends on a versioned package name or objfile registration pattern that changed between releases;
- two LLDB-family observations can both say “formatter rendered correctly” while one was captured through `lldb` CLI and another through `lldb-dap` plus an IDE integration;
- and a backend-family upgrade can be a **comparison-basis drift** even when no asset bytes changed.

## New archive-level stance

For debugger-visualizer work, the archive should now prefer this layering:

1. **P-0491** for asset inventory, activation route, formatter origin, probe surface, comparison basis, backend verdicts, and portable visualizer-support bundles;
2. **P-0486** for broad debuginfo / symbol / backend support posture;
3. **P-0493** for source lookup and path hygiene;
4. broader debugger wrappers or formatter packs only after the visualizer-support bundle stays honest on its own.

That keeps the portfolio from minting another crate that merely says “visualizers passed on CI” without clarifying whether the relevant lane was LLDB CLI, `lldb-dap`, CDB/WinDbg/Visual Studio, or a GDB pretty-printer route whose versioning and objfile-registration assumptions changed.

## What should count as a worthy crate contribution after this pass

A worthy debugger-visualizer contribution should now be able to answer all of these cleanly:

1. **What exact debugger surface observed the value?**
2. **What engine/frontend/version/OS basis did that observation depend on?**
3. **What delivery container or load precedence carried the active visualizer asset?**
4. **Which formatter origin actually produced the display?**
5. **Are two observations comparable, only partially comparable, or not honestly comparable?**
6. **What exact portable bundle can another maintainer inspect?**

If a candidate crate cannot answer those questions, the archive should usually treat it as debugger folklore rather than a serious compatibility contract.
