# Entry 347 — lint-policy evidence deepened around authority, checked scope, diagnostic channels, and waiver truth for P-0459

This pass deepened **P-0459 Clippy Safety Profile & Waiver Kit** instead of adding another static-analysis dashboard, another “strict mode” wrapper, or another folklore-heavy waiver spreadsheet.

## Why this lane earned another pass now

Fresh official Rust/Cargo/Clippy signals line up unusually well:

- the 2026 flagship goals explicitly call out **safety-critical lints in Clippy**;
- Cargo already has first-class manifest lint configuration via `[lints]` and inheritance via `workspace.lints`;
- nightly Cargo already has an emerging `[lints.cargo]` surface behind `-Zcargo-lints`;
- Cargo’s January 2026 development notes show that workspace-lint semantics and inherited-dependency linting are still active design seams;
- and Clippy configuration is rich enough that private-item coverage, test-only MSRV coverage, and safety-comment interpretation can materially change what a “clean” run even means.

Together these make one conclusion stronger: a worthy ecosystem contribution here is not just “run more lints.” It is a crate that helps other people inspect **who set the policy, what was actually checked, which channel produced each finding, which waivers were explicit, and how that story changed over time**.

## Main judgment after the pass

The strongest near-term contribution in this lane is **not** another lint runner.
It is a **lint-policy contract layer** above Cargo manifests, Clippy configuration, nightly Cargo-lint experiments, inline attributes, and CI glue.

This pass promotes six P-0459 review objects into first-class status:

1. **policy-authority receipt** — where each effective lint level really came from;
2. **checked-scope matrix** — which packages / targets / features / test-private surfaces were actually checked;
3. **diagnostic-channel receipt** — whether a finding came from stable rustc, stable Clippy, or nightly Cargo linting;
4. **waiver-decision record** — who owns an exception and when it expires;
5. **lint-policy drift diff** — what changed across revisions;
6. **lint-support bundle manifest** — the portable review bundle joining those facts.

## Why these objects matter

Current lint substrate is finally specific enough that the archive should stop flattening it:

- a workspace can declare `workspace.lints` and still leave one member outside the policy because it never opted into inheritance;
- a crate can deny `missing_safety_doc` and still leave private items out of scope if `check-private-items = false`;
- a team can claim “MSRV linting passed” while test-only MSRV checks remained off;
- and a nightly Cargo finding can be useful without being the same evidence channel as a stable rustc/Clippy finding.

## New archive-level stance

For lint-facing work, the archive should now prefer this layering:

1. **P-0459** for policy authority, checked scope, diagnostic channels, waiver decisions, and drift;
2. **P-0473** when the hard problem is workspace rollout and inheritance cleanup more than safety-review evidence;
3. **P-0042** when the hard problem is future-incompatibility triage;
4. **P-0120** when the hard problem is broader unsafe evidence rather than lint policy posture.

That keeps the portfolio from minting another crate that merely says “strict linting enabled” without clarifying who set it, what it covered, or which findings came from which channel.

## What should count as a worthy crate contribution after this pass

A worthy lint-policy contribution should now be able to answer all of these cleanly:

1. **Which effective lint levels came from which authority source?**
2. **Which packages / targets / features / tests / private-item scopes were actually checked?**
3. **Which findings came from stable rustc/Clippy and which came from nightly Cargo linting?**
4. **Which exceptions are explicit, owned, and time-bounded?**
5. **Can another engineer compare the lint-policy story across revisions without reverse-engineering every manifest and CI job by hand?**

If a candidate crate cannot answer those questions, the archive should usually treat it as lint folklore rather than a serious lint-policy contract.
