# Entry 341 — dependency lifecycle frontier mapping and new P-0535 Dependency Lifecycle Transition Kit

This pass deliberately added a new top-level proposal: **P-0535 Dependency Lifecycle Transition Kit**.

## Why this lane earned a dedicated proposal

Fresh official Rust signals line up around one under-modeled reality:

- the January 2026 safety-critical write-up explicitly says teams often **use crates early, track carefully, and then shrink or replace them for higher-criticality parts**;
- the same post says other teams avoid third-party crates in the highest-assurance lanes or hide them behind abstraction layers and plan to replace them later;
- the December 2025 Vision Doc work says Rust should expand crate-side **supportive interfaces** and do more to help users navigate the ecosystem;
- the 2025 State of Rust survey says online documentation remains the preferred canonical reference;
- and the January 2026 crates.io update says the registry now exposes stronger trust/support facts like a Security tab, Trusted Publishing Only Mode, SLOC, and `pubtime`.

That combination makes one boring conclusion stronger: the ecosystem still lacks a crate that turns **dependency lifecycle planning** into a compact, reviewable artifact instead of architecture folklore.

## Main judgment after the pass

The worthy contribution is **not** another scanner, score, or graph viewer.
It is a crate that tells other people:

1. where third-party crates are allowed to live today,
2. what seam makes later replacement plausible,
3. which dependencies are temporary, pinned, forked, vendored, or being designed out,
4. and what release-to-release drift widened or tightened that posture.

## The new first-class review objects

This pass promotes these P-0535 artifacts into first-class status:

1. `dependency-lane.snapshot.json`
2. `criticality-boundary.report.json`
3. `abstraction-seam.receipt.json`
4. `replacement-readiness.report.json`
5. `dependency-exception.ledger.json`
6. `lifecycle-drift.diff.json`

## Why these objects matter

Current Cargo and crates.io substrate is already strong enough to feed them:

- Cargo can expose the current resolved graph through `cargo metadata` and `cargo tree`;
- the resolver and `Cargo.lock` already make dependency choice and freeze posture concrete;
- `rust-version` already participates in dependency selection and package support expectations;
- `patch` / `replace` / path overrides already support real-world transition moves;
- crates.io now exposes stronger trust/support context that can be imported without pretending it settles local architecture policy.

But none of those pieces currently say whether a dependency is **allowed inside the control core**, **must stay behind a sidecar boundary**, **is intentionally temporary**, or **quietly escaped its containment seam in the last release**.

## New archive-level stance

For dependency-heavy work, the archive should now prefer this layering:

1. **P-0535** for dependency lifecycle / criticality / seam / transition truth,
2. **P-0036** for toolchain-version compatibility truth,
3. **P-0017** for trust/risk import,
4. **P-0011** for maintenance/support posture,
5. **P-0515** for successor-specific off-ramp recipes.

That keeps the archive from duplicating dependency planning across trust, MSRV, and off-ramp lanes.

## What should count as a worthy crate contribution after this pass

A worthy dependency-planning crate should now be able to answer all of these cleanly:

1. **Which third-party crates are allowed in which lanes?**
2. **What real seam makes replacement plausible?**
3. **What is the next intended transition for each tracked dependency?**
4. **Which waivers are conscious exceptions rather than accidental architecture drift?**
5. **What changed between releases that widened or narrowed dependency exposure?**

If a candidate cannot answer those questions, the archive should usually synthesize it into adjacent trust / MSRV / off-ramp lanes rather than mint another proposal.
