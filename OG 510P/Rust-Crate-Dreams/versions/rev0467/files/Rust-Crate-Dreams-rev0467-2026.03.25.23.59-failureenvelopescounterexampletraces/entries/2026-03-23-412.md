# Entry 412 — concurrency-contract deepened around cancellation classes, recovery posture, and stronger claim ceilings

This pass chose to **deepen** the new concurrency-contract frontier rather than opening another async helper, lock wrapper, or runtime-abstraction lane.

The archive re-read the latest revision, checked fresh official and primary-source signals again, and then asked a narrower question:

> if **P-0538 Concurrency Contract Kit** is really worthy, what does it need to provide other people in practice beyond the first four reports?

The answer was that the lane still needed two more pieces of product shape:

1. **cancellation classes that mean something across real surfaces** — the repo needed a sharper way to distinguish:
   - queued waiters that lose place on cancellation,
   - true cancel-safe operations that guarantee no message or “seen” state was consumed,
   - and broader manual-review cases where cancellation can still perturb state;
2. **panic / recovery posture** — the repo needed an explicit optional artifact for poisoning, advisory poisoning, no-poisoning, and experimental non-poisoning surfaces, because those are materially different receiver-facing promises.

## Why this deepening pass earned a full revision

Fresh current sources make the distinction sharper than yesterday:

- the March 2026 Rust challenges note still frames async complexity, fragmentation, and lock-in as a live ecosystem problem;
- the 2025 State of Rust survey still says resource usage and debugging remain major productivity problems;
- Tokio `Notify` documents fair queueing together with queue-place loss on cancellation, while also documenting stored-permit behavior for `notify_one`;
- Tokio `watch::Receiver::changed` documents true cancel safety by guaranteeing that cancellation does **not** mark a value seen;
- Tokio `mpsc::Receiver::recv` documents true cancel safety by guaranteeing that cancellation does **not** consume a message;
- Tokio `RwLock` still documents `blocking_*` methods that panic in an async execution context;
- `std::sync::Mutex` source/docs now make poisoning’s status as an **advisory** signal explicit via `PoisonError::into_inner`;
- `parking_lot::Mutex` explicitly documents **no poisoning** plus eventual fairness;
- and nightly `std::sync::nonpoison::Mutex` makes non-poisoning an explicit experimental posture rather than an unspoken implementation choice.

That combination means **P-0538** is strongest when it can answer not only:

- is this surface FIFO / eventually fair / reentrant / context-limited,

but also:

- what exactly is preserved when a wait is cancelled,
- what exactly is lost,
- what recovery promise exists after panic,
- and where the claim is stable, advisory, experimental, or manual-review-only.

## Main judgment after this pass

The top frontier still begins:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But **P-0538** is now stronger because the archive no longer stops at “fairness/cancellation/context matter.”
It now has a clearer product shape for:

- **wait cancellation class**
- **queue-membership effect**
- **value / seen-state effect**
- **stored-permit or analogous wake effect**
- **panic / poison / recovery posture**
- and a bundle that keeps those separate from reentrancy and context legality.

## What should count as a worthy crate contribution in this lane now

A worthy concurrency-contract crate should provide other people:

1. **one cancellation-class report** that says whether cancellation preserves queue membership, loses queue place, preserves message/value state, or needs manual review;
2. **one recovery-posture report** that says whether panic leads to poisoning, advisory poisoning, no poisoning, forced recovery hooks, or experimental/non-stable posture;
3. **one shared vocabulary** that compares Tokio, `std`, `parking_lot`, and future surfaces without pretending their words mean the same thing;
4. **one bundle manifest** that keeps reentrancy, fairness, cancellation, recovery, and context legality visibly separate;
5. **one claim ceiling** that says where docs are stable and where nightly / experimental / inferred surfaces still require caution.

If a candidate crate cannot export those artifacts, it is probably still one of these instead:

- a primitive implementation,
- a runtime wrapper,
- a channel helper,
- a deadlock detector,
- or a guide/tutorial.

Useful, yes.
But not the receiver-facing support-contract layer this archive now thinks is missing.
