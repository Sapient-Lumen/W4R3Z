
# Entry 374 — MSRV workspace work deepened around effective workspace promises, policy-split drift, and portable support bundles

This pass continued the archive’s current strategy of **deepening one high-value support-contract lane until it looks genuinely buildable** instead of opening another finder, badge generator, or version-matrix helper.

The lane chosen here was **P-0036 MSRV Workspace Lab**.
The archive already had a solid thesis, core schemas, and a product sketch for policy activation, command-family floors, lockfile-floor receipts, and blame.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when a workspace says “our MSRV is X”, what exactly should another engineer receive if different members, commands, or lockfile-authoring paths really mean different support promises?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh Cargo docs and issue traffic still pull in the same direction:

- the current Cargo `rust-version` docs frame MSRV as a package support promise and say the unsupported-toolchain diagnostic affects all Cargo targets in the package;
- the current resolver docs make mixed-MSRV workspace behavior explicit and warn that shared resolution can still pick dependency versions that are too low or too high for individual members;
- the Rust 2024 Edition Guide and Cargo workspaces docs make explicit that resolver choice is a root-level workspace setting and that virtual workspaces must set `workspace.resolver` explicitly;
- Cargo’s changelog now warns when a virtual workspace omits `workspace.resolver`, and Cargo 1.83 made lockfile v4 the default for create/update paths while warning about compatibility with earlier MSRVs;
- Rust 1.93 release notes say Cargo now respects `rust-version` when generating lockfiles;
- issue traffic shows command-family divergence is not theoretical: `cargo run` can succeed while `cargo metadata` fails, and mixed-MSRV workspaces can still produce surprising resolution pressure;
- and `cargo-msrv` remains useful and alive, but it is still centered on find/verify rather than publishing a portable support contract for policy activation, member splits, command families, and authoring floors.

That combination makes one archive lesson sharper:

**A worthy MSRV crate is not just “find the oldest compiler that builds.”  
It is a reviewable contract for what each workspace member promises, whether the intended policy activated, which command families actually hold at that floor, what lockfile authoring requires, and how that story changed across revisions.**

## Main repo judgment from this pass

The strongest next move for **P-0036** was to make three more receiver-facing review objects first-class:

1. **`effective-workspace-promise.manifest.json`** — normalize workspace support promises after inheritance and split policy.
2. **`policy-split-diff.report.json`** — compare revisions without pretending a single member move means the whole workspace moved.
3. **`msrv-support-bundle.manifest.json`** — give another engineer one compact pack for policy, activation, command-family floors, lockfile-floor truth, and any split-policy drift.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0484** still owns broader toolchain/target support posture;
- **P-0535** still owns dependency placement and off-ramp planning;
- **P-0468** still owns generic resolver explanation;
- but **P-0036** owns the receiver-facing workflow for **workspace support promises, command-family floors, and lockfile-authoring honesty**.

That separation matters.
Otherwise the archive would quietly confuse “Cargo has more MSRV substrate” with “another reviewer can now tell what this workspace honestly supports.”

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One policy-activation receipt** that says whether the intended MSRV-aware resolver was truly active.
2. **One effective workspace-promise manifest** that says what each member really promises instead of compressing the whole repo into one floor.
3. **One command-family floor report** that keeps `build`, `metadata`, `doc`, `update`, `generate-lockfile`, and `package` meaningfully separate.
4. **One lockfile-floor receipt** that keeps pinned-build support separate from lockfile-authoring support.
5. **One policy-split diff** that says exactly which member or command-family promise changed across revisions.
6. **One portable support bundle** that another reviewer can archive, diff, or hand to downstream users.

If a crate idea in this territory cannot supply those review objects, it is still probably a finder, a CI helper, or raw Cargo substrate rather than the missing contract layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **one observed green lane** into **one workspace-wide support promise**.

Future passes should therefore keep asking:

1. what each member actually promises,
2. whether the policy was really active,
3. which command family was checked,
4. whether lockfile authoring means something newer,
5. and whether the drift was whole-workspace or only one member.

That is a better use of repo time than inventing another one-number MSRV badge, binary-search wrapper, or matrix dashboard.
