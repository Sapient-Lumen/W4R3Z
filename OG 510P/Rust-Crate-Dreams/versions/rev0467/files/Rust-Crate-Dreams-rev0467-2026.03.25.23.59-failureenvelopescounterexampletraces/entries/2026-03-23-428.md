# Entry 428 — concurrency-contract deepened around delivery acceptance, sender-side success meaning, and observation-evidence ceilings

This pass chose to **deepen P-0538 Concurrency Contract Kit** again instead of inventing another channel wrapper, actor helper, or queue chooser.

The sharper question was:

> once a concurrency surface can describe reentrancy, fairness, cancellation, context legality, locality, liveness, delivery memory, pressure, audience, and claim semantics, how does it also say **what a successful send / notify actually means** and **what evidence exists later that anybody really observed the unit**?

## Why this deepening pass earned a full revision

Fresh primary sources made the next missing layer concrete:

- the March 2026 Rust challenges write-up still says async complexity is part of the current Rust pain picture;
- Tokio `mpsc::Sender::send` explicitly says `Ok` does **not** mean the data will be received; it only means the receiver had not hung up already when acceptance was determined;
- Tokio `broadcast::Sender::send` explicitly says success means at least one active receiver existed, and `receiver_count()` explicitly says that returned count is **not guaranteed** to equal the number of receivers that will actually receive the value;
- Tokio `watch::Sender::send` explicitly says success updates the shared latest value and notifies receivers, while failure returns the value and does **not** make it available for future receivers;
- Tokio `oneshot` explicitly says a sent message can remain in the channel even if the receiver closes before receiving it, while the sender can observe closure with `poll_closed` / `is_closed` rather than successful receipt;
- Tokio `Notify` explicitly says it carries **no data**, and `notify_one()` only makes a permit available;
- Flume explicitly says `send` / `send_async` return an error if all receivers have been dropped, but success is still queue or handoff admission rather than processing receipt.

That means the next worthy move for **P-0538** is not just broader “channel behavior.”
It is to make **delivery-acceptance** and **observation-evidence ceilings** first-class review artifacts.

## Main judgment after this pass

The top frontier still begins:

1. **P-0537 Compile Iteration Feedback Kit**
2. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
3. **P-0535 Dependency Lifecycle Transition Kit**
4. **P-0536 Crate Knowledge Pack Kit**
5. **P-0538 Concurrency Contract Kit**

But **P-0538** is stronger now because the archive no longer stops at:

- reentrancy scope,
- progress/fairness class,
- wait-cancellation semantics,
- recovery posture,
- execution-context boundaries,
- mobility / affinity,
- driver-liveness,
- delivery memory,
- backlog pressure,
- delivery audience,
- consumption claim.

It now has a clearer product shape for:

- **delivery-acceptance reports**,
- **observation-evidence reports**,
- **“send returned `Ok`” versus “somebody definitely observed it” honesty**,
- **count-hint versus proof-of-observation distinctions**,
- and portable bundle inventory that keeps acceptance/evidence separate from memory, pressure, audience, claim, fairness, cancellation, or context legality.

## What should count as a worthy crate contribution in this lane now

A worthy concurrency-contract crate should provide other people:

1. **one delivery-acceptance report** that says whether success means permit recorded, latest state replaced, queue admission, active receivers existed, or only that the endpoint had not hung up yet;
2. **one observation-evidence report** that says whether the producer later has no evidence, only a close signal, only a receiver-count hint, or must add an application-level acknowledgment if real observation / processing proof is needed;
3. **one explicit separation between “the send succeeded” and “someone definitely received or processed it”**;
4. **one explicit separation between “there were active receivers” and “this exact value reached them”**;
5. **one portable bundle** that keeps delivery acceptance and observation evidence separate from memory, pressure, audience, claim, fairness, cancellation, recovery, context, locality, and liveness.

That is closer to an ecosystem-worthy crate than another queue helper, actor mailroom, or channel-comparison blog post.
