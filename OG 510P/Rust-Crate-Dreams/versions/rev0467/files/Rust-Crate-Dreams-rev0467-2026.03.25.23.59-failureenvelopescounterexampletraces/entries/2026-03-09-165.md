# Entry 165 — local-first sync becomes lane-explicit and fixture-first

This pass again chose **not** to add another narrow proposal.

The better move was to upgrade **P-0076 Local-first Sync Kit** from a high-salience essay into a more buildable, receiver-facing plan.
The proposal was already ambitious and correctly aimed at a real ecosystem gap.
What it still lacked was a sharper answer to:

> what should this crate actually hand to another person when sync succeeds, stalls, or breaks?

## Main judgment

Rust now has enough substrate in this area that “Rust needs a local-first story” is too vague.
The sharper truth is:

- Rust has meaningful CRDT engines,
- meaningful sync / replication substrate,
- and meaningful encrypted-group substrate,

but still lacks the **boring coordination kit** above those pieces.

So the revised proposal now treats the missing crate as a lane-explicit stack:

1. **repo contract**,
2. **sync-state receipts**,
3. **transport session receipts**,
4. **membership / key-epoch receipts**,
5. **divergence triage**,
6. and one portable **`syncbundle@1`** artifact.

That is much closer to something another builder could really start implementing.

## Why these changes were the right ones

### 1. The old proposal still blurred too many layers together
The archive already knew that local-first is more than just CRDT choice.
But the old version still behaved a bit like:

- one repo abstraction,
- one transport choice,
- one future security story,
- and one generic “bundle” idea.

The revised version is more honest and useful because it separates:

- engine lane,
- store lane,
- transport lane,
- membership lane,
- and support-bundle lane.

That gives future builders a much better map.

### 2. The proposal needed a real golden path
The repo has accumulated enough frontier breadth that every strong proposal now needs to answer:

> what exact first profile should a real team adopt?

The revised plan now makes a concrete recommendation:

- an **Automerge-shaped** first engine profile,
- SQLite-backed durable receipts,
- one reliable ordered transport adapter,
- and a `syncbundle@1` export/diff flow.

That is still ambitious, but much less hand-wavy than “support many CRDTs later”.

### 3. E2EE and revocation needed to stop being a future footnote
A common failure mode in local-first design writing is to treat encrypted collaboration as an afterthought.
The revised version now freezes a much better planning stance:

- same-user multi-device and shared-group collaboration are distinct profiles,
- membership/key epochs must become first-class receipts,
- and revoked-device failures should diagnose as **membership drift**, not generic sync weirdness.

### 4. P-0076 needed fixture-first planning
The new schema pack gives the proposal a buildable receiver surface:

- repo manifest,
- sync-state report,
- transport-session receipt,
- membership ledger,
- and divergence-triage report.

That moves it closer to the newer top-tier proposals in this archive, which increasingly win by freezing a compact coordination artifact rather than by promising a giant future platform.

## New planning stance

For the next few passes, the archive should prefer:

- treating **P-0076** as a shared coordination artifact above CRDT engines,
- keeping same-user and shared-group profiles distinct,
- making redaction and comparability explicit,
- and reusing shared bundle substrate where possible.

It should **not** drift into:

- another CRDT-engine proposal,
- another vague “sync platform” idea,
- or a claim that convergence alone solves authorization, revocation, or privacy.
