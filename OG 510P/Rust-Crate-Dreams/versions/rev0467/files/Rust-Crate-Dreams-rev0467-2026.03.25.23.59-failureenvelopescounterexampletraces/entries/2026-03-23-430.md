# Entry 430 — concurrency-contract deepened around closure finality, post-close availability, and tail-honesty

This pass chose to **deepen P-0538 Concurrency Contract Kit** again instead of inventing another queue wrapper, shutdown helper, or “best channel close semantics” explainer.

The sharper question was:

> once a concurrency surface can already describe memory, pressure, audience, claim, acceptance, evidence, order, and gap visibility, how does it also say **what closed actually means** and **what remains observable after closure**?

## Why this deepening pass earned a full revision

Fresh primary sources made the next missing layer concrete:

- the March 2026 Rust challenges write-up still says async complexity remains part of the current Rust pain picture;
- Tokio `mpsc` clean-shutdown docs explicitly say the receiver should `close` and then drain to completion, and `Receiver::close` explicitly says buffered messages remain receivable while outstanding permits may still yield values;
- Tokio `broadcast` explicitly says the channel is closed once all senders drop, but receivers still get retained values until exhausted, after which `recv` returns `RecvError::Closed`;
- Tokio `watch` docs explicitly say `changed` returns `RecvError` only when the channel is closed **and** the current value is already seen, while `Sender::closed` explicitly says the channel can be reopened by `subscribe`;
- Tokio `oneshot` docs explicitly say `Receiver::close` prevents future sends but `try_recv` should still be used to recover a value sent before close completed, and the module docs explicitly say a value already sent can remain in the channel until the receiver is dropped;
- `async-channel` docs explicitly say a closed channel cannot accept further sends but remaining messages can still be received;
- `std::sync::mpsc::Receiver` explicitly says that once the sender disconnects, buffered messages sent before disconnect can still be properly received.

That means the next worthy move for **P-0538** is not just broader “channel lifecycle.”
It is to make **closure finality** and **post-close availability** first-class review artifacts.

It now has a clearer product shape for:

- **closure-finality reports**,
- **post-close-availability reports**,
- **drain-then-terminal versus reopenable-closed honesty**,
- **retained-tail versus latest-snapshot versus in-flight-value honesty**,
- and portable bundle inventory that keeps closure truth separate from memory, pressure, audience, claim, acceptance/evidence, order/gaps, fairness, cancellation, recovery, context, locality, or liveness.

## What should count as a worthy crate contribution in this lane now

A worthy concurrency-contract crate should provide other people:

1. **one closure-finality report** that says whether closure is immediate terminal, drain-then-terminal, reopenable, or subject to an in-flight close/send race;
2. **one post-close-availability report** that says whether buffered tail, retained history, latest snapshot, or a maybe-sent in-flight value remains observable after closure;
3. **one explicit separation between “no new sends may enter” and “nothing else can be observed”**;
4. **one explicit separation between “the surface is closed now” and “the closed state is permanent”**;
5. **one portable bundle** that keeps closure finality and post-close availability separate from memory, pressure, audience, claim, acceptance/evidence, order/gaps, fairness, cancellation, recovery, context, locality, and liveness.

That is closer to an ecosystem-worthy crate than another shutdown helper or channel-comparison article because it tells adopters whether closure actually ends the story.
