# Entry 399 — crate knowledge packs now need answerability scope, claim traces, and refusal honesty for support/search/assistant consumers

This pass stays inside an already-important docs / support / machine-consumable handoff lane.
It deepens:

**P-0536 Crate Knowledge Pack Kit**.

## Why this lane earned another serious refresh now

The archive already knew that crates increasingly need one compact, provenance-aware handoff pack above rustdoc JSON, docs.rs pages, READMEs, and examples.
What it still left too easy to fake was a more operational question:

> “What ordinary questions can this pack answer directly, what must be refused or routed to manual review, and which exported claims can be traced back to exact excerpts and materials?”

Current official sources make that seam sharper than before:

- the 2025 State of Rust survey still says online documentation is the preferred canonical reference and hints that some learning/support traffic is moving toward LLM tooling;
- docs.rs now documents hosted rustdoc JSON, version-sensitive `format_version` handling, semver and `latest` redirect behavior, configurable target/feature/doc build metadata, and downloadable documentation archives that are useful but caveated;
- Cargo still describes `cargo rustdoc --output-format json` as tooling-facing access to rustdoc’s experimental JSON format;
- and the rustdoc JSON RFC still frames JSON as a way for other tools to build different frontends above rustdoc’s data collection rather than to scrape HTML.

Together those sources say the next missing crate contribution is **not** another crate-chat interface and **not** another retrieval wrapper.
It is a **reviewable answerability contract** for compact crate-knowledge exports.

## Main judgment after the refresh

**P-0536** is now stronger as a crate-knowledge lane when it owns three more receiver-facing truths:

1. **assistant-context structure** — what stable sections, exclusions, manual-review zones, and bundle links a compact machine-facing pack actually contains;
2. **query-support scope** — which question classes are `supported`, `partial`, `manual_review_required`, or `refused`;
3. **claim traceability** — which exported claims map back to which excerpt IDs and source-material IDs.

That means a worthy crate in this lane should now explicitly own:

- `assistant-context.pack.json`,
- `query-support.matrix.json`,
- `claim-trace.report.json`,
- plus the earlier `material-basis`, `export-policy`, and `excerpt-lineage` artifacts that make those claims reviewable.

It should **not** try to own:

- ranking or retrieval policy for one search engine,
- model prompting or answer-generation strategy,
- full offline docs hosting,
- or a generic “the assistant understands the crate” score.

## What should count as a worthy crate contribution in this lane now

A worthy crate-knowledge contribution should now hand other people:

1. **one compact assistant/support pack** with stable sections, exclusions, and manual-review zones;
2. **one query-support matrix** that says which ordinary question classes the pack can and cannot answer honestly;
3. **one claim-trace report** that ties compact summaries back to exact excerpts and source materials;
4. **one material/import/export basis** that keeps floating docs.rs URLs, hosted downloads, local notes, and README slices visibly distinct;
5. **one portable bundle** another team can reopen later without guessing what the machine-facing slice was actually allowed to say.

If a candidate crate cannot do those things, the archive should usually treat it as substrate, exporter glue, or product-specific retrieval logic — not the missing epic handoff layer.
