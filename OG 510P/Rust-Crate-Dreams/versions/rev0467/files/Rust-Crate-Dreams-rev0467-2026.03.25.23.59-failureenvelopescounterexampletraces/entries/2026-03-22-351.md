# Entry 351 — rebuild explanation deepened around baseline authority and reverse-impact honesty for P-0469

This pass deepened **P-0469 Cargo Rebuild Explanation Kit** instead of adding another general build-performance dashboard, another historical warehouse, or another lock-contention explainer.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- Cargo’s unstable build-analysis docs now say each invocation can persist JSONL logs under `$CARGO_HOME/log/` with a unique session id and expose `cargo report sessions`, `cargo report timings`, and `cargo report rebuilds`.
- The Cargo 1.94 development-cycle update says `cargo report sessions` exists specifically to find the id needed for `cargo report timings` and `cargo report rebuild`, and that the report surfaces are still being refined.
- The build-analysis goal says Cargo wants to record invocation metadata and rebuild reasons across runs, but does **not** yet promise a frozen downstream schema.
- The relink-don’t-rebuild goal makes reverse-dependency fanout after non-interface edits an explicit upstream pain point.
- The 2025 State of Rust survey still says slow compile times and storage/resource usage remain among the main productivity limits.

Together these make one conclusion stronger: the worthy crate here is not merely “show me the rebuild reason Cargo printed”.
It is a crate that helps other people inspect **why a baseline was chosen, whether the comparison was apples-to-apples enough to trust, which reverse dependencies merely rebuilt, and where public-interface change is still unproven**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still **not** another recorder.
It is a **stable support-contract layer** above Cargo’s evolving session/report substrate.

This pass promotes two additional P-0469 review objects into first-class status:

1. **baseline-authority receipt** — why this session or run was selected as the comparison baseline, what alternatives were rejected, and whether the comparison stays within a compatible scope;
2. **reverse-impact report** — which dependents rebuilt, whether that fanout was directly observed, whether a relink-only opportunity is plausible, and where public-interface change remains unproven.

## Why these objects matter

Current Cargo substrate is finally specific enough that the archive should stop flattening rebuild investigations:

- a support bundle can import a valid session id yet still compare the wrong baseline;
- the nearest prior run can be less authoritative than a farther-but-same-profile/target run;
- reverse dependencies can visibly rebuild without any stable proof that the upstream edit changed the public interface;
- and a future “relink don’t rebuild” world will make it even more important to separate **observed rebuild fanout** from **proven interface-affecting change**.

## New archive-level stance

For Cargo build explainability work, the archive should now prefer this layering:

1. **P-0469** for session freeze, baseline authority, exactness, and reverse-impact honesty;
2. **P-0035** for many-session warehousing and regression adjudication;
3. **P-0490** for waiting / lock-contention facts;
4. **P-0494** for tool-surface / compile-time-deps parity;
5. **P-0468** for resolver and feature-cause-chain explanation.

That keeps the portfolio from minting another crate that merely says “we know why Cargo rebuilt things” without clarifying whether the comparison window itself was trustworthy.

## What should count as a worthy crate contribution after this pass

A worthy rebuild-explanation contribution should now be able to answer all of these cleanly:

1. **Why was this baseline chosen instead of another session?**
2. **Is the comparison compatible enough to support a rebuild-cause claim?**
3. **Which dependents visibly rebuilt?**
4. **Does the bundle prove interface change, or only show fanout?**
5. **Where would a future relink-only opportunity plausibly live?**

If a candidate crate cannot answer those questions, the archive should usually treat it as rebuild folklore rather than a serious support contract.
