# Entry 242 — Node-API package contract deepening around prebuild coverage, loader routes, and publish identity

This pass did **not** invent a brand-new JavaScript binding lane.
It sharpened **P-0498 Node-API Package & Prebuild Contract Kit** into a more believable shipping-contract crate.

## Why this moved now

The Node/native-addon substrate is now real enough that the missing value is no longer just “please make Rust call into Node somehow.”
The sharper gap is a **boring publish and support contract above already-working authoring tools**:

- Node.js still documents **Node-API** as the ABI-stable native-addon surface, which means the core compatibility promise is real and worth packaging honestly. [Sources: Node-API reference; Node ABI-stability guide]
- modern Node package docs now make the **`"node-addons"` export condition** and `--no-addons` behavior explicit, which means loader routing between native and more universal fallbacks should no longer stay folklore. [Sources: Node packages docs]
- Node still treats **context-aware / Worker-safe loading** as an explicit addon boundary, which keeps runtime claims from being “any native addon should work everywhere Node runs.” [Sources: Node addons docs; CLI/docs errors]
- `napi-rs` v3 and current CLI/docs make cross compilation, generated loaders, and even **WebAssembly fallback stories** much more ordinary, which is good substrate but also makes overclaiming easier. [Sources: napi-rs homepage/docs/blog]
- npm now documents **trusted publishing** and automatic **provenance attestation** generation for public packages from supported CI providers, which means publish identity has become part of the release contract rather than an external afterthought. [Sources: npm trusted publishing docs]

So the gap is not “there is no Rust Node addon tooling.”
The gap is that maintainers still rarely get one **reviewable npm-native bundle** that says:

- which prebuilt artifacts actually shipped,
- what loader path users will actually take,
- and what publishing identity / provenance posture the package really has.

## Main planning move

This pass kept the archive honest about what the crate should be.
The right `0.1` is **not** another binding generator, not another npm release bot, and not a general Node package builder.

The sharper missing crate is:

- a **cargo-native inspect/check/diff/bundle** workflow,
- scoped to **Rust-built Node-API packages and their npm-facing release contract**,
- above today’s Node-API, `napi-rs`, package exports, loader shims, and npm publishing substrate,
- with three first-class review objects that were previously still too implicit:
  1. **prebuild coverage**
  2. **loader route**
  3. **publish identity**

## Main judgment after the pass

A worthy Node-API package-contract crate should now provide not only a bundle format, but also:

- explicit **prebuild-coverage truth** (`fully_prebuilt`, `native_gap_hidden_by_source_build`, `local_build_only`, etc.),
- explicit **loader-route truth** for `node-addons`, native-first, `default` fallback, local-build hooks, or WASM fallback,
- explicit **publish-identity truth** for trusted publisher / provenance / token/manual release posture,
- and a compact review bundle that another person can inspect without rerunning the whole npm release pipeline.

That is a much sharper and more believable contribution than “yet another Rust-to-Node helper crate.”
