# Entry 197 — shared ecosystem interop profiles promoted as a distinct library-compatibility lane

This pass added a new top-level proposal: **P-0511 Crate Interop Profile Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing shared ecosystem profile packs, producer-side capability contracts, task-first crate choice, trait-evolution planners, and semver slice tools into one fake “interop support” story.

## Why this moved now

Several current official Rust signals line up unusually well.

### 1. The new ecosystem-supportiveness work exposed a third missing layer

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**, and
- **producer-side support / interop claims** via **P-0510**.

But there was still no shared, versioned way to define the *ecosystem boundary itself*.
That left the archive with good answers to:

- “Which crates fit this task?”
- “What does this crate claim to support?”

but not a good answer to:

- “What does it actually mean to fit this library ecosystem profile, and can two crates prove that they do?”

### 2. Official vision-doc guidance now names smoother library interop directly

The December 2025 Rust vision-doc work says that helping users orient in the crate ecosystem requires better interop between libraries.
It also explicitly points to likely shapes such as **key interop traits** and **standard building blocks** like the `http` crate.

That is a strong hint that a worthy missing crate here is not just another per-crate contract.
It is also a **shared interop profile pack** above those building blocks.

### 3. The language/library substrate is evolving, but profile contracts are still missing

The project is now actively working on **externally implementable items** and **evolving trait hierarchies**.
Those are strong ecosystem-shaping moves: they make it easier to define and evolve shared extension points.

But they still do **not** create a boring profile-pack layer that tells other people:

- which public surfaces count for a lane,
- which coupling is forbidden,
- what adapters are acceptable,
- and where manual review is still required.

### 4. Slice tools are getting better, but the joined interop contract is still missing

The `cargo-semver-checks` goal shows real progress toward witness-based compatibility analysis and more precise public-API reasoning.
That is valuable and should be imported.

But semver witness generation is still not the same thing as a shared ecosystem profile that a provider and consumer crate can both be checked against.

## Current judgment

The worthy crate here is not:

- another “best crate” list,
- another producer metadata schema,
- another semver checker,
- or another domain-specific validator.

The worthy crate is the boring shared profile layer that can hand other people:

1. one **interop profile pack**,
2. one **static conformance receipt**,
3. one **behavioral probe report**,
4. one **pair-compatibility report**,
5. one **migration-hazards report**,
6. and one explicit **manual-review boundary** when the profile still depends on human judgment.
