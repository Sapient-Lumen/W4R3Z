# Entry 138 — debugger visualizer implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded **P-0491 Debugger Visualizer Compatibility Kit** from a good debugging-frontier idea into a more implementation-ready crate plan.

## Main judgment

Rust’s visualizer substrate is now explicit enough that the archive should stop treating this as a vague “debugger automation” idea.

The current upstream story already has:

- stable `#[debugger_visualizer]`,
- explicit NatVis and GDB asset lanes in the Rust reference,
- an explicit NatVis-on-`-windows-msvc` restriction,
- an explicit warning that embedded GDB pretty printers are not auto-loaded by default,
- and a concrete GDB trust model around `auto-load safe-path`.

So the missing value is not another debugger platform.
It is the **receiver-facing compatibility bundle** above those surfaces.

## New planning stance

**P-0491** should now be read as a crate that hands other people:

- one `visualizer-policy.toml`,
- one `visualizer-assets.manifest.json`,
- one `backend-matrix.receipt.json`,
- one `render-golden.report.json`,
- one `embed-vs-external.report.json`,
- optionally one `visualizer-drift.diff.json`,
- and one compact `notes.md`.

That is much sharper than “visualizer tooling.”

## Archive-level lesson

Once upstream docs make the awkward constraints explicit, the right archive move is often to make the crate **smaller and more honest**.

The worthy contribution here was not another debugging proposal.
It was to define the first boring artifact that can say whether a visualizer lane was supported, unsupported by design, blocked by trust policy, or still manual-review-only.
