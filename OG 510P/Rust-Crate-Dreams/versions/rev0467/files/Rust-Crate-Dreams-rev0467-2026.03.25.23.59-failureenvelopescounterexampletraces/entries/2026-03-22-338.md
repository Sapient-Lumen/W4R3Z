# Entry 338 — broad territory rerank, epic-crate rubric, and target-readiness deepening for P-0484

This pass deliberately chose **not** to add another narrow top-level proposal.
The archive is now large enough that a broad rerank can be more valuable than one more lane.

## Why this pass happened now

Fresh official signals line up unusually well:

- the 2025 State of Rust survey still puts **resource usage** and **debugging** near the top of ecosystem pain;
- the March 2026 Rust challenges write-up explicitly calls out **no_std gaps**, **cross-compilation friction**, **GUI compile-time pain**, and **safety-critical tooling gaps**;
- the January 2026 safety-critical post explicitly recommends **target-focused readiness checklists**, **dependency lifecycle guidance**, **safety-case-friendly async runtime requirements**, and better **interop** support;
- and the 2026 program-management update reorients Rust’s strategic framing around **roadmaps** and application areas like **Cross-language interop** and **Safety-critical & regulated**.

That combination means the strongest missing crates are increasingly the crates that make support, stability, interop, runtime posture, and reviewability explicit for other people.

## Main judgment

The archive’s highest-value near-term work is now **support-contract infrastructure**.
The strongest “epic crate” opportunities are often not new substrate libraries, but the boring middle layers that publish:

- stable vocabularies,
- receipts and reports,
- human-readable summaries,
- drift reports,
- and portable handoff bundles.

That does **not** mean the archive should collapse into Cargo-only work.
It means broad reranks should reward proposals that help many downstream teams understand what a project actually supports and what evidence backs the claim.

## Why P-0484 earned concrete deepening

The January 2026 safety-critical post does more than mention target support in passing.
It effectively sketches a missing artifact: a target-focused readiness checklist that says which targets exist, which are `no_std` only, what the last known tested environment was, and which blockers still matter.

That is exactly the kind of “boring support answer” the archive should reward.
So this pass deepened **P-0484** around a new first-class review object:

- **`target-readiness.report.json`**

The point is to keep these truths separate:

- Rust-project target tier,
- project support class,
- `std` / `no_std` posture,
- last known tested environment,
- external prerequisites,
- known blockers,
- and actual exercise scope.

## What should count as a worthy crate contribution after this pass

A worthy crate should now be able to answer all of these cleanly:

1. **What recurring pain does it solve?**
2. **What substrate already exists?**
3. **What new artifact does it export for other people?**
4. **What drift can it detect over time?**
5. **What neighboring lanes does it refuse to absorb?**
6. **What does a believable `0.1` look like?**

If a candidate cannot answer those questions, the archive should usually rerank or synthesize instead of adding another lane.

## New archive-level stance

For the next few passes, prefer:

- deepening the top support / interop / debugging / assurance lanes,
- keeping the frontier ranked across multiple application areas,
- and using explicit archive-refresh notes to resist duplication and LLM amnesia.

The archive should **not** drift into:

- score-only proposals,
- giant “one dashboard for everything” ideas,
- or narrow one-off lanes that duplicate a stronger neighboring contract crate.
