# Entry 85 — frontier pass: geospatial interchange seams, device onboarding evidence, GNSS stream/file parity, model-file artifact contracts, and HID descriptor correctness

Added five proposals after a pass aimed at **maximum domain variety** while preserving a tight thesis: the next great Rust crates here are often **not** new engines or full stacks, but **coordination artifacts** that sit above real substrate.

New proposals:

- P-0377 GeoParquet + GeoArrow + FlatGeobuf Interop & Canonicalization Workbench Kit
- P-0378 FIDO Device Onboard 2.0 / 1.1 Interop & Certification Evidence Kit
- P-0379 RINEX 4.02 + NTRIP v2 Replay & Evidence Kit
- P-0380 SafeTensors + GGUF Model Artifact Interop Workbench Kit
- P-0381 USB HID Report Descriptor + Usage Tables Conformance Kit

Pass notes:

- **GeoParquet + GeoArrow + FlatGeobuf** made the cut because Rust now has real geospatial columnar substrate, but the sharper missing value is **conversion-loss accounting and CRS/profile evidence**, not another reader.
- **FDO** rose because Rust already has a serious implementation, the spec surface is moving again, and the missing layer is still **safe, portable onboarding/certification evidence** rather than yet another full provisioning stack.
- **RINEX + NTRIP** was promoted because Rust has stream/file/QC substrate, but no boring default bundle for **session → archive parity and station-profile debugging**.
- **SafeTensors + GGUF** rose because the operational pain is increasingly at the **artifact contract** level: shard manifests, metadata, quantization expectations, and explainable conversion loss.
- **USB HID** made the cut because Rust can already generate and parse descriptors, but the higher-leverage crate is a **descriptor/usage/host-quirk conformance layer** above existing firmware crates.

Archive hygiene added in this pass:

- Added an LLM-hygiene reminder to **pin moving registries/tables/spec revisions explicitly** and to separate **format core** from **adjacent registries or usage tables**.
- Added a reminder that future format/interchange proposals should state their **loss surface** explicitly rather than merely claiming to “support both formats”.
