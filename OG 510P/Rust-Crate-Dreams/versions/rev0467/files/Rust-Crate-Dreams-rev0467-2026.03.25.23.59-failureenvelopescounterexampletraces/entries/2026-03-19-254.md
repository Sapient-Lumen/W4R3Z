# Entry 254 — MCP guard planning sharpened around transport exposure, auth boundaries, and operation guards

This pass did **not** add another MCP SDK or another generic enterprise gateway.
It sharpened **P-0071 MCP Guard Kit** into a more believable, implementation-ready product.

## Why this moved now

The current MCP deployment story is no longer empty.
That changes the shape of the missing value.

- MCP now publishes official SDK tiers and the Rust SDK is listed as an official Tier 2 SDK.
- The official Rust SDK has crossed into 1.x and is actively gaining auth and transport improvements.
- The specification now includes explicit authorization and security requirements such as resource indicators, audience validation, origin validation, and security considerations for tools/roots/sampling.
- The official security guide now names concrete attack families: confused deputy flows, token passthrough, SSRF, session hijacking, risky local-server startup commands, and scope minimization failures.
- The 2026 roadmap explicitly names enterprise readiness as a priority.
- The reference-server repository explicitly warns that its servers are educational examples, not production-ready deployments.
- The interceptor extension exists, but remains experimental rather than normative.

That combination means the missing crate is no longer “Rust needs MCP support.”
The sharper missing crate is a **shared deployment guard contract** above today’s SDK, spec, and security guidance.

## Main planning move

This pass made the crate more concrete by promoting three first-class review objects that were still too implicit in the older proposal:

1. **transport exposure receipt** — what is actually local-only, remotely reachable, or missing origin/bind safeguards,
2. **auth-boundary receipt** — whether audience binding, token passthrough prohibition, consent, and scope posture are actually in force,
3. **operation-guard contract** — what tools/resources/prompts/sampling paths require approval, limits, and audit/redaction.

That move matters because the archive had not yet separated:

- “MCP auth exists somewhere,”
- “the deployment is exposed safely,”
- and “high-risk operations are actually bounded”

into one implementation-ready `0.1` plan.
This pass fixes that.

## Main judgment after the pass

A worthy MCP guard crate contribution for Rust should now provide **more than middleware hooks**.
It should provide:

- explicit **transport exposure truth** for stdio, local HTTP, remote HTTP, and origin/bind posture,
- explicit **auth-boundary truth** for resource indicators, audience validation, token passthrough, and consent/scope posture,
- explicit **operation-guard truth** for tools/resources/prompts/sampling/roots,
- and one compact review bundle another maintainer or security reviewer can inspect without reading a deployment archaeology stack.

That is more believable and more ecosystem-multiplying than either:

- “just another MCP SDK wrapper”,
- or “just another policy engine binding” with no deployment receipts attached.
