# Entry 180 — delegated build-script units elevated into their own lane, with artifact-dependency adoption refreshed beside them

This pass added one new top-level proposal and refreshed one older one.
The repo’s best next move was to sharpen the boundary between:

- **delegated reusable build-script units**, and
- **artifact-dependency bridge adoption and fallback posture**.

That produced two focal crates:

- **P-0508 Cargo Build Script Delegation Kit**
- **P-0495 Cargo Artifact Dependency Adoption Kit**

## Why these moved now

Several official signals now line up unusually well.

### 1. Upstream is no longer assuming one handwritten `build.rs` forever

The 2025 GSoC results explicitly say the path toward delegation to reusable build-script packages starts with:

- multiple build scripts per crate,
- deterministic order,
- separate output-directory access,
- then parameter passing via manifest metadata,
- and finally build-script delegation to external packages using artifact dependencies.

That is strong evidence that a new crate lane is warranted **above** current Cargo substrate.

### 2. The substrate already exists in pieces

Cargo’s unstable docs already expose:

- `metabuild`,
- `multiple-build-scripts`,
- and any build script metadata.

Stable build-script docs already explain:

- metadata passing,
- `links` overrides,
- order-sensitive emitted instructions,
- and persistent `OUT_DIR` behavior.

So the missing crate is no longer “invent a build-time model from nothing.”
It is the boring plan/receipt/fallback layer above a substrate that is real but not yet packaged for ordinary maintainers.

### 3. Artifact dependencies are now part of the likely bridge story

Cargo 1.93’s design notes discuss a build-script artifact directive as a possible polyfill/bridge and explicitly ask how it should connect back to artifact dependencies.
That means **P-0495** is no longer just a niche unstable-feature adoption crate.
It is adjacent to the likely future path for external build helpers.
