# Entry 289 — crate ecosystem pathfinder sharpened around revisit triggers, freeze horizons, and decision-watch truth

This pass came from noticing that **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit** had become much better at saying when a starter set is ready to freeze, where it buys lock-in, and when teaching and production defaults should diverge.

It still left one quiet bluff available:

> a frozen starter-set lock could look durable while saying almost nothing about when it must be reviewed again, what kinds of new evidence invalidate it, or whether a fired trigger means “review this” versus “replace this now”.

## What moved this time

Several live Rust signals made that gap more concrete:

- the Rust vision-doc work still says users struggle with crate discovery and starter-set choice, which means more teams will want to **freeze** scoped default stacks once they finally choose them;
- the 2025 State of Rust survey still says docs and code are the main learning/reference surfaces and notes continuing concern about maintainer support, which raises the cost of stale frozen choices;
- crates.io now exposes faster-moving signals like a **Security** tab, **Trusted Publishing only mode**, and `pubtime` in the index;
- the crates.io malicious-crate policy now routes routine malware removals through **RustSec advisories** and RSS rather than one blog post per incident;
- docs.rs changed its default targets in late 2025, proving that a crate’s **visible support story** can shift without the team touching its own starter-set lock.

That combination means the missing layer is no longer only “freezeable crate choice”.
It is **freezeable-and-reviewable crate choice**.

## Main planning move

This pass promoted three more review objects to first-class status for **P-0509**:

1. **revisit-trigger truth** — which event classes force review of a frozen decision, such as RustSec advisories, malicious-crate notices, docs-surface shifts, imported health/support changes, or task-constraint changes,
2. **freeze-horizon truth** — how long a frozen starter set may sit without review even when no event trigger has fired,
3. **decision-watch truth** — whether the current state is `steady`, `review_due`, `invalidated`, `superseded`, or `manual_review_required`, and why.

## Why this matters

Without those three objects, the archive still permits one ordinary lie:

- a team can freeze a starter set once,
- keep carrying that lock in docs, onboarding material, or internal policy,
- import new security/support/docs signals later,
- and still have no compact way to say whether the frozen answer remains usable, is merely due for review, or is actively invalidated.

That is not just maintenance ceremony.
It is the difference between “we once made a thoughtful crate choice” and “we still have a living, reviewable dependency decision.”

## Main judgment after the pass

A worthy crate-discovery / starter-set contribution for Rust should now provide more than ranking, readiness, and freeze locks.
It should provide:

- one explicit **revisit-trigger policy**,
- one explicit **freeze-horizon policy**,
- one explicit **decision-watch report**,
- and one clear distinction between **review due** and **automatic replacement required**.

That is a better answer to real ecosystem drift than either:

- “just trust the frozen starter set until someone complains”,
- “just re-rank everything on every run”,
- or “any advisory/docs/support change means silently replace the chosen crate”.
