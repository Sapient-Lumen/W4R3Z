# Entry 218 — crate test-surface planning sharpened into an implementation-ready v0.1 shape

This pass did **not** promote a new lane.
It sharpened **P-0523 Crate Test Surface Pack Kit** into a more buildable shape.

## Why this moved now

The archive had already promoted crate test surfaces as one of the stronger missing receiver-facing support lanes.
The sharper move now was **not** to add another adjacent test helper idea, but to make P-0523 believable enough that someone could start `0.1` work this week.

Several current Rust and ecosystem signals make that move unusually well-timed:

1. **Supportive crate interfaces are now a live strategic theme.**
   The December 2025 Rust vision-doc work explicitly argues that crates still lack good tools for supportive interfaces.

2. **Docs and code are still the main learning surfaces.**
   The 2025 State of Rust survey says online documentation remains the preferred canonical reference, followed by studying the code itself.
   That means testing support should not stay trapped in helper modules and tribal knowledge.

3. **The substrate is real, but fragmented.**
   Cargo already distinguishes unit, integration, doctest, and example-adjacent test structure.
   Tokio already provides paused-time testing guidance and mock I/O helpers.
   `rstest`, `proptest`, `wiremock`, `assert_cmd`, `tempfile`, `insta`, and `testcontainers` already cover big slices of the problem.
   But they still do **not** add up to one crate-authored contract for which test surfaces are official, what environment they need, and which named scenarios are actually witnessed.

## Main planning move

This pass made three previously fuzzy things explicit:

- **support level** — is a fixture or recipe `officially_supported`, only a `best_effort_example`, still `experimental`, or only `manual_review_required`?
- **environment requirements** — does a scenario require tempdir access, env mutation, loopback networking, Docker, paused time, or a real external service?
- **scenario witnesses** — which named scenarios are backed by real fixtures, seams, assets, and topologies instead of aspirational prose?

Those are the pieces that make the difference between “this crate has tests” and “this crate publishes a reviewable downstream testing contract”.

## Main judgment after the pass

A worthy `0.1` here is a **small cargo subcommand plus library** centered on:

- `init`
- `capture`
- `check`
- `doctor`
- `summary`
- `diff`
- `pack`

with explicit artifacts for:

- `support-level.policy`
- `test-environment.requirements`
- `scenario-witness.receipt`

The key repo-memory lesson is that future passes should not mistake any of the following for proof that a *new* crate lane is needed:

- missing support-level vocabulary,
- missing environment-requirements vocabulary,
- missing scenario-to-fixture witness links,
- missing import adapters for Tokio paused time or `rstest` / `wiremock` / `assert_cmd` / `testcontainers`,
- or missing doctor warnings around overclaimed deterministic seams.

The sharper move, for now, is to keep making **P-0523** more buildable and more falsifiable.
