
# Entry 327 — Stable Plugin Host Kit deepened for ABI-surface truth, capability negotiation, lifecycle posture, and compatibility witnesses

This pass deepened **P-0081 Stable Plugin Host Kit** instead of adding another loader, another Wasm plugin pass, or another generic FFI helper.

## Why this lane earned another serious pass

The archive already knew that Rust could build native plugin systems today.
What it lacked was a build-shaped answer for *which truths actually belong in one reviewable native plugin contract*.

Current substrate is now strong enough to make that precise:

- `abi_stable` explicitly supports runtime-loaded Rust libraries, plugin systems, FFI-safe trait objects, prefix types, and load-time checking over referenced types;
- `abi_stable::library` documents root-module loading and compatibility checking;
- prefix types make additive module and vtable evolution concrete enough to treat as a first-class contract fact;
- `libloading` is explicit that dynamic-library initialization and termination routines behave like unknown foreign code from a safety perspective;
- `cglue`, `safer_ffi`, and `interoptopus` prove there is meaningful adjacent FFI substrate, but not one shared native-plugin review contract;
- Cargo’s current “plugin of the cycle” framing is another reminder that extension surfaces remain strategically important even when the core tool cannot absorb them all.

That means a worthy crate here should not simply say “supports native plugins”.
It should say what ABI surface is authoritative, how optional capabilities are negotiated, what lifecycle / unload truth really applies, and what compatibility witness another team can trust.

## What moved this time

The main planning move was to stop treating “native plugins” as one blob.

This pass elevated four review objects into first-class status for **P-0081**:

1. **ABI-surface truth** — `abi_stable` prefix/root module, trait-object surface, serialized fallback, C-ABI shim, or manual-review-only route;
2. **capability-negotiation truth** — required capabilities, optional capabilities, negotiation route, downgrade policy, and failure posture;
3. **lifecycle-posture truth** — startup vs on-demand load, unload support, restart-only replacement vs true hot reload, and state persistence posture;
4. **compatibility-witness truth** — what target/version/layout checks or integration evidence justified trust in the plugin.

## Why this matters now

The evidence is sharp enough that the missing layer is no longer vague:

- `abi_stable` shows that real load-time type/layout checking and additive prefix evolution are possible today;
- `libloading` shows why low-level dynamic loading cannot be mistaken for a proved-safe unload/reload story;
- adjacent FFI crates show active ecosystem energy without solving the receiver-facing native-plugin contract;
- and current Cargo writing is still explicitly celebrating plugin ecosystems instead of pretending the core tool can absorb every extension workflow.

That means a worthy crate should not let “dynamic plugin”, “stable ABI”, or “hot reload” quietly over-claim lifecycle or compatibility truth.

## Main judgment after the pass

A worthy native-plugin crate should now provide more than a loader and a macro.
It should also provide:

- one explicit **ABI-surface receipt**,
- one explicit **capability-negotiation receipt**,
- one explicit **lifecycle-posture receipt**,
- one explicit **compatibility-witness receipt**,
- and one conservative rule for when a useful native plugin path is still too weak, too restart-bound, or too ad hoc to bluff full stable-plugin support.
