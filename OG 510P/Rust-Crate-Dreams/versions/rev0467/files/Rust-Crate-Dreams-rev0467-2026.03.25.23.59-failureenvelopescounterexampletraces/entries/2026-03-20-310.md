# Entry 310 — request-execution-policy-contract-kit added for idempotency basis, attempt budgets, admission paths, and hedge/retry topology

This pass added a new top-level proposal: **P-0530 Request Execution Policy Contract Kit**.

## Why this lane earned a slot

The archive already had better answers for:

- channel semantics,
- lifecycle/shutdown aftermath,
- observability delivery truth,
- resource saturation,
- feature/config/MSRV support truth,
- and crate choice / upgrade support.

It still lacked one receiver-facing answer to a common networking and service-integration question:

> “What actually happens when this request is slow, duplicated, retried, hedged, rate-limited, or rejected under load?”

Current Rust substrate now makes that absence concrete enough to justify a dedicated lane.

## What moved this time

The main planning move was to treat **request execution as a support contract layer**, not as raw middleware wiring.

This pass therefore promoted four review objects to first-class status:

1. **idempotency-basis truth** — why replay is safe, and whether cloning/rebuilding or idempotency keys are required;
2. **attempt-budget truth** — serial attempts, retry budgets, timeouts, deadlines, backoff, and jitter;
3. **admission-path truth** — queue/buffer/limit/load-shed order and quota scope;
4. **attempt-topology truth** — single-shot, serial retry, or hedged parallel attempts.

## Why this matters

Without those objects, the ecosystem still permits a common shortcut:

- `reqwest`, `reqwest-retry`, Tower, `governor`, and `tonic` can all truthfully say “supports retries / timeouts / rate limits / overload control”,
- maintainers can truthfully say “uses best-practice retry budgets” or “has load shedding”,
- and a downstream team can still have no compact answer for:
  - why replay is safe,
  - whether admission waits or rejects,
  - whether layer order changes in-flight totals,
  - whether timeouts are per-attempt or end-to-end,
  - and whether multiple attempts ever run in parallel.

That is not just wiring detail.
It is supportiveness.

## Main judgment after the pass

A worthy request-execution contribution for Rust should now provide more than a retry helper, one timeout knob, or prose about resilience.
It should provide:

- one explicit **idempotency-basis receipt**,
- one explicit **attempt-budget receipt**,
- one explicit **admission-path receipt**,
- and one honest **attempt-topology report**.
