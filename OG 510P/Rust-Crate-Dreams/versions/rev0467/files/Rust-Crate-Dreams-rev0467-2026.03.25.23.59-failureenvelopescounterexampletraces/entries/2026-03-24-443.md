# Entry 443 — make basis witnesses first-class, define first-usable release contracts, and bind pathfinder packets to replayable evidence locks

This pass again chose **deepen over append**.

The archive already had:
- a stronger front-door pairing between **P-0509 Pathfinder** and **P-0536 Crate Knowledge Pack**,
- packet-family discipline,
- and receiver/pilot thinking.

What it still lacked was a cleaner answer to three practical questions:

1. what **evidence-bearing basis** should support the leading packets,
2. what a **first usable release** for the top crates should actually hand another team,
3. and how those two ideas should fit together so the archive does not keep describing “smart crates” that cannot survive replay, review, or handoff.

## Main judgment

Three repo moves were worth making now.

### 1. Make **basis witnesses** first-class in the archive

The top lanes are increasingly downstream of official machine surfaces, not just prose pages.
Current Rust substrate now offers enough structured material to justify a real **basis witness stack**:
- `cargo metadata --format-version 1` for workspace and dependency topology,
- Cargo `--message-format=json` for artifacts and build-script results,
- docs.rs rustdoc JSON plus docs.rs metadata/build rules for hosted documentation basis,
- Cargo registry index records for release identity, checksum, and publication time,
- and `cargo package` packaging behavior plus `.cargo_vcs_info.json` for packaged-state and source provenance.

That means a worthy crate in the top packet-producing lanes should stop hand-waving about “evidence” and start naming exactly which witnesses it imports or emits.

### 2. Raise the bar from “good idea” to **first usable release contract**

The archive already had a stronger epic-crate bar and better first-release bundle language.
But there was still room for a sharper test:

> if a maintainer shipped `0.1.0` next month, what exact packet would another engineer receive, and what repeated workflow would that packet shorten?

The new first-usable-release note answers this for the leading lanes.
It says a worthy first release should have:
- one named receiver cohort,
- one repeated painful workflow,
- one narrow packet family,
- one explicit replay/basis story,
- and one explicit refusal boundary.

Anything broader should be demoted back to research.

### 3. Bind Pathfinder packets to a replayable **basis lock**

The archive already treated **P-0509** and **P-0536** as a practical pair.
This pass makes the contract tighter.

A pathfinder decision packet is not ready for another team if it only says:
- which crates were considered,
- which one won,
- and what public links were visible that day.

It also needs to carry a replayable basis lock that says:
- which registry or index entries were consulted,
- which packaged version and VCS witness were used,
- which docs.rs recipe and rustdoc JSON surfaces were in scope,
- which target or platform filters were applied,
- and which trust or advisory surfaces were imported without being mistaken for task fit.

That is the point of the new basis-lock plan and fixture.

## Salience consequence

This pass still does **not** justify a dramatic frontier rerank.
The top salience block remains broadly stable:

1. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
2. **P-0486 Debuggability Support Contract Kit**
3. **P-0538 Concurrency Contract Kit**
4. **P-0472 Docs.rs Build Parity & Evidence Kit**
5. **P-0536 Crate Knowledge Pack Kit**
6. **P-0496 Cargo Vendor & Source Parity Kit**

What changed is the **buildability test** for the first slice.
Pathfinder and knowledge-pack work now need a more explicit basis-witness story, not just packet-family names.

## Practical queue consequence

The practical queue now reads best as:

1. **P-0509 + P-0536** — decision packets and review packets with replayable basis locks
2. **P-0486** — debug capability packets that can emit comparable witness bundles
3. **P-0496** — source-parity and restricted-delivery packets that can reuse the same lock discipline
4. **P-0472** — docs.rs parity doctor and issue bundles
5. **P-0489** — build-dir dual-support transition
6. **P-0535** — lifecycle / off-ramp packets
7. **P-0484** — hard-domain target/support truth
8. **P-0058** — native prerequisites and ABI provenance

Interpretation:
- this is **not** a claim that every crate should emit every witness surface;
- it **is** a claim that the leading receiver-facing crates should stop publishing packets that cannot say what evidence basis they stand on.

## What this pass says a worthy crate should provide other people

A worthy crate now needs a cleaner answer to **seven** practical questions:

1. **receiver** — who gets the packet?
2. **workflow** — what repeated painful task becomes shorter or safer?
3. **packet family** — what receipts, reports, manifests, packs, locks, notes, or imports appear?
4. **basis witnesses** — what exact machine and document surfaces support the packet?
5. **replay** — can another team reproduce the packet basis later, or at least see why not?
6. **schema** — how do downstream consumers survive evolution?
7. **ceiling** — what must the crate still refuse to claim?

If a proposal cannot answer those yet, it may still be important, but it is probably not ready for promotion.
