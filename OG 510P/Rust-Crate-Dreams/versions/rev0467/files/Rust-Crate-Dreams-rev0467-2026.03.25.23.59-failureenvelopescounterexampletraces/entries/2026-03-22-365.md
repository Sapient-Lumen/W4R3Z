# Entry 365 — public dependency boundary work deepened around manifest intent, effective boundary verdicts, and migration posture for P-0431

This pass deepened **P-0431 Public Dependency Boundary Kit** instead of adding another generic public-API diff tool, another SemVer checker, or another wrapper around `exported_private_dependencies`.

## Why this lane earned another pass now

Fresh official and primary-source signals line up unusually well:

- the 2025H2 Rust goal is explicitly about finding an MVP for stabilizing public/private dependencies;
- the 2026 flagships keep that stabilization effort live;
- Cargo’s unstable docs already support `public = true`, make private the default, and explicitly say `workspace.dependencies` does **not** support `public`;
- `cargo add` already exposes `--public` / `--no-public` on nightly;
- recent Cargo changelogs now show broader user-facing substrate for this lane, including support for publishing packages with a `public` field, public/private status in `cargo metadata`, `cargo tree --edges public`, and better manifest errors;
- RFC 3516 gives concrete examples of accidental publicness through convenience error types, doc-hidden shims, and reexports, and it explicitly prefers false negatives to false positives;
- and current rustdoc-based tools (`public_api`, `cargo-public-api`, `cargo-check-external-types`) make it practical to import public-surface evidence instead of guessing.

Together these make one conclusion stronger: the worthy crate here is not just “run the lint and print warnings.”
It is a crate that helps other people inspect **what the manifest intended, what dependencies are effectively public now, how they escaped, what evidence supports that verdict, where Cargo still has a workspace gap, and what migration is safest**.

## Main judgment after the pass

The strongest near-term contribution in this lane is still **not** another analyzer in isolation.
It is a **stable support-contract layer** above Cargo/rustc, rustdoc JSON, and existing public-API tooling.

This pass promotes eight P-0431 review objects into first-class status:

1. **manifest-intent receipt** — what the manifest declared and where inheritance/unsupported fields apply;
2. **boundary-verdict report** — what is effectively public now;
3. **exposure-route report** — how each dependency crossed the boundary;
4. **evidence-provenance receipt** — which facts came from Cargo/rustc versus rustdoc-based inference;
5. **workspace-gap receipt** — where current Cargo behavior blocks a cleaner declaration;
6. **boundary-migration plan** — the safest next move;
7. **public-dependency drift diff** — what changed across releases;
8. **public-dependency support-bundle manifest** — the compact handoff artifact joining those truths.

## Why these objects matter

Current Rust/Cargo substrate is finally concrete enough that the archive should stop flattening public/private dependency work:

- a manifest can say nothing while the crate is still effectively exposing a dependency;
- a rustdoc-based external-type witness can be real without proving the exact same thing as Cargo/rustc’s unstable lint path;
- a workspace can *want* to declare publicness centrally while Cargo still rejects `public` inside `workspace.dependencies`;
- a hidden shim can stay intentionally allowlisted without becoming a fully private dependency story;
- and shrinking the boundary via a wrapper can be the right migration even when it is SemVer-sensitive.

## New archive-level stance

For public/private dependency work, the archive should now prefer this layering:

1. **P-0431** for manifest intent, effective boundary verdicts, exposure routes, evidence provenance, workspace gaps, and migration posture;
2. `public_api` / `cargo-public-api` for rustdoc-based public-item substrate;
3. `cargo-check-external-types` for external-type allowlist substrate;
4. SemVer/public-API readiness lanes for larger release governance after the boundary bundle is honest on its own.

That keeps the portfolio from minting another crate that merely says “external types escaped” or “the lint fired” without clarifying what boundary claim is actually warranted.

## What should count as a worthy crate contribution after this pass

A worthy public/private-dependency-facing contribution should now be able to answer all of these cleanly:

1. **What did the manifest intend?**
2. **Which dependencies are effectively public today?**
3. **What exact route exposed them?**
4. **Which parts of the verdict came from Cargo/rustc versus rustdoc-based inference?**
5. **What current workspace/scope limitation still blocks a cleaner claim?**
6. **What migration is safest?**

If a candidate crate cannot answer those questions, the archive should usually treat it as boundary folklore rather than a serious support contract.
