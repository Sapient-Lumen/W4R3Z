# Entry 217 — crate persistence-surface planning sharpened into an implementation-ready v0.1 shape

This pass did **not** promote a new lane.
It sharpened **P-0522 Crate Persistence Surface Pack Kit** into a more buildable shape.

## Why this moved now

The archive had already promoted persistence surfaces as one of the stronger missing receiver-facing crate lanes.
The sharper move now was **not** to add another adjacent serializer/storage/migration idea, but to make P-0522 believable enough that someone could start `0.1` work this week.

Several current Rust and ecosystem signals make that move unusually well-timed:

1. **Supportive crate interfaces are now a live strategic theme.**
   The December 2025 Rust vision-doc work explicitly argues for more supportive interfaces from crates.

2. **Docs and code are still the main learning surfaces.**
   The 2025 State of Rust survey says online documentation remains the preferred canonical reference, followed by studying code itself.
   That means persisted-state behavior should not stay trapped in folklore and source dives.

3. **The substrate is real, but fragmented.**
   `std::fs::File` already distinguishes `sync_data`, `sync_all`, and the fact that dropping a file ignores close errors.
   `std::fs::rename`, `tempfile::NamedTempFile::persist`, and `atomic-write-file` already expose useful replace/write semantics, but they do **not** by themselves tell downstream users what a crate promises about durability.
   Serde, `serde-reflection`, Postcard, `revision`, and redb already expose compatibility/recovery substrate, but still do not add up to one crate-authored persistence contract.

## Main planning move

This pass made three previously fuzzy things explicit:

- **contract level** — are these bytes a public contract, a soft contract, a rebuildable cache, or internal-only?
- **write path** — did the save path write in place, replace via temp file, append a journal, commit a transaction, or only reach a weaker/manual-review boundary?
- **failure model** — does the claim cover clean shutdown only, process crash, OS crash, power loss, external modification, or only a narrower subset?

Those are the pieces that make the difference between “this crate persists state” and “this crate publishes a reviewable persistence support contract”.

## Main judgment after the pass

A worthy `0.1` here is a **small cargo subcommand plus library** centered on:

- `init`
- `capture`
- `check`
- `doctor`
- `summary`
- `diff`
- `pack`

with explicit artifacts for:

- `surface-contract.policy`
- `write-path.receipt`
- `failure-model.profile`

The key repo-memory lesson is that future passes should not mistake any of the following for proof that a *new* crate lane is needed:

- missing public-vs-cache contract language,
- missing write-path vocabulary,
- missing crash/power-loss/external-mutation coverage vocabulary,
- missing adapters for `tempfile`, Postcard, `revision`, or redb,
- or missing doctor warnings around overclaimed durability.

The sharper move, for now, is to keep making **P-0522** more buildable and more falsifiable.
