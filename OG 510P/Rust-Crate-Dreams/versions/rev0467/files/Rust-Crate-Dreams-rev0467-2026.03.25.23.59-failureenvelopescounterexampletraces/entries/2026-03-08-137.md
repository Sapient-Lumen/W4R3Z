# Entry 137 — debuggability support implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded **P-0486 Debuggability Support Contract Kit** from a strong debugging-frontier idea into a more implementation-ready crate plan.

## Main judgment

Rust’s debugging substrate is now explicit enough that the archive should stop talking about “better debugging” in general terms.

The current upstream story already has:

- documented `debug`, `split-debuginfo`, and `strip` profile knobs,
- documented platform-specific sidecar expectations like `pdb`, `dSYM`, `dwo`, and `dwp`,
- stable `#[debugger_visualizer]` assets,
- explicit path-hygiene direction via `trim-paths`,
- and even documented behavior shifts that can quietly weaken support posture.

So the missing value is not another debugger or formatter wish list.
It is the **receiver-facing support bundle** above those surfaces.

## New planning stance

**P-0486** should now be read as a crate that hands other people:

- one `debuggability.receipt.json`,
- one `symbol-layout.manifest.json`,
- one `visualizer.manifest.json`,
- one `support-posture.report.json`,
- optionally one `debuggability-drift.diff.json`,
- and one compact `notes.md`.

That is a much sharper contract than “debug support tooling.”

## Archive-level lesson

When Cargo and `rustc` make the substrate more explicit, the right archive move is often to make the crate **smaller and more honest**.

The worthy contribution here was not another debugging proposal.
It was to define the first boring release/support artifact that can say, in one place, what a build actually promises to another human.
