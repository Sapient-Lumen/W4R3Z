# Entry 406 — FFI callback support now needs callback-authority receipts and callback-completion truth

This pass deliberately **deepens P-0121 FFI Boundary & Bindings Conformance Kit** instead of opening another generator comparison, language-specific runtime helper, or mobile/package shipkit.

## Why this lane earned another serious pass now

The archive already had stronger stories for:
- interface authority,
- projection basis and parity,
- ownership transfer,
- unwind posture,
- callback execution,
- callback lifecycle,
- binding coverage,
- layout authority,
- and error channels.

What it still left too easy to blur was a more operational question:

> “Who actually defines this callback surface, which direction does the call cross, and what completion / cancellation / unexpected-error obligations are required for the boundary to remain honest?”

Current sources make that split unusually concrete:

- the Rust project now explicitly frames **cross-language interop** as an application area and continues investing in component-model support;
- the January 2026 safety-critical write-up says many teams will carry C/C++ boundaries for years and explicitly calls for tooling that keeps interfaces correct, auditable, and in sync;
- UniFFI documents foreign callback ownership, foreign-trait error conversion, exactly-once async completion obligations, optional dropped-future cancellation hooks, and late-callback caveats;
- Diplomat explicitly says it is for **unidirectional** bindings and that callback support in parameters is **limited**;
- CXX documents that direct async FFI is **not implemented yet** and recommends an opaque-context + oneshot callback adapter instead;
- and `wit-bindgen` makes world import/export directionality explicit and keeps generated Rust traits/functions tied to that world contract.

Together those sources say the sharper missing crate is not another bridge.
It is a reviewable layer for **callback authority truth** and **callback completion truth** above today’s bridge/generator substrate.

## Main judgment after the refresh

**P-0121** is stronger when it owns two more receiver-facing truths:

1. **callback authority truth** — which artifact actually defines the callback surface, which direction the boundary call crosses, whether the callback is native to that family or only an adapter recipe, and whether the support is symmetric or intentionally one-way;
2. **callback completion truth** — whether completion is inline, exactly-once via done callback, channel-based adapter completion, cancellation-aware, late-completion-capable, or still manual-review territory, including what happens on unexpected callback failures.

That means a worthy crate in this lane should now explicitly own:

- `callback-authority.receipt.json`
- `callback-completion.report.json`

above the earlier callback-execution / callback-lifecycle / error-channel lane.

It should **not** try to become:
- another bindings generator,
- another async runtime,
- another mobile SDK shipkit,
- or a magical “callbacks supported” badge that hides directionality and completion hazards.

## What should count as a worthy crate contribution in this lane now

A worthy interop contribution should now hand other people:

1. **one callback-authority receipt** that says what artifact defines the callback surface, which direction the call crosses, and whether the family is native, one-way, or adapter-mediated;
2. **one callback-completion report** that says whether completion is inline, exactly-once, channel-mediated, cancellation-aware, late-completion-capable, or manual-review-only;
3. **one explicit unexpected-error story** that says whether callback failures map into declared errors, internal error channels, or panic paths;
4. **one portable support bundle** that joins callback authority/completion facts with execution, lifecycle, and error-channel receipts without flattening them.

If a candidate crate cannot do those things, the archive should usually treat it as bridge substrate, generator substrate, or a delivery/runtime lane — not the missing reviewable support-contract layer.
