# Entry 256 — Crate diagnosis support sharpened around symptom identity, first-inspection order, instrumentation honesty, and safe capture boundaries

This pass did **not** add another logger, another metrics exporter, another debugger helper, or another hosted support portal.
It sharpened **P-0525 Crate Diagnosis Surface Pack Kit** into a more implementation-ready support crate.

## Why this moved now

The Rust ecosystem now has enough diagnosis substrate that the missing value has changed shape.

- The December 2025 Rust vision-doc work explicitly asks for **supportive interfaces from crates** rather than only safe abstractions.
- The 2025 State of Rust survey still shows debugging as a real productivity problem while online documentation and code remain the main learning surfaces.
- The February 2026 debugging survey says debugger quality still varies across debuggers, operating systems, async code, visualizers, and expression evaluation.
- Tokio’s tracing guidance and Tokio Console already make structured async diagnosis real.
- `console-subscriber` makes console support easy to advertise, but only when the runtime actually emits the compatible events the console path needs.
- `tokio-metrics` and `metrics` already make runtime/task counters and interval metrics available.
- `miette` and `tracing-error` already make rich codes, help/URL metadata, and async-friendly span context real enough to import.

That combination means the missing crate is no longer “Rust needs better diagnostics in general”.
The sharper missing crate is a **reviewable diagnosis contract** above today’s signal substrate.

## Main planning move

This pass promoted six review objects to first-class status for **P-0525**:

1. **symptom taxonomy** — what a symptom class means and what aliases still point at it,
2. **triage sequence** — what to inspect first, next, and only after explicit escalation,
3. **triage origin** — where each troubleshooting step came from,
4. **signal map** — which traces, metrics, warnings, or diagnostic codes matter for a symptom,
5. **support capture + bundle safety** — what may be attached safely and what must be redacted or blocked,
6. **diagnosis check / diff** — whether the declared contract still matches reality and what changed across releases.

That move matters because the archive had already articulated the lane, but it had not yet made **instrumentation honesty** and **safe support-bundle boundaries** concrete enough to survive real product use.
This pass fixes that.

## Main judgment after the pass

A worthy diagnosis-support crate contribution for Rust should now provide **more than signal emission**.
It should provide:

- explicit **symptom identity** instead of vague timeout/stall buckets,
- explicit **first-inspection order** with provenance,
- explicit **instrumentation honesty** about whether console/tracing/metrics guidance is actually supported,
- explicit **support-capture boundaries** with safety verdicts and redaction posture,
- explicit **remediation classes** with honest manual-review boundaries,
- and a **release-diffable diagnosis surface** another maintainer can inspect without spelunking old issues.

That is more believable and more ecosystem-multiplying than either:

- “just add tracing”,
- “just document tokio-console”,
- or “just pretty-print errors better”.
