# Entry 238 — crate ecosystem pathfinder deepening around evidence origin, freshness windows, and starter-set scope

This pass did **not** promote a new lane.
It sharpened **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit** into a more reviewable shape.

## Why this moved now

The archive had already made P-0509 believable as a `0.1` candidate, but three important decision questions were still too easy to blur together:

1. **Where did this recommendation actually come from?**
   Registry metadata, crate-authored docs, official Rust policy, imported health/trust receipts, and local observation do not carry the same authority.

2. **How fresh does the signal need to be before we freeze a starter set?**
   A newly published crate, a new support signal, or a documentation-surface change may be worth seeing, but not worth silently promoting into a default stack on day one.

3. **What scope is the starter set really for?**
   A teaching baseline, a production baseline, an org-policy baseline, and a target-specific baseline are not interchangeable just because the same crates appear in all four conversations.

Current Rust and ecosystem substrate makes that split timely rather than speculative:
- the official Rust vision-doc work still treats crate discoverability and supportive ecosystem surfaces as part of the real product experience of Rust;
- the 2025 State of Rust survey still says documentation and code remain the main learning surfaces;
- the 2026 debugging survey says debugging remains a major pain point, which means a crate recommendation that ignores support surfaces is still incomplete;
- crates.io now exposes a Security tab, Trusted Publishing enhancements, source-lines-of-code, and `pubtime` in the index;
- crates.io now filters download graphs to Cargo user agents, which improves one signal but still does not turn popularity into task fit;
- docs.rs changed its default target list in October 2025, which can materially change what people see without changing the underlying crate;
- Cargo is actively pushing build-dir-layout changes and build-analysis work that will further change what advanced tool support looks like;
- and rustup continues to evolve rapidly enough that toolchain/setup assumptions drift faster than static crate-picking folklore.

## Main planning move

This pass made three more review objects explicit:

- **evidence origin** — which recommendation facts came from registry metadata, crate-authored docs, official Rust/tooling policy, adjacent imported receipts, or direct local observation;
- **freshness window** — how recent a publish or signal change can be before the recommendation should remain review-first instead of starter-set-first;
- **starter-set scope** — whether the frozen answer is for teaching, production, org-policy, target-specific, or some other bounded lane.

Those are the pieces that make the difference between “the tool ranked some crates” and “the tool emitted a reviewable starter-stack decision somebody else can trust”.

## Main judgment after the pass

A worthy `0.1` crate-choice / starter-set crate should now publish not just a task profile, role coverage report, interop report, decision axes, and a starter-set lock, but also:

- **where each important recommendation fact came from**,
- **how recent signal changes are allowed to affect automatic freezing**,
- and **which exact scope the frozen starter set is intended to serve**.

The sharper move, for now, is still to deepen **P-0509** rather than open another neighboring ranking, curation, docs, or trust-only crate.
