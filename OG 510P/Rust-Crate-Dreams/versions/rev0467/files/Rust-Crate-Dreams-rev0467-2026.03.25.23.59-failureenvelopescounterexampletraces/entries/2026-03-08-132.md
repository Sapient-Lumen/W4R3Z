# Entry 132 — Cargo tool-workflow stack and P-0494 implementation refresh

This pass again did **not** add another top-level proposal.

Instead, it upgraded the archive’s reading of **P-0494 Cargo Compile-Time-Deps Workflow Kit** and gave the Cargo/editor/tooling frontier a cleaner internal shape.

## Main judgment

The repo did not need another vaguely editor-adjacent idea.
It needed a better answer to:

- what **P-0494** should now hand another person,
- how **P-0494** differs from **P-0490** and **P-0489**,
- and what concrete example bundles prove the difference.

The sharper answer is that **P-0494** is a **tool-workflow parity / fallback artifact**:
- one tool-build receipt,
- one compile-surface manifest,
- one parity report,
- and one fallback plan.

## New planning stance

The Cargo tool-workflow stack should now be read as:

1. **P-0494** — what the tool-facing workflow actually built, plus fallback truth
2. **P-0490** — who blocked whom, on which root, plus mitigation
3. **P-0489** — which build-dir consumers still depend on Cargo internals, plus transition receipts

That is a better map than “several similar Cargo/editor problems.”

## Archive-level lesson

When upstream docs become clearer, one of the best repo moves is often not another proposal.
It is a better **receiver-facing crate contract**.

That is what this pass mainly contributed.
