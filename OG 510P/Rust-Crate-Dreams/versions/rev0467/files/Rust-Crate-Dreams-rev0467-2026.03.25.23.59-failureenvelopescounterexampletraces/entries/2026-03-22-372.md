# Entry 372 — Crate health work deepened around imported stewardship signals, routing drift, and portable support bundles

This pass continued the archive’s current strategy of **deepening one top lane until it looks buildable** instead of adding another adjacent scorecard, funding dashboard, or support portal.

The lane chosen here was **P-0011 Crate Health Contract Kit**.
The archive already had a solid thesis, core schemas, and scenario fixtures for health profile, maintenance windows, succession, support intent, coverage, routing, channels, and continuity.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when registry and repository substrate gets richer, and when stewardship posture changes over time, what exactly should another engineer or platform reviewer receive?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official signals still pull in the same direction:

- the January 2026 Rust maintenance post says maintenance work is broad, ongoing, and not reducible to a narrow release-centric story;
- the 2025 State of Rust survey says online documentation remains the preferred canonical reference while worries about developer and maintainer support ticked upward and the post explicitly calls on companies to support crate authors and Rust contributors;
- the January 2026 crates.io update adds a Security tab, Trusted Publishing Only Mode, SLOC, and `pubtime`, which are useful imported stewardship signals but still not the same thing as support routing or continuity truth;
- GitHub’s CODEOWNERS docs remain explicit that CODEOWNERS is about review responsibility and review requests, not a universal release or incident route;
- GitHub’s private vulnerability reporting docs remain explicit that the feature is separate from `SECURITY.md` and provides a secure, structured private intake path only when enabled;
- and the Rust Foundation’s 2026–2028 strategy keeps **Sustainable Maintenance** as a core pillar rather than treating stewardship as a side concern.

That combination makes one archive lesson sharper:

**A worthy crate-health crate is not just “status words plus a few host signals.”
It is a reviewable contract for which stewardship signals were imported, which routes changed, and what portable bundle another person can inspect without flattening substrate into promises.**

## Main repo judgment from this pass

The strongest next move for **P-0011** was to make three more review objects first-class:

1. **`registry-signal.import.json`** — imported crates.io / repository substrate should stay explicit about source, mutability, and whether it informs routing or only context.
2. **`routing-drift.diff.json`** — support posture changes should be diffable when channels, backstops, or ownership routes change.
3. **`health-support-bundle.manifest.json`** — another team should be able to receive one compact bundle that joins declared artifacts, imported signals, and manual-review gaps without pretending they mean the same thing.

The repo also now states a sharper boundary against adjacent lanes:

- crates.io trust/security/publishing substrate can and should be imported into **P-0011** as stewardship context;
- but **P-0011** still owns the receiver-facing workflow for **support routing, continuity, and support-bundle truth**;
- and broader trust/provenance/security posture still belongs to adjacent trust lanes rather than being laundered into “maintained crate” verdicts.

That separation matters.
Otherwise the archive would quietly confuse “the host platform exposes more trust/security substrate” with “another team can now tell who responds, where to file, what changed, and what happens during absence.”

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One imported-signal receipt** that says which registry/repo host facts were imported and how much they are allowed to mean.
2. **One routing drift object** that says whether support posture actually changed across releases or repository moves.
3. **One portable support bundle** that joins declarations, imports, and manual-review gaps without flattening them.
4. **One continuity view** that remains usable even when ownership or repository location changes.
5. **One conservative stewardship verdict** that keeps review routing, security reporting, release ownership, docs freshness, and succession from becoming one fake status word.
6. **One diffable contract** that a downstream adopter, internal platform team, or maintainer successor can actually review.

If a crate idea in this territory cannot supply those review objects, it is still probably substrate, social analytics, or scorekeeping.

## New repo-level lesson

The archive is stronger when it refuses to flatten **imported stewardship context** into **declared support promises**.

Future passes should therefore keep asking:

1. what was maintainer-declared,
2. what was only imported from crates.io or the host platform,
3. what changed in routing or continuity over time,
4. and what still remains manual-review-only despite richer platform substrate.

That is a better use of repo time than inventing another maintainer score, popularity ranking, or donation dashboard.
