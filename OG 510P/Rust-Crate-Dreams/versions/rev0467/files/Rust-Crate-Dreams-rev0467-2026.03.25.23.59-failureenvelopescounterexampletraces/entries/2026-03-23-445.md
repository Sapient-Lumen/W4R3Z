# Entry 445 — make trigger intake and recheck cadence first-class, and treat packet ops as part of the practical core

This pass again chose **deepen over append**.

The archive already had a better answer for:
- how a team compares plausible crates,
- how it freezes a basis,
- how it refreshes that basis later,
- and how it records a transition posture when the old answer stops holding.

What it still lacked was a clean answer to the next operational question:

> how does a worthy crate tell another team **when** to come back, **why** to come back, and **what packet** should be opened next?

That missing seam matters because the current Rust substrate now exposes more usable drift signals than it used to:
- crates.io now records `pubtime`, surfaces advisories on the Security tab, and strengthens trusted-publishing posture;
- crates.io also intentionally reduced routine malware blog-post noise in favor of RustSec advisories and more selective public notices;
- docs.rs now has clearer build constraints, metadata knobs, rustdoc JSON, and target/build visibility that can drift over time;
- Cargo is explicitly asking projects to test build-dir layout changes because many tools still depend on internal paths;
- Cargo build-analysis planning is about persisting local build metadata, rebuild reasons, and run-linked timing data;
- and `cargo metadata`, Cargo JSON messages, and `cargo package` already give versioned or compatibility-governed machine surfaces a recheck system can stand on.

## Main judgment

A worthy crate in the current practical core should no longer stop at:
- **compare**,
- **freeze**,
- **refresh**,
- **transition**.

It should also provide a credible **ops loop** for those packets.

That means three extra product obligations now belong in the bar:

### 1. Trigger intake must be explicit

A later review must say **what opened it**.

Examples:
- new release,
- advisory,
- docs surface shift,
- build substrate change,
- target/support visibility shift,
- local incident,
- or manual architectural recheck.

Without that, later passes too easily collapse “new fact exists” into “therefore replace the dependency” or “therefore rerun the whole comparison from scratch”.

### 2. Recheck cadence must be reviewable

A worthy crate should tell other people:
- what it watches,
- how often it expects revalidation,
- which triggers are urgent,
- which triggers only open a review ticket,
- and which triggers are merely informative.

This is especially important now that crates.io is intentionally reducing high-noise malicious-crate announcements and because public surfaces like docs.rs, Cargo, and registry metadata keep evolving.

### 3. Trigger intake and posture must stay separate

A crate should not silently convert imported signals into a posture decision.

It should keep these separate objects:
1. **trigger intake** — what was observed,
2. **recheck ticket** — what review is being opened,
3. **revalidation packet** — whether the old choice still stands,
4. **transition packet** — what new posture is being adopted if it does not.

That separation is what keeps a review system honest.

## Salience consequence

This pass still does **not** justify a dramatic salience rerank.
The top frontier remains broadly stable.

But it does sharpen the practical interpretation of the front door:
- **P-0509 Pathfinder** is no longer just a comparator;
- **P-0536 Crate Knowledge Pack** is no longer just a frozen review basis;
- **P-0535 Dependency Lifecycle Transition Kit** should now supply the minimal **trigger-intake and recheck-loop** layer that keeps those packets alive over time.

## Practical queue consequence

The practical queue now reads best as:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, trigger intake, and recheck tickets
2. **P-0486** — debug witness bundles with comparable support packets
3. **P-0496** — restricted-delivery / source-parity bundles
4. **P-0472** — docs.rs parity doctor and issue bundles
5. **P-0489** — build-dir dual-support transition
6. **P-0484** — hard-domain target/support truth
7. **P-0058** — native provenance for offline and mixed-language stacks

Interpretation:
- the front door is now best thought of as a **living packet loop**, not a one-shot recommendation;
- `P-0535` still does not outrank debuggability or async in broad salience,
- but it now belongs inside the **first practical slice** because compare/freeze packets without a trigger/recheck loop are not enough for long-lived teams.

## What this pass says a worthy crate should provide other people

A worthy crate in the practical core should now answer **ten** operational questions:

1. **compare** — what are the plausible choices now?
2. **freeze** — what exact basis did the chosen answer stand on?
3. **watch** — which surfaces are being watched later?
4. **trigger** — what exact event opened review?
5. **ticket** — what review packet should be opened next?
6. **refresh** — what later facts changed and which did not?
7. **revalidate** — does the old choice still stand under the same task and policy?
8. **transition** — if not, what posture follows now?
9. **anchor** — what lock, patch, mirror, fork, or shared policy currently makes that posture hold?
10. **ceiling** — what still requires manual review?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
