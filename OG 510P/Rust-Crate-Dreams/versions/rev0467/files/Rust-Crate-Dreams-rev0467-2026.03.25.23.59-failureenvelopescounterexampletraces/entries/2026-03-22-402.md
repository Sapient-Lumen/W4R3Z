# Entry 402 — debuggability support now needs session-scope receipts, capability witnesses, and claim-ceiling honesty

This pass deepens an existing debugging / release-support lane instead of opening another debugger wrapper, crash backend, or IDE integration helper.
It sharpens:

**P-0486 Debuggability Support Contract Kit**.

## Why this lane earned another serious refresh now

The archive already had a stronger-than-average story for symbol sidecars, visualizer assets, broad support posture, backend coverage, source-lookup materials, and portable support bundles.
What it still left too easy to flatten was a more operational question:

> “Which *user-facing debugger tasks* were actually witnessed in which session scope, and where does the claim stop even though symbols and one checked lane exist?”

Current official sources make that split sharper than before:

- the Rust debugging survey says ideal support means multiple debugger versions across operating systems, quality visualizers, first-class async debugging, and Rust expression evaluation, while warning that support quality still varies a lot by debugger and OS;
- the rustc debugging-support guide says GDB’s Rust expression parser supports only a subset of Rust, LLDB implements slightly less than GDB, GDB generally works better on Linux, and WinDbg/CDB rely on PDB-based visualization on Windows;
- the Rust Reference says embedded GDB pretty printers are **not** auto-loaded by default and require safe-path configuration or per-user setup;
- compiletest directives in the rustc-dev-guide keep debugger testing explicitly lane-scoped by debugger family, version, OS, compare mode, and related conditions;
- and the LLDB internals guide now documents that LLDB’s PDB support changed reader defaults in version 22, which is exactly the kind of debugger-version seam that makes “debugging worked” too vague to review.

Together those sources say the missing crate contribution is no longer just “capture a debug-support bundle” or even “record backend coverage.”
It is a reviewable support layer for **session scope**, **capability witnesses**, and **claim ceilings** above symbol/visualizer discovery and backend-family observation.

## Main judgment after the refresh

**P-0486** is stronger when it owns three more receiver-facing truths:

1. **session scope** — whether evidence came from a live local session, remote target, post-mortem core / minidump lane, containerized process, or other bounded subject;
2. **capability witness** — which concrete user-facing tasks were actually demonstrated (`breakpoint_hit`, `step_over`, `backtrace`, `locals_expand`, `pretty_render`, `rust_expression_eval`, `async_task_inspection`, etc.);
3. **claim ceiling** — what the strongest honest external claim is after accounting for debugger family, version, OS, subject scope, and unwitnessed tasks.

That means a worthy crate in this lane should now explicitly own:

- `session-scope.receipt.json`,
- `capability-witness.report.json`,
- and `claim-ceiling.report.json`

above the earlier support-posture / symbol-layout / visualizer / backend-observation / source-material lane.

It should **not** try to become:

- a debugger itself,
- a universal expression-evaluation bridge,
- an async-debugger platform,
- or a replay / record-debugger product.

## What should count as a worthy crate contribution in this lane now

A worthy debuggability-support contribution should now hand other people:

1. **one session-scope receipt** that says what sort of debug subject was actually under test and what host/target/session route bounded the claim;
2. **one capability-witness report** that records concrete debugger tasks as observed, partial, blocked, unwitnessed, or manual-review-only;
3. **one claim-ceiling report** that explains why a successful backtrace/locals/pretty-render lane still does not justify broad claims about Rust expression evaluation, async debugging, or other OS / backend / version lanes;
4. **one portable bundle** that keeps posture, artifacts, source materials, session scope, witnessed tasks, and remaining claim ceilings separate.

If a candidate crate cannot do those things, the archive should usually treat it as debugger folklore, a launcher helper, debugger automation, or a broader debugging platform — not the missing reviewable support-contract layer.
