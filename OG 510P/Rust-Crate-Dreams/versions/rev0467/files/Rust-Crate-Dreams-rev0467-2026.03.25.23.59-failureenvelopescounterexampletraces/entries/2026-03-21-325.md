# Entry 325 — Wasm plugin kit deepened for WIT world truth, capability grants, execution budgets, and instance lifecycle

This pass deepened **P-0002 Wasm Plugin Kit** instead of adding another runtime, plugin marketplace, or native ABI-stable dynamic-library lane.

## Why this lane earned another serious pass

The archive already had the intuition that Rust should have a better plugin story.
What it lacked was a build-shaped answer for *which truths actually belong in one reviewable Wasm plugin contract*.

Current substrate is now strong enough to make that precise:

- the Rust project’s 2026 flagships explicitly elevate Wasm Components as a major Rust frontier;
- Wasmtime now documents a calculator-with-plugins example built out of WebAssembly components;
- Wasmtime’s component API makes WIT worlds, generated bindings, and host linkers first-class;
- the component-model docs now make packages, worlds, and distribution/fetching part of the ordinary mental model;
- `cargo component` can scaffold and publish components, but it still explicitly says it is experimental;
- Extism documents a practical plugin stack with manifests, immutable host config, allowlisted hosts/paths, timeouts, and pooled instances;
- Wasmtime’s execution docs make fuel, epochs, and pooling decisions materially different operational truths.

That means a worthy crate here should not simply say “supports Wasm plugins”.
It should say what interface world is being promised, what the host grants, how the plugin is budgeted, and whether instance reuse/state persistence are in play.

## What moved this time

The main planning move was to stop treating all Wasm plugin support as one kind of truth.

This pass elevated four review objects into first-class status for **P-0002**:

1. **plugin-interface truth** — which WIT package/world or host-function surface is actually authoritative;
2. **capability-grant truth** — what filesystem/network/host-function/configuration reach really exists;
3. **execution-budget truth** — whether interruption/budget semantics are fuel, epochs, timeout-only, pool/store limits, or weaker/manual-review posture;
4. **instance-lifecycle truth** — whether calls are fresh, pooled, warm-reused, or long-lived.

## Why this matters now

The ecosystem evidence is no longer ambiguous:

- official Rust planning says Wasm Components matter in 2026;
- Wasmtime shows real plugin loading patterns rather than just low-level runtime APIs;
- WIT packages and worlds give an explicit interface vocabulary;
- `cargo component` proves the build lane exists but is not yet stable enough to stand in for a whole contract;
- Extism proves capability grants and configuration posture can already be typed concretely;
- Wasmtime’s own docs show that fuel, epochs, timeouts, pooling, and warm-slot reuse are materially different truths.

That means a worthy plugin crate should not let “component build succeeded” or “plugin is sandboxed” quietly over-claim interface authority, capability scope, budget determinism, or per-call freshness.

## Main judgment after the pass

A worthy Wasm plugin contribution should now provide more than a loader or scaffolder.
It should also provide:

- one explicit **plugin-interface receipt**,
- one explicit **capability-grant receipt**,
- one explicit **execution-budget receipt**,
- one explicit **instance-lifecycle receipt**,
- and one conservative rule for when a build artifact is useful but still too experimental, host-specific, or stateful to bluff stronger portability.
