# Entry 268 — crate upgrade support sharpened around source lineage, hazard arbitration, and active follow-through state

This pass came from a cross-datacube read rather than from another Rust release-tool scan.
The winning changes were the ones that cleanly transferred into **P-0514 Crate Upgrade Pack Kit** without collapsing its lane.

## What moved this time

Three unrelated datacubes kept pointing at the same missing discipline inside the upgrade-pack story:

- **TriKEM** made the strongest case that imported human-authored surfaces need a **fetch boundary / source-lineage / fail-closed** posture before they get promoted into something load-bearing.
- **DelayBasin** made the strongest case that when adjacent authorities disagree, the archive should preserve a compact **arbitration / tie / abstention** object instead of forcing one polished winner.
- **pyCausalWeave** made the strongest case that “this step belongs to the object” and “this step is currently being requested or has been completed on the current head” are different truths.

Those three moves apply directly to release-to-release upgrade support.

## Main planning move

The previous pass already made **hazard authority**, **package-scope truth**, and **follow-through coverage** explicit.
This pass adds three sharper review objects above them:

1. **source-lineage truth** — which imported release/changelog/docs/thread surfaces were allowed to back hazard authority, how they were fetched, and whether they were pinned strongly enough to count as load-bearing evidence;
2. **hazard-arbitration truth** — what happens when SemVer/public-API evidence, maintainer notes, feature-policy facts, and observed behavior checks disagree or only nearly agree;
3. **active follow-through state** — which migration steps belong to the lane, which ones are still actively requested, which were completed only on an older lane, and which need an explicit re-request on the current `from -> to` pair.

## Why this matters

Without **source lineage**, the crate can accidentally treat:

- a floating “latest release” page,
- an unpinned changelog path,
- a docs page that moved,
- or an issue-thread comment

as if they all carried the same authority as a release-pinned migration note.
They do not.

Without **hazard arbitration**, the crate can accidentally flatten:

- “SemVer diff stayed green,”
- “feature/default policy changed,”
- “the checked recipe still failed,”
- and “the maintainer note says manual review is required”

into one fake consensus.
That is the wrong shape.
Sometimes the right answer is **manual-review-required because the authorities do not honestly collapse**.

Without **active follow-through state**, the crate can accidentally flatten:

- “docs/config/example updates are part of this migration family,”
- “those steps were completed on an older release pair,”
- and “the current release pair still needs a fresh pass”

into one stale “already handled” story.
That is the same structural mistake as keeping reviewer roster presence and active review request in one field.

## Main judgment after the pass

A worthy upgrade-support crate should now provide **more than hazard classes, package scope, and fix receipts**.
It should also provide:

- **source-lineage receipts** for imported human-authored migration evidence,
- **hazard-arbitration reports** when adjacent authorities disagree,
- and **followthrough-state reports** that keep lane membership, current request state, and prior completion receipts separate.

That makes the upgrade pack more honest in exactly the places where release support usually starts to lie:

- source surfaces look canonical when they are only nearby,
- disagreements get polished into consensus,
- and old manual work quietly gets counted as current completion.
