# Entry 384 — FFI boundary conformance deepened around projection basis, derivative parity, and receiver-visible drift

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another generator wrapper, language shipkit, or generic interop dashboard.

The lane chosen here was **P-0121 FFI Boundary & Bindings Conformance Kit**.
The archive already had a strong story for interface authority, ownership transfer, unwind posture, callback execution, callback lifecycle, binding coverage, layout authority, error channels, and portable support bundles.
What it still lacked was a sharper answer to one downstream question:

> when a generated header, source binding, export macro, or component custom section exists, what exactly should another maintainer receive so **projection basis**, **derivative parity**, and **receiver-visible drift** do not get flattened into one vague “the bindings are covered” story?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official and current ecosystem sources all reinforce the same pressure point:

- the February 2026 program-management update keeps **cross-language interop** explicit as an application area;
- current release notes keep both `unsafe extern` and `extern "C-unwind"` as explicit, reviewable boundary substrate rather than background details;
- UniFFI’s current docs say foreign-language bindings generation produces **source code** and does not build that code for you, and its current proc-macro guide allows mixed UDL/proc-macro surfaces while warning that `#[cfg]` inside `#[uniffi::export]` blocks does not behave as one might naively assume;
- Diplomat’s current backend-attribute docs make backend-specific renames, namespaces, and other projection changes first-class rather than incidental;
- current `cbindgen` docs expose substantial configuration around generated bindings, including layout, renaming, macro expansion, parsing, and documentation style/length;
- current `wit-bindgen-rust` options show that export-macro visibility/naming, custom-section helper generation, and generated type breadth can materially shape emitted derivative artifacts;
- and current `cxx` docs still distinguish bridge source-of-truth direction, namespaces, names, async lanes, and error conversion rather than treating generated glue as a single opaque certainty.

That combination makes one archive lesson sharper:

**A worthy FFI support crate is not just authority + ownership + callbacks.**
**It is also a reviewable contract for what generated foreign surface is being discussed, how it was shaped, whether it still faithfully reflects the authority source, and what changed across releases.**

## Main repo judgment from this pass

The strongest next move for **P-0121** was to make three more receiver-facing review objects first-class:

1. **`projection-basis.receipt.json`** — records what derivative foreign artifact is being reviewed, what authority it projects from, what tool/backend/configuration shaped it, whether it is full, subset, renamed, backend-shaped, or packaging-only, and what still requires manual review.
2. **`derivative-parity.report.json`** — records whether that derivative artifact still faithfully reflects the primary authority, what receiver-visible differences remain, and what proof class backs the parity judgment.
3. **`projection-drift.report.json`** — records release-to-release foreign-surface drift, whether it came from authority change versus generator/config change, and whether the result is additive, receiver-visible, breaking, or manual-review-only.

The repo also now states a sharper boundary against adjacent lanes:

- shipkits still own package/distribution truth for SwiftPM, Node-API, JNI/JAR, NuGet, RubyGems, and similar delivery lanes;
- generators/bridges still own generation/runtime substrate;
- schema/API-compatibility lanes still own broader language-agnostic compatibility review;
- but **P-0121** now owns the receiver-facing workflow for **authority, projection basis, derivative parity, lifecycle, boundary semantics, and receiver-visible drift**.

That separation matters.
Otherwise the archive would quietly confuse “we generated a header,” “a binding package exists,” “the same bridge family is still in use,” and “the foreign-facing contract is faithfully unchanged” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One interface-authority import** that says what artifact is actually primary.
2. **One projection-basis receipt** that says what generated foreign artifact is under discussion and how it was shaped.
3. **One derivative-parity report** that says whether that generated artifact is a faithful stand-in, a subset, a backend-specific variant, or a manual-review surface.
4. **One ownership-transfer receipt** that says who owns values, handles, and frees.
5. **One unwind-posture receipt** that says what panic/unwind story actually crosses the boundary.
6. **One callback execution/lifecycle pair** that says where callbacks run and what teardown/cancel/drop rules keep them honest.
7. **One binding/layout/error set** that says what is checked, what representation crosses, and what failure semantics actually exist.
8. **One projection-drift report** so a release cannot quietly change the foreign-facing surface just because a generator/backend/config changed.
9. **One portable bundle** that another maintainer can inspect without reverse-engineering generator output, build scripts, and docs by hand.

If a crate idea in this territory cannot supply those review objects, it is still probably a generator helper, a shipkit, or a generic compatibility tool rather than the missing boundary-support layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten:

1. **primary interface authority** and **configured derivative projection**,
2. **generated source exists** and **generated source was actually built/packaged/proved**, 
3. **same boundary family is still present** and **the receiver-visible projection is still the same**,
4. **backend-specific shaping** and **cross-backend equivalence**.

Future passes should therefore keep asking:

- what exact foreign artifact is being discussed,
- what authority it projects from,
- what tool/backend/config shaped it,
- whether parity is full, subset, nonuniform, or manual-review-only,
- and what one portable boundary bundle another maintainer should receive.

That is a better use of repo time than inventing another generator wrapper, language-package helper, or broad “FFI support” dashboard that still cannot hand someone an honest projection witness.
