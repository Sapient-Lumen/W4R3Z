# Entry 403 — crate off-ramp work now needs successor-authority receipts, stopgap horizons, and witnessed migration scope

This pass deepens an existing ecosystem-supportiveness lane instead of adding another advisory client, dependency score, or registry policy helper.
It sharpens:

**P-0515 Crate Off-Ramp Pack Kit**.

## Why this lane earned another serious refresh now

The archive already had a stronger story for successor maps, deprecation-surface receipts, declared migration recipes, successor-compat checks, and sunset diffs.
What it still left too easy to flatten was a more operational question:

> “Who actually authored the successor claim, is the current answer only a stopgap, and what migration path was really witnessed?”

Current official sources make that split sharper than before:

- the March 2026 challenges write-up says ecosystem navigation and tacit knowledge are still live pain points;
- the January 2026 crates.io update adds richer receiver-visible security / trusted-publishing / SLOC substrate but still only as imported context;
- the Rust Reference says `#[deprecated]` can carry a `since` and `note`, and rustdoc will display them;
- the rustc lint docs still say deprecations should usually include what to use instead;
- Cargo’s SemVer guide explicitly discusses staging deprecations and suggests feature-gating them before a later breaking removal;
- and Cargo’s yank docs still say yanking changes new dependency resolution without deleting code or explaining the long-term replacement plan.

Together those sources say the missing crate contribution is no longer just “capture an off-ramp pack” or even “record a successor map.”
It is a reviewable support layer for **successor authority**, **stopgap horizon**, and **recipe witness scope** above deprecation/advisory/yank substrate.

## Main judgment after the refresh

**P-0515** is stronger when it owns four more receiver-facing truths:

1. **successor authority** — whether the long-term successor claim came from a crate-authored pack, rustdoc deprecation note, docs page, advisory stopgap, yank pressure, or third-party inference;
2. **stopgap horizon** — whether a shim, last-safe pin, or migrate-now lane is temporary, deadline-known, deadline-unknown, review-due, or manual-review-only;
3. **recipe witness scope** — which migration recipe actually ran, under which feature/target/runtime axes, and which axes remain uncovered or behavior-review-only;
4. **portable off-ramp bundle inventory** — how successor class, authority basis, horizon, declared recipe, and witnessed recipe scope travel together without collapsing into one fake verdict.

That means a worthy crate in this lane should now explicitly own:

- `successor-authority.receipt.json`,
- `stopgap-horizon.report.json`,
- `recipe-witness.report.json`,
- and `offramp-support-bundle.manifest.json`

above the earlier successor-map / deprecation-surface / recipe / compat / sunset-check lane.

It should **not** try to become:
- a universal code rewrite engine,
- a generic maintenance score,
- a security scanner,
- or a registry policy service.

## What should count as a worthy crate contribution in this lane now

A worthy off-ramp-support contribution should now hand other people:

1. **one successor-authority receipt** that says who actually authored the exit claim and whether it is long-term or only a stopgap;
2. **one stopgap-horizon report** that makes expiry, review windows, and “successor still maturing” lanes visible;
3. **one recipe-witness report** that records the exact migration path actually exercised and the axes still uncovered;
4. **one portable off-ramp bundle** that keeps successor class, authority, horizon, declared steps, and witnessed scope separate.

If a candidate crate cannot do those things, the archive should usually treat it as deprecation prose, security/advisory tooling, or migration folklore — not the missing reviewable exit-contract layer.
