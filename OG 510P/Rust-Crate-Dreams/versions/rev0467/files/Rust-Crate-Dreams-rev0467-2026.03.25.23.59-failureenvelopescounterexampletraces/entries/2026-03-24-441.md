# Entry 441 — map receiver personas, design first-adopter programs, and make restricted-delivery evidence a real product lane again

This pass again chose **deepen over append**.

The archive already has a broad frontier and a decent first-release-bundle vocabulary.
What it still needed was a more operational answer to three harder questions:

1. **who** the leading crates should serve first,
2. what a realistic **first adopter program** looks like for those crates in theory and practice,
3. and whether offline / mirrored / vendored delivery truth is important enough to pull back toward the practical core.

## Main judgment

Three repo moves were worth making now.

### 1. Add a receiver-persona map for the current epic frontier

The archive had already become much better at saying what files a crate should emit.
It still needed a more durable answer to:

> which other people actually receive that value?

The new receiver map keeps the archive from designing only for “the maintainer in the abstract”.
It makes the top lanes answer for real receivers such as:

- an application maintainer choosing a baseline stack,
- a platform engineer standardizing internal defaults,
- a release / CI engineer trying to freeze or replay an environment,
- a reviewer or security engineer who needs one auditable packet,
- an offline / regulated adopter who cannot rely on hosted surfaces,
- and an LLM/tooling consumer that needs a pinned machine-usable basis.

That matters because a crate is not “epic” just because it is broadly useful.
It is epic when it gives **multiple receiver classes** a boring, replayable artifact they can actually use.

### 2. Add first-adopter programs for the top practical crates

The archive already had delivery cards and first-release bundles.
The next missing layer was:

> how would we introduce this crate to the world without overclaiming?

The new first-adopter-program note answers that for the leading practical lanes:
- **P-0509 Pathfinder**
- **P-0536 Crate Knowledge Pack**
- **P-0486 Debuggability Support**
- **P-0496 Cargo Vendor & Source Parity**

Each program now has:
- a narrow first cohort,
- a task shape,
- the exact packets they should receive,
- success and failure conditions,
- and a rule for what the crate must still refuse to claim.

That makes the repo more buildable because it shifts attention from abstract “ecosystem need” to a pilotable `0.1`.

### 3. Restore restricted-delivery evidence as a serious practical lane

Fresh 2025–2026 signals now make it harder to leave source-parity / restricted-delivery support below the practical core:

- the Rust ecosystem is actively pursuing **cryptographically verified mirrors** and local mirror use,
- crates.io now publishes `pubtime` in the index and improved trust surfaces,
- Cargo is still changing build-dir internals because tools depend on unspecified details,
- the latest Cargo extraction CVE is a reminder that “dependency download” is not a trivial side concern,
- and safety-critical / offline / enterprise adopters still thin out at the tooling and evidence boundary.

That does **not** mean the archive should collapse mirroring, vendoring, source parity, transfer, or review into one universal supply-chain crate.
It does mean **P-0496 Cargo Vendor & Source Parity Kit** should be treated again as a practical near-frontier lane, because other people still need one boring bundle that answers:

- what source identities resolved,
- what physical roots and mirrors were actually used,
- what stayed outside the covered boundary,
- what offline claim is honest,
- and what imported mirror verification does **not** settle.

## Salience consequence

This pass still does **not** justify a dramatic top-three rerank.
The top control-plane salience remains:

1. **P-0509 Crate Ecosystem Pathfinder & Decision-Pack Kit**
2. **P-0486 Debuggability Support Contract Kit**
3. **P-0538 Concurrency Contract Kit**
4. **P-0472 Docs.rs Build Parity & Evidence Kit**

The main change is below that top block:
- **P-0536 Crate Knowledge Pack Kit** remains high because supportive, cited, machine-usable packets are now central rather than optional;
- **P-0496 Cargo Vendor & Source Parity Kit** is promoted back into the active practical frontier because restricted-delivery truth is increasingly a cross-domain adoption bottleneck rather than a niche Cargo edge case.

## Practical queue consequence

The practical near-term queue is now best read as:

1. **P-0509** — receiver-facing decision packets
2. **P-0536** — pinned citation + answer-boundary packs for those packets
3. **P-0486** — debug capability packets aligned to the same review flows
4. **P-0496** — restricted-delivery / source-parity bundles
5. **P-0472** — docs.rs hosted/local parity doctor
6. **P-0489** — build-dir dual-support transition
7. **P-0535** — dependency lifecycle / off-ramp packets
8. **P-0484** — target/support truth for hard domains
9. **P-0058** — native prerequisite / ABI provenance

Interpretation:
- the archive is still not saying “supply chain before everything else”;
- it is saying that **restricted-delivery evidence** belongs in the same practical build conversation as docs/build parity and target/native truth.

## What this pass says a worthy crate should provide other people

A worthy crate contribution should now answer **all four** of these questions cleanly:

1. **receiver** — who gets the packet?
2. **artifact** — what exact files / reports / manifests do they receive?
3. **program** — what narrow first adoption loop proves the crate is useful?
4. **ceiling** — what must the crate refuse to claim even after that loop succeeds?

If the archive cannot answer those yet, the proposal may still be important, but it is probably not yet ready for promotion.
