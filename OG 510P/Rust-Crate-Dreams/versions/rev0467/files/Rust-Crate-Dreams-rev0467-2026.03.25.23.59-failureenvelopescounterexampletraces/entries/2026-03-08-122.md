# Entry 122 — JAR/JNI ship contracts and a stricter worthy-crates frontier

This pass did two things on purpose:

1. it promoted one more **foreign package ecosystem seam** that now looks genuinely sharp, and
2. it added a tighter salience scan so future revisions spend more time **ranking and compressing** rather than reflexively widening the archive.

New proposal:

- P-0500 JAR/JNI Native ShipKit

Why it rose:

- The archive already had a convincing foreign-package pattern for **Python wheels**, **Apple XCFrameworks**, **Node/npm prebuilds**, and **NuGet native assets**.
- The next missing sibling was the **JVM**.
- Oracle now documents native-library loading as a more explicit **restricted/native-access** surface, while Maven classifiers and JNI authoring substrate (`jni` / `jni-rs`) are already real enough that “how do I bind Rust to Java?” is no longer the sharp question.
- The sharper question is: **what exactly did we ship, how does the Java side load it, and how honest is the support contract?**

What changed in archive judgment:

- The archive now treats **Rust→JVM native shipping** as a proper package-contract problem, not as just another JNI-binding problem.
- A worthy crate here is a **classifier matrix + loader receipt + native-access report + support-risk bundle**, not a new wrapper generator.
- The archive also now has a newer salience file that makes the current top tier more explicit: the strongest crates are increasingly the ones that make Rust more **explainable, reviewable, and shippable**.

Archive hygiene added in this pass:

- Added a `known-existing` note that future revisions must not confuse **JNI authoring substrate** with a boring **JAR/JNI shipping contract**.
- Added an `llm-hygiene` reminder that modern JVM native access, loader strategy, classifiers, and library-base-name drift are all part of the actual release contract.
- Added a fresh salience scan (`meta/frontier-salience-2026-03-08.md`) that ranks the current frontier and explicitly demotes more archive sprawl.
