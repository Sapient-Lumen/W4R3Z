# Entry 199 — crate runtime handoff packs promoted as the runtime-side supportiveness lane

This pass added a new top-level proposal: **P-0513 Crate Runtime Handoff Pack Kit**.
It also added the lane-boundary and fixture scaffolding needed to stop future passes from collapsing crate choice, support claims, shared interop profiles, compile-time guidance, generic report rendering, tracing/observability, and runtime failure handoff into one fake “supportiveness tooling” story.

## Why this moved now

Several current Rust signals line up unusually well.

### 1. The ecosystem frontier still lacked a runtime-side supportiveness lane

The archive already had stronger answers for:

- **task-first crate choice** via **P-0509**,
- **producer-side support / interop claims** via **P-0510**,
- **shared interop profile contracts** via **P-0511**,
- and **compile-time / early-failure guidance** via **P-0512**.

But it still lacked a good answer to:

- “Once the chosen crate has already failed at runtime, what exactly does it hand off?”

That left the archive with better answers for **selection**, **support claims**, and **early failure guidance** than for **runtime recovery handoff**.

### 2. Official Rust guidance now names supportive crate interfaces while debugging remains a live pain

The December 2025 vision-doc post says Rust should “double down on extensibility” and specifically calls for **better diagnostics and guidance from crates**.
The 2025 State of Rust survey says debugging remains a non-trivial productivity problem, while online documentation and code are still the primary learning path.

That combination makes runtime support surfaces worth treating as first-class crate design.

### 3. The standard library has runtime-failure substrate, but not the maintainer workflow

The `std::error` docs explicitly define errors as Rust’s mechanism for anticipated runtime failure modes.
`Error::source()` is documented as the way to cross abstraction boundaries honestly.
`std::backtrace` exists, but capture is environment-controlled because of runtime cost.
`std::panic::set_hook` lets applications customize panic reporting with payload and location.

Those are real ingredients, but they still do **not** give crate authors one boring workflow for:

- declaring what runtime facts are handed off,
- classifying safe versus sensitive fields,
- separating error-path receipts from panic-path receipts,
- attaching recovery steps,
- and diffing the runtime support surface across releases.

### 4. The RFC and ecosystem trail show real demand for richer runtime context, but only in fragments

RFC 3192 / dyno explicitly uses `Error` as a motivating example for richer typed context like backtraces, runtime state, environment details, and help-text suggestions.
The surviving `Request` API is still largely `std`-internal, which is itself evidence that the broader ecosystem workflow is incomplete.

At the same time, current crates show useful pieces already exist:

- `error-stack` captures contexts and attachments,
- `miette` can render machine-readable JSON,
- `tracing-error` captures logical span context,
- and `human-panic` generates a user-submittable crash report with an explicit privacy stance.

What is still missing is the **joined pack/check/redact/diff layer**.

## Current judgment

The worthy crate here is not:

- another ranking engine,
- another support-claims schema,
- another interop profile pack,
- another renderer,
- or a whole observability backend.

The worthy crate is the boring runtime supportiveness layer that can hand other people:

1. one **runtime handoff pack**,
2. one **runtime-context receipt**,
3. one **panic-handoff receipt**,
4. one **redaction profile**,
5. one **runtime-handoff check report**,
6. one **failure-shape diff**,
7. and one explicit **manual-review boundary** when automatic export would be unsafe.
