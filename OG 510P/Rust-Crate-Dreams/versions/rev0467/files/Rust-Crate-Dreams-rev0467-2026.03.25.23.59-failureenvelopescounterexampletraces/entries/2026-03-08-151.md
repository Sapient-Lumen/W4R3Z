# Entry 151 — resolver why-bundles also need dependency-kind lane and platform-coverage truth

This pass again did **not** add another top-level proposal.

Instead, it sharpened **P-0468 Cargo Resolver Explanation Kit** where the archive still had the most leverage left: the crate now has a clearer plan for **dependency-kind lane partition** and **target/platform coverage truth** above today’s mixed Cargo surfaces.

## Main judgment

The important missing crate is not another dependency graph explorer.
It is a **receiver-facing resolver bundle** that can tell another person:

- whether a feature state belongs to a normal, build/proc-macro, or dev lane,
- whether a human-facing surface merged lanes that the selected build keeps separate,
- which target-specific clauses were actually in scope for the selected command,
- whether metadata/graph capture included all targets or was narrowed with `--filter-platform`,
- and whether the answer should stay conservative or manual-review-required.
