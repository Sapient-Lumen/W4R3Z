# Entry 379 — crate knowledge pack work deepened around material basis, export policy, and excerpt-lineage honesty

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another docs portal, parser wrapper, or assistant-facing gimmick.

The lane chosen here was **P-0536 Crate Knowledge Pack Kit**.
The archive already had a strong thesis, API authority receipts, docs-source manifests, example lineage, hosted docs.rs presence, slice manifests, and a compact bundle story.
What it still lacked was a sharper answer to a harder receiver-facing question:

> when somebody says “here is the small crate pack you should trust for support, search, or assistant work”, what exactly should another engineer receive so **floating docs.rs redirects**, **rustdoc JSON availability/version drift**, **download/archive caveats**, **redaction policy**, and **actual excerpt lineage** do not get flattened into one vague “the docs pack is canonical” tone?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Rust and docs.rs sources still converge on the same pressure point:

- the 2025 State of Rust survey still says online documentation is the preferred canonical reference, followed by studying the code itself, while hinting that some learning activity is moving toward LLM tooling;
- the March 2026 Rust challenges write-up again argues for better ecosystem guidance and domain-specific learning materials rather than one generic tutorial surface;
- docs.rs now explicitly hosts rustdoc JSON, but says files may have been built with older rustdoc versions and that consumers may need to inspect `format_version`;
- docs.rs also says rustdoc JSON hosting only began on 2025-05-23, so older releases may still lack that material entirely until rebuild coverage reaches them;
- docs.rs build docs make hosted README rules, `docsrs` cfg behavior, target posture, sandbox limits, and metadata knobs concrete enough that “hosted docs truth” is richer than one page URL;
- docs.rs shorthand URLs deliberately float across semver ranges or “latest”, which is convenient for browsing but not the same thing as a pinned review/citation surface;
- docs.rs download archives include HTML for all built targets, but come with `static-root-path` caveats, target-root layout differences, and missing invocation-specific toolchain assets;
- and current Cargo/rustdoc docs still say JSON output is experimental/nightly-driven substrate.

That combination makes one archive lesson sharper:

**A worthy crate-knowledge crate is not just “join rustdoc JSON, docs.rs, and a README into one bundle.”  
It is a reviewable contract for what exact materials were imported, what export/redaction policy shaped the bundle, and what exact excerpts made it into the small slice another reviewer or support engineer received.**

## Main repo judgment from this pass

The strongest next move for **P-0536** was to make three more receiver-facing review objects first-class:

1. **`material-basis.receipt.json`** — records the exact materials imported into the pack: rustdoc JSON availability and format version, pinned vs floating docs.rs URLs, hosted HTML/download archive usage, target/default-target context, and caveats such as missing pre-2025 rustdoc JSON coverage.
2. **`export-policy.receipt.json`** — records the consumer profile, allowed source kinds, redaction rules, floating-vs-pinned policy, hosted-vs-local precedence, and manual-review gates that shaped a public or machine-consumable export.
3. **`excerpt-lineage.report.json`** — records which concrete doc/example excerpts entered a slice or compact pack, from which source material IDs they came, and whether they were authoritative, imported, inferred, or still manual-review-only.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0051** still owns rustdoc JSON generation, compatibility, and normalization;
- **P-0472** still owns local-vs-docs.rs parity evidence;
- **P-0455** still owns doctest extraction and execution truth;
- **P-0476** still owns docs debt and coverage review;
- but **P-0536** owns the receiver-facing workflow for **exact material basis, export policy, excerpt lineage, and one portable crate-knowledge handoff bundle**.

That separation matters.
Otherwise the archive would quietly confuse “docs.rs has a latest URL”, “rustdoc JSON exists somewhere”, “README text was imported”, and “this assistant slice is safe to trust” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One material-basis receipt** that says exactly which hosted/local/versioned/floating documentation materials fed the pack.
2. **One provenance-aware API/docs map** that still keeps rustdoc facts, hosted facts, and inference separate.
3. **One example-lineage answer** that still distinguishes official runnable examples from illustrative snippets and generated output.
4. **One export-policy receipt** that states what consumer profile, redaction rules, and manual-review gates shaped the compact pack.
5. **One excerpt-lineage report** that says which exact fragments were exported instead of bluffing with generic “assistant context” language.
6. **One diff artifact** for release review so API/doc/example/hosted-material drift becomes visible.
7. **One portable knowledge-pack manifest** that another reviewer can archive, diff, or attach to support/search pipelines.
8. **One manual-review zone** whenever floating docs.rs links, absent rustdoc JSON, unstable output formats, or ambiguous excerpt selection outruns what the pack can honestly prove.

If a crate idea in this territory cannot supply those review objects, it is still probably rustdoc substrate, docs.rs parity evidence, doctest/execution truth, docs debt review, or consumer product logic rather than the missing handoff layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **floating shorthand URLs** into **pinned material basis**, or **download archives exist** into **all offline materials are self-contained**, or **a small support slice exists** into **the excerpt lineage is reviewable**.

Future passes should therefore keep asking:

1. what exact materials were imported,
2. whether they were pinned or floating,
3. which export/redaction policy shaped the pack,
4. which exact excerpts entered the small handoff slice,
5. and where manual review still begins.

That is a better use of repo time than inventing another docs portal, retrieval wrapper, or “chat with your crate” layer that cannot export an honest crate-knowledge witness.
