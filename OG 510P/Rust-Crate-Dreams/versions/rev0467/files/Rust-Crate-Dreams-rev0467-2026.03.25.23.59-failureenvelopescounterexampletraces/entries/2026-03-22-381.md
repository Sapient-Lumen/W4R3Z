# Entry 381 — FFI boundary-conformance work deepened around interface authority, callback lifecycle, and portable support bundles

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another generator wrapper, package shipkit, or language-specific SDK helper.

The lane chosen here was **P-0121 FFI Boundary & Bindings Conformance Kit**.
The archive already had a strong thesis, six core review objects, and useful scenario coverage.
What it still lacked was a sharper answer to a harder downstream question:

> when somebody says “this Rust crate publishes a checked foreign boundary”, what exactly should another engineer receive so **the Rust-side declaration**, **a generated header or binding layer**, **callback registration/cancellation details**, and **one downstream handoff zip** do not get flattened into one vague “FFI is covered” tone?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official and project-maintained sources still converge on the same pressure point:

- the Rust project now explicitly frames **Cross-language interop** as an application area for 2026 roadmaps;
- the 2024 Edition requires `unsafe extern` blocks and says the author is responsible for correct signatures and manual review;
- RFC 2945 keeps `"C"` and `"C-unwind"` meaning sharply distinct and still leaves some foreign-unwind / `catch_unwind` corners explicitly unresolved;
- UniFFI’s current object-reference and async FFI docs make `Send + Sync`, `Arc`-backed handles, foreign-thread reality, completion callbacks, cancellation hooks, and final free requirements explicit;
- CXX keeps shared-by-value types, opaque indirection-only types, and `ExternType` assertions materially distinct;
- Diplomat keeps opaque types, result lowering, and backend-specific throw-vs-result behavior explicit;
- and the component-model/WIT docs make interface authority and resource ownership live on one side of the boundary even when code is generated for many languages.

That combination makes one archive lesson sharper:

**A worthy FFI boundary crate is not just “show the bindings and run CI.”**
**It is a reviewable contract for what artifact is authoritative, what callback lifetime/teardown rules actually exist, and what one portable support bundle another engineer can review without over-reading it.**

## Main repo judgment from this pass

The strongest next move for **P-0121** was to make three more receiver-facing review objects first-class:

1. **`interface-authority.import.json`** — records what artifact is authoritative for a given boundary surface: Rust `unsafe extern` definitions, a `cxx::bridge` module, UniFFI UDL/proc-macro metadata, a Diplomat bridge, a WIT package/world, or a generated header that is explicitly derivative rather than primary authority.
2. **`callback-lifecycle.receipt.json`** — records registration, clone/free routes, unregister-before-drop or not, cancellation/drop callbacks, late-callback-after-destruction caveats, and whether the lifecycle claim is imported, observed, or still manual-review territory.
3. **`ffi-support-bundle.manifest.json`** — records one portable pack tying together interface authority, ownership, unwind posture, callback execution, callback lifecycle, layout authority, error channels, and binding coverage so another reviewer can open one bundle instead of scraping several generators and docs by hand.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0484** still owns target/toolchain support truth;
- **P-0536** still owns crate-knowledge export policy and excerpt lineage;
- plugin/component lanes still own capability budgets and runtime lifecycle;
- package/shipkit lanes still own language-distribution workflows;
- but **P-0121** owns the receiver-facing workflow for **foreign-boundary contract meaning**: interface authority, ownership, unwind posture, callback execution/lifecycle, binding coverage, representation authority, error channels, and one portable boundary-support bundle.

That separation matters.
Otherwise the archive would quietly confuse “we generated a header”, “we have Swift/Kotlin bindings”, “callbacks exist”, “we use `catch_unwind` somewhere”, and “the boundary is reviewable” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One interface-authority import receipt** that says what declaration artifact is primary and what is generated or derived.
2. **One ownership-transfer receipt** instead of folklore about who frees what.
3. **One unwind-posture receipt** instead of scattered ABI and panic caveats.
4. **One callback-execution report** instead of guessing thread/runtime origin from generator docs.
5. **One callback-lifecycle receipt** instead of vague “callback supported” language that omits unregister, cancellation, or late-call hazards.
6. **One binding-coverage report** instead of equating generation with verification.
7. **One layout-authority receipt** instead of flattening by-value types, opaque handles, serialized buffers, and canonical ABI resources.
8. **One error-channel receipt** instead of flattening `Result`, exceptions, status returns, callback failures, and panic translation into “returns errors”.
9. **One diff artifact** for release review so authority source, callback lifetime policy, or checked surfaces can be compared over time.
10. **One portable boundary-support bundle** that another reviewer can archive, diff, and use without scraping docs or generators by hand.

If a crate idea in this territory cannot supply those review objects, it is still probably just generation, header emission, runtime glue, or package shipping rather than the missing support layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **primary interface authority** into **generated artifacts**, or **callback existence** into **callback lifetime clarity**, or **a green binding build** into **an honest multi-surface boundary contract**.

Future passes should therefore keep asking:

1. what artifact is actually authoritative for the foreign boundary,
2. which other artifacts are generated, imported, or derivative,
3. what callback lifetime/teardown/cancellation rules really exist,
4. which surfaces are actually checked,
5. and what one portable bundle another engineer can review later.

That is a better use of repo time than inventing another generator wrapper, bridge comparison dashboard, or multi-language package helper that still cannot hand someone an honest boundary-support witness.
