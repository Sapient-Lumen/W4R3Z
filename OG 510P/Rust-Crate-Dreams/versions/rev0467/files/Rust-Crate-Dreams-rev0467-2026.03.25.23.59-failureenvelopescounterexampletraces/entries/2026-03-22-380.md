# Entry 380 — cargo feature-surface work deepened around resolution scope, hosted docs profiles, and portable support bundles

This pass continued the archive’s current strategy of **taking one already-important support-contract lane and making it more reviewable** instead of opening another feature lister, combo runner, or workspace-speed helper.

The lane chosen here was **P-0528 Cargo Feature Surface Contract Kit**.
The archive already had a strong thesis, a public/internal feature receipt, named activation profiles, explicit conflict-policy receipts, and unification-risk reporting.
What it still lacked was a sharper answer to a harder downstream question:

> when somebody says “this crate supports these features”, what exactly should another engineer receive so **one observed command scope**, **one docs.rs feature profile**, and **one green all-features build** do not get flattened into one vague “feature support” tone?

This pass answers that more concretely.

## Why this lane deserved more work now

Fresh official Cargo/docs.rs/Rust sources still converge on the same pressure point:

- Cargo’s feature reference still says feature flags are conditional-compilation and optional-dependency substrate, but it also documents sharp edges around default-feature leakage, optional-dependency aliases, `dep:` hiding, `?` forwarding, SemVer sensitivity, and feature documentation/discovery;
- the same reference now explicitly notes a crates.io cap of 300 features per published crate version, which makes feature-surface clarity more valuable rather than less;
- the resolver docs and edition-guide docs keep resolver-v2 scope changes concrete: target-specific dependencies, build/proc-macro splits, dev-dependency activation, workspace package selection, and `--no-default-features` behavior can all change what “the feature profile” really means;
- docs.rs metadata still allows packages to build docs with explicit `features`, `all-features`, or `no-default-features`, plus a chosen default target, which means the public documentation feature surface can diverge from the support profile a downstream user actually gets;
- Rust release notes keep reminding us that namespaced and weak dependency features were a real stabilization milestone because feature-system pain is real and structural;
- the 2025 State of Rust survey still says docs are the preferred canonical reference while compile/resource pain remains high;
- and the March 2026 challenges write-up still calls out ecosystem navigation, crate-choice tacit knowledge, and compilation performance as ongoing friction.

That combination makes one archive lesson sharper:

**A worthy feature-surface crate is not just “show the `[features]` table nicely.”  
It is a reviewable contract for what scope was actually observed, what public hosted-docs profile is being shown to users, and what one portable support bundle another engineer can review without over-reading it.**

## Main repo judgment from this pass

The strongest next move for **P-0528** was to make three more receiver-facing review objects first-class:

1. **`resolution-scope.receipt.json`** — records the exact observation scope: subject package(s), resolver version, workspace selection, command family, host/target context, requested feature flags, and caveats about what this scope can and cannot prove.
2. **`hosted-feature-profile.receipt.json`** — records what public documentation posture is actually being shown through docs.rs or equivalent hosted-doc builds: explicit features, `all-features`, `no-default-features`, target/default-target assumptions, and the warning that public docs posture is not automatically runtime/support posture.
3. **`feature-support-bundle.manifest.json`** — records one portable pack tying together the maintainer-authored contract, the observed scope receipt, hosted-docs posture, conflict policy, unification risk, and named profile reports so another reviewer can open one bundle instead of guessing which pieces matter.

The repo also now states a sharper boundary against adjacent lanes:

- **P-0036** still owns workspace MSRV activation and command-floor truth;
- **P-0469** still owns rebuild causality and comparison scope for build sessions;
- **P-0484** still owns toolchain/target support truth and public docs surface at the target/support level;
- **P-0536** still owns crate-knowledge export policy and excerpt lineage;
- but **P-0528** owns the receiver-facing workflow for **feature support meaning**: public names versus plumbing, supported activation profiles, explicit observation scope, hosted-doc feature posture, and one portable feature-support bundle.

That separation matters.
Otherwise the archive would quietly confuse “docs.rs built with all features”, “one workspace build passed”, “the feature table is documented”, and “these are the supported downstream feature profiles” into one fake certainty tone.

## What a worthy crate in this lane should provide other people

The archive now has a tighter answer:

1. **One public feature-surface receipt** that separates public names from hidden dependency plumbing.
2. **One activation-profile report** that says which named combinations are observed, sampled, recipe-only, unsupported, or still manual-review territory.
3. **One conflict-policy receipt** that states whether features compose, are mutually exclusive, select a winner, or require manual review.
4. **One unification-risk report** that keeps resolver-v2 splitting, default leakage, and duplicate-build/workspace pressure visible.
5. **One resolution-scope receipt** that says exactly what command/package/target/workspace context the observations came from.
6. **One hosted-feature-profile receipt** that says what docs.rs or equivalent public documentation is actually showing users.
7. **One diff artifact** for release review so public names, defaults, conflict policy, or scope assumptions can be compared over time.
8. **One portable feature-support bundle** that another reviewer can archive, diff, and use without scraping Cargo output or hosted pages by hand.

If a crate idea in this territory cannot supply those review objects, it is still probably just feature enumeration, combination execution, docs rendering, or workspace-build optimization rather than the missing support layer itself.

## New repo-level lesson

The archive is stronger when it refuses to flatten **one observed resolver scope** into **global feature support**, or **docs.rs built with `all-features`** into **the supported downstream profile**, or **a green all-features build** into **an honest conflict and profile contract**.

Future passes should therefore keep asking:

1. what exact command/workspace/target scope was observed,
2. which public feature names are contract versus plumbing,
3. what hosted-doc feature posture is being shown to users,
4. which named profiles are actually supported,
5. and what one portable bundle another engineer can review later.

That is a better use of repo time than inventing another feature lister, combo runner, or docs page that still cannot hand someone an honest feature-support witness.
