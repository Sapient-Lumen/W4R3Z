# Entry 326 — Array API deepened for semantic profiles, layout truth, device/dtype inspection, and interop routes

This pass deepened **P-0003 Array API** instead of adding another tensor engine, backend runtime, or one-off adapter.

## Why this lane earned another serious pass

The archive already had the intuition that Rust should have a more unified array story.
What it lacked was a build-shaped answer for *which truths actually belong in one reviewable array support contract*.

Current substrate is now strong enough to make that precise:

- the Python Array API standard explicitly treats fragmentation across array/tensor libraries as a standardization problem and responds with conformance, semantics, device support, data interchange, and inspection APIs;
- `ndarray` documents dense n-D arrays with views, slicing, row-major default order, and custom-stride support;
- `nalgebra` documents a low-dimensional linear-algebra focus;
- `faer` documents medium/large dense linear algebra with column-major layout;
- `linalg-traits` proves generic abstractions are useful but also explicitly documents semantic mismatch between `ndarray` and `nalgebra` operator behavior;
- `candle` and `burn` make backend/device posture first-class rather than incidental;
- `arrow-array` makes it clear that columnar arrays are adjacent interop substrate, not silent proof of dense n-D compatibility.

That means a worthy crate here should not simply say “supports arrays”.
It should say what semantic family is promised, what layout assumptions are safe, what devices and dtype defaults exist, what namespaces are covered, and how interop routes behave.

## What moved this time

The main planning move was to stop treating all Rust numerics surfaces as one kind of truth.

This pass elevated five review objects into first-class status for **P-0003**:

1. **semantic-profile truth** — dense n-D core, dense linear algebra, tensor backend, columnar bridge only, or manual review;
2. **layout-view truth** — row/column/custom stride posture, borrowed views, mutation views, and contiguous assumptions;
3. **device-dtype truth** — runtime devices, default device, dtype defaults, and transfer posture;
4. **namespace-coverage truth** — which operation families are exact, partial, extension-only, imported, or unsupported;
5. **interop-route truth** — whether crossings are borrowed, zero-copy, copy-required, lossy, or manual-review-only.

## Why this matters now

The ecosystem evidence is no longer ambiguous:

- the array-API standard shows that fragmentation, conformance, and inspection deserve first-class vocabulary;
- Rust crate docs now make their differences concrete enough to classify honestly rather than hand-wave;
- `linalg-traits` demonstrates why trait unification without semantic receipts is not enough;
- tensor crates make device/dtype behavior part of the user-facing contract;
- Arrow makes it easier to keep columnar bridges separate from dense-core claims.

That means a worthy crate should not let “backend agnostic”, “NumPy-like”, or “matrix support” quietly over-claim layout, device, or namespace compatibility.

## Main judgment after the pass

A worthy array-related crate should now provide more than a trait or an adapter.
It should also provide:

- one explicit **semantic-profile receipt**,
- one explicit **layout-view receipt**,
- one explicit **device-dtype receipt**,
- one explicit **namespace-coverage receipt**,
- one explicit **interop-route receipt**,
- and one conservative rule for when a bridge is useful but still too lossy, backend-specific, or semantically mismatched to bluff broader compatibility.
