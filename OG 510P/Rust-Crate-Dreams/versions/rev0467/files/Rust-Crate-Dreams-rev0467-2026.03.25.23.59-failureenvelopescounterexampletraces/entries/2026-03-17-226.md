# Entry 226 — memory-observability planning sharpened into an implementation-ready v0.1 shape

This pass did **not** promote a new lane.
It sharpened **P-0084 Memory Observability Kit** into a more buildable shape.

## Why this moved now

Several current Rust and ecosystem signals line up well enough that this older proposal deserved the same product discipline as the archive’s newer cross-cutting lanes.

### 1. The archive had a real memory-analysis idea, but not a receiver-facing build sketch

The archive already had a promising proposal for allocator tracing, profile capture, and shareable memory reports.
What it lacked was the same implementation-ready discipline recently given to crate pathfinding, lifecycle, resource, persistence, performance, and authority work.

That gap mattered because the operational question is not:

- “does Rust have *any* profiler or allocator hook?”

It is:

- “what should a good Rust-native memory-evidence crate actually hand another person when memory usage drifts, leaks, regresses, or becomes impossible to explain?”

### 2. Current substrate is good enough that the missing value is above it

The ecosystem now has enough real pieces to justify a contract-and-evidence layer instead of another generic profiler pitch:

- `leaktracer` already shows a very low-friction allocator-interception path.
- `dhat` already provides a scoped heap profiler built around a global allocator and an explicit profiler lifetime.
- `tikv-jemalloc-ctl` already exposes allocator introspection and statistics.
- `jemalloc_pprof` already shows a path from jemalloc heap profiling to pprof-compatible output.

So the sharper question is no longer “can Rust observe heap behavior at all?”
It is “what reviewable artifact should sit above these backends so memory evidence, symbolization quality, regression policy, and redaction posture stop living in tribal setup knowledge?”

### 3. This lane is distinct from the newer support-surface crates

This pass deliberately kept **P-0084** separate from:

- **P-0521 Crate Resource Surface Pack Kit**, which is about **crate-authored steady-state capacity and saturation promises**;
- **P-0517 Crate Performance Envelope Pack Kit**, which is about **which performance metrics and workloads are authoritative**;
- and **P-0518 Crate Observability Surface Pack Kit**, which is about **crate-authored emitted signals and activation recipes**.

Memory observability is different.
It is the dynamic evidence bundle for:

- where allocations came from,
- which bytes stayed live,
- what RSS did,
- what the profiler could or could not symbolize,
- what the backend could or could not observe,
- and whether a regression gate is justified.

### 4. Rust’s current messaging still supports this move

The current Rust vision-doc work explicitly argues for more supportive interfaces from crates.
The 2025 State of Rust survey still reports resource usage as a recurring productivity problem, while debugging also remains a notable pain point.
That makes a memory-evidence kit feel more like ecosystem support infrastructure and less like a side hobby for perf specialists.

## Main judgment after the pass

The worthy crate here is still **not** another allocator, another one-off profiler wrapper, or another hosted dashboard.
It is the boring crate that can hand other people:

- one **capture-scope policy**,
- one **symbolization-fidelity report**,
- one **backend-capability report**,
- one **allocation-attribution receipt**,
- one **memory-regression gate policy**,
- one **redaction profile**,
- one **memory-check report**,
- and one **memory diff**.
