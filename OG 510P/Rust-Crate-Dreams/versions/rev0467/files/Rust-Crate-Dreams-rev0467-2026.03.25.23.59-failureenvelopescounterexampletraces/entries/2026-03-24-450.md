# Entry 450 — add decision programs so profile-aware packet stacks can be run, not just admired

This pass again chose **deepen over append**.

The archive already had much better answers for:
- compare,
- freeze,
- watch,
- trigger,
- intake,
- materialize,
- adjudicate,
- exception,
- carry forward,
- reopen review,
- and profile for different adopters.

What it still lacked was a clean answer to the next operational question:

> once a team has a packet stack and a policy profile, how does it **run a staged adoption program** from exploration toward enterprise-offline or safety-adjacent use without rewriting the original basis every time?

That seam matters now because the Rust substrate increasingly exposes the ingredients for a real program loop instead of a single verdict:

- the Rust challenges write-up still says users struggle with crate choice and uneven domain maturity;
- the 2025 survey still reports resource usage and debugging as live productivity pain while online docs remain the canonical reference;
- 2026 flagships still emphasize secure supply chain, safety-critical work, SBOM, async, and cargo plumbing;
- Cargo’s plumbing work explicitly breaks build operations into programmatic phases;
- Cargo build-analysis is explicitly about recording machine-readable build metadata across invocations;
- docs.rs exposes versioned rustdoc JSON, hosted build metadata, and download caveats;
- Cargo Vet already has expiring renewals and criteria/policy structure;
- cargo-deny already distinguishes target-scoped graph construction and offline mode caveats;
- and the safety-critical write-up explicitly describes teams moving from broad early crate use toward narrower or replace-later postures.

## Main judgment

A worthy control-plane crate in the practical core should now publish not only:
- profile packs,
- profile-satisfaction reports,
- adjudication sessions,
- exception receipts,
- carry-forward receipts,
- and recheck tickets,

but also a credible **decision program**.

That means it should provide:
1. named review stages with stable IDs,
2. stage entry requirements and stage-exit outcomes,
3. artifact requirements per stage,
4. owner/approver roles per stage,
5. explicit carry-forward rules from one stage to the next,
6. reopen triggers and cooldown rules,
7. and explicit program exits such as keep / conditional keep / hold / replace-later / split-boundary.

## Practical consequence

This still does **not** justify a major salience rerank.

But it sharpens the first practical slice again:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, profile packs, profile-satisfaction reports, decision-program runbooks, profile-progression reports, adjudication sessions, policy-exception receipts, carry-forward receipts, expiry tickets, and recheck tickets
2. **P-0486** — debug support bundles should also say which program stage they are strong enough for instead of one vague supported/not-supported claim
3. **P-0496** — source-parity and restricted-delivery work should export stage-entry evidence for enterprise-offline and safety-adjacent adoption paths
4. **P-0472** — docs.rs parity should be consumed as one stage input rather than treated as the whole answer

Interpretation:
- the front door is no longer only “answer under a profile honestly”;
- it is now also “**show how that answer can progress, stall, split, or exit without rewriting history**”.

## What this pass says a worthy crate should provide other people

A worthy front-door crate should now answer **twenty** operational questions:

1. compare — what are the plausible choices now?
2. freeze — what exact basis did the chosen answer stand on?
3. profile — which adopter profile is asking?
4. floor — what evidence is minimally required for that profile?
5. watch — which surfaces are being watched later?
6. trigger — what exact event opened review?
7. intake — what imported material was actually consumed?
8. materialize — what can be made portable or offline-friendly?
9. conflict — which claims disagree and on which route or time basis?
10. adjudicate — what decision was made about that disagreement, by whom, and under what policy?
11. exception — what temporary relief was granted, to whom, for which scope, and why?
12. carry forward — which old claims remain inherited and which became superseded?
13. stage — which named decision-program stage is active now?
14. gate — what evidence must exist to enter or leave that stage?
15. progress — what exactly moved from explore to team-default or enterprise-offline?
16. exit — did the program end in keep, hold, split-boundary, replace-later, or stop?
17. ticket — what review packet should be opened next?
18. refresh — what later facts changed and which did not?
19. revalidate — does the old choice still stand under the same task and profile?
20. ceiling — what still requires manual judgment even after the workbench runs?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
