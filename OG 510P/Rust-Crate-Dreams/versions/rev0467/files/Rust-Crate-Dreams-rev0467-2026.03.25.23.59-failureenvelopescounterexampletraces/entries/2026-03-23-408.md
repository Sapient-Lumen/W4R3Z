# Entry 408 — workspace tool support now needs command-authority receipts, component-availability reports, and fallback ceilings

This pass returned to an already-strong workspace-tooling lane instead of adding another installer, package manager, or editor bootstrapper.
It deepened:

**P-0055 Cargo Workspace Toolchain Manifest Kit**.

## Why this lane earned another serious refresh now

Fresh official substrate makes one support gap much sharper than before:

- the March 2026 rustup 1.29 release now explicitly says the rustup proxy will consider a `rust-analyzer` binary from `PATH` when a rustup-managed one is not found;
- the rustup book still makes **proxy-backed commands** and **optional components** first-class concepts, rather than treating every Rust-adjacent executable as the same kind of thing;
- the rustup book still makes toolchain selection order explicit (`+toolchain`, `RUSTUP_TOOLCHAIN`, directory override, toolchain file, default toolchain), which means “the same command name ran” is not yet a precise route claim;
- Cargo’s external-tools docs still say external `cargo-*` subcommands are resolved from executables on the user’s path, with `$CARGO_HOME/bin` prioritized by default;
- and `cargo install` / Cargo config docs still make install-root choice explicit, which means workspace intent, rustup component posture, and executable resolution remain different support surfaces even when they all look like “the tool worked”.

Together those sources say the missing value is no longer only:

> “Can a workspace declare and sync tool binaries?”

It is now also:

> “Which command family actually answered the request, which component/toolchain surface was really available, and where does the claim ceiling stop when the result depended on PATH fallback or cargo-home precedence?”

## Main judgment after the refresh

**P-0055** is now stronger as a **command-authority and fallback-honesty lane**.

That means a worthy crate in this lane should explicitly own:

- `command-authority.receipt.json`,
- `component-availability.report.json`,
- `fallback-ceiling.report.json`,
- and a portable `tool-support-bundle.manifest.json`.

It should **not** try to own:

- rustup itself,
- global package-management policy for non-Rust tools,
- editor-specific language-server launch code,
- or a universal PATH mutator.

## What should count as a worthy crate contribution in this lane now

A worthy workspace-tool contract crate should hand other people:

1. **one command-authority receipt** that says whether a request was answered by a rustup proxy/component lane, a Cargo external-subcommand lane, a workspace-managed binary, or a plain PATH fallback,
2. **one component-availability report** that says which toolchain/context was checked and whether the expected optional component was installed, merely available, missing, or irrelevant,
3. **one fallback-ceiling report** that says where PATH fallback, cargo-home precedence, or toolchain drift stop stronger support claims,
4. **one portable bundle manifest** another team can reopen later,
5. **one exactness story** instead of pretending that “the tool ran” proves component parity, workspace governance, or rustup-backed execution.

If a candidate crate cannot do those things, the archive should usually treat it as an installer helper, local bootstrap script, or editor integration — not the missing support-contract layer.
