# Entry 446 — make packet consumers and materialization first-class, not an implementation afterthought

This pass again chose **deepen over append**.

The archive already had a much better answer for:
- how a team compares plausible crates,
- how it freezes a basis,
- how it opens later review,
- and how it records a transition posture.

What it still lacked was a clean answer to the next operational question:

> once a worthy crate emits a decision packet or knowledge pack, how does another tool, teammate, CI job, or assistant **consume** it without flattening source routes, schema versions, or offline caveats?

That seam matters more now because the current Rust substrate has become more machine-readable but also more route-sensitive:
- `cargo metadata` explicitly asks consumers to use `--format-version` because the JSON format can change;
- the Cargo registry index warns that its JSON differs in subtle but important ways from both the Publish API and `cargo metadata`;
- `cargo package` provides `.cargo_vcs_info.json`, but says it is only a best-effort snapshot and does **not** verify provenance;
- docs.rs says rustdoc JSON carries a `format_version` and that parsers need to respect it;
- docs.rs download archives are useful base material for offline processing, but they are **not directly usable** as offline docs, have target-layout/static-root caveats, and may omit invocation-specific static assets;
- and Cargo build-analysis planning explicitly discusses storing evolving machine data across invocations in JSON blobs / SQLite because schema evolution is expected during prototyping.

## Main judgment

A worthy packet-producing crate in the practical core should now publish not only:
- compare packets,
- basis locks,
- trigger intake,
- recheck tickets,
- refresh and transition packets,

but also a credible **consumer contract**.

That means it should say:
1. what a downstream consumer imports,
2. how it resolves live routes into pinned material,
3. what stays partial or degraded,
4. what can be materialized for offline review,
5. and where the ceiling stays manual.

## Practical consequence

This pass still does **not** justify a major salience rerank.

But it does sharpen the first practical slice:

1. **P-0509 + P-0536 + minimal P-0535 loop** — comparator packets, basis locks, intake/materialization receipts, trigger intake, and recheck tickets
2. **P-0486** — debug witness bundles that can later be imported by the same consumer discipline
3. **P-0496** — restricted-delivery packets that reuse the same intake/materialization honesty
4. **P-0472** — docs.rs parity bundles that explicitly separate hosted facts from locally materialized support

Interpretation:
- the front door is no longer just “choose and freeze”; it is now “choose, freeze, intake, materialize, watch, and reopen honestly”.
- `P-0536` remains below the very top salience cluster in the flat ladder,
- but the archive should now treat **consumer-contract quality** as part of whether a crate is truly implementation-ready.

## What this pass says a worthy crate should provide other people

A worthy crate in the practical core should now answer **thirteen** operational questions:

1. compare — what are the plausible choices now?
2. freeze — what exact basis did the chosen answer stand on?
3. watch — which surfaces are being watched later?
4. trigger — what exact event opened review?
5. ticket — what review packet should be opened next?
6. refresh — what later facts changed and which did not?
7. revalidate — does the old choice still stand under the same task and policy?
8. transition — if not, what posture follows now?
9. anchor — what lock, patch, mirror, fork, or shared policy currently makes that posture hold?
10. intake — what imported material was actually consumed, and under what schema/version rules?
11. materialize — what can be made portable or offline-friendly, and what still depends on live remote surfaces?
12. degrade — what became partial, unresolved, or route-limited during import/materialization?
13. ceiling — what still requires manual review?

If a proposal cannot answer those, it may still be interesting, but it is not yet ready for the practical core.
