# Entry 342 — sanitizer workflow contract deepened for instrumentation scope, runtime linkage, symbolization routes, and suppression policy

This pass deepened **P-0434 Sanitizer Profile & Evidence Kit** instead of adding another debugging helper, another target-support artifact, or another verification lane.

## Why this lane earned a serious pass now

Fresh official Rust signals line up unusually well:

- the 2026 project-goals slate still includes **stabilizing MemorySanitizer and ThreadSanitizer support**, including the infrastructure needed for precompiled and instrumented standard libraries;
- the January 2026 goals update reports continued progress and target work for sanitizer-enabled support;
- the current unstable-book sanitizer docs are now unusually concrete about the real workflow seams: `--target` is needed so build scripts and procedural macros stay off the sanitizer lane, MemorySanitizer needs fully instrumented code, mixed-language builds may need `external-clangrt`, and useful reports depend on `llvm-symbolizer`;
- and the March 2026 challenges write-up again says debugging, compile-time friction, embedded constraints, and safety-critical tooling gaps remain ecosystem pain.

That combination means the missing crate is no longer “some way to pass `-Zsanitizer=*`”.
The sharper missing contribution is a **portable workflow-and-evidence contract** that tells another person:

1. what was actually instrumented,
2. which runtime-linkage route was used,
3. whether reports were symbolized well enough to hand off,
4. and which suppressions were active, justified, or still provisional.

## Main judgment after the pass

A worthy sanitizer crate should not flatten all of the following into one fake result:

- “sanitizer flag was set,”
- “CI job passed,”
- “stack trace exists,”
- “mixed Rust/C++ build linked somehow,”
- and “we have a suppression file.”

Those are different truths.

The crate should instead publish explicit first-class review objects for:

1. **instrumentation scope** — what code and libraries were instrumented, excluded, or only partially covered;
2. **runtime linkage** — which sanitizer runtime actually provided the symbols and whether mixed-language routing was involved;
3. **symbolization route** — whether stack traces were symbolized locally, partially, or not at all, and why;
4. **suppression policy** — which suppressions were active, on what grounds, and whether they remain reviewable debt.

## What moved this time

This pass promoted four new artifacts into first-class status for **P-0434**:

- `instrumentation-scope.receipt.json`

## What should count as a worthy crate contribution after this pass

A worthy sanitizer-support crate should now be able to answer all of these cleanly:

1. **Which code was actually instrumented, and which lanes were intentionally not?**
2. **Was instrumented `std` required, recommended, or absent?**
3. **Did the runtime route stay inside Rust’s default compiler runtime, or did mixed-language linkage require an explicit external route?**
4. **Are the stack traces symbolized enough to be useful to another engineer?**
5. **Which suppressions are in force, and what debt or review obligation do they create?**

If a candidate crate cannot answer those questions, the archive should usually treat it as incomplete sanitizer folklore rather than a serious workflow contribution.
