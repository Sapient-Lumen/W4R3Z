# Entry 249 — UI Accessibility Doctor deepened around semantic contracts, rule authority, and baseline drift

This pass did **not** open another broad GUI framework lane, another generic testing harness, or another cross-platform accessibility bundle system.
It sharpened **P-0087 UI Accessibility Doctor Kit** into a more believable, implementation-ready product.

## Why this moved now

The Rust GUI/accessibility substrate is more real than it was when this archive first sketched P-0087.

- **AccessKit** now explicitly presents itself as cross-platform accessibility infrastructure for UI toolkits, and it already lists Rust integrations including **Bevy**, **egui**, **Freya**, **Slint**, and **Xilem**.
- **accesskit_winit** now gives `winit`-based projects a platform-accessibility adapter rather than forcing each toolkit to re-invent OS exposure from scratch.
- **egui** documents an `accesskit` feature, which is strong evidence that accessibility is no longer a purely hypothetical Rust GUI concern.
- **kittest** now exists as an AccessKit-powered, framework-agnostic GUI testing layer, which is important because it proves part of the testing substrate is becoming real.
- At the same time, the broader Rust story still says **supportive tooling**, **diagnostics**, and **helping users navigate complexity** are strategic needs, while a current field survey of Rust GUI libraries still reads like an ecosystem with uneven maturity and inconsistent end-user quality expectations.

That combination changes the shape of the missing value.
The next worthy crate is **not** another raw accessibility abstraction and **not** another standards document in code form.
It is a **doctor/gating kit above existing substrate**.

## Main planning move

This pass made the crate more concrete by promoting three first-class review objects that were still too implicit in the older proposal:

1. **semantic contract** — what authoring-side tree the toolkit/app is actually claiming,
2. **rule authority** — which checks are structural, standards-inspired, toolkit-specific, or manual-review-only,
3. **baseline drift** — what changed between releases or snapshots and whether that drift should block, warn, or escalate to manual review.

That move matters because the archive had already separated:

- **P-0087** as the authoring-side doctor/gating lane,
- **P-0202** as the observer-side capture/interop/bundle lane.

But P-0087 still lacked a tight `0.1` product shape.
This pass fixes that.

## Main judgment after the pass

A worthy accessibility crate contribution for Rust should now provide not only a lint report, but also:

- explicit **semantic-contract truth** for what the toolkit/app claims to expose before backend/platform translation,
- explicit **rule-authority truth** for whether a finding is structural, standards-inspired, toolkit-local, or manual-review-only,
- explicit **baseline-drift truth** for whether a release changed names, roles, focus order, or node identity in ways another maintainer can review,
- and one compact bundle that a teammate or CI system can inspect without manually replaying the UI, guessing at intended semantics, or flattening every accessibility question into fake “automatic compliance”.

That is a sharper and more believable contribution than “yet another Rust GUI framework feature” or “some accessibility helper utilities.”
