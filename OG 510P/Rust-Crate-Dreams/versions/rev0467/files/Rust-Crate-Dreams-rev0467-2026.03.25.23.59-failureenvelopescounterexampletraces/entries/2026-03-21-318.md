# Entry 318 — cargo-workspace-toolchain-manifest deepened for install-root posture, tool-route authority, and shadowing honesty

This pass deepened **P-0055 Cargo Workspace Toolchain Manifest Kit** rather than opening another adjacent installer, shell bootstrapper, or cargo-plugin launcher lane.

## Why this lane earned another serious pass

The archive already had sharper answers for:

- workspace-scoped tool manifests,
- lockfiles for crate-shipped tools,
- runner receipts,
- and the broad separation between tool dependencies and rustup compiler policy.

What still needed a more disciplined answer was the route question:

> “Which executable actually ran, from which install root, and under which rustup/toolchain context?”

Current Cargo and rustup docs now make that question concrete enough to build around.

## What moved this time

The key planning move was to stop treating “the workspace pinned a tool” as sufficient execution truth.

This pass elevated three review objects more explicitly:

1. **install-root posture** — whether a workspace is depending on a workspace-local root, shared user cache, `$CARGO_HOME/bin`, ephemeral CI root, or some custom path;
2. **tool-route authority** — whether a requested command resolved to the intended workspace-managed executable, a user-global cargo-home install, another PATH entry, or a manual wrapper;
3. **shadowing / context honesty** — whether competing binaries existed and whether rustup overrides or `+toolchain` changed the run context even when the binary path stayed the same.

## Main judgment after the pass

A worthy workspace-tooling contribution should not stop at a manifest, lockfile, or “repo-local tools” claim.
It should also provide:

- one explicit **install-root receipt**,
- one honest **tool-route receipt**,
- and one conservative **shadowing / rustup-context** story when a requested command can route through multiple executable candidates.
