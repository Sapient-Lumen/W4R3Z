# Entry 400 — workspace-boundary diagnosis now needs ancestor-discovery receipts, config-layering reports, and invocation-mode honesty

This pass deepens an existing Cargo / workspace / support-contract lane instead of opening a duplicate one.
It sharpens:

**P-0506 Cargo Workspace Boundary Doctor Kit**.

## Why this lane earned another serious refresh now

The archive already had a good diagnosis story for parent-manifest poisoning, `--manifest-path` surprises, and accidental workspace membership.
What it still left too easy to blur together was a more operational question:

> “Which ancestor files were actually candidates, how did config layering and path bases work, and did this invocation mode even allow workspace auto-discovery in the first place?”

Current Cargo docs make that split much more actionable than before:

- Cargo’s config docs explicitly say config files are probed from the current directory through parent directories and then `$CARGO_HOME`, with deeper directories taking precedence.
- The same docs now spell out `include` support, left-to-right include merging, file-local precedence, and config-relative path rules.
- Those docs also say environment variables override TOML config and `--config` overrides environment variables.
- Cargo’s February 2026 cycle notes now call workspace/config discovery an active design topic, spell out parent `Cargo.toml` / `.cargo/config.toml` poisoning, and mention `package.workspace = false` plus broader discovery improvements.
- Cargo’s single-file package docs say `.rs` packages cannot be auto-discovered the way `Cargo.toml` manifests are, and manifest-command mode uses config for the subject path rather than the caller cwd.

Together those sources say the missing crate contribution is not just “diagnose the wrong workspace root.”
It is a reviewable boundary-support layer for **ancestor discovery**, **config layering**, **invocation mode**, and **portable boundary bundles**.

## Main judgment after the refresh

**P-0506** is stronger when it owns three more receiver-facing truths:

1. **ancestor discovery** — which parent manifests/config candidates existed, what order they were considered in, and what boundary or stop condition was observed;
2. **config layering** — which files/includes/env/CLI overrides existed, what precedence they had, and which path basis each route used;
3. **invocation mode** — whether the run used cwd auto-discovery, `--manifest-path`, manifest-command mode, or a single-file package lane with workspace auto-discovery disabled.

That means a worthy crate in this lane should now explicitly own:

- `ancestor-discovery.receipt.json`,
- `config-layering.report.json`,
- `invocation-mode.report.json`,
- and `boundary-support-bundle.manifest.json`

above the earlier context / trace / membership / diagnosis bundle.

It should **not** try to become:

- a Cargo replacement,
- a generic config editor,
- a silent workspace auto-rewriter,
- or a universal explanation engine for every build failure.

## What should count as a worthy crate contribution in this lane now

A worthy workspace/config boundary contribution should now hand other people:

1. **one ancestor-discovery receipt** that says which parent candidates existed and where observation stopped;
2. **one config-layering report** that keeps file layers, include edges, env overrides, CLI overrides, and path bases visible;
3. **one invocation-mode report** that distinguishes cwd auto-discovery, `--manifest-path`, manifest-command mode, and single-file package behavior;
4. **one portable bundle** another maintainer, CI engineer, or editor author can reopen later without guessing what discovery mode was in play;
5. **one conservative diagnosis** that routes to workaround, repo cleanup, or upstream design gap without faking certainty.

If a candidate crate cannot do those things, the archive should usually treat it as adjacent Cargo folklore, config documentation, or editor glue — not the missing reviewable boundary-support layer.
