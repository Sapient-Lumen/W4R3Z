## What changed in rev0125

rev0125 closes the next staged-write risk after provider-local active tracking: cross-provider recovery needs the same coordination boundary as cross-provider writes. Before this pass, a second raw provider could call `recoverStagedWrites()` while another provider had a live staged `put()` in progress and delete the staged temp before publish.

Now `WebLockGuardedBlockStore.recoverStagedWrites()` exists and uses the same exclusive Web Lock path as guarded `put()`, `delete()`, and `cleanupForTest()`. The new proof intentionally demonstrates the unguarded failure mode, then proves a guarded recovery request queues behind a live staged put, the staged temp remains untouched until publish, the writer cleans the staged file, and the canonical block is readable through the recovery guard.

This is still not a fresh browser matrix or crash-durability claim. It is a release-tier fake-OPFS/fake-Web-Locks proof that the product API now exposes the correct coordination seam when callers opt into a shared guard lock name/prefix.
