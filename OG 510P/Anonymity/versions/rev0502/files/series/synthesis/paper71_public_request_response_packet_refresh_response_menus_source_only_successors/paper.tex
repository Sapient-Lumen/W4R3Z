\begin{abstract}
The source-only successor branch can now say which exact bounded response packet is being reused, whether that packet survives a successor release, which packet-local field families refresh when it is reused, what exact visible reissue sentence may be emitted, what canonical family sits behind that sentence, and why that canonical family was selected for the shipped successor-facing token basis. One operational question still remained implicit: when a referee asks one concrete follow-up about that visible packet-refresh sentence, which already-maintained object is the smallest sufficient thing to hand over? This note gives that successor-facing response choice one home. It defines compact \emph{public request response packet refresh response menus}: emitted-refresh-notice keyed maps from common successor follow-up classes to the smallest sufficient already-owned packet, carryforward, delta, sentence, family, or family-choice owner.
\end{abstract}

\section{Why packet-refresh response menus deserve their own note}
Once the successor-facing line owns packet membership, packet reuse, packet-local refresh deltas, emitted visible reissue sentences, canonical wrapper families, and token-keyed family choice, a short paper still faces one last repetition problem.
If a reader asks ``which exact bounded packet is this notice talking about?'', ``did that packet really carry forward or reopen?'', ``what exactly changed inside that packet?'', ``which canonical wrapper family is this sentence in?'', or ``why that family rather than another one?'', the answer is not always the same artifact.
Without a maintained response menu, later papers either overshare the whole successor-facing tail or improvise the handoff in prose. In the worked route/spine bridge it is also the first reopened owner when a visible-refresh closure fails because the shipped successor follow-up taxonomy itself has expanded.
A response menu keeps those follow-up choices explicit and auditable while leaving packet, delta, sentence, and family ownership where they already belong.

\begin{definition}[Public request response packet refresh response menu]
Fix one emitted public request response packet refresh notice $N$ for a reusable source-only response packet.
A \emph{public request response packet refresh response menu} is a tuple
\[
M(N)=(\pi,\chi,\delta,\nu,\phi,\sigma)
\]
containing one imported response-packet owner $\pi$, one imported packet-carryforward owner $\chi$, one imported packet-delta owner $\delta$, one imported emitted-refresh-notice owner $\nu$, one imported canonical refresh-notice normal-form owner $\phi$, and one imported refresh-notice-selection owner $\sigma$, together with an ordered family of response entries for the follow-up classes
\[
\begin{array}{l}
\textsf{packet-membership-check},\ \textsf{packet-reuse-check},\ \textsf{packet-delta-check},\\
\textsf{visible-refresh-sentence-check},\ \textsf{canonical-refresh-family-check},\ \textsf{refresh-family-choice-check}.
\end{array}
\]
Each entry names the smallest sufficient already-maintained object for that follow-up class together with its canonical citation path and why that object is sufficient.
\end{definition}

\begin{definition}[Follow-up-class coverage rule]
A public request response packet refresh response menu satisfies the \emph{follow-up-class coverage rule} if it covers exactly the six follow-up classes above for the same emitted refresh notice.
So the menu cannot silently omit one of the common successor-facing questions that recur after a packet-refresh sentence is printed.
\end{definition}

\begin{definition}[Smallest-sufficient successor response rule]
A public request response packet refresh response menu satisfies the \emph{smallest-sufficient successor response rule} if it chooses:
\begin{enumerate}[leftmargin=*]
\item the imported response packet for packet-membership checks,
\item the imported packet-carryforward profile for packet-reuse checks,
\item the imported packet-delta ledger for packet-delta checks,
\item the imported emitted packet-refresh notice for visible-refresh-sentence checks,
\item the imported canonical packet-refresh-notice normal form for canonical-refresh-family checks, and
\item the imported packet-refresh-notice selection for refresh-family-choice checks.
\end{enumerate}
So the menu changes only successor follow-up selection; it does not widen or replace any imported owner.
\end{definition}

\begin{definition}[Selector-visibility rule]
A successor-facing refresh response menu satisfies the \emph{selector-visibility rule} if every response entry keeps the selecting refresh-response-menu object visible beside the imported selected handoff by recording both the owner-side menu key and the exact selected object key. So a later terse paper can recover not only what successor-facing object should travel, but also which maintained menu selected that handoff for the refreshed visible sentence in question.
\end{definition}

\begin{definition}[Imported-locality rule]
A public request response packet refresh response menu satisfies the \emph{imported-locality rule} if every imported key belongs to the same emitted refresh-notice lineage and every response entry copies the imported packet membership, reuse verdict, delta fields, rendered sentence, canonical family, or family choice exactly.
So the menu may not create a new packet slice, a new successor verdict, a new refresh sentence, or a new family while pretending only to select a handoff object.
\end{definition}

\begin{lemma}[Packet-refresh response menus keep successor-facing follow-up handling brief without changing ownership]
Assume every public request response packet refresh response menu satisfies the follow-up-class coverage rule, the smallest-sufficient successor response rule, the selector-visibility rule, and the imported-locality rule.
Then a later terse paper may cite one menu as the maintained guide for concrete follow-up about one shipped packet-refresh notice without changing the ownership of its packet membership, reuse verdict, packet-local delta, visible sentence, canonical family, or family choice.
\end{lemma}

\begin{proof}
The follow-up-class coverage rule ensures that the common successor-facing follow-up requests are covered explicitly.
The smallest-sufficient successor response rule ensures that each request class resolves to one already-owned object and no larger one.
The selector-visibility rule keeps the selecting refresh-response-menu key and selected object key visible beside that imported handoff even after the chosen successor-facing owner is reused downstream.
The imported-locality rule then prevents the menu from rewriting any imported packet, delta, sentence, or family owner.
So the menu changes only handoff policy: it stabilizes what to hand over for one follow-up class while keeping the selector visible, but it does not alter the truth or ownership of the underlying successor-facing packet-refresh line.\qedhere
\end{proof}

\section{Worked example pointer}
The maintained worked bundle now ships \nolinkurl{example_public_request_response_packet_refresh_response_menus.json}.\cite{series:workedexample}
It contains one successor-facing response menu for every emitted packet-refresh notice in the canned successor comparison.
Each menu records the imported exact packet, carryforward profile, packet-delta ledger, emitted refresh sentence, canonical family, and family-selection entry, then maps the six follow-up classes above to the smallest sufficient already-owned handoff object.
So later terse papers no longer have to infer whether a concrete follow-up about a visible successor reissue sentence should be answered with the packet itself, the reuse verdict, the delta ledger, the emitted wrapper, the canonical family, or the family-choice selector.
In the worked request-scope branch the menu-side route is now explicit rather than merely representative:
\begin{quote}\small\ttfamily
\path{worked_example_receipt_interlock_successor_public_request_response_menu__request_scope_check__delta__refresh_notice__selection__response_menu}\\
$\to$ \path{packet_membership_check}\\
$\to$ \path{worked_example_receipt_interlock_successor_public_request_response_menu__request_scope_check__delta__refresh_notice__selection__response_menu__packet_membership_check}
\end{quote}
The maintained worked route catalog now also imports this successor-facing response-menu key together with the selected-object key carried by the successor-followup owner map for each shipped notice/follow-up pair. So the visible refresh branch's first sufficient successor owner and the maintained selector that chose it can both be recovered without reopening adjacent ledgers by hand. If a later paper instead needs the exact bounded successor-facing handoff slice after one such menu choice has been fixed, that narrower packet owner belongs in Synthesis~72 rather than here.
