\section{Why packet-closure verdicts deserve their own note}
The successor-facing response packet from Synthesis~72 solves the \emph{what exact bounded slice should travel?} question.
A later terse paper still faces one smaller maintenance question.
May it stop there?
Without one maintained closure verdict, the reader must infer from surrounding notes that no further public-request owner remains on this branch once the exact successor-facing packet has been cut.
That inference is short but still reconstructive.
A closure verdict turns ``nothing more is needed here'' into a positive, digest-bound object.

\begin{definition}[Public request response packet refresh response packet closure verdict]
Fix one public request response packet refresh response packet $\Pi^{\mathrm{succ}}$.
A \emph{public request response packet refresh response packet closure verdict}
\[
C(\Pi^{\mathrm{succ}})=(\Pi^{\mathrm{succ}},\sigma,\kappa,R,H,P,V)
\]
contains one exact successor-facing packet $\Pi^{\mathrm{succ}}$, one closure status $\sigma$, one closure-scope token $\kappa$, one reopen-trigger set $R$, one reopen-owner map $H$ sending each trigger in $R$ to the first maintained owner that regains authority when that trigger fires, one closed public-path set $P$, and one mirrored outside-closure validation set $V$.
When $\sigma=\texttt{closed\_finite\_basis}$, the verdict certifies that the exact successor-facing packet already contains the whole bounded public slice needed for the shipped follow-up taxonomy and that no further successor-facing public-request owner must be imported unless some trigger in $R$ fires.
\end{definition}

\begin{definition}[Terminal-basis rule]
A packet-closure verdict satisfies the \emph{terminal-basis rule} if it cites exactly one successor-facing response packet from Synthesis~72 and declares \texttt{closed\_finite\_basis} only when the cited packet already contains the selected owner excerpt and every narrower companion path that owner requires for auditability of that visible reissue sentence.
So closure may certify only a packet that is already exact, not a menu choice that still needs packetization.
\end{definition}

\begin{definition}[Closure-scope rule]
A packet-closure verdict satisfies the \emph{closure-scope rule} if it certifies closure only for the exact public packet basis already cut by the imported successor-facing response packet, while any reused shared validation companions are mirrored only as outside-closure support surface. So closure may name those companions for auditability, but it may not silently absorb them into the finite public basis or let them replace the packet as the terminal owner.
\end{definition}

\begin{definition}[No-hidden-successor-owner rule]
A packet-closure verdict satisfies the \emph{no-hidden-successor-owner rule} if it certifies closure only when no additional successor-facing public-request owner kind remains unresolved for the same emitted refresh notice and shipped follow-up class.
So closure may not hide an unowned tail behind the words ``already complete''.
\end{definition}

\begin{definition}[Reopen-trigger rule]
A packet-closure verdict satisfies the \emph{reopen-trigger rule} if it lists only branch-local events that invalidate closure of the cited packet, such as a shipped follow-up taxonomy expansion, a packet-reuse verdict of \texttt{reopen}, or a future rewrite in which the emitted visible sentence no longer compresses the same packet-local delta family.
So the verdict certifies finite basis only until a named local reason to reopen appears.
\end{definition}

\begin{definition}[Reopen-owner rule]
A packet-closure verdict satisfies the \emph{reopen-owner rule} if it maps every listed reopen trigger to the first already-maintained owner that regains authority when that trigger fires: the successor follow-up response menu when the shipped follow-up taxonomy expands, the predecessor packet carryforward profile when packet reuse reopens, or the refresh-notice selection when the visible sentence must rebind to a new packet-local delta family.
So the verdict does not merely say that the branch can reopen; it says where the next auditable stop lives once it does.
\end{definition}

\begin{definition}[Request-side terminal citation normal form]
A packet-closure verdict together with its already-fixed predecessor notice/packet owners satisfies the \emph{request-side terminal citation normal form} if a later terse paper may cite exactly four maintained anchors in order: one paper-level public request notice from Synthesis~61, one exact bounded response packet from Synthesis~65, one exact successor-facing response packet from Synthesis~72, and one packet-closure verdict from this note.
All intermediate notice-normal-form, selector, response-menu, refresh-notice, refresh-family, and packet-reuse owners remain cited support for those four anchors rather than extra terminal stops.
So the normal form compresses one already-audited request branch into one reuse-ready citation tuple without creating a new owner.
\end{definition}

\begin{definition}[Request-side terminal sentence normal form]
A request-side terminal citation normal form satisfies the \emph{request-side terminal sentence normal form} if a later terse paper may render those same four owned anchors as one exact sentence with four slots: one opener slot naming the public request notice, one first-cut slot naming the bounded request packet, one surviving-public-cut slot naming the successor-facing response packet, and one closure slot naming the closure verdict together with its explicit scope and reopen posture.
So the sentence adds no new owner and no extra bridge step; it is only a stable one-clause rendering of the already-owned four-anchor stop.
\end{definition}

\begin{lemma}[Packet-closure verdicts let later papers stop at the exact successor packet without silent branch growth]
Assume every packet-closure verdict satisfies the terminal-basis rule, the closure-scope rule, the no-hidden-successor-owner rule, the reopen-trigger rule, and the reopen-owner rule.
Then a later terse paper may cite one maintained closure verdict to say that the refreshed visible-handoff branch is closed by one exact successor-facing packet under the shipped follow-up taxonomy, without extending the source-only successor tail by implication.
\end{lemma}

\begin{proof}
The terminal-basis rule ensures the cited packet is already the exact bounded successor-facing slice rather than a still-unpacked owner choice.
The closure-scope rule ensures the certified finite basis stays attached to the exact public packet rather than drifting outward to reused validation companions.
The no-hidden-successor-owner rule ensures no further public-request owner remains unresolved for the same visible sentence and follow-up class.
The reopen-trigger rule names the only local ways in which that closure can fail later.
The reopen-owner rule says which already-maintained owner answers first once one such trigger fires.
So the verdict adds one narrow but useful fact: that the branch may stop here until one named trigger reopens it, and that reopenings still land at a first-sufficient owner rather than an improvised prose tail.\qedhere
\end{proof}

\begin{lemma}[The terminal citation normal form is enough for request-side reuse]
Assume one paper-level public request notice still names the same source-only lineage, one exact bounded response packet from Synthesis~65 still answers the opening follow-up class on that lineage, one exact successor-facing packet from Synthesis~72 still carries the visible refreshed public basis for the successor-facing follow-up class, and the cited packet-closure verdict satisfies the terminal-basis rule, the closure-scope rule, the no-hidden-successor-owner rule, the reopen-trigger rule, and the reopen-owner rule.
Then a later terse paper may cite just the four-anchor request-side terminal citation normal form --- notice, bounded request packet, successor-facing packet, closure verdict --- to say where the request branch begins, what exact omitted-support slice first answers it, what exact visible-refresh slice remains public in the successor cut, and why that branch currently stops there.
\end{lemma}

\begin{proof}
The opening notice fixes the public lineage that made the source-only branch available.
The bounded response packet fixes the first exact omitted-support handoff for that lineage.
The successor-facing packet fixes the exact public slice that survives once the visible refresh wrapper has been chosen.
The closure verdict then certifies that no additional public-request owner remains on that successor-facing branch under the shipped follow-up taxonomy, while still naming the local events that would reopen it and the first owner that would regain authority.
So the four-anchor tuple is enough for reuse-ready citation unless the question changes family or one named reopen trigger fires.\qedhere
\end{proof}
