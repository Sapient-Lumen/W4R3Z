## Evidence found

The maintained support-bundle materializer had started to expose richer resolver payloads, but the shipped `example_support_bundle_map.json` did not yet make bundle-to-owner-row multiplicity authoritative. The sharp case was `bundle://worked-example/fallback-cct`: it is consumed by `eval-fallback-cct-v1`, but the current archive uses that same replay/support bundle for both the base fallback contact row and the verifier-carried notary replay packet.

## Change made

The Synthesis~17 materializer now groups materialized owner-map rows by `support_bundle_id`. For each materialized support-bundle row it emits:

- `resolved_owner_map_row_names`,
- `resolved_owner_map_rows`,
- row-local materialization status,
- receipt / variant receipt / verifier report file where applicable,
- replay plan id and plan spec id,
- support consumed-by / required-artifact / pointer payloads,
- public objects,
- and evidence, coarsening, or contact-surface identifiers where applicable.

The fallback-CCT row now resolves both `fallback_contact_surface` and `notary_replay_packet`. This prevents a later bridge note from treating the bundle as though it had only one current-cut owner row.

## Validator hardening

`validate_example.py` now records:

- `verifier support-bundle resolver owner-row multiplicity closure`.

The check rebuilds the expected resolver rows from the materialized owner-map rows, rejects missing or mismatched `resolved_owner_map_rows`, fails if legacy singleton shortcut fields leak back onto support-bundle rows, and specifically checks that `bundle://worked-example/fallback-cct` resolves both `fallback_contact_surface` and `notary_replay_packet`.
