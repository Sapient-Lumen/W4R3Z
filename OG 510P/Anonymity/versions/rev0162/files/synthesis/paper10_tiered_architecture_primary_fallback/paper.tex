\begin{abstract}
Several papers in this archive quantify a recurring empirical/operational lesson:
in low-latency DHT lookups, repeated use drives per-lookup identification budgets into the $10^{-2}$--$10^{-4}$ bit range, making dummy cover and equalization alone economically collapse (dummy fractions $w/K\to 1$) unless observation probability is extremely small.
This note makes the deployment implication explicit and non-redundant: treat the raw DHT as a \emph{budgeted fallback}, and put strong privacy mechanisms in a \emph{primary path} whose surface is small enough for cryptographic query privacy and stricter change control.
\end{abstract}

\paragraph{Scope.}
This is an architectural synthesis note. It does not introduce new bounds; it composes the Boss-Fight dial sheet, destination-equalization contracts, and release/certification machinery into a single deployment pattern.

\paragraph{Exports.}
A concrete, auditable \emph{two-path} pattern (primary + fallback) and a checklist of what must be declared in receipts so the pattern is honest.

\section{Why a two-path pattern}
Boss Fight budgeting (repetition) is not a ``corner case'': deployed clients make many lookups per window.
In the simplest ``forced destination + dummies'' slice, once the per-lookup budget $b$ becomes tiny, the required dummy fraction approaches $w/K\approx p_{\mathrm{obs}}/(2^b-1+p_{\mathrm{obs}})$ (Boss Fight B).\cite{series:bossfightB}
Under an IPFS-style Kademlia slice and a modest corruption fraction, this pushes $w/K$ close to $1$ at $Q\approx 10^3$ lookups per window.\cite{series:bossfightB}

The design implication is not that all anonymity is hopeless, but that \emph{mechanisms must change}: either (i) reduce the repeated-use budget pressure (rate-limit, cache, coarse bucketing), (ii) reduce observation probability dramatically (shield contacts; see Synthesis~11), and/or (iii) use cryptographic query privacy on a surface small enough to afford it.

\section{Pattern: primary cryptographic path + budgeted DHT fallback}
\paragraph{Primary path (do privacy work here).}
Route the majority of ``routine'' queries through a small, managed surface (e.g., delegated routing / indexer-like services) where cryptographic query privacy, auditing, and hardening are tractable.
The primary path should export:
\begin{itemize}[leftmargin=1.2em]
\item a clear query-privacy mechanism description (what is hidden from whom, under what assumptions),
\item any destination/privacy equalization contract (MC-EQ) if transcript structure remains observable,\cite{series:mceq}
\item change-control gates and recertification triggers for drift.\cite{series:recert}
\end{itemize}

\paragraph{Fallback path (treat raw DHT as residual).}
Use the raw DHT only when the primary path cannot answer (long tail, outages).
The fallback path is not ``free'': publish its Boss-Fight budget assumptions (window $Q$, observation model, and resulting per-lookup budget) as a receipt line item.\cite{series:receiptitems,series:bossfightB}
If a deployment cannot make the fallback budget small enough, the receipt must say so.

\paragraph{Rate limiting as a first-class privacy knob.}
The most effective lever in the fallback path is the query budget $Q$ per window.
A deployment should expose $Q$ as an explicit policy parameter (not just an abuse-control parameter) and include it in ABOM/OINL and release receipts.\cite{series:receiptitems,series:abomoinl,series:release}


\subsection{Accounting across paths (mixture bound)}
If path choice is public (or independent of the secret), the overall observation channel is a mixture.
A conservative bound for maximal leakage is convenient for receipts.

\begin{theorem}[Mixtures of channels are log-sum-exp bounded]
Let $W$ be a random path selector independent of the secret $C$, with $\Pr[W=1]=\pi$.
Let $\mathcal{L}_1$ and $\mathcal{L}_0$ be the induced transcript channels for the fallback and primary paths, with maximal leakages $b_1$ and $b_0$.
Then the mixture channel satisfies
\[
\MaxL(C\to Y)\;\le\;\log_2\big(\pi\,2^{b_1} + (1-\pi)\,2^{b_0}\big).
\]
\end{theorem}
\begin{remark}
This bound makes the practical requirement explicit: receipts should publish an upper bound on fallback usage $\pi$ (or a monitored estimate with a confidence bound), because even a strong primary path can be dominated by frequent fallback.

\paragraph{Secret-dependent fallback is worse.}
If fallback selection depends on the hidden destination/profile or on secret-correlated state (cache hits, popularity, rate-limit state), then the indicator ``used fallback'' is itself a witness stream.
In that case, mixture accounting is insufficient: one must also budget the \emph{path-selection tax} and publish bounds on the secret-dependence of fallback selection (e.g., ratio bounds on $\pi_c$ across declared secret pairs).\cite{series:fallbacktax}
\end{remark}

\section{What to publish so the pattern is honest}
ABOM/OINL and release receipts should include at least one line item per path using the series' minimal schema (Synthesis~12).\cite{series:receiptitems}
To keep the boundary legible, publish:
\begin{itemize}[leftmargin=1.2em]
\item the path policy (when each path is used) and the transcript tier(s) it exposes,
\item the threat window and usage assumptions (e.g., $Q$ per window) and a bound/estimate for fallback usage $\pi$,
\item the observation parameter(s) $p_{\mathrm{obs}}$ (or monitored upper bounds); if multiple tiers are published, include a tiered observation vector and its combination rule,\cite{series:obsatten,series:tieredobs}
\item the per-path budget value(s) and the knob hashes that determine the accountant (dummies, timeouts, equalization parameters).
\end{itemize}

\section{Takeaways}
\begin{itemize}[leftmargin=*]
\item \textbf{Stop trying to make the raw DHT do everything:} use it as a fallback with an explicit, published Boss-Fight budget.
\item \textbf{Put strong privacy in the primary path:} small surfaces are where cryptographic query privacy and strict change control are feasible.
\item \textbf{Publish the boundary:} receipts must state when fallback happens and what it costs.
\end{itemize}
