\begin{abstract}
Most mechanism papers in this archive culminate in a published receipt payload: an ABOM/OINL envelope plus a small set of line items, anchored in an append-only transparency log.\cite{series:abomoinl,series:receiptitems,series:transparencyprimitives}
A natural question is what an \emph{end user} can verify while interacting with a live system.
This note does not attempt to solve ``trustless anonymity''; it standardizes a small \emph{user-verifiability interface} that is sufficient to (i) discover the relevant receipt, and (ii) validate that the receipt is anchored in an append-only log with inclusion/consistency proofs.
The goal is to make the gap between provider-side accountability and user-side assurance explicit and machine-addressable, without bloating mechanism papers.
\end{abstract}

\paragraph{Scope.}
This is a short interface note.
It specifies the minimal discoverability and validation hooks a deployment can expose so that users can \emph{locate} and \emph{validate} published claims.
It does not cover external probing of a dishonest provider, censorship-resistance of publication, or client-side traffic analysis; those are separate threat models.

If the deployment uses OHTTP-style gateways and wants standardized \emph{transport} discovery, RFC~9540 (SVCB/HTTPS parameters for oblivious services) can be used; the UVI record remains a higher-layer pointer to the published receipt.\cite{rfc9540OHTTPDiscovery}

\paragraph{Imports.}

\section{The user-verifiability record}

A UVI is a \emph{small} object carried by the client (or shown by a UI) that points to a published receipt and the log proofs needed to trust that receipt.

\begin{definition}[User-verifiability record]\label{def:uvir}
A \emph{user-verifiability record} (UVI record) is a small object a client can retrieve while interacting with a deployment.
It contains:
\begin{enumerate}[leftmargin=*]
\item \textbf{Receipt pointer (envelope ids):} \texttt{claim\_id}, \texttt{tw\_id}, and (when applicable) \texttt{state\_decl\_id}, matching the receipt envelope (Synthesis~12).\cite{series:receiptitems}
\item \textbf{Surface identifier:} the declared \texttt{exposure\_nf\_id} naming the transcript projection the receipt covers.\cite{series:traceifaces}
\item \textbf{Receipt digest:} a cryptographic digest of the exact receipt payload being relied on (ABOM/OINL carrier + line items).\cite{series:abomoinl,series:receiptitems}
\item \textbf{Log anchor:} a tuple sufficient to check inclusion in an append-only log: log id, signed checkpoint, and an inclusion proof for \texttt{receipt\_digest}.\cite{series:transparencyprimitives}
\item \textbf{Consistency context:} either (i) a recent signed checkpoint previously trusted by the client, or (ii) a pointer to a consistency proof chain, so clients can detect equivocation across time.\cite{series:transparencyprimitives}
\end{enumerate}
The record may be served via an HTTP endpoint, a signed gossip message, a DHT record, or a handshake extension; this note is agnostic to transport.
\end{definition}

\begin{remark}[Why this is minimal]
The UVI record does \emph{not} ship artifacts, evaluation traces, or proofs-of-correctness.
It only lets a user answer three basic questions: ``what receipt is the provider claiming?'', ``what transcript surface does that receipt actually cover?'', and ``is that receipt publicly anchored in an append-only log?''
Those questions are sufficient to prevent a large class of \emph{silent drift}, \emph{interface drift}, and \emph{selective disclosure} failures from being invisible to users.
\end{remark}

\begin{remark}[What a client can compare across releases]
A client does not need to understand the budget math to notice when a provider changes claim surface.
If two releases advertise the same \texttt{claim\_id} but a different \texttt{exposure\_nf\_id}, the client has learned something operationally important: the deployment is no longer presenting the same interface claim and should expose a new receipt lineage.
Optional deployment-specific adjuncts may make that comparison easier (for example a watch policy or a compact compare profile), but those should remain \emph{adjacent} public objects rather than extra mandatory UVI fields.
The worked-example micro-note (Synthesis~17) shows one concrete way to pair a minimal UVI record with such adjuncts while keeping Def.~\ref{def:uvir} unchanged.\cite{series:workedexample}
\end{remark}

\section{A validation lemma (what a user can check)}
Let $R$ be a receipt payload (ABOM/OINL carrier + line items), and let $h(R)$ be the digest the UVI record presents.
Let $\mathcal{L}$ be an append-only log that supports (i) checkpointed signed tree heads and (ii) inclusion/consistency proofs.\cite{series:transparencyprimitives}

\begin{lemma}[User-side validation is mechanical]\label{lem:validate}
Assume:
(i) the receipt payload $R$ is signed under the deployment's declared release key (or notarization key), and
(ii) the UVI record provides a valid inclusion proof that $h(R)$ is included under a signed log checkpoint.
Then a client can mechanically validate that (a) the provider is committing to $R$ as a public claim object, and (b) the claim is anchored in an append-only log state that is auditable by third parties.
\end{lemma}

\begin{proof}[Proof sketch]
Verify the receipt signature using the declared release key.
Verify the inclusion proof against the signed checkpoint.
A standardized checklist for these mechanical steps (and for the auditor-side replay workflow) is given in Synthesis~20.\cite{series:auditorreplay}
These checks are exactly the interface provided by the log primitive.\cite{series:transparencyprimitives}
No privacy-domain reasoning is needed at validation time; semantics of the receipt line items are owned by their respective series notes and can be audited separately.\cite{series:receiptitems}
\end{proof}

\section{Failure modes (what this does \emph{not} solve)}
The UVI record is intentionally small; it does not eliminate all ways a provider can misbehave.
We list common residual failure modes so mechanism papers do not have to repeat them.

\paragraph{Withholding / non-discoverability.}
A provider can simply refuse to serve a UVI record.
This is a product and governance issue: UVI is meaningful only if clients treat absence as a policy failure.

\paragraph{Equivocation across users.}
A provider can serve different receipts to different users.
Inclusion in an append-only log helps only if clients (or watchdogs) obtain and compare checkpoints and require consistency proofs.
This is why Def.~\ref{def:uvir} includes \emph{consistency context}.

\paragraph{Compliance versus behavior.}
A receipt is a claim; it does not force runtime compliance.
Detecting runtime deviation requires monitoring, audits, and (often) closed-view attestations, which are treated elsewhere in the series.\cite{series:state3}

\section{How this plugs into the series (one paragraph)}
Synthesis~0 states a provider-side scope limitation: the archive is primarily about making claims addressable and auditable.\cite{series:contractobjects}
This note adds a minimal user-facing hook that preserves that philosophy:
users need not re-derive anonymity proofs, but they can \emph{pin} the provider to a public receipt, see which transcript surface that receipt covers, and detect silent drift or selective disclosure.
Mechanism papers should not repeat UVI details; they should merely ensure their exported receipt line items carry an \texttt{exposure\_nf\_id}, can be carried by ABOM/OINL, and can be anchored by the transparency interface.
When user-facing drift comparison matters, deployments may publish small adjunct objects around the UVI record, but the core discoverability contract should stay minimal.
