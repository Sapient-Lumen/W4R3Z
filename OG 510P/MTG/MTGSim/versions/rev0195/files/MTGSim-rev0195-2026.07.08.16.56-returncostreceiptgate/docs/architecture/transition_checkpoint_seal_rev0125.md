# rev0125 — Transition checkpoint seal

rev0125 audits the transition-result boundary after rev0124's selected-action seal. A committed transition could already expose the selected canonical `LegalAction`, checked page/queue proofs, the staged causal receipt hash, and post-action/pre-receipt journal evidence. The remaining caller-facing gap was that the result still carried those facts mostly as scalar hashes and counts; a search/replay/agent caller could not verify the exact pre-state it proposed against and the exact post-state that was adopted using the cube's existing checkpoint protocol.

This revision makes before/after checkpoint seals first-class on `TransitionResult` through `StateCheckpointSeal checkpoint_before` and `StateCheckpointSeal checkpoint_after`. `capture_transition_before(...)` now samples `make_state_checkpoint_seal(game)` once and derives the transition scalar fields from that seal. `capture_transition_after(...)` does the same for the post-state. That refactor removes the private duplicate action-receipt counter helper and prevents the scalar StateCore/journal/action-receipt/event-sequence fields from drifting independently from the durable checkpoint contract.

The new helpers are `has_transition_checkpoint_seals()`, `checkpoint_stable()`, `rejected_with_checkpoint_stability()`, and `committed_with_checkpoint_seals()`. `committed_with_atomic_adoption_guard()` now requires checkpoint-seal consistency in addition to staged adoption, checked receipt consistency, the hashed causal receipt, choice proofs, and the post-action journal seal. The public `transition_result_matches_receipt(result, receipt)` verifier also rejects result/receipt verification when the result's checkpoint seals no longer match its scalar fields.

`test_commit_action_transition_carries_state_checkpoint_seals` proves the new contract both ways: a committed priority pass carries a before seal that verifies against the proposal state and an after seal that verifies against the adopted state, while an illegal wrong-player transition rejects with stable before/after checkpoint seals and no caller-state mutation. The regression also tampers with the post-state checkpoint journal hash to prove both the helper and public receipt verifier catch checkpoint drift.

The next deep semantic cut should push this same staged/checkpointed transition surface into one multi-phase action family, preferably paid casting or activated abilities, where target/mode locks, mana/payment, stack placement, and failure rollback can be named as transaction phases instead of hidden inside a single mutation call.
