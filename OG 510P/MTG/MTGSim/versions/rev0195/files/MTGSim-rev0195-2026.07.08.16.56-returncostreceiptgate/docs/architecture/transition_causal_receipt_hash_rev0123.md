# rev0123 — Transition causal receipt hash

rev0123 audits the last unsealed handoff inside the staged transition adoption path. rev0120 made adoption atomic, rev0121 exposed the post-action/pre-receipt journal sample on `TransitionResult`, and rev0122 made the same sample explicit on `ActionReceiptRecord`. The remaining gap was row identity: immediate transition callers could see the causal receipt index and compare typed fields, but they could not carry a compact hash of the exact receipt row that was checked before adoption.

This revision adds `kActionReceiptRecordSchemaVersion`, public `action_receipt_hash(const ActionReceiptRecord&)`, and `TransitionResult::causal_receipt_hash`. `commit_action_transition(...)` now hashes the latest staged `ActionReceiptRecord` immediately after receipt append, before the staged state is adopted. `committed_with_hashed_causal_receipt()` and the strengthened `committed_with_atomic_adoption_guard()` make the row-hash contract executable: a committed transition must name one causal receipt, expose the current receipt hash schema, and bind a nonzero hash for the exact row that passed `transition_receipt_matches_result(...)`.

The hash domain is `MTGSim.ActionReceiptRecord.v1`, and the hash covers the existing structured receipt payload: canonical action identity, choice request and APNAP queue proof fields, StateCore hashes, post-action/pre-receipt journal aliases, event-sequence bounds, legality, and applied status. This is intentionally an immediate transition-result surface, not an `ActionTrace.v17` change. Persisted trace text remains at `ActionTrace.v16` while the reducer API gains a stronger in-memory proof for branch/search/agent consumers that want to cache or compare the adopted receipt row without re-reading the whole journal.

The regression `test_commit_action_transition_carries_hashed_causal_receipt` proves that the transition result hash equals the adopted latest receipt hash and changes when action or post-action journal evidence drifts. Existing commit and rejection tests were also tightened so rejected transitions carry no causal receipt hash while committed transitions satisfy the new helper. The datacube audit now probes the type, engine, tests, docs, rule ledger, and receipt wiring for this hash seam.

The next semantic step remains paid-cast or activated-ability staging. This receipt hash does not by itself add multi-phase rollback inside an action body; it seals the current top-level staged adoption contract so deeper reducers can reuse one checked, hashed receipt boundary after their internal transaction phases succeed.
