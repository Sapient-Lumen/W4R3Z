# AGENTS.md

Purpose: keep future LLM/archive-maintenance passes **small, cumulative, mirrored, and honest**.

## Read before editing
1. `INDEX.md`
2. `PRIORITIES.md`
3. `STRATEGIC_FRONTIER.md`
4. `RESEARCH_LOG.md`
5. `meta/AMNESIA_RESISTORS.md`

Do not start by appending ideas blindly. First identify whether the next worthy move is:
- a new gap,
- a design/pilot deepening,
- an explicit epic/proposal-layer promotion,
- a ranking/frontier correction,
- or repo hygiene/meta-engineering.

## Archive invariants
- Root files are the editable canonical surfaces.
- `archive/` must mirror any referenced root files changed in the same revision.
- Keep additions **tight and salient**. Prefer synthesis to sprawl.
- Prefer citations/URLs over long quotations or downloaded bulk artifacts.
- Do not silently convert tentative frontier notes into executable seams; when promoting a seam, pair it with an epic and/or pilot or state clearly that it remains note-only.
- Do not flatten adjacent layers into one fake story. Follow `meta/AMNESIA_RESISTORS.md`.

## Preferred move selection
Choose **one high-leverage move per revision** unless a second change is required for integrity.
Good moves:
- promote an already-strong seam into an explicit epic;
- promote a high-reuse lower-level anchor inside an already-explicit stack when that anchor is what multiple stacks actually import and it still lacks its own proposal-layer file;
- when multiple stacks keep re-describing invocation/root/config-walk truth, prefer promoting a dedicated discovery-boundary anchor instead of letting repo/script/editor/environment notes each re-own discovery;
- when release, manifest, publisher-identity, and CI notes keep re-describing source-package publication, prefer promoting a dedicated publish-set anchor instead of letting release tooling, registry UX, and package-admission notes each re-own publish subject/payload/receipt truth;
- when publish-set, API, inventory, trust, and policy notes keep re-describing the same package publication decision, prefer sharpening Package Admission as the linked publish-review layer instead of letting every imported kit grow its own stealth verdict surface;
- promote a stack that already has a design note + pilot program but still lacks its proposal-layer file before inventing another adjacent kit;
- add one missing cross-stack synthesis that current ecosystem evidence makes timely;
- sharpen ranking when upstream motion changes the map;
- periodically rebalance toward underrepresented deployment domains and ecosystem bands (robotics, geospatial, industrial/ops, scientific/physical systems, dynamic testing/security tooling) instead of only Cargo-adjacent seams;
- when upstream language motion reopens a userland frontier (for example reflection/comptime), prefer a transition boundary that compares real existing lanes before inventing a winner;
- when official Rust challenge/vision work says a pain point is caused by ecosystem lock-in across competing runtimes/frameworks (for example async runtime choice), prefer promoting the lower-level commons boundary beneath lifecycle/productization stacks instead of letting each downstream stack re-own portability folklore;
- when safety-critical or formal-methods activity rises and backend plurality is increasing, prefer a proof-artifact boundary plus ranked pilot program before inventing another verifier wrapper, proof badge, or certification-facing mega-stack;
- add one amnesia resistor or repo-operational guardrail that reduces future drift.

Avoid:
- many small adjacent ideas,
- generic ecosystem wishlists,
- duplicating an existing seam under a new name,
- framework bake-offs without a missing portable boundary.

## Evidence discipline
- Research current signals before promoting a seam.
- Favor primary / official sources where possible.
- Name what is still unstable, partial, or connector-specific.
- Preserve migration/deprecation realities when upstream APIs are moving.
- For starter/bootstrapping revisions, do not assume `cargo new` + `cargo-generate` cover the whole space; cite at least one real domain bootstrapper when arguing the shape of the seam.
- For reflection revisions, cite at least one language-roadmap source and at least two live userland lanes from different semantic families (for example runtime reflection, visit-only inspection, schema tracing, or associated-const shape metadata) before claiming the seam has moved.
- For testing-stack revisions, cite at least one upstream Rust/Cargo testing source and at least one live runner/tooling source before claiming the seam has moved, and keep unstable native output, portable pack shape, and runner-native recording posture explicit.
- For coverage revisions, cite at least one upstream compiler/coverage source, at least one live execution or runner/tooling source, and at least one contrasting engine or criterion signal before claiming the seam has moved; keep criterion identity, execution imports, merge comparability, and gate posture explicit.
- For benchmark-evidence revisions, cite at least one upstream Cargo/Rust benchmark source and at least two live benchmark lanes from different semantic families (for example statistical benchmarking, deterministic callgrind-style measurement, runner imports, or hosted compatibility layers) before claiming the seam has moved; keep harness discovery, benchmark-native results, runner imports, baseline imports, and Perf Labs policy handoff explicit.
- For cargo-report/build-analysis revisions, cite at least one stable Cargo report source and at least one unstable/build-analysis source before claiming the seam has moved; keep authoritative native basis, authority-origin/import-path truth, fallback-order posture, refusal-posture gates, stable-vs-unstable posture, exact session/report scope, observed coverage slice, lane-wide claim-class honesty, contradiction/arbitration posture for same-scope competing artifacts, review-queue hold status, observation epoch, currentness class, recheck-gate posture, local-private-versus-shared-versus-frozen-head posture, promotion/head warnings, replay-versus-copy provenance, superseded/stale-head warnings, import-compatibility receipts, decoder/toolchain/schema-drift posture, material-change reimport/re-review triggers, and downstream build/perf/debug handoffs explicit.

## What not to confuse
- repo-operational instructions are not research canon;
- support/docs claims are not evidence by themselves;
- derived assistant renderings are not canonical archive truth;
- one provider/framework/runtime lane is not the whole ecosystem.
- accepted RFCs, project-goal milestones, nightly experiments, and stable shipped capability are not the same thing.
- userland workaround crates are not language-native closure, even when they are strategically important.
- declared auth-method support is not the same thing as protected-surface coverage, provider/session/key activation, or authorization-policy reality.
- a working CRDT demo, sync session, or app shell is not the same thing as durable replica truth, awareness/presence truth, relay/runtime-role truth, recovery/export posture, or supported local-first product behavior.
- checked queries, generated or introspected database schema, migration execution, runtime backend/secret activation, and public API/schema attachments are not the same thing, even when one app imports all of them.
- board/probe/run truth is not the same thing as target/linker/sysroot/build-std activation, footprint/layout evidence, runtime-evidence channels, or shipped/support conclusions, even when a single firmware repo contains all of them.
- declared query/ranking support is not the same thing as corpus freshness/import truth, hybrid/model attachments, runtime search activation, or shipped/support/agent conclusions, even when one search repo contains all of them.
- declared spatial semantics are not the same thing as dataset/catalog/archive publication truth, runtime/native/object-store/backend activation, or imported client/search/service/support conclusions, even when one geospatial repo contains all of them.
- declared operator CRDs, status/condition semantics, RBAC/capability posture, webhook/health/admin surfaces, install/upgrade/Kubernetes-version truth, and downstream release/support conclusions are not the same thing, even when one operator repo ships all of them.
- declared jobs/workflows/schedules, runtime/engine/storage activation, history/journal/retry/recovery evidence, long-lived release lineage, and downstream support/incident/release conclusions are not the same thing, even when one durable-work repository ships all of them.
- selected build subject, final Cargo-facing artifacts, sidecar attachments, release bundles, and installed-state receipts are not the same thing, even when one CI run emits all of them.
- imported recommendation truth, starter render-plan/adapter truth, rendered working-tree ownership, local overlays, and derived quickstart/assistant outputs are not the same thing, even when a single starter repo makes all of them look adjacent.
- Cargo-native build-state reuse, editor-private duplication, compiler-wrapper cache hits, container-layer reuse, and CI/plugin exchange are not the same thing, even when one pipeline makes them look adjacent.


- Device-lab proposals must separate board/profile truth, lab capability/quarantine truth, run-plan truth, native capture imports, normalized run reports, and downstream firmware/support/release claims: do not collapse `probe-rs`, `embedded-test`, serial/defmt output, shared-lab maintenance state, and final “tested on hardware” statements into one fake artifact or one runner-shaped story.

## Cargo Report Kit review-separation rule (rev0319)
If stronger Cargo-report reuse depends on manual review, do not stop at `requester` and `reviewer` strings alone.
Preserve one explicit **review-separation receipt** saying who proposed the stronger carry, who reviewed it, who executed it, whether the reviewer was an independent checker, and which compensating control plus expiry applies when the same actor or same team carried too much of the flow.
A decision witness without that separation receipt is incomplete for public-example, frozen-head, contradiction-resolution, or rechecked-current carry.

- initialization-surface revisions must separate storage origin, address-stability timing, staged assembly, weak/self or borrowed-handle exposure, publication transitions, and teardown guarantees instead of narrating one fake constructor-support story.
