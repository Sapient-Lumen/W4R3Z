# Kernel slice protocol (rev0484)

## Why this protocol exists
The archive now has v0 kernel briefs for the top band.
Those briefs say what a bounded first repo should contain, but they are still too broad to govern the **first thin milestone**.
This protocol exists so future revisions stop collapsing “honest first repo shape” into “ship everything in the brief now”.

## When to use this protocol
Use this protocol when the question is any of:
- what should land in the first real milestone of a top-band kernel;
- what files, commands, schemas, fixtures, or cards belong in slice 0;
- what is postponed to later slices;
- what proof should be demanded before the kernel widens.

Do **not** use this protocol merely to rerank candidates, invent a new frontier, or bypass live packet posture.

## Minimum required moves
A kernel-slice revision must:
1. Name the governing kernel brief and current live-packet verdict.
2. State why this slice is first instead of adjacent alternatives.
3. Keep deliverables bounded enough that one small team could honestly attempt them next.
4. Name at least one proving ground that is real, local, and replayable.
5. Name what is explicitly postponed beyond slice 0.
6. Ship failure receipts or unsupported-state notes whenever imported seams are unstable, partial, or tuple-specific.
7. State the next-slice trigger so “later” does not become hand-wavy expansion permission.

## Required fields
Every kernel slice should contain:
- identity
- why this slice first
- exact deliverables
- acceptance checks
- proving grounds
- imports and dependencies
- postponed work
- failure receipts
- next-slice trigger

## Refusal rules
A slice note must refuse:
- hosted-service dreams when a local-first slice is enough;
- dashboards that replace proof assets;
- claims of stable substrate where only a prototype seam exists;
- and milestone plans for candidates still in `hold` posture.

## Default interpretation
When this protocol is active:
- broad rank remains unchanged;
- live packets decide whether the candidate is `advance`, `deepen`, or `hold`;
- kernel briefs decide the first honest repo shape;
- and kernel slices decide the first bounded implementation milestone inside that shape.
