# Design: Epic Contribution Ladder 2026

## Thesis
This file ranks **what the archive should actually try to build next**, not just which research seams are intellectually interesting.

The archive now has enough stack notes that a new risk has appeared: **frontier richness can turn into implementation drift**.
A worthy Rust contribution in 2026 is increasingly not “one more good idea” but a **thin companion tool / artifact family** that can survive contact with real projects, real CI, real editors, and real maintenance.

## Why this file exists
The archive already has a good **research priority ladder**.
What it lacked was a second ladder for **build readiness**.
Those are not the same thing.

A seam can be strategically important but still be too socially or technically blurry to turn into a durable companion tool this year.
Conversely, a seam can be somewhat lower in the research hierarchy but much closer to a **thin implementation** because Cargo or crates.io already expose the necessary facts.

This distinction matters more now because official Rust signals are unusually aligned:
- Rust’s March 20, 2026 challenges post says ecosystem navigation still depends too much on tacit knowledge and choice paralysis.
  https://blog.rust-lang.org/2026/03/20/rust-challenges/
- The 2025 State of Rust survey says online docs remain the canonical reference while editor/LLM-mediated learning is rising.
  https://blog.rust-lang.org/2026/03/02/2025-State-Of-Rust-Survey-results/
- Rust’s December 2025 vision work recommends expanding crate-level supportive interfaces and build-workflow extensibility, not just more bare language power.
  https://blog.rust-lang.org/2025/12/19/what-do-people-love-about-rust/
- The 2026 flagship goals keep pushing toward cargo-script, public/private dependencies, SBOM support, and build-std / better build-system integration.
  https://rust-lang.github.io/rust-project-goals/2026/flagships.html
- Cargo 1.94 says workspace/config discovery still poisons unrelated builds too easily, and the March 2026 build-dir-layout testing call shows many tools still rely on Cargo internals because the contract surface is incomplete.
  https://blog.rust-lang.org/inside-rust/2026/02/18/this-development-cycle-in-cargo-1.94/
  https://blog.rust-lang.org/2026/03/13/call-for-testing-build-dir-layout-v2/
- Cargo 1.86 explicitly highlighted `cargo install-update` and says built-in support is still being tracked, showing that consumer lifecycle continuity remains outside Cargo proper.
  https://blog.rust-lang.org/inside-rust/2025/02/27/this-development-cycle-in-cargo-1.86/
- The Rust Foundation’s 2026–2028 strategy explicitly couples stable infrastructure, sustainable maintenance, and adoption growth.
  https://rustfoundation.org/strategic-plan/

Together, those signals say the archive should stop treating “interesting seam” and “buildable epic contribution” as interchangeable.

## Ranking rule
When choosing what to build next, score candidate contributions against six questions:
1. **Breadth of pain** — does it solve a recurring pain for many Rust users or maintainers?
2. **Official momentum** — is Rust/Cargo/crates.io/Foundation already moving in a compatible direction?
3. **Leaf readiness** — does the archive already have enough lower-level kits/stacks for this to be a thin composition layer rather than a moonshot?
4. **Machine-usable boundary** — can the contribution emit portable artifacts / reports instead of screenshots and folklore?
5. **Renewal economics** — can the result stay fresh without a permanent centralized curation empire?
6. **Non-imperial shape** — can it help without becoming the one true installer, workspace manager, registry, or hosted platform?

Default rule: prefer candidates that score well on **at least five** of those six questions.

### 4) Consumer Lifecycle Continuity bundle
Primary files:
- [`design/consumer-lifecycle-continuity-bundle.md`](./consumer-lifecycle-continuity-bundle.md)

Why it is fourth:
- Rust has many ways to acquire and mutate software, but the install → update → rollback/uninstall → route-change story is still fragmented;
- official Cargo semantics already distinguish install roots, install tracking files, lockfile posture, route classes, and built-in installed-binary update gaps;
- it is one of the clearest places where a thin cross-tool receipt chain could reduce folklore without replacing existing tools.

What a worthy contribution looks like in practice:
- a deliberate bundle around one shared `consumer-lifecycle-pack/v0` family rather than another isolated installer or updater;
- first implementation should prove: install receipt import, current managed-state export, one typed update/rollback/uninstall event, one route-change annotation, and one bounded support/incident handoff;
- explicit separation between **published release truth**, **selected acquisition route**, **applied lifecycle event**, and **current managed ownership scope**.

What not to build:
- a universal updater,
- an app store,
- or a stealth package-manager wrapper.

## Practical consequence for this archive
When the frontier feels crowded, the default next move should now be:
1. strengthen the **top buildable candidate ladder**;
2. improve the MVP / artifact shape / non-goals of one Tier A candidate;
3. only then mint a new cross-cutting seam.

This is a deliberate anti-sprawl rule.
It keeps the archive from turning “we understand many missing layers” into “we never choose which ones should actually exist first”.

## The three best immediate bets
If the archive had to fund or build only three things next, the default answer should now be:
1. **Build-State Evidence Stack**
2. **Workspace Environment Stack**
3. **Consumer Lifecycle Continuity bundle**

Reason:
- together they improve day-0 through day-2 reality for a very large share of Rust users;
- each can ship as a thin companion layer instead of a platform rewrite;
- each composes naturally with Package Admission, Canonical Learning, and Adoption Decision later.

## Archive hygiene consequence
Do not mint another frontier note merely because a seam is real.
Mint it only when one of these is also true:
- it clearly changes the buildable-candidate ladder,
- it collapses repeated future drift,
- or it unlocks one Tier A candidate in a way existing notes cannot.
