# Gap: Polyglot host packages, runtime contracts, and support truth

## Summary
A lot of real Rust adoption now happens **inside somebody else's package/runtime surface**:
- a Python wheel built with PyO3 + maturin,
- a Node addon built on Node-API / `napi-rs`,
- Kotlin/Swift/Python bindings generated by UniFFI,
- headers + static/shared libraries handed to a native build,
- or a Wasm component consumed from another language/runtime.

Rust has credible tools in each lane, but the ecosystem still lacks a **portable, reviewable contract** for the thing foreign consumers actually install, import, link, or embed.

Today teams often have to reverse-engineer or manually curate:
- Cargo package identity versus foreign package/module/bundle identity,
- which boundary truth was imported (`ffi-pack`, WIT/component, generated bindings, schema attachments) versus invented locally,
- runtime initialization, threading, callback, async, error, interpreter, ABI, and SDK assumptions,
- platform / interpreter / ABI / SDK support claims,
- exactly which artifacts were packaged and how they should be installed,
- and which docs/debug/support claims are real versus folklore.

## Ecosystem signals
- Rust’s 2026 flagship slate explicitly includes **Wasm Components**, which makes foreign-consumer packaging/runtime lanes a first-class ecosystem concern rather than a niche side topic.
  https://rust-lang.github.io/rust-project-goals/2026/flagships.html
- The Rust/component-model docs now say native `wasm32-wasip2` support is first-class, while the `cargo-component` repository says plain Cargo already covers simple WASI-only lanes but custom-WIT workflows still need `cargo-component` and remain experimental. That is exactly the sort of plural package/runtime reality a portable host-package contract should preserve.
  https://component-model.bytecodealliance.org/language-support/rust.html
  https://github.com/bytecodealliance/cargo-component
- The Rust safety-critical writeup is explicit that many teams will integrate Rust into existing C and C++ systems and carry that boundary for years, and that guidance/tooling to keep interfaces correct, auditable, and in sync would help.
  https://blog.rust-lang.org/2026/01/14/what-does-it-take-to-ship-rust-in-safety-critical/
- The 2025H2 project goal **C++/Rust Interop Problem Space Mapping** exists because mixed-language adoption is a first-class Rust problem, not a niche.
  https://rust-lang.github.io/rust-project-goals/2025h2/interop-problem-map.html
- PyO3 recommends `maturin`, while maturin explicitly says it can build and publish crates with PyO3, cffi, UniFFI bindings, and Rust binaries as Python packages; its distribution docs make Linux wheel portability (`manylinux` / `musllinux`) and cross compilation first-class packaging concerns.
  https://pyo3.rs/main/
  https://github.com/PyO3/maturin
  https://www.maturin.rs/distribution.html
- UniFFI already spans Kotlin, Swift, and Python bindings and is explicit that generated bindings should be safe by default, exposed interfaces must be `Send` + `Sync`, and borrowed-return-style foreign contracts should not leak across the boundary.
  https://mozilla.github.io/uniffi-rs/latest/Getting_started.html
  https://mozilla.github.io/uniffi-rs/latest/internals/design_principles.html
  https://mozilla.github.io/uniffi-rs/0.27/udl/interfaces.html
- Node-API gives a stable addon ABI across Node versions, but that guarantee belongs to the Node-API boundary itself rather than every external library or runtime assumption surrounding an addon. That is exactly the kind of host-package truth that should become machine-readable.
  https://nodejs.org/api/n-api.html
- The 2025 State of Rust survey says online docs remain the preferred canonical reference while some learning traffic appears to be shifting toward LLM tooling. That strengthens the case for small machine-readable package/support artifacts rather than more README archaeology.
  https://blog.rust-lang.org/2026/03/02/2025-State-Of-Rust-Survey-results/

## What “good” looks like
- A machine-readable manifest that keeps **crate identity, foreign package identity, and imported boundary identity separate**.
- Generated bindings, stubs, headers, WIT packages, or package metadata tied to exact source/tool versions.
- Runtime/threading/lifetime/init/error/interpreter/ABI assumptions made explicit per host lane.
- Platform / interpreter / ABI / SDK support exported as reviewable evidence rather than README prose.
- Release/install receipts that tell support and downstream consumers exactly what was shipped for each foreign lane.
- Diff reports that can say whether a change broke the Rust boundary, the foreign package surface, the runtime assumptions, or only the packaging metadata.
