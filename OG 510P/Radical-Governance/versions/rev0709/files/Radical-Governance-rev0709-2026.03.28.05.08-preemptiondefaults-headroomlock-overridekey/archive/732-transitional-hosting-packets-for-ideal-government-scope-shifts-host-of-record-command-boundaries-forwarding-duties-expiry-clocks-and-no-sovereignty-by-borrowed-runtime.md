# 732 — Transitional hosting packets for ideal-government scope shifts: host of record, command boundaries, forwarding duties, expiry clocks, and no sovereignty by borrowed runtime

## One-line thesis

Once the archive has a continuity packet (`730`) and a cutover witness packet (`731`), it should also keep one compact **transitional hosting packet** for the awkward but common period when legal authority has moved while some systems, staff, channels, or operational substrate are still being hosted by the predecessor or a third party: every such bridge should name the principal public holder, the temporary host, the exact host-only powers, the forwarding and cure duties, the money and service-floor terms, the evidence and logging boundary, the break-glass path, and the hard expiry or re-clearance clock — so a borrowed runtime never silently becomes the real constitution.

## Why this matters

The archive can now say where a function should live (`725`, `726`), when that default should be overridden (`727`), how a sideways authority should be built (`728`), who must ratify a move (`729`), what continuity objects must survive it (`730`), and what contemporaneous witness should freeze the handoff state (`731`).

That is enough to design and prove a serious scope shift. It still leaves one practical seam under-specified.

In real reorganisations, the new holder is often legally live before it is fully self-hosting. The predecessor may still run the case system for a short period. A parent department may still host payroll, identity, records storage, or web publishing. A municipality may still answer the phone for a new metro function. A contractor may still operate the intake shell while the successor stands up its own front door. A cloud tenant, service desk, or archive repository may remain with the former institution even though the constitutional holder has changed.

Sometimes that bridging is sensible. Very often it is unavoidable.

But it is also one of the easiest places for constitutional dishonesty to hide.

Without a typed transitional-hosting packet, the polity drifts into a familiar ambiguity:

- the new holder has the law but not the keys;
- the old holder has the keys but claims to be only helping;
- the public cannot tell which front door is merely forwarding and which one is still deciding;
- operators keep taking instructions from the host because the host still controls permissions, templates, routing, or incident handling;
- and what was introduced as a ninety-day bridge quietly becomes the enduring structure of power.

That is not only an implementation risk. It is a constitutional one. Hosting can quietly reallocate agenda control, evidence custody, budget throttling, notice practice, and practical review access even after the formal transfer has occurred.

The archive already has adjacent notes on delegated public functions (`544`), service homes (`615`), workforce homes (`620`), pre-launch conformance (`639`), post-launch observability (`640`), pending-matter transitions (`656`), successor accountability (`657`), evidentiary continuity (`658`), and the new continuity and cutover packets (`730`, `731`). What it still lacked was one smaller reusable object tailored to the claim:

**yes, the new holder is live, but some part of the runtime is still hosted elsewhere for a bounded period.**

That missing object is the **transitional hosting packet**.

Its job is narrower than the continuity packet and more operational than the cutover witness. It does not justify the scope shift. It does not describe every asset and queue in motion. It simply disciplines the bridge, so temporary hosting stays visibly subordinate to the new constitutional home.

## Pattern pack

### 1. Treat transitional hosting as a declared constitutional bridge, not background convenience

Whenever a function has moved in law or public authority but some runtime substrate still sits with another body, the polity should say so openly.

The packet should therefore be required whenever the predecessor, a parent body, a shared-service centre, or a vendor temporarily hosts any materially consequential part of the successor’s live operation.

A bridge that is not declared is already halfway to becoming hidden government.

### 2. Name the principal holder and the host of record separately

The packet should always identify:

- the **principal public holder** that now lawfully owns the function,
- the **temporary host** that still provides bounded operational substrate,
- and any additional sub-hosts or suppliers that the bridge depends on.

This sounds simple, but it is the core anti-fog move. The host may run the shell; it should not become the silent sovereign merely because it still runs the shell.

### 3. Enumerate the host-only powers and prohibit host spillover by implication

A host should possess only the powers needed to keep the bridge running. Those powers should be enumerated explicitly.

At minimum, the packet should say whether the host may:

- receive or forward submissions,
- maintain system availability,
- manage credentials,
- process payments,
- administer records storage,
- answer routine service queries,
- apply emergency fixes,
- or act only on written instruction from the principal holder.

Everything outside that list should be treated as remaining with, or requiring fresh clearance from, the new holder.

### 4. Keep the public route honest during the bridge

If the public still reaches a legacy channel during transitional hosting, the packet should say exactly how that channel behaves.

It should name:

- whether the old front door is only forwarding,
- whether it may still acknowledge receipt,
- what cure rule protects misdirected submissions,
- which notice head is authoritative,
- and when the public should expect the legacy surface to disappear.

No resident, applicant, worker, or supplier should have to infer from branding alone whether they are dealing with a mere relay or a still-live authority.

### 5. Bind hosting to service-floor, budget, and cost rules

A temporary host can silently control the constitution by controlling uptime, staff time, or transaction budgets. The packet should therefore state:

- who pays for the bridge,
- what minimum service floor the host owes,
- what budget or charging rule applies,
- what happens if the host underperforms,
- and whether the host may ration the function by local convenience, cash pressure, or staff scarcity.

Temporary hosting should not become a covert veto over the supposedly transferred function.

### 6. Keep records, logs, and evidence lineage visibly split

During a bridge, evidence often remains in the host’s systems even though the principal holder now owns the function. The packet should therefore name:

- which system is the temporary runtime,
- which body is the authoritative records custodian,
- how logs, timestamps, and identifiers are preserved,
- what export or retrieval route the principal holder can use,
- and how review, audit, discovery, or complaint bodies access the relevant trace.

This prevents a common later failure: the successor is legally answerable, but the host still controls the proof.

### 7. Keep command boundaries sharper than operating boundaries

A host may continue operating part of the runtime without continuing to set policy, priority, review posture, or risk appetite. The packet should therefore separate:

- operational hosting,
- incident response,
- content or template control,
- queue prioritisation,
- rule interpretation,
- and release approval.

Where those powers remain mixed, the bridge is constitutionally unsafe even if technically functional.

### 8. Give the bridge one break-glass and one failure-exit path

The packet should say what happens if the host fails, refuses, is compromised, or becomes politically unusable.

At minimum it should name:

- who can declare bridge failure,
- what emergency continuation path exists,
- what minimum export or manual fallback is ready,
- what rollback or constrained-operation lane opens,
- and how the public is told which route still counts.

A bridge without a failure-exit path is not a bridge. It is dependency with better branding.

### 9. Put every hosting bridge on a hard clock

The archive should prefer one visible expiry, review, or re-clearance clock for every transitional-hosting arrangement.

The packet should state:

- the planned end date,
- the review date before that end,
- the conditions for extension,
- and the lane required if the host relationship must continue longer than planned.

Elapsed time should never convert a temporary host into the normal constitutional home by custom.

### 10. Close the bridge with one exit witness

When transitional hosting ends, the polity should not merely stop talking about it. It should produce one compact closure object saying:

- which hosted elements ended,
- which keys, routes, or records were handed over,
- which legacy channels were retired,
- what residual exceptions remain if any,
- and whether the successor is now fully self-hosting or still partly dependent elsewhere.

Otherwise the archive can prove the start of the bridge but not its honest end.

## Guardrails

- Do not let the host relationship remain implicit in procurement, MOU, or helpdesk habit alone.
- Do not let a host control queue priority, templates, review access, or interpretation merely because it still controls the runtime.
- Do not let legacy front doors keep receiving matters without an explicit forwarding and cure rule.
- Do not let the principal holder become answerable for acts it cannot evidence because logs and retrieval remain host-controlled.
- Do not let transition charges, uptime decisions, or staff scarcity become a covert veto over the transferred function.
- Do not extend a hosting bridge by silence, convenience, or backlog alone.

## Failure modes

- **sovereignty by borrowed runtime**: the law moved, but the host still decides in practice because it kept the systems and keys.
- **ghost relay front door**: the old channel looks authoritative and keeps shaping citizen behavior even after it was supposedly downgraded to forwarding only.
- **host veto by uptime or staffing**: temporary service provision becomes a covert power to delay, throttle, or refuse the new holder’s work.
- **evidence captivity**: the principal holder is answerable, but the host still controls the logs, identifiers, or retrieval path needed for review.
- **template capture**: the host’s manuals, forms, or release process quietly become the rulemaking lane for the successor.
- **extension by backlog**: a bridge meant to expire survives because nobody wants the disruption of ending it while work remains in queue.
- **dual-command runtime**: incidents, fixes, priorities, and public notices are governed by mixed signals from host and principal with no explicit hierarchy.

## Practical tests

A transitional-hosting regime is honest when it can answer yes to all of the following:

1. Does every materially consequential bridge produce one explicit hosting packet rather than hiding inside implementation folklore?
2. Does the packet distinguish clearly between the principal holder and the temporary host of record?
3. Are the host’s powers enumerated narrowly enough that silence does not expand them?
4. Is the public route honest about forwarding, cure, notice, and eventual retirement of legacy channels?
5. Are cost, uptime, service-floor, and underperformance rules explicit enough to block host veto by operations?
6. Can the principal holder retrieve the records, logs, and evidence needed for review even while hosting continues elsewhere?
7. Are command boundaries sharper than operating boundaries, so the host does not quietly inherit agenda control or interpretive authority?
8. Is there a break-glass and failure-exit path if the host arrangement degrades or becomes unsafe?
9. Does the bridge have a hard expiry or re-clearance clock rather than an open-ended “temporary” label?
10. Is there one exit witness showing that hosting really ended or openly moved into a newly cleared arrangement?

## Compression rule for the archive

If a polity can say **the function has moved** but must still add **the old body hosts the live runtime for now**, then it should also be able to show one compact packet naming **who now owns the function, what the host may and may not do, how the public route behaves, where evidence lives, how the bridge fails safely, and when the bridge must end**. Otherwise the scope shift remains vulnerable to **sovereignty by borrowed runtime**.
