# 746 — Historical-register rehousing and cross-catalog migration packets for absorbed tombstones: register-home change, stable entry identifiers, alias continuity, and no disappearance-by-replatforming

## One-line thesis

Once the archive can absorb standalone tombstones into grouped historical registers (`745`), it should also keep one compact **historical-register rehousing and cross-catalog migration packet**: one bounded proof object for moving absorbed dead-object entries from one register, catalogue, directory, or memorial platform to another without losing individually addressable identity, alias coverage, correction lineage, or the plain statement that the authority is dead, so the polity does not mistake platform migration for permission to break historical lookup.

## Why this matters

The archive now has a credible tombstone grammar.

It can retire a body, scope lane, service route, or closeout shell without constitutional ghosting (`642`, `740`). It can leave one honest tombstone (`741`), reroute it when successors drift (`742`), correct it when the dead-page story is materially wrong (`743`), steward it over time (`744`), and even absorb it into a broader historical register when grouping is truly better than standalone sprawl (`745`).

What it still lacked was the smallest object for the next ordinary move: **what happens when the grouped historical register itself changes home**.

That gap matters because historical registers rarely remain still. A department redesigns its publishing stack and moves memorial entries to a new platform. A national archive takes over a departmental historical catalogue. A legacy-body directory is merged into a broader cross-government register. A municipal merger creates one shared historical register where several departmental or local memorial lists used to sit. A catalogue changes domain, URL structure, API, or identifier pattern. Or the steward for absorbed dead-page entries moves again because the first successor later disappears, reorganises, or hands memorial maintenance elsewhere.

Without one compact migration packet, these moves create a familiar kind of institutional loss. The grouped register still “exists”, but old URLs stop resolving. Absorbed entries pick up new identifiers with no crosswalk. The new platform keeps only the latest routing facts and drops the correction or stewardship lineage that made the old memorial trustworthy. Search catches the new register name but no longer catches older aliases, acronyms, or case prefixes. One register becomes two, or two become one, and nobody can later prove which new entry is the truthful continuation of which old entry. Replatforming teams may even think they are improving findability while silently cutting the lookup threads that kept dead institutions publicly legible.

The archive therefore needs one compact packet for **historical-register rehousing and cross-catalog migration**. This packet should not freeze every memorial platform forever. But it should force the polity to prove that when a grouped historical register, catalogue, or directory changes home, every absorbed object remains individually findable, the old lookup routes still land somewhere honest, the death statement remains plain, the route history remains reachable, and the move is recorded as migration rather than accidental disappearance. Without that packet, the archive still permits **disappearance by replatforming**.

## Pattern pack

### 1. Require one explicit migration packet before moving absorbed entries from one historical register or catalogue home to another

A grouped memorial surface should not quietly change homes just because a platform is being replaced or because another institution is taking over maintenance.

If a polity wants to move absorbed dead-object entries from one historical register, directory, or catalogue to another, it should open one explicit packet saying:

- which source register or catalogue is being left;
- which target register, catalogue, or platform will receive the entries;
- whether the move is full, partial, phased, or pilot-only;
- which absorbed entries are in scope;
- and which old URLs, identifiers, aliases, APIs, and lookup surfaces must continue to resolve after the move.

Rehousing should be a named act, not an emergent side effect of redesign.

### 2. Distinguish migration from rerouting, absorption, duplication, and deletion

A register-migration packet should classify the move correctly.

At minimum it should distinguish:

- **home change** — the same absorbed entry moves to a new register or platform home;
- **register merge** — several grouped memorial surfaces become one;
- **register split** — one grouped memorial surface is partitioned across several homes;
- **dual-running migration** — old and new grouped surfaces run together during a bounded overlap window;
- **duplicate publication risk** — the same dead object appears in several homes with no clear canonical continuation;
- **mistaken deletion risk** — the proposed move is really lookup breakage rather than honest rehousing.

Without typed classes, platform teams can call almost any disappearance “migration”.

### 3. Preserve one stable object identity across the move, even if the platform issues new local identifiers

The most important historical fact is not the new page template. It is that the same dead object can still be found and distinguished from other dead objects after the move.

The packet should therefore preserve one stable object identity by keeping at least one of the following visible:

- the old identifier carried forward as a permanent alias;
- a new identifier published with an explicit old-to-new crosswalk;
- or a durable resolver that maps both old and new identifiers to the same absorbed entry.

A new catalogue row or platform-specific UUID is not enough if it severs the identity chain.

### 4. Keep old URLs, paths, aliases, and major search names live through exact redirects or lookup fields

Historical migration fails most often through lost paths.

The packet should therefore prove that the move catches:

- legacy standalone tombstone URLs where they still exist;
- old grouped-register entry URLs;
- old domain or subdomain paths where the grouped register used to live;
- major acronyms, former names, case prefixes, and known identifier forms;
- and any attachment or sub-entry paths that users still realistically reach from search results, saved emails, reports, or citations.

Users should not have to know that the memorial platform changed in order to find a dead institution.

### 5. Preserve the canonical death statement and object-specific routing facts inside the new home

A moved memorial entry should still say what the old home said at minimum.

The new surface should preserve, for each absorbed object:

- what ended;
- the effective date and end-state type;
- the successor pattern, including split or no-direct-successor cases;
- the records home;
- the archive home;
- and the bounded legacy-question lane.

Migration is not permission to flatten a rich memorial entry into a thinner but less truthful card.

### 6. Carry forward correction, rerouting, stewardship, and absorption lineage rather than only the latest location

Historical registers are trustworthy partly because they show how the memorial object evolved.

A migration packet should therefore preserve or link to:

- the original tombstone or retirement packet (`741`);
- later rerouting acts (`742`);
- correction records (`743`);
- stewardship-transfer history (`744`);
- and any absorption packet (`745`) that explains why the object was grouped in the first place.

Otherwise the move launders history into one fresh page that looks authoritative only because the earlier chain vanished.

### 7. Make source-home and target-home provenance visible during and after the move

A later researcher should be able to tell not just where the entry is now, but how it got there.

The migration packet should therefore publish:

- the source register or catalogue name;
- the target register or catalogue name;
- the effective migration date;
- the steward that approved the move;
- and whether the old home remains as redirect-only, read-only, archive-only, or fully retired.

A memorial entry that changed homes without provenance becomes hard to audit and easy to rewrite.

### 8. Use bounded dual-running or monitored overlap when the move risks wrong-door traffic

Some migrations are simple. Others involve high legacy traffic, complicated alias maps, or many external links.

Where the risk is material, the packet should allow a short dual-running period with:

- a declared overlap start and end;
- one canonical target identity for each entry;
- monitoring for unresolved old paths, major search misses, and alias failures;
- and a visible exit decision when the old home stops serving as a lookup surface.

Dual-running should be a bounded safety lane, not permanent duplication.

### 9. Forbid the target register from becoming a shadow live service front door or faux record system during migration

A new historical home can easily drift into role confusion, especially when many old domains and entry points are being redirected into it.

The migration packet should therefore keep the target surface visibly historical. It should not:

- accept ordinary new transactions for dead authorities;
- replace the actual records home;
- blur memorial lookup with current service intake;
- or use migration as an excuse to collapse several different legacy-question lanes into one generic helpdesk that cannot route by object.

Rehousing a memorial register should improve continuity, not create one bigger shadow front door.

### 10. Keep a reversal or re-migration lane if the new home proves lossy, unstable, or misleading

Not every target home is honest enough in practice.

The packet should therefore name:

- the trigger for rollback, partial rollback, or re-migration;
- the steward who may declare the new home unfit;
- the evidence threshold for finding the move materially lossy;
- and how old identifiers, redirects, and lineage will be preserved if the entry moves again.

A credible migration packet should assume that platforms can fail without letting lookup identity fail with them.

## Guardrails

- Do not move absorbed historical entries to a new register home without an old-to-new identity crosswalk.
- Do not break old URLs, aliases, or attachment paths and call the result “platform modernisation”.
- Do not flatten object-specific successor, record-home, or archive-home facts into one generic historical-directory template.
- Do not discard rerouting, correction, stewardship, or absorption lineage merely because the target platform prefers cleaner metadata.
- Do not leave several live memorial copies online without one clearly stated canonical lookup continuation.
- Do not let dual-running become permanent duplication with no closure date.
- Do not let a migrated historical register impersonate a live service hub or records-management system.

## Failure modes

- **disappearance by replatforming**: the historical entry supposedly moved, but the old path and common lookup routes no longer land on an individually identifiable continuation.
- **identity break on migration**: the new platform issues fresh identifiers with no reliable old-to-new crosswalk, so citations and saved references go dead.
- **latest-home laundering**: the target register preserves only the newest location and drops the correction, rerouting, or absorption chain that made the object intelligible.
- **duplicate memorial fog**: several homes now contain plausible-looking versions of the same dead object and the public cannot tell which one is canonical.
- **template flattening**: the target register’s common card structure erases object-specific successor, record, archive, or question-routing facts.
- **migration without exit**: the old home and new home both remain half-live indefinitely, so stewardship, correction authority, and lookup responsibility are never settled.

## Practical tests

A historical-register rehousing and cross-catalog migration packet is honest when it can answer yes to all of the following:

1. Is the move named explicitly as migration, merge, split, dual-running, or mistaken deletion risk?
2. Does every absorbed object keep one stable identity across the move, even if the platform creates new local identifiers?
3. Do old URLs, aliases, and major search names still resolve to the exact entry or an exact crosswalk?
4. Does the new home preserve the plain death statement, effective date, successor pattern, records home, archive home, and bounded legacy-question lane?
5. Are rerouting, correction, stewardship, and absorption histories preserved or linked rather than flattened away?
6. Is the provenance of source home, target home, migration date, and steward visibly recorded?
7. Where risk is material, is there a bounded monitored overlap rather than a blind cutover?
8. Does the target register stay visibly historical rather than drifting into live intake or faux records custody?
9. Is there one canonical continuation for each moved entry, avoiding duplicate memorial fog?
10. Is there a credible rollback or re-migration lane if the new home proves lossy or misleading?

## Compression rule for the archive

If a polity can absorb standalone tombstones into a broader historical register (`745`), it should also be able to show one compact packet for **when absorbed dead-object entries later move between register homes, domains, platforms, or catalogue stewards, how stable identity and old lookup routes survive the move, how correction and stewardship lineage remains reachable, how overlap is bounded and monitored where needed, and how the new home stays historical instead of becoming a shadow live front door**. Otherwise it still permits **disappearance by replatforming**.
