# 885 — Applied transition-receipt case packet for ArriveCAN: emergency border app, Advance Declaration conversion, procurement failures, and no modernization by survivorship

## One-line thesis

ArriveCAN should be classified as an emergency digital border application converted into an optional Advance CBSA Declaration platform with serious management, procurement, testing, cost, and record failures in its emergency phase; the successor modernization use does not erase the emergency-period transition receipt, and there is no border modernization by survivorship.

## Why this matters

ArriveCAN is a near-perfect transition-receipt stress case because the system did not simply disappear. It began as an emergency public-health border app used to collect traveller contact and health information. Mandatory COVID-related health collection ended in October 2022. The platform then survived as an optional customs and immigration declaration channel through Advance CBSA Declaration and became part of a broader traveller-modernization path.

That mixed ending is exactly where governance can become slippery. One narrative says the emergency app was necessary and later became useful border infrastructure. Another says the procurement, records, costs, contracting, version control, and testing record were badly governed. Both can be true. The archive should not let the later usefulness of a surviving platform cure the earlier lack of management discipline; nor should it pretend that a flawed emergency build proves every successor function must be abandoned.

The honest question is: what transition receipt separates emergency authority, public-health data collection, customs declaration modernization, procurement repair, data / privacy repurposing, testing failures, user harms, and successor benefit claims?

## Pattern pack

### 1. Trigger and dispatcher table

| Field | Finding |
| --- | --- |
| trigger | emergency border-entry application built and changed during the COVID-19 pandemic, later converted to optional border declaration platform |
| boundary mismatch | public-health collection, quarantine enforcement support, customs / immigration declaration, suppliers, task authorizations, cloud services, testing versions, privacy impact, and border modernization claims diverged |
| first-form question | whether the app should be treated as emergency health measure, border-service platform, procurement failure, data-governance incident, or modernization success |
| lower-form test | ordinary app-decommission notice is too thin because the system held personal information, shaped border compliance, and left procurement / records failures |
| heavier-form test | permanent border-law authority is too thick; the current Advance Declaration function remains an optional pre-arrival declaration route subject to ordinary border officer processing |
| form verdict | emergency digital border-service waist converted into optional traveller-modernization platform, with unresolved transition-receipt duties |

### 2. Legal and operational boundary

| Component | Boundary rule |
| --- | --- |
| emergency health collection | must be closed by legal terminal event, data retention / deletion record, and affected-user / defect tail |
| Advance CBSA Declaration | must be reauthorized as ordinary border-processing convenience, not as leftover emergency compliance infrastructure |
| border officer role | remains the live public authority; app submission cannot replace final officer processing and declaration correction |
| procurement | must be judged on emergency-period competition, documentation, task authorization, invoice, subcontract, and conflict controls |
| testing / releases | must preserve version, test, defect, and wrongly instructed-user records |
| cost and benefit | successor speed or convenience benefits must not be used to blur emergency build costs or invoice weakness |
| privacy | emergency public-health collection and ordinary customs / immigration declaration must remain separate data purposes |

### 3. Evidence-grade table

| Evidence | Governance meaning |
| --- | --- |
| launch and mandatory-use period | emergency public authority and traveller compliance channel existed, not merely optional convenience software |
| October 2022 change | COVID health-information collection stopped, but the app platform survived |
| current Advance Declaration pages | users can submit customs and immigration declaration information before arrival, then review / edit at kiosks or eGates and proceed to an officer |
| privacy impact summary | CBSA describes Advance Declaration and saved traveller profiles as current ArriveCAN actions and Traveller Modernization as future context |
| Auditor General report | management, contracting, documentation, cost, and version-testing failures create a transition receipt problem |

### 5. Transition-receipt docket

This case activates all transition-receipt tests:

1. **Terminal event and status** — show which emergency duties ended in October 2022 and what remained.
2. **Successor function map** — separate public-health collection from Advance Declaration and Traveller Modernization.
3. **Affected-user and remedy tail** — identify wrongly instructed, excluded, delayed, fined, quarantined, or otherwise affected users.
4. **Record preservation** — retain version, testing, invoice, contract, task-authorization, decision, and defect records.
5. **Data closeout** — prove separation of emergency health data from ordinary customs / immigration declarations and saved profiles.
6. **Procurement and contract closeout** — test supplier influence, non-competitive awards, amendments, invoices, qualifications, and subcontract visibility.
7. **Incident and defect ledger** — preserve release and testing failures, including quarantine instruction errors.
8. **Cost / benefit separation** — do not launder emergency-period costs through current border-speed claims.
9. **Residual dependency review** — test continuing cloud, vendor, support, and internal capacity dependencies.
10. **Relaunch / expansion gate** — require ordinary-law, privacy, testing, procurement, and public-benefit proof before expanding the surviving platform.

### 6. Opposition and rival readings

**Rival 1: emergency urgency justified flexible procurement and rapid iteration.** The archive accepts urgency as a mitigating context. It rejects urgency as a record-destruction licence. Emergency flexibility increases the need for after-action documentation.

**Rival 2: the platform still provides value through Advance Declaration.** The archive accepts the possibility of value. It rejects modernization-by-survivorship: current utility does not repair poor emergency management, weak cost attribution, or missing testing records.

**Rival 3: no COVID health data is collected now, so the issue is closed.** The archive rejects closure by function change. The receipt must show data-purpose separation, deletion / retention treatment, affected-user tail, and procurement / records repair.

**Rival 4: the app was only a delivery channel; border officers remained the authority.** The archive accepts that final border authority remained with officials, but the app still shaped compliance, information flow, queueing, quarantine instruction, and traveller expectations.

### 7. Capture and theater channels

- **emergency theater**: urgency becomes a standing excuse for missing records after the emergency ends.
- **modernization laundering**: surviving Advance Declaration benefits blur emergency-period management failures.
- **platform survivorship**: the system is treated as validated because it was not fully retired.
- **cost fog**: weak invoices and cost allocation prevent final public account.
- **supplier opacity**: prime, subcontractor, resource, and task-authorization roles become hard to trace.
- **release-log evaporation**: rapid versions hide testing failures and user-harm signals.
- **data-purpose drift**: public-health data collection, saved profiles, and customs / immigration declarations blur.
- **officer-boundary theater**: final officer authority is used to minimize app-created compliance harms.

### 8. Repair surfaces

The packet should remain open until these are visible or explicitly marked unavailable:

- emergency legal terminal event and ordinary-use authority map;
- health-data retention / deletion / repurposing record;
- Advance Declaration purpose, optionality, and officer-processing boundary;
- release, testing, and defect ledger for emergency versions;
- affected-user remedy and quarantine-error record;
- contract, task authorization, invoice, subcontract, and qualification trace;
- final cost and cost-allocation explanation;
- supplier / cloud residual dependency register;
- procurement-control repair evidence;
- public expansion gate for future Traveller Modernization uses.

### 9. Holding

ArriveCAN should not be filed as either simple scandal or simple modernization. It is an emergency digital border-service waist that converted into an optional ordinary border-processing tool while carrying unresolved transition-receipt issues. The rule is: **no emergency tool by successor convenience, and no modernization by survivorship**.

## Anti-theater tests

This packet fails if officials use “no longer mandatory,” “Advance Declaration is useful,” “recommendations accepted,” or “new procurement controls exist” as substitutes for a complete transition receipt. The receipt must separately prove terminal status, data-purpose closeout, user-harm tail, procurement and contract closeout, version / testing preservation, cost separation, residual dependency, and future expansion gates.
