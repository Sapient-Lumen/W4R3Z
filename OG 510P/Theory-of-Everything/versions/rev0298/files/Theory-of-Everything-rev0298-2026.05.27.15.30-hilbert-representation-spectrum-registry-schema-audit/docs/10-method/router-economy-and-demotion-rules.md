# Router economy and demotion rules

## Purpose

Keep single-home routers from becoming a second kind of archive sprawl.
A router is earned only when it compresses broad continuation surfaces more than it widens canon.

## Admission rule

A new router belongs in canon only if **all** of the following are true:
- it absorbs **at least two already-live subordinate surfaces** that broad, restart, or program mirrors would otherwise need to name separately,
- it shortens **at least two stable / restart / program surfaces** or one default restart tier,
- it expresses **one clearer ordered burden or control route** than the loose bundle it replaces,
- and it can be wired in the same revision through `docs/00-meta/canonical-homes.md`, `docs/00-meta/archive-policy.md`, `docs/00-meta/llm-runbook.md`, `ARCHIVE_INDEX.md`, and lint.

If one of those tests fails, do not mint a new router.
Refine an existing router, keep the change in a subordinate canonical home, or record the issue in a registry / workstream note instead.

## Demotion rule

A router should be demoted when it stops buying real compression.
Demote it back into its parent or subordinate home if any of the following become true:
- it now wraps only one meaningful subordinate surface,
- broad surfaces no longer need it because the parent router already carries the same burden cleanly,
- it preserves names but not routing work,
- or it adds more mirror text than it deletes.

A router that no longer shortens continuation is not a control surface; it is stale indirection.

## One-level-above rule

Broad surfaces should name the **highest router that actually matches the burden in play**.
Do not name both a parent router and its child router in the same broad mirror unless the revision is changing both levels directly.
Do not let sibling routers accumulate as a checklist when one parent route already captures the current burden cleanly.
Treat parent-plus-child co-naming in broad stable summaries as a regrowth smell and wire lint against it when a revision trims that pattern.

## Touching rule

If a revision changes only one subordinate lane, edit that subordinate surface.
Touch the router only if the route itself changed: order, stop rule, lane ownership, or broad continuation economy.
This keeps routers from becoming mini-changelogs.

## Wiring rule

A new router is not complete until the same revision:
- records its canonical home,
- updates the operator policy and runbook,
- refreshes generated restart mirrors if posture changed,
- and adds or updates at least one lint guard against the regrowth it is meant to prevent.

If those wiring steps do not happen, the router is still provisional and should not be treated as a durable broad home.
