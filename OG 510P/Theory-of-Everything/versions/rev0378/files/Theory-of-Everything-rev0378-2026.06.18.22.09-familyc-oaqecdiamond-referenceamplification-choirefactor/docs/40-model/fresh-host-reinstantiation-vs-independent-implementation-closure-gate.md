# Fresh-host-reinstantiation versus independent-implementation-closure gate

Purpose: split the archive's **witness-package progress** one step further.
A candidate should not earn the same witness credit merely because it can **let outsiders reinstantiate the original executable evidential process on a fresh host from a preserved public bundle** and because it can **let outsiders reach the same evidential class through independently implemented code paths that answer to a public semantic specification, conformance clause, and cross-implementation agreement test rather than to one inherited executable lineage**.
Those are related, but they are not the same achievement.

## Compression verdict

Inside the archive's witness package, once a lane has already moved beyond public evidence custody and fresh-host reinstantiation, the current score should now distinguish four nested layers:

1. **public evidence-custody closure** — the decisive evidence bundle or reference object is stably extractable, versioned, fixity-checkable, preservable, citable, and reopenable beyond one privileged repository or operator chain;
2. **fresh-host reinstantiation closure** — outsiders can take that public bundle, identify the exact workflow / software / environment objects it depends on, materialize an executable environment on a fresh host or stack, and rerun or rehydrate the evidential process under declared equivalence rules without privileged manual setup;
3. **independent implementation closure** — outsiders can implement the relevant workflow semantics, protocol, model, or measurement logic through a genuinely separate code lineage, test it against a public conformance or agreement criterion, and still recover the same evidential class without carrying the originating executable bundle itself;
4. **independent evidence-generation closure** — outsiders can regenerate the same evidential class through separately acquired, separately prepared, or blind / holdout evidence routes rather than only by reimplementing the analysis of one inherited evidence source;
5. **local public witness closure** — a lane can say where the physical records live, what stabilizes them, how they are reread, why they remain public evidence, and why that empirical loop is not mainly outsourced.

A lane may earn real credit on layer 2 while still being weak on layer 3.
That is progress.
It is just not yet independent implementation closure, much less independent evidence-generation closure or full witness closure.

## Why this gate exists

Shared witness-gate scaffolding now lives in `docs/40-model/witness-closure-gate-family-frame.md`. This document only names the pair-specific inflation move below.

**a successful public rerun of the original executable bundle being retold as if outsiders therefore already possessed a public, implementation-independent route to the same evidence.**

That inflation can happen in at least seven ways:
- a lane can publish a fully runnable workflow bundle while the decisive semantics still live only in that code path rather than in a public specification;
- a lane can support fresh-host reruns while leaving conformance criteria tacit, so later users can rerun the original stack but cannot tell whether a different implementation is equivalent or merely nearby;
- a lane can preserve one reference implementation whose behavior silently fixes ambiguities that the prose specification never resolved;
- a lane can claim “replication” when all later teams still depend on the originating code, workflow graph, or container lineage rather than a separately implemented one;
- a lane can expose tests, but only tests that overfit one implementation rather than the public semantics of the claimed method;
- a lane can claim interoperability while key options, edge cases, or tolerance rules have never been demonstrated across genuinely independent implementations;
- or a lane can support independent source retrieval while failing to provide an independently verifiable path from source to operative binary or service image.

## The five-step independent-implementation test

### 1. Public semantics, not just one executable lineage

Before awarding independent-implementation credit, the archive should ask whether the method is described in a public semantics-bearing form rather than only as one runnable bundle.
At minimum, a lane should disclose:
- the public specification, semantic contract, or method description that an implementation is supposed to realize,
- which behaviors are normative and which are merely one reference implementation's convenience choices,
- which inputs, outputs, states, and transitions must be preserved across implementations,
- and which ambiguities remain unresolved.

A lane that wins only here earns **fresh-host reinstantiation credit**, not yet independent implementation closure.

### 2. Conformance clause and testable agreement criteria

A lane earns more than reinstantiation credit only when outsiders can tell what counts as a conforming independent implementation.
At minimum, the archive should ask:
- what public conformance clause, assertion list, or equivalent behavioral requirements exist,
- what tests, fixtures, traces, or expected results operationalize that clause,
- which features are mandatory, optional, profiled, or implementation-dependent,
- and whether the agreement criterion names exact matches, tolerance windows, or admissible divergences.

Without that route, apparent independent implementation may still be one executable lineage plus commentary.

### 3. Genuine implementation independence

A lane earns stronger independent-implementation credit only when later implementations are genuinely separate rather than thin wrappers around the originating one.
At minimum, the archive should ask:
- whether the later code lineage is independently authored or merely rebundled,
- whether it can be built and exercised without calling back into the original executable object,
- what shared libraries, generated code, model weights, or hidden services still collapse the supposed independence,
- and whether multiple implementations cover the same declared feature set rather than disjoint subsets.

Without those answers, apparent independence may still be bundle transport in disguise.

### 4. Cross-implementation agreement and dispute handling

A lane earns still stronger independent-implementation credit only when the archive can compare implementations against the same public criterion.
At minimum, the archive should ask:
- whether at least two implementations have been exercised against the same public tests or fixtures,
- whether disagreements are public enough to expose under-specification rather than being normalized away,
- what happens when one implementation passes the reference bundle's tests but fails a broader interoperability or conformance suite,
- and whether public replacement, revision, or narrowing of claims follows from those divergences.

Without that route, apparent independence may still be rhetorical pluralism rather than tested semantic agreement.

### 5. Independent source-to-binary or source-to-service verifiability

A lane earns **independent implementation closure** credit only when later users can connect the public semantics not just to source code, but to the operative object they actually run.
At minimum, it should name:
- the public semantic spec,
- the conformance clause and public tests,
- the genuinely separate implementation lineage,
- the cross-implementation agreement rule,
- and the independently verifiable source-to-binary or source-to-service path for the implementations being compared.

This is still not the same thing as independent evidence-generation closure or full local public witness closure.
A lane may support independent implementation very well while still borrowing the actual physical record carrier, stabilization story, or rereadability semantics from ordinary laboratory witness structure.

## Common failure modes

1. **rerun-to-independence inflation** — fresh-host reruns of the original bundle are retold as if they were already independent implementations.
2. **reference-implementation capture** — one implementation silently fixes the semantics because the public specification is too weak.
3. **conformance silence** — no public clause says what counts as equivalence, tolerance, or coverage.
4. **wrapper independence theater** — later “implementations” still call the original code, weights, service, or hidden build chain.
5. **subset mismatch** — two implementations exist, but they never exercise the same mandatory feature set.
6. **test-suite overfitting** — the public tests certify one code path rather than the claimed method.
7. **source-to-binary gap** — the implementation looks public at source level, but the executable or deployed service cannot be independently verified against that source.

## Compact current readout

- **ACM's current artifact terminology** makes the first burden explicit by distinguishing reproducibility, where an independent group uses the author's own artifacts, from replicability, where an independent group obtains the same result using artifacts it develops independently.
- **The National Academies overview of terminology conflict** makes the naming caution explicit: disciplines disagree about which word attaches to which achievement, but the important split is stable — reuse of the original digital artifacts is weaker than independently created artifacts and broader-context confirmation.
- **NIST conformance-testing guidance** makes the second burden explicit by insisting that conformance requires criteria stated in the specification itself; if the criteria are not specified, there can be no conformance testing.
- **Current IETF implementation-report practice** makes the third and fourth burdens explicit by still treating at least two independent and interoperable implementations as the standard for advancing a protocol specification to Internet Standard.
- **Reproducible Builds practice** makes the fifth burden explicit by treating trustworthy software delivery as an independently verifiable path from source to binary rather than as a repository pointer or trusted release blob.

That does not refute current observer-relative or bridge-theory programs.
It just means they have not yet paid this stronger independent-implementation debt.

## Net rule

Within the archive:
- fresh-host reinstantiation closure earns real witness-package credit;
- but it does **not** yet count as independent implementation closure;
- and independent implementation does **not** yet count as independent evidence-generation closure;
- and neither of those automatically counts as local public witness closure.

Any future completion bid or bridge-family claim that wants stronger witness credit should now say not only how outsiders can rerun the preserved executable bundle on fresh infrastructure, but how a genuinely separate implementation can be derived from public semantics, checked against a public conformance clause, compared across implementations, and verified down to the operative executable or service object; `docs/40-model/independent-implementation-vs-independent-evidence-generation-closure-gate.md` now treats the stronger burden of fresh evidence generation beyond that implementation step.
