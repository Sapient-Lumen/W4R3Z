# Interoperability, open standards, and vendor exit are world contracts, not data plumbing

Recent work adds another missing layer to Concord's long-horizon stewardship and successor-transfer worlds: **it matters whether future stewards inherit a portable, standards-aligned, inspectable system they can reconnect, federate, and exit — or a bespoke stack whose meaning, access paths, and operating rights are trapped inside one vendor or institutional silo**.

- `RS-GR-319` shows that DOE treats enterprise data catalogs, metadata standards, persistent identifiers, standardized retrieval protocols, and API-enabled interoperability as prerequisites for trustworthy enterprise-scale data use.
- `RS-GR-320` shows that current CISA guidance tells operators to prioritize open standards because interoperability lets buyers select products without lock-in.
- `RS-GR-321` shows that a modern repository architecture can become meaningfully more durable through common metadata schemas, controlled vocabularies, persistent identifiers, and synchronized harvesting across institutions.
- `RS-GR-325` shows that resilient federal plans treat backup communications and cross-jurisdictional interoperability as operational design choices rather than as accidental side effects.
- Together, these sources warn that a benchmark can look more successor-safe, more legible, or more durable because it changed **open-standard support, metadata alignment, persistent-identifier use, API / export architecture, or vendor-exit optionality** — not because the underlying Golden-Rule disposition improved.

## Why this matters for Concord

A future-facing benchmark should not report that an institution “respects future stewards” when the world mainly changed its **portability and anti-lock-in architecture**.

There is a real institutional difference between:
1. a world with records but no standard export or interoperable interfaces;
2. a world with nominal export but brittle, lossy, or vendor-specific semantics;
3. a world with portable metadata but weak persistent identification or discovery;
4. a world with open standards, persistent identifiers, interoperable APIs, and plausible exit routes;
5. a world that looks durable only because successors can actually inherit, inspect, and re-home the system.

Those are not data-plumbing details.
They change whether successors inherit data they can use or merely artifacts they can store.

## Minimal implementor handoff

If Concord adds long-horizon record, stewardship, archive, or handoff lanes, publish at least:

1. whether core artifacts use open or bespoke formats and which interfaces are standards-based;
2. whether metadata schemas, controlled vocabularies, and persistent identifiers are portable across institutions;
3. whether export, synchronization, and API paths allow successor institutions to re-home the system without semantic loss;
4. whether a vendor or single operator can practically trap future stewards inside one toolchain or custody path;
5. whether headline results survive one same-behavior comparison where only interoperability / vendor-exit semantics change.

Without that compact contract, future inheritors can mistake portable structure, open standards, or exit rights for the same thing as deeper reciprocity toward successors.
