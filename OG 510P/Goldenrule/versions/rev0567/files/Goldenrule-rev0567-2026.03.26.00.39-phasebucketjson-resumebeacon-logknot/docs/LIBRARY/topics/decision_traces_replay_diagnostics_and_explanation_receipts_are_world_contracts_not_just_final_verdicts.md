# Decision traces, replay diagnostics, and explanation receipts are world contracts, not just final verdicts

Portable evidence, policy snapshots, designated-speaker rules, quorum semantics, and conflict-resolution profiles are still not enough for any successor-facing archive if future inheritors cannot also reconstruct **why a verifier reached its verdict on that occasion, what paths were taken, what failed or was skipped, and which implementation / policy bundle actually produced the answer**.

- `RS-GR-407` shows that RFC 9334 defines an Attestation Result as the output generated by a Verifier after applying appraisal policy to Evidence, Endorsements, and Reference Values, which means a future relying party can inherit a verifier's conclusion without automatically inheriting the reasoning path that produced it.
- `RS-GR-408` shows that the XACML core specification defines rule- and policy-combining algorithms and lets policies / policy sets carry obligations or advice, which means a decision can contain both a verdict and attached follow-on duties that are not visible if the archive keeps only Permit / Deny.
- `RS-GR-409` shows that current OPA evaluation APIs can emit explanation traces with query ids, parent ids, AST nodes, local bindings, and fail / redo events, which means the reasoning path itself can be preserved as a compact replay artifact rather than left to memory.
- `RS-GR-410` shows that current OPA decision logs can retain decision id, queried path, input, result, requester correlation, and bundle metadata, which means a historical verdict can be tied to the exact request and policy bundle that produced it.
- `RS-GR-411` shows that current OPA provenance output can retain verifier version, build commit, build timestamp, build host, and bundle revisions, which means replay conditions include implementation identity and not only the abstract policy text.
- `RS-GR-412` shows that current Cedar authorization responses include determining policies plus error diagnostics and use explicit default-deny / forbid-overrides-permit / skip-on-error semantics, which means the same top-line `Deny` can arise from very different decision routes.
- `RS-GR-413` shows that current Verified Permissions authorization responses return `decision`, `determiningPolicies`, and `errors`, which means a compact production-grade explanation receipt can fit beside the verdict without retaining a bulky full trace every time.
- Together, these sources warn that a benchmark can look more successor-safe because it started shipping **determining-policy diagnostics, trace events, request / decision ids, obligations / advice, or verifier-build provenance** — not because the underlying Golden-Rule disposition improved.

A future benchmark should not treat “we saved the final answer” as the end of the story.

At minimum, it should distinguish between:

1. a world where only the final `Allow` / `Deny` or pass / fail verdict survives;
2. a world where policy snapshots survive, but the archive does not preserve which policies or rules actually matched, were skipped, or overrode other paths;
3. a world where determining policies survive, but verifier build identity, bundle revision, and request / decision correlation are missing;
4. a world where the archive preserves matched policies / rules, default / fallback path, skipped-error branches, and any obligations / advice, but not the exact verifier build or loaded bundle revision;
5. a world where future inheritors can replay the compact explanation receipt — request id, decision id, determining rules, error / skip path, obligations / advice, and verifier / bundle provenance — and see why this verdict happened instead of merely seeing that it happened.

These are different worlds.
They change whether future inheritors can merely observe a conclusion, explain it in a human-auditable way, correlate it to a concrete verifier run, or reproduce the exact branch structure that made one result prevail.

So decision traces, replay diagnostics, and explanation receipts belong in the world contract.

## Minimum contract to publish

Any Golden Rule benchmark that claims durable provenance, successor-safe authenticity, or replayable long-horizon verification should publish at least:

1. a stable request / decision identifier and the exact evidence or input slice that was evaluated;
2. the verifier implementation identity used for the decision: version, build / commit, and loaded bundle or policy revision;
3. the determining rules / policies / statements that actually matched, plus the combining or precedence rule that made them outcome-determining;
4. whether the final outcome came from explicit allow / permit / accept logic, explicit deny / forbid / veto logic, default deny, no-match fallback, or skip-on-error behavior;
5. any skipped, failing, or erroring branches that were visible during evaluation and whether they changed or merely annotated the final outcome;
6. any obligations, advice, warning messages, remediation hints, or attached duties that accompanied the verdict;
7. the retained trace granularity — final verdict only, determining-policy set, fail-only trace, full trace, or debug trace — and any masking / redaction policy applied to it.

Without that compact contract, future inheritors can mistake silent default-deny, hidden skip-on-error, changed verifier builds, or lost remediation obligations for stable Golden-Rule progress.
