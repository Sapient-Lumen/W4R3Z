**what should happen to queued claims between pulls so the backlog stays real instead of becoming a cemetery, a political performance, or a duplicate-work factory?**

So this note is a compression note, not a new doctrinal branch.
Its job is to gather the archive’s waiting-state logic, quarantine logic, pull-cadence logic, and correction-cycle logic into one first-stop **backlog-hygiene** canon [S123][S127][S150][S151][S152][S153][S154].

## Fast rule

**A queued claim should not just “remain on the list.” It should age toward one of five visible outcomes: pull now, keep waiting with a next review date, merge into a batch, move to quarantine, or drop. If a queued claim cannot name its owner, target weak signal, proof path, or reason for continued waiting, it should not keep occupying backlog space as if it were still live.**

## The compact backlog-hygiene map

### 1. Every queued item needs a real waiting state
A queued claim should never sit as a flattering undefined maybe.
It should carry one explicit state such as:
- waiting for next scheduled review
- waiting for a free active slot
- waiting for stronger evidence
- waiting for clearer ownership
- waiting to be batched with similar claims
- quarantined pending boundary review

Undefined backlog is how programmes confuse remembered discussion with governed work.

### 2. Waiting must have a review date, not just a status label
A waiting state is only real if it has a next check date or trigger.
Otherwise “queued” becomes permanent decorative ambiguity.

Each waiting claim should therefore name:
- why it is not active now
- what would make it more admissible
- when it will be reviewed again
- and what could cause early re-review

### 3. Merge duplicates and recurring classes aggressively
If several queued items share one failure pattern, backlog hygiene means turning them into:
- one batch
- one reusable template
- one standard correction package
- or one shared bottleneck-release intervention

Do not preserve five near-identical queue entries just because they arrived from different venues or sponsors.

### 4. Demote stale, overtaken, or weakly evidenced claims
A queue that only admits and never demotes is not disciplined.
It is ceremonial accumulation.

Queued claims should be pushed downward, parked, or dropped when:
- their evidence is stale
- their target weak signal has improved or moved
- a better batch or template now covers them
- a cleaner upstream correction makes them unnecessary
- or the programme can no longer explain why they deserve a place near the front of the queue

### 5. Quarantine or drop claims that cannot survive honest review
Not every non-active item deserves indefinite waiting.
Some claims should be:
- **quarantined** if they still need proof, boundaries, or ownership
- or **dropped** if they are duplicative, obsolete, decorative, or incompatible with the archive’s design rules

A serious programme protects attention not only by capping active work, but by refusing to carry dead or rotten backlog.

## Minimal operating sequence

1. Rank claims with triage.
2. Cap live work with queue discipline.
3. Reopen the queue only on explicit pull clocks or triggers.
4. Between pulls, keep every queued item in a real waiting state with a next review date.
5. Merge duplicates, batch recurring classes, demote stale claims, quarantine weak ones, and drop dead ones.
6. Pull only from a backlog that is still honest enough to deserve being pulled from.

## Bottom line

**Queue discipline caps live work. Pull cadence decides when the queue reopens. Backlog hygiene keeps the waiting queue honest enough to deserve reopening at all. A serious climate state should age every queued claim toward pull, batch, demotion, quarantine, or drop — never toward decorative permanence.**
