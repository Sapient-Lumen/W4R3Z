# 204 — Ideal Solutions: Five Front-Door Questions Before a Claimed Solution Enters the Winning Loop Compact Canon

## Claim

The archive now has a shortest whole answer (`195`), a seriousness threshold (`197`), a transition-mechanism note (`198`), a replacement-proof note (`199`), a basic unit of progress (`200`), a basic unit of scale (`201`), a completion condition (`202`), and a minimum winning loop (`203`).
That is already a strong front door.
But it still left one small practical gap:

**what is the shortest intake note for any claimed climate solution before the archive should let it enter the winning loop at all?**

That gap matters because many proposals arrive half-shaped.
They name a technology, policy, target, funding stream, or pilot and then ask the archive to treat it as if it were already a serious climate pathway.
But the archive’s house view is stricter.
Before a proposal deserves to enter the winning loop, it should be able to answer five front-door questions:
what real control point it moves,
what full replacement package it creates,
how the gain will be proved,
what reusable archetype could carry it beyond one case,
and what dirtier path will actually shrink because of it.
This note is therefore a compression note, not a new doctrinal branch.
Its job is to gather the archive’s intake logic, design kernel, transition-mechanism rule, replacement-proof rule, atomic-unit rule, scaling-unit rule, and winning-loop rule into one smallest proposal interview [S97][S100][S101][S103][S106][S127][S128][S145][S147][S148][S163][S168][S169][S171][S176][S180].

## Fast rule

**Before a claimed climate solution enters the winning loop, ask five questions: what control point does it move, what verified replacement package does it create, how will the gain be proved, what archetype makes it replicable, and what dirty path becomes smaller, harder, or retired because of it? If it cannot answer most of these, treat it as unfinished design rather than serious programme material.**

## The five front-door questions

### 1. What real control point does it move?
A serious proposal should name the place where one decision can shape many later outcomes: procurement, grid connection, code, standard, landlord duty, lease renewal, fleet renewal, tariff, finance term, replacement cycle, public rebuild, or another concentrated lever.
If the proposal only names a desirable technology or aspiration without naming the control point that can spread it, the archive should treat it as under-specified [S103][S106][S163][S169][S180].

### 2. What verified replacement package does it create?
A serious proposal should describe a joined package, not a floating ingredient.
What cleaner service becomes usable enough to carry load?
What finance, installation, grid work, maintenance, standards, user support, or protection steps make the switch actually stick?
If the proposal cannot name the full replacement package, the archive should assume important work has been pushed into the fog of “later implementation” [S100][S101][S103][S106][S128][S145].

### 3. How will the gain be proved in physical outcomes?
A serious proposal should say how the archive will know whether it worked: lower gross emissions, lower methane, lower waste, lower exposure, lower bills for the intended group, lower peak load, lower dirty throughput, or another checkable physical or service outcome.
If the proposal offers only targets, spend, claims, or symbolic adoption counts, the archive should treat the proof rule as unmet [S97][S101][S103][S106][S145].

### 4. What archetype makes it replicable beyond one case?
A serious proposal should point beyond the first successful case.
What standard offer, reference design, procurement form, training pattern, financing path, or operating playbook would let later adopters reuse the design without reopening everything from zero?
If the proposal has no story about how one verified package becomes a repeatable archetype, the archive should treat it as an isolated project rather than a scaling path [S147][S168][S171][S176].

### 5. What dirtier path becomes smaller, harder, or retired because of it?
A serious proposal should name the inferior path that loses ground: a leaky system repaired, a fossil asset retired, a new lock-in denied, a dirty default displaced, a harmful practice constrained, or a fallback made visibly subordinate.
If the proposal cannot say what actually shrinks, it is usually describing clean addition beside continued dirty normality rather than real transition [S101][S145][S148][S180].

## Why this compression helps

### It turns the archive into a better first interview
Instead of asking only whether a proposal sounds promising, the archive can now ask whether the proposal is formed enough to enter the serious design lane at all.

### It prevents premature promotion
This note keeps the archive from promoting targets, pilots, funding announcements, or technology names before they are attached to a real package, a proof rule, and a retirement story.

### It gives teams a better next move
When a proposal fails one of the five questions, the next task becomes clearer: specify the control point, finish the package, define the proof ledger, standardize the archetype, or name the dirty path that should lose ground.

## Preferred use

Open this note first when the live question is any of the following:
