# 154 — Ideal Solutions: Whole-System Pull-Cadence Map — How to Refresh the Queue and Admit the Next Correction (Compact Canon)

## Claim

A serious climate programme now has joined notes for:
- routine attention allocation (`151`)
- triage across simultaneous weak signals (`152`)
- and queue discipline / work-in-progress limits (`153`)

That is enough to decide **what matters**, **what ranks higher**, and **how much active correction work can truthfully be carried at once**.
What the archive still lacked was the shortest joined note for the next operating question:

**when should the programme reopen the queue, refresh rankings, pull the next correction into active work, or leave the queue alone?**

Without that rule, the programme oscillates between two bad states:
- constant re-ranking that destroys throughput and verification discipline
- stale backlog ritual where nothing is rechecked until failure is already visible

So this note is a compression note, not a new doctrinal branch.
Its job is to gather the archive’s clocks rule, weak-signal rule, tripwire rule, attention rule, triage rule, and queue-discipline rule into one first-stop **pull-cadence** canon [S102][S103][S123][S124][S138][S150][S151][S152][S153].

## Fast rule

**Do not reopen the whole correction queue continuously. Pull new work only on a small set of explicit clocks and triggers: when a protected slot frees, when a weak signal worsens past a triage threshold, when a queued item’s evidence materially improves, or when a fixed review cadence arrives. Everything else waits visibly instead of churning the queue by noise, pressure, or novelty.**

## The compact pull-cadence map

### 1. Protect a small set of legitimate pull triggers
New correction work should enter active review only through a few explicit gates:
- a live correction slot becomes free
- a weak signal crosses a triage threshold or tripwire
- the evidence quality for a queued item materially improves
- a fixed scheduled review point arrives
- or a stop-harm emergency temporarily opens a protected emergency lane

Do not let media cycles, anecdote spikes, VIP discomfort, or generic calls to “move faster” function as stealth pull triggers.

### 2. Separate emergency pull from routine pull
Run two visibly different lanes:
- **emergency pull** for stop-harm, continuity, or integrity threats that cannot wait
- **routine pull** for ranked backlog movement when ordinary capacity frees or planned review clocks arrive

Do not let routine work crowd out the emergency lane.
Do not let emergency rhetoric become a back door for ordinary queue jumping.

### 3. Re-rank on a cadence, not continuously
Use fixed queue-review clocks rather than permanent real-time churn:
- immediate review when a real tripwire fires
- short-cycle review for active corrections and emergency items
- medium-cycle review for queued items with plausible next-entry potential
- slower-cycle review for parked, batched, or quarantine items

The purpose is not administrative tidiness.
It is to protect throughput, preserve verification windows, and keep the programme from spending more attention on re-ranking than on governed correction.

### 4. Admit only corrections that can actually be carried now
A queued item should move into live work only when the programme can name:
- the slot it is entering
- the owner who will carry it
- the target weak signal it is supposed to improve
- the verification path that will tell whether it worked
- and the displaced work, if admission requires pushing something else back

If those are not yet clear, the honest state is **waiting**, not pseudo-admission.

### 5. Age, refresh, batch, or demote the queue visibly
Queued work should not sit as a timeless honorable mention.
Each queued item needs one of four visible states at review:
- **pull now**
- **keep waiting with next review date**
- **batch with similar items into one reusable correction package**
- **demote or quarantine because evidence is stale, weak, or overtaken**

A queue that never demotes or batches is not disciplined.
It is just an accumulation ritual.

## Minimal operating sequence

1. Watch the scoreboard and weak signals.
2. Rank claims with triage.
3. Protect the live-work cap.
4. Reopen the queue only on explicit clocks or triggers.
5. Pull the next correction only if a real slot, owner, target signal, and verification path exist.
6. Leave the rest visibly queued, batched, or quarantined until the next legitimate review point.

## Bottom line

The programme should not pretend the correction queue is always in motion.
It should reopen the queue on explicit clocks and triggers, pull only what can be truthfully carried now, and let everything else wait visibly rather than thrash active work or let backlog decisions fossilize in silence.
