## What this is for

Use `639` when a later packet preserves or reenacts a **visible wrapper reader-state layer** around same-route detached derivatives:
- Reader View or Show Reader posture,
- Chrome Reading mode side-panel posture,
- Edge Immersive Reader posture,
- simplified article extraction or clutter-reduced reading shells,
- stripped navigation/toolbar/sidebar context,
- reader-specific themes, fonts, spacing, or line-focus posture,
- or similar later packet reader-state signals.

Those reader surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added reader posture**, not automatic proof of:
- source-native layout,
- source-native omission,
- source-native emphasis,
- office-curated simplification,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded reader-state bridge.
Google Chrome Help says Reading mode opens text in a side panel, reduces distractions from images and videos, and lets the reader change font, font size, color theme, and spacing.
Mozilla Support says Firefox Reader View strips away buttons, ads, background images, and videos into a clean reading experience.
Microsoft Support says Edge Immersive Reader simplifies the current page, hides distracting pop-ups and buttons, and offers text preferences plus line focus.
Apple Support says Safari Reader shows just the relevant text and images, can hide reader mode again, and lets the reader change theme, font, and zoom; on iPad, longer pages can also expose a summary and table of contents in Reader.
That is enough for one bounded firewall here.
(xref: `google_chrome_help_reading_mode_page`; xref: `firefox_reader_view_help_page`; xref: `microsoft_support_edge_immersive_reader_page`; xref: `apple_support_safari_reader_mac_page`; xref: `apple_support_ipad_safari_reader_page`)

`639` exists so maintainers can say:
**this packet preserved a later reader-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the reader layer itself does not silently prove source-native layout, source-native omission, office-curated simplification, or the governing member.**

## Why this is distinct

`440` asks whether the current official page remains trustworthy when consumed directly through reader mode or simplified extraction.

`489` asks whether read-aloud or page-audio narration of the already-open page changes authority or meaning.

`595` asks whether a detached text derivative carries — or disproves — surrounding authenticity-cue posture.

`610` asks whether a later packet preserved **styling posture** — themes, color coding, or visual tone.

`613` asks whether a later packet preserved **view-state posture** — open page, zoom, fit, or initial viewport.

`638` asks whether a later packet preserved **translation posture** — translated renderings, show-original state, or language-pair badges.

`639` asks a different question:
**did a later packet add or preserve a visible reader-state layer — Reader View, Reading mode, Show Reader, Immersive Reader, stripped chrome, simplified article extraction, or line-focus posture — and did later readers start overreading that layer as if it proved source-native layout, source-native omission, office-curated simplification, or the packet's governing member?**

If the real problem is whether the live official page survives reader extraction safely, use `440`.
If the real problem is read-aloud or page-audio narration, use `489`.
If the real problem is just a detached text derivative, use `595`.
If the real problem is styling alone, use `610`.
If the real problem is opening viewport alone, use `613`.
If the real problem is translation posture, use `638`.
Use `639` only when the missing distinction is **wrapper reader-state posture itself**.

## Decision test

Use `639` when all three conditions hold:

1. later evidence preserves or reenacts a **visible reader-state layer** around same-route detached derivatives — for example Reader View, Reading mode, Immersive Reader, Show Reader, simplified article extraction, stripped surrounding chrome, or line-focus posture;
2. that layer is **later wrapper-added reader state**, not proof that the underlying source route itself officially removed the missing chrome, officially simplified the page, officially omitted the hidden material, or officially made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native layout, source-native omission, source-native emphasis, office-curated simplification, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a route-level reader-mode problem, a page-audio problem, a text-derivative problem, a styling problem, a view-state problem, or a translation problem with some visible reader posture around it, keep reader-mode authority in `440`, keep page audio in `489`, keep detached text in `595`, keep styling in `610`, keep view state in `613`, keep translation in `638`, and add one bounded `639` reader-state note only if the visible reader layer itself changed the reading.

## Keep route-level reader mode, view state, styling, translation, and reader state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **route-level reader-mode authority boundary** — when the already-open official page itself is being consumed through reader mode and the archive needs the route-level extraction boundary (`440`);
5. **wrapper-added page-audio posture** — Read Aloud / Listen to page / page narration (`489`);
6. **wrapper-added styling state** — reader themes, font changes, spacing changes, or similar tone/appearance posture (`610`);
7. **wrapper-added view state** — open-page/open-slide choice, zoom, fit, or initial viewport (`613`);
8. **wrapper-added translation state** — translated reader output, show-original posture, or language-pair state (`638`);
9. **wrapper-added reader state** — Reader View, Reading mode, Show Reader, Immersive Reader, stripped chrome, simplified article extraction, summary/TOC in reader, or line-focus posture (`639`);
10. **carrier wrapper** — slide deck, PDF memo, doc shell, browser shell, saved page, email thread, or other transport context (`437`, `490`, `600`);
11. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible reader-state layer as if it proved the underlying source route itself natively lacked the stripped controls, sidebars, notices, or surrounding context; or
- letting a later simplified-reading wrapper become evidence that the packet itself is governance-bearing, office-curated, or the governing member.

`639` exists so the archive can keep that later visible reader layer **truthful but non-governing**.

## Minimal wrapper-reader-state note grammar

When wrapper reader state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_reader_kind=<reader_view|reading_mode_side_panel|immersive_reader|show_reader|simplified_article_view|mixed|unknown>; extraction_scope=<whole_page|main_content_only|article_only|selection_opened_in_reader|mixed|unknown>; stripped_context=<nav_only|sidebar_only|chrome_and_controls|mixed|unknown>; source_layout_proved=<forbid>; source_omission_proved=<forbid>; source_emphasis_proved=<forbid>; office_curated_simplification_proved=<forbid>; governing_member_from_reader_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|review_shell|slide_deck|pdf_memo|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_639_when=<reader_state_changed_reading>; promote_wrapper_reader_state=<no>; basis=<why the later reader layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried Reader View / Reading mode / stripped-chrome posture” without minting a new detached-derivative member or silently rewriting source layout, source omission, office simplification, or packet governance.

## Typical uses

1. **Stripped-chrome overread**
   A later packet shows the same detached derivative through Reader View and later readers start retelling the stripped presentation as if the original page itself had no sidebars, banners, navigation, or surrounding qualifiers.
2. **Reader-theme overread**
   A later packet preserves dark-theme or high-contrast reader settings and later readers start treating that simplified reader styling as if it were the source route's own authored emphasis or design choice.
3. **Immersive Reader line-focus overread**
   A later packet shows Edge Immersive Reader with line focus and later readers start retelling that narrowed presentation as if the source itself highlighted or isolated those lines.
4. **Reading-mode side-panel overread**
   A later packet shows Chrome Reading mode in a side panel and later readers start treating that extracted panel as if it were the office's own reviewed shortform or main published layout.
5. **Reader summary / TOC overread**
   A later packet shows Safari Reader on a long page with a summary or table of contents and later readers start treating that reader-produced structure as if it were the office's native page structure or official abstract.

## When not to use this

Do **not** use `639` when:
- the decisive issue is still whether the live official page survives reader extraction safely (`440`),
- the decisive issue is still read-aloud or page-audio narration (`489`),
- the decisive issue is still detached text carriage (`595`),
- the decisive issue is still styling/tone alone (`610`),
- the decisive issue is still opening viewport posture (`613`),
- the decisive issue is still translation posture (`638`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible reader layer leaves an ordinary route-level reader-mode, page-audio, text-derivative, styling, viewport, or translation problem, use the narrower doc and omit `639`.
If deleting it would erase **why a later Reader View / Reading mode / Immersive Reader layer changed the way the packet was being read or retold**, `639` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried Reader View, Reading mode, Show Reader, Immersive Reader, simplified article extraction, stripped chrome, or line-focus posture.
Tighten `440`, `489`, `595`, `600`, `610`, `613`, `638`, or `639` first.
Only add another numbered doc when repeated wrapper-reader-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-reader-state note under `639`.
