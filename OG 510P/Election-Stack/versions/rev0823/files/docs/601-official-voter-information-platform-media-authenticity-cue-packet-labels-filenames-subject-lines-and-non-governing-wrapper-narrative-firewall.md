# 601 — Official voter-information platform media authenticity-cue packet labels, filenames, subject lines, and non-governing wrapper-narrative firewall

**Track:** Shared

This document defines a bounded control for **later packets or carrier wrappers that add their own short labels around same-route detached derivatives without proving that those labels came from the official media route itself**:
slide titles,
PDF headings,
attachment filenames,
email subject lines,
chat-thread titles,
issue-ticket summaries,
callout captions,
or similar wrapper-added labels that sit around preserved text/audio/still/metadata/locator derivatives.

It does not create a new authenticity cue family.
It does not create a new detached-derivative member.
It adds one narrow rule:
**when later evidence adds its own packet label around same-route detached derivatives, the archive should preserve that wrapper-label fact honestly and should not quietly treat the packet label as if it were copied source metadata, route-level authenticity posture, or the governing detached-derivative member by itself.**

## Why this exists (bounded)

The archive already distinguishes source-derived metadata extracts (`598`) from mixed detached-derivative packets (`600`).
A smaller but still important seam remains:
**later packets often add their own descriptive label around preserved same-route derivatives, and later readers start treating that packet label as if it were copied from the official media route or as if it governed the packet's detached-derivative classification by itself.**

Current primary-source guidance is specific enough to justify one compact bridge here.
YouTube's current help says titles, descriptions, and chapter labels belong to the media route and can be edited there.
Its share help and Microsoft's current sharing guidance show that links or files can then travel outward into later sharing contexts.
Apple's current Safari guidance and Chrome's current offline-reading guidance show that later saved-page or archived-page carriers are real preserved forms around a page.
That is enough to support one bounded maintainer rule:
**a later packet label is not automatically a copied source label just because it surrounds genuine same-route derivatives.**
(xref: `youtube_edit_video_settings_help_page`; xref: `youtube_video_chapters_help_page`; xref: `youtube_share_videos_channels_help_page`; xref: `microsoft_share_video_audio_m365_help_page`; xref: `apple_support_safari_save_webpage_mac_page`; xref: `google_chrome_read_pages_later_offline_computer_page`)

`601` exists so the archive can say, compactly and honestly, that a slide title like “official clip lacks badge,” a PDF filename like `clerk-video-proof.pdf`, or an email subject like “county video confirms hours” may be **later wrapper narrative** rather than copied source metadata — even when the packet also contains truthful same-route derivatives.

## This is not the same thing as `598`, `600`, `591`, `514`, `437`, or `490`

`598` asks whether later evidence preserved metadata-like labels from the official media route itself — copied title text, description text, chapter labels, playlist labels, or similar source-derived metadata.

`600` asks how to route a mixed same-route packet when several detached derivatives coexist and no single `595–599` member clearly dominates.

`591` asks whether later materials fused observations from different routes, times, viewer conditions, or interaction states into one faux simultaneous posture.

`514` asks whether live-route metadata wrappers around the current media object became a public-answer authority problem in the first place.

`437` and `490` ask whether print/save/offline/web-archive carriers changed the authority or portability posture of the already-open route.

`601` asks a different question:
**did a later packet add its own descriptive label around same-route detached derivatives, and did later readers start overreading that wrapper label as if it were copied source metadata, a route-level authenticity fact, or the governing detached-derivative member?**

If the real problem is that the official media route's own title, description, chapter list, or playlist label was copied outward, use `598`.
If the real problem is that the packet is mixed and no detached-derivative member dominates, use `600`.
If the real problem is later composite assembly across states, use `591`.
If the real problem is print/save/offline/web-archive authority or portability, use `437` or `490`.
If the real problem is later wrapper-summary prose such as forwarding comments, share messages, speaker notes, or memo-body synopsis text, use `602`.
Use `601` only when the decisive ambiguity is **wrapper-added packet narrative being mistaken for source metadata or for detached-derivative governance.**

## Default rule: classify the surviving derivative first; treat later packet labels as descriptive unless provenance proves otherwise

By default, later notes SHOULD still cite the current controlling head under `530`, or the fallback anchor if the chain is headless.
A `601` note exists only to explain one bounded labeling mistake around that head.

Use this triage order:
1. if the decisive issue is still a source-derived metadata extract, use `598`;
2. if the decisive issue is still a locator-only pointer extract, use `599`;
3. if the decisive issue is still a mixed detached-derivative packet with no dominant member, use `600`;
4. if the decisive issue is still cross-state composite assembly, use `591`;
5. if the decisive issue is still saved-page / print / offline portability or authority boundary, use `437` or `490`;
6. use `601` only when the decisive issue is that **a later wrapper-added packet label changed how the packet sounded or got misclassified.**

That means `601` is not a new citation lane.
It is a compact bridge for one bounded sentence saying that the packet had a later wrapper label and that the label should not be silently upgraded into copied source metadata or governing derivative proof.

## Keep source-derived labels and wrapper-added labels separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived metadata** — labels copied from the official route itself (`598`);
5. **wrapper-added packet label** — filename, subject line, slide title, memo heading, ticket summary, callout caption, or similar short later-added narrative (`601`);
6. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, memo-body synopsis text, or similar longer later packet narrative (`602`);
7. **carrier wrapper** — slide deck, PDF memo, chat export, saved page, web archive, issue ticket, or other transport context (`437`, `490`, `600`);
8. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two opposite mistakes:
- treating a wrapper-added packet label as if it were copied source metadata from the official route, or
- letting the packet label become the governing member instead of first classifying the surviving detached derivative.

`601` exists so the archive can keep that wrapper label **truthful but non-governing**.

## Minimal wrapper-label note grammar

When wrapper-label overread itself matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; packet_label_kind=<filename|email_subject|slide_title|pdf_heading|chat_thread_title|ticket_summary|attachment_label|callout_caption|mixed|unknown>; packet_label_origin=<later_wrapper_added|copied_from_source|mixed|unknown>; treat_packet_label_as_source_metadata=<forbid>; treat_packet_label_as_governing_member=<forbid>; carrier_wrapper=<slide_deck|pdf_memo|chat_export|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_601_when=<wrapper_label_changed_routing_or_sounded_like_source_metadata>; promote_packet_label=<no>; basis=<why the later label needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this packet title/filename/subject line was later wrapper narrative” without minting a new detached-derivative member or silently rewriting copied-source provenance.

## Typical uses

1. **Slide-title overread**
   A deck contains a frame grab, a transcript excerpt, and a watch URL, but later readers start treating the slide title itself as if it were the official media title or the decisive detached derivative.
2. **PDF filename overread**
   A memo preserves a still image and copied link from the same route, but the PDF's filename starts sounding like a source-derived metadata fact.
3. **Email subject overread**
   A forwarded packet preserves one same-route derivative, but later readers cite the email subject line as if it came from the original official route.
4. **Saved-page attachment-label overread**
   A saved-page or archive file has a local filename or attachment label that later readers mistake for source metadata instead of later storage context.
5. **Mixed packet with argumentative heading**
   A packet really belongs under `600`, but a strong wrapper heading starts pushing reviewers toward `598` or toward inventing a new carrier-specific sibling.

## When not to use this

Do **not** use `601` when:
- the decisive label was actually copied from the official route itself (`598`),
- the decisive issue is later wrapper-summary prose rather than a short label (`602`),
- the decisive problem is still locator-only or another specific detached derivative (`595–599`),
- the decisive problem is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive problem is still print/save/offline/web-archive authority or portability (`437`, `490`),
- or the decisive problem is still cross-state composite assembly (`591`).

If deleting the wrapper-label fact leaves an ordinary metadata-derivative, locator-derivative, mixed-packet, saved-page, or composite-assembly claim, use the narrower doc and omit `601`.
If deleting it would erase **why a later packet title/filename/subject line changed the way the packet was being routed or retold**, `601` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet used a strong filename, subject line, slide title, memo heading, or other wrapper-added label around same-route detached derivatives.
Tighten `598`, `600`, `591`, `437`, `490`, or `601` first.
Only add another numbered doc when repeated packet-label mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-label note under `601`.
