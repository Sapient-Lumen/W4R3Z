## What this is for

Use `646` when a later packet preserves or reenacts a **visible wrapper player-state layer** around same-route detached derivatives:
- fullscreen playback,
- theater mode or another widened player layout,
- miniplayer or floating reduced-context playback,
- picture-in-picture or a similarly detached small-player state,
- popout playback in another tab/window,
- or similar later packet player-state foregrounding.

Those player-state surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added player posture**, not automatic proof of:
- source-native framing or source-native omission of surrounding route context,
- office-preferred presentation or review posture,
- an officially republished immersive or detached edition,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded player-state bridge.
YouTube Help says viewers can switch a video to full screen, can change the player size, and on supported mobile surfaces can continue playback in picture-in-picture after exiting the app.
Vimeo Help says videos play inline on mobile by default, can enter fullscreen from the player, and can be forced to open fullscreen on mobile from embed parameters.
Microsoft Support says embedded video or audio can be opened in a new browser tab with the Popout button for a more immersive full-screen experience, and that the player supports entering or exiting full screen from keyboard controls.
That is enough for one bounded firewall here.
(xref: `youtube_watch_videos_full_screen_mode_help_page`; xref: `youtube_change_video_player_size_help_page`; xref: `youtube_picture_in_picture_android_help_page`; xref: `vimeo_inline_playback_mobile_help_page`; xref: `microsoft_video_player_playback_experience_help_page`)

`646` exists so maintainers can say:
**this packet preserved a later fullscreen / theater-mode / miniplayer / picture-in-picture / popout posture around same-route detached derivatives, and that posture mattered for how later readers interpreted the packet, but the player-state layer itself does not silently prove source-native framing, source-native omission of surrounding route context, office-preferred presentation, an officially republished immersive edition, or the governing member.**

## Why this is distinct

`502` asks whether detached playback modes such as picture-in-picture, popout, or background play became the voter-facing authority-boundary problem in the first place.

`504` asks whether fullscreen, theater mode, or immersive presentation itself displaced the surrounding official answer lane as the operative public surface.

`546` asks whether the same current media object preserved a **player-view-state alias** — fullscreen, theater mode, miniplayer, picture-in-picture, popout, or similar reduced-context container — while the same object still controlled.

`593` asks whether the same current media object entered a reduced-context player state and surrounding authenticity-adjacent cues fell out of view, creating an occlusion / non-absence-inference problem.

`611` asks whether a later packet preserved **timing / motion wrapper posture** such as autoplay, animation build order, or delayed reveals around a derivative carrier.

`639` asks whether a later packet preserved **reader-mode simplification posture** rather than player-container posture.

`642` asks whether a later packet preserved **rendition / fidelity posture** such as `Auto`, `Data saver`, visible resolution picks, or quality-menu state.

`646` asks a different question:
**did a later packet add or preserve a visible player-state layer — fullscreen, theater mode, miniplayer, picture-in-picture, popout, or similar reduced-context playback posture — and did later readers start overreading that layer as if it proved source-native framing, source-native omission of surrounding route context, office-preferred presentation, an officially republished immersive edition, or the packet's governing member?**

If the real problem is authority-boundary displacement, use `502` or `504`.
If the real problem is same-object player-view-state classification while the current head still controls, use `546`.
If the real problem is cue hiddenness caused by reduced-context viewing, use `593`.
If the real problem is wrapper timing, reader-state simplification, or rendition posture, use `611`, `639`, or `642`.
Use `646` only when the missing distinction is **wrapper player-state posture itself** around a later detached derivative packet.

## Decision test

Use `646` when all three conditions hold:

1. later evidence preserves or reenacts a **visible player-state layer** around same-route detached derivatives — for example fullscreen playback, theater mode, miniplayer, picture-in-picture, popout, or another reduced-context player posture;
2. that layer is **later wrapper-added player state**, not proof that the underlying source route itself officially published an immersive or detached edition, officially omitted surrounding route context, or officially made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native framing, source-native omission of surrounding route context, office-preferred presentation, an officially republished immersive edition, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an authority-boundary problem, same-object player-view-state problem, occlusion problem, wrapper timing problem, reader-state problem, or rendition-state problem with some visible player-state posture around it, keep authority-boundary in `502` / `504`, keep same-object player state in `546`, keep occlusion in `593`, keep wrapper timing in `611`, keep reader posture in `639`, keep rendition posture in `642`, and add one bounded `646` player-state note only if the visible reduced-context player shell itself changed the reading.

## Keep player state, authority boundary, cue occlusion, timing, reader state, and rendition separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **authority-boundary / same-object player-state class** — whether fullscreen / popout / picture-in-picture already became the route problem or remained a same-object alias (`502`, `504`, `546`);
5. **cue occlusion** — whether surrounding authenticity-adjacent cues fell out of view because of reduced-context playback (`593`);
6. **wrapper timing / motion state** — animation, autoplay, or delayed-build posture in the later packet (`611`);
7. **wrapper-added reader state** — simplified reading posture rather than player-container posture (`639`);
8. **wrapper-added rendition state** — visible quality selectors or fidelity posture (`642`);
9. **carrier wrapper** — slide deck, PDF memo, browser shell, doc shell, saved page, ticket, or email thread (`437`, `490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible fullscreen / theater-mode / miniplayer / picture-in-picture / popout shell as if it proved the source itself was natively framed that way, natively stripped of surrounding context, or officially republished in immersive form; or
- letting a later reduced-context player shell become evidence that the packet itself is governance-bearing rather than just a later viewing layer around one preserved derivative.

`646` exists so the archive can keep that later visible player-state layer **truthful but non-governing**.

## Minimal wrapper-player-state note grammar

When wrapper player state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_player_state_kind=<fullscreen|theater_mode|miniplayer|picture_in_picture|popout|mixed|unknown>; context_visibility=<player_only|reduced_context|detached_controls|mixed|unknown>; state_scope=<viewer_selected|platform_auto|session_persistent|device_default|unknown>; source_native_framing_proved=<forbid>; source_route_context_absence_proved=<forbid>; official_presentation_default_proved=<forbid>; governing_member_from_player_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|pdf_shell|review_shell|slide_deck|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_646_when=<player_state_changed_reading>; promote_wrapper_player_state=<no>; basis=<why the later player-state layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried a visible reduced-context player state” without minting a new detached-derivative member or silently rewriting source framing, source route context, office presentation defaults, or packet governance.

## Typical uses

1. **Fullscreen screenshot overread**
   A later packet shows the preserved derivative in fullscreen and later readers start retelling the source as if the office itself published a stripped immersive edition rather than a later fullscreen viewing state.
2. **Picture-in-picture overread**
   A later packet captures the same derivative in picture-in-picture and later readers start treating the floating-player shell as if it proved the source route lacked surrounding context or that the floating view itself was the operative public answer surface.
3. **Popout playback overread**
   A later packet shows the preserved derivative in a popout tab/window and later readers start treating that detached playback container as if it proved official republication or a new governing route.
4. **Miniplayer/theater-mode bundle**
   A later packet carries a still image, shared URL, or copied metadata from the same route and also preserves a visible miniplayer or theater-mode shell; keep the detached derivative governing and use `646` only for the later player-state drift.

## When not to use this

Do **not** use `646` when:
- the decisive issue is still detached playback or fullscreen as a voter-facing authority boundary (`502`, `504`),
- the decisive issue is still same-object player-view-state aliasing (`546`),
- the decisive issue is still cue hiddenness / reduced-context non-absence inference (`593`),
- the decisive issue is still wrapper timing / motion posture (`611`),
- the decisive issue is still reader-state simplification (`639`),
- the decisive issue is still rendition / quality posture (`642`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible player-state layer leaves an ordinary authority-boundary, same-object player-state, occlusion, wrapper-timing, reader-state, or rendition-state problem, use the narrower doc and omit `646`.
If deleting it would erase **why a later reduced-context player shell changed the way the packet was being read or retold**, `646` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried fullscreen, theater mode, miniplayer, picture-in-picture, popout, or similar reduced-context player posture around same-route detached derivatives.
Tighten `502`, `504`, `546`, `593`, `600`, `611`, `639`, `642`, or `646` first.
Only add another numbered doc when repeated wrapper-player-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-player-state note under `646`.
