# 611 — Official voter-information platform media authenticity-cue packet motion, build order, autoplay, and non-governing wrapper-timing firewall

**Track:** Shared / Public surfaces

This document defines a bounded control for **later packet-level motion and timing around same-route detached derivatives**:
later-applied object animations,
build-order staging,
autoplay or timed-advance settings,
transition timing,
revealed-after-previous sequencing,
or similar wrapper-added motion choices that change **how, when, or in what temporal cadence one preserved member appears** without proving that the official source route itself natively carried that same reveal sequence, animation timing, emphasis cadence, or implied chronology.

It does not create a new authenticity cue family.
It adds one narrow rule:
**when a later packet changes the motion, reveal timing, or autoplay behavior around preserved same-route detached derivatives, the archive should preserve that wrapper-timing fact honestly and should not quietly treat the resulting build order, delay, animation, or auto-advance cadence as if it proved source-native chronology, source-native urgency, source-native emphasis, or the packet's governing member.**

## Why this exists (bounded)

The archive already distinguishes detached stills (`597`), copied text (`595`), copied metadata (`598`), clipped observation windows (`594`), mixed detached-derivative packets (`600`), short wrapper labels (`601`), longer wrapper summaries (`602`), wrapper-added emphasis markup (`603`), wrapper-added concealment (`604`), wrapper-added ordering (`605`), wrapper-added membership (`606`), wrapper-added repetition (`607`), wrapper-added layout (`608`), wrapper-added prominence (`609`), and wrapper-added styling (`610`).
A smaller but still important seam remains:
**a later packet can animate, auto-advance, or stage one same-route detached derivative or the packet around it over time, and later readers can start narrating that wrapper timing as if it proved source-native chronology, source-native urgency, source-native emphasis cadence, or the packet's governing member.**

Current primary-source guidance is specific enough to justify one compact bridge here.
Google Slides' current help says object animations can start on click or after a previous animation, and that animation and transition speed can be changed.
Microsoft's current support says PowerPoint transitions can have sounds, durations, and an automatic advance time to the next slide.
Apple's current Keynote guidance says objects can have multiple action builds, duration controls, and explicit build order, including combined builds that play together.
(xref: `google_slides_add_change_animations_transitions_help_page`; xref: `microsoft_powerpoint_set_transition_timing_speed_help_page`; xref: `apple_keynote_animate_objects_slide_mac_help_page`)

That is enough to support one bounded maintainer rule:
**later packet motion is still only later packet motion.**
An autoplay deck, delayed reveal packet, bounce-emphasis packet, or staged-after-previous packet can honestly be the temporal experience later readers encountered while still failing to prove that the source route itself natively carried that same reveal order, urgency cadence, or governing status.
`611` exists so the archive can preserve that timing fact without quietly promoting wrapper motion into source-native meaning.

## Keep source-derived content and wrapper-added timing separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **wrapper-added packet label** — filename, subject line, slide title, memo heading, or similar short later-added narrative (`601`);
7. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, memo-body summaries, or similar longer later packet narrative (`602`);
8. **wrapper-added markup/emphasis** — highlight boxes, circles, arrows, underlines, comment anchors, zoom lenses, ink, or similar later visual emphasis (`603`);
9. **wrapper-added concealment/suppression** — redactions, crop-hidden regions, hidden slides, hidden objects, or similar later visual withholding (`604`);
10. **wrapper-added ordering/sequence** — reordered slide order, reordered PDF page order, moved packet sections, or similar later arrangement (`605`);
11. **wrapper-added membership/composition** — imported slides, merged-page subsets, chosen attachments, appended packet members, or similar later included-member selection (`606`);
12. **wrapper-added repetition/multiplicity** — duplicated slides, repeated pages, repeated excerpts, repeated attachments, gallery-style repeats, or similar later same-member multiplication (`607`);
13. **wrapper-added layout/spatial relation** — side-by-side placement, inset-over-main placement, gallery rows, stacked columns, split-screen comparison framing, or similar later positioning (`608`);
14. **wrapper-added prominence/salience** — enlarged hero panels, thumbnail demotion, resized excerpt blocks, large-versus-small weighting, or similar later visual importance allocation (`609`);
15. **wrapper-added styling/tone** — later themes, palettes, fonts, background styles, grayscale/sepia effects, warning-color coding, or similar visual tone choices (`610`);
16. **wrapper-added motion/timing** — later object animations, build order, delays, autoplay, transition timing, reveal-after-previous settings, or similar temporal staging choices (`611`);
17. **carrier wrapper** — slide deck, PDF memo, chat export, saved page, web archive, issue ticket, or other transport context (`437`, `490`, `600`);
18. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating wrapper-added motion as if it proved source-native chronology, source-native urgency, or source-native emphasis cadence, or
- letting an autoplay deck or staged-reveal wrapper become the governing member instead of first classifying the surviving detached derivative.

`611` exists so the archive can keep that later timing layer **truthful but non-governing**.

## Minimal wrapper-timing note grammar

When wrapper-timing overread itself matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_timing_kind=<object_animation|build_order|autoplay|transition_timing|delay|mixed|unknown>; timing_relation=<same_route_packet_staging|same_route_member_staging|mixed|unknown>; wrapper_timing_origin=<later_wrapper_added|copied_from_source|mixed|unknown>; treat_timing_as_source_chronology=<forbid>; treat_timing_as_source_urgency=<forbid>; treat_timing_as_governing_member=<forbid>; carrier_wrapper=<slide_deck|powerpoint_show|video_export|pdf_memo|chat_export|saved_page|web_archive|ticket|email_thread|shared_link_message|none>; cite_default=<head|fallback anchor>; use_611_when=<wrapper_timing_changed_perceived_sequence>; promote_wrapper_timing=<no>; basis=<why the later motion/timing needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this packet later made the material appear in a staged or auto-advanced way” without minting a new detached-derivative member or silently rewriting chronology, urgency, or governance.

## Typical uses

1. **Autoplay-overread**
   A packet auto-advances slides or starts playing without click input and later readers start retelling that wrapper timing as if the source route itself enforced the same sequence or urgency.
2. **Build-order overread**
   A packet reveals one preserved member only after a previous build completes and later readers start treating that staged appearance as if it proved source-native chronology or deliberateness.
3. **Bounce / flash emphasis overread**
   A packet animates one preserved member with motion that makes it look newly urgent or highlighted and later readers start treating that movement as if it came from the source route itself.
4. **Timed-delay overread**
   A packet pauses before revealing or advancing to a preserved member and later readers start narrating that delay as if the source route natively withheld or sequenced the material that way.
5. **Video-export overread**
   A later video export preserves one packet's motion, narration timing, or staged reveal sequence and later readers start treating that rendered timing as if it were source-native media chronology rather than wrapper-added playback behavior.
