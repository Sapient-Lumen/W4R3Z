## Why this exists (bounded)

The archive already made the right move by splitting detached same-route extracts into bounded families:
text (`595`),
audio (`596`),
still image (`597`),
metadata (`598`),
and locator-only pointers (`599`).
That kept transcript/caption/OCR text, spoken-audio derivatives, frame grabs/posters, copied labels, and copied pointers from collapsing into one vague “extracted artifact” note.

But that success creates a second risk:
**once `595–599` exists, reviewers can start acting as if every mixed packet, saved-page copy, or archive-style export deserves either several carried derivative docs at once or one more numbered detached-derivative sibling.**

Current primary-source guidance is already enough to justify one compact family firewall here.
YouTube, Microsoft, Vimeo, and related platform docs already distinguish transcript/caption text, alternate/background audio consumption, thumbnails/posters, editable titles/descriptions/chapters, and copied share/embed/current-time links as genuinely different artifact forms around the same media object. Browser guidance likewise treats offline reading-list copies, saved pages, and web-archive files as real carrier forms without turning them into new authority surfaces or new media-authenticity cue families by themselves.
(xref: `youtube_view_video_transcripts_help_page`; xref: `youtube_use_automatic_captioning_help_page`; xref: `youtube_premium_background_play_help_page`; xref: `vimeo_multiple_audio_tracks_help_page`; xref: `youtube_thumbnail_title_tips_help_page`; xref: `youtube_video_chapters_help_page`; xref: `youtube_share_videos_channels_help_page`; xref: `microsoft_share_video_audio_m365_help_page`; xref: `google_chrome_read_pages_later_offline_computer_page`; xref: `apple_support_safari_keep_reading_list_mac_page`; xref: `apple_support_safari_save_webpage_mac_page`)

That is enough for one bounded maintainer rule:
**most remaining detached-derivative work is routing and compression work, not a reason to mint `652+`.**

## This is not another authenticity-cue family or another carrier subtype

`600` does **not** define a new supportive authenticity cue.
It does **not** define a new route.
It does **not** define a new evidence kind.
It does **not** say text/audio/still/metadata/locator distinctions were unnecessary.

It exists only for one bounded question:
**when the same current route is already understood but later materials preserve one or more detached derivative slices of that route, how should maintainers choose among the existing `595–599` docs without fragmenting the archive further?**

If the real issue is already one specific derivative class, use that class's doc directly.
Use `600` only when the problem is:
- choosing among `595–599`,
- describing a mixed detached-derivative packet where no single member clearly dominates,
- or applying the archive's anti-growth rule for future detached-derivative additions.

## Saved-page, print-render, offline-copy, and web-archive rule

Saved-page copies, print-to-PDF renders, offline reading-list copies, MHTML/web-archive captures, and similar preserved page artifacts often carry a **mixture** of detached derivative facts at once:
visible still-image shell,
stripped text,
metadata labels,
and sometimes a copied locator.

Those artifacts SHOULD usually start with the archive's already-existing page/archive controls:
- `437` for portable record / print-save-to-PDF / off-screen-fidelity questions;
- `490` for offline saved-page / web-archive authority-boundary questions.

Add `600` only when the remaining ambiguity is specifically:
- which detached-derivative member inside that preserved page artifact is doing the argumentative work,
- or whether no single detached-derivative member dominates and the packet therefore needs one compact family-level anti-fragmentation note.

That means `600` is also a **growth stop**:
a saved-page or web-archive case should not automatically become `601`, `602`, `603`, `604`, `605`, `606`, `607`, or another detached-derivative-style add-on just because it truthfully contains a mixed derivative bundle.

## Minimal family-level note grammar

When `600` is genuinely needed, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; derivative_mix=<text|audio|still|metadata|locator|mixed>; governing_member=<595|596|597|598|599|600>; packet_mixed=<yes|no>; dominant_overread=<text|audio|still|metadata|locator|mixed>; carrier_wrapper=<slide_deck|pdf_memo|chat_export|saved_page|web_archive|ticket|none>; carrier_governs=<no>; page_archive_baseline=<437|490|none>; cross_state_companion=<591|585|587|589|590|594|none>; stack_many_derivative_docs=<forbid>; cite_default=<head|fallback anchor>; use_600_when=<no_single_member_dominates|family_growth_question>; promote_new_member=<no>; basis=<why one family-level routing note was still needed>`

This is a note contract, not a new schema.
It exists so later packets can say “this preserved a mixed detached-derivative bundle from the same route” without carrying several near-neighbor derivative docs by reflex.
