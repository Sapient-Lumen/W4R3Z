## What this is for

Use `644` when a later packet preserves or reenacts a **visible wrapper playback-rate-state layer** around same-route detached derivatives:
- `1.25x`, `1.5x`, `1.8x`, `2x`, `0.8x`, or similar displayed playback-rate selections,
- temporary hold-to-scan or fast-forward posture,
- a speed menu open with one rate visibly selected,
- remembered playback-rate defaults that survived into the later packet,
- or similar later packet timing foregrounding.

Those timing surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added playback-rate / scan posture**, not automatic proof of:
- source-native brevity or source-native pacing,
- an officially summarized or officially abridged edition,
- office-preferred review tempo,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded playback-rate-state bridge.
YouTube Help says viewers can play videos at different speeds and can click and hold on a video to play it at `2x` speed.
Vimeo Help says playback-speed controls can be enabled or disabled, supported viewers can use slower or faster playback on Vimeo and embedded players, and temporary `2x` hold-to-scan posture is available.
Microsoft Support says the SharePoint / OneDrive web player supports playback speeds including `2x`, `1.8x`, `1.5x`, `1.2x`, `1x`, and `0.8x`.
That is enough for one bounded firewall here.
(xref: `youtube_speed_up_or_slow_down_videos_help_page`; xref: `vimeo_playback_speed_controls_help_page`; xref: `microsoft_video_player_playback_experience_help_page`)

`644` exists so maintainers can say:
**this packet preserved a later playback-rate / scan posture around same-route detached derivatives, and that posture mattered for how later readers interpreted the packet, but the playback-rate layer itself does not silently prove source-native brevity, source-native pacing, an officially summarized edition, office-preferred review tempo, or the governing member.**

## Why this is distinct

`505` asks whether playback-speed, scrubbing, skipping, or seek posture became the public-surface boundary problem in the first place.

`548` asks whether the same current media object preserved **selected playback-rate state** — accelerated playback, slowed playback, or temporary scan-hold posture — while the same object still controlled.

`611` asks whether a later packet preserved **timing / motion wrapper posture** such as animation build order, autoplay, or transition timing around a derivative carrier.

`642` asks whether a later packet preserved **rendition / fidelity posture** such as `Auto`, `Data saver`, visible resolution picks, or quality-menu state.

`643` asks whether a later packet preserved **caption-display / caption-selection posture** such as captions-on/off, selected caption language, or caption appearance customization.

`644` asks a different question:
**did a later packet add or preserve a visible playback-rate / scan layer — `1.25x`, `1.5x`, `2x`, `0.8x`, temporary hold-to-scan posture, remembered speed defaults, or speed-menu state — and did later readers start overreading that layer as if it proved source-native brevity, source-native pacing, an officially summarized edition, office-preferred review tempo, or the packet's governing member?**

If the real problem is route-level playback speed / scrub / seek authority, use `505`.
If the real problem is same-object selected playback-rate state while the current head still controls, use `548`.
If the real problem is wrapper timing/motion posture, use `611`.
If the real problem is rendition or caption posture, use `642` or `643`.
Use `644` only when the missing distinction is **wrapper playback-rate-state posture itself**.

## Decision test

Use `644` when all three conditions hold:

1. later evidence preserves or reenacts a **visible playback-rate layer** around same-route detached derivatives — for example `1.25x`, `1.5x`, `2x`, `0.8x`, temporary hold-to-scan posture, a speed menu showing one selected rate, or remembered speed defaults;
2. that layer is **later wrapper-added playback-rate / scan state**, not proof that the underlying source route itself officially published a shorter or faster edition, officially summarized the source, officially preferred one review tempo, or officially made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native brevity, source-native pacing, an officially summarized edition, office-preferred review tempo, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a playback-boundary problem, same-object playback-rate-state problem, wrapper timing problem, rendition-state problem, or caption-state problem with some visible playback-rate posture around it, keep playback-boundary in `505`, keep same-object playback-rate state in `548`, keep wrapper timing in `611`, keep rendition posture in `642`, keep caption posture in `643`, and add one bounded `644` playback-rate-state note only if the visible playback-rate layer itself changed the reading.

## Keep playback-rate state, playback-boundary, timing, rendition, and caption separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **route-level playback boundary** — whether playback-speed / scrubbing / seek posture already became the surface problem (`505`);
5. **same-object playback-rate state** — accelerated/slowed/scan posture while the same object still controlled (`548`);
6. **wrapper timing / motion state** — animation, autoplay, or timed build posture in the later packet (`611`);
7. **wrapper-added rendition state** — visible quality selectors or fidelity posture (`642`);
8. **wrapper-added caption state** — CC on/off posture, selected caption language, auto-generated-caption inclusion, or caption-style posture (`643`);
9. **carrier wrapper** — slide deck, PDF memo, browser shell, doc shell, saved page, ticket, or email thread (`437`, `490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible playback-rate shell as if it proved the source itself was natively brief, officially shortened, or officially paced for review; or
- letting a later playback-rate wrapper become evidence that the packet itself is governance-bearing rather than just a later timing layer around one preserved derivative.

`644` exists so the archive can keep that later visible playback-rate layer **truthful but non-governing**.

## Minimal wrapper-playback-rate-state note grammar

When wrapper playback-rate state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_playback_rate_kind=<accelerated_playback|slowed_playback|temporary_scan_hold|speed_menu_open|remembered_rate_default|mixed|unknown>; displayed_rate=<0_8x|1x|1_2x|1_25x|1_5x|1_8x|2x|other|unknown>; selection_scope=<viewer_selected|session_persistent|platform_default|device_default|unknown>; source_native_brevity_proved=<forbid>; official_summary_proved=<forbid>; office_review_tempo_proved=<forbid>; governing_member_from_rate_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|pdf_shell|review_shell|slide_deck|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_644_when=<playback_rate_state_changed_reading>; promote_wrapper_playback_rate_state=<no>; basis=<why the later playback-rate layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried a visible playback-rate / scan posture” without minting a new detached-derivative member or silently rewriting source duration, source pacing, summary authority, review-tempo authority, or packet governance.

## Typical uses

1. **Visible `1.5x` overread**
   A later packet shows a visible `1.5x` or `2x` chip and later readers start retelling the packet as if the office itself published a shortened or faster review edition rather than a viewer-side timing posture.
2. **Remembered speed-default overread**
   A later packet opens with a remembered playback-rate state already active and later readers start treating that resumed speed as if it were the office's default or governing presentation choice.
3. **Temporary scan-hold overread**
   A later packet captures a temporary hold-to-scan posture and later readers start treating that scan posture as if it proved source-native brevity, source-native urgency, or an officially compressed explanation.
4. **Playback-rate plus detached derivative bundle**
   A later packet carries a still image, shared URL, or copied metadata from the same route and also preserves a visible speed chip; keep the detached derivative governing and use `644` only for the later playback-rate-state drift.

## When not to use this

Do **not** use `644` when:
- the decisive issue is still route-level playback-speed / scrubbing / seek authority (`505`),
- the decisive issue is still same-object playback-rate selection state (`548`),
- the decisive issue is still wrapper timing / motion posture (`611`),
- the decisive issue is still rendition / quality posture (`642`),
- the decisive issue is still caption posture (`643`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible playback-rate layer leaves an ordinary playback-boundary, same-object playback-rate, wrapper-timing, rendition-state, or caption-state problem, use the narrower doc and omit `644`.
If deleting it would erase **why a later speed / scan layer changed the way the packet was being read or retold**, `644` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried `1.25x`, `1.5x`, `2x`, `0.8x`, temporary hold-to-scan posture, remembered speed defaults, or a visible speed menu around same-route detached derivatives.
Tighten `505`, `548`, `600`, `611`, `642`, `643`, or `644` first.
Only add another numbered doc when repeated wrapper-playback-rate-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-playback-rate-state note under `644`.
