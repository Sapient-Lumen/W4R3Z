# 626 — Official voter-information platform media authenticity-cue packet command bars context menus and non-governing wrapper-action-state firewall

**Track:** Shared / Public surfaces

## What this is for

Use `626` when a later packet preserves or reenacts a **visible wrapper action-state layer** around same-route detached derivatives:
- a command bar or top-of-list action row,
- a right-click or ellipsis / more-actions menu,
- quick-action buttons like Share, Copy link, Download, Move, Rename, or Delete,
- state-conditioned actions like Check out, Check in, Discard check out, or Pin,
- disabled, absent, or greyed-out commands,
- or similar later packet affordance posture.

Those action surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added action posture**, not automatic proof of:
- official permission,
- official capability,
- source-native control,
- endorsed next steps,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded action-state bridge.
Google Drive documents quick actions and a More actions menu for selected files.
Microsoft documents file actions from command bars and more-action menus in SharePoint and OneDrive, including share/copy-link affordances and state-conditioned commands like check out/check in.
Adobe documents a More menu for file-management tools and explicitly notes that listed tools can differ based on the selected file's type and status.
That is enough for one bounded firewall here.
(xref: `google_drive_how_to_use_google_drive_help_page`; xref: `microsoft_sharepoint_document_library_web_part_help_page`; xref: `microsoft_sharing_files_sensitivity_labels_help_page`; xref: `microsoft_sharepoint_check_out_or_check_in_files_in_document_library_help_page`; xref: `adobe_acrobat_manage_files_and_folders_help_page`)

`626` exists so maintainers can say:
**this packet preserved a later command/menu layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the action layer itself does not govern the packet and does not silently prove permission, capability, control, or the governing member.**

## Why this is distinct

`612` asks whether later evidence preserved **navigation posture** — hyperlinks, action buttons, hotspots, or internal jumps that move the reader within or between packet members.

`619` asks whether a later packet preserved **access posture** — roles, link scopes, manage-access settings, or request-access posture.

`624` asks whether a later packet preserved **information posture** — owner/location/size/type fields, info cards, details panes, or properties dialogs.

`625` asks whether a later packet preserved **listing posture** — file lists, saved views, sort order, filters, group headers, or shown/hidden columns.

`626` asks a different question:
**did a later packet add or preserve a visible action layer — command bars, more-action menus, context menus, quick-action buttons, disabled commands, or state-conditioned actions — and did later readers start overreading that layer as if it proved official permission, official capability, source-native control, endorsed next steps, or the packet's governing member?**

If the real problem is click-path navigation, use `612`.
If the real problem is access scope or permissions state, use `619`.
If the real problem is visible file details or file-list posture, use `624` or `625`.
Use `626` only when the missing distinction is **wrapper action-state posture itself**.

## Decision test

Use `626` when all three conditions hold:

1. later evidence preserves or reenacts a **visible action or affordance layer** around same-route detached derivatives — for example a command bar, more-actions menu, context menu, quick-action row, disabled command, or state-conditioned action;
2. that layer is **later wrapper-added action state**, not proof that the underlying source route itself published, endorsed, or canonically fixed the same commands, permissions, or workflow authority; and
3. later readers are drifting toward treating that layer as if it proved **official permission, official capability, source-native control, endorsed next steps, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a navigation, access, information, or listing problem with some command-bar/menu posture around it, keep navigation in `612`, keep access in `619`, keep information in `624`, keep listing in `625`, and add one bounded `626` action-state note only if the visible action layer itself changed the reading.

## Keep navigation, access, information, listing, and action state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added navigation state** — links, hotspots, jump targets, or internal click paths (`612`);
5. **wrapper-added access state** — link scopes, roles, or request-access posture (`619`);
6. **wrapper-added information state** — owner, location, size, type, created, modified, details-pane, info-card, or properties-dialog posture (`624`);
7. **wrapper-added listing state** — sort keys, sort direction, filters, groupings, visible columns, saved views, or list/tile modes (`625`);
8. **wrapper-added action state** — command bars, more-action menus, context menus, quick-action buttons, disabled commands, or state-conditioned commands (`626`);
9. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, or other transport context (`490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible action affordance as if it proved real authority, permission, or canonical workflow control, or
- letting a file-manager or document-library command surface become evidence that the packet itself governs what readers should do next.

`626` exists so the archive can keep that later visible action layer **truthful but non-governing**.

## Minimal wrapper-action-state note grammar

When wrapper action state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_action_kind=<command_bar|context_menu|more_actions|quick_actions|disabled_command|state_conditioned_action|mixed|unknown>; actions_seen=<share|copy_link|download|move|rename|delete|check_out|check_in|discard_check_out|pin|open|mixed|unknown>; action_anchor_relation=<whole_member|member_link|attachment|slide|page|object|message|collection|mixed|unknown>; wrapper_action_origin=<later_wrapper_added|file_manager_ui|document_library_ui|desktop_client|web_app_ui|mixed|unknown>; permission_proved=<forbid>; capability_proved=<forbid>; source_control_proved=<forbid>; endorsed_next_step_proved=<forbid>; treat_action_state_as_governing_member=<forbid>; carrier_wrapper=<doc_shell|file_manager|document_library|desktop_client|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_626_when=<action_state_changed_reading>; promote_wrapper_action_state=<no>; basis=<why the later command/menu layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible action affordances” without minting a new detached-derivative member or silently rewriting permission, capability, control, or governance.

## Typical uses

1. **Quick-action overread**
   A later packet shows Share, Copy link, or Download and later readers start retelling those visible affordances as if they proved route-level publicness, official export authority, or the office's endorsed next step.
2. **Context-menu overread**
   A later packet shows a right-click / more-actions menu and later readers start retelling that wrapper menu as if it proved source-native control or canonical workflow authority.
3. **State-conditioned command overread**
   A later packet shows Check out, Check in, Discard check out, or a similarly state-conditioned command and later readers start retelling that menu state as if it were the office's own substantive publication or control decision.
4. **Disabled-command overread**
   A later packet shows a disabled or absent command and later readers start retelling that wrapper limitation as if it proved route-level prohibition, absence of authority, or official refusal.
5. **Command-bar primacy overread**
   A later packet preserves a command bar above a derivative and later readers start treating those surfaced actions as if they defined what the packet itself canonically is or what readers must do next.

## When not to use this

Do **not** use `626` when:
- the decisive issue is still navigation (`612`),
- the decisive issue is still access posture (`619`),
- the decisive issue is still information or listing posture (`624–625`),
- the decisive issue is still lifecycle or sync posture (`621–622`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive issue is still print/save/offline/web-archive authority or portability (`490`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible command/menu layer leaves an ordinary navigation, access, information, or listing problem, use the narrower doc and omit `626`.
If deleting it would erase **why a later command bar, more-actions menu, or disabled-action surface changed the way the packet was being read or retold**, `626` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried a command bar, context menu, quick-action row, disabled command, or more-actions sheet.
Tighten `612`, `619`, `624–626`, or `600` first.
Only add another numbered doc when repeated wrapper-action-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-action-state note under `626`.
