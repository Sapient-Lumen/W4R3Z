# 621 — Official voter-information platform media authenticity-cue packet trash, recycle-bin, delete/restore, and non-governing wrapper-lifecycle-state firewall

**Track:** Shared / Public surfaces

This document covers a narrow packet-wrapper problem:
**later packets can preserve trash views, recycle-bin entries, deleted queues, delete confirmations, restore notices, second-stage deletion posture, or similar visible lifecycle-state layers around same-route detached derivatives, and later readers can start mistaking that wrapper lifecycle posture for source-route retraction, source-route disappearance, current public absence, restored official republication, or the packet's governing member.**

## What this is for

Use `621` when a later packet preserves or reenacts a **visible wrapper lifecycle-state layer** around same-route detached derivatives:
- trash views,
- recycle-bin entries,
- deleted queues,
- delete confirmations,
- restore confirmations,
- “removed from shared library” or “item was deleted” notices,
- second-stage recycle-bin posture,
- permanent-delete warnings,
- or similar later packet deletion / recovery posture.

Those lifecycle states are real packet facts and should be preserved honestly.
But they are still **later wrapper-added lifecycle posture**, not automatic proof of:
- source-route retraction,
- source-route nonexistence,
- the current public route's absence,
- official repudiation,
- restored official republication,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded lifecycle bridge.
Google Drive treats deleted files as Trash items that can be restored and notes that they remain in Trash for 30 days before being deleted forever.
OneDrive and SharePoint treat deleted files as Recycle Bin items with restore behavior and retention windows, and SharePoint separately documents second-stage recycle-bin handling plus permanent deletion after later delete actions.
Adobe documents deleted agreements/templates and cloud files as recoverable deleted-state entries for a bounded period and separately documents permanent deletion as non-restorable.
(xref: `google_drive_recover_deleted_file_help_page`; xref: `microsoft_restore_deleted_files_folders_onedrive_help_page`; xref: `microsoft_manage_recycle_bin_sharepoint_site_help_page`; xref: `microsoft_delete_items_empty_recycle_bin_sharepoint_site_help_page`; xref: `adobe_acrobat_recover_deleted_agreements_templates_help_page`; xref: `adobe_creative_cloud_permanently_delete_files_help_page`)

`621` exists so maintainers can say:
**this packet preserved a later delete / trash / restore lifecycle layer around a same-route detached derivative, and that layer mattered for how later readers interpreted the packet, but the lifecycle layer itself does not govern the packet and does not silently rewrite route control, public reachability, or official publication history.**

## Why this is distinct

`512` asks whether the public source route itself currently lands on an unavailable, private, blocked, or otherwise restricted shell.

`618` asks whether the packet preserved **history posture** — prior versions, restore points, or compare-old-vs-new state.

`619` asks whether the packet preserved **access posture** — link scopes, roles, access requests, or similar permissions state.

`620` asks whether the packet preserved **event posture** — notification cards, activity feeds, or similar workflow-event state.

`602` asks whether packet synopsis or forwarding prose is being overread.

`621` asks a different question:
**did a later packet add or preserve a visible deletion/recovery layer — trash state, recycle-bin status, deleted queue posture, restore confirmation, or permanent-delete warning — and did later readers start overreading that layer as if it proved official retraction, current source disappearance, restored official publication, or the packet's governing member?**

If the real problem is the public route itself being unavailable or private, use `512`.
If the real problem is version history or restore-point posture, use `618`.
If the real problem is access state, use `619`.
If the real problem is notifications or activity posture, use `620`.
If the real problem is wrapper summary prose, use `602`.
Use `621` only when the missing distinction is **wrapper lifecycle-state posture itself**.

## Decision test

Use `621` when all three conditions hold:

1. later evidence preserves or reenacts a **visible deletion / trash / recovery layer** around same-route detached derivatives — for example a Trash view, Recycle Bin entry, Deleted queue card, delete confirmation, restore confirmation, “removed from shared library” notice, or permanent-delete warning;
2. that layer is **later wrapper-added lifecycle posture**, not proof that the underlying source route itself was officially retracted, ceased to exist, or was republished in that same way; and
3. later readers are drifting toward treating that layer as if it proved **official withdrawal, current public absence, official repudiation, restored source publication, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly copied source text or copied source metadata with some trash/recycle/delete posture around it, keep the detached derivative in `595–600`, keep any source-route restriction fact in `512`, keep any history-state fact in `618`, keep any access-state fact in `619`, keep any event-state fact in `620`, and add one bounded `621` lifecycle-state note.

## Keep source-derived content, route-level absence, and wrapper-added lifecycle state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **route-level public restriction or absence** — whether the public source route itself was unavailable, blocked, removed, or otherwise not ordinarily reachable at route level (`512`, `529`, `530`);
7. **wrapper-added summary prose** — forwarding comments, memo-body summaries, or similar later packet narrative (`602`);
8. **wrapper-added history state** — version-history panes, restore points, prior-version labels, or similar source-history posture (`618`);
9. **wrapper-added access state** — share scopes, roles, request-access posture, or similar later permissions state (`619`);
10. **wrapper-added event state** — activity feeds, alert cards, notification emails, or similar later workflow-event posture (`620`);
11. **wrapper-added lifecycle state** — Trash/Recycling/Deleted queue status, delete-confirmation posture, restore notices, second-stage recycle posture, or permanent-delete warnings (`621`);
12. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, or other transport context (`490`, `600`);
13. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible trash / deleted / recycle state as if it proved the source route itself was officially retracted or currently nonexistent, or
- treating a restore confirmation or recovered-item view as if it proved official republication or current authoritative re-endorsement.

`621` exists so the archive can keep that later visible lifecycle layer **truthful but non-governing**.

## Minimal wrapper-lifecycle-state note grammar

When wrapper lifecycle state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_lifecycle_kind=<trash_view|recycle_bin_entry|deleted_queue|delete_confirmation|restore_confirmation|removed_notice|second_stage_recycle|permanent_delete_warning|mixed|unknown>; lifecycle_anchor_relation=<whole_member|member_link|attachment|slide|page|object|message|mixed|unknown>; wrapper_lifecycle_origin=<later_wrapper_added|storage_trash_ui|recycle_bin_ui|deleted_queue_ui|recovery_notice|imported_lifecycle_capture|mixed|unknown>; source_retraction_proved=<forbid>; source_nonexistence_proved=<forbid>; current_public_absence_proved=<forbid>; restored_source_publication_proved=<forbid>; treat_lifecycle_state_as_governing_member=<forbid>; carrier_wrapper=<trash_view|recycle_bin|doc_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_621_when=<lifecycle_state_changed_reading>; promote_wrapper_lifecycle_state=<no>; basis=<why the later visible deletion/recovery layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible deletion/recovery posture” without minting a new detached-derivative member or silently rewriting route control, public absence, official withdrawal, or governance.

## Typical uses

1. **Trash-overread**
   A later packet shows an item in Trash / Recycle Bin and later readers start retelling that wrapper state as if the source route itself was officially withdrawn or no longer existed.
2. **Second-stage-overread**
   A later packet shows second-stage recycle-bin posture and later readers start treating that later retention state as if it settled source-route authenticity or final official disappearance.
3. **Restore-overread**
   A later packet shows a restore confirmation or recovered-item view and later readers start narrating that wrapper recovery action as if it proved official republication or renewed endorsement.
4. **Delete-confirmation overread**
   A later packet preserves a delete warning or “item removed” notice and later readers start treating that wrapper action as if it displaced head-first source control.
5. **Permanent-delete overread**
   A later packet shows a permanent-delete warning and later readers start narrating that wrapper lifecycle posture as if it independently proved source history, current public absence, or the governing member.

## When not to use this

Do **not** use `621` when:
- the decisive issue is the public source route itself being unavailable, private, blocked, or absent (`512`, `529`, `530`),
- the decisive issue is still wrapper summary prose (`602`),
- the decisive issue is still wrapper history-state posture (`618`),
- the decisive issue is still wrapper access-state posture (`619`),
- the decisive issue is still wrapper event-state posture (`620`),
- the decisive issue is still copied source text (`595`),
- the decisive issue is still copied source metadata (`598`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive problem is still print/save/offline/web-archive authority or portability (`490`),
- or the decisive problem is still cross-state composite assembly (`591`).

If deleting the visible lifecycle layer leaves an ordinary source-route absence problem, history-state problem, access-state problem, event-state problem, summary problem, or mixed-packet problem, use the narrower doc and omit `621`.
If deleting it would erase **why a later trash / recycle / deleted / restored layer changed the way the packet was being read or retold**, `621` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried Trash state, Recycle Bin posture, Deleted queue entries, restore confirmations, or permanent-delete warnings.
Tighten `512`, `600`, `618`, `619`, `620`, or `621` first.
Only add another numbered doc when repeated wrapper-lifecycle-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-lifecycle-state note under `621`.
