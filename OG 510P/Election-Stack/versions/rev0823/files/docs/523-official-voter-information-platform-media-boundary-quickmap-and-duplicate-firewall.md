# 523 — Official voter-information platform media boundary quickmap and duplicate firewall

**Track:** Shared

This document turns the recent **official voter-information platform media stack** into a compact, maintainable neighbor map instead of a serial pile of almost-adjacent additions.

It exists to do five things:

1. give maintainers and reviewers one fast place to decide **which existing media-surface doc actually controls**;
2. stop future adjacent media-growth from restating a nearby wrapper, route, or state distinction in slightly different words;
3. keep the archive biased toward **overlap tightening, checklist/template refinement, and cross-link repair** before adding another numbered surface;
4. make mixed media incidents easier to describe as **one primary surface plus secondary wrappers** rather than as a synthetic mega-surface;
5. keep this family compact enough that it still helps operators under pressure.

## The anti-bloat rule for this family

For this subfamily, maintainers SHOULD prefer the following order of operations:

1. tighten an existing doc's **overlap / not-the-same-as** section,
2. refine an existing checklist or payload template,
3. repair entrypoint or cross-link wiring,
4. add one short quickmap note here,
5. map the route through `524` if the problem is mostly state vocabulary or capture-order drift,
6. use `525` if the problem is mostly packet size, first-contact capture discipline, or wrapper-mutation note quality,
7. use `526` if the problem is mostly re-anchor-target precedence or wrapper-exit choice,

## Mixed incidents: record one primary surface and a small set of secondary wrappers

Many real incidents span more than one row.
That does **not** mean the archive needs a synthetic umbrella surface.

Prefer this pattern instead:
1. identify the **primary surface** that most directly changed what the voter thought the route was;
2. record only the secondary wrappers needed to reconstruct the confusion;
3. when a packet also needs bounded same-object chain facts, keep the most control-salient ones in `527`'s optional canonicalized `companions=` line rather than inflating the primary summary into a synthetic mega-surface;
4. do not read later omission of a companion tag as proof that the fact cleared unless `528` or the packet body says so explicitly;
5. if a later packet reuses the same companion doc with a different canonical token, read that as an explicit scoped observed-state replacement inside that later packet, not as automatic head churn or universal negation of earlier scoped facts unless `528–529` say a controlling field moved;
6. if one companion doc has several co-true bounded facts, prefer that doc's own `header_pick_order=<...>` winner in `527`, prefer its `detail_pick_order=<...>` winner in `companions_detail=` when that single extra-token slot is enough, and carry anything beyond that in one short scoped sentence or `528` note rather than duplicating that doc across header and overflow or minting a sibling doc just to preserve a second same-object nuance;
7. if the AI surface is already understood but the same current-object boundary still answers the line by itself, omit `582` and leave the point in `523`; otherwise use `582`'s **neighbor-side handoff default** here: keep the line in `523` while same-object boundary/current-route duplication is still the live question, then swap to the single governing `582` slice only after that handoff is real;
8. keep `527`'s `companions=` line within the archive's three-tag header budget; if more same-object facts matter, use one compact `companions_overflow=` spillway before falling back to prose, let `527`'s comparison-selection order decide which docs stay in the header versus overflow, and do not promote a new hybrid surface just to make the header longer;

## Required wiring for any future media-surface promotion

A future media-surface addition after this quickmap/lexicon/mutation-pack layer is not considered integrated unless the same revision also includes the right wiring for its class.

**If it is a primary boundary / operator-facing surface** (a new first-contact object, a new checklist-bearing review lane, or a new payload-bearing proof shape), the revision must include:
- the numbered canonical doc,
- the matching checklist,
- the matching payload template,
- at least two tightened adjacency declarations in nearby docs,
- one changelog entry and version bump,
- and navigation updates where readers and maintainers actually look first (`docs/13-*`, `docs/START_HERE.md`, and `docs/207-*`).

**If it is only a doc-only same-object chain-layer companion** (a bounded `528–573`-style retention / citation / head-default rule that intentionally reuses the existing capture stack instead of minting a new operator workflow), the revision must still include:
- the numbered canonical doc,
- at least two tightened adjacency declarations in nearby docs,
- explicit routing through this quickmap where relevant,
- the matching `530`/`528`/`529`-family integration needed to keep citation and chain-control semantics coherent,
- one changelog entry and version bump,
- and navigation updates where readers and maintainers actually look first (`docs/13-*`, `docs/START_HERE.md`, and `docs/207-*`).

That rule is intentionally stricter than "write another doc."
The family is now large enough that growth without rewiring is more dangerous than slow growth, but not every honest chain-layer clarification should be forced to pretend it needs a new checklist or payload template.
