# 635 — Official voter-information platform media authenticity-cue packet download print copy forward edit restrictions and non-governing wrapper-rights-state firewall

**Track:** Shared / Public surfaces

This document covers a narrow packet-wrapper problem:
**later packets can preserve “Can't download” settings, no-print / no-copy / no-forward restrictions, review-only or read-only usage limits, expiration-based use rights, IRM permission banners, permissions-password posture, or similar visible wrapper rights-state layers around same-route detached derivatives, and later readers can start mistaking that later rights posture for source-route official publication, source-route authorship, office adoption, legal finality, or the packet's governing member.**

## What this is for

Use `635` when a later packet preserves or reenacts a **visible wrapper rights-state layer** around same-route detached derivatives:
- “Can't download” or similar no-download posture,
- print-disabled / copy-disabled / forward-disabled posture,
- read-only / review-only / no-edit usage limits,
- permissions-password or restricted-permission posture,
- explicit per-recipient rights levels,
- expiration-based use rights,
- or similar later packet usage-rights / restriction posture.

Those rights surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added rights posture**, not automatic proof of:
- source-route official publication,
- source-route authorship,
- office adoption,
- legal finality,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded rights-state bridge.
Google Docs Editors Help says owners can prevent people from downloading, printing, or copying a file, can control which roles get those abilities, and warns that those limits apply within Google's surfaces rather than proving what others can never do with content.
Microsoft Support says SharePoint sharing can expose a visible `Can't download` right, and Office IRM can define Read / Change / Full Control permission levels, with default no-print / no-copy posture for some roles, plus expiration and restricted-use messaging.
Adobe Help says PDF security options and permissions passwords can control whether viewers can print, edit, or copy content.
That is enough for one bounded firewall here.
(xref: `google_docs_stop_limit_change_sharing_help_page`; xref: `microsoft_share_sharepoint_files_or_folders_help_page`; xref: `microsoft_restrict_access_documents_irm_word_help_page`; xref: `adobe_restrict_printing_editing_copying_pdfs_help_page`; xref: `adobe_pdf_security_options_help_page`)

`635` exists so maintainers can say:
**this packet preserved a later rights-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the rights layer itself does not silently prove source-route official publication, source-route authorship, office adoption, legal finality, or the governing member.**

## Why this is distinct

`619` asks whether a later packet preserved **access posture** — who could open, receive, or reach the file / link / audience scope.

`624` asks whether a later packet preserved **information posture** — owner/location/type fields, details panes, or file cards.

`626` asks whether a later packet preserved **action posture** — command bars, context menus, quick actions, or disabled commands as visible affordances.

`631` asks whether a later packet preserved **classification posture** — sensitivity labels, retention labels, policy tips, or message-bar labels.

`632` asks whether a later packet preserved **security posture** — suspicious-file warnings, blocked-file markers, protected-view shells, or trust-gated warnings.

`633` asks whether a later packet preserved **signature posture** — signature lines, validation badges, signer-certificate details, or audit-trail pages.

`634` asks whether a later packet preserved **workflow posture** — pending/approved/rejected state, approval sidebars, or publish-after-approval stages.

`635` asks a different question:
**did a later packet add or preserve a visible rights layer — no-download / no-print / no-copy / no-forward / review-only / read-only / expiring-rights posture — and did later readers start overreading that layer as if it proved source-route official publication, source-route authorship, office adoption, legal finality, or the packet's governing member?**

If the real problem is who can reach the file or link, use `619`.
If the real problem is owner/location/type details, use `624`.
If the real problem is visible buttons / menu items / affordances without a rights-policy claim, use `626`.
If the real problem is classification or retention labeling, use `631`.
If the real problem is warning / blocked / trust-gated security posture, use `632`.
If the real problem is signature / validation posture, use `633`.
If the real problem is approval / disposition workflow, use `634`.
Use `635` only when the missing distinction is **wrapper rights-state posture itself**.

## Decision test

Use `635` when all three conditions hold:

1. later evidence preserves or reenacts a **visible rights layer** around same-route detached derivatives — for example a `Can't download` control, no-print / no-copy / no-forward rule, read-only or review-only restriction, IRM permissions banner, expiration notice, or permissions-password posture;
2. that layer is **later wrapper-added rights state**, not proof that the underlying source route itself is officially published, officially authored, officially adopted, legally final, or governed by that visible rights state; and
3. later readers are drifting toward treating that layer as if it proved **source-route official publication, source-route authorship, office adoption, legal finality, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an access, information, action, classification, security, signature, or workflow problem with some visible rights posture around it, keep access in `619`, keep information in `624`, keep action posture in `626`, keep classification posture in `631`, keep security posture in `632`, keep signature posture in `633`, keep workflow posture in `634`, and add one bounded `635` rights-state note only if the visible rights layer itself changed the reading.

## Keep access, information, action, classification, security, signature, workflow, and rights state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added access state** — permissions, link scope, viewer/editor roles, or request-access posture (`619`);
5. **wrapper-added information state** — owner/location/type/details panes or file cards (`624`);
6. **wrapper-added action state** — command bars, context menus, quick actions, or disabled commands as affordance facts (`626`);
7. **wrapper-added classification state** — classification labels, sensitivity labels, retention labels, policy tips, message-bar labels, or similar protection badges (`631`);
8. **wrapper-added security state** — suspicious-file warnings, blocked-file markers, protected-view shells, trust prompts, or similar warning posture (`632`);
9. **wrapper-added signature state** — signature lines, validation badges, certificate details, eSignature status, audit-trail pages, or timestamp posture (`633`);
10. **wrapper-added workflow state** — submit-for-approval posture, pending/approved/rejected disposition, approval sidebars, approved versions, or publish-after-approval stages (`634`);
11. **wrapper-added rights state** — no-download / no-print / no-copy / no-forward / review-only / read-only / expiration-limited use posture (`635`);
12. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, desktop client, or other transport context (`437`, `490`, `600`);
13. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible rights-restriction layer as if it proved what the underlying source officially is, how authoritative it is, or whether the office adopted it as final; or
- letting a later rights wrapper become evidence that the packet itself is governance-bearing, office-issued, or authenticity-dispositive.

`635` exists so the archive can keep that later visible rights layer **truthful but non-governing**.

## Minimal wrapper-rights-state note grammar

When wrapper rights state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_rights_kind=<cant_download|cant_print|cant_copy|cant_forward|read_only|review_only|restricted_access|permissions_password|expires_on|mixed|unknown>; rights_scope=<viewer|commenter|reader|selected_people|link_holder|organization|mixed|unknown>; modification_rights=<none|comment_only|review_only|edit_allowed|mixed|unknown>; redistribution_rights=<download_blocked|copy_blocked|forward_blocked|print_blocked|mixed|unknown>; source_authorship_proved=<forbid>; official_publication_proved=<forbid>; office_adoption_proved=<forbid>; legal_finality_proved=<forbid>; governing_member_from_rights_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_635_when=<rights_state_changed_reading>; promote_wrapper_rights_state=<no>; basis=<why the later rights layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible usage-rights / restriction posture” without minting a new detached-derivative member or silently rewriting source publication, source authorship, office adoption, legal finality, or packet governance.

## Typical uses

1. **Can't-download overread**
   A later packet shows `Can't download` or similar visible restriction posture and later readers start retelling that setting as if it proved the underlying source route was draft, unofficial, or non-public in every relevant sense.
2. **No-print / no-copy overread**
   A later packet shows print-disabled or copy-disabled posture and later readers start treating that rights shell as if it proved legal finality, controlled dissemination by the office, or source-route authenticity.
3. **Read-only / review-only overread**
   A later packet shows review-only or read-only posture and later readers start treating that later restriction as if it proved the underlying source itself was final, adopted, or canonically frozen.
4. **IRM permission overread**
   A later packet shows restricted-permission / rights-managed posture, explicit Read / Change / Full Control framing, or an expiration date, and later readers start retelling that visible rights regime as if it governed the source route itself rather than one later wrapper around a detached derivative.
5. **Permissions-password overread**
   A later packet shows PDF permissions-password posture or similar restrictions and later readers start treating that later protection shell as if it proved the office published the visible packet as the governing or final artifact.

## When not to use this

Do **not** use `635` when:
- the decisive issue is still who can access or receive the route (`619`),
- the decisive issue is still owner/location/type/details metadata (`624`),
- the decisive issue is still buttons / affordances / disabled-command visibility without a rights-policy claim (`626`),
- the decisive issue is still classification or retention labeling (`631`),
- the decisive issue is still warning / blocked / trust-gated security posture (`632`),
- the decisive issue is still signature / validation posture (`633`),
- the decisive issue is still approval / disposition workflow (`634`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible rights layer leaves an ordinary access, information, action, classification, security, signature, or workflow problem, use the narrower doc and omit `635`.
If deleting it would erase **why a later rights / restriction layer changed the way the packet was being read or retold**, `635` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried no-download / no-print / no-copy / no-forward / read-only / review-only / expiring-rights posture.
Tighten `619`, `624`, `626`, `631`, `632`, `633`, `634`, `635`, or `600` first.
Only add another numbered doc when repeated wrapper-rights-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-rights-state note under `635`.
