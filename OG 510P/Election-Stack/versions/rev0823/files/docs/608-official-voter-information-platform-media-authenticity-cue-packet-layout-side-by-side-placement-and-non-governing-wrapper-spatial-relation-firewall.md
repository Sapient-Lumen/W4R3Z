# 608 — Official voter-information platform media authenticity-cue packet layout, side-by-side placement, and non-governing wrapper-spatial-relation firewall

**Track:** Shared / Public surfaces

This document defines a bounded control for **later packet-level spatial arrangement around same-route detached derivatives**:
side-by-side placement,
staggered or stacked positioning,
inset-over-main layouts,
grid or gallery rows,
split-screen comparison frames,
or similar later wrapper-added layout decisions that change **how preserved members sit next to, above, below, or inside each other on the packet surface** without proving that the official source route itself natively had that same adjacency, simultaneity, comparison posture, or governing layout.

It does not create a new authenticity cue family.
It adds one narrow rule:
**when a later packet places same-route detached derivatives into one chosen spatial layout, the archive should preserve that wrapper-layout fact honestly and should not quietly treat the resulting side-by-side, inset, gallery, or stacked placement as if it proved source-native adjacency, source-native simultaneity, source-native comparison framing, source priority, or the packet's governing member.**

## Why this exists (bounded)

The archive already distinguishes detached stills (`597`), copied text (`595`), copied metadata (`598`), clipped observation windows (`594`), mixed detached-derivative packets (`600`), short wrapper labels (`601`), longer wrapper summaries (`602`), wrapper-added emphasis markup (`603`), wrapper-added concealment (`604`), wrapper-added ordering (`605`), wrapper-added membership (`606`), and wrapper-added repetition (`607`).
A smaller but still important seam remains:
**a later packet can place same-route detached derivatives side by side, inset one inside another, tile them in a gallery row, or otherwise choose one spatial arrangement, and later readers can start narrating that wrapper layout as if it proved source-native adjacency, source-native simultaneity, source-native comparison framing, or source priority.**

Current primary-source guidance is specific enough to justify one compact bridge here.
Google Slides' current help says objects on a slide can be arranged in front of or behind each other, aligned, distributed, centered, rotated, grouped, and snapped to guides or a grid.
Microsoft's current support says objects can be aligned to each other or to the slide, distributed horizontally or vertically, and arranged on dynamic guides or the grid.
Apple's current Preview guidance says annotation shapes, highlights, zoom lenses, text boxes, signatures, notes, and crop frames can be dragged, resized, and repositioned where the reviewer wants.
(xref: `google_slides_insert_arrange_text_shapes_diagrams_lines_help_page`; xref: `microsoft_align_or_arrange_objects_help_page`; xref: `apple_preview_annotate_pdf_mac_help_page`)

That is enough to support one bounded maintainer rule:
**later packet layout is still only later packet layout.**
A side-by-side packet, inset packet, or gallery packet can honestly be the layout later readers encountered while still failing to prove that the source route itself natively put those members in that same relation or that one positioned member became the governing source object.
`608` exists so the archive can preserve that spatial-relation fact without quietly promoting packet-level layout into source-native relation.

## Keep source-derived content and wrapper-added layout separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **wrapper-added packet label** — filename, subject line, slide title, memo heading, or similar short later-added narrative (`601`);
7. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, memo-body summaries, or similar longer later packet narrative (`602`);
8. **wrapper-added markup/emphasis** — highlight boxes, circles, arrows, underlines, comment anchors, zoom lenses, ink, or similar later visual emphasis (`603`);
9. **wrapper-added concealment/suppression** — redactions, crop-hidden regions, hidden slides, hidden objects, or similar later visual withholding (`604`);
10. **wrapper-added ordering/sequence** — reordered slide order, reordered PDF page order, moved packet sections, or similar later arrangement (`605`);
11. **wrapper-added membership/composition** — imported slides, merged-page subsets, chosen attachments, appended packet members, or similar later included-member selection (`606`);
12. **wrapper-added repetition/multiplicity** — duplicated slides, repeated pages, repeated excerpts, repeated attachments, gallery-style repeats, or similar later same-member multiplication (`607`);
13. **wrapper-added layout/spatial relation** — side-by-side placement, inset-over-main placement, gallery rows, stacked columns, split-screen comparison framing, or similar later positioning (`608`);
14. **carrier wrapper** — slide deck, PDF memo, chat export, saved page, web archive, issue ticket, or other transport context (`437`, `490`, `600`);
15. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating wrapper-added layout as if it proved source-native adjacency, simultaneity, comparison posture, or priority, or
- letting the layout layer become the governing member instead of first classifying the surviving detached derivative.

`608` exists so the archive can keep that later spatial-relation layer **truthful but non-governing**.

This is a note contract, not a new schema.
It exists so packets and summaries can say “this packet later positioned preserved members into one chosen layout” without minting a new detached-derivative member or silently rewriting relation, simultaneity, or priority.

## Typical uses

1. **Side-by-side comparison overread**
   A packet places two same-route detached derivatives next to each other and later readers start retelling that side-by-side arrangement as if the source route itself natively presented them as a comparison pair.
2. **Inset-over-main overread**
   A packet places one detached still, text excerpt, or metadata block inside or on top of another preserved member and later readers start treating that inset relation as if the source route itself foregrounded that inner member.
3. **Gallery-row overread**
   A packet tiles several same-route members into one gallery or contact-sheet row and later readers start treating that layout as if the source route itself natively grouped those members in that exact adjacent posture.
4. **Split-screen overread**
   A packet uses a split-screen or before/after frame and later readers start treating that simultaneous-looking composition as if the source route itself natively displayed those members together.
5. **Stacked-priority overread**
   A packet uses top/bottom or large/small placement and later readers start treating that wrapper positioning as if it proved source-native priority or governing status.
