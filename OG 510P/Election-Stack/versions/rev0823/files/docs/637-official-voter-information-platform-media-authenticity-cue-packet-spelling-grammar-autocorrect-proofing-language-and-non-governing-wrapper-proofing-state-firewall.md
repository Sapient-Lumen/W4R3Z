## What this is for

Use `637` when a later packet preserves or reenacts a **visible proofing layer** around same-route detached derivatives:
- red/blue/green spelling or grammar underlines,
- Editor or proofing sidebars listing corrections or refinements,
- autocorrect substitutions or auto-replacement hints,
- “ignore,” “add to dictionary,” or personal-dictionary posture,
- proofing-language badges, detected-language posture, or section-language picks,
- grammar/style refinement hints that travel with a screenshot or packet,
- or similar later packet proofing posture.

Those proofing surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added proofing state**, not automatic proof of:
- source-native error,
- source-native correction,
- official terminology rulings,
- source language,
- office adoption,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded proofing-state bridge.
Google Docs Help says misspelled words are underlined in red, grammar suggestions are underlined in blue, suggestions can be accepted or ignored, and personal-dictionary choices can stop a term from being marked as misspelled; separate Google Docs Help says autocorrect substitutions can be turned off, removed, or permanently undone.
Microsoft Support says Word's Editor offers spelling, grammar, and style suggestions, can list corrections in the Editor pane, and lets reviewers set or automatically detect proofing language for selected text or for multi-language documents.
Apple's Pages and macOS guidance says spelling and grammar can be checked inside Pages, grammar errors are visibly underlined, and a document can be formatted for another language in a way that affects only that current document.
That is enough for one bounded firewall here.
(xref: `google_docs_check_spelling_grammar_help_page`; xref: `google_docs_manage_autocorrect_help_page`; xref: `microsoft_word_check_grammar_spelling_help_page`; xref: `microsoft_word_check_spelling_grammar_different_language_help_page`; xref: `apple_pages_check_spelling_grammar_help_page`; xref: `apple_pages_format_document_for_another_language_help_page`)

`637` exists so maintainers can say:
**this packet preserved a later proofing-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the proofing layer itself does not silently prove source-native error, source-native correction, official terminology rulings, source language, office adoption, or the governing member.**

## Why this is distinct

`603` asks whether a later packet preserved **wrapper markup** — manually added highlights, arrows, circles, underlines, zoom callouts, or similar packet-authored emphasis.

`617` asks whether a later packet preserved **revision posture** — tracked changes, suggestions, redlines, insert/delete proposals, or similar proposed edits.

`624` asks whether a later packet preserved **file-information posture** — details panes, properties dialogs, owner/location/size/type fields, or similar visible file metadata.

`626` asks whether a later packet preserved **action affordance posture** — command bars, context menus, “Accept,” “Ignore,” or similar command availability.

`637` asks a different question:
**did a later packet add or preserve a visible proofing layer — spelling underlines, grammar marks, autocorrect substitutions, proofing-language badges, personal-dictionary / ignore state, or similar language-check posture — and did later readers start overreading that layer as if it proved source-native error, source-native correction, official terminology rulings, source language, office adoption, or the packet's governing member?**

If the real problem is manual highlighting or annotation, use `603`.
If the real problem is tracked changes or a visible edit proposal, use `617`.
If the real problem is document properties or file metadata, use `624`.
If the real problem is which accept/ignore/change commands were available, use `626`.
Use `637` only when the missing distinction is **wrapper proofing-state posture itself**.

## Decision test

Use `637` when all three conditions hold:

1. later evidence preserves or reenacts a **visible proofing layer** around same-route detached derivatives — for example a red misspelling underline, a grammar mark, an Editor suggestion pane, a proofing-language badge, or an autocorrect replacement hint;
2. that layer is **later wrapper-added proofing state**, not proof that the underlying source route itself officially contained an error, officially adopted a correction, officially fixed terminology, officially changed language, or officially adopted the packet as governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native error, source-native correction, official terminology rulings, source language, office adoption, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a markup, revision, information, or action-affordance problem with some proofing posture around it, keep markup in `603`, keep revision state in `617`, keep information posture in `624`, keep action posture in `626`, and add one bounded `637` proofing-state note only if the visible proofing layer itself changed the reading.

## Keep markup, revision, information, action, and proofing state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added markup state** — manual highlights, arrows, circles, underlines, zoom callouts, or ink (`603`);
5. **wrapper-added revision state** — tracked changes, suggestions, insert/delete proposals, redlines, or replace-text posture (`617`);
6. **wrapper-added information state** — details panes, properties, owner/location/type/language fields, or similar visible file-information posture (`624`);
7. **wrapper-added action state** — accept/ignore/change affordances, menus, disabled actions, or similar visible control posture (`626`);
8. **wrapper-added proofing state** — spelling/grammar underlines, autocorrect substitutions, proofing-language picks, dictionary-ignore posture, or similar visible language-check posture (`637`);
9. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, desktop client, browser shell, email thread, or other transport context (`437`, `490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible proofing layer as if it proved what the underlying source officially said, how it was officially spelled, what language it officially used, or whether an office adopted a correction; or
- letting a later proofing wrapper become evidence that the packet itself is governance-bearing, source-corrective, or the governing member.

`637` exists so the archive can keep that later visible proofing layer **truthful but non-governing**.

## Minimal wrapper-proofing-state note grammar

When wrapper proofing state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_proofing_kind=<spelling_underline|grammar_underline|style_refinement|autocorrect_substitution|proofing_language_badge|dictionary_ignore_state|mixed|unknown>; proofing_scope=<document|selection|current_view|mixed|unknown>; proofing_language_binding=<none|selected_text|document_default|keyboard_language|auto_detect|mixed|unknown>; source_native_error_proved=<forbid>; source_native_correction_proved=<forbid>; official_terminology_ruling_proved=<forbid>; source_language_proved=<forbid>; office_adoption_proved=<forbid>; governing_member_from_proofing_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_637_when=<proofing_state_changed_reading>; promote_wrapper_proofing_state=<no>; basis=<why the later proofing layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried spelling / grammar / proofing posture” without minting a new detached-derivative member or silently rewriting source text, source language, source correction state, office adoption, or packet governance.

## Typical uses

1. **Spellcheck underline overread**
   A later packet shows a red or blue underline on a candidate name, office title, or date string, and later readers start retelling that mark as if it proved the official source itself published a typo or officially acknowledged one.
2. **Autocorrect overread**
   A later packet captures an automatic replacement or “always correct” suggestion and later readers start treating that substitution as if the source route itself officially changed wording or spelling.
3. **Proofing-language overread**
   A later packet shows a proofing-language selection or auto-detected language state and later readers start treating that viewer-side language posture as if it proved the source route's official language or reviewed translated edition.
4. **Style-refinement overread**
   A later packet shows an Editor/refinement pane suggesting concision, formality, or grammar changes and later readers start treating that pane as if it were a reviewed office correction or official terminology ruling.
5. **Dictionary/ignore absence misread**
   A local personal dictionary or ignore choice suppresses future misspelling marks and later readers start retelling the absence of underlines as if it disproved earlier proofing-state packets or proved the source spelling was officially accepted.

## When not to use this

Do **not** use `637` when:
- the decisive issue is still manual highlighting, circling, or annotation (`603`),
- the decisive issue is still tracked changes / suggestions / redlines (`617`),
- the decisive issue is still file information or properties (`624`),
- the decisive issue is still command visibility or action affordance posture (`626`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible proofing layer leaves an ordinary markup, revision, information, or action-affordance problem, use the narrower doc and omit `637`.
If deleting it would erase **why a later proofing / spellcheck / grammar layer changed the way the packet was being read or retold**, `637` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried spelling underlines, grammar marks, autocorrect suggestions, proofing-language picks, or personal-dictionary posture.
Tighten `603`, `617`, `624`, `626`, `637`, or `600` first.
Only add another numbered doc when repeated wrapper-proofing-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-proofing-state note under `637`.
