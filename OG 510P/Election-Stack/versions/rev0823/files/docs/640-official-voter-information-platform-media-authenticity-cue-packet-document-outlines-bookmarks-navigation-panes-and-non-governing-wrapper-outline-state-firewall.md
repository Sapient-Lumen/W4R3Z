## What this is for

Use `640` when a later packet preserves or reenacts a **visible wrapper outline-state layer** around same-route detached derivatives:
- document-outline sidebars,
- bookmark panels or bookmark trees,
- heading-navigation panes or document maps,
- table-of-contents sidebars,
- page/heading structure trees used for jump navigation,
- or similar later packet structural-navigation posture.

Those outline surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added structural-navigation posture**, not automatic proof of:
- source-native hierarchy,
- source-native completeness,
- source-native priority ordering,
- office-curated structure,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded outline-state bridge.
Google Docs Help says the document outline detects and lists headings, can be shown or hidden on the left, and can remove or re-add headings.
Microsoft Support says Word's Navigation pane lets viewers browse by headings or pages, highlights where they are, and can expose only headings that appear in supported places.
Adobe Help says a PDF bookmark is a representative-text link in the Bookmarks panel, that bookmarks are often generated automatically from table-of-contents entries, and that bookmark destinations can encode a particular view.
Apple Support says Pages generates an automatically updating table of contents in the left sidebar based on paragraph styles, and that the entries are links used to jump through the document.
That is enough for one bounded firewall here.
(xref: `google_docs_view_document_outlines_help_page`; xref: `microsoft_word_navigation_pane_help_page`; xref: `adobe_acrobat_page_thumbnails_bookmarks_pdfs_help_page`; xref: `apple_pages_create_table_of_contents_mac_help_page`)

`640` exists so maintainers can say:
**this packet preserved a later outline/bookmark/navigation layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the outline layer itself does not silently prove source-native hierarchy, source-native completeness, office-curated structure, or the governing member.**

## Why this is distinct

`598` asks whether a later packet preserved **copied metadata-like extracts** — titles, descriptions, chapter lists, or other detached labeling text.

`612` asks whether a later packet preserved **generic navigation posture** — hyperlinks, hotspots, internal jumps, or action buttons.

`615` asks whether a later packet preserved **active selection/focus posture** — the currently selected thumbnail, selected object, or selected sidebar item.

`625` asks whether a later packet preserved **file-list or collection posture** — sort order, filters, groups, visible columns, or saved views across multiple files.

`639` asks whether a later packet preserved **reader posture** — Reader View, simplified extraction, stripped chrome, or line-focus state.

`640` asks a different question:
**did a later packet add or preserve a visible outline/bookmark/navigation-tree layer — document outlines, bookmark panels, heading-navigation panes, table-of-contents sidebars, or similar structure maps — and did later readers start overreading that layer as if it proved source-native hierarchy, source-native completeness, office-curated priority ordering, or the packet's governing member?**

If the real problem is copied heading/chapter text standing on its own, use `598`.
If the real problem is links or hotspots, use `612`.
If the real problem is merely which sidebar item was active, use `615`.
If the real problem is a file list or saved collection view, use `625`.
If the real problem is simplified reading / Reader View posture, use `639`.
Use `640` only when the missing distinction is **wrapper outline-state posture itself**.

## Decision test

Use `640` when all three conditions hold:

1. later evidence preserves or reenacts a **visible outline/bookmark/navigation layer** around same-route detached derivatives — for example a document outline, bookmark panel, heading-navigation pane, document map, or table-of-contents sidebar;
2. that layer is **later wrapper-added structural-navigation state**, not proof that the underlying source route itself officially limited scope to what the pane lists, officially omitted what the pane omits, officially prioritized one branch of the tree, or officially made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native hierarchy, source-native completeness, source-native priority ordering, office-curated structure, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a metadata-extract problem, a generic link-path problem, an active-selection problem, a file-list problem, or a reader-state problem with some visible outline posture around it, keep copied structure text in `598`, keep generic navigation in `612`, keep selected-item emphasis in `615`, keep collection posture in `625`, keep simplified-reading posture in `639`, and add one bounded `640` outline-state note only if the visible structure layer itself changed the reading.

## Keep outline state, selection state, listing state, and reader state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added metadata/label extract** — copied heading/chapter/title text detached from the view (`598`);
5. **wrapper-added generic navigation state** — hyperlinks, hotspots, jump buttons, or click-path posture (`612`);
6. **wrapper-added selection/focus state** — active sidebar item, selected thumbnail, or selected node posture (`615`);
7. **wrapper-added information state** — details panes, owner/location/type, or file-card posture (`624`);
8. **wrapper-added listing state** — sort order, filters, groups, or collection framing across files (`625`);
9. **wrapper-added reader state** — Reader View, simplified extraction, stripped chrome, or line focus (`639`);
10. **wrapper-added outline state** — document outlines, bookmark panels, heading-navigation panes, document maps, or table-of-contents sidebars (`640`);
11. **carrier wrapper** — slide deck, PDF memo, doc shell, browser shell, saved page, ticket, or email thread (`437`, `490`, `600`);
12. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible outline/bookmark/navigation tree as if it proved the underlying source route itself officially excluded anything not shown in the tree; or
- letting a later structural sidebar become evidence that the packet itself is governance-bearing, office-curated, or the governing member.

`640` exists so the archive can keep that later visible structure layer **truthful but non-governing**.

## Minimal wrapper-outline-state note grammar

When wrapper outline state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_outline_kind=<document_outline|bookmark_panel|navigation_pane|document_map|toc_sidebar|mixed|unknown>; outline_basis=<heading_styles|auto_generated|manual_bookmarks|mixed|unknown>; structure_scope=<whole_member|heading_tree|bookmark_tree|page_tree|mixed|unknown>; source_hierarchy_proved=<forbid>; source_completeness_proved=<forbid>; source_priority_proved=<forbid>; office_curated_outline_proved=<forbid>; governing_member_from_outline_state=<forbid>; carrier_wrapper=<doc_shell|pdf_shell|browser_shell|review_shell|slide_deck|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_640_when=<outline_state_changed_reading>; promote_wrapper_outline_state=<no>; basis=<why the later outline layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried a document outline / bookmark tree / TOC sidebar” without minting a new detached-derivative member or silently rewriting source hierarchy, source completeness, office structure, or packet governance.

## Typical uses

1. **Outline-omission overread**
   A later packet shows a document outline or heading-navigation pane and later readers start retelling non-listed material as if it were absent from the source route rather than merely absent from that structural navigator.
2. **Bookmark-tree overread**
   A later packet shows a PDF bookmark panel and later readers start treating the bookmark tree as if it were the office's full reviewed hierarchy or canonical priority order for the derivative.
3. **TOC-sidebar overread**
   A later packet shows an automatically updating table-of-contents sidebar and later readers start treating that sidebar as if it were the source's own final public abstract or definitive table of contents.
4. **Navigation-pane priority overread**
   A later packet foregrounds a heading-navigation pane and later readers start treating the pane's branching order as if it proved source emphasis, source scope boundaries, or the packet's governing member.

## When not to use this

Do **not** use `640` when:
- the decisive issue is still copied heading/chapter/label text detached from the pane (`598`),
- the decisive issue is still generic links or hotspots (`612`),
- the decisive issue is still merely which node or sidebar item is active (`615`),
- the decisive issue is still a file list, saved view, or multi-file grouping (`625`),
- the decisive issue is still Reader View / simplified extraction / stripped chrome (`639`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible outline/bookmark/navigation layer leaves an ordinary metadata-extract, navigation, selection, listing, or reader-state problem, use the narrower doc and omit `640`.
If deleting it would erase **why a later document outline / bookmark panel / navigation tree changed the way the packet was being read or retold**, `640` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried a document outline, bookmark panel, heading-navigation pane, table-of-contents sidebar, or similar structure map.
Tighten `598`, `600`, `612`, `615`, `625`, `639`, or `640` first.
Only add another numbered doc when repeated wrapper-outline-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-outline-state note under `640`.
