# 636 — Official voter-information platform media authenticity-cue packet watermarks confidentiality overlays viewer-email burn-ins and non-governing wrapper-watermark-state firewall

## What this is for

Use `636` when a later packet preserves or reenacts a **visible watermark layer** around same-route detached derivatives:
- text or image watermarks behind page content,
- diagonal `CONFIDENTIAL` / `DRAFT` / ownership overlays,
- viewer-email or participant-email dynamic watermarks,
- repeated anti-leak burn-ins,
- playback-time watermarks on meeting recordings,
- overlaid marks on shared-content capture shells,
- or similar later packet watermark posture.

Those watermark surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added watermark state**, not automatic proof of:
- source-route official publication,
- source-route authorship,
- source-native classification,
- office adoption,
- legal finality,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded watermark-state bridge.
Google Docs Help says watermarks can be text or image, appear behind the text, repeat on every page, and can later be edited or removed.
Microsoft Learn says sensitivity-label content markings such as headers, footers, and watermarks are added directly to the content and remain visible until someone modifies or deletes them; the same guidance says dynamic watermarks can display the email address of the user currently opening the document and cannot be changed or removed without removing the label or exporting if allowed.
Microsoft Teams guidance says watermark-enabled meetings can overlay each participant's email address on shared content or video, and meeting recordings show the viewer's own email address as a watermark at playback time even though downloaded `.mp4` files do not contain that watermark.
Adobe Help says Acrobat watermarks are fixed text or images embedded into pages to indicate ownership, display branding, or mark content as confidential.
That is enough for one bounded firewall here.
(xref: `google_docs_insert_edit_delete_watermarks_help_page`; xref: `microsoft_manage_sensitivity_labels_office_apps_help_page`; xref: `microsoft_require_watermark_sensitive_teams_meetings_help_page`; xref: `adobe_add_watermarks_pdfs_help_page`)

`636` exists so maintainers can say:
**this packet preserved a later watermark-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the watermark layer itself does not silently prove source-route official publication, source-route authorship, source-native classification, office adoption, legal finality, or the governing member.**

## Why this is distinct

`610` asks whether a later packet preserved **styling or tone posture** — themes, palette shifts, font/background restyling, warning-looking visual treatment, or other packet-level tone.

`631` asks whether a later packet preserved **classification posture** — sensitivity labels, retention labels, policy tips, or message-bar labels.

`632` asks whether a later packet preserved **security posture** — suspicious-file warnings, blocked-file markers, protected-view shells, or trust-gated warning bars.

`635` asks whether a later packet preserved **rights posture** — no-download / no-print / no-copy / read-only / review-only / expiring-rights controls.

`636` asks a different question:
**did a later packet add or preserve a visible watermark layer — text/image watermarks, confidentiality overlays, viewer-email burn-ins, repeated anti-leak marks, playback-time watermarks, or similar overlaid ownership/classification/deterrence posture — and did later readers start overreading that layer as if it proved source-route official publication, source-route authorship, source-native classification, office adoption, legal finality, or the packet's governing member?**

If the real problem is warning or trust-gated security posture, use `632`.
If the real problem is a sensitivity/retention label or policy-tip regime, use `631`.
If the real problem is explicit download/print/copy/edit restriction posture, use `635`.
If the real problem is ordinary tone or visual styling without watermark-specific semantics, use `610`.
Use `636` only when the missing distinction is **wrapper watermark-state posture itself**.

## Decision test

Use `636` when all three conditions hold:

1. later evidence preserves or reenacts a **visible watermark layer** around same-route detached derivatives — for example a repeated `CONFIDENTIAL` overlay, a viewer-email watermark, a diagonal ownership mark, or playback-time watermarking on a recording;
2. that layer is **later wrapper-added watermark state**, not proof that the underlying source route itself is officially published, officially authored, natively classified the same way, officially adopted, or legally final in virtue of that watermark alone; and
3. later readers are drifting toward treating that layer as if it proved **source-route official publication, source-route authorship, source-native classification, office adoption, legal finality, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a styling, classification, security, rights, signature, or workflow problem with some visible watermark posture around it, keep styling in `610`, keep classification in `631`, keep security in `632`, keep rights in `635`, keep signature in `633`, keep workflow in `634`, and add one bounded `636` watermark-state note only if the visible watermark layer itself changed the reading.

## Keep styling, classification, security, rights, signature, workflow, and watermark state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added styling state** — themes, palettes, tone-coding, or other general visual treatment (`610`);
5. **wrapper-added classification state** — classification labels, sensitivity labels, retention labels, policy tips, or message-bar labels (`631`);
6. **wrapper-added security state** — suspicious-file warnings, blocked-file markers, protected-view shells, trust prompts, or similar warning posture (`632`);
7. **wrapper-added signature state** — signature lines, validation badges, certificate details, eSignature status, audit-trail pages, or timestamp posture (`633`);
8. **wrapper-added workflow state** — submit-for-approval posture, pending/approved/rejected disposition, approval sidebars, approved versions, or publish-after-approval stages (`634`);
9. **wrapper-added rights state** — no-download / no-print / no-copy / no-forward / review-only / read-only / expiration-limited use posture (`635`);
10. **wrapper-added watermark state** — text/image watermarks, confidentiality overlays, viewer-email burn-ins, repeated anti-leak marks, or playback-time overlaid identity posture (`636`);
11. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, meeting recording playback shell, desktop client, or other transport context (`437`, `490`, `600`);
12. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible watermark layer as if it proved what the underlying source officially is, how it was classified, who authored it, or whether the office adopted it as final; or
- letting a later watermark wrapper become evidence that the packet itself is governance-bearing, authenticity-dispositive, or the governing member.

`636` exists so the archive can keep that later visible watermark layer **truthful but non-governing**.

## Minimal wrapper-watermark-state note grammar

When wrapper watermark state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_watermark_kind=<text_watermark|image_watermark|confidentiality_overlay|ownership_mark|dynamic_email_watermark|participant_email_overlay|playback_watermark|mixed|unknown>; watermark_scope=<document_page|slide_page|shared_content|video_feed|recording_playback|mixed|unknown>; watermark_binding=<none|label_applier|current_viewer|meeting_participant|mixed|unknown>; source_authorship_proved=<forbid>; official_publication_proved=<forbid>; source_native_classification_proved=<forbid>; office_adoption_proved=<forbid>; legal_finality_proved=<forbid>; governing_member_from_watermark_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|meeting_player|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_636_when=<watermark_state_changed_reading>; promote_wrapper_watermark_state=<no>; basis=<why the later watermark layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible watermark / overlay posture” without minting a new detached-derivative member or silently rewriting source-route publication, authorship, classification, adoption, legal finality, or packet governance.

## Typical uses

1. **Confidential-overlay overread**
   A later packet shows a large diagonal `CONFIDENTIAL` or `DRAFT` overlay and later readers start retelling that watermark as if it proved the underlying source route itself was officially classified that way or was never officially published.
2. **Viewer-email deterrence overread**
   A later packet shows the current viewer's email address as a dynamic watermark and later readers start treating that overlay as if it proved source authorship, official recipient scoping, or the governing route.
3. **Meeting-playback watermark overread**
   A later packet is captured from a watermarked meeting recording playback shell and later readers start treating that playback-time watermark as if it were embedded source-native media content or a proof that all downloadable copies carried the same mark.
4. **Ownership/branding watermark overread**
   A later packet preserves a visible ownership or branding watermark and later readers start treating it as if it proved the office authored or officially adopted the underlying source route.
5. **Watermark absence misread**
   A later downloadable copy or exported derivative lacks a watermark that was visible in playback or in a labeled shell, and later readers start retelling that absence as if it disproved the earlier watermark-state packet instead of recognizing a wrapper-state difference.

## When not to use this

Do **not** use `636` when:
- the decisive issue is still ordinary theme/color/tone styling without watermark-specific semantics (`610`),
- the decisive issue is still classification or retention labeling (`631`),
- the decisive issue is still warning / blocked / trust-gated security posture (`632`),
- the decisive issue is still signature / validation posture (`633`),
- the decisive issue is still approval / disposition workflow (`634`),
- the decisive issue is still no-download / no-print / no-copy / no-forward / review-only / read-only restriction posture (`635`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible watermark layer leaves an ordinary styling, classification, security, signature, workflow, or rights problem, use the narrower doc and omit `636`.
If deleting it would erase **why a later watermark / overlay layer changed the way the packet was being read or retold**, `636` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried `CONFIDENTIAL` overlays, viewer-email deterrence watermarks, branding marks, ownership marks, or playback-time identity burn-ins.
Tighten `610`, `631`, `632`, `633`, `634`, `635`, `636`, or `600` first.
Only add another numbered doc when repeated wrapper-watermark-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-watermark-state note under `636`.
