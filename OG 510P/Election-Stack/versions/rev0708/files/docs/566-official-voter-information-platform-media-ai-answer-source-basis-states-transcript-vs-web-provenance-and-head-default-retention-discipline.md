# 566 — Official voter-information platform media AI-answer source-basis states, transcript-vs-web provenance, and head/default retention discipline

**Track:** Shared

This document gives the recent platform-media chain layer one more compact rule.

It exists because the archive already knows how to separate:
- the underlying media object itself (`369` and `528–529`),
- player-native AI answer modules as public-answer boundaries (`499`),
- AI-pane open/summary/answer-visible state inside the same object (`562`),
- AI question-thread carryover and prompt-origin ownership inside the same object (`563`),
- AI-answer output-language state inside the same object (`564`),
- AI-answer grounding/reference state inside the same object (`565`),
- official language-selector and machine-translation boundaries on the surrounding route (`377`),
- transcript-pane, searchable-transcript, and jump affordances around the recording (`493`, `494`, `544`, `557`),
- browser/page AI-answer boundaries outside the player (`386`, `486`),
- derivative-readiness / transcript-prerequisite lag (`561`),
- and head-first citation / historical-leg scoping inside one same-object chain (`530`).

A smaller ambiguity still remains:
**what should the archive do when the same media object stays current, the AI-answer surface, pane, thread, language, and grounding state are already understood, but the visible answer is documented or disclosed as drawing on a transcript-only basis, a platform-and-web basis, or an unclear/not-disclosed basis — and that source-basis fact starts to look like a new authority object, a safer citation target, or a reason to collapse same-object platform AI back into `499` every time?**

This document answers that narrow question.

## Why this exists (bounded)

Current official platform help already shows that player-native video-answer tools do **not** all claim the same answer basis.
YouTube's current conversational-AI help says responses are generated by large language models using information from YouTube and the web.
Vimeo's current Ask AI guidance says the tool generates answers to questions about the video, says viewers may ask about scenes, objects, or slides not limited to transcript text, and its video-page guidance says answers are based on the video transcript.
Microsoft's current Clipchamp Copilot support says the tool answers based on information in the transcript, and its FAQ says Copilot only reads the first transcript generated for the video.
(xref: `youtube_conversational_ai_tool_help_page`; xref: `vimeo_ai_ask_questions_about_videos_help_page`; xref: `vimeo_video_page_help_page`; xref: `microsoft_clipchamp_copilot_video_player_support_page`; xref: `microsoft_clipchamp_copilot_video_player_faq_page`)

That means one same-object chain can truthfully contain all of the following at once:
- one current controlling head,
- one AI pane already governed by `499` and `562`,
- one thread-state note already governed by `563`,
- one answer-language note already governed by `564`,
- one grounding note already governed by `565`,
- one answer card whose platform documentation says it is transcript-only or platform-and-web in basis,
- and no new office-published explanation route at all.

Without a compact rule here, reviewers tend to make one of four mistakes:
- they keep answer-basis facts trapped in `499` as if every later packet had to re-argue the whole public-answer boundary,
- they flatten source-basis facts into `565` even when visible grounding cues are already understood,
- they flatten same-video scene/object/slide basis facts into `566` even when the answer never left the media object and the real ambiguity is narrower than transcript-vs-web,
- they treat a transcript-only or platform-and-web disclosure as if it were itself a safer citation lane than the controlling head,
- or they omit the provenance fact entirely and later cannot explain why one same-object AI answer looked more like transcript compression while another looked more like a web-augmented synthesis.

This document fixes that bounded ambiguity.
It standardizes one small note for **same-object AI-answer source-basis state + head/default retention**.

## This is not the same thing as `386`, `486`, `493`, `499`, `561`, `562`, `563`, `564`, `565`, or `574`

`386` governs off-platform AI answer surfaces before the voter reaches the official player.

`486` governs browser-integrated page/context AI summaries around already-open web pages or documents.

`493` governs transcript panes and transcript sidecars around the same media object.

`499` governs player-native AI answer modules as public-answer boundaries around already-open official media.

`561` governs whether transcript-ready, caption-ready, chapter-ready, replay-ready, or other ordinary same-object derivatives are still settling.

`562` governs whether the AI pane is open, summary-focused, suggested-question-focused, or currently shows an answer card.

`563` governs whether the visible answer is fresh, follow-up-conditioned, or visibly reset, and it owns prompt-origin ownership.

`564` governs whether the visible answer stayed in the source language, appeared in translated output, or mixed languages.

`565` governs whether the visible answer exposed linked grounding, weaker/nonlinked grounding, or no visible grounding.

`574` governs the narrower same-video scene/object/slide basis question when the answer may use non-transcript material from the same media object without becoming a web-augmentation claim.

`566` is different.
It says that sometimes one same-object chain should keep:
- one full-object current head or fallback anchor,
- plus one **AI-answer source-basis note** such as `transcript_only_basis`, `platform_and_web_basis`, or `basis_not_disclosed`,
- while recording that the generated answer was documented or disclosed as drawing from one answer-basis posture rather than another **without** creating a new reviewed citation lane, a new head, or a new authority object.

If the decisive issue is that the voter encountered an AI answer surface before reaching the official player, use `386`.
If the decisive issue is browser/page AI summarization over an already-open page, use `486`.
If the decisive issue is that transcript generation or other derivatives were still settling, use `561`.
If the decisive issue is merely which AI pane state was visible, use `562`.
If the decisive issue is prompt/thread conditioning, use `563`.
If the decisive issue is answer-language mode, use `564`.
If the decisive issue is visible grounding/reference cues, use `565`.
If the decisive issue is the narrower same-video scene/object/slide basis question, use `574`.
Use `566` only when the surface, pane, thread, language, grounding, and answer outcome/disposition state are already understood but the archive still needs to classify the **same-object AI-answer source-basis/provenance state** inside an already-governed media chain.

## Default rule: preserve source-basis truth, but keep control with the head

Inside one `528` same-object chain, reviewers MAY keep a compact **AI-answer source-basis note** when all of the following hold:

1. **The underlying object is still the same.**
   Playback stayed within the same office-controlled event, recording, or published media answer.
2. **The practical difference is answer-basis posture, not a new publication.**
   The decisive fact is that the visible answer is documented or disclosed as transcript-only, platform-and-web, or not-disclosed/unclear inside the same AI surface.
3. **Treating the basis posture as a new route would mislead.**
   A reader could mistake a transcript-only disclosure or platform-and-web disclosure for a safer citation target, a new current route, or the office's own reviewed explanation posture.
4. **A better present-tense default still exists or the chain is honestly headless.**
   `529` and `530` can still name the current head, or `533` can honestly say no public media head exists and point to the best fallback anchor instead.
5. **The provenance fact still matters.**
   The archive would lose useful truth if it omitted whether the observed AI answer was documented or disclosed as transcript-only, platform-and-web, or not clearly disclosed while the same object still controlled.

When those conditions hold, keep the head/default under `529–530`, keep any AI-answer-surface boundary fact under `499`, keep any pane-state fact under `562`, keep any thread-state fact under `563`, keep any answer-language fact under `564`, keep any grounding/reference fact under `565`, keep any transcript-sidecar or derivative-readiness fact under `493` or `561`, and add one `566` AI-answer source-basis note.
Do **not** silently promote answer-basis posture into the chain's current head.

## Minimal AI-answer source-basis grammar

When a same-object chain has a current head or fallback anchor plus a meaningful AI-answer source-basis state, reviewers SHOULD prefer one line in this shape:

`chain=<stable object label>; head=<current tuple|none>; source_basis_state=<platform_and_web_basis|transcript_only_basis|basis_not_disclosed|basis_unclear|unknown>; provenance_basis=<platform_help_disclosure|video_page_help_text|faq_limit_note|unclear|unknown>; cite_default=<head|fallback anchor>; cite_source_basis_when=<transcript-only claim, platform-and-web claim, or why answer-basis did not become a safer citation lane>; promote_source_basis=<no>; basis=<why the answer-basis state mattered without becoming the public default>`

This is a compact note contract, not a new schema field.
It exists so packet notes can preserve **what the same AI answer layer was documented or disclosed as drawing on** without making every transcript-only or web-augmented answer sound like a new authority object or a safer citation target than the head.

`header_pick_order=<platform_and_web_basis|transcript_only_basis|basis_not_disclosed|basis_unclear|unknown>`

`detail_pick_order=<platform_and_web_basis|transcript_only_basis|basis_not_disclosed|basis_unclear|unknown>`

For packet headers, that winner order means the carried `566` token should prefer the most reconstructively specific disclosed basis: platform-and-web outranks transcript-only, which outranks a not-disclosed basis, which outranks a merely unclear one. If one extra same-doc `566` residue fact still matters after the header winner is chosen, use the first applicable token from `detail_pick_order=<...>` that is not already carried for `566`. The losing co-true provenance facts still belong in scoped prose or one short `528` note when they matter; the winner/order pair exists only to keep one-line packet headers and one-line same-doc residue stable.

## When to use an AI-answer source-basis note

Typical uses include:

1. **Transcript-only answer basis, same controlling object**
   The same head still controls, but the archive needs to preserve that the observed AI answer was documented as transcript-based rather than as a broader web synthesis.
2. **Platform-and-web answer basis, same controlling object**
   The same object stayed current, but later reviewers need to preserve that the answer basis was documented as drawing on platform content plus the web rather than as transcript-only compression.
3. **Not-disclosed or unclear basis is itself the bounded truth**
   The same object stayed current, but the archive needs to preserve that no sufficiently specific answer-basis disclosure was visible or documented for the observed answer state.
4. **Source-basis note plus grounding/language/thread note**
   The archive may need `566` plus `565` when the same answer exposed linked grounding but the more specific ambiguity is still whether the answer was transcript-only or platform-and-web; it may need `566` plus `564` when the answer was both translated and transcript-only; and it may need `566` plus `563` when the answer was both follow-up-conditioned and platform-and-web. Keep those facts separate instead of letting grounding, language, or thread notes absorb provenance semantics.
5. **Source-basis note plus derivative-readiness note**
   The archive may need `566` plus `561` when the practical answer basis only became transcript-usable after transcript generation settled; once the readiness question is already preserved, `566` can carry the later provenance fact without pretending that answer-basis posture became a new route.

## Citation rule

By default, later notes SHOULD still cite the **current controlling head** under `530`, or the fallback anchor if the chain is headless under `533`.
A `566` AI-answer source-basis note SHOULD be cited only when the later claim is specifically about:
- whether the visible or documented AI answer basis was transcript-only, platform-and-web, not disclosed, or unclear,
- whether that source-basis posture shaped what looked like the practical answer on the same object,
- whether the archive refused to treat a provenance disclosure as a safer citation lane than the head,
- or why answer-basis state did **not** outrank the head-first citation rule.

That means `566` preserves one honest answer-provenance exception to head-first citation without letting transcript-only or web-augmented answer posture quietly become the archive's present-tense authority object.

## When not to use this

Do **not** use `566` when:
- the decisive issue is off-platform AI retrieval or synthesis before the player opens — use `386`,
- the decisive issue is browser/page AI summarization over an already-open page rather than a player-native video-answer layer — use `486`,
- the decisive issue is transcript-pane visibility, transcript search, or copyable transcript text — use `493` or `557`,
- the decisive issue is the AI answer module as a public-answer boundary in the first place — use `499`,
- the decisive issue is merely that the AI pane was open, summary-focused, or answer-visible — use `562`,
- the decisive issue is prompt/thread conditioning rather than answer-basis provenance — use `563`,
- the decisive issue is answer-language mode rather than answer-basis provenance — use `564`,
- the decisive issue is visible grounding/reference state rather than answer-basis provenance — use `565`,
- the decisive issue is answer outcome/disposition rather than answer-basis provenance — use `567`,
- or the archive is trying to preserve every long generated answer body, model name, or other high-volume implementation detail beyond what bounded reconstruction requires.

If deleting the provenance fact would erase **what the same generated answer was documented or disclosed as drawing on**, `566` is probably the right companion. If the missing fact is instead whether the interaction returned an answer at all, or ended in a scope-limited / prerequisite-missing / retry no-answer state, use `567`.
If deleting that fact would erase the whole public-answer boundary or transcript/jump routing story, the problem probably belongs elsewhere.

## Tie-breaker when reviewers ask “if the tool says what it draws on, why isn't that the head?”

Ask three questions:
- does the observed source-basis state prove **what the same generated answer was documented or disclosed as drawing on** rather than **what the archive says controls for the ordinary public now**,
- would a head-first summary become less accurate if it defaulted to the provenance disclosure instead of the controlling head,
- and is the missing fact really about answer-basis provenance rather than pane state, prompt/thread conditioning, answer-language mode, visible grounding, transcript readiness, or the public-answer boundary itself?

If yes, keep current control under `529–530`, preserve any AI-answer-surface boundary fact under `499`, preserve any pane-state fact under `562`, preserve any thread-state fact under `563`, preserve any answer-language fact under `564`, preserve any grounding/reference fact under `565`, preserve any transcript/derivative issue under `493` or `561`, and record the source-basis state under `566`.
Do **not** let provenance disclosure absorb chain control.

## Promotion rule

Future media additions should usually **not** be promoted just because the same AI answer was documented as transcript-only or platform-and-web.
Tighten `566` first.
Only add another numbered surface when the ambiguity is really about a new public-answer boundary, a new transcript/jump route, or a new authority object rather than about **AI-answer source-basis/provenance state inside an already-governed same-object media chain**.
