# 554 — Official voter-information platform media metadata-wrapper drift, playlist-local relabeling, and head-default-retention discipline

**Track:** Shared

This document gives the recent platform-media chain layer one more compact rule.

It exists because the archive already knows how to separate:
- the underlying media object itself (`369` and `528–529`),
- mutable media-metadata wrapper risk as a public surface (`514`),
- collection and playlist routing (`507`),
- search/discovery or copied-wrapper entry (`510–511`),
- source-identity and policy wrappers (`520–521`),
- and saved/offline re-entry through viewer-managed shelves (`553`).

A smaller ambiguity still remains:
**what should the archive do when the same media object stays current, but its surrounding title, description, thumbnail, poster, or playlist-local display label changes across time or container context — and that wrapper drift starts to look like a new current route, a new reviewed edition, or a safer citation target than the controlling head?**

This document answers that narrow question.

## Why this exists (bounded)

Current official platform help already shows that the same media object can stay current while its **metadata wrapper state** changes around it.
YouTube says viewers usually first see the thumbnail and title before deciding whether to watch, and that creators can edit a video's title and description after upload.
Vimeo says creators can update a video's title and description from the video settings page and can replace or choose a different thumbnail image.
Microsoft says uploaded videos can use autogenerated or custom thumbnails, and that playlist-local displayed titles can be edited without automatically inheriting later source-file metadata changes.
(xref: `youtube_thumbnail_title_tips_help_page`; xref: `youtube_edit_video_settings_help_page`; xref: `vimeo_update_video_title_description_help_page`; xref: `vimeo_change_video_thumbnail_help_page`; xref: `microsoft_clipchamp_custom_thumbnail_help_page`; xref: `microsoft_video_playlists_onedrive_sharepoint_help_page`; xref: `microsoft_sharepoint_video_thumbnail_help_page`)

That means one same-object chain can truthfully contain all of the following at once:
- one current controlling head,
- one mutable wrapper state that really changed what a viewer first saw,
- one container-local display label or thumbnail that differed from another presentation of the same object,
- and no new office-published route at all.

Without a compact rule here, reviewers tend to make one of four mistakes:
- they treat a retitled row, revised description, or changed thumbnail as if the office published a new current route,
- they collapse metadata-wrapper drift into `514` even when the decisive issue is no longer whether wrappers are a bounded public-surface family but whether the same-object chain needs one wrapper-state note,
- they let a playlist-local label or fresh-looking thumbnail quietly become the citation-safe present-tense default,
- or they leave the wrapper drift out entirely and later cannot explain why two captures of the same current object looked differently labeled while the head never changed.

This document fixes that bounded ambiguity.
It standardizes one small note for **same-object metadata-wrapper drift + head/default retention**.

## This is not the same thing as `514`, `507`, `510`, `520`, `521`, or `553`

`514` governs whether mutable titles, descriptions, thumbnails, posters, or playlist-local labels became a public-surface authority problem in the first place.

`507` governs whether a channel home, showcase, playlist, or other office-curated collection became the practical router.

`510` governs whether ranked search, homepage, or browse-feed discovery became the practical router before the viewer opened the media.

`520` governs whether bylines, handles, badges, profile names, or other source-identity cues became the whole proof of officialness.

`521` governs whether platform-added information panels, disclosure labels, ratings, or other policy/context wrappers became the whole explanation of authority or currentness.

`553` governs saved-shelf or offline-library re-entry when the same object resurfaced through Watch Later, a saved playlist entry, or another kept library path.

`555` governs same-object collection context when the same object is opened inside playlist/showcase/list-view context and the real ambiguity is the collection-bearing shell rather than the wrapper wording itself.

`554` is different.
It says that sometimes one same-object chain should keep:
- one full-object current head or fallback anchor,
- plus one or more **metadata-wrapper-state notes** such as retitled-same-object, redescribed-same-object, rethumbnailed-same-object, playlist-local-relabel, or container-local metadata drift,
- while recording that those wrapper states changed first-contact labeling **without** creating a new published route, a new head, or a safer citation target than the controlling head.

If the decisive issue is whether metadata wrappers became unsafe as a public-answer surface at all, use `514`.
If the decisive issue is whether the collection, discovery surface, or policy/identity wrapper itself did the routing, use `507`, `510`, `520`, or `521`.
If the decisive issue is a saved/offline reopen path, use `553`.
Use `554` only when the wrapper family is already understood but the archive still needs to classify the **same-object metadata-wrapper state** inside an already-governed media chain.

## Default rule: preserve wrapper truth, but keep control with the head

Inside one `528` same-object chain, reviewers MAY keep a compact **metadata-wrapper-state note** when all of the following hold:

1. **The underlying object is still the same.**
   The route still resolves to the same office-controlled recording, livestream archive, or published media answer.
2. **The practical difference is wrapper state, not a new publication.**
   The decisive fact is that the viewer encountered a changed title, changed description, changed thumbnail/poster, playlist-local label, or another bounded metadata-wrapper drift.
3. **Treating the state as a new route would mislead.**
   A reader could mistake wrapper wording or imagery for a new current head, a newly reviewed edition, or a distinct publication route.
4. **A better present-tense default still exists or the chain is honestly headless.**
   `529` and `530` can still name the current head, or `533` can honestly say no public media head exists and point to the best fallback anchor instead.
5. **The wrapper fact still matters.**
   The archive would lose useful truth if it omitted what label/thumbnail/description a viewer actually saw first, whether a playlist-local row drifted from the source object, or why two captures of the same object carried different wrapper claims while the same head still controlled.

When those conditions hold, keep the head/default under `529–530`, keep any authority-boundary fact under `514`, keep any collection/discovery/wrapper-routing fact under `507`, `510`, `520`, or `521`, keep any saved/offline re-entry fact under `553`, and add one `554` metadata-wrapper-state note.
Do **not** silently promote the changed wrapper into the chain's current head.

## Minimal metadata-wrapper-state grammar

When a same-object chain has a current head or fallback anchor plus a meaningful wrapper drift, reviewers SHOULD prefer one line in this shape:

`chain=<stable object label>; head=<current tuple|none>; metadata_aliases=<wrapper family>; metadata_class=<retitled_same_object|redescribed_same_object|rethumbnailed_same_object|playlist_local_relabel|container_local_metadata_drift|mixed_wrapper_drift>; wrapper_scope=<source_page|playlist_row|collection_row|embed_shell|search_card|mixed>; cite_default=<head|fallback anchor>; cite_metadata_when=<wrapper-wording, first-contact-label, playlist-local display-label, or thumbnail/poster claim>; promote_metadata=<no>; basis=<why the wrapper drift mattered without becoming the public default>`

This is a compact note contract, not a new schema field.
It exists so packet notes can preserve **which labeling or thumbnail state the viewer actually encountered** without making every metadata edit sound like a fresh publication or a safer citation target than the head.

## When to use a metadata-wrapper-state note

Typical uses include:

1. **Same recording, new title/description wrapper**
   The current head still controls, but the archive needs to record that a later or container-specific title/description changed what viewers were told the same object was about.
2. **Same recording, different thumbnail/poster**
   The same object is still current, but a fresh-looking poster or chosen frame materially changed first-contact currentness cues.
3. **Same object, playlist-local relabeling**
   The same source object stays current, but a playlist row or collection entry displays a different label than the source page and that first-contact drift matters.
4. **Metadata wrapper drift intertwined with collection context, saved-shelf, discovery, or identity/policy wrappers**
   The archive may need `554` plus `555`, `553`, `507`, `510`, `520`, or `521` when the same object is open inside playlist/showcase/list-view context, resurfaced from a saved shelf, or carried discovery/identity/policy wrappers alongside changed metadata. Keep those facts separate instead of letting one note absorb the others.

## Citation rule

By default, later notes SHOULD still cite the **current controlling head** under `530`, or the fallback anchor if the chain is headless under `533`.
A `554` metadata-wrapper-state note SHOULD be cited only when the later claim is specifically about:
- what title, description, thumbnail, poster, or playlist-local label a viewer actually saw,
- whether a wrapper drifted between source-page and container-local presentations of the same object,
- whether first-contact labeling or imagery overstated currentness/scope while the same object still controlled,
- or why the archive refused to let wrapper drift outrank the head-first citation rule.

That means `554` preserves one honest wrapper-state exception to head-first citation without letting metadata edits quietly become the archive's present-tense authority object.

## When not to use this

Do **not** use `554` when:
- the decisive issue is whether metadata wrappers became an authority-boundary problem at all — use `514`,
- the decisive issue is the collection/discovery router that put the object in front of the viewer — use `507` or `510`,
- the decisive issue is source-identity or platform-policy chrome rather than metadata wording/imagery — use `520` or `521`,
- the decisive issue is a saved/offline reopen path — use `553`,
- or the archive is trying to preserve a whole moderation/admin history rather than the bounded public wrapper state a voter could actually encounter.

If deleting the wrapper fact would erase **what first-contact label or imagery the viewer actually saw around the same current object**, `554` is probably the right companion.
If deleting that fact would erase the whole authority-boundary or routing story, the problem probably belongs elsewhere.

## Tie-breaker when reviewers ask “if viewers saw that title/thumbnail first, why isn't that the head?”

Ask three questions:
- does the changed wrapper prove **how the same object was presented first** rather than **what the archive says controls for the ordinary public now**,
- would a head-first summary become less accurate if it defaulted to a changed label, poster, or playlist-local row title,
- and is the missing fact really about metadata-wrapper state rather than about collection routing, identity proof, policy chrome, or saved/offline re-entry?

If yes, keep current control under `529–530`, preserve any authority-boundary or routing fact under `514`, `507`, `510`, `520`, `521`, or `553`, and record the wrapper drift under `554`.
Do **not** let metadata-wrapper state absorb chain control.

## Promotion rule

Future media additions should usually **not** be promoted just because the same object exposed another changed title, thumbnail, poster, or playlist-local label.
Tighten `554` first.
Only add another numbered surface when the ambiguity is really about a new route class, a new public surface, or a new authority object rather than about **metadata-wrapper state inside an already-governed same-object media chain**.
