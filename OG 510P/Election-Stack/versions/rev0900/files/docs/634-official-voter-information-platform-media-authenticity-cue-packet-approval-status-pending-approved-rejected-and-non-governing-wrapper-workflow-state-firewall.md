## What this is for

Use `634` when a later packet preserves or reenacts a **visible wrapper workflow-state layer** around same-route detached derivatives:
- submit-for-approval controls,
- pending approval / approved / rejected / canceled disposition badges,
- approval sidebars or approval detail cards,
- review-approvals buttons,
- locked-for-approval posture,
- approved-version affordances,
- publish-after-approval stages,
- or similar later packet workflow / approval disposition posture.

Those workflow surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added workflow posture**, not automatic proof of:
- source-route official publication,
- source-route authorship,
- office adoption,
- legal finality,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded workflow-state bridge.
Google Drive Help says a file in approval can show a top-of-file banner, approve/reject actions, an approval sidebar with details, and approved versions for Docs, Sheets, and Slides files.
Microsoft Support says SharePoint/OneDrive items can carry Approval Status such as Approved or Rejected and that SharePoint page life cycles can include Submit for approval, Pending approval, Review approvals, and Published stages when content approval is turned on.
That is enough for one bounded firewall here.
(xref: `google_drive_get_approvals_on_files_help_page`; xref: `microsoft_approve_reject_items_or_files_site_list_library_help_page`; xref: `microsoft_sharepoint_modern_page_lifecycle_content_approval_help_page`)

`634` exists so maintainers can say:
**this packet preserved a later workflow-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the workflow layer itself does not silently prove source-route official publication, source-route authorship, office adoption, legal finality, or the governing member.**

## Why this is distinct

`616` asks whether a later packet preserved **review discourse** — comment threads, replies, or note exchanges.

`618` asks whether a later packet preserved **history posture** — version-history panes, named versions, restore candidates, or prior-version comparisons.

`620` asks whether a later packet preserved **event posture** — notifications, activity feeds, or alert delivery.

`629` asks whether a later packet preserved **participation posture** — avatars, presence cursors, participant lists, or reviewer-status chips.

`633` asks whether a later packet preserved **signature posture** — signature lines, signer certificates, validation badges, or audit-trail pages.

`634` asks a different question:
**did a later packet add or preserve a visible workflow-disposition layer — submit-for-approval posture, pending/approved/rejected status, approval sidebars, review-approvals buttons, approved versions, or publish-after-approval state — and did later readers start overreading that layer as if it proved source-route official publication, source-route authorship, office adoption, legal finality, or the packet's governing member?**

If the real problem is review discussion content, use `616`.
If the real problem is version/history posture, use `618`.
If the real problem is notifications or activity delivery, use `620`.
If the real problem is participant presence or reviewer rosters, use `629`.
If the real problem is signature or certificate posture, use `633`.
Use `634` only when the missing distinction is **wrapper workflow-state posture itself**.

## Decision test

Use `634` when all three conditions hold:

1. later evidence preserves or reenacts a **visible workflow-disposition layer** around same-route detached derivatives — for example a pending-approval badge, approval sidebar, review-approvals button, approved-version control, or published-after-approval stage;
2. that layer is **later wrapper-added workflow state**, not proof that the underlying source route itself is the current public head, officially adopted, legally final, or governed by that visible workflow state; and
3. later readers are drifting toward treating that layer as if it proved **source-route official publication, source-route authorship, office adoption, legal finality, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an event, history, participation, discourse, or signature problem with some visible workflow posture around it, keep event posture in `620`, keep history posture in `618`, keep participation posture in `629`, keep discourse in `616`, keep signature posture in `633`, and add one bounded `634` workflow-state note only if the visible workflow layer itself changed the reading.

## Keep discourse, history, event, participation, signature, and workflow state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added review discourse** — comments, replies, task-like notes, or resolution prose (`616`);
5. **wrapper-added history state** — version-history panes, named versions, restore candidates, or prior-version posture (`618`);
6. **wrapper-added event state** — notifications, activity feeds, or alert delivery posture (`620`);
7. **wrapper-added participation state** — avatars, presence cursors, participant lists, or reviewer-status chips (`629`);
8. **wrapper-added signature state** — signature lines, validation badges, signer certificates, eSignature status, audit-trail pages, or certified-document markers (`633`);
9. **wrapper-added workflow state** — submit-for-approval posture, pending/approved/rejected disposition, approval sidebars, review-approvals buttons, approved versions, or publish-after-approval stages (`634`);
10. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, desktop client, or other transport context (`437`, `490`, `600`);
11. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible workflow badge or approval pane as if it proved what the underlying source officially published, officially adopted, or finally decided; or
- letting a later approval/rejection/publish-after-approval shell become evidence that the packet itself is governance-bearing.

`634` exists so the archive can keep that later visible workflow layer **truthful but non-governing**.

## Minimal wrapper-workflow-state note grammar

When wrapper workflow state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_workflow_kind=<submit_for_approval|pending_approval|approved|rejected|canceled|approval_sidebar|review_approvals|approved_versions|published_after_approval|locked_for_approval|mixed|unknown>; workflow_subject=<file|page|request|version|mixed|unknown>; source_route_publication_proved=<forbid>; source_authorship_proved=<forbid>; office_adoption_proved=<forbid>; legal_finality_proved=<forbid>; governing_member_from_workflow_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_634_when=<workflow_state_changed_reading>; promote_wrapper_workflow_state=<no>; basis=<why the later approval/workflow layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible approval/workflow posture” without minting a new detached-derivative member or silently rewriting publication, authorship, adoption, legal finality, or governance.

## Typical uses

1. **Pending-approval overread**
   A later packet shows `Pending approval` or a submit-for-approval stage and later readers start retelling that visible workflow state as if it proved the underlying source route was not yet official, not public, or not current in every relevant sense.
2. **Approved-status overread**
   A later packet shows `Approved` or a review-approvals success state and later readers start retelling that visible wrapper status as if it proved office adoption, legal finality, or governing-member status for the preserved derivative.
3. **Rejected-status overread**
   A later packet shows `Rejected` and later readers start retelling that visible wrapper rejection as if it proved source falsity, official repudiation of every route variant, or total withdrawal of the underlying source.
4. **Approved-version overread**
   A later packet shows approved versions or locked-for-approval posture and later readers start retelling that workflow shell as if it proved the visible packet itself was the authoritative current publication lane.
5. **Mixed workflow-state overread**
   A later packet mixes pending, approved, rejected, or publish-after-approval cues, and later readers collapse that later workflow posture into one stronger publication or finality claim than the packet can support.

## When not to use this

Do **not** use `634` when:
- the decisive issue is still review discourse (`616`),
- the decisive issue is still version/history posture (`618`),
- the decisive issue is still notifications or activity delivery (`620`),
- the decisive issue is still participant presence (`629`),
- the decisive issue is still signature or certificate posture (`633`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible workflow layer leaves an ordinary discourse, history, event, participation, or signature problem, use the narrower doc and omit `634`.
If deleting it would erase **why a later approval/workflow layer changed the way the packet was being read or retold**, `634` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried submit-for-approval posture, pending/approved/rejected badges, approval sidebars, review-approvals buttons, approved versions, or similar visible workflow disposition.
Tighten `616`, `618`, `620`, `629`, `633`, `634`, or `600` first.
Only add another numbered doc when repeated wrapper-workflow-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-workflow-state note under `634`.
