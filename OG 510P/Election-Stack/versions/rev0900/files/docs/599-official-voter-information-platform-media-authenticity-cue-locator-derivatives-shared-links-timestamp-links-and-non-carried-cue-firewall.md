# 599 — Official voter-information platform media authenticity-cue locator derivatives, shared links, timestamp links, and non-carried-cue firewall

**Track:** Shared / Public surfaces

This document defines a bounded control for **later notes, packets, exports, or derivatives that preserve only a locator-like pointer to the same current official media route while dropping some or all of that route's surrounding authenticity-adjacent cue posture**:
copied watch-page URLs,
short share links,
timestamp or current-time links,
embed/player `src` URLs,
canonical watch URLs copied out of chat, docs, or slides,
or similar locator-only derivatives that preserve where the same object could be opened without preserving the whole viewed route.

It does not create a new authenticity cue family.
It adds one narrow rule:
**when later evidence preserves only a locator/pointer from the same official media route, the archive should preserve that locator-derivative fact honestly and should not quietly treat missing route-level identity, context, or provenance cues in the pointer itself as if those cues were disproved absent on the route — or as if the locator automatically carried the whole route's authenticity posture.**

## Why this exists (bounded)

The archive already distinguishes live share/export wrapper authority problems (`511`), direct-embed/player-host aliases (`538`), same-object current-time entrypoint aliases (`539`), clipped route captures (`594`), and stripped metadata extracts (`598`).
A smaller but still important seam remains:
**a later locator derivative can preserve only how to reach the route — a watch URL, short share link, timestamp link, or embed/player URL — while dropping the byline, badge, context panel, provenance disclosure, expanded details, or other authenticity-adjacent cues that surrounded that route when it was actually viewed.**

Current primary-source guidance is specific enough to justify one compact bridge here.
YouTube's current sharing help says the share panel can copy a link, generate embed code, and create a “Start at” link for a specific moment.
Its current embed help says viewers can copy HTML embed code from the Share menu.
Vimeo's current timecode help says a share link can start playback at a specified `#t=` moment and that the same parameter can be added to an embedded player URL.
Microsoft's current Microsoft 365 video-sharing help says a video or audio file can be shared by copy link at current time or by embed code.
At the same time, YouTube's current verified-channel help treats badges as source-identity cues, and its current provenance help says provenance disclosures can appear in the player or description rather than in the copied locator itself.
(xref: `youtube_share_videos_channels_help_page`; xref: `youtube_embed_videos_playlists_help_page`; xref: `vimeo_start_playback_specific_timecode_help_page`; xref: `microsoft_share_video_audio_m365_help_page`; xref: `youtube_verified_channels_help_page`; xref: `youtube_how_this_content_was_made_disclosures_help_page`; xref: `youtube_captured_with_a_camera_disclosure_help_page`)

That is enough to support one bounded maintainer rule:
**a truthful locator derivative is still only a locator derivative.**
A copied watch URL, short share link, timestamp link, or embed/player `src` URL can honestly preserve how later readers could arrive at the same object while still failing to preserve route-level identity cues, context/policy wrappers, provenance disclosures, or other authenticity-adjacent surfaces that lived around the route when it was viewed.
`599` exists so the archive can preserve that locator-derivative fact without overpromoting the pointer into route-total proof.

## This is not the same thing as `511`, `538`, `539`, `592`, `594`, `598`, `591`, `585`, or `588`

`511` asks whether the **live share/export surface or the resulting portable wrapper** became a shadow current-answer object in the first place.

`538` asks whether a **direct embed/player-host render alias** for the same object should be recorded as a same-object render-path note without becoming the public default.

`539` asks whether a **current-time or “Start at” entrypoint alias** should be recorded as a same-object landing-point note without becoming a new head or a quoted-moment answer object.

`592` asks whether a **preview shell and an opened target** were later treated as if they shared one cue posture.

`594` asks whether a **later screenshot, crop, clipped embed, or other narrow observation window** preserved only part of the route and then got overread as if it proved the route's whole authenticity-cue posture.

`598` asks whether a **metadata-like label extract** such as a copied title, description, chapter list, or playlist label got overread as if route-level cues traveled with it.

`591` asks whether later materials **fused observations from different routes, times, viewer conditions, or interaction states** into one faux simultaneous posture.

`585` asks whether **supportive authenticity-adjacent cues traveled unevenly across real routes or wrappers** and later readers started treating that cue transport drift like proof that the answer changed.

`588` asks which supportive cue on one route belonged to the channel/account, the route context, or the object itself.

`599` asks a different question:
**even if the route stayed the same, did later evidence preserve only a locator-like pointer to that route and then get overread as if the pointer itself carried — or disproved — the route's surrounding authenticity-cue posture?**

If the real problem is that the live share/export wrapper itself became a shadow answer, use `511`.
If the real problem is a same-object direct-embed/player-host alias, use `538`.
If the real problem is a same-object current-time/start-at alias, use `539`.
If the real problem is shell-versus-target inheritance, use `592`.
If the real problem is a clipped route capture, use `594`.
If the real problem is metadata-only extraction, use `598`.
If the real problem is later multi-state composite assembly, use `591`.
If the real problem is cross-route cue transport drift, use `585`.
If the real problem is cue attachment scope on the already-open route, use `588`.
Use `599` only when the decisive ambiguity is **locator-only evidence from the route being overread as if authenticity-adjacent cues automatically traveled with it — or as if their absence from the pointer disproved their presence on the route.**

## Default rule: keep current control with the head; classify the locator derivative before narrating cue absence

By default, later notes SHOULD still cite the current controlling head under `530`, or the fallback anchor if the chain is headless.
A `599` note exists only to explain one bounded extraction mistake around that head.

Use this triage order:
1. if the decisive issue is still live share/export wrapper authority, use `511`;
2. if the decisive issue is still direct-embed/player-host aliasing, use `538`;
3. if the decisive issue is still current-time/start-at aliasing, use `539`;
4. if the decisive issue is still shell-versus-target inheritance, use `592`;
5. if the decisive issue is still a clipped route capture, use `594`;
6. if the decisive issue is still metadata-only extraction, use `598`;
7. if the decisive issue is still later cross-state composite assembly, use `591`;
8. use `599` only when the decisive issue is that **later evidence carried a locator-like pointer but not the whole route-level authenticity posture.**

That means `599` is not a new citation lane.
It is a compact bridge for one bounded sentence saying that the derivative was locator-only and that route-level cue absence should not be inferred from the stripped pointer.

## Keep route state and locator-derivative state separate before narrating authenticity posture

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **route/object state** — which current route, object, and entrypoint were actually open (`369`, `511`, `538`, `539`, `585`, `592`);
3. **locator layer** — which pointer later survived: watch URL, short share link, timestamp link, embed/player URL, or similar locator (`511`, `538`, `539`);
4. **cue family** — identity, context/policy, provenance (`520`, `521`, `584`);
5. **attachment / transport / viewer conditions** — whether the cue belonged elsewhere on the route, traveled unevenly to another wrapper, or depended on bounded conditions (`585`, `588`, `589`, `590`);
6. **derivative form** — whether later evidence preserved only the pointer rather than the surrounding route (`599`);
7. **assembly state** — whether later materials kept those limits separate or fused them with other observations (`591`).

That separation matters because later materials can otherwise make two opposite mistakes:
- treating a truthful locator derivative as if it disproved any same-route cue that did not survive into the pointer, or
- refusing to use locator derivatives at all even though they still truthfully preserve one bounded routing fact.

`599` exists so the archive can keep the locator derivative **truthful but non-total**.

## Minimal locator-derivative note grammar

When locator-overread itself matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; derivative_kind=<watch_url_copy|share_link|shortlink|timestamp_link|embed_src|player_url|mixed|unknown>; source_layer=<511|538|539|mixed>; extracted_fields=<locator_only|locator_with_offset|embed_src|mixed|unknown>; cue_family=<520|521|584|mixed>; extract_carries_route_level_cues=<no>; cue_absence_from_extract_implies_route_absence=<forbid>; cite_default=<head|fallback anchor>; cite_derivative_when=<claim that locator-only evidence was later overread as full-route cue posture>; promote_derivative=<no>; basis=<why the locator-only limit mattered>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later artifact preserved only the pointer to the route” without minting a new head, a new cue family, or a new route.

## Typical uses

1. **Copied watch URL overread**
   A memo, brief, or chat thread preserves only a watch-page URL and later retells missing byline, badge, panel, or provenance cues as if they had been disproved absent on the live route.
2. **Timestamp-link overread**
   A copied “Start at” or current-time link circulates outside the player and later readers treat that stripped pointer as if it carried the whole same-route authenticity posture around the selected moment.
3. **Embed/player URL overread**
   A deck, CMS snippet, or notes packet preserves only an iframe `src` or player URL and later readers quietly treat that stripped locator as if it settled route-level authenticity or currentness.
4. **Short share-link overread**
   A copied short share link survives in later evidence while the surrounding route-level badge, panel, disclosure, or recovery path does not.
5. **Locator bundle plus other extract confusion**
   A later packet mixes copied pointers with screenshots or metadata extracts and later readers quietly narrate the whole bundle as if every cue came from one preserved route state.

## When not to use this

Do **not** use `599` when:
- the decisive issue is still live share/export wrapper authority (`511`),
- the decisive issue is still direct-embed/player-host aliasing or current-time/start-at aliasing (`538`, `539`),
- the decisive issue is still shell-versus-target inheritance, clipped-window non-totality, or later multi-state assembly (`592`, `594`, `591`),
- the decisive issue is still metadata-only extraction (`598`),
- or the decisive issue is still cue transport, attachment scope, discoverability, or viewer-conditionality (`585`, `588`, `589`, `590`).

If deleting the locator-derivative fact would leave an ordinary live share/export, direct-embed, current-time alias, shell/target, clipped-capture, or metadata-derivative claim, use the narrower doc and omit `599`.
If deleting it would erase **why a copied pointer got overread as full-route authenticity posture**, `599` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because later packets preserved copied watch URLs, short share links, timestamp links, embed/player URLs, or similar locator-only pointers without surrounding authenticity-adjacent cues.
Tighten `511`, `538`, `539`, `591`, `594`, `598`, or `599` first.
Only add another numbered surface when repeated locator-derivative mistakes still cause misrouting after this compact non-carried-cue control exists.
