## What this is for

Use `649` when a later packet preserves or reenacts a **visible wrapper successor-state layer** around same-route detached derivatives:
- an up-next row or queue slot,
- an autoplay-next countdown or next-video preview,
- a playlist-side next item or showcase-next tile,
- a TV queue or sender-staged successor item,
- a visible queue order that implies which object comes next,
- or similar later packet foregrounding of a successor object.

Those successor surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added successor posture**, not automatic proof of:
- official continuation,
- official endorsement of the next object,
- source-native chronology,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded successor-state bridge.
YouTube says that when Autoplay is on, another related video will automatically play after a video ends and the player shows what is going to play next.
YouTube also says queueing lets viewers set up videos to watch next without interrupting the current watch session, including play-next and play-last placement.
Its loop guidance matters here too: looping repeats the same video or playlist item, which is not the same thing as a successor object being staged or handed off.
Vimeo says showcase viewers can turn Autoplay on or off and that when it is on, the next video in the playlist begins automatically after the current one ends.
Microsoft says viewers can select the next video from playlist view, but there is currently no way to shift to the next video from within the playback experience and autoplay is not available in playlists.
(xref: `youtube_autoplay_videos_help_page`; xref: `youtube_queue_videos_help_page`; xref: `youtube_loop_videos_playlists_help_page`; xref: `vimeo_showcase_viewing_experience_help_page`; xref: `microsoft_video_playlists_onedrive_sharepoint_help_page`)

`649` exists so maintainers can say:
**this packet preserved a later up-next / queue / autoplay-next / playlist-progression posture around same-route detached derivatives, and that posture mattered for how later readers interpreted the packet, but the successor-state layer itself does not silently prove official continuation, official endorsement of the next object, source-native chronology, or the packet's governing member.**

## Why this is distinct

`496` asks whether autoplay, end screens, cards, or other play-next surfaces became the **authority-boundary** problem on the public surface in the first place.

`507` asks whether a channel home, playlist, showcase, or other collection page acted as the router or currentness map.

`551` asks whether playback actually moved into a **different object** through autoplay, queue progression, playlist-next mechanics, or another successor handoff.

`560` asks whether the **same current object** was still controlling while an up-next row, queue, TV queue, or another pending-next list was merely foregrounded.

`611` asks whether later packet motion, build-order staging, autoplay, or reveal timing changed how preserved derivatives were experienced over time.

`649` asks a different question:
**did a later packet add or preserve a visible successor-state layer — up-next row, queue slot, autoplay-next countdown, playlist-side next item, showcase-next tile, TV queue successor, or similar — and did later readers start overreading that layer as if it proved official continuation, official endorsement of the next object, source-native chronology, or the packet's governing member?**

If the real problem is autoplay / play-next as a voter-facing authority boundary, use `496`.
If the real problem is collection routing or collection context, use `507`.
If the real problem is a completed cross-object handoff, use `551`.
If the real problem is same-object pending-next state while the current object still controls, use `560`.
If the real problem is wrapper timing or auto-advance choreography rather than successor-object posture, use `611`.
Use `649` only when the missing distinction is **wrapper successor-state posture itself** around a later detached-derivative packet.

## Decision test

Use `649` when all three conditions hold:

1. later evidence preserves or reenacts a **visible successor-state layer** around same-route detached derivatives — for example an up-next row, queue slot, autoplay-next countdown, playlist-side next item, showcase-next tile, TV queue successor, or similar next-object foregrounding;
2. that layer is **later wrapper-added successor posture**, not proof that the underlying source route itself officially continued into the next object, officially endorsed that next object, or made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **official continuation, official endorsement of the next object, source-native chronology, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an authority-boundary problem, collection-routing problem, completed successor-handoff problem, same-object queue-state problem, or wrapper-timing problem with some visible next-item posture around it, keep authority-boundary in `496`, keep collection routing in `507`, keep completed handoffs in `551`, keep same-object pending-next posture in `560`, keep motion/timing in `611`, and add one bounded `649` successor-state note only if the visible next-object layer itself changed the reading.

## Keep successor state, handoff, queue state, collection routing, and timing separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **authority-boundary / collection routing class** — whether autoplay/play-next or collection routing already became the decisive public-surface problem (`496`, `507`);
5. **same-object versus cross-object state** — whether the current object still controlled (`560`) or playback actually moved into a different object (`551`);
6. **wrapper timing** — whether the packet's own motion or auto-advance cadence changed the temporal feel (`611`);
7. **carrier wrapper** — slide deck, PDF memo, browser shell, doc shell, saved page, ticket, or email thread (`437`, `490`, `600`);
8. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible up-next row, autoplay-next countdown, queue slot, or playlist-next preview as if it proved that the source itself officially continued into that successor object; or
- letting a later successor preview become evidence that the packet itself is governance-bearing rather than just a later foregrounding layer around one preserved derivative.

`649` exists so the archive can keep that later visible successor-state layer **truthful but non-governing**.

## Minimal wrapper-successor-state note grammar

When wrapper successor state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_successor_kind=<up_next_row|queue_slot|autoplay_next_countdown|playlist_next_item|showcase_next_item|tv_queue_successor|mixed|unknown>; successor_scope=<pending_only|countdown_visible|queue_order_visible|playlist_progression_visible|post_end_preview|unknown>; successor_object=<packet|route label|unknown|none>; source_native_continuation_proved=<forbid>; official_successor_endorsement_proved=<forbid>; source_native_chronology_proved=<forbid>; governing_member_from_successor_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|pdf_shell|review_shell|slide_deck|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_649_when=<successor_state_changed_reading>; promote_wrapper_successor_state=<no>; basis=<why the later next-object layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried a visible up-next / queue / autoplay-next / playlist-progression layer” without minting a new detached-derivative member or silently rewriting continuity, endorsement, chronology, or governance.

## Typical uses

1. **Autoplay-next overread**
   A later packet shows an autoplay-next countdown or next-video preview around a preserved derivative and later readers start retelling the source as if the office itself officially continued into that successor object.
2. **Queue-slot overread**
   A later packet foregrounds queue order or a play-next slot and later readers start treating that staged successor as if it had already inherited official currentness.
3. **Playlist-next overread**
   A later packet preserves a playlist-side next item or showcase-next tile and later readers start treating that successor preview as if it were an office-endorsed continuation rather than merely the wrapper's visible next-object posture.
4. **Countdown versus handoff split**
   A later packet preserves a next-item countdown or preview that mattered for interpretation, but playback had not yet crossed into the next object; keep `551` for completed handoffs and use `649` only for the later successor-state drift.

## When not to use this

Do **not** use `649` when:
- the decisive issue is still autoplay / play-next as a voter-facing authority boundary (`496`),
- the decisive issue is still collection routing or collection context (`507`),
- the decisive issue is still same-object pending-next foreground while the current object remains in control (`560`),
- the decisive issue is still a completed successor-object handoff (`551`),
- the decisive issue is still wrapper timing, build-order staging, or auto-advance choreography (`611`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible next-object layer leaves an ordinary autoplay-boundary, collection-routing, same-object queue-state, completed handoff, timing, mixed-packet, or cross-state problem, use the narrower doc and omit `649`.
If deleting it would erase **why a later successor preview changed the way the packet was being read or retold**, `649` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried an up-next row, queue slot, autoplay-next countdown, playlist-side next item, showcase-next tile, TV queue successor, or similar visible next-object posture around same-route detached derivatives.
Tighten `496`, `507`, `551`, `560`, `600`, `611`, or `649` first.
Only add another numbered doc when repeated wrapper-successor-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-successor-state note under `649`.
