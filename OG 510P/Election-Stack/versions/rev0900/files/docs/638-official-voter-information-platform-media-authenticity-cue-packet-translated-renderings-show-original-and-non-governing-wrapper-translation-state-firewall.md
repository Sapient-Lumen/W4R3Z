# 638 — Official voter-information platform media authenticity-cue packet translated renderings, show-original, and non-governing wrapper-translation-state firewall

**Track:** Shared / Public surfaces

This document covers a narrow packet-wrapper problem:
**later packets can preserve browser- or app-translated renderings, selected-text translation popups, “Show original” posture, language-pair badges, auto-translate indicators, or similar visible wrapper translation-state layers around same-route detached derivatives, and later readers can start mistaking that translation posture for a reviewed official translation, source-native language, office adoption, or the packet's governing member.**

## What this is for

Use `638` when a later packet preserves or reenacts a **visible wrapper translation-state layer** around same-route detached derivatives:
- translated page renderings,
- selected-text translation popups,
- “Show original” toggles,
- language-pair badges or translated-status chips,
- always-translate / auto-translate posture,
- same-tab or same-session continued translation posture,
- or similar later packet translation-state signals.

Those translation surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added translation posture**, not automatic proof of:
- a reviewed official multilingual publication,
- source-native language,
- source-native wording,
- office adoption,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded translation-state bridge.
Google Chrome Help says Chrome can translate full pages, translate selected text, and manage automatically translated languages.
Mozilla Support says Firefox can translate full pages, translate selected text, and revert to “Show original.”
Microsoft Support says Edge can translate webpages, always translate from a language, show translated status, and revert to “Show original.”
Apple Support says Safari can translate webpages, translate selected text, and may keep translating other webpages in the same domain within the same tab after one translation.
That is enough for one bounded firewall here.
(xref: `google_chrome_help_translate_pages_page`; xref: `mozilla_support_firefox_translations_page`; xref: `microsoft_support_edge_translator_page`; xref: `apple_support_safari_translate_webpage_page`; xref: `apple_support_safari_web_page_translation_auto_same_domain_page`)

`638` exists so maintainers can say:
**this packet preserved a later translation-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the translation layer itself does not silently prove a reviewed official translation, source-native language, office adoption, or the governing member.**

## Why this is distinct

`487` asks whether browser-integrated translation of an already-open official page needs its own route-level authority boundary.

`492` asks whether generated captions or translated subtitles over already-open media start sounding like reviewed official transcript or subtitle publication.

`545` asks whether a selected caption/subtitle language pick or text-track state within the same current object needs a bounded same-object retention note.

`595` asks whether a text-only detached derivative carries — or disproves — surrounding authenticity-cue posture.

`624` asks whether a later packet preserved **information posture** — details panes, language fields, owner/location/type fields, or similar visible file-information state.

`637` asks whether a later packet preserved **proofing posture** — spelling underlines, grammar marks, proofing-language picks, or autocorrect posture.

`638` asks a different question:
**did a later packet add or preserve a visible translation layer — translated renderings, selected-text translation popups, show-original posture, language-pair badges, or auto-translate persistence — and did later readers start overreading that layer as if it proved a reviewed official translation, source-native language, office adoption, or the packet's governing member?**

If the real problem is page-translation authority while the original page is still open, use `487`.
If the real problem is generated subtitle or caption translation over media playback, use `492` or `545`.
If the real problem is just a detached text derivative, use `595`.
If the real problem is file-information language metadata, use `624`.
If the real problem is spelling / grammar / proofing-language posture, use `637`.
Use `638` only when the missing distinction is **wrapper translation-state posture itself**.

## Decision test

Use `638` when all three conditions hold:

1. later evidence preserves or reenacts a **visible translation layer** around same-route detached derivatives — for example a translated page view, selected-text translation popup, show-original toggle, language-pair badge, or auto-translate posture;
2. that layer is **later wrapper-added translation state**, not proof that the underlying source route itself officially published that translation, officially changed source language, officially adopted the visible translated wording, or officially made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **a reviewed official translation, source-native language, source-native wording, office adoption, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a page-translation authority problem, a caption/subtitle track problem, a text-derivative problem, an information-state problem, or a proofing-state problem with some visible translation posture around it, keep page-translation authority in `487`, keep subtitle/track state in `492` or `545`, keep detached text in `595`, keep information posture in `624`, keep proofing posture in `637`, and add one bounded `638` translation-state note only if the visible translation layer itself changed the reading.

## Keep page translation, track selection, proofing, information, and translation state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **page-translation authority boundary** — when the already-open official page itself is being translated and the archive needs the route-level translation boundary (`487`);
5. **text-track or subtitle state** — caption/subtitle language picks, translated subtitle tracks, or other same-object text-track posture (`492`, `545`);
6. **wrapper-added information state** — visible file-information language fields, properties, owner/location/type panels, or similar metadata posture (`624`);
7. **wrapper-added proofing state** — proofing-language picks, spelling/grammar marks, autocorrect posture, or similar language-check signals (`637`);
8. **wrapper-added translation state** — translated renderings, selected-text translation popups, show-original posture, language-pair badges, auto-translate persistence, or similar visible machine-translation posture (`638`);
9. **carrier wrapper** — slide deck, PDF memo, doc shell, browser shell, saved page, email thread, or other transport context (`437`, `490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible translation layer as if it proved the underlying source route officially published, reviewed, or adopted that translated wording; or
- letting a later translation wrapper become evidence that the packet itself is governance-bearing, office-adopted, or the governing member.

`638` exists so the archive can keep that later visible translation layer **truthful but non-governing**.

## Minimal wrapper-translation-state note grammar

When wrapper translation state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_translation_kind=<full_page_translation|selected_text_translation|translation_popup|show_original_toggle|auto_translate_persistence|language_pair_badge|mixed|unknown>; translation_scope=<whole_packet|selection|current_view|same_tab_session|mixed|unknown>; translation_source_binding=<machine_generated|unknown>; reviewed_official_translation_proved=<forbid>; source_language_proved=<forbid>; source_wording_proved=<forbid>; office_adoption_proved=<forbid>; governing_member_from_translation_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|review_shell|slide_deck|pdf_memo|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_638_when=<translation_state_changed_reading>; promote_wrapper_translation_state=<no>; basis=<why the later translation layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried translated rendering / show-original / auto-translate posture” without minting a new detached-derivative member or silently rewriting source language, source wording, official translation status, office adoption, or packet governance.

## Typical uses

1. **Translated rendering overread**
   A later packet shows the same detached derivative in a translated browser view and later readers start retelling that translation as if it were the office's reviewed official translation rather than a viewer-side convenience layer.
2. **Selected-text popup overread**
   A later packet preserves a translated popup for one highlighted sentence and later readers start treating that excerpt as if it were the complete or officially adopted wording of the source route.
3. **Show-original misread**
   A later packet shows a translated state plus a “Show original” recovery path and later readers stop distinguishing between the translated rendering and the underlying original-language source.
4. **Auto-translate persistence overread**
   A later packet preserves always-translate or same-tab continued translation posture and later readers start treating that continued translated view as if it proved a stable reviewed multilingual publication lane.
5. **Mixed language context misread**
   A later packet carries translated renderings around one same-route detached derivative while nearby labels, attachments, or metadata remain untranslated, and later readers start overreading the mixed packet as if the whole packet had one officially reviewed language state.

## When not to use this

Do **not** use `638` when:
- the decisive issue is still browser-integrated translation of the already-open official page (`487`),
- the decisive issue is still generated subtitle or caption translation over media playback (`492`, `545`),
- the decisive issue is still text-derivative non-carriage (`595`),
- the decisive issue is still file-information language metadata (`624`),
- the decisive issue is still proofing-language / spelling / grammar posture (`637`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible translation layer leaves an ordinary page-translation authority, text-track, text-derivative, information, or proofing problem, use the narrower doc and omit `638`.
If deleting it would erase **why a later translation / show-original / translated-popup layer changed the way the packet was being read or retold**, `638` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried translated renderings, selected-text translation popups, show-original posture, or auto-translate persistence.
Tighten `487`, `492`, `545`, `595`, `624`, `637`, `638`, or `600` first.
Only add another numbered doc when repeated wrapper-translation-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-translation-state note under `638`.
