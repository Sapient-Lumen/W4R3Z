# 609 — Official voter-information platform media authenticity-cue packet prominence, size weighting, and non-governing wrapper-salience firewall

**Track:** Shared / Public surfaces

This document defines a bounded control for **later packet-level prominence allocation around same-route detached derivatives**:
enlarged hero panels,
thumbnail demotion,
small-versus-large weighting,
resized excerpt blocks,
or similar later wrapper-added scale choices that change **which preserved member visually reads as "main," foregrounded, or merely supporting** without proving that the official source route itself natively gave that member the same prominence, priority, or governing status.

It does not create a new authenticity cue family.
It adds one narrow rule:
**when a later packet changes how big or visually primary one preserved same-route detached derivative appears relative to others, the archive should preserve that wrapper-prominence fact honestly and should not quietly treat the resulting size weighting as if it proved source-native emphasis, source-native priority, or the packet's governing member.**

## Why this exists (bounded)

The archive already distinguishes detached stills (`597`), copied text (`595`), copied metadata (`598`), clipped observation windows (`594`), mixed detached-derivative packets (`600`), short wrapper labels (`601`), longer wrapper summaries (`602`), wrapper-added emphasis markup (`603`), wrapper-added concealment (`604`), wrapper-added ordering (`605`), wrapper-added membership (`606`), wrapper-added repetition (`607`), and wrapper-added layout (`608`).
A smaller but still important seam remains:
**a later packet can enlarge one same-route detached derivative, shrink another to thumbnail scale, or otherwise change visual weight among preserved members, and later readers can start narrating that wrapper prominence as if it proved source-native emphasis, source-native priority, or the packet's governing member.**

Current primary-source guidance is specific enough to justify one compact bridge here.
Google Slides' current help says objects and text boxes can be changed through **Size & Position**.
Microsoft's current support says pictures, shapes, text boxes, and other objects can be resized by dragging their frames or entering exact sizes.
Apple's current Preview guidance says shapes, highlights, and zoom lenses can be dragged and resized.
(xref: `google_slides_insert_arrange_text_shapes_diagrams_lines_help_page`; xref: `microsoft_resize_picture_shape_text_box_object_help_page`; xref: `apple_preview_annotate_pdf_mac_help_page`)

That is enough to support one bounded maintainer rule:
**later packet prominence is still only later packet prominence.**
A hero-panel packet, thumbnail-demoted packet, or resized-excerpt packet can honestly be the salience later readers encountered while still failing to prove that the source route itself natively foregrounded that same member or that the visually largest member became the governing source object.
`609` exists so the archive can preserve that salience fact without quietly promoting wrapper size weighting into source-native priority.

## This is not the same thing as `603`, `604`, `608`, `607`, `606`, `600`, `597`, `595`, `598`, `591`, `437`, or `490`

`603` asks whether later wrapper-added markup or emphasis such as highlight boxes, arrows, circles, underlines, comment anchors, zoom callouts, or ink starts sounding like source-native emphasis or like the packet's governing member.

`604` asks whether later wrapper-added concealment such as redaction, crop-hide, hidden slides, or hidden objects starts sounding like source absence, source-native redaction, or like the packet's governing member.

`608` asks whether later wrapper-added spatial layout or placement starts sounding like source-native adjacency, source-native simultaneity, source priority, or like the packet's governing member.

`607` asks whether later wrapper-added same-member repetition starts sounding like independent corroboration, source-native multiplicity, or like the packet's governing member.

`606` asks whether later wrapper-added membership or inclusion choices start sounding like source-native completeness, source-native scope, or like the packet's governing member.

`600` asks how to route a mixed same-route packet when several detached derivatives coexist and no single `595–599` member clearly dominates.

`597`, `595`, and `598` ask whether the decisive surviving artifact is still the detached still-image derivative, copied source text, or copied source metadata themselves.

`591` asks whether later materials fused observations from different routes, times, viewer conditions, or interaction states into one faux simultaneous posture.

`437` and `490` ask whether print/save/offline/web-archive carriers changed the authority or portability posture of the already-open route.

`609` asks a different question:
**did a later packet change the apparent visual importance of same-route detached derivatives by resizing, scaling, or thumbnailing them, and did later readers start overreading that chosen prominence as if it proved source-native emphasis, source-native priority, or the packet's governing member?**

If the real problem is wrapper-added markup, use `603`.
If the real problem is concealment, use `604`.
If the real problem is spatial arrangement, use `608`.
If the real problem is same-member repetition, use `607`.
If the real problem is chosen membership, use `606`.
If the real problem is mixed detached-derivative routing, use `600`.
If the real problem is still the detached still, copied text, or copied metadata, use `597`, `595`, or `598`.
If the real problem is cross-state composite assembly, use `591`.
If the real problem is print/save/offline/web-archive authority or portability, use `437` or `490`.
Use `609` only when the decisive ambiguity is **wrapper-added prominence or size weighting inside the packet** rather than copied source content or cross-state fusion.

## Default rule: classify the surviving derivative first; treat later wrapper prominence as descriptive unless provenance proves otherwise

By default, later notes SHOULD still cite the current controlling head under `530`, or the fallback anchor if the chain is headless.

## Keep source-derived content and wrapper-added prominence separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **wrapper-added packet label** — filename, subject line, slide title, memo heading, or similar short later-added narrative (`601`);
7. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, memo-body summaries, or similar longer later packet narrative (`602`);
8. **wrapper-added markup/emphasis** — highlight boxes, circles, arrows, underlines, comment anchors, zoom lenses, ink, or similar later visual emphasis (`603`);
9. **wrapper-added concealment/suppression** — redactions, crop-hidden regions, hidden slides, hidden objects, or similar later visual withholding (`604`);
10. **wrapper-added ordering/sequence** — reordered slide order, reordered PDF page order, moved packet sections, or similar later arrangement (`605`);
11. **wrapper-added membership/composition** — imported slides, merged-page subsets, chosen attachments, appended packet members, or similar later included-member selection (`606`);
12. **wrapper-added repetition/multiplicity** — duplicated slides, repeated pages, repeated excerpts, repeated attachments, gallery-style repeats, or similar later same-member multiplication (`607`);
13. **wrapper-added layout/spatial relation** — side-by-side placement, inset-over-main placement, gallery rows, stacked columns, split-screen comparison framing, or similar later positioning (`608`);
14. **wrapper-added prominence/salience** — enlarged hero panels, thumbnail demotion, resized excerpt blocks, large-versus-small weighting, or similar later visual importance allocation (`609`);
15. **carrier wrapper** — slide deck, PDF memo, chat export, saved page, web archive, issue ticket, or other transport context (`437`, `490`, `600`);
16. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating wrapper-added size weighting as if it proved source-native emphasis or source-native priority, or
- letting the largest-looking member become the governing member instead of first classifying the surviving detached derivative.

`609` exists so the archive can keep that later salience layer **truthful but non-governing**.

## Minimal wrapper-prominence note grammar

When wrapper-prominence overread itself matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_prominence_kind=<hero_panel|thumbnail_demotion|large_small_weighting|resized_excerpt|rescaled_compare|mixed|unknown>; prominence_relation=<same_route_member_weighting|same_route_member_weighting_likely|mixed|unknown>; wrapper_prominence_origin=<later_wrapper_added|copied_from_source|mixed|unknown>; treat_prominence_as_source_emphasis=<forbid>; treat_prominence_as_source_priority=<forbid>; treat_prominence_as_governing_member=<forbid>; carrier_wrapper=<slide_deck|pdf_memo|chat_export|saved_page|web_archive|ticket|email_thread|shared_link_message|none>; cite_default=<head|fallback anchor>; use_609_when=<wrapper_prominence_changed_perceived_importance>; promote_wrapper_prominence=<no>; basis=<why the later size weighting needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this packet later made one preserved member visually primary” without minting a new detached-derivative member or silently rewriting emphasis, priority, or governance.

## Typical uses

1. **Hero-panel overread**
   A packet enlarges one same-route detached still, transcript excerpt, or metadata block so it dominates the page and later readers start retelling that size choice as if the source route itself foregrounded that same member.
2. **Thumbnail-demotion overread**
   A packet leaves other same-route preserved members present but shrinks them to thumbnail scale and later readers start treating that demotion as if the source route itself made them secondary or negligible.
3. **Large text-block overread**
   A packet blows up one copied text or metadata derivative and later readers start treating that larger block as if it were the source route's own main wording lane.
4. **Rescaled comparison overread**
   A packet keeps the same positioned members but changes their relative sizes and later readers start treating the larger member as if the source route itself declared that hierarchy.
5. **Dominant inset overread**
   A packet keeps roughly the same layout but enlarges the inset or callout content so strongly that later readers start treating scale rather than provenance as the reason it governs.
