# 632 — Official voter-information platform media authenticity-cue packet suspicious-file warnings blocked-file status protected-view and non-governing wrapper-security-state firewall

**Track:** Shared / Public surfaces

This document covers a narrow packet-wrapper problem:
**later packets can preserve suspicious-file warnings, blocked-file markers, protected-view shells, read-only sandboxes, security dialogs, or similar visible wrapper security-state layers around same-route detached derivatives, and later readers can start mistaking that security posture for source inauthenticity, official withdrawal, official danger classification, or the packet's governing member.**

## What this is for

Use `632` when a later packet preserves or reenacts a **visible wrapper security-state layer** around same-route detached derivatives:
- suspicious-file warnings,
- download warnings,
- blocked malicious-file markers,
- protected-view or read-only-sandbox posture,
- warning bars that require an explicit trust/allow step,
- restricted-action warnings tied to an untrusted file or location,
- or similar later packet security posture.

Those security surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added security posture**, not automatic proof of:
- source inauthenticity,
- official withdrawal,
- official repudiation,
- source-native danger classification,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded security-state bridge.
Google Drive Help says suspicious files can produce warning messages when opened or downloaded, and violation-flagged files can show a flag next to the filename, lose sharing, and stop being publicly accessible even to people with the link.
Microsoft Support says malicious files in SharePoint, OneDrive, or Teams are blocked, show a warning marker, and cannot be opened.
Adobe Help says Protected View opens untrusted PDFs in a read-only sandbox, shows a warning bar, and blocks some actions until the file is explicitly trusted; Adobe also says enhanced security can trigger warnings when a PDF from an untrusted file or location attempts a restricted action.
That is enough for one bounded firewall here.
(xref: `google_drive_view_open_files_help_page`; xref: `google_drive_download_file_help_page`; xref: `google_drive_request_review_violation_help_page`; xref: `microsoft_malicious_file_found_sharepoint_onedrive_teams_help_page`; xref: `adobe_acrobat_protected_view_overview_help_page`; xref: `adobe_acrobat_enhanced_security_setting_pdfs_help_page`; xref: `adobe_acrobat_respond_security_warnings_help_page`)

`632` exists so maintainers can say:
**this packet preserved a later security-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the security layer itself does not silently prove source inauthenticity, official withdrawal, source-native danger classification, or the governing member.**

## Why this is distinct

`619` asks whether a later packet preserved **access posture** — share dialogs, link scope, role matrices, or permission settings.

`624` asks whether a later packet preserved **information posture** — owner/location/type fields, details panes, or file cards.

`626` asks whether a later packet preserved **action posture** — command bars, context menus, quick actions, or disabled commands.

`628` asks whether a later packet preserved **launch posture** — open-in-app choices, browser-versus-desktop handoff, or default handlers.

`631` asks whether a later packet preserved **classification posture** — sensitivity labels, retention labels, policy tips, or message-bar labels.

`632` asks a different question:
**did a later packet add or preserve a visible security layer — suspicious-file warnings, blocked-file markers, protected-view/read-only posture, trust/allow prompts, or similar security dialogs — and did later readers start overreading that layer as if it proved source inauthenticity, official withdrawal, source-native danger classification, or the packet's governing member?**

If the real problem is permission scope or audience reach, use `619`.
If the real problem is owner/location/type metadata, use `624`.
If the real problem is command availability or affordance state, use `626`.
If the real problem is browser-versus-desktop launch choice, use `628`.
If the real problem is classification or retention labeling, use `631`.
Use `632` only when the missing distinction is **wrapper security-state posture itself**.

## Decision test

Use `632` when all three conditions hold:

1. later evidence preserves or reenacts a **visible security layer** around same-route detached derivatives — for example a suspicious-file warning, blocked malicious-file marker, protected-view shell, or restricted-action warning tied to an untrusted file or location;
2. that layer is **later wrapper-added security state**, not proof that the underlying source route itself is inauthentic, officially withdrawn, or natively classified as dangerous; and
3. later readers are drifting toward treating that layer as if it proved **source inauthenticity, official withdrawal, source-native danger classification, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an access, information, action, launch, or classification problem with some visible security posture around it, keep access in `619`, keep information posture in `624`, keep action posture in `626`, keep launch posture in `628`, keep classification posture in `631`, and add one bounded `632` security-state note only if the visible security layer itself changed the reading.

## Keep access, information, action, launch, classification, and security state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added access state** — permissions, link scope, viewer/editor roles, or request-access posture (`619`);
5. **wrapper-added information state** — owner/location/type/details panes or file cards (`624`);
6. **wrapper-added action state** — command bars, context menus, quick actions, or disabled commands (`626`);
7. **wrapper-added launch state** — open-in-app choices, default handlers, browser-versus-desktop handoff, or auto-open posture (`628`);
8. **wrapper-added classification state** — classification labels, sensitivity labels, retention labels, policy tips, message-bar labels, or similar protection badges (`631`);
9. **wrapper-added security state** — suspicious-file warnings, blocked-file markers, protected-view shells, trust/allow prompts, or similar warning posture (`632`);
10. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, desktop client, or other transport context (`437`, `490`, `600`);
11. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible warning or blocked-state badge as if it proved what the underlying source officially is, officially means, or officially requires; or
- letting a later security wrapper become evidence that the packet itself is governance-bearing, office-retracted, or authenticity-dispositive.

`632` exists so the archive can keep that later visible security layer **truthful but non-governing**.

## Minimal wrapper-security-state note grammar

When wrapper security state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_security_kind=<suspicious_file_warning|download_warning|blocked_malicious_marker|protected_view|read_only_sandbox|security_dialog|restricted_action_warning|mixed|unknown>; trust_posture=<warn_only|blocked|read_only_until_trusted|allow_after_prompt|appeal_or_admin_review_needed|mixed|unknown>; visibility_surface=<banner|warning_bar|dialog|filename_marker|download_gate|browser_shell|desktop_client|mixed|unknown>; source_inauthenticity_proved=<forbid>; official_withdrawal_proved=<forbid>; source_native_danger_classification_proved=<forbid>; governing_member_from_security_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_632_when=<security_state_changed_reading>; promote_wrapper_security_state=<no>; basis=<why the later warning/block layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible warning / blocked / trust-gated posture” without minting a new detached-derivative member or silently rewriting source authenticity, office publication status, or governance.

## Typical uses

1. **Suspicious-file overread**
   A later packet shows a suspicious-file warning when opening or downloading a file and later readers start retelling that warning as if it proved the underlying source itself was forged or inauthentic.
2. **Blocked-file overread**
   A later packet shows a blocked malicious-file marker in a document library and later readers start retelling that blocked state as if the office itself withdrew or repudiated the underlying route.
3. **Protected-view overread**
   A later packet shows a PDF in Protected View or another read-only sandbox and later readers start retelling that container posture as if it proved the PDF's source-native status, official classification, or governing authority.
4. **Trust-prompt overread**
   A later packet shows a warning bar or dialog that requires an explicit Allow / Enable / Trust step and later readers start retelling that trust gate as if it proved the office had declared the underlying material false, unsafe, or nonofficial.
5. **Mixed security-state overread**
   A later packet mixes warnings, blocked state, and reduced feature availability, and later readers collapse that later wrapper posture into one stronger authenticity or withdrawal claim than the packet can support.

## When not to use this

Do **not** use `632` when:
- the decisive issue is still permissions or audience scope (`619`),
- the decisive issue is still owner/location/type/details metadata (`624`),
- the decisive issue is still command availability or disabled actions (`626`),
- the decisive issue is still browser-versus-desktop launch choice (`628`),
- the decisive issue is still classification or retention labeling (`631`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible security layer leaves an ordinary access, information, action, launch, or classification problem, use the narrower doc and omit `632`.
If deleting it would erase **why a later warning / blocked / trust-gated layer changed the way the packet was being read or retold**, `632` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried suspicious-file warnings, blocked-file markers, protected-view shells, trust prompts, or similar visible security posture.
Tighten `619`, `624`, `626`, `628`, `631`, `632`, or `600` first.
Only add another numbered doc when repeated wrapper-security-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-security-state note under `632`.
