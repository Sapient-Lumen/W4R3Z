## Core point

**later packets can preserve signed-in account chips, profile switchers, personal-versus-business or work-or-school account selections, tenant badges, multi-account shells, or similar visible wrapper account-state layers around same-route detached derivatives, and later readers can start mistaking that account posture for source ownership, official control, official affiliation, governing identity, or the packet's governing member.**

That drift is real enough to warrant one bounded bridge.
But the remedy is still **non-promotion**:
keep visible account or profile state descriptive, keep it subordinate to the current route head and governing detached derivative, and do not let the shown account shell silently become proof that the underlying route is officially owned, officially controlled, officially adopted, or governed by that shown account.

## What this is for

Use `630` when a later packet preserves or reenacts a **visible wrapper account-state layer** around same-route detached derivatives:
- signed-in email or profile-photo account chips,
- personal-versus-business or work-or-school profile selectors,
- organization / tenant badges,
- multi-account side-by-side shells,
- account add/remove or disconnect posture,
- or similar later packet account / profile state.

Those account surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added account posture**, not automatic proof of:
- source ownership,
- source authorship,
- official control,
- official affiliation,
- governing identity,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded account-state bridge.
Google Docs Editors help explains that users can switch among multiple Google accounts through the profile-photo or email chooser, and Google Drive for desktop separately supports multiple concurrent accounts.
Microsoft Support explains that users can switch between personal and work-or-school OneDrive accounts, that multiple work-or-school accounts can coexist in some contexts, and that personal and work-or-school OneDrive accounts are used side by side rather than merged.
Adobe Help explains that sign-in may present a profile switcher where the same email address can expose Personal and Business profiles.
That is enough for one bounded firewall here.
(xref: `google_docs_switch_between_multiple_google_accounts_help_page`; xref: `google_drive_desktop_multiple_accounts_help_page`; xref: `microsoft_onedrive_add_remove_account_help_page`; xref: `microsoft_onedrive_personal_and_work_school_side_by_side_help_page`; xref: `adobe_profiles_profile_switcher_help_page`)

`630` exists so maintainers can say:
**this packet preserved a later account-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the account layer itself does not govern the packet and does not silently prove source ownership, official control, official affiliation, governing identity, or the governing member.**

## Why this is distinct

`619` asks whether a later packet preserved **access posture** — share dialogs, role matrices, link scope, or permission settings.

`624` asks whether a later packet preserved **information posture** — owner/location/type fields, details panes, or file cards.

`628` asks whether a later packet preserved **launch posture** — `Open with`, `Open in app`, default handlers, or browser-versus-desktop choices.

`629` asks whether a later packet preserved **participation posture** — avatars, anonymous-viewer chips, presence cursors, or participant-status lists.

`630` asks a different question:
**did a later packet add or preserve a visible account shell — signed-in account chips, profile switchers, business-versus-personal selections, work-or-school badges, tenant labels, or multi-account shells — and did later readers start overreading that layer as if it proved source ownership, official control, official affiliation, governing identity, or the packet's governing member?**

If the real problem is permission scope or audience reach, use `619`.
If the real problem is owner/location/type metadata, use `624`.
If the real problem is which app opens the file, use `628`.
If the real problem is who is currently present in the file, use `629`.
Use `630` only when the missing distinction is **wrapper account-state posture itself**.

## Decision test

Use `630` when all three conditions hold:

1. later evidence preserves or reenacts a **visible account layer** around same-route detached derivatives — for example a signed-in account chip, profile switcher, business-profile selection, or work-or-school badge;
2. that layer is **later wrapper-added account state**, not proof that the underlying source route itself is officially owned, officially controlled, officially affiliated, or governed by the shown account; and
3. later readers are drifting toward treating that layer as if it proved **source ownership, official control, official affiliation, governing identity, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an access, information, launch, or participation problem with some account shell around it, keep access in `619`, keep information posture in `624`, keep launch posture in `628`, keep participation posture in `629`, and add one bounded `630` account-state note only if the visible account layer itself changed the reading.

## Keep access, information, launch, participation, and account state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added access state** — permissions, link scope, viewer/editor roles, or request-access posture (`619`);
5. **wrapper-added information state** — owner/location/type/details panes or file cards (`624`);
6. **wrapper-added launch state** — `Open with`, `Open in app`, browser-versus-desktop defaults, or handler posture (`628`);
7. **wrapper-added participation state** — avatars, anonymous-viewer markers, presence cursors, participant lists, or review-status chips (`629`);
8. **wrapper-added account state** — signed-in account chips, profile switchers, business/personal selections, tenant badges, or multi-account shells (`630`);
9. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, desktop client, or other transport context (`437`, `490`, `600`);
10. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating the visible account shell as if it proved who officially owned, controlled, or endorsed the underlying route, or
- letting a business-profile, work-or-school badge, or multi-account shell become evidence that the packet itself is official, adopted, or governance-bearing.

`630` exists so the archive can keep that later visible account layer **truthful but non-governing**.

## Minimal wrapper-account-state note grammar

When wrapper account state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_account_kind=<signed_in_account|profile_switcher|personal_profile|business_profile|work_or_school_account|tenant_badge|multi_account_shell|disconnect_state|mixed|unknown>; account_scope=<personal|work_or_school|business|mixed|unknown>; account_identity_certainty=<named|partially_named|badge_only|mixed|unknown>; source_ownership_proved=<forbid>; official_control_proved=<forbid>; official_affiliation_proved=<forbid>; governing_member_from_account_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_630_when=<account_state_changed_reading>; promote_wrapper_account_state=<no>; basis=<why the later account/profile shell needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible account/profile posture” without minting a new detached-derivative member or silently rewriting ownership, control, affiliation, governance, or the governing member.

## Typical uses

1. **Wrong-account overread**
   A later packet shows the wrong signed-in account or a switched account and later readers start retelling that shell as if it proved the file belonged to, was issued by, or was governed by that shown account.
2. **Profile-switcher overread**
   A later packet shows a Personal-versus-Business profile picker and later readers start retelling the selected profile as if it proved official adoption, formal office control, or the only legitimate controlling identity for the underlying route.
3. **Work-or-school badge overread**
   A later packet shows a work-or-school account badge or organization tag and later readers start retelling that wrapper fact as if it proved the packet itself was official, endorsed, or governance-bearing.
4. **Multi-account shell overread**
   A later packet shows several available accounts side by side and later readers collapse that shell into one stronger ownership or approval claim than the packet can support.
5. **Disconnect / sign-out overread**
   A later packet shows an account removed, disconnected, or signed out and later readers start retelling that wrapper account transition as if it proved source withdrawal, transfer of ownership, or official disavowal.

## Non-uses

Do **not** use `630` when:
- the real dispute is still permission scope, link reach, or role posture (`619`),
- the real dispute is owner/location/type metadata or an information pane (`624`),
- the real dispute is which app or handler opened the file (`628`),
- the real dispute is current collaborator presence or participant status (`629`), or
- the packet never preserved a meaningful visible account/profile layer at all.

If deleting the visible account layer leaves an ordinary access, information, launch, or participation problem, use the narrower doc and omit `630`.
If deleting it would erase **why a later signed-in account, profile switcher, tenant badge, or multi-account shell changed the way the packet was being read or retold**, `630` is probably right.

## Growth firewall

Do **not** respond to every account/profile nuance by minting another numbered doc.
Tighten `619`, `624`, `628`, `629`, or `600` first.
Only add another numbered doc when repeated wrapper-account-state mistakes still cannot be expressed as:
- one governing detached derivative,
- one current head note,
- one narrower access/information/launch/participation note,
- plus one bounded wrapper-account-state note under `630`.
