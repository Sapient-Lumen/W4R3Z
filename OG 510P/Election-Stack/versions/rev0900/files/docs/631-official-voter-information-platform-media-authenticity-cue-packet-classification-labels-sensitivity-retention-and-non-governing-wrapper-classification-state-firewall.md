# 631 — Official voter-information platform media authenticity-cue packet classification labels sensitivity retention and non-governing wrapper-classification-state firewall

**Track:** Shared / Public surfaces

**later packets can preserve classification labels, sensitivity labels, retention labels, policy-tip recommendations, message-bar protection labels, or similar visible wrapper classification-state layers around same-route detached derivatives, and later readers can start mistaking that classification posture for source-native secrecy, official endorsement, legal handling duty, final retention posture, or the packet's governing member.**

## What this is for

Use `631` when a later packet preserves or reenacts a **visible wrapper classification-state layer** around same-route detached derivatives:
- classification labels or label fields shown in side panels,
- sensitivity labels,
- retention labels,
- recommended-label or auto-applied-label policy tips,
- message-bar label posture,
- record / protected / restricted handling badges,
- or similar later packet classification / protection posture.

Those classification surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added classification posture**, not automatic proof of:
- source-native classification,
- official endorsement,
- legal finality,
- mandatory secrecy,
- final retention duty,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded classification-state bridge.
Google Drive Help explains that labels can be applied to unopened files, to Docs/Sheets/Slides from the File menu, and to non-Google files from Drive Preview, with label review happening in side panels.
Microsoft Support explains that organizations can expose retention labels in SharePoint and OneDrive, that those labels appear through the details pane and can be made visible in a Labels column or record-oriented view, and that sensitivity labels can also appear as automatically applied or recommended policy tips.
Adobe Help explains that Acrobat can apply Microsoft sensitivity labels and display the applied label on the document message bar.
That is enough for one bounded firewall here.
(xref: `google_drive_apply_labels_to_files_help_page`; xref: `microsoft_apply_retention_labels_sharepoint_onedrive_help_page`; xref: `microsoft_sensitivity_labels_auto_apply_or_recommend_help_page`; xref: `adobe_acrobat_mpip_support_help_page`)

`631` exists so maintainers can say:
**this packet preserved a later classification-state layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the classification layer itself does not govern the packet and does not silently prove source-native classification, official endorsement, legal handling duty, final retention posture, or the governing member.**

## Why this is distinct

`601` asks whether a later packet preserved **wrapper-authored labels** — packet titles, filenames, subject lines, or memo headings.

`619` asks whether a later packet preserved **access posture** — share dialogs, link scope, role matrices, or permission settings.

`624` asks whether a later packet preserved **information posture** — owner/location/type fields, details panes, or file cards.

`626` asks whether a later packet preserved **action posture** — command bars, context menus, quick actions, or disabled commands.

`630` asks whether a later packet preserved **account posture** — signed-in account chips, profile switchers, or tenant shells.

`631` asks a different question:
**did a later packet add or preserve a visible classification layer — classification labels, sensitivity labels, retention labels, policy-tip recommendations, message-bar labels, or similar protection badges — and did later readers start overreading that layer as if it proved source-native classification, official endorsement, legal handling duty, final retention posture, or the packet's governing member?**

If the real problem is wrapper-authored titles or filenames, use `601`.
If the real problem is permission scope or audience reach, use `619`.
If the real problem is owner/location/type metadata, use `624`.
If the real problem is command availability or affordance state, use `626`.
If the real problem is signed-in account identity or tenant shell, use `630`.
Use `631` only when the missing distinction is **wrapper classification-state posture itself**.

## Decision test

Use `631` when all three conditions hold:

1. later evidence preserves or reenacts a **visible classification layer** around same-route detached derivatives — for example a retention label in a details pane, an automatically applied sensitivity-policy tip, or a message-bar label on a protected PDF;
2. that layer is **later wrapper-added classification state**, not proof that the underlying source route itself is officially endorsed, canonically classified, legally final, or governed by that visible label state; and
3. later readers are drifting toward treating that layer as if it proved **source-native classification, official endorsement, legal handling duty, final retention posture, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a narrative-label, access, information, action, or account problem with some visible classification posture around it, keep labels in `601`, keep access in `619`, keep information posture in `624`, keep action posture in `626`, keep account posture in `630`, and add one bounded `631` classification-state note only if the visible classification layer itself changed the reading.

## Keep label text, access, information, action, account, and classification state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-authored label text** — packet title, filename, subject line, or memo heading (`601`);
5. **wrapper-added access state** — permissions, link scope, viewer/editor roles, or request-access posture (`619`);
6. **wrapper-added information state** — owner/location/type/details panes or file cards (`624`);
7. **wrapper-added action state** — command bars, context menus, quick actions, or disabled commands (`626`);
8. **wrapper-added account state** — signed-in account chips, profile switchers, business/personal selections, or tenant badges (`630`);
9. **wrapper-added classification state** — classification labels, sensitivity labels, retention labels, policy tips, message-bar labels, or similar protection badges (`631`);
10. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, desktop client, or other transport context (`437`, `490`, `600`);
11. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible label or protection badge as if it proved what the underlying source officially is, officially means, or officially requires; or
- letting a later retention/sensitivity/protection wrapper become evidence that the packet itself is governance-bearing, secrecy-bearing, or legally conclusive.

`631` exists so the archive can keep that later visible classification layer **truthful but non-governing**.

## Minimal wrapper-classification-state note grammar

When wrapper classification state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_classification_kind=<classification_label|sensitivity_label|retention_label|policy_tip|message_bar_label|record_badge|mixed|unknown>; label_application_state=<manual|organization_defined|auto_applied|recommended|defaulted|mixed|unknown>; label_visibility=<badge|side_panel|details_pane|column|policy_tip|message_bar|mixed|unknown>; source_native_classification_proved=<forbid>; official_endorsement_proved=<forbid>; legal_handling_duty_proved=<forbid>; governing_member_from_classification_state=<forbid>; carrier_wrapper=<doc_shell|review_shell|document_library|desktop_client|browser_shell|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_631_when=<classification_state_changed_reading>; promote_wrapper_classification_state=<no>; basis=<why the later label/protection layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible classification / protection posture” without minting a new detached-derivative member or silently rewriting source-native classification, official endorsement, legal handling duty, or governance.

## Typical uses

1. **Retention-label overread**
   A later packet shows a retention label in a details pane or library column and later readers start retelling that label as if it proved the underlying source was officially final, permanently retained, or governance-bearing.
2. **Sensitivity-tip overread**
   A later packet shows an automatically applied or recommended sensitivity-policy tip and later readers start retelling that tip as if it proved the underlying route was source-natively secret, source-natively restricted, or officially endorsed.
3. **Message-bar label overread**
   A later packet shows a PDF message bar with an applied sensitivity label and later readers start retelling that visible label as if it proved the underlying detached derivative itself was the governing official artifact.
4. **Mixed label-state overread**
   A later packet mixes a visible classification label, a record/retention view, and a protection badge, and later readers start collapsing that later wrapper posture into one stronger legal or governance claim than the packet can support.
5. **Organization-policy overread**
   A later packet shows labels that are clearly customized or defined by the surrounding organization, and later readers start mistaking that wrapper policy layer for source authorship, official adoption, or route-native classification.

## When not to use this

Do **not** use `631` when:
- the decisive issue is still packet-authored titles, filenames, or subject lines (`601`),
- the decisive issue is still permissions or audience scope (`619`),
- the decisive issue is still owner/location/type/details metadata (`624`),
- the decisive issue is still command availability or disabled actions (`626`),
- the decisive issue is still signed-in account identity or tenant shell (`630`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible classification layer leaves an ordinary narrative-label, access, information, action, or account problem, use the narrower doc and omit `631`.
If deleting it would erase **why a later classification/sensitivity/retention/protection layer changed the way the packet was being read or retold**, `631` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried classification labels, sensitivity labels, retention labels, policy tips, message-bar labels, or similar visible protection posture.
Tighten `601`, `619`, `624`, `626`, `630`, `631`, or `600` first.
Only add another numbered doc when repeated wrapper-classification-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-classification-state note under `631`.
