# 602 — Official voter-information platform media authenticity-cue packet synopses, forwarding comments, speaker notes, and non-governing wrapper-summary firewall

**Track:** Shared / Public surfaces

This document defines a bounded control for **later packet prose wrapped around same-route detached derivatives but not copied from the official media route itself**:
forwarding comments,
share-dialog messages,
email-body summaries,
slide speaker notes,
cover-note paragraphs,
notes-page synopsis text,
ticket descriptions,
or similar wrapper-added packet summaries.

It does not create a new detached-derivative member.
It adds one narrow rule:
**when later packet prose summarizes, frames, or retells same-route detached derivatives without itself being copied source text or copied source metadata, the archive should preserve that wrapper-summary fact honestly and should not quietly treat the summary as if it were copied from the source route, as if it carried the route's surrounding authenticity-cue posture, or as if it had become the packet's governing member.**

## Why this exists (bounded)

The archive already distinguishes copied source text (`595`), copied source metadata (`598`), mixed detached-derivative packets (`600`), and wrapper-added packet labels (`601`).
A smaller but still important seam remains:
**later packets often add prose around the surviving derivative — a forwarded note, a share-message paragraph, speaker notes, or a cover-note summary — and later readers can start treating that wrapper prose as if it were copied source language, as if it carried the route's authenticity posture, or as if it governed the packet more than the surviving derivative itself.**

Current primary-source guidance is specific enough to justify one compact bridge here.
Google's current Gmail help distinguishes a reply from quoted original message content and shows that a responder can enter a new response that stands apart from the quoted text.
Google's current Drive sharing help says a sender can email collaborators from the sharing dialog and add a message in a dedicated Message field.
Microsoft's current sharing help says a sender can share a document, add an optional message, and send the link.
Microsoft's current PowerPoint help says presenters can add speaker notes that are visible to the presenter while the audience sees only the slides.
That is enough to support one bounded maintainer rule:
**later wrapper-summary prose is real packet evidence, but it is not automatically copied source text and it is not automatically the governing packet member.**
(xref: `gmail_reply_to_email_help_page`; xref: `google_drive_share_files_from_google_drive_help_page`; xref: `microsoft_share_your_documents_help_page`; xref: `microsoft_powerpoint_add_speaker_notes_help_page`; xref: `microsoft_powerpoint_presenter_view_notes_help_page`)

`602` exists so the archive can say, compactly and honestly, that a forwarded “this proves the badge is gone” note, a share-dialog message, speaker notes beneath a slide, or a memo-body synopsis may be **later wrapper summary** rather than copied source text or copied source metadata — even when the packet also contains truthful same-route derivatives.

## This is not the same thing as `595`, `598`, `600`, `601`, `591`, `437`, or `490`

`595` asks whether later evidence preserved transcript text, caption/subtitle text, downloaded transcript files, OCR-derived text, or another text-only derivative copied from the route itself.

`598` asks whether later evidence preserved metadata-like labels from the official media route itself — copied title text, description text, chapter labels, playlist labels, or similar source-derived metadata.

`600` asks how to route a mixed same-route packet when several detached derivatives coexist and no single `595–599` member clearly dominates.

`601` asks whether later packet titles, filenames, subject lines, memo headings, or similar short wrapper-added labels were mistaken for source metadata or for the governing member.

`591` asks whether later materials fused observations from different routes, times, viewer conditions, or interaction states into one faux simultaneous posture.

`437` and `490` ask whether print/save/offline/web-archive carriers changed the authority or portability posture of the already-open route.

`602` asks a different question:
**did a later packet add its own summary prose around same-route detached derivatives, and did later readers start overreading that wrapper summary as if it were copied source language, copied source metadata, route-level authenticity proof, or the packet's governing member?**

If the real problem is copied transcript/caption/OCR text, use `595`.
If the real problem is copied source metadata, use `598`.
If the real problem is mixed detached-derivative routing, use `600`.
If the real problem is a short wrapper-added label, use `601`.
If the real problem is later composite assembly across states, use `591`.
If the real problem is print/save/offline/web-archive authority or portability, use `437` or `490`.
Use `602` only when the decisive ambiguity is **wrapper-added packet summary prose** rather than copied source content.

## Default rule: classify the surviving derivative first; treat later wrapper summaries as descriptive unless provenance proves otherwise

By default, later notes SHOULD still cite the current controlling head under `530`, or the fallback anchor if the chain is headless.
A `602` note exists only to explain one bounded summary-prose mistake around that head.

Use this triage order:
1. if the decisive issue is still copied source text, use `595`;
2. if the decisive issue is still copied source metadata, use `598`;
3. if the decisive issue is still a mixed detached-derivative packet with no dominant member, use `600`;
4. if the decisive issue is still a short wrapper-added label, use `601`;
5. if the decisive issue is still cross-state composite assembly, use `591`;
6. if the decisive issue is still saved-page / print / offline portability or authority boundary, use `437` or `490`;
7. use `602` only when the decisive issue is that **a later wrapper-added summary paragraph, forwarding comment, share message, speaker note, or similar synopsis changed how the packet sounded, got routed, or got retold.**

That means `602` is not a new citation lane.
It is a compact bridge for one bounded sentence saying that the packet carried later wrapper-summary prose and that this prose should not be silently upgraded into copied source text, copied source metadata, route-level authenticity proof, or governing derivative proof.

## Keep copied-source text and wrapper-added summary prose separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **wrapper-added label** — filename, subject line, slide title, memo heading, or similar short later-added narrative (`601`);
7. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, cover notes, memo-body summaries, ticket descriptions, or similar later packet synopsis (`602`);
8. **carrier wrapper** — slide deck, PDF memo, chat export, saved page, web archive, issue ticket, or other transport context (`437`, `490`, `600`);
9. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two opposite mistakes:
- treating wrapper-added summary prose as if it were copied from the source route, or
- letting the wrapper summary become the governing packet member instead of first classifying the surviving detached derivative.

`602` exists so the archive can keep that summary prose **truthful but non-governing**.

## Minimal wrapper-summary note grammar

When wrapper-summary overread itself matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_summary_kind=<forwarding_comment|share_message|speaker_notes|cover_note|memo_body_summary|ticket_description|chat_intro|notes_page|mixed|unknown>; wrapper_summary_origin=<later_wrapper_added|quoted_source|mixed|unknown>; treat_wrapper_summary_as_source_text=<forbid>; treat_wrapper_summary_as_source_metadata=<forbid>; treat_wrapper_summary_as_governing_member=<forbid>; carrier_wrapper=<slide_deck|pdf_memo|chat_export|saved_page|web_archive|ticket|email_thread|shared_link_message|none>; cite_default=<head|fallback anchor>; use_602_when=<wrapper_summary_changed_routing_or_retelling>; promote_wrapper_summary=<no>; basis=<why the later summary needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this forwarding note / share message / speaker notes text was later wrapper narrative” without minting a new detached-derivative member or silently rewriting copied-source provenance.

## Typical uses

1. **Forwarding-comment overread**
   An email forwards a frame grab and a watch URL from the same route, but later readers start citing the forwarding paragraph as if it were copied source language.
2. **Share-message overread**
   A shared document or link carries an optional sender-written message, and later readers start treating that message as if it came from the official media route.
3. **Speaker-notes overread**
   A slide deck preserves a transcript excerpt or frame grab, but later readers start treating the notes-page synopsis as if it were the official route's own wording.
4. **Memo-body synopsis overread**
   A memo includes one governing same-route derivative, but the memo body retells it in stronger prose and later readers treat that prose as the governing proof.
5. **Mixed packet with argumentative summary paragraph**
   A packet really belongs under `600`, but a strong wrapper summary starts pushing reviewers toward `595`, `598`, or a new carrier-specific sibling even though the summary was later-added prose.

## When not to use this

Do **not** use `602` when:
- the decisive text was actually copied from the official route itself (`595`),
- the decisive label was actually copied source metadata (`598`),
- the decisive problem is still a short wrapper-added label (`601`),
- the decisive problem is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive problem is still print/save/offline/web-archive authority or portability (`437`, `490`),
- or the decisive problem is still cross-state composite assembly (`591`).

If deleting the wrapper-summary prose leaves an ordinary text derivative, metadata derivative, label problem, mixed packet, saved-page, or composite-assembly claim, use the narrower doc and omit `602`.
If deleting it would erase **why a later packet summary paragraph, forwarding note, share message, or speaker notes block changed the way the packet was being routed or retold**, `602` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet used a forwarding paragraph, share-dialog message, speaker notes block, cover-note summary, memo-body synopsis, or similar wrapper-added prose around same-route detached derivatives.
Tighten `595`, `598`, `600`, `601`, `591`, `437`, `490`, or `602` first.
Only add another numbered doc when repeated wrapper-summary mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-label note under `601`,
- plus one bounded wrapper-summary note under `602`.
