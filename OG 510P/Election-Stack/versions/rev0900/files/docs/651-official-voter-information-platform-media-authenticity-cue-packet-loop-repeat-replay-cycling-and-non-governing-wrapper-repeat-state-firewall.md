# 651 — Official voter-information platform media authenticity-cue packet loop repeat replay cycling and non-governing wrapper-repeat-state firewall

**Track:** Shared / Public surfaces

## What this is for

Use `651` when a later packet preserves or reenacts a **visible wrapper repeat-state layer** around same-route detached derivatives:
- a loop-on control or repeat icon,
- a repeat-one indicator,
- replay-after-end posture,
- continuous replay cycling,
- an embed-loop setting or loop-enabled player shell,
- or similar later packet foregrounding of same-item repetition.

Those repeat surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added repeat posture**, not automatic proof of:
- source-native repetition,
- official continuous rebroadcast,
- office-preferred replay posture,
- source-native chronology,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded repeat-state bridge.
YouTube says viewers can loop a video or a playlist on computer or mobile.
Vimeo says embedded videos can be configured with loop parameters, including `loop=1`, so the same item continues replaying in the embed rather than handing the viewer into a different object.
That is enough to keep a later visible loop/repeat layer separate from both successor-object posture and same-object chain control.
(xref: `youtube_loop_videos_playlists_help_page`; xref: `vimeo_autoplay_loop_embed_code_help_page`)

`651` exists so maintainers can say:
**this packet preserved a later loop / repeat / replay-cycling posture around same-route detached derivatives, and that posture mattered for how later readers interpreted the packet, but the repeat-state layer itself does not silently prove source-native repetition, official continuous rebroadcast, office-preferred replay posture, source-native chronology, or the packet's governing member.**

## Why this is distinct

`496` asks whether autoplay, end screens, cards, or other play-next surfaces became the **authority-boundary** problem on the public surface in the first place.

`551` asks whether playback actually moved into a **different object** through autoplay, queue progression, playlist-next mechanics, or another successor handoff.

`556` asks whether the **same current object** repeated after the endpoint while chain control and head-default citation still stayed with that same object.

`611` asks whether packet motion, build-order staging, autoplay, or reveal timing changed how preserved derivatives were experienced over time.

`649` asks whether the later wrapper foregrounded a *next-object* or successor layer rather than repetition of the same item.

`651` asks a different question:
**did a later packet add or preserve a visible repeat-state layer — loop-on control, repeat-one indicator, replay-after-end posture, continuous replay cycling, embed-loop setting, or similar — and did later readers start overreading that layer as if it proved source-native repetition, official continuous rebroadcast, office-preferred replay posture, source-native chronology, or the packet's governing member?**

If the real problem is autoplay / play-next as a voter-facing authority boundary, use `496`.
If the real problem is a completed cross-object handoff, use `551`.
If the real problem is same-object repeat retention in the chain itself, use `556`.
If the real problem is wrapper timing or auto-advance choreography, use `611`.
If the real problem is next-object successor posture, use `649`.
Use `651` only when the missing distinction is **wrapper repeat-state posture itself** around a later detached-derivative packet.

## Decision test

Use `651` when all three conditions hold:

1. later evidence preserves or reenacts a **visible repeat-state layer** around same-route detached derivatives — for example a loop-on control, repeat-one indicator, replay-after-end posture, continuous replay cycle, embed-loop setting, or similar same-item repetition foregrounding;
2. that layer is **later wrapper-added repeat posture**, not proof that the underlying source route itself officially repeated, officially rebroadcast continuously, or made the packet governing; and
3. later readers are drifting toward treating that layer as if it proved **source-native repetition, official continuous rebroadcast, office-preferred replay posture, source-native chronology, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly an authority-boundary problem, completed successor-handoff problem, same-object repeat-retention problem, wrapper-timing problem, or wrapper-successor-state problem with some visible loop posture around it, keep authority-boundary in `496`, keep completed handoffs in `551`, keep same-object repeat retention in `556`, keep motion/timing in `611`, keep successor posture in `649`, and add one bounded `651` repeat-state note only if the visible repeat layer itself changed the reading.

## Keep repeat state, repeat retention, successor state, and timing separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **authority-boundary / same-object versus cross-object class** — whether autoplay/play-next already became the decisive public-surface problem (`496`), whether the same object simply repeated (`556`), or whether playback actually moved into a different object (`551`);
5. **adjacent wrapper state** — whether the real drift is timing choreography or successor-state posture instead (`611`, `649`);
6. **carrier wrapper** — slide deck, PDF memo, browser shell, doc shell, saved page, ticket, or email thread (`437`, `490`, `600`);
7. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a visible loop icon, repeat-one badge, or replay-after-end posture as if it proved that the source itself officially repeated or was natively cyclical; or
- letting a later repeat-state overlay become evidence that the packet itself is governance-bearing rather than just a later repetition layer around one preserved derivative.

`651` exists so the archive can keep that later visible repeat-state layer **truthful but non-governing**.

## Minimal wrapper-repeat-state note grammar

When wrapper repeat state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_repeat_kind=<single_item_loop|playlist_loop|repeat_one|embed_loop|replay_after_end|mixed|unknown>; repeat_scope=<control_visible|repeat_one_active|loop_parameter_present|continuous_replay_posture|reached_end_then_restarted|unknown>; source_native_repetition_proved=<forbid>; official_continuous_rebroadcast_proved=<forbid>; office_preferred_replay_posture_proved=<forbid>; source_native_chronology_proved=<forbid>; governing_member_from_repeat_state=<forbid>; carrier_wrapper=<browser_shell|doc_shell|pdf_shell|review_shell|slide_deck|saved_page|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_651_when=<repeat_state_changed_reading>; promote_wrapper_repeat_state=<no>; basis=<why the later repeat layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried a visible loop / repeat / replay-cycling layer” without minting a new detached-derivative member or silently rewriting continuity, chronology, replay authority, or governance.

## Typical uses

1. **Loop-icon overread**
   A later packet shows a visible loop-on control or repeat icon around a preserved derivative and later readers start retelling the source as if the office itself officially repeated that item indefinitely.
2. **Repeat-one overread**
   A later packet foregrounds repeat-one posture and later readers start treating that loop state as if it proved source-native repetition or an office-preferred replay mode rather than a viewer-side or wrapper-side state.
3. **Embed-loop overread**
   A later packet preserves an embed configured to loop and later readers start treating that looping shell as if it were proof of official continuous rebroadcast rather than later wrapper configuration.
4. **Repeat-versus-successor split**
   A later packet preserves replay-after-end or continuous replay that mattered for interpretation, but there is no need to imply a successor object; keep `649` for next-object posture and use `651` only for the later repeat-state drift.

## When not to use this

Do **not** use `651` when:
- the decisive issue is still autoplay / play-next as a voter-facing authority boundary (`496`),
- the decisive issue is still a completed successor-object handoff (`551`),
- the decisive issue is still same-object repeat-retention in the chain itself (`556`),
- the decisive issue is still wrapper timing, build-order staging, or auto-advance choreography (`611`),
- the decisive issue is still next-object successor posture (`649`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible repeat layer leaves an ordinary autoplay-boundary, completed-handoff, same-object-repeat, timing, successor-state, mixed-packet, or cross-state problem, use the narrower doc and omit `651`.
If deleting it would erase **why a later repeat-state layer changed the way the packet was being read or retold**, `651` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried a loop-on control, repeat-one indicator, replay-after-end posture, continuous replay cycle, embed-loop setting, or similar visible repeat posture around same-route detached derivatives.
Tighten `496`, `551`, `556`, `600`, `611`, `649`, or `651` first.
Only add another numbered doc when repeated wrapper-repeat-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-repeat-state note under `651`.
