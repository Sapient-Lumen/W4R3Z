# 618 — Official voter-information platform media authenticity-cue packet version history, named versions, restore points, and non-governing wrapper-history-state firewall

**Track:** Shared / Public surfaces

This document covers a narrow packet-wrapper problem:
**later packets can preserve version-history panes, named-version labels, restore candidates, compare-against-older-version views, or similar visible history-state layers around same-route detached derivatives, and later readers can start mistaking that history posture for current source text, adopted source chronology, accepted source state, or the packet's governing member.**

## What this is for

Use `618` when a later packet preserves or reenacts a **history-state layer** around same-route detached derivatives:
- version-history sidebars,
- named-version labels,
- restore-point lists,
- prior-version compare panes,
- current-versus-older-version split views,
- signed-version comparisons,
- or similar visible file-history posture.

Those history states are real packet facts and should be preserved honestly.
But they are still **later wrapper-added history posture**, not automatic proof of:
- current source wording,
- current source chronology,
- current source approval,
- which older state was officially restored,
- or the packet's governing member.

`618` exists so maintainers can say:
**this packet preserved a later version-history layer around a same-route detached derivative, and that layer mattered for how later readers interpreted the packet, but the history layer itself does not govern the packet and does not silently rewrite source provenance or current control.**

## Why this is distinct

`617` asks whether later packets preserved visible **revision proposals** — tracked changes, suggestions, redlines, replace-text notes, or similar in-place edit posture.

`616` asks whether later packets preserved **review discourse** — comment threads, replies, task-like notes, or similar attached discussion.

`605` asks whether later packets rearranged the packet's own slide/page/section order.

`595` and `598` ask whether the decisive surviving artifact is still copied source text or copied source metadata.

`618` asks a different question:
**did a later packet add or preserve a visible version-history layer — named versions, restore candidates, previous-version lists, or compare-old-vs-new posture — and did later readers start overreading that layer as if it proved current source text, accepted chronology, restored source state, or the packet's governing member?**

If the real problem is only in-place revision proposal posture, use `617`.
If the real problem is only review conversation, use `616`.
If the real problem is only packet sequence, use `605`.
If the real problem is still copied source text or metadata, use `595` or `598`.
Use `618` only when the missing distinction is **history-state posture itself**.

## Decision test

Use `618` when all three conditions hold:

1. later evidence preserves or reenacts a **visible version-history layer** around same-route detached derivatives — for example a version-history sidebar, named-version label, restore-point list, compare-old-vs-new view, or similar prior-version posture;
2. that layer is **later wrapper-added history state**, not the source route's already-established current head or already-adopted current wording; and
3. later readers are drifting toward treating that layer as if it proved **current source text, source chronology, restored source state, accepted office change, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly copied source text or copied source metadata with some version-history posture around it, keep the detached derivative in `595–600`, keep any review-discourse fact in `616`, keep any revision-proposal fact in `617`, and add one bounded `618` history-state note.

## Keep source-derived content and wrapper-added history state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `369`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **source-derived text** — transcript/caption/OCR or other copied route text (`595`);
5. **source-derived metadata** — labels copied from the official route itself (`598`);
6. **wrapper-added summary prose** — forwarding comments, share messages, speaker notes, memo-body summaries, or similar longer later packet narrative (`602`);
7. **wrapper-added ordering** — later slide/page/section sequence inside the packet (`605`);
8. **wrapper-added review discourse** — comment-thread bodies, replies, task assignments, or similar later attached discussion (`616`);
9. **wrapper-added revision state** — suggestions, tracked changes, redlines, replace-text proposals, insert-text proposals, deletion proposals, or accept/reject preview posture (`617`);
10. **wrapper-added history state** — version-history lists, named-version labels, restore candidates, previous-version panes, compare-old-vs-new views, signed-version comparisons, or similar prior-version posture (`618`);
11. **carrier wrapper** — slide deck, PDF memo, doc history pane, saved page, web archive, issue ticket, or other transport context (`490`, `600`);
12. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating one prior version or restore candidate as if it were automatically the current source state, or
- letting the existence of a history list or compare pane become evidence that the packet itself governs the source route.

`618` exists so the archive can keep that later visible history layer **truthful but non-governing**.

## Minimal wrapper-history-state note grammar

When wrapper history state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_history_kind=<version_history|named_version|restore_point_list|prior_version_compare|signed_version_compare|mixed|unknown>; history_anchor_relation=<whole_member|member_region|slide|page|object|text_range|mixed|unknown>; wrapper_history_origin=<later_wrapper_added|editor_history_pane|storage_history_pane|imported_history_capture|mixed|unknown>; current_state_proved=<forbid>; restored_state_proved=<forbid>; treat_history_as_source_chronology=<forbid>; treat_history_as_governing_member=<forbid>; carrier_wrapper=<doc_history_pane|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_618_when=<history_state_changed_reading>; promote_wrapper_history_state=<no>; basis=<why the later visible history layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible version-history posture” without minting a new detached-derivative member or silently rewriting current control, accepted chronology, or governance.

## Typical uses

1. **Named-version overread**
   A later packet shows a named version and later readers start retelling that label as if it were the current official answer rather than one recorded historical state.
2. **Restore-list overread**
   A later packet shows a version-history list or restore candidate and later readers start narrating that candidate as if the source had already been restored to it.
3. **Compare-old-vs-new overread**
   A later packet shows an older/newer comparison view and later readers start treating the compared older version as if it were the packet's governing member or current source wording.
4. **History-pane chronology overread**
   A later packet captures a prior-version pane and later readers start narrating its visible order or labels as if that alone proved authoritative publication chronology.
5. **Signed-version comparison overread**
   A later packet compares a signed version with the current file and later readers start treating the compared historical state as if it displaced the current head.

## When not to use this

Do **not** use `618` when:
- the decisive issue is still packet synopsis or forwarding summary prose (`602`),
- the decisive issue is still wrapper ordering or sequence (`605`),
- the decisive issue is still wrapper-added review-thread discourse (`616`),
- the decisive issue is still wrapper-added revision-state posture (`617`),
- the decisive issue is still copied source text (`595`),
- the decisive issue is still copied source metadata (`598`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive problem is still print/save/offline/web-archive authority or portability (`490`),
- or the decisive problem is still cross-state composite assembly (`591`).

If deleting the visible history layer leaves an ordinary review-discourse problem, revision-state problem, ordering problem, or mixed-packet problem, use the narrower doc and omit `618`.
If deleting it would erase **why a later version-history / restore-state / prior-version layer changed the way the packet was being read or retold**, `618` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried version-history panes, named versions, restore candidates, prior-version comparisons, or similar history posture.
Tighten `605`, `616`, `617`, `600`, or `618` first.
Only add another numbered doc when repeated history-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-history-state note under `618`.
