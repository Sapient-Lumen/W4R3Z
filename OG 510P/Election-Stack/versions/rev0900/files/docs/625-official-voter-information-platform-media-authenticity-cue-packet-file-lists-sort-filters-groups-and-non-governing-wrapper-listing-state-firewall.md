## What this is for

Use `625` when a later packet preserves or reenacts a **visible wrapper listing-state layer** around same-route detached derivatives:
- a file list or saved library view,
- a sort key or sort direction,
- filter chips, filter panes, or narrowed subsets,
- grouped headers or grouped collapsible sections,
- visible or hidden columns,
- list / compact-list / tile-like view choices,
- or similar later packet collection posture.

Those listing surfaces are real packet facts and should be preserved honestly.
But they are still **later wrapper-added listing posture**, not automatic proof of:
- official chronology,
- official completeness,
- official categorization,
- canonical membership,
- or the packet's governing member.

Current primary-source guidance is already enough to justify one bounded listing-state bridge.
Google Drive documents list/grid layout changes, list-column sorting, and filter chips that narrow file lists.
Microsoft documents OneDrive file sorting and filtered browse views, and SharePoint documents saved views whose sort, filter, grouping, and shown/hidden columns change display rather than underlying content.
Adobe documents cloud-file search and sorting by name, modified date, or size.
That is enough for one bounded firewall here.
(xref: `google_drive_view_reorder_files_folders_help_page`; xref: `google_drive_search_for_files_help_page`; xref: `microsoft_onedrive_sort_rename_move_files_help_page`; xref: `microsoft_sharepoint_create_change_delete_view_list_library_help_page`; xref: `adobe_acrobat_sort_search_files_help_page`)

`625` exists so maintainers can say:
**this packet preserved a later file-list or library-view layer around same-route detached derivatives, and that layer mattered for how later readers interpreted the packet, but the listing layer itself does not govern the packet and does not silently prove chronology, completeness, categorization, or canonical membership.**

## Why this is distinct

`614` asks whether later evidence preserved **query state** — search terms, find-hit lists, highlighted matches, or result panes.

`623` asks whether a later packet preserved **organization posture** — starred state, recent-file listings, pinned recents, shortcut placement, favorites, or moved-location cues.

`624` asks whether a later packet preserved **information posture** — owner/location/size/type fields, info cards, details panes, or properties dialogs.

`625` asks a different question:
**did a later packet add or preserve a visible file-list or library-view layer — sort order, filters, group headers, shown/hidden columns, saved view name, or list-vs-tile mode — and did later readers start overreading that layer as if it proved official chronology, official completeness, official categorization, canonical membership, or the packet's governing member?**

If the real problem is query-conditioned reading, use `614`.
If the real problem is starred/recent/shortcut/favorite posture, use `623`.
If the real problem is visible properties or details panes, use `624`.
Use `625` only when the missing distinction is **wrapper listing-state posture itself**.

## Decision test

Use `625` when all three conditions hold:

1. later evidence preserves or reenacts a **visible file-list or library-view layer** around same-route detached derivatives — for example a sort order, filter subset, group heading, column set, saved view, or layout mode;
2. that layer is **later wrapper-added listing state**, not proof that the underlying source route itself published, endorsed, or canonically fixed the same order, subset, grouping, or classification; and
3. later readers are drifting toward treating that layer as if it proved **official chronology, official completeness, official categorization, canonical membership, or the governing member**.

If any condition fails, keep the packet under the narrower doc that already owns the real problem.
If the surviving packet is still mainly a query-state problem, an organization-state problem, or an information-state problem with some list-view posture around it, keep query state in `614`, keep organization posture in `623`, keep information posture in `624`, and add one bounded `625` listing-state note only if the file-list view itself changed the reading.

## Keep query state, organization state, information state, and listing state separate

At minimum, keep these layers separate:
1. **current office control** — the current written/help lane and current media head (`194`, `529`, `530`);
2. **surviving detached derivative** — which `595–599` member, if any, the packet actually preserved;
3. **family routing** — whether the packet needed `600` because no single detached derivative dominated;
4. **wrapper-added query state** — search terms, filter chips inside search, find-hit panes, highlighted matches, or result ranking (`614`);
5. **wrapper-added access state** — link scopes, roles, or request-access posture (`619`);
6. **wrapper-added event state** — notifications or activity posture (`620`);
7. **wrapper-added lifecycle state** — Trash/Recycling/delete-restore posture (`621`);
8. **wrapper-added sync state** — offline/local/pending/conflict posture (`622`);
9. **wrapper-added organization state** — starred, recent, pinned, shortcut, favorite, or moved-location posture (`623`);
10. **wrapper-added information state** — owner, location, size, type, created, modified, details-pane, info-card, or properties-dialog posture (`624`);
11. **wrapper-added listing state** — sort keys, sort direction, filters, groupings, visible columns, saved views, or list/tile modes (`625`);
12. **carrier wrapper** — slide deck, PDF memo, doc shell, saved page, web archive, issue ticket, or other transport context (`490`, `600`);
13. **assembly state** — whether later materials also fused several observations into one stronger-looking posture (`591`).

That separation matters because later packets can otherwise make two different mistakes:
- treating a filtered or sorted list as if it were the office's own authoritative chronology, complete bundle, or official category boundary, or
- letting a file-manager or document-library view become evidence that the packet itself governs what belongs in the set.

`625` exists so the archive can keep that later visible listing layer **truthful but non-governing**.

## Minimal wrapper-listing-state note grammar

When wrapper listing state matters, reviewers SHOULD prefer one compact line in this shape:

`head=<current tuple|none>; governing_member=<595|596|597|598|599|600|none>; wrapper_listing_kind=<sort|filter|group|visible_columns|saved_view|list_mode|mixed|unknown>; listing_fields_seen=<sort_key|sort_direction|filter_chip|filter_value|group_key|visible_column|hidden_column|view_name|layout_mode|mixed|unknown>; listing_anchor_relation=<collection|whole_member|member_link|attachment|slide|page|object|message|mixed|unknown>; wrapper_listing_origin=<later_wrapper_added|file_manager_ui|document_library_ui|desktop_client|web_app_ui|mixed|unknown>; chronology_proved=<forbid>; completeness_proved=<forbid>; official_categorization_proved=<forbid>; canonical_membership_proved=<forbid>; treat_listing_state_as_governing_member=<forbid>; carrier_wrapper=<doc_shell|file_manager|document_library|desktop_client|slide_deck|pdf_memo|saved_page|web_archive|ticket|email_thread|none>; cite_default=<head|fallback anchor>; use_625_when=<listing_state_changed_reading>; promote_wrapper_listing_state=<no>; basis=<why the later file-list or library-view layer needed one bounded note>`

This is a note contract, not a new schema.
It exists so packets and summaries can say “this later packet also carried visible list-view posture” without minting a new detached-derivative member or silently rewriting chronology, scope, category, or governance.

## Typical uses

1. **Sort-order overread**
   A later packet sorts by Modified and later readers start retelling that wrapper ordering as if it proved official chronology or newest-valid source state.
2. **Filter-overread**
   A later packet shows only a filtered subset and later readers start retelling that narrowed view as if it were the complete official set.
3. **Group-header overread**
   A later packet groups items by owner, type, or another column and later readers start retelling that wrapper grouping as if it were the office's own published category boundary.
4. **Visible-columns overread**
   A later packet hides some columns and shows others, and later readers start treating the shown fields as if they were the whole authoritative metadata contract.
5. **Saved-view overread**
   A later packet preserves one named view or list/tile mode and later readers start treating that convenience view as if it were the governing canonical presentation.

## When not to use this

Do **not** use `625` when:
- the decisive issue is still query state (`614`),
- the decisive issue is still organization state (`623`),
- the decisive issue is still information state (`624`),
- the decisive issue is still access, event, lifecycle, or sync posture (`619–622`),
- the decisive issue is still a mixed detached-derivative packet with no dominant member (`600`),
- the decisive issue is still print/save/offline/web-archive authority or portability (`490`),
- or the decisive issue is still cross-state composite assembly (`591`).

If deleting the visible file-list view leaves an ordinary query, organization, or information problem, use the narrower doc and omit `625`.
If deleting it would erase **why a later sort/filter/group/columns view changed the way the packet was being read or retold**, `625` is probably right.

## Promotion rule

Future media additions should usually **not** be promoted just because a later packet carried a file list, view name, sort order, filter subset, grouped header, visible-column set, or list/tile mode.
Tighten `614`, `623–625`, or `600` first.
Only add another numbered doc when repeated wrapper-listing-state mistakes still cannot be expressed as:
- one governing `595–599` member,
- or a mixed-packet routing note under `600`,
- plus one bounded wrapper-listing-state note under `625`.
