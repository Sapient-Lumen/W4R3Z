## 3. What changed in executable code

### 3.1 The ordinary friendship surface

The runtime root now publishes:

```text
friendship.help
friend-events
friend-events.previous             only after rotation
requests/<PUBLIC_KEY>/accept        private mode-0600 FIFO
requests/<PUBLIC_KEY>/reject        private mode-0600 FIFO
peers/<PUBLIC_KEY>/remove           private mode-0600 FIFO
```

Request and peer directories are named by canonical uppercase 32-byte Tox public-key hex. A writer
must place exactly one matching lowercase word and LF into the matching lane:

```text
accept\n
reject\n
remove\n
```

Case changes, spaces, suffixes, wrong-lane words, partial records, oversize records, regular-file
substitution, symlink substitution, foreign ownership, permissive modes, and inode replacement are
rejected or repaired according to the existing hardened FIFO service contract.

The service queries each FIFO's actual `_PC_PIPE_BUF` and requires the maximum complete record to fit
an atomic write. An abandoned partial record expires rather than joining a later writer. FIFO write
success remains kernel evidence only; semantic disposition appears through structured control or
`friend-events`.

### 3.2 Incoming requests remain honest live projections

The c-toxcore request callback gives IoTox a sender public key and request-message bytes. It does not
create a durable provider request object. rev0014 therefore retains one bounded in-memory request
record per key and transactionally publishes one complete request directory.

Acceptance requires that the same public key still exist in the live IoTox inbox. It then uses the
provider's no-request add operation on the exclusive toxcore owner thread. Rejection removes only the
IoTox callback projection. It does not add and immediately delete a temporary friend, and it does not
claim the remote sender received a refusal.

Restart discards pending request projections. This is deliberate. Durable request history, blocking,
replay, privacy, signature, retention, and operator-attention policy require a separate product
decision rather than accidental persistence of `/run` state.

### 3.3 Destructive transport mutation is bound to public key

The exact consumed c-toxcore ABI now includes `tox_friend_by_public_key`. Runtime-loaded, official-
header-linked, and exact-mock providers expose the same function type and error enum.

The transport adapter adds:

```text
ToxTransport::remove_friend_by_public_key(32-byte key)
```

Inside one queued operation owned by the single toxcore thread, the adapter performs public-key
lookup and deletion. Lookup and delete are not two independently queued operations.

That distinction is security-relevant because c-toxcore documents friend numbers as local, unstable,
and reusable. A gap left by deleting friend zero may be assigned to another key. A delayed numeric
delete could therefore remove the wrong peer. The key-bound one-turn operation either deletes the
current friend for the requested key or fails without retargeting.

The exact mock deliberately fills the lowest available numeric gap. Tests delete one peer, add a
different peer into the reused slot, remove the replacement by public key, require the removal event
to carry the replacement key, and reject a duplicate removal.

The CLI keeps numeric friend selectors as a compatibility convenience, but resolves the selected
current peer to its public key before sending local protocol operation 30. Numeric friend numbers are
lifecycle evidence only.

### 3.4 Friendship remains separate from authority

Every request arrival and local accept, reject, or remove decision records that the IoTox
authorization ledger is unchanged.

The semantic layers remain:

```text
Tox friendship             transport recognition and reachability
IoTox session              negotiated machine-protocol compatibility
stable-principal proof     transcript-bound application identity
signed authority ledger    roles, capabilities, epochs, and revocation
```

Acceptance does not grant ownership, roles, capabilities, firmware authority, or actuation.
Removal does not revoke a stable principal. Rejection does not block a stable principal. A future
compound revoke-and-remove ceremony must have an explicit name, commit order, failure state, and
recovery contract; silent coupling remains prohibited.

### 3.5 One product, reused implementation seams

No second daemon or product binary was introduced. The same `iotox` executable remains both agent and
operator client.

The existing generalized FIFO service is instantiated over two bounded directory sets:

```text
established public-key peer directories
live public-key request directories
```

FIFO workers own path validation and record framing only. They converge on typed Agent methods; they
do not call toxcore or mutate authority directly. The structured Unix `SOCK_SEQPACKET` control path,
ordinary files, and provider callbacks therefore share one implementation of friendship semantics.

Local control protocol major version remains 1 and minor version advances to 15. Operation 30 is
frozen as the 32-byte public-key removal operation. Older numeric removal remains an internal
compatibility operation but is not the ordinary destructive selector.

### 3.6 Bounded lifecycle evidence

`friend-events` is a private mode-0600, bounded, rotating operational journal. It can record:

```text
request callback observed
outgoing request accepted or rejected locally
request accept/reject admitted or rejected
provider friend addition/removal observed
public key and current friend number where available
authority-unchanged boundary
```

Request text is rendered as escaped untrusted bytes. The journal is unsigned, not rollback-resistant,
not synchronously fsync-committed per record, and may disappear with the runtime tree. Its sequence
is process-local and may repeat after restart. It is useful operator evidence, not durable audit or
remote acknowledgement.

## 5. Defects found and repaired while constructing rev0014

### 5.1 Stale objects concealed the revision boundary

An inherited build directory appeared healthy until a clean rebuild exposed a process fixture still
expecting revision 13 while current source emitted revision 14. The fixture and mock-node assertions
were corrected. The final matrix always removes its configuration directories before compilation.

Lesson: retained binaries and build timestamps are evidence for the source that produced them, not
for the source currently beside them.

### 5.2 Shared acceptance helper used the wrong ownership type

The first strict build found a vector/span mismatch at the new common acceptance boundary. The helper
contract was corrected instead of weakening warnings or adding an implicit lifetime assumption.

### 5.3 Public-key removal was projected before it was complete

The inherited interrupted draft had begun local protocol operation 30 and some filesystem objects,
but not every semantic handler was connected. rev0014 completed the exact ABI, transport method,
Agent dispatch, CLI compatibility path, projection cleanup, event evidence, mock behavior, and tests
before packaging.

### 5.4 Numeric deletion remained vulnerable to reuse

Resolving a key outside the owner thread and queuing a later numeric delete would not satisfy the
c-toxcore lifetime contract. Lookup and delete were moved into one serialized provider operation.
The exact mock's gap-reuse behavior turned that source warning into executable regression evidence.

### 5.5 One request test reused an exhausted deadline

A request-count assertion reused a deadline already spent waiting for earlier work. Slow scheduling
could therefore fail the later assertion without allowing its own interval. The assertion now owns a
fresh deadline. Product timeouts were not relaxed.

### 5.6 Journal follow assumed a frozen file

The process fixture read `friend-events` and then started bounded follow while a required removal
event could still append. Whole-file equality was invalid. The fixture now requires the prior bytes
as a prefix and permits later committed lifecycle evidence.

### 5.7 FIFO admission was mistaken for request-decision completion

A repeated one-binary run exposed a fixture-only ordering error. The writer's `write(2)` to a request
`reject` FIFO returned before the Agent had withdrawn the live request projection and appended the
matching lifecycle record. That is permitted: FIFO write success is kernel admission, not a semantic
receipt. The fixture now polls the authoritative structured request projection and the exact
lifecycle evidence while requiring the daemon to remain alive. No product delay or sleep-based
ordering promise was added.

### 5.8 Peer projection withdrawal was mistaken for journal completion

A second repeated run observed the established peer directory disappear before the adjacent
best-effort `friend-events` append became readable. Runtime projection withdrawal and bounded journal
append are separate Agent effects, not one filesystem transaction. The fixture now waits for both
observations independently. The journal was not promoted into a commit log, and disappearance of a
path was not promoted into remote acknowledgement or durable audit. The clean rebuilt fixture then
completed ten sequential repetitions without reproducing the false failure.

### 5.9 Concurrent stress runs could corrupt evidence

The stress tool originally had no exclusive lock. Two invocations could truncate and append the same
file. The tool now fails closed under contention with status 75. A later final-evidence run also
exposed a legacy writer that had begun outside the new lock contract: it truncated the destination at
run 67 even though the current producer completed and returned zero. That transcript was rejected.
The producer now writes a private same-directory stage, validates exact ordered run lines and one
terminal summary, and atomically renames only a complete transcript. Retention independently repeats
those checks. No damaged or interleaved log is retained.

### 5.10 RecallRoot smoke could expose generated sovereign material

The original CTest registration invoked `iotox recall-generate` directly. A normal non-verbose run
did not display passing output, but verbose CTest, failure diagnostics, wrappers, or future logging
could retain a generated permanent owner phrase. The test now runs through
`cmake/CheckRecallGenerate.cmake`, which validates the exact record inside the child process and
emits only a suppression status. The phrase is never copied into the retained evidence set.

## 10. Next executable direction

The most ratox-faithful immediate next step is one ordinary outgoing request entrance at the runtime
root. It must converge on the already typed operation carrying a complete 38-byte Tox address and a
1..921-byte message.

A candidate line grammar is:

```text
<76-HEX-TOX-ADDRESS><TAB><UTF-8-MESSAGE><LF>
```

That grammar is not yet frozen. Before implementation, decide whether its TAB/LF exclusions are an
acceptable cost of plain Unix writes. Do not add shell quoting, escaping, globbing, or a hidden
language. Whatever the surface becomes, it must preserve:

```text
one complete atomic bounded record
provider checksum/nospam validation
no hidden retry or offline queue claim
semantic disposition in friend-events
no authority grant
same typed Agent operation as the structured client
```

After that, add one useful harmless read, then cross the official source-linked build and two genuine
native Tox peers. Mutorr, direct Tor/I2P transport, routed Tox, OTA, and physical effects remain later
work.
